工程实践 · Q4

如何处理 Agent 的长对话场景(> 10 轮)?

⭐⭐⭐⭐ #Agent#长对话#Memory
先说人话:这道题问的是:对话超过 10 轮后,历史记录既塞不进、也塞不起模型的上下文,你怎么让 Agent 依然记得前面聊了什么。面试官爱考,因为张口就答「换个 128K 长上下文模型」的人没算过成本账,真做过的人开口是分层、水位线、一致性验证。答错暴露的是:没把记忆当成一套存储系统来设计。
30秒电梯稿

"把记忆当一套冷热分层存储系统来设计,而不是死命往上下文里塞:最近 4~6 轮保原文(热数据/工作记忆)→ 出窗口的轮次合并进滚动摘要(温数据,定期用原文重写防漂移)→ 用户目标、约束、已确认事实槽位化抽取成结构化 Memory(永不丢的元数据)→ 全量历史原文进向量库按需检索(冷归档)。一句话:重要的留下、啰嗦的压掉、需要的随时找得回来。触发上用 token 预算水位线,压缩后跑多轮一致性测试防丢信息。"

通俗类比

先搞懂「上下文窗口」为什么是硬约束(用内存想):LLM 是无状态的(stateless)——它自己不记得任何历史,所谓「记得」,是服务端每轮把之前所有对话原文重新拼进请求、整个再发一遍;单次请求能装下的 token 上限,就是上下文窗口。类比:上下文像内存——快、小、按量计费;历史像磁盘——大,但每次都得显式加载。要命的是「每轮重发」:第 30 轮对话时,开场白已经被原样搬运了 30 次,对话越长,重复搬运的废 token 越多——成本不是线性涨,是越滚越快。

分层压缩,就是冷热数据分层存储:最近几轮原文是热数据,放 NVMe,一字不动;出窗口的旧轮次压成滚动摘要,温数据;全量原文归档进向量库,要用才回捞;目标、预算、已确认事实这类关键信息抽成槽位,它是元数据目录——体积极小、永远在线、丢失零容忍。给外行的版本是「开会纪要」:最近半小时记得原话,上午只剩要点,关键结论写在白板上人人可见,要翻旧账就去调录音。哪里像:都按访问频率和重要性分配容量,常读且重要的给最贵的位置,都是「容量有限所以必须分级」。哪里不像:存储分层搬字节是无损的,搬过去一个 bit 不少;摘要却是有损压缩,一次写错细节就永远丢了——所以要有槽位层兜底,要拿一致性测试当「恢复演练」,压缩质量必须专门验证,不能像搬磁盘那样放心。

详细拆解

第 0 步:先算账(不算这笔账,压缩就是拍脑袋)

为什么 10 轮是道坎?不是模型「记不住 10 轮」,而是三个硬账:

  • 成本账:LLM 无状态,每轮重发全部历史。一场 30 轮对话按平均每轮 700 token 算,第 30 轮单次请求就是 2 万+ token,30 轮累计发送约 33 万 token——账单随轮数滚雪球。
  • 塞得进 ≠ 记得住:超长上下文里中段信息利用率显著下降,即 Lost in the Middle 现象——50 轮原文全塞进去,模型大概率「看过了但没用上」。
  • Agent 场景更凶:人聊一轮几十 token,Agent 一轮工具调用(查表、拉日志、贴代码)动辄几千 token,几轮就能吃掉半个窗口。
不压缩(每轮把全部历史原文重新发给模型):
  第  4 轮请求   历史原文 ≈  2,800 token
  第 10 轮请求   历史原文 ≈  7,000 token   ← 撞上水位线(10K 窗口的 70%)
  第 15 轮请求   历史原文 ≈ 10,500 token   ← 超出窗口上限,请求直接报错
  第 30 轮请求   历史原文 ≈ 21,000 token
  30 轮累计发送 ≈ 33 万 token——开场白被原样搬运了 30 遍

分层压缩后(每次请求的组装量基本恒定):
  第 10 轮: 近 6 轮原文 3,000 + 摘要 300 + 槽位 200 + 系统 200 ≈ 3,700 token
  第 30 轮: 近 6 轮原文 3,000 + 摘要 350 + 槽位 250 + 系统 200 ≈ 3,800 token
            ↑ 历史再长,组装量也近似恒定——成本从滚雪球变成一条平线

1. 上下文组装的分层结构

每次请求,按下图的顺序把各层拼成一条上下文发给模型——各层预算固定,内容按「新进旧出」流动:旧原文出窗口进摘要,新消息从底部进来:

把六层映射到你熟悉的存储侧,每层都有固定预算,组装上下文就像管理一个容量固定的资源池:

层装什么存储侧对应物token 预算丢失容忍度
System Prompt角色 + 规则固化的系统配置,变更走评审~200零容忍
槽位区目标 · 预算 · 约束 · 已确认事实元数据目录:体积极小、永远在线~200零容忍,永不淘汰
历史摘要出窗口轮次的合并要点温数据:压缩后常驻在线~300有损,须防漂移
近期原文最近 4~6 轮逐字热数据:高频访问、原样保留~3,000窗口内不丢
检索补充向量库按需捞回的历史片段冷归档:平时不加载,要用才回捞按需 0~1,500原文不丢,怕「想不起来」
当前消息用户最新输入新写入的数据块变长—

排版的顺序也有讲究:开头和结尾是模型注意力的高利用率区(lost in the middle 的另一面),所以最关键的槽位放最前、用户最新消息放最后,中间才轮到摘要和近期原文——关键信息永远站在「黄金位置」。

2. 各层实现要点

  • 滑动窗口:保留最近 4~6 轮原文。两个坑:① 轮不均——人类一轮几十 token,Agent 一轮工具输出几千 token,成熟实现按 token 而非轮数滑窗;② 窗口边界是信息丢失高发区,最危险的是「只出现在边界外一轮、摘要又没接住」的信息——判断"哪些信息只在这几轮里"很关键。切分时对齐完整任务边界,不在任务中间切,像日志轮转不能把一个事务截成两半;任务要跨窗口时,先把结论写进槽位,再让原文滑出去。
  • 滚动摘要:出窗口的轮次合并进旧摘要,生成新摘要。最大的坑是漂移——摘要套摘要,细节逐层蒸发,像无限增量备份链:每层依赖上一层,链条越长误差越累积。对策:① 每 5~10 轮做一次「全量重写」,用原始对话 + 旧摘要重新生成(而非摘要的摘要),等价于增量链跑久了做一次全量重同步;② 摘要 Prompt 明确保留"数字、日期、决定、待办、用户给过的明确约束",并设 ~300 token 上限——超限说明压不动了,该按话题拆分。
滚动摘要的日常更新(增量,快但会累积失真):
  出窗口的第 7 轮原文 ──合并──→ 旧摘要 v3 ──LLM 重写──→ 新摘要 v4
                                  (摘要套摘要,细节逐层蒸发 = "漂移")

定期全量重写(每 5~10 轮一次,把失真清零):
  第 1~16 轮【原始对话】 + 旧摘要 v4 ──LLM 重写──→ 全新摘要 v5
  ↑ 原文一直躺在归档里没删——这就是"增量链再长,全量备份永远有底"的意思
  • 槽位抽取:异步任务从对话里抽数据结构(目标、约束、已完成步骤、关键实体)。这是永不丢失的一层,也是最便宜的一层——几百 token 就能存下整场对话的骨架,像元数据目录以极小体积索引全库。槽位要带时间戳和置信度:低置信度的抽取不直接覆盖旧值,先标记待确认;冲突仲裁时这一层说了算(见追问)。
  • 按需检索:全量对话(原文)按轮次/话题边界做 chunk、算 Embedding 入向量库,当前话题相关时向量检索捞回 top-k 片段——专治"你把我们 20 轮之前讨论的那个方案改成 B 版"这类回指:原文没删,只是搬进了归档,靠索引找回来,而不是从头倒带。注意 chunk 别按固定字数硬切,一句话劈成两半,向量基本就废了。

3. 触发时机与工程化

  • 水位线策略:上下文用量 > 70% 触发压缩,给生成留余量,别等到爆。为什么留 30%?和磁盘水位线同一个道理——不能等写满才动手:工具输出不可预测,单轮可能暴涨几千 token,请求跑到一半爆窗是直接失败,比慢更糟。
  • 压缩是异步的:压缩进行中不阻塞当前回复,压缩任务不在回复的关键路径上;压缩失败要有兜底——下一轮重试,期间降级用「应急粗摘要」(只保最近决定 + 槽位)顶住。
  • 多任务对话(用户中途换话题):按话题分段,各自摘要,互不污染——像按卷分桶存储,话题 A 的预算别混进话题 B;用户切回旧话题时,用对应分段的摘要 + 检索恢复上下文。

4. 防丢信息的验证(压缩不验证,等于没压缩)

  • 长对话测试集:30~50 轮的脚本对话,在末尾专门问开头提过的细节(预算数字、日期、约束),比对不压缩 vs 压缩的回答一致率——这是衡量压缩质量的硬指标。逻辑同备份:不演练恢复的备份等于没有备份,不做一致性测试的压缩等于没验证过压缩。
  • 线上监控:盯"用户重复告知率"——用户把说过的事再说一遍,就是记忆丢了,这是主诉级指标,等价于线上监控恢复失败事件;再配一个"回指命中率"(检索层能否捞回 N 轮前的实体)。能讲出这两个指标,面试官就知道你真上过线。
面试官追问
Q:现在长上下文模型都能塞 128K 了,还需要压缩吗?
人话:需要。塞得下不等于用得起,更不等于记得住——大窗口只解决"放不放得下",没解决"花不花得起、找不找得到"。类比:给你一台超大容量存储,你也不会把十年前的原始日志全量挂到生产路径上天天全读一遍;容量再大,热温冷分层该做还是得做。技术:① 成本与延迟随 token 线性涨,30 轮不压缩等于每轮都重发几万 token;② lost in the middle:超长上下文中段利用率显著下降,塞进去了模型未必用;③ Agent 的工具输出膨胀极快,几轮就吃掉半个窗口;④ 高 QPS 多会话并发下,KV Cache 的显存成本还会被成倍放大。压缩+检索是长期方案,大窗口只是让"近期原文层"可以留得更多。
Q:摘要和槽位信息打架(摘要说预算 5 万,槽位记的是 3 万)?
人话:听槽位的。槽位是台账,摘要只是回忆——回忆走样很正常,台账不能跟着错。类比:像备份系统的元数据目录和某份历史巡检报告打架:以 catalog 为准,再回头修报告,而不是让目录迁就报告。技术:① 槽位是唯一可信源:结构化、带时间戳、每次更新都有明确写入动作,冲突时取时间戳最新的槽位值;② 触发修复——冲突说明对应段落的摘要失真了,从归档捞回该段原文重写;③ 低置信度的槽位抽取不直接覆盖旧值,标记待确认,避免把对的改错;④ 把"槽位-摘要冲突率"做成监控指标,持续偏高说明抽取或摘要链路有病。
Q:Agent 的工具输出动辄几千 token(查表、拉日志、贴代码),几轮就吃掉半个窗口,这部分怎么处理?
人话:工具输出是长对话里膨胀最快的东西,必须单独治理,不能和人机对话的原文享受同一待遇。类比:像备份系统里的大文件卷不进日常增量链——单独全量加去重归档,主链路只留一个指针。技术:① 工具输出当场摘要:只把"结论 + 关键数字"留在对话层,原文落到外部存储并留 ID,后续轮次要用按 ID 取回;② 给每个工具输出设 token 上限,超限就截断,并提示模型改用分页/过滤式查询;③ 只有用户可见的最终结论进滑动窗口,中间过程全部走归档;④ 与水位线联动,防止单轮暴涨直接击穿窗口。
Q:把全量历史存向量库按需检索,这不就是 RAG 吗?跟检索外部文档有什么区别?
人话:骨架确实一样——都是向量检索后把片段拼回上下文;但检索对象从"外部资料"变成了"你自己的对话",坑完全不同。类比:查公共档案馆资料 vs 查自己项目的变更记录:后者有时间线、有指代("上面说的那个方案"),查的时候必须知道"何时说的、哪个版本"。技术:① chunk 按轮次和话题边界切,不按固定字数硬切;② 检索前要做指代改写:用槽位 + 当前话语把"那个方案"解析成具体实体再算向量,否则检索根本准不了;③ 捞回的片段要带轮次/时间标注,防止模型把 20 轮前的旧方案当成最新决定;④ 对话记忆对一致性的要求比文档检索更高,常与摘要层互相校验。
术语卡
上下文窗口:模型单次请求能读入的 token 上限——类比内存:装不下直接报错,装得下也按量计费。
无状态(stateless):LLM 自己不记得任何历史,「记得」是每轮把全部历史重发一遍换来的——长对话成本滚雪球的根源。
Lost in the Middle:长上下文中段信息利用率显著下降——塞得进窗口,不等于模型用得上。
槽位(slot):预定义的关键信息字段,把散落对话里的目标/约束抽成结构化台账——永不淘汰,冲突时说了算。
滚动摘要:出窗口旧轮次合并出的"温数据";摘要套摘要会漂移,要定期用原文全量重写。
KV Cache:推理端缓存历史 token 的计算结果——省的是算力不是容量,窗口该爆还是爆。
