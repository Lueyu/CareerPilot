工程实践 · Q4

如何处理 Agent 的长对话场景(> 10 轮)?

⭐⭐⭐⭐ #Agent#长对话#Memory
30秒电梯稿

"上下文不能无限塞,做分层压缩:最近 K 轮保原文(工作记忆)→ 出窗口的合并进滚动摘要(摘要本身定期重写防漂移)→ 关键信息(用户目标、约束、已确认事实)槽位化抽取成结构化 Memory → 全量历史进向量库按需检索。一句话:重要的留下、啰嗦的压掉、需要的随时找得回来。触发上用 token 预算水位线,压缩后跑多轮一致性测试防丢信息。"

通俗类比

就是开会做纪要:最近半小时的讨论你记得清清楚楚(原文保留);上午聊了啥只记得要点(摘要);"已决定 15 号上线"这种关键结论写在白板上谁都看得见(结构化槽位);要吵架时翻录音笔原话(按需检索历史)。如果每开一小时会你就把之前的对话原文从头到尾再读一遍——那就是不压缩的 LLM,又慢又贵还容易看串行。

详细拆解

1. 上下文组装的分层结构

2. 各层实现要点

  • 滑动窗口:保留最近 N 轮原文,判断"哪些信息只在这几轮里"很关键——窗口边界处的信息最容易丢,切分时在完整任务边界切,不在任务中间切。
  • 滚动摘要:出窗口的轮次合并进旧摘要,生成新摘要。坑:摘要套摘要会漂移(细节逐层丢失)——对策:每 5~10 轮用"原始对话 + 旧摘要"重新生成一次全量摘要(而非摘要的摘要),并且摘要 Prompt 里明确"保留数字、日期、决定、待办"。
  • 槽位抽取:异步任务从对话里抽数据结构(目标、约束、已完成步骤),这是永不丢失的一层,也是最便宜的(几百 token 就能存下整个对话的骨架)。
  • 按需检索:全量对话(原文)存向量库,当前话题相关时捞 top-k 片段——处理"你把我们 20 轮之前讨论的那个方案改成 B 版"这类回指需求。

3. 触发时机与工程化

  • 水位线策略:上下文用量 > 70% 触发压缩,给生成留余量,别等到爆。
  • 压缩是异步的:压缩进行中不阻塞当前回复。
  • 多任务对话(用户中途换话题):按话题分段,各自摘要,互不污染。

4. 防丢信息的验证

  • 长对话测试集:30~50 轮的脚本对话,在末尾问开头提过的细节,比对不压缩 vs 压缩的回答一致率——这是衡量压缩质量的硬指标。
  • 线上:监控"用户重复告知率"(用户把说过的事再说一遍 = 记忆丢了)。
面试官追问
Q:现在长上下文模型都能塞 128K 了,还需要压缩吗?
需要:① 成本与延迟随 token 线性涨;② lost in the middle——超长上下文中部信息利用率显著下降,塞得多不等于记得住;③ 多轮 Agent 中工具输出膨胀极快,几轮就能撑爆。压缩+检索是长期方案。
Q:摘要和槽位信息打架(摘要说预算 5 万,槽位记的是 3 万)?
以槽位(结构化、抽取时带置信度)为准,摘要只做背景;槽位更新是唯一可信源,冲突时取最近时间戳的。
术语卡
滑动窗口:只保留最近 N 轮原文。
Lost in the middle:长上下文中部信息容易被忽略。
槽位(slot):预定义的关键信息字段。
