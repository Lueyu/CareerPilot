Agent Memory 压缩算法设计

⭐⭐⭐⭐ #Memory#压缩算法#Agent 所有公司（通用）
先说人话:Agent 聊得越久,历史对话越像滚雪球——10 轮就 5000 token,成本、上下文窗口、回答精度三头同时被挤压。这题问的是:怎么把历史压到 30% 左右,还保证该记住的一句不丢。面试官爱考它,因为最容易暴露「只会说截断/摘要两个词」的人;追问一句「怎么证明压缩没坏事」,没设计过评估的当场就露馅。
30秒电梯稿

"Memory 爆炸的解法不是'无脑截断',而是分级压缩,像存储的冷热分层一样分三层治理:第一,关键信息抽取——从对话里抽出事实、任务目标、未完成事项、用户偏好、约束条件,这些是'删除代价最高'的信息,优先保真;第二,递进式摘要——超出滑动窗口的旧轮次压成摘要,摘要积累后再'摘要的摘要',形成金字塔,越旧越省;第三,结构化分流——高频稳定信息沉淀到长期记忆(向量+属性表),瞬态信息留在窗口里随用随弃。目标是10 轮 5000 token 压到约 30%,但压缩率只是手段,用『信息保留率 + 下游任务成功率』双指标验收——就像备份压得再小,恢复不出来就是零分。"

通俗类比

最贴近的类比:给第二天接班的同事写交接纪要。开了 3 小时会、录音转成 5000 字,你不能把全文甩给同事,得写一页纸——结论、待办、关键数字、人名都留,寒暄和三轮重复讨论都删。压缩算法就是"AI 纪要员",真正的难点不是"删字",而是判断哪些字删了会坏事:漏记一条"客户要求周五前交付",同事第二天就翻车。所以好的压缩算法是"有选择地忘",不是"平均地砍"。

用你熟悉的备份存储体系再映射一遍:这套架构就是一个冷热分层 + 增量合成的存储系统——滑动窗口是热数据层(最近几轮原文放 SSD,读写最快,容量最小);滚动摘要 L1/L2 是温数据层(近备份数据做增量+合成,占用递减);长期记忆库是归档层(带索引,按需检索恢复);"去停用词/去冗余"对应源端去重(写之前先把明显重复的块砍掉);"异步压缩"对应备份窗口外跑任务,不占生产链路 IO;"召回保护"(原始记录落库可回查)对应你的职业底线——线上工作副本和可回查的原始副本分离,纪要丢了还能翻原始录音。"递进式摘要+定期全局重整"就是增量备份攒多了定期做一次合成全量,防止增量链太长导致恢复慢、误差攒多了导致纪要走样。

哪里像:都是容量压力下分层治理、都是"越旧越浓缩"、都强调原始数据保底可回查、都必须做"恢复演练"验证(压缩率好看不等于真可用)。哪里不像:备份压缩是确定性无损算法,gzip/重删解开后一字节不差,恢复就是逐字还原;Memory 压缩是有损的语义压缩,信息密度靠"判断哪些重要"来决定,而且没有"逐字还原"这回事——追问细节时靠检索把原始片段捞回来,是近似重建,不是解开压缩包。所以备份的验收指标是"校验和一致",而它的验收指标必须是"下游任务成功率不掉",这是两个行业最本质的差别。

详细拆解

1. 问题定义:为什么必须压缩

  • 长对话 10 轮轻松到 5000 token,而成本、上下文窗口、注意力稀释三重压力同时存在:成本(每轮都重算全历史,API 按输入 token 计费,第 10 轮等于为前 9 轮反复付费,类似每轮增量备份都先全量重传一遍)、窗口(超长被截断丢尾部)、精度(关键信息淹没在冗长历史里,模型越聊越"失焦"——这个现象有专门研究,见 Lost in the Middle:模型对超长上下文中部信息的利用率显著低于首尾,历史越长"中间埋的信息"越容易被无视)。
  • 压缩到 30% 只是手段,真正的目标是"压缩后模型表现不降"——所以评估必须绑定下游任务,不能只看压缩率。这和备份行业"压缩比是次要指标、可恢复性是一票否决"完全同构。
不压缩时第 10 轮的成本账(每轮全量重放历史):
  第1轮 输入   500 token        第6轮 输入  3000 token
  第2轮 输入  1000 token        第7轮 输入  3500 token
  第3轮 输入  1500 token        第8轮 输入  4000 token
  第4轮 输入  2000 token        第9轮 输入  4500 token
  第5轮 输入  2500 token        第10轮 输入 5000 token
  ── 10 轮累计输入 27500 token;再聊 10 轮,数字翻倍还带平方级的注意力开销

2. 压缩的三个层次(别只想到摘要)

层次做法信息损失适用
Token 级去停用词、压缩冗长工具输出、截断重复小(有损)打底,先砍掉明显冗余
块级(摘要)把若干轮对话重写成更短的摘要/要点中历史轮次、已闭环的旧任务
语义级(抽取)抽成结构化记忆:事实/目标/偏好/约束可控跨会话必须保留的核心信息

三层的关系是逐层递进、层层兜底:Token 级像源端去重,便宜、确定性高、先跑;块级摘要处理"过程性冗长";语义级抽取处理"必须原样保真的少量关键信息"。三层不是互斥的——同一段对话先去冗余,过程部分进摘要,关键信息进结构化表。

3. 关键信息识别(压缩算法的灵魂)

  • 按"删除代价"给信息分级:① 任务目标与约束("周五前交付""预算 5 万")删除代价最高,必留;② 未完成事项 / 待办必留;③ 用户偏好与事实("不吃香菜""base 在上海")长期有效,抽到长期记忆;④ 已完成任务的中间过程可大胆压缩,只留结论;⑤ 寒暄、重复、兜圈子直接删。
  • 实现:用 LLM 做抽取 + 打分(重要性/时效性/可复用性),结构化输出成 key-value 或三元组,便于后续检索与更新。一个可落地的打分公式:score = w1×重要性 + w2×时效性(随时间衰减) + w3×可复用性,外加两条硬规则:用户显式说"记住这个"直接置顶进受保护列表;已写入用户档案的事实(如偏好)不再重复占窗口。
抽取示例:一段对话 → 结构化记忆(语义级压缩,保留密度最高)
输入对话:
  用户:"帮我订周五下午的活动场地,预算 5 万以内,我们 base 在上海,
        团队大概 20 人。对了 12 点到 13 点不要安排,大家要午休。
        上次那家日料店不错,我们团队不吃香菜的人多。"

抽取输出(三元组 / key-value):
  { "type": "任务目标",   "content": "订周五下午活动场地",        "status": "未完成" }
  { "type": "约束条件",   "content": "预算 <= 5 万" }
  { "type": "约束条件",   "content": "周五 12:00-13:00 不可占用" }
  { "type": "事实",       "content": "团队 base 上海, 20 人" }
  { "type": "偏好",       "content": "偏好日料; 多人不吃香菜",   "scope": "长期" }

原文 ~90 token → 结构化后 ~60 token 且零关键信息损失;
剩下的"上次那家不错"这类过程性寒暄,在摘要层一句话带过即可。

4. 分级压缩架构(金字塔)

对着图从上往下读,就是一条"越旧越冷、越旧越小"的分层沉降链,和热层→温层→归档层的存储 tiering 完全同构:

  • 滑动窗口 + 递进式摘要(rolling summary):窗口外的轮次异步压成摘要,新内容进来时旧摘要被"再摘要"一次,保证越旧的信息占用越少。L1 合并的操作是增量的:L1_new = summarize(L1_old, 窗口外新增的轮次)——只处理新增量,不重读全量,这正是增量备份相对于每轮全量的优势;L2 定期把多份 L1 合并重述,相当于攒了一批增量后做一次合成全量,防止摘要链太长导致"纪要的纪要的纪要"误差累积。
  • 异步压缩:压缩不阻塞回复,在回复返回后/空闲时进行,避免增加首字延迟——等价于把重删/压缩作业放到备份窗口之外跑,生产链路零感知。触发条件设阈值而不是每轮必跑:比如窗口内 token 超过模型上下文的 30%~50% 才触发,高频对话时用优先级队列保证压缩不落后太多。
  • 召回保护:被压缩掉的内容不是真删——原始记录落库保留,压缩后的摘要只是"在线工作副本";用户追问细节时可按时间/话题检索回原始片段(类似人"想起细节去翻记录")。这是整套设计的安全网:摘要坏了可以重建,原始库在就永远有底——和"工作副本损坏时从备份副本恢复"是同一条工程铁律。
  • 与 p1q7 的长期记忆系统打通:压缩后抽取出的稳定事实流入长期记忆,避免"每次会话都重新自我介绍"。跨请求持久化这条思路,工业界有完整参考实现——MemGPT 论文把 LLM 上下文当"内存分页"管理,主上下文放不下就换页到外部存储,和操作系统虚拟内存的思想一模一样,值得面试时点名。

5. 压缩率与评估(说清 30% 怎么达成、怎么验证)

  • 达成 30% 靠组合拳:去冗余(省 10%~20%)+ 块级摘要(历史轮次可压到原文 1/3~1/5)+ 关键信息结构化(只保留"信息"不保留"修辞")。通常 token 级 + 块级就能把历史压到 30% 附近。
第 10 轮时的记忆账本(5000 → 约 1500 token, ≈ 30%):
┌───────────────────────────────────────────────────────┐
│ 当前窗口:最近 3 轮原文            ~ 900 token (热层)  │
│ L1 摘要:第 4~7 轮浓缩           ~ 250 token (温层)  │
│ L2 摘要:第 1~3 轮再浓缩         ~ 150 token (冷层)  │
│ 长期记忆:受保护事实/偏好结构化   ~ 200 token (归档)  │
│ 合计注入 prompt ≈ 1500 token —— 压缩率 30%           │
│ 原始对话全量落库(不计入上下文)   5000 token (保底)  │
└───────────────────────────────────────────────────────┘
  • 评估三指标:压缩率(压缩后/原 token 数)、信息保留率(构造"关键信息清单"看压缩后还剩多少条可被召回)、下游任务成功率(同一批任务用压缩 vs 全历史的答对率之差,这是最硬的指标)。这个验收逻辑你闭着眼都能背:压缩率对应"压缩比",保留率+成功率对应"恢复演练成功率"——没做过恢复演练的备份策略不算备份策略,同理,没跑过下游任务对比的压缩算法不算设计完成。
  • trade-off:压得越狠越省越便宜,但细节丢失风险越高;所以压缩率应该按任务风险动态调——高价值任务(合同、医疗)保守压缩,闲聊类可激进。对应存储行业的"重要卷高 RPO 要求、日志卷低 RPO 要求",一份数据一个策略,不搞一刀切。
面试官追问
Q:怎么证明压缩后关键信息没丢?
人话:不能靠"看着像",必须像恢复演练一样跑量化测试,拿数字说话。类比:备份工程师从来不信"压缩比 5:1 所以肯定没问题",只信定期恢复演练的成功率——工作副本好不好用,演练一次就知道。技术:构造一批带明确关键信息的会话(目标/约束/偏好各若干条),压缩后让模型回答针对这些信息的追问,计算信息保留率;再跑一遍真实任务对比压缩版与全历史版的下游任务成功率,差值超过阈值即回退压缩策略。同时原始记录落库可回查,被压缩掉不等于永久丢失——这层保底让评估容错空间大很多。
Q:递进式摘要和直接全文摘要有什么区别?为什么用递进式?
人话:直接全文摘要是每次都从头读完整历史重写一遍;递进式只处理新增的那一段,和旧摘要合并再浓缩。类比:这就是"每轮全量备份"和"增量备份+定期合成全量"的区别——前者简单但每次都贵且慢,后者增量处理 O(新增量)、延迟低,链子太长时做一次合成校准。技术:递进式计算量随会话增长是线性的,适合流式在线场景;全文摘要要等会话很长才重算全量,又贵又慢。代价是摘要误差逐层累积,所以要定期"全局重整"(用原始记录重写高层摘要),并让关键信息走结构化抽取通道不进摘要链,从源头切断误差传播。
Q:压缩是同步做还是异步做?会不会拖慢回复?
人话:异步。压缩是后台作业,用户等的这条回复不能被它卡住。类比:重删和压缩任务从来不在业务高峰的生产链路上同步跑,而是排进备份窗口/空闲时段的队列——先把数据写下去,瘦身的事后台慢慢做。技术:主链路用现有窗口+上次摘要直接生成回复,压缩任务丢后台队列,完成后更新"下一轮可用的记忆",首字延迟零影响。代价是极高频对话下压缩可能落后一拍,缓解手段是"token 达阈值立刻触发 + 优先级队列",并且压缩任务幂等、可重入,落后多拍就合并一次做,不追每轮。
Q:用户明确说"这个一定要记住"的信息,怎么保证不被压缩掉?
人话:给这类信息开例外通道:显式标记、单独存放、不参与任何压缩和衰减。类比:关键库的高 RPO 卷会打上"禁止重删/禁止覆盖"的保留标签,存储策略再激进也碰不到它——保留策略优先于一切空间优化。技术:识别显式记忆指令后进入"受保护记忆":写入独立的关键事实表,加"用户明确要求"标签和来源轮次;摘要层处理时强制原样保留或只做无损改写(如去寒暄不动事实);抽取打分中该类信息权重置顶、不参与时效衰减。定期审计受保护列表,防止它无限膨胀把 30% 的预算吃光。
Q:摘要本身是 LLM 生成的,万一它摘要时"编错了"或漏了,误差一层层传下去怎么办?
人话:这是这套架构的真实风险,要主动承认并用机制兜住,而不是假装不会发生。类比:链式增量备份最怕"中间某一环损坏导致后面全废",对策是周期性合成全量重新校验整条链——摘要误差累积和坏链问题同构,解法也同构。技术:四道防线:① 关键信息不进摘要链,走结构化抽取通道,摘要层只负责过程性内容;② 摘要 prompt 强制"只删不加",禁止推断和补全,降低幻觉混入;③ 定期用原始记录对高层摘要做全局重整,误差不无限累积;④ 终极保底是原始记录全量落库,任何摘要都可重建、可回查——摘要只是工作副本,真相永远在底层。
Q:滑动窗口设多大?压到 30% 是拍脑袋还是有依据?
人话:窗口大小和压缩率都不是常数,是拿预算和实验测出来的。类比:热存储层容量怎么定?看最热数据的访问分布和成本预算,再留余量——拍脑袋定 10% 热层要么浪费要么颠簸。技术:窗口取最近 3~6 轮,覆盖大多数指代消解需要(用户说"还是用刚才那个"通常指近几轮);窗口 token 上限设在模型上下文的 30%~50%,给检索结果和输出留空间。30% 的依据是:去冗余省 10%~20%,块级摘要把历史压到 1/3~1/5,两者叠加实测落在 25%~35% 区间——最终以"下游任务成功率持平"为验收线,而非死守 30% 这个数字。
术语卡
递进式摘要:增量地不断把旧内容再摘要,形成多层浓缩——增量备份的摘要版,只处理新增量。
滑动窗口:只保留最近 N 轮原文,更旧的交给压缩层——对话里的热数据层。
Lost in the Middle:模型对超长上下文中部信息利用率显著偏低的现象——历史越长,埋在中间的关键信息越容易被无视。
信息保留率:压缩后仍可被召回的关键信息占比——压缩版的"恢复演练成功率"。
关键信息抽取:把事实/目标/偏好抽成结构化记忆,密度最高、不进摘要链,误差传不到它。
MemGPT:把 LLM 上下文当内存做分页管理的经典方案,主上下文装不下就换页到外部存储。
异步压缩:后台做压缩不阻塞对话回复,像备份窗口外跑重删作业,生产链路零感知。
