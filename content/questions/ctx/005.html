Agent核心 · Q20

你是怎么设计agent的记忆系统？长期记忆如何存储？如果历史记录量非常大，怎么优化查询效率？

⭐⭐⭐ #记忆系统#存储优化 字节 / 阿里(高频)
先说人话:这题在问:聊天窗口装不下的历史放哪、怎么存、量大了怎么查得快——本质是一道存储架构题披着 Agent 的皮。字节/阿里高频考它,因为一次就能测出你会不会分层设计、会不会存储选型、有没有查询优化的手感。答「全塞进 context」或「全扔向量库一把梭」的,直接暴露没有工程思维。
30秒电梯稿

"我按认知分层设计:工作记忆(当前对话滑动窗口,Redis)→ 会话摘要(超窗口的历史压缩)→ 长期记忆(抽取出来的事实/偏好)。长期记忆分多种存储各司其职:结构化高频字段走属性表、语义事实走向量库、带时序关系走知识图谱、原始对话归档对象存储。历史量非常大时,查询优化靠四招:① 冷热分层,热记忆小索引、冷记忆归档不参与默认检索;② 粗筛精排,先用属性过滤把候选砍到千级,再向量精排取 top-k;③ 索引优化,HNSW + PQ 量化压缩内存、标量字段建过滤索引;④ 压缩,原始对话做增量摘要,只保留抽取后的记忆。核心是别全量塞,按需检索注入。"

通俗类比

先搞懂为什么必须分层(用内存想 context 窗口):LLM 每次回答时能「现场翻阅」的只有 context 窗口——它就是这台机器的内存:容量有限、按 token 计费、而且每次请求都要重新装载。把所有历史塞进去,等于每答一句话前把整个数据库 load 进内存:装不下、贵得离谱,还会被无关数据稀释注意力。所以记忆系统的思路和存储系统一模一样:装不下就分级,不能丢就归档,要查快就建索引。哪里像:都是「热数据放快的贵的介质,冷数据放慢的便宜的介质,要时找得回」。哪里不像:备份系统是灾难时才读的离线资产,记忆系统是每次回复都要在线查的服务——读频率高几个数量级,所以索引必须建得比备份目录细得多。

整个系统像一个认识你很久的老管家:他脑子里记着你们「正在聊的事」(工作记忆,相当于内存里的工作集);上周聊过什么,他只留一份大概笔记(会话摘要,相当于 checkpoint——旧内容不断合并压缩,笔记不随时间越记越厚);而你「不吃辣」「公司在上海」这种沉淀下来的事实,他写进分门别类的档案柜(长期记忆),常用信息贴在柜门(热层),陈年旧账装箱进地下室(冷归档)。找信息时,他从不翻遍地下室,而是先按标签抽出几本候选,再逐页精读(粗筛精排)。哪里像:这套「抽取-分级-索引-按需取」正是备份体系的日常——全量沉淀出关键资产、增量控制体积、归档留底、恢复先查目录再取带。哪里不像:备份最怕「丢」,记忆还怕「错」——取回一条过时记忆(用户早就不吃辣了)比漏取更糟,所以记忆多出「版本覆盖+时间衰减」这一层;且备份是写一次很久才读一次,记忆是边写边读的在线服务,读写取舍的方向完全不同。

详细拆解

第 0 步:先立设计目标(这本质是一道存储架构题)

记忆系统要同时满足三个互相打架的约束,而每一个在存储界都有现成解法:

  • 装不下:context 窗口就 128K~200K token,历史一长必然爆——容量矛盾,解法是分级存储;
  • 不能丢:用户三周前说过「对花生过敏」,今天聊聚餐忘了这条是事故——持久性矛盾,解法是归档留底;
  • 要查得快:回忆发生在回复的同步路径上,记忆查询慢 500ms,回复就慢 500ms——检索矛盾,解法是索引+分层。

所以整题的答法就一句话:用存储系统的思路给对话数据做架构设计——按访问模式分级、按查询模式选介质、按规模上索引和分片。

1. 分层记忆模型:按访问频率分三级

为什么不一层存到底?因为「最近几轮」和「三个月前的某句话」的访问频率差着几个数量级,混存必然是热数据被冷数据拖累——和内存、SSD、磁带为什么要分介质是同一个道理。认知科学里的分层是现成的,直接照搬:

层级存什么存储介质生命周期存储系统里的对应
工作记忆当前会话最近 N 轮原文Redis 列表(滑动窗口)会话期间内存里的工作集,用完即弃
会话摘要超窗口历史压缩成的摘要Redis + DB数天~数周checkpoint:旧增量不断合成,体积恒定
长期记忆抽取的事实/偏好/事件三元组向量库 + 属性表 + 图存储长期(可衰减)带索引的持久库 + 对象存储归档
一条消息进来,数据怎么流(所有"写入"都异步,不卡回复):

  当前会话最近 N 轮 ─────→ 工作记忆(Redis 滑动窗口)────→ 直接整段注入 Prompt
                               │ 滚出窗口的历史
                               ▼ 异步压缩,体积恒定
  超窗历史 ────────────→ 会话摘要(像 checkpoint,不随对话变长而膨胀)

  每轮对话 ───异步──→ 事实抽取管道:挖出"用户不吃辣""5 月换了城市"
                             │ 打分(近期性 × 频率 × 重要性)+ 建索引 + 冷热分层
                             ▼
                        长期记忆 = 属性表 + 向量库 + 知识图谱 + 对象存储归档

  生成回复前 ──→ 按需检索:标量预过滤(千万级 → 千级)→ 向量精排(→ top-k)→ 只注入几条

三层各司其职:

  • 工作记忆:最近 N 轮原文,Redis 列表做滑动窗口(新消息进、老消息出),O(1) 读写,生成时整段直接注入。类比:开会时手边的白板,只写当前这摊事。
  • 会话摘要:窗口滚出去的历史异步压缩成摘要;每轮都是「旧摘要 + 新滚出的内容 → 再压缩一次」,像 日志压缩/合成备份——不管对话多长,摘要体积恒定,不会越聊越贵。
  • 长期记忆:对话里挖出的事实(偏好、事件、关系)单独入库,是唯一跨会话、真正会「量大到要优化」的一层——后面四板斧全是为它打的。

2. 长期记忆怎么存(多存储协同,不是只塞向量库)

核心原则和存储选型一致:查询模式不同,介质就该不同。确定字段走点查、模糊语义走向量、时序关系走图、原文走归档——一份「什么查询走什么库」的路由表:

记忆类型例子查询模式放哪
确定字段称呼、语言偏好、所在城市KV 点查,O(1)属性表(Redis/MySQL)
模糊语义事实"用户喜欢简洁回答"按意思相似度检索向量库
带时序的关系"3 月还在 A 公司,5 月离职"图遍历 + 时间过滤知识图谱
原始对话全文完整流水(审计/重抽取用)按需拉取,不进默认检索对象存储归档
  • 结构化属性表:高频确定字段(称呼、语言偏好、所在城市)直接 KV 存,读起来 O(1),不走向量检索,又准又快——「能枚举键的事实就别按意思查」,这类字段走 embedding 相似度纯属浪费,还可能查错。
  • 向量库:没法枚举键的模糊事实("用户喜欢简洁回答")存 Embedding,靠向量检索按意思找。记忆库的量级大头在这一层,是查询优化的主战场。
  • 知识图谱:实体间带时间的关系(在职/离职、素食→复食),能回答"上个月还是 A,现在呢"这类时序问题——纯向量库给不出时间维度。
  • 对象存储归档:原始对话全文不删,压缩后归档做冷备,供审计和未来重抽取——兜底留痕,但绝不参与默认检索。

3. 历史量非常大时,查询效率优化的四板斧(重点)

先点破慢的根源:不是向量算得慢,是每次扫的候选太多。四板斧按「先砍扫描量、再降单条成本」的顺序使:

① 冷热分层:把"默认要扫的量"压到总量的 1/10 以下

记忆按分数分层:score = 近期性 × 频率 × 重要性(加权可调),和缓存淘汰、备份保留策略是同一个思路。热记忆(高活跃)进小索引,默认检索只查热层;冷记忆归档,只有显式搜索("我们去年三月聊过什么")才扫。物理介质对应:热层常驻内存索引、温层 SSD、冷层对象存储。升层降层像 LRU:被再次命中的记忆加分升热,长期不碰的降冷,自然"遗忘"。为什么不干脆删冷记忆?审计合规和"用户偶尔翻旧账"决定了归档必须留——和备份保留期一个逻辑。

② 粗筛精排(两阶段检索):先用便宜的操作砍候选

  • 先用元数据过滤(必做,user 级隔离 + 时间窗 + 类型),再用向量算相似度——过滤索引比暴力向量扫描快两个数量级。道理朴素:标量过滤是 B-tree/位图,便宜;向量距离计算贵,而且贵在乘以候选数——先用便宜的操作把千万级砍到千级,贵的操作才有预算可花。
  • 混合检索:重要关键词(如"发票""报销")走倒排索引精确命中,语义模糊走向量,RRF 融合后精排——专有名词、工号这类词 embedding 容易丢,倒排补位。

③ 索引与压缩:单机装得下、算得快

  • HNSW 图索引换查询速度(吃内存),配合 PQ(乘积量化)/SQ 把向量压缩 4~8 倍,内存降了缓存命中率反而升、距离计算变快。PQ 的思路和备份去压缩同源:向量切块、每块只存聚类中心的编号——有损压缩,拿 Recall@k 掉零点几个点换内存砍半,要拿召回曲线护航,不做无依据的牺牲。
  • 分片:记忆量超单机内存时按 user_id 一致性哈希分片,检索只落在目标分片,天然并行——分布式存储的基本功直接搬过来:千万级全局库变成万级单分片,每个查询只扫自己那片。

④ 数据层压缩:别让历史越滚越贵

原始对话不无限堆,走增量摘要——旧对话先异步抽出记忆,原文降级为摘要或删除。这一步省的不只是存储,更是生成质量:注入 10 条抽取好的事实,远好于塞 10 轮原文流水——历史原文进上下文,token 贵、噪声多,模型反而被带偏。类比:备份不留每天全量,靠增量+定期合成,否则空间和恢复时间一起失控。

4. 读写的 trade-off:宁慢写,不慢读

写入(抽取、打分、建索引、分层)全走异步管道,不阻塞回复;读取在回复的同步路径上,必须快。这和备份系统的取舍一模一样:备份窗口可以慢、可以挪到低峰,恢复 RTO 必须快——所以宁可写入时多做一步,换读取时的低延迟。用户对「后台几秒后记忆才入库」毫无感知,对「回复卡了 500ms」直接皱眉。

面试官追问
Q:向量检索在千万级记忆库下还是很慢,怎么进一步压?
人话:别指望把「算」提速,要让向量根本别面对千万级——先拆小、先过滤、再压缩。类比:恢复某个用户的单个文件,没人会全库扫描:先按 user 定位到那个用户的备份集(分片),再按时间点缩小范围(预过滤),最后才翻具体数据块——扫描量降两个数量级,速度自然起来。技术:① user_id 一致性哈希分片,单查询只落一个分片;② 标量预过滤把候选降到千级再算向量;③ PQ 量化降低单条距离计算成本;④ 热层常驻内存、温层 SSD、冷层归档,分级响应。极端场景上 GPU 暴力检索(百毫秒扫千万)或倒排索引先命中再精排兜底。
Q:记忆库和 RAG 知识库有什么区别?
人话:一个记「这个用户的事」,一个存「全公司的资料」——服务对象、生命周期、更新方式都不一样,不能混为一谈。类比:记忆库像每个客户专属的跟进档案,随交往持续更新,旧结论要被新结论覆盖;知识库像全员共享的产品手册,大家查同一份,靠发新版更新。技术:① 作用域:user 级、随对话演化 vs 全局静态;② 时效:记忆要时间衰减+冲突消解(新事实覆盖旧事实),知识库靠版本更新;③ 粒度:记忆返回事实/偏好三元组,知识库返回文档 chunk;④ 隔离:记忆查询必须带 user_id 过滤,这是合规红线。读写模式不同,存储与索引策略就该分开设计。
Q:原始对话记录要不要全留?
人话:留,但「可追溯」和「可检索」分开解决——留是归档着留,不是让它平等参与检索。类比:这就是备份界的归档分层:完整数据放对象存储留底可审计,日常恢复永远先走热层和索引——底账在,但翻底账不能成为每次操作的必经之路。技术:热数据(近 N 天)原文放可快速访问介质;冷数据先异步抽取出记忆,原文压缩归档对象存储;抽取失败的进重试队列,不许静默丢。每次生成注入的只有抽取后的记忆条目,原始流水只在审计或用户翻旧账时才按需拉回。
Q:旧记忆和新事实打架怎么办?比如用户之前说爱吃辣,今天说不吃辣了。
人话:这是记忆系统最容易翻车的点——取回一条过时记忆比漏取更糟:Agent 会理直气壮地给你推荐川菜。类比:像备份的版本管理:默认恢复点永远只有「最新有效版」,旧版本不删、标记失效留痕——你能查历史版本,但生产恢复永远用最新那份。技术:① 抽取时按主键(如「饮食偏好」)做 upsert:新值覆盖,旧值标失效并留时间戳;② 注入时按「近期性×频率×重要性」加权,老记忆自然衰减;③ 关系类记忆在图上标生效区间,支持「上个月还是 A,现在是 B」;④ 高风险场景(点菜、用药)宁可现场重确认一句,也不赌旧记忆。
术语卡
分层记忆:工作/摘要/长期三层——本质是给对话数据做分级存储,热的在内存、沉淀的带索引、原文进归档。
HNSW:多层图索引,拿内存换查询速度,向量检索默认主力——记忆库越大越吃内存,所以要配量化。
PQ(乘积量化):向量切块、每块只存聚类编号,压缩 4~8 倍——备份去压缩的同源思路,有损但划算。
冷热分层:活跃记忆小索引、冷记忆归档不进默认检索,把每次扫描量压到总量的 1/10 以下。
粗筛精排:先标量过滤砍候选(千万级→千级),再向量精排取 top-k——便宜的操作先干,贵的才有预算。
一致性哈希:按 user_id 把记忆库拆成独立分片,单查询只落一个分片,天然并行、随规模水平扩展。
