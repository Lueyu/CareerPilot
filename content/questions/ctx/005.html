Agent核心 · Q20

你是怎么设计agent的记忆系统？长期记忆如何存储？如果历史记录量非常大，怎么优化查询效率？

⭐⭐⭐ #记忆系统#存储优化 字节 / 阿里(高频)
30秒电梯稿

"我按认知分层设计:工作记忆(当前对话滑动窗口,Redis)→ 会话摘要(超窗口的历史压缩)→ 长期记忆(抽取出来的事实/偏好)。长期记忆分多种存储各司其职:结构化高频字段走属性表、语义事实走向量库、带时序关系走知识图谱、原始对话归档对象存储。历史量非常大时,查询优化靠四招:① 冷热分层,热记忆小索引、冷记忆归档不参与默认检索;② 粗筛精排,先用属性过滤把候选砍到千级,再向量精排取 top-k;③ 索引优化,HNSW + PQ 量化压缩内存、标量字段建过滤索引;④ 压缩,原始对话做增量摘要,只保留抽取后的记忆。核心是别全量塞,按需检索注入。"

通俗类比

像给一个认识你很久的老管家建档案:他脑子里记着"你正在聊的事"(工作记忆);昨天聊过啥,他只留个大概(摘要);而你"不吃辣""公司在上海"这种沉淀下来的事实,他写进分门别类的档案柜(长期记忆)——常用信息贴在柜门(热存储),陈年旧账装箱进地下室(冷存储)。要找信息时,他不会把整个地下室搬出来,而是先按标签筛出几本,再逐页精读(粗筛精排)——档案越多,越要靠索引和分类,而不是靠翻。

详细拆解

1. 分层记忆模型

层级存什么存储介质生命周期
工作记忆当前会话最近 N 轮原文Redis 列表(滑动窗口)会话期间
会话摘要超窗口历史压缩成的摘要Redis + DB数天~数周
长期记忆抽取的事实/偏好/事件三元组向量库 + 属性表 + 图存储长期(可衰减)

2. 长期记忆怎么存(多存储协同,不是只塞向量库)

  • 结构化属性表:高频确定字段(称呼、语言偏好、所在城市)直接 KV 存,读起来 O(1),不走向量检索,又准又快。
  • 向量库:模糊语义事实("用户喜欢简洁回答")存 embedding,靠相似度检索。
  • 知识图谱:实体间带时间的关系(在职/离职、素食→复食),能回答"上个月还是 A,现在呢"这类时序问题。
  • 对象存储归档:原始对话全文不删,压缩后归档做冷备,供审计和未来重抽取。

3. 历史量非常大时,查询效率优化的四板斧(重点)

① 冷热分层:记忆按分数(近期性×频率×重要性)分热/温/冷。热记忆(高活跃)进小索引,默认检索只查热层;冷记忆归档,只有显式搜索才扫——把"每次要扫的候选量"压到总量的 1/10 以下。

② 粗筛精排(两阶段检索):

  • 先用元数据过滤(必做,user 级隔离 + 时间窗 + 类型),再用向量算相似度——过滤索引比暴力向量扫描快两个数量级。
  • 混合检索:重要关键词(如"发票""报销")走倒排精确命中,语义模糊走向量,融合后精排。

③ 索引与压缩:

  • HNSW 图索引换查询速度(吃内存),配合 PQ(乘积量化)/SQ 把向量压缩 4~8 倍,内存降了缓存命中率反而升、距离计算变快。
  • 分片:记忆量超单机内存时按 user_id 一致性哈希分片,检索只落在目标分片,天然并行。

④ 数据层压缩:原始对话不无限堆,走增量摘要——旧对话先抽取出记忆,原文降级为摘要或删除,避免"历史越长上下文越贵越吵"。

4. 读写的 trade-off:写入走异步抽取管道(不阻塞回复),读取是同步路径所以要快;为保查询效率,宁可写入时多做一步(抽取+建索引),换来读取时的低延迟。

面试官追问
Q:向量检索在千万级记忆库下还是很慢,怎么进一步压?
组合拳:① user 级一致性哈希分片,单查询只扫一个分片;② 属性预过滤把候选降到千级再向量算;③ PQ 量化降低单次距离计算成本;④ 热数据放内存、温数据放 SSD、冷数据归档,分级响应。必要时上 GPU 暴力检索(百毫秒扫千万),或用倒排索引先命中再精排。
Q:记忆库和 RAG 知识库有什么区别?
三个区别:① 作用域——知识库是全局静态文档,记忆是 user 级、随对话演化;② 时效——知识库靠版本更新,记忆要时间衰减和冲突消解(新事实覆盖旧事实);③ 检索粒度——知识库返回文档片段,记忆返回结构化事实/偏好。所以两者存储和更新策略都不一样,别混为一谈。
Q:原始对话记录要不要全留?
全留但分级:热数据(近 N 天)原文存可快速访问介质;冷数据先抽取出记忆后,原文压缩或归档到对象存储(便宜、可审计)。目的是"既能追溯,又不让它污染每次检索的上下文"。
术语卡
分层记忆:工作/摘要/长期三层,按粒度与生命周期分。
HNSW:多层图索引,查询快、吃内存。
PQ(乘积量化):向量压缩技术,换内存和速度。
冷热分层:活跃数据与归档数据分开存、分开查。
粗筛精排:先过滤砍候选,再精算排序。
一致性哈希:按 key 分片,检索只落单分片。
