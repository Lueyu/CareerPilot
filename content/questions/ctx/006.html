Agent核心 · Q21

有没有做记忆衰退，避免旧数据干扰新任务？

⭐⭐⭐ #记忆管理#遗忘机制 字节(真题)
先说人话:这道题问的是:你的 Agent 记忆系统会不会越攒越乱——过期事实还参不参与今天的决策,有没有一套淘汰机制。面试官爱考它,因为"只会存记忆"和"会管记忆生命周期"的人一聊就分层;答"数据越多越好、从不删除",直接暴露没被旧账噪音和 token 账单教育过。
30秒电梯稿

"有,而且这是记忆系统的标配而不是可选。我给每条记忆打一个分:score = 近期性(时间衰减)× 访问频率 × 重要性,分数随时间指数下降;低分记忆降级到冷存储(不参与默认检索,但可显式搜索),再低就归档删除。同时防干扰靠检索侧三道闸:只按当前话题检索 top-k、带时间窗过滤、新事实覆盖旧事实(冲突消解)。用户明确说'记住这个'的记忆重要性封顶,几乎不衰减——遗忘是让系统越来越聚焦,而不是把重要东西忘掉。"

通俗类比

先看你最熟悉的:备份系统的数据生命周期(ILM)。做备份的人天天在管"数据活多久":热数据在生产库,近期备份放性能层,老备份归档到对象存储,到期按保留策略清理。记忆系统干的是一模一样的事,只是把"备份集"换成了"一条条记忆":每条记忆带一个 score,分高分低;掉到阈值以下先降级、再归档、最后才清理——和"降冷—归档—到期删除"是同一条流水线。连"重要数据不能删"都有现成对应物:合规界的 legal hold(法务保留),被标记的数据无论过期多久都不许清理,对应到记忆系统就是用户那句"这个记住",衰减直接豁免。哪里像:分层存放、降级先于删除、重要数据豁免、清理走后台任务。哪里不像:备份保留策略基本按时间一刀切("30 天前的全删"),不看这条数据最近有没有人用过;记忆的 score 是连续打分,而且被访问会续命——每命中一次就加分、越用越难忘记,更接近"按数据温度自动分层",而不是"按日历删数据"。

再看人脑这版"祖传实现":遗忘曲线(艾宾浩斯)早就量过——不复习,记忆保持量几天就掉一半;复习一次,曲线重新爬起来。所以你"对花生过敏"记得死死的(重要性高),"半年前临时改的收货地址"早就模糊了(一次性、再没访问过),"老板天天提的价值观"滚瓜烂熟(访问频率高)。记忆系统照抄的正是这三个要素:近期性、频率、重要性。哪里像:三要素人脑和打分模型完全同构,连"复习=续命"都对上了——frequency 加分,等于每次命中算复习一次。哪里不像:人脑遗忘是被动且不可解释的,忘没忘全凭感觉;系统遗忘是显式分数、可解释、可干预——用户能查看、能置顶、能喊"这个别忘",这一点比人脑强。

详细拆解

1. 为什么要做遗忘(旧数据干扰的三种表现)

记忆系统只进不出,就像备份目录只写不清——先出质量问题,再出成本问题。具体三种表现:

  • 事实过时:用户"上月说在字节工作"→"这周已离职",旧记忆若还参与检索,会答出错误结论。这是三种里最危险的:它答得自信满满、错得悄无声息——像恢复时挂载了过期版本的快照,数据"看起来好好的",其实是旧的。
  • 噪音污染:记忆越多,检索越容易命中"语义相近但不相关"的旧信息,把当前任务带偏。检索是按相似度取 top-k 的,库里旧账越多,分给真正相关那条的位置就越挤。
  • 成本失控:上下文塞的旧记忆越多,token 越贵、首字越慢,P99 越难看——等于为一年来无人问津的旧账,在每一轮对话里持续付费,这笔账备份工程师最会算。

2. 打分模型(遗忘的依据)

遗忘不是拍脑袋"满 90 天全删",而是每条记忆带一个随时可重算的分数——分数就是这条记忆的"体温",冷热全由它说了算:

score = recency(t) × frequency(n) × importance(i)

recency(t) = e^(-λ·Δt)        # 时间衰减,Δt 距上次访问/写入的天数,λ 控制半衰期
frequency(n) = 1 + α·log(1+n)  # 访问越频繁分越高,log 防止无限膨胀
importance(i)  # LLM 抽取时打的初始重要性 + 用户显式指令加成

三项各管一件事,拆开看:

  • 时间衰减:用指数衰减模拟遗忘,是遗忘曲线的工程简化版。半衰期取经验值 30 天(λ = ln2/30 ≈ 0.023/天),含义就是"30 天没人用,权重腰斩",衰减速度一目了然:
距上次访问recency 剩余直观感受
0 天1.00刚写入 / 刚被命中
30 天0.50一个半衰期,腰斩
60 天0.25两个半衰期
90 天0.12若无 frequency/importance 兜底,基本该降冷了
一条记忆的"体温曲线"(纵轴 score,横轴:距上次访问天数)

 1.0 ┤ ● 写入,LLM 打初始分
     │  ╲
 0.5 ┤   ╲___                 ← 无人访问:30 天腰斩,60 天剩 1/4
     │       ╲
     │        ╲▲ 第 40 天被检索命中:frequency 加分 + recency 重置
     │         ╲╲              → "复习一次,续命一次"
 0.1 ┤ 冷线 ────╲─────────────  掉破冷线:降冷,只显式搜索可见
     │
     └────┬─────┬─────┬─────┬──→
          0     30    60    90   (天)
  • 访问频率:每次被检索命中就加分,学的是缓存淘汰里的 LFU 思路——"常用数据更抗换出"。用 log 包一层是防止高频记忆长成巨无霸、把别人全压死;命中时顺手刷新"上次访问时间",等于给 recency 也续了命——所以"越用越记得住"是机制保证的,不是玄学。
  • 重要性:写入时由 LLM 初判打分,做法可参照 Generative Agents 论文——它给每条记忆都打 importance 分,再据此决定去留,是这套打分的出处;用户显式说"记住这个"的直接封顶、衰减系数≈0,相当于备份里的法务保留——保留策略怎么算,都绕不开被标记的数据。

拿两条真实记忆对账,一看就明白:

记忆importance30 天后score 走向处置
"我对花生过敏"(用户叮嘱记住)封顶,衰减豁免recency 恒 1不掉永久留热

3. 分层处置(不是粗暴删除)

这张图对存储工程师就是老熟人——分层存储加归档的翻版,对照着看:

层score 区间(示例)检索行为备份世界的对应物
热记忆> 0.6参与默认检索、优先注入生产库 / SSD 热层
温记忆0.3 ~ 0.6参与检索,排序靠后近期备份 / 性能层
冷存储< 0.3退出默认检索,显式搜索可见归档层 / 对象存储
归档/删除极低或确认过期退出检索,留保留期后物理清理到期清理,删前留宽限期

关键设计是降级先于删除:冷记忆只是"退出默认检索",不是没了——用户提一句"我之前让你记的那个",显式搜索还能捞回来,捞回时 score 重置、记忆重新升温。等于给遗忘留了恢复通道:像到期清理前先归档、留宽限期,真物理删除之前都有反悔机会。分层的完整玩法可参考 MemGPT:把 LLM 上下文当内存、外部存储当磁盘,自己做换入换出——记忆系统是同一个思路。

4. 检索侧防干扰(光靠遗忘不够)

遗忘是"库存侧"治理,决定哪些记忆还在货架;防干扰还得有"取用侧"治理,决定每轮往 prompt 里放什么。三道闸:

当前对话
  │ 拿当前话题的 Embedding 去检索
  ▼
[闸1] 按需注入:只在热+温层取 top-k(5~10 条),不搞全量塞入
[闸2] 时间窗过滤:近期优先,旧记忆除非被显式点名否则让位
[闸3] 冲突消解:同主题新旧事实并存时,只取最新,旧版本标记 superseded
  ▼
注入 prompt,每条带时间戳:"用户 3 月说自己已离职" ← 新旧判断连模型一起兜底
  • 按需注入:每轮只用当前话题的 Embedding 检索 top-k(5~10 条),不是把全部记忆塞进上下文——相关性过滤是第一道闸。类比恢复流程:先查目录定位要恢复的那几块数据,不是把整个备份库灌进恢复路径。
  • 时间窗过滤:优先检索近期的记忆,旧记忆除非被显式引用否则让位——和"恢复默认取最新有效备份点"是同一条经验:时间上更新的,通常更可信。
  • 冲突消解:新旧事实矛盾时,以新覆盖旧(保留历史版本),从源头避免"过时答案"。做法同版本链 latest-wins:旧记忆打上 superseded 标记退出默认检索,但历史版本仍在——用户追问"我之前说的是什么"或需要审计时翻得出来;注入时再给每条带时间戳,等于把新旧判断也交给模型兜底,双保险。

5. 工程细节:遗忘是异步后台任务定期跑(每天/每周),不影响线上读取——和备份生命周期清理任务一个跑法:低峰错峰、可重跑幂等,线上检索永远读分层后的结果,升降级对用户只是"旧记忆慢慢淡出",无感。衰减参数按业务 A/B 调,配合"用户重复告知率"评估——用户老得重新自我介绍,就说明衰减太快了;反过来,跨会话还拿旧公司、旧城市说事,就是衰减太慢、旧账没沉下去,该收紧半衰期。参数改动走灰度发布,别全量一刀切;物理删除前留宽限期加审计日志,误删可追。

面试官追问
Q:重要信息也会被遗忘吗?
人话:不会。显式叮嘱过的记忆走"豁免通道",衰减系数接近 0,基本永久保留。类比:备份合规里的 法务保留——数据一旦挂上 legal hold 标记,保留策略算出"该删"也绝不清理;用户那句"记住这个"就是给记忆挂标记。技术:importance 封顶 + recency 恒为 1;普通事实由 LLM 写入时初判重要性,用户可在记忆面板查看、手动置顶或删除——哪些不能忘,最终控制权在用户手里,系统不全自动拍板。
Q:衰减率怎么定?会不会忘太快或太慢?
人话:没有天生正确的值,先经验值起步,再拿业务指标闭环校准。类比:备份保留策略也没人一开始就知道留 30 天还是 90 天,是看"第 31 天还有没有人来要数据"的使用分布反推出来的——衰减率同理,拿分布喂出来,不是拍出来。技术:半衰期从 30 天这类经验值起步,盯两条指标做平衡:用户重复告知率(老得重新自我介绍 = 忘太快,调慢)与旧事实干扰率/跨会话不一致率(拿旧公司旧城市说事 = 忘太慢,调快);参数改动走灰度 A/B,两条曲线交叉点附近就是合理区间。
Q:遗忘和知识库更新会不会冲突?
人话:不会,是两个部门各管各的账:知识库存"对谁都一样的静态文档",记忆存"这个用户独有的动态事实"。类比:像全局配置库和每台机器的本地状态——前者整体升版本号发布,后者各自逐条演化,谁也盖不住谁。技术:知识库靠版本号整体更新、重建索引;user 级记忆逐条打分衰减 + 冲突消解(以新覆盖旧、旧版本留档)。注入 prompt 时两路各自检索再合并去重排序;评估也分开做——知识库看文档覆盖率,记忆看重复告知率,别用一套逻辑硬套两套东西。
Q:现在长上下文模型窗口都到百万 token 了,把全部记忆塞进去不行吗?
人话:不行,窗口变大解决的是"装得下",不解决"该不该装"。类比:等于把整个备份库全量挂进恢复路径——容量装得下,不代表恢复流程该读它:读得越多越慢,还容易挑错版本,噪音的代价每一轮都在付。技术:① 成本和 TTFT 随注入量线性恶化,长尾尤其难看;② Lost in the Middle 现象——模型对长上下文中段信息利用率显著偏低,旧记忆塞得越多,真正相关那条越容易被稀释;③ 信噪比问题与窗口大小无关,检索 top-k 按需注入永远是更优解,大窗口只做兜底。
术语卡
时间衰减:记忆分数随时间指数下降,半衰期 30 天即"30 天不用权重掉一半"——遗忘的第一驱动力。
遗忘曲线:艾宾浩斯曲线,记忆保持量随时间先快后慢地衰减,是打分模型的心理学出处。
冷热分层:按活跃度把数据放进不同层级、分级检索——记忆系统照搬存储界这套管法。
冲突消解:新旧事实矛盾时以新覆盖旧、保留历史版本,防止"过时答案"混进当前对话。
LFU:Least Frequently Used,缓存按访问频率淘汰的算法;记忆打分借它让"常用"更抗遗忘。
MemGPT:把 LLM 上下文当内存、外部存储当磁盘做分层的代表论文,记忆分层的理论参照。
