系统设计 · Q7

设计一个 Memory 管理系统(长期记忆)

⭐⭐⭐⭐ #Memory#存储#检索
先说人话:这道题问的是:聊天 Agent 怎么在「关掉窗口再打开」之后还记得你是谁——你说过的事实怎么抽出来存、记错了怎么改、过期了怎么忘、几十万用户怎么互不串号。面试官爱考它,因为这是「个性化」的地基题,一眼能分清「把聊天记录全塞进 prompt」的莽夫和真设计过存储系统的人——答不出冲突消解和遗忘策略,基本等于没做过设计。
30秒电梯稿

"我按人的记忆分三层,正好对应存储分层:工作记忆(当前对话原文,内存级,滑动窗口)→ 会话摘要(温层,压缩过的历史)→ 长期记忆(归档库,从对话中抽取的事实和偏好,向量+结构化双存储)。写入走『抽取 → 冲突消解 → 更新』的异步管道,不阻塞回复;读取用当前话题检索 top-k 注入上下文,不是全量塞;遗忘用时间衰减 × 访问频率 × 重要性打分,低分降冷存储;个性化靠 user_id 强隔离,外加可查看可删除(合规硬要求)。业内参考 Mem0(抽取+检索)和 Zep(时间感知知识图谱)。"

通俗类比

先想想你自己的脑子:工作记忆是"手头正在聊的事"(聊到哪了,得记清);今天发生的事过几天就模糊成摘要("上周聊过报销的事");而"我同事小王不吃香菜"这种沉淀下来的事实才是长期记忆,下次点菜自动想起来。人还会遗忘不重要的琐碎(时间衰减),重要的事常想起就记得牢(访问频率加成)——Memory 系统完全照抄这套认知逻辑。

换成存储人熟悉的语言,这就是一套分层存储系统:工作记忆 = 内存/缓存(会话结束即失效),会话摘要 = 温层缓存副本(近期历史的低分辨率拷贝),长期记忆 = 持久化归档库(全生命周期、可检索可降级)。整个写入管道像异步备份作业——对话结束才触发抽取,不阻塞生产回复;冲突消解像快照链管理——新快照设为 active,旧的进版本历史而不是直接删;遗忘像备份保留策略(GFS:热的常留、旧的归档、过期的下架);检索注入像恢复时只挂载需要的卷,绝不整库恢复。哪里像:都是分层、异步、带保留策略的存储设计,你排过的所有账都能平移过来。哪里不像:备份讲究"全量忠实保存、到期硬删",Memory 讲究"只存提炼后的事实、衰减而非硬删"——而且一条记忆被访问得越多,就越不容易被删,这在备份世界里没有对应物(一份磁带不会因为常被读就延长保留期)。一句话:备份保真,记忆提炼。

详细拆解

1. 三层存储模型

先想清楚"什么数据放什么层"——这和"什么数据放 NVMe、什么放 SAS、什么下沉带库"是同一个决策问题,判断依据都是访问频率 × 生命周期:

层级存什么怎么存生命周期
工作记忆当前对话最近 N 轮原文Redis 列表会话期间
会话摘要超窗口的历史压缩成摘要Redis + DB数天~数周
长期记忆事实("用户base在上海")、偏好("回答要简洁")、事件向量库 + 结构化属性表永久(可衰减)

为什么原文不进长期记忆层?因为原始对话是未提炼的日志,直接存有三大罪:占存储、检索出来全是噪音、token 成本爆炸(注入 10 轮原文 ≈ 几千 token,注入 3 条事实 ≈ 几十 token)。所以长期记忆存的是抽取后的事实,不是流水账——这点想通,后面整套设计就顺了。

2. 写入管道(核心亮点)

写入是整个系统最有设计感的部分,因为它要异步、幂等、还要解决"新事实和旧事实打架":

  • 异步触发:对话结束(或每 N 轮)往消息队列丢一个任务,像备份作业调度——用户回复零感知。抽取失败可重试;入库幂等(以对话 ID + 轮次做去重键),队列重复消费不会重复入库——这套兜底就是你在分布式作业里烂熟的那套。
  • 抽取:用 prompt 让 LLM 从对话里抽出三元组(主体-关系-客体,概念见 知识图谱):"(用户, 居住地, 上海)""(用户, 饮食偏好, 不吃香菜)""(用户, 待办, 报销单在审批中)"。一条三元组十几个字,替代整段对话几百字——这是压缩比最高的去重。
  • 冲突消解:新旧记忆打架是常态,策略和存储版本管理同构:
冲突场景策略存储里的对应物
事实矛盾(上海 → 深圳)新覆盖旧,旧的不删,标记失效时间,保留历史轨迹快照链:新快照 active,旧的进版本历史
重复事实去重合并,刷新时间戳增量备份重删
部分更新(能吃辣 → 不能吃辣了)LLM 判断是"补充"还是"替换",拿不准就两条并存,读取时按时间新者优先写冲突靠仲裁规则,不靠运气

3. 读取:按需检索注入

每轮生成前:
当前话题 embedding ──→ 记忆库向量检索 top-k(5~10 条,相关性排序)
结构化高频字段(称呼/语言偏好)──→ 属性表直查,不走向量
                │
                └→ 合并去重,按 相关性+记忆分数 排序,裁剪到 token 预算(~500 token)
                   拼进 system prompt:"记住:用户base在上海;回答要简洁;报销单在上周提交审批"

原则:不是全量塞——像恢复时只挂载需要的卷,绝不做整库恢复:
     记忆越多 token 越贵、噪音越大,检索精度才是生命线
  • 每轮生成前,用当前话题的 embedding 去 Memory 库检索 top-k(5~10 条)相关记忆,拼进 system prompt。相关性排序是关键——用户问报销,你注入"用户不吃香菜"就是纯噪音,几条错记忆比没记忆更伤答案质量。
  • 结构化高频字段(称呼、语言偏好)直接走属性表,不走向量检索——像元数据查询走索引、不走全文扫描,一次毫秒级 SQL 搞定。

4. 遗忘机制

  • 记忆打分 = 近期性(时间衰减,如半衰期 30 天)× 访问频率(每次被检索加分,类 LFU)× 重要性(LLM 初始标注)。
score = recency × frequency × importance
  recency    = 0.5^(距今天数/30)          # 半衰期 30 天:30 天前 0.5,90 天前 0.125
  frequency  = 1 + log(1 + 被检索命中次数)  # 越被用到越牢,类 LFU 缓存
  importance = LLM 抽取时标注 1~10;用户明确说"记住这个" → 封顶,几乎不衰减

算笔账:
  30 天前存、命中过 4 次、重要性 8   → 0.5 × 2.6 × 8  ≈ 10.4  留在热区
  90 天前存、从未命中、重要性 2     → 0.125 × 1 × 2 = 0.25   降级冷存储
  • 低分记忆降级到冷存储(不参与默认检索,但可显式搜索)——注意是降级不是硬删,和备份"过期下架但归档可回捞"一个思路。
  • 用户明确说的("记住这个")重要性封顶,几乎不衰减——这是记忆版的 legal hold:被合规冻结的备份不许碰保留策略。
  • 用户可查看、可删除——这是合规硬要求(个保法的记忆版"被遗忘权"),面试提一句很加分。

5. 个性化:user_id 强隔离(每个用户一个独立命名空间,检索必须先带 user_id 过滤——这是租户隔离,串号是 P0 事故);画像 = 静态属性(注册信息)+ 动态偏好(从行为和反馈学习,如"用户总追问细节 → 回答风格调详细")。效果上等价于"system prompt 动态生成":同一个模型,不同用户拼出不同的提示词,答出不同味道。

6. 参考产品(展示知识面)

  • Mem0(论文见 arXiv:2504.19413):轻量,抽取-更新管道 + 向量/图存储,和我们上面设计的高度同构,易集成、社区活跃。
  • Zep / Graphiti(论文见 arXiv:2501.13956):把记忆组织成时间感知知识图谱(实体+关系+生效时间区间),能回答"用户上个月还是素食者,现在呢"这种时序问题——向量化方案只能回答"现在是什么",回答不了"什么时候变的",图谱方案适合重度记忆场景。
  • LangChain Memory(概念文档见 LangChain 官方文档):接口规范、适合原型,但内置实现偏基础,生产一般自己写或用上面两个。
面试官追问
Q:记忆越存越多,检索会不会变慢、变吵?
人话:会,而且"变吵"比"变慢"更早杀死你——慢是性能问题,吵是答案质量问题,注入一条不相关记忆就够污染答案。类比:像备份库不做保留策略,十年全量都堆着,恢复时你在一堆过期快照里找"对的那份",找到也未必敢用。技术:分层治理:高频热记忆单独小索引;检索先做属性过滤(user_id/类型)再走向量,缩小候选集;定期做记忆"GC"(合并重复、归档低分);注入条数上限 k≤10,宁少勿吵;再大规模就按 user_id 分区。一句话:用管备份库的思路管记忆库——分层、限流、定期清理。
Q:抽取出的记忆是错的(模型幻觉)怎么办?
人话:记忆库会被幻觉污染,而且错记忆会被反复检索命中、不断放大——脏数据进了热区,比没有数据更糟。类比:像备份目录里混进一份损坏的快照,还偏偏挂着"最新"标签,后续恢复优先挂它,错误自动传播。技术:每条记忆带置信度和来源对话 ID(可溯源、可审计,和备份要能定位到源卷一个道理);低置信度标记"待确认"不进默认检索;用户纠正时纠正优先级最高,立即覆盖/删除;关键决策(支付、健康建议)不单靠记忆,答案要求引用原始对话来源兜底。
Q:怎么评估记忆系统的好坏?
人话:专门测"隔了三天还记得吗",而不是当下聊得溜不溜——短期聊得好只要模型强就行,记忆系统考核的是跨会话延续性。类比:像容灾演练不看系统平时跑得多顺,专门设计"真恢复一次"的场景来验证 RTO/RPO——平时无感的东西必须靠专项演练暴露问题。技术:构造多会话延续性测试:会话 A 埋事实,隔会话 B,在会话 C 验证回答是否一致;用 LOCOMO 这类长对话记忆基准;线上看"用户重复告知率"(用户老得重新自我介绍就是记忆差)和记忆命中率,再配合 A/B 看留存与负反馈。
Q:这个记忆库和 RAG 的知识库有什么区别?
人话:RAG 是公司的公共文档库,人人共享、基本只读;Memory 是每个用户的私人笔记本,一人一份、随对话不断被改写——两套系统长得像,但写入路径和隔离要求完全不同。类比:像公司共享盘 vs 你的个人工作笔记:共享盘由文档发布方管理版本,个人笔记由系统随你说的话自动增删改。技术:相同点是读取层可以复用同一套技术(向量化+检索+注入);不同点是 Memory 必须做 user_id 强隔离、写路径复杂(抽取+冲突消解+衰减)、要支持查看/删除等合规操作,而 RAG 更偏文档级更新和读路径优化。能主动说"读取复用、写入分家",说明你没把两个概念搅成一团。
术语卡
工作记忆:当前上下文窗口内的对话原文,内存级数据,会话结束即失效。
冲突消解:新旧事实矛盾时的覆盖/合并策略——核心思想是"覆盖但不删旧",保留变更轨迹,和快照链管理同构。
时间衰减:记忆分数随时间指数下降(半衰期模型),对应备份的保留策略,但记忆可被访问频率"救活"。
知识图谱记忆:实体+关系+时间区间的记忆组织方式,Zep/Graphiti 的核心,能回答"事实什么时候变的"这类时序问题。
Mem0:开源长期记忆框架,抽取-更新管道+向量/图存储,生产级 Agent 记忆的事实参考实现之一。
LOCOMO:超长对话记忆评估基准,专门考核 LLM Agent 的超长期对话记忆能力。
