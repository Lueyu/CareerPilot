工程实践 · Q6

如何实现 Agent 的异常重试机制?

⭐⭐⭐⭐ #异常处理#重试#Agent
先说人话:Agent 调模型、调工具难免失败,这题问的是「失败之后怎么再试一次,而且不闯祸」。面试官爱考它,是因为重试谁都会写个 for 循环,但答错的人往往暴露两点:一是把不可重试的错也硬重试,二是不知道重试会把故障放大。能讲清风暴、幂等、降级的人,才是真在生产里救过火的。
30秒电梯稿

"先给错误分类:超时/限流/5xx 是瞬时故障,可重试;4xx 参数错误、内容审核拒绝,重试一百遍也是浪费,立即失败上报告警。可重试的用指数退避 + 随机抖动——等待时间 1s、2s、4s 翻倍,给下游喘息时间;加抖动是防止几百个并发在同一个时刻一起杀回来,把下游彻底压死。再设两道闸:最大重试次数、总时长预算。副作用操作(下单、写库、发消息)重试前必须先有幂等键,否则重试变成重复下单。预算烧完不报错了事,走降级链:备用模型 → 缓存/模板 → 兜底话术 + 转人工。最后每跳重试都打日志、盯重试率——重试率飙高就是下游要出事的前兆。"

通俗类比

整个机制像备份作业的失败处理,你天天在干:一个备份作业跑挂了,你第一件事不是无脑重跑,而是看日志分类——网络闪断、备份窗口撞上生产高峰,这是瞬时故障,错峰重跑就好;存储池配额没申请、路径写错了,这是配置错误,重跑一万次也是同一个错,得停下来改配置。Agent 调 LLM 一模一样:超时、429 限流、503,是下游「忙不过来」,等一等再试有机会成功;400 参数错、401 认证失败、内容审核拒绝,是「你自己的问题」,重试只会白烧 token。哪里像:都是先分类再决定动不动手,都知道「有些失败重试是徒劳的」。哪里不像:备份作业失败顶多晚个窗口,Agent 的重试还花钱——每次调用 LLM 都烧 token,失败响应消耗的 token 也是真金白银,所以 Agent 重试比备份重跑多一层成本预算的概念。

指数退避 + 抖动,就是分布式重试的错峰重跑:下游刚挂,你 1 秒后重试它还没缓过来,2 秒、4 秒逐步拉长,给它做 GC、重启、限流窗口恢复的时间——这跟指数退避在分布式系统里的用法完全同源,你在备份调度里限制「失败任务重新入队的间隔」就是它的雏形。抖动(jitter)防的是惊群效应:想象凌晨 2 点 300 个备份作业同时失败,如果调度器让它们「+60s 统一重跑」,那 60 秒后这 300 个作业会在同一毫秒再次砸向同一台存储——把它打死。给每个作业加 0~60s 的随机偏移,重试就摊开了。降级链则像多级容灾:主中心 → 同城 → 异地 → 最后人工介入。哪里不像:容灾切换是分钟级、重资产的决策,切错了回切很痛;Agent 降级是毫秒级的路由切换,成本几乎为零——所以 Agent 可以更激进地层层兜底,不用像容灾那样反复演练确认才敢切。

详细拆解

1. 错误分类(第一步,分类错了全白干)

为什么不先写重试代码?因为分类决定后面所有动作:可重试的错,退避重试;不可重试的错,重试是纯烧钱,甚至有害——比如内容审核拒绝的请求再发一遍,大概率再被拒一次,还多一次审核调用、多一份风控日志。这跟备份排障先区分「介质坏 vs 网络抖 vs 配置错」是同一个职业本能。

错误类型例子策略
可重试·瞬时超时、连接重置、502/503指数退避重试 2~3 次
可重试·限流429 Too Many Requests按 Retry-After 头等待;退避重试
不可重试400 参数错、401 认证、内容审核拒绝立即失败,上报告警,修代码/换内容
不可重试·部分模型输出格式错(JSON 解析失败)换措辞重问一次(带纠错提示),仍失败走降级

注意最后一行是 LLM 特有的灰色地带:模型没报 HTTP 错,但吐出的 JSON 缺个括号——这不是「下游坏了」,是「下游答非所问」。硬重试发一模一样的请求意义不大,正确姿势是把上次的错误信息塞回 Prompt,要求「修正格式重新输出」,相当于给模型一次自查机会;仍失败就走降级,别无限纠缠。

2. 指数退避 + 抖动(必须能写出公式)

delay = min(base * 2**attempt, max_delay) + random_jitter
# 例:base=1s → 1s → 2s → 4s(封顶 8s),每次加 0~1s 随机抖动
# 抖动的作用:300 个并发同时失败,不会在恰好 +1s 时又一起涌进来

公式拆开讲:base * 2**attempt 是等待时间按 2 的幂翻倍——第 1 次失败等 1s,第 2 次等 2s,第 3 次等 4s,意思是「每多失败一次,我就多给你一倍的时间恢复」;min(..., max_delay) 是封顶,不然第 8 次重试要等 128 秒,用户早跑了;random_jitter 是随机抖动,专治惊群——没有它,300 个并发失败的请求会在 +1s、+2s、+4s 这些精确的时间点整齐划一地杀回来,下游刚缓一口气又被同一记重拳打倒。抖动把整齐的方阵打散成散兵线,和分布式系统里给定时任务加随机启动偏移是同一个思想。

3. 预算控制

重试没有预算就是无赖。两道闸必须设:

  • 次数闸:最大重试次数(2~3 次足够,再多说明该降级了);总时长预算(如 10s,防止 3 次退避+慢响应把用户卡死);重试预算耗尽立即触发降级,不让用户干等。总时长预算跟备份窗口是一个概念——窗口就那么长,超了就砍掉低优先级任务,而不是无限拖。
  • 流量闸:重试是流量放大器。平均每个请求重试 1.5 次,意味着下游实际承受 2.5 倍 QPS——下游本来就快挂了,你的「善意重试」正在补刀。所以要全局设重试率上限(如只允许 10% 的请求在重试),超了宁可快速失败。
  • LLM 特有:token 预算——重试也是花钱的,失败响应已消耗的 token 要计入成本。一个 4k token 的请求重试 3 次,即使全失败也烧掉上万 token;放在批量 Agent 任务里,这笔账必须有人看。

4. 幂等性(重试安全的前提)

重试的本质是「同一个操作发第二次」,所以先问:这个操作发两次会怎样?读操作天然无害(查两遍天气,结果一样);写操作就危险了——下单重试两次就是两个订单。解法是幂等键(请求生成唯一 ID,服务端去重:见过这个键直接返回上次结果)。类比备份系统:同一个备份任务带同一个任务 ID,重跑时先查「这个 ID 的备份点是不是已经存在」,存在就跳过——这就是「先查后写」的幂等,和备份去重是同一个骨架。

  • 副作用操作(下单、发消息、写库)带幂等键(请求生成唯一 ID,服务端去重:见过这个键直接返回上次结果)。
  • Agent 场景:工具调用重试前检查"这一步是否可能已执行"(先查后写,或事务包裹)。

Agent 还有比传统调用更阴的场景:超时 ≠ 失败。工具调用 30 秒超时,但工具可能已经执行完了,只是响应慢——这时盲目重试就是重复执行(比如重复下单)。所以 Agent 的工具层要能「先查状态再决定重试」,和容灾切换前先探测主中心「是真死了还是脑裂」是同一类问题:响应丢失和执行失败必须区分开。

5. 降级链(重试的尽头不是报错)

预算烧完,用户的请求总得有个交代。降级链就是提前铺好的多级容灾路径,一层不行换下一层:

几个设计细节容易被追问:① 备用模型要选不同供应商——同一家挂了往往是全挂,备一份同源的等于没备,这和容灾强调「异地不同机房不同供电」的独立性是同一个道理;② 缓存/模板层返回的答案要标明「非实时」,常见问题的陈旧答案好过报错;③ 兜底层不是「系统繁忙」四个字就完事——道歉 + 记录现场 + 转人工工单,把失败变成可跟进的事件,像备份失败自动开工单一样。

6. 可观测(重试不能是黑箱)

  • 每跳重试记日志:第几次、错误类型、等待多久、结果。重试率是一个核心健康指标——某供应商重试率突然从 2% 涨到 30%,说明它要出事,熔断该上了。
  • 用户侧:适当暴露"正在重试"状态,比无限转圈体验好。

这里有个反直觉的点要主动讲出来:重试会掩盖故障。一个供应商半死不活,重试两下总能成功,于是用户没投诉、大盘没报错,你以为系统健康——直到某个峰值把重试预算也击穿,才发现它坏了一晚上。这跟备份作业「静默重跑成功掩盖了介质逐渐劣化」一模一样。防线就是两条:重试率作为一级监控指标单独告警;重试次数分布进大盘(重试 3 次才成功的请求,哪怕成功了也要计入「带伤运行」统计)。

面试官追问
Q:流式请求生成到一半失败了,怎么重试?
人话:内容已经吐给用户一半了,不能当无事发生整体重来,要么接着写,要么体面地重来。类比:像增量备份——已完成的部分不必推倒重传,从断点继续;实在续不上,就回滚成一次全量重跑,但要提前告诉用户。技术:① 断点续写:把已生成内容放进新请求,要求"接着写,不要重复",可复用流式输出的会话上下文;② 回退整体重新生成并告知用户"刚才生成中断,正在重新生成";③ 关键在副作用——失败前如果执行过工具调用(下单、写库),重试时要靠幂等键识别"已执行",绝不重执行。
Q:重试和熔断怎么配合?
人话:重试管单次请求的「再试一下」,熔断管整个下游的「先别去试了」,一个微观一个宏观,缺一不可。类比:备份作业失败重跑是重试;发现备份存储后端今天连续挂三次,暂停所有指向它的作业、切到备用后端,这就是熔断器。技术:重试失败计数汇入熔断器统计,失败率超阈值熔断打开,期间新请求不再重试、直接走降级链——防止"越重试越堵,越堵越重试"的死亡螺旋。半开状态放少量探测请求,下游恢复后熔断闭合,流量再放回来。
Q:下游已经过载了,大家都在重试,这不是火上浇油吗?怎么办?
人话:是的,重试是把双刃剑——下游过载时全员重试,流量放大几倍,能把「半死」打成「全死」,这叫重试风暴。类比:一台存储响应变慢,几百个备份作业同时超时、同时重试,QPS 瞬间翻几倍,把它彻底压垮——分布式系统里雪崩经常这么开始。技术:四层防御:① 抖动错峰;② 全局重试预算——限制同一时刻处于重试态的请求比例(如 10%),超了直接快速失败;③ 熔断兜底,失败率高的下游直接熔掉走降级;④ 退避用满,且优先遵守 429 返回的 Retry-After 头,那是下游亲口说的"我需要多久缓过来"。
Q:幂等键怎么设计?没有天然唯一 ID 的操作怎么办?
人话:有业务单号就用单号;没有就自己造一个,原则是「同一个逻辑操作,两次发送生成同一个键」。类比:备份任务的去重键 = 任务模板 ID + 目标 + 时间窗,同一个时间窗的重跑会被识别为重复,和备份去重一个思路。技术:① 调用方在发起前生成 UUID 作为键,随请求携带,重试时复用同一个键(切忌每次重试生成新键,那就失去去重意义);② 无 UUID 场景用内容哈希:操作类型 + 参数哈希 + 业务时间窗(如分钟级)做键;③ 服务端按键去重并返回上次结果;④ 键要有 TTL,过旧的键可清理——时间窗拉太长会误伤合法的重复操作(用户真的下了两单)。
Q:重试逻辑放在哪一层?Agent 编排框架、SDK 还是网关?
人话:没有标准答案,但答「都放」或「随便放」都会被追问死,要能讲清各层的分工。类比:和备份系统里「重试放作业调度层还是存储驱动层」同构——驱动层管瞬时闪断这种小重试,调度层管任务级的大重试和切备用后端。技术:推荐分层:SDK/网关层管通用瞬时错误(超时、503、429)的短平快重试,统一实现退避和抖动,业务无感;Agent 编排层管有业务语义的重试——改写 Prompt 重问、换工具、换模型、走降级链,这些 SDK 做不了。两层要约定好预算上限,避免重试叠加(每层都重 3 次 = 最多 9 次调用)。
术语卡
指数退避:等待时间 1s→2s→4s 翻倍,给下游逐级加倍的恢复时间,分布式重试的标准姿势。
抖动(jitter):每次等待加随机偏移,把整齐的重试方阵打散成散兵线,防同步风暴。
幂等键:标识「同一个逻辑操作」的唯一 ID,服务端见键去重——重试安全的前提,像备份任务 ID 防重复备份。
Retry-After:429/503 响应里服务端建议的等待秒数,是下游亲口报的恢复时间,优先于自己的退避公式。
熔断器:失败率超阈值就「跳闸」,期间请求不再重试直接降级——重试的宏观刹车,防死亡螺旋。
惊群效应:大量客户端在同一时刻被同时唤醒/重试,集体砸向同一下游——抖动存在的原因。
