工程实践 · Q6

如何实现 Agent 的异常重试机制?

⭐⭐⭐⭐ #异常处理#重试#Agent
30秒电梯稿

"先给错误分类:超时/限流/5xx 可重试,4xx 参数错误/内容审核拒绝重试也没用;可重试的用指数退避 + 随机抖动(防止集体重试形成风暴),设最大次数和总时长预算;副作用操作先做幂等(幂等键);重试耗尽走降级链:备用模型 → 缓存结果 → 兜底话术+转人工。重试的每一跳都要打日志,不然问题被重试掩盖了都不知道。"

通俗类比

打电话:没人接(超时)→ 等一会儿再打,越等越久(指数退避);对方在通话中(限流)→ 挂了过两分钟再打;号码不存在(参数错误)→ 打一百遍也没用,赶紧检查号码;全公司同一时刻都在重拨,交换机炸了(重试风暴)→ 所以每个人加个随机等待(抖动);实在找不到人,找他同事转达(降级)。

详细拆解

1. 错误分类(第一步,分类错了全白干)

错误类型例子策略
可重试·瞬时超时、连接重置、502/503指数退避重试 2~3 次
可重试·限流429 Too Many Requests按 Retry-After 头等待;退避重试
不可重试400 参数错、401 认证、内容审核拒绝立即失败,上报告警,修代码/换内容
不可重试·部分模型输出格式错(JSON 解析失败)换措辞重问一次(带纠错提示),仍失败走降级

2. 指数退避 + 抖动(必须能写出公式)

delay = min(base * 2**attempt, max_delay) + random_jitter
# 例:base=1s → 1s → 2s → 4s(封顶 8s),每次加 0~1s 随机抖动
# 抖动的作用:300 个并发同时失败,不会在恰好 +1s 时又一起涌进来

3. 预算控制

  • 最大重试次数(2~3 次足够,再多说明该降级了);总时长预算(如 10s,防止 3 次退避+慢响应把用户卡死);重试预算耗尽立即触发降级,不让用户干等。
  • LLM 特有:token 预算——重试也是花钱的,失败响应已消耗的 token 要计入成本。

4. 幂等性(重试安全的前提)

  • 副作用操作(下单、发消息、写库)带幂等键(请求生成唯一 ID,服务端去重:见过这个键直接返回上次结果)。
  • Agent 场景:工具调用重试前检查"这一步是否可能已执行"(先查后写,或事务包裹)。

5. 降级链(重试的尽头不是报错)

6. 可观测(重试不能是黑箱)

  • 每跳重试记日志:第几次、错误类型、等待多久、结果。重试率是一个核心健康指标——某供应商重试率突然从 2% 涨到 30%,说明它要出事,熔断该上了。
  • 用户侧:适当暴露"正在重试"状态,比无限转圈体验好。
面试官追问
Q:流式请求生成到一半失败了,怎么重试?
不能盲目整体重试(已推送的内容用户看了一半)。策略:① 断点续写——把已生成内容放进新请求,要求"接着写,不要重复";② 或回退到"重新生成"并告知用户;幂等键防重复副作用(比如已执行的工具调用不重执行)。
Q:重试和熔断怎么配合?
重试是微观(单请求韧性),熔断是宏观(系统保护);重试失败计数汇入熔断器统计,熔断打开期间新请求不再重试直接走降级——防止"越重试越堵,越堵越重试"的死亡螺旋。
术语卡
指数退避:等待时间 1s→2s→4s 翻倍。
抖动(jitter):随机偏移,防同步风暴。
幂等键:去重重复操作的唯一标识。
Retry-After:限流响应里的建议等待时间。
