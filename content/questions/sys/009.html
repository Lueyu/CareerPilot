Agent核心 · Q30

多轮对话上下文状态管理是如何做的？如何在高并发场景下保证一致性？

⭐⭐⭐ #状态管理#并发一致性#会话 字节(真题)
30秒电梯稿

"核心是状态外置 + 会话隔离:对话历史、槽位状态统一存 Redis(key = session_id),Agent 本身无状态、可水平扩展。一致性靠三点:① 每会话串行化——同一会话的写操作加锁/单队列,保证顺序;② 版本号 + 乐观锁(CAS)防并发覆盖;③ 关键业务状态走状态机/事务。上下文管理上区分"给程序的持久状态"(结构化)和"给模型的上下文"(摘要+窗口压缩),并设 token 预算——状态要小、要能迁移、要版本化。"

通俗类比

就像餐厅一桌客人的点菜本:每桌一张点菜单(会话状态),服务员的脑子不记菜(无状态),谁都能拿这桌的菜单继续服务(水平扩展)。客人催菜时,服务员先翻菜单看点到哪了(读状态),加菜就往上写(写状态)。如果两个服务员同时往同一张单子上加菜,容易覆盖——所以规定"一桌同一时刻只一个服务员动笔"(串行化),或写之前看版本号对得上才写(乐观锁)。菜上完,菜单归档(持久化),客人下次来能查历史(恢复)。

详细拆解

1. 存什么:上下文的两种形态(关键区分)

  • 给程序的状态(结构化):意图、槽位、工具执行结果、迭代计数——确定性、可校验。
  • 给模型的上下文(自然语言):对话历史(可能被摘要/裁剪)、工具结果——喂给 LLM。
  • 二者分离:结构化状态做持久化与并发控制,模型上下文是它的"投影"。

2. 存哪:存储选型

存储存什么理由
Redis热状态(当前会话历史+槽位)亚毫秒、TTL、原子操作
PostgreSQL/MongoDB冷历史/审计持久、可查询
对象存储大对象引用状态本体保持小
  • key:state:{tenant_id}:{session_id},TTL 会话级(如 7 天),活跃续期。

3. 上下文压缩(token 预算)

  • 窗口裁剪:只保留最近 N 轮,更早的做摘要。
  • 分层:原始历史 + 滚动摘要 + 长期记忆(关键事实向量化检索)。
  • 预算控制:给"系统 prompt + 历史 + 工具结果"设总 token 上限,超了就摘要,再超就丢最旧。

4. 高并发一致性(核心考点)

  • 每会话串行化:同一 session 的消息按到达顺序排队处理(分布式锁 SETNX 或按 session hash 分区到单队列),不同 session 天然并行——既保证一致性又保吞吐。
  • 乐观锁/CAS:读状态带版本号,写回时比对版本,不一致说明有并发写,重试或合并。
  • 原子操作:用 Redis Lua/事务把"读-改-写"合并为原子,避免竞态窗口。
  • 关键业务状态:订单/退款等用状态机 + 事务,状态迁移幂等(带版本/乐观锁)。
# 乐观锁更新(Redis Lua 保证原子性)
cur = GET key
new = transform(cur)          # 追加消息 / 改槽位
# 仅当版本仍为 cur.version 时才写入,否则重试
if CAS(key, cur.version, new): done
else: retry from GET

5. 状态版本化与恢复

  • 状态 schema 带版本号,代码升级时跑迁移函数;反序列化宽容(缺字段给默认值)。
  • 恢复:从 checkpoint 重放;LLM 重放不确定 → 恢复点选"已完成的节点",已执行的副作用标记跳过。

6. 高并发的经验值

  • 无状态 Agent + Redis 状态,单机数千并发不难;瓶颈常在下游 LLM/工具,而非状态读写。
  • 热 key(高频活跃会话)本地缓存 + 定期同步;写多读多时用分片 + 每会话单写者。
面试官追问
Q:同一用户并发发两条消息,怎么定顺序?
语义上对话有先后,应按到达顺序串行。实现:网关给每条消息打递增序号,进入按 session 分区的队列,消费者按序处理;或同一 session 的请求路由到同一处理单元加锁。若必须真并发,则处理后按序号合并,冲突字段以最后序号为准并记录。
Q:状态存 Redis,Redis 挂了怎么办?
分层:Redis 挂不影响"服务可用",降级为"该会话失忆"(提示用户重述)+ 写 DB 冷备异步兜底;用 Redis 主从/哨兵/集群保可用。关键业务状态(订单)不以 Redis 为唯一真相源,DB 才是真相源,Redis 只是缓存——缓存丢了能重建。
Q:上下文很长,摘要会丢关键信息怎么办?
摘要只压缩"背景/已办事项",关键事实(订单号、金额、用户明确要求)用结构化槽位单独存、永不摘要;摘要用"抽取式要点 + 生成式压缩"结合,重要信息先抽取再压缩;长期记忆走向量检索,按需召回,而不是全塞进摘要。
术语卡
乐观锁(CAS):写回时比对版本号,冲突则重试。
分布式锁:跨进程保证同一时刻只有一个写者。
无状态服务:会话状态外置,服务器可随意扩缩容。
滚动摘要:只保留最近对话 + 更早内容的摘要。
状态机:限定状态合法迁移,业务一致性基础。
