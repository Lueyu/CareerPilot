工程实践 · Q9

如何实现 LLM 响应的流式处理?

⭐⭐⭐⭐ #流式处理#WebSocket#SSE
先说人话:这题问的是:AI 的答案怎么一个字一个字往外蹦,而不是憋二十秒整段甩出——这条「逐字管道」怎么搭、生产上怎么不翻车。面试官爱考,因为 demo 五分钟就能写,断线续传、取消止损、代理缓冲这些坑只有真上过线才踩得到;张口就『上 WebSocket』的,多半没想过这是单向推送。
30秒电梯稿

"先定方向:推答案是单向场景,首选 SSE 而不是 WebSocket。后端把 LLM 的流式输出包装成异步生成器逐块 yield,事件按类型设计(status/sources/delta/done/error);客户端断开要向上游传播取消(省 token 钱);断线重连用 Last-Event-ID 续传(浏览器 EventSource 原生自动重连);反向压力靠生成器「拉取」模型的天然机制缓解;上线前记得关 Nginx buffering——最常见的翻车点,没有之一。语音、双向协作这类真双向场景才用 WebSocket。"

通俗类比

先搞懂「流式」到底在优化什么(用备份管道想):传统接口是「全量交付」——后端等 LLM 把整段答案生成完,再一次性打包返回,像先把整个库 dump 成一个大文件才开始传输;流式输出是「边产边传」——生成一个词就推一个词,像备份作业边读源端边写磁带的流式管道,数据不在内存里过夜。核心洞察:用户感知的是首字时间 TTFT,不是总时长——总生成时间一毫秒没少,但第一个字 300ms 就蹦出来,用户就觉得「它在干活」;这和容灾里大家在意「系统多久能重新登录」而不是「后台数据还要校验多久」是同一个逻辑。哪里像:都是把「整体完成」拆成「第一份可用的尽快送到」。哪里不像:备份做流式是为了内存和吞吐(机器受益),LLM 做流式几乎纯粹为了感知延迟(人受益)。

整套方案像「电台 + 断点续听」:SSE 像广播电台:你打开收音机(建立连接),台里说一句你听一句,节目播完自动挂断;中途信号断了,回来报「上次听到第几条」,从断点续播(Last-Event-ID)。这套语义你在存储侧天天见:单向推送 + 断点续传 + 心跳保活——EventSource 断线自动重连并带上最后事件的 id,像备份作业中断后从上次 checkpoint 续传增量,而不是推倒重来一次全量;每 15 秒一发的心跳注释行,就是集群的心跳包,防中间的代理/负载均衡误判「这连接闲置了」把它掐掉。WebSocket 则像打电话——双向都能说,但你要维护整通电话的状态,对应双向同步复制:贵,而且单向推答案用不上。哪里像:单工/双工、断点、心跳这套语义完全同构。哪里不像:备份断点续传续的是数据块,源头还在、随时能重读;LLM 生成是一次性的——上游调用一断就没法「接着生成」,只能把已生成的半截暂存到 Redis 续发,这是设计续传时最容易想错的地方。

详细拆解

第 0 步:先选协议(方向决定一切)

判据就一个问题:客户端要不要在收流的同时、高频地往回发消息?不要——单工,上 SSE;要——才上 WebSocket。别为了 10% 的双向需求,上 100% 的复杂度。

方案方向底层断线重连基础设施友好度适用场景
短轮询客户端拉普通 HTTP 请求天然(每次新请求)高低频状态查询
SSE服务端推(单工)一条 HTTP 长连接EventSource 原生自动 + Last-Event-ID中(要关代理缓冲)推答案/进度/日志
WebSocket双向(双工)HTTP Upgrade 升级出的独立协议要自己写低(代理/LB 要额外配)语音对话/多人协作

选 SSE 还有一层隐藏红利:它本质就是普通 HTTP 响应(靠 chunked 分块传输),鉴权头、网关、CDN 整套生态直接复用;WebSocket 这些都得自己搬。整条链路先看清楚再动工:

一次流式问答的完整旅程:

 ① 建流   浏览器 ──POST /chat──→ Nginx ──→ FastAPI ──astream()──→ 上游 LLM
 ② 出字   LLM 每生成一个词 → FastAPI yield 一条 SSE 事件 → Nginx 透传 → 浏览器逐字渲染
 ③ 保活   FastAPI 每 15s 补一行注释 ": ping",防中间设备掐掉"看似空闲"的连接
 ④ 收尾   上游结束 → 发 data:{"type":"done"} → 连接关闭
 ⑤ 断开   用户中途关页面 → 连接关闭 → FastAPI 收到 CancelledError → abort 上游,止损 token

 每一跳都是坑位:Nginx 默认攒缓冲(②失效)、网关默认空闲超时(③防的就是它)、
 上游不取消(⑤失效,token 白烧)——生产化就是逐跳把这些默认值改掉。

1. 服务端实现(FastAPI 示例,能写出来更佳)

用 FastAPI 的异步生成器把上游流「接」过来再「转」出去,核心不到 20 行:

@app.post("/chat")
async def chat(req: ChatRequest):
    async def gen():
        try:
            async for chunk in llm.astream(req.messages):  # 上游流式
                data = {"type":"delta","text":chunk.text}
                yield f"data: {json.dumps(data)}\n\n"
            yield f"data: {json.dumps({'type':'done'})}\n\n"
        except asyncio.CancelledError:
            # 客户端断开:传播取消,停止上游生成,省token!
            raise
        except Exception as e:
            yield f"data: {json.dumps({'type':'error','msg':str(e)})}\n\n"
    return StreamingResponse(gen(), media_type="text/event-stream")

代码走读(面试最好能背着讲出这三个点):

  • llm.astream():上游 SDK 的异步流式接口,来一个 chunk 迭代一次——整条链路从「等全文」变成「拉一块、转一块」,这是流式的根。
  • StreamingResponse + text/event-stream:把生成器的每个 yield 原样写进响应体。对服务端来说 SSE 没有新协议,就是「响应头对 + 格式对」的普通流式 HTTP 响应。
  • except CancelledError: raise 是全段最值钱的三行。客户端断开时,asyncio 向生成器抛入取消信号,这里必须 raise 传播出去(吞掉它 = 取消了作业单但底层进程还在跑):async for 循环被拆除、上游连接关闭、后续 token 不再计费。类比备份:作业被取消必须 kill 底层读取进程,否则源端还在白读。

事件协议设计——就是给这条流定「报文格式」,和备份日志定级别一个道理:

事件类型触发时机载荷备份世界的对应物
status生成开始前阶段描述(检索中/生成中)作业状态:running
sources检索完成(RAG 场景)引用文档列表备份 manifest 清单
delta上游每来一个词增量文本增量数据块
done上游正常结束用量统计(token 数/耗时)作业完成报告
error任何环节异常错误信息作业失败事件

2. SSE 协议要点

线上抓包就是这副样子(注意 data: 前缀 + 双换行,一个事件一整块):

HTTP/1.1 200 OK
Content-Type: text/event-stream
Cache-Control: no-cache

id: 41
event: status
data: {"type":"status","phase":"generating"}

id: 42
data: {"type":"delta","text":"你"}

id: 43
data: {"type":"delta","text":"好"}

: ping
  • HTTP 响应头:Content-Type: text/event-stream + 禁缓存;data: 前缀 + 双换行分隔事件;id: 字段给事件编号(供续传)、event: 字段区分类型。
  • 心跳:每 15s 发一行注释(: ping\n\n),防中间代理掐掉"看似空闲"的连接。为什么是 15s?很多网关空闲超时默认 60s,心跳就是主动报「我还活着」——和集群心跳防误判下线一个用途。另外 retry: 字段还能让服务端建议客户端的重连间隔(毫秒)。

3. 断线重连与续传

这一段是「流式 demo」和「流式生产」的分水岭,客户端断线后服务端怎么接,要提前设计:

  • 浏览器 EventSource 原生自动重连,并带上最后事件的 id(Last-Event-ID 请求头);服务端把已生成内容存 Redis,断点续发;LLM 调用已中断就返回半截结果 + 完整状态标记。
  • 断线瞬间,服务端有两种姿势,要主动选:①「后台续跑」——检测到断开不取消上游,让生成继续写进 Redis(作业降级为后台任务),客户端几秒内重连就从断点补发,体验无缝;②「立即止损」——直接 abort 上游,重连后返回半截 + incomplete 标记,省钱。高频短断线选①,长答案且 token 敏感选②。类比备份:作业断了,是「后台继续跑、重连看进度」还是「杀掉作业、保留部分成果」——这是个明确的策略选择,不能靠默认值。
  • Last-Event-ID 就是 checkpoint/offset:每个 delta 带递增 id,断线后客户端报最后一个 id,服务端从 Redis 补发之后的——事件粒度的 checkpoint,断线最多丢「正在路上」的那一个事件,RPO 趋近于零,代价是每个事件都要落一次暂存。
  • 大坑:原生 EventSource 只能发 GET,而 /chat 通常要 POST(消息体 + 鉴权头)。两条出路:① 前端放弃 EventSource,用 fetch 流式读响应体,自己按「data: 前缀 + 双换行」解析,重连逻辑自己写(有现成库);② 接口拆两步——POST /chat 创建会话拿 id,GET /chat/{id}/stream 用 EventSource 收流,会话状态放 Redis。能把 GET 限制说出来的,是真对接过前端的。

4. 背压

背压(backpressure,存储人再熟悉不过)——消费方慢了,要能反向拖住生产方。备份里:源端读得飞快、磁带写得慢,写缓冲一满就反压读端限速,否则要么撑爆内存要么丢数据。这里同理:

  • 生成器是"客户端拉取"模型,天然背压:客户端读得慢,迭代慢,上游 chunk 在缓冲等待,不会撑爆内存;要警惕的反而是上游 LLM 到服务端这一段不要用无界缓冲无脑拉。
  • 这条「反压链」在 asyncio 里靠挂起实现:客户端读得慢 → ASGI 服务器写 socket 变慢 → 它不再向 gen() 要下一块 → yield 处挂起 → async for 不再向上游拉 chunk → 整条链自动限速。和磁带机「写满就阻塞读端」是同一个物理直觉,只是实现从「缓冲水位」换成了「协程挂起」。
  • 反面教材:图省事把上游所有 chunk 先收进一个 list、拼完再返回——无界缓冲,等于把整个备份集先堆进内存暂存区再倒给磁带,长答案高峰直接 OOM。自己包转发层时同理:别用「后台任务 + 无界队列」把生产者消费者解耦——解耦之后背压就断了;队列要有界,满了就挂起生产者。

5. 基础设施坑(实战经验值)

流式服务上线翻车,九成翻在中间的基础设施——它们的设计假设是「普通请求快进快出」,和长连接流式天然打架:

  • Nginx 反代必须 proxy_buffering off(否则攒满缓冲才发,流式失效);超时配置 read timeout 拉长(生成长答案要几分钟)。为什么 Nginx 默认要攒?对普通接口,攒一批再发减少小包开销,是优化;对流式,「攒」意味着用户盯着空白屏。两种关法:配置里 proxy_buffering off,或应用侧响应头加 X-Accel-Buffering: no(Nginx 认这个头):
location /chat {
    proxy_pass http://llm_backend;
    proxy_buffering off;            # 关键:不攒缓冲,来一块转一块
    proxy_cache off;
    proxy_http_version 1.1;
    proxy_set_header Connection ""; # 长连接不被反复掐建
    proxy_read_timeout 300s;        # 长答案生成可能要几分钟,默认 60s 会掐
}
  • 网关/CDN 是否支持长连接要验证;负载均衡选 ip_hash 或会话粘性(或无状态化+Redis 续传)。要逐跳排查:每一跳(网关、CDN、sidecar)都可能有默认缓冲或空闲超时,像备份链路里每台中转机都有自己的暂存策略,得逐台过。粘性的根因:SSE 是有状态连接,重连被 LB 轮询打到另一台机器,那台没有你的会话;要么粘住,要么把会话状态外置到 Redis(推荐,和备份元数据外置到独立库一个思路)。
  • 压测要专门测"长连接堆积"(1 万并发 SSE,连接数/FD/内存都要监控)。注意压测指标变了:普通接口看 QPS,流式看「峰值同时挂着的连接数」——1 万用户平均看 30 秒答案,峰值就是 1 万条长连接,吃的是 FD(ulimit)、每连接缓冲、内存。这和备份窗口里算「峰值并发作业数」而不是「日作业总量」是同一张表。

6. WebSocket 什么时候用:判据就一条——客户端要不要在收流的同时高频往回发消息。要,才上:语音对话(边听边说)、多 Agent 多人协作画板(多方实时互推状态)、需要客户端高频推送指令的场景。纯"服务端推答案"SSE 足够——协议简单、复用 HTTP 生态、自带重连语义;为双向需求把升级握手、心跳、重连、代理适配全自己搬一遍,不划算。

收个尾:这道题的高分信号不是「会写生成器」,而是能主动说出「Nginx buffering、取消传播、EventSource 只支持 GET」这三个坑里的任意两个——每一个都是真上过线才踩得到的疤。

面试官追问
Q:生成到一半用户关页面,token 已经烧了多少?
人话:已经烧掉的要不回来,但后面的能止损——关键看「取消」有没有传播到上游;不传播,人走了作业还在空跑,烧的全是真金白银。类比:备份作业被取消,如果只删了作业记录、不 kill 底层进程,源端还在白读、磁带还在白写;连接断开也只是「作业单没了」,底层生成还在跑。技术:客户端断开 → ASGI 服务器向生成器抛 asyncio.CancelledError → except 里必须 raise 而不是吞 → async for 被拆除 → 上游连接关闭、生成停止;再配 max_tokens 上限防单次跑飞。高频场景这笔账非常大:取消若全部失效,月底账单能吓死人。
Q:怎么测试流式接口?
人话:分三层——肉眼看流、自动验格式、压测扛连接;漏哪层,上线就翻在哪层。类比:像验收一条备份管道:先小文件看进度条走不走,再自动校验恢复数据的完整性,最后满负荷并发作业压一轮。技术:① curl -N 直连后端看逐块输出,再过一层 Nginx 对比——buffering 没关立刻现形;② 自动化断言事件序列:delta 按序拼接完整、done 收尾、模拟上游 500 时走 error 事件而不是挂死;③ 压长连接堆积(并发连接数/FD/内存),加断连恢复用例:中途掐线,重连后按 Last-Event-ID 续传不丢字。
Q:你的 /chat 是 POST,但 EventSource 只支持 GET,前端怎么收流?
人话:撞上的是 SSE 最著名的限制——原生 EventSource 发不了 POST,也带不了自定义鉴权头。类比:就像老备份客户端只会从拉取通道取数据,你要带请求体过去,就得在前面加一步「登记、拿凭证」。技术:两条路:① 放弃 EventSource,用 fetch 流式读响应体(ReadableStream),自己按「data: 前缀 + 双换行」解析,重连和 Last-Event-ID 自己实现(有现成库如 fetch-event-source);② 接口拆两步:POST /chat 创建会话返回 id,GET /chat/{id}/stream 用 EventSource 收流,会话状态放 Redis。
Q:一万个用户同时在线看 AI 逐字吐答案,服务端最该盯什么?
人话:流式系统的压力不是 QPS,是「峰值同时挂着的连接数」——答案越长、用户越多,长连接堆得越高。类比:和备份窗口规划同一个逻辑:要算的不是一天多少作业,而是峰值时刻同时在跑的作业数,吃的是并发资源不是总量。技术:盯并发连接数、FD(ulimit -n)、每连接内存、网关/LB 的连接上限与空闲超时;ASGI 协程模型单进程扛几千长连接可行,但要压测验证;配心跳防空闲误杀;容量按「峰值并发连接 × 平均时长」估,和估备份窗口占用同一张表。
术语卡
SSE:Server-Sent Events,基于一条 HTTP 长连接的服务端单向推送标准,自带重连语义。
EventSource:浏览器原生 SSE 客户端,断线自动重连并带 Last-Event-ID,但只支持 GET。
Last-Event-ID:重连时带回的最后事件编号,连接世界的 checkpoint——断点续传全靠它。
背压:消费方慢了反向拖住生产方的机制,防无界缓冲撑爆内存——磁带机限速的软件版。
心跳:周期性保活信号,防中间设备把「看似空闲」的长连接掐掉,同集群心跳。
proxy_buffering:Nginx 攒上游响应的开关,流式场景必须关,否则攒满缓冲才转发。
WebSocket:全双工消息协议,HTTP Upgrade 握手升级;真双向场景(语音/协作)才值得上。
