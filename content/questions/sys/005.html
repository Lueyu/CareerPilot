工程实践 · Q9

如何实现 LLM 响应的流式处理?

⭐⭐⭐⭐ #流式处理#WebSocket#SSE
30秒电梯稿

"首选 SSE:后端把 LLM 的流式输出包装成异步生成器逐块 yield,事件按类型设计(status/sources/delta/done/error);客户端断开要向上游传播取消(省 token 钱);断线重连用 Last-Event-ID 续传;反向压力靠生成器天然拉取模型缓解;上线前记得关 Nginx buffering——这是最常见的翻车点。语音/双向场景才用 WebSocket。"

通俗类比

SSE 像广播电台:你打开收音机(建立连接),台里说一句你听一句,说完了节目结束(自动挂断);中途信号断了,回来可以从"上次听到第几条"续播(Last-Event-ID)。WebSocket 则像打电话——双向都能说,但维护成本高。日常听广播的场景(推答案)没必要打电话。

详细拆解

1. 服务端实现(FastAPI 示例,能写出来更佳)

@app.post("/chat")
async def chat(req: ChatRequest):
    async def gen():
        try:
            async for chunk in llm.astream(req.messages):  # 上游流式
                data = {"type":"delta","text":chunk.text}
                yield f"data: {json.dumps(data)}\n\n"
            yield f"data: {json.dumps({'type':'done'})}\n\n"
        except asyncio.CancelledError:
            # 客户端断开:传播取消,停止上游生成,省token!
            raise
        except Exception as e:
            yield f"data: {json.dumps({'type':'error','msg':str(e)})}\n\n"
    return StreamingResponse(gen(), media_type="text/event-stream")

2. SSE 协议要点

  • HTTP 响应头:Content-Type: text/event-stream + 禁缓存;data: 前缀 + 双换行分隔事件;id: 字段给事件编号(供续传)、event: 字段区分类型。
  • 心跳:每 15s 发一行注释(: ping\n\n),防中间代理掐掉"看似空闲"的连接。

3. 断线重连与续传

  • 浏览器 EventSource 原生自动重连,并带上最后事件的 id(Last-Event-ID 请求头);服务端把已生成内容存 Redis,断点续发;LLM 调用已中断就返回半截结果 + 完整状态标记。

4. 背压

  • 生成器是"客户端拉取"模型,天然背压:客户端读得慢,迭代慢,上游 chunk 在缓冲等待,不会撑爆内存;要警惕的反而是上游 LLM 到服务端这一段不要用无界缓冲无脑拉。

5. 基础设施坑(实战经验值)

  • Nginx 反代必须 proxy_buffering off(否则攒满缓冲才发,流式失效);超时配置 read timeout 拉长(生成长答案要几分钟)。
  • 网关/CDN 是否支持长连接要验证;负载均衡选 ip_hash 或会话粘性(或无状态化+Redis 续传)。
  • 压测要专门测"长连接堆积"(1 万并发 SSE,连接数/FD/内存都要监控)。

6. WebSocket 什么时候用:双向实时——语音对话、多 Agent 多人协作画板、需要客户端高频推送指令的场景。纯"服务端推答案"SSE 足够。

面试官追问
Q:生成到一半用户关页面,token 已经烧了多少?
必须靠取消传播止损:连接断开事件 → CancelledError → 调用上游 abort;不处理的话一次几万 token 的生成会跑完,高频场景月底账单能吓死人。同时建议:上下文很大时设"生成上限",防止跑飞。
Q:怎么测试流式接口?
curl -N 直连看逐块输出;自动化测试断言事件序列(delta 顺序、done 收尾、error 路径);压测长连接数和断连恢复。
术语卡
EventSource:浏览器原生 SSE 客户端。
心跳:空注释行防空闲断连。
proxy_buffering:Nginx 攒响应开关,流式必关。
