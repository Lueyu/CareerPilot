Agent核心 · Q17

如果你要在 GPU 资源有限的条件下同时提供推理和微调服务，如何做资源分配和任务调度以保证时延和吞吐？

⭐⭐⭐⭐ #资源管理#调度策略 字节(真题)
先说人话:一批 GPU 既要跑「用户在线等答案」的推理,又要跑「几小时才跑完」的微调,这题问的是卡怎么分、谁给谁让路。面试官爱考它,因为一题同时压住资源隔离、优先级调度、SLA 取舍三块工程判断;答「加卡」「排个队就行」的,直接暴露没在资源真紧张的环境里救过火。
30秒电梯稿

"这套打法你在备份行业见过一模一样的:生产流量优先,跑批作业让路。核心原则:在线推理 SLA 优先,离线微调低优先级、可抢占。资源上用 MIG 或显存配额做切分隔离;调度上给推理配高优先级,微调支持抢占式调度——推理流量上来,微调自动降速/暂停并落 checkpoint;微调侧用 QLoRA/PEFT 把显存压进单卡;推理侧用动态批处理 + 量化小模型提吞吐;再加弹性扩缩容:闲时把卡还给训练,忙时收回,夜间低谷就是微调的全力窗口。"

通俗类比

整个局面你在备份容灾这行天天见:一套机器既要跑生产交易(慢一秒都是事故),又要塞进备份跑批(晚两小时没人报警)。行业规矩立了几十年:生产永远优先;备份作业可暂停、可限速、可断点续传;时间上往夜间低谷挪。这道题就是同一道题换了硬件:推理 = 生产系统(用户在屏幕前等,慢了就是 SLA 事故);微调 = 备份作业(本质是离线批处理,没有任何实时性可言,它全部的「本钱」就是可以让路)。

每个机制都能在存储/备份世界找到原型:MIG = 在阵列上给备份划独立 LUN——硬件级切片,容量和带宽各用各的,谁也挤不到谁;显存配额 = 软件层限额,灵活,但底层盘子还是同一块,带宽照样会争;抢占 + checkpoint = 断点续传——作业跑到 70% 被叫停,存进度,回头从 70% 接着跑,而不是推倒重来;QLoRA = 增量备份——几十 GB 的「全量」基座冻结不动,只训一小片适配器参数,要搬的数据量小一个数量级;动态批处理 = 把碎小 IO 攒成大块顺序写——吞吐上去了,代价是攒批要等;夜里把卡还给微调 = 备份窗口——只不过反着用:白天是生产窗口,夜里是训练窗口。

哪里像:两道题问的都是「实时活和跑批活怎么塞进一套资源」,答案骨架完全一致——优先级 + 隔离 + 可中断 + 错峰。哪里不像:备份限速是「平滑变慢」——IO 打八折,作业还是稳稳在跑;GPU 共享的争抢是「断崖式」的——显存是硬上限,挤爆直接 OOM 崩给你看,而且时间片级别的算力争抢会让推理延迟周期性地抖。所以 GPU 侧要更强调硬隔离和主动让路,不能指望「大家都克制一点」。

详细拆解

1. 先把矛盾讲透(这是这道题的立意)

在线推理和离线微调要的东西天然相反:推理要低时延、稳波形——用户在屏幕前等,P99 一抖就是 SLA 事故,所以它讨厌任何「卡一下」;微调要长时独占、吃满算力——一个任务跑几小时到几天,GPU 利用率越高越好,它最讨厌被打断。两者抢的是同一批卡的算力(SM 计算时间)和显存(HBM 容量)。硬凑在一起的两种典型死法:① 微调一个大 batch 把显存占满,推理请求一来就 OOM;② 两个任务在算力上互相踩,推理延迟每隔几百毫秒抖一下,P99 直接不可用。所以答案的骨架是四件套:隔离 + 优先级 + 抢占 + 弹性——先把这四个词摆出来,面试官就知道你懂这题在考什么,而不是背了一堆工具名。

2. 资源隔离方案(对比选型)

方案粒度特点适用
MIG 硬隔离物理切分 GPU显存/算力强隔离,互不干扰A100/H100,固定配比
显存配额逻辑限制灵活但算力仍可能争抢显存是主要瓶颈时
容器 + 时间片K8s 调度按时间/权重轮换多任务混合

选型口诀:要硬隔离、且卡支持(A100/H100 这类)→ MIG,显存、算力、缓存带宽物理分开,推理和微调互不干扰,代价是切分配比固定,白天夜里不能动态改;卡不支持 MIG → 显存配额 + 调度让路,给每个进程设显存上限,算力层面靠优先级压制;任务又多又杂 → 用 K8s 统一编排。这里有个容易被追问的点:显存配额只管得住「容量」,管不住「算力」——算力争抢不会被配额消除,只能靠抢占或降频兜底,这和你在存储上「限了 IOPS 却限不住别人占缓存」是同一个道理。

3. 调度策略(优先级 + 抢占 + 弹性)

  • 优先级:推理 = 在线服务,SLA 一票否决,永远优先;微调 = 批处理任务,可延迟、可中断。判断依据很朴素:推理挂了是事故,微调晚两小时是排期问题——优先级就是按「故障的痛感」排的,和你们「生产系统压过一切」的铁律同源。
  • 抢占式调度:推理需要算力/显存时,微调任务被挂起——先发优雅停止信号,让任务落好 checkpoint 再释放 GPU,忙完从 checkpoint 恢复。这比「杀掉重跑」省的不是一点半点:重跑浪费的是几小时的算力,断点恢复只浪费最近一个保存间隔——断点续传和「整个作业重跑」的差距,你太熟了。
  • 弹性:按推理 QPS 的历史曲线做预测,低谷期把空闲卡划给训练,高峰期收回;K8s 或云上弹性实例都能落地。细节上别忘排水:收卡之前先停止派新任务、等存量请求跑完,和「节点下线前先从负载均衡摘除」是同一个操作习惯。
一天的卡归属规划(把"备份窗口"反过来用):

时间轴   0点 ────── 7点 ════════ 12点 ════════ 19点 ── 22点 ────── 24点
推理QPS   低谷          ↑午高峰            ↑晚高峰        回落      低谷
GPU归属   [微调全力]    [推理优先 · 微调暂停/低速陪跑]    [逐步还给微调]

抢占触发(信号驱动,不拍脑袋):
  推理队列等待 > 高水位   ──→  发"优雅停止"信号 → 微调落 checkpoint → 让出显存
  推理队列持续 < 低水位   ──→  从最近 checkpoint 恢复微调
  (高低水位之间留迟滞区间:流量在中间晃不触发动作,防止任务反复横跳)

4. 微调侧省显存(让离线"挤得进去")

  • QLoRA/PEFT:基座量化到 4-bit 冻结,只训低秩适配器(LoRA),把全参微调的显存需求压 1~2 个数量级——7B 模型全参微调要几十 GB,QLoRA 下一张 24GB 的卡就能跑。这正是「增量备份」思想:全量大文件不动,只维护一小份可变的增量。
  • 梯度累积 + 小 batch:降低瞬时显存峰值,拿训练吞吐换显存余量——微调本来就是离线活,慢一点是它最便宜的让路方式。
  • 定期 checkpoint:每 N 步或每 N 分钟落一次盘,这是"可被抢占"的前提——保存间隔越短,被抢占时损失的进度越少;代价是落盘开销,按「丢多少步能接受」来定间隔,而不是随手一设。

5. 推理侧保时延 + 提吞吐

  • 动态批处理(工业界演进形态叫 continuous batching,出自 Orca 论文):把并发请求攒成 batch 一起算,GPU 利用率和吞吐显著上升;但 batch 大 → 排队久 → 时延高,所以必须按 SLA 反推最大 batch 和最长排队,发车策略用「攒到上限或超时(比如 5ms)就发车」,而不是死等凑满。
  • 量化 / 蒸馏小模型:显存和算力占用小,同一张卡能并发更多请求——降低单请求成本,等于变相扩容。
  • 模型分级:简单请求路由到小模型,复杂请求才上大模型,把最稀缺的算力留给真正需要的请求——和存储分层(热数据上 SSD、冷数据下 HDD)是同一个思路。

6. 保证 SLA 的最后一道:对推理做严格的并发上限和队列超时;一旦算力吃紧,宁可对新请求返回排队提示或降级到小模型,也不让已接受请求的时延失控。这是「保时延优先于保吞吐」的取舍:吞吐掉了损失的是成本,时延炸了损失的是用户和 SLA。这和你熟悉的过载保护完全同构——系统满负荷时,拒绝比拖垮体面。

常见翻车点(主动说出来是加分项):① 不做隔离直接混跑——微调一个 memory spike 就把推理打挂;② 抢占用 kill -9 而不是优雅信号——checkpoint 写一半损坏,恢复直接失败;③ checkpoint 间隔太长——一次抢占丢几小时进度,下次没人敢再抢它,抢占机制名存实亡;④ batch 一味拉满冲吞吐——吞吐报表好看,P99 全线超标。每一条都对应「备份塞进生产环境」里踩过的同类坑,你全有现成经验可以对照。

面试官追问
Q:抢占微调时,训练进度会丢吗?
人话:会丢,但只丢「最近一个保存间隔」,设计得好可以小到忽略——前提是抢占必须「优雅」,不能硬杀。类比:备份作业被生产打断,断点信息落了盘就能续传;进程被 kill -9 强杀,断点文件可能写了一半就损坏,恢复直接失败——「停得体面」比「停得快」重要。技术:训练框架定期落 checkpoint(每 N 步/每 N 分钟),抢占时先发 SIGTERM 类信号,让任务走到安全点(比如当前 step 算完)再退出;恢复时 load 最近 checkpoint 续训。再给微调设一个「最小运行时间片」+ 抢占冷却窗口,防止它被反复抢占、来回切换的开销超过收益。
Q:单张卡上能同时跑推理和微调吗?
人话:能跑,但「能跑」和「该这么跑」是两回事——共存的质量取决于隔离是否彻底。类比:两个进程抢同一块物理盘做 IO:共享一块盘没问题,共享「同一时刻」才是问题——备份的大顺序写会把生产读的延迟拖出毛刺,而且毛刺是间歇性的,平时看不出来,高峰期才炸。技术:有 MIG 就物理切块,推理、微调各占一块,显存算力都隔开,这是单卡共存的首选;没有 MIG 的卡,退而求其次用显存配额 + 「推理优先、微调可抢占」的分时复用,避免两者在微观时间片上互踩。硬共享的两大风险要主动点名:算力争抢把推理 P99 抖花,显存碎片化导致谁先 OOM 谁倒霉。
Q:时延和吞吐怎么权衡(batch 到底设多大)?
人话:跷跷板——batch 越大吞吐越高,但排队越久;正确姿势是先立时延红线,再在红线内把吞吐拉满。类比:像调备份并发度:并发拉满总吞吐最高,但单个作业的排队时长不可控;而生产在意的恰恰是「单笔请求多久回来」。技术:从 SLA 反推:P99 要求 < 800ms,这笔预算要覆盖排队 + 计算,由此定出「最大 batch × 最长队列长度」的组合;发车用动态批处理——攒满上限或超时(如 5ms)立即发车;上了 continuous batching 之后,完成的槽位立刻补新请求,不用等整批一起结束,吞吐还能再上一截。
Q:为什么不干脆买两套 GPU,推理一套、微调一套?
人话:可以,那是「用钱换简单」;但这题明确说了资源有限,面试官就是想听你怎么用一套资源办两件事,顺带把账算清。类比:为备份单独买一套存储 vs 复用生产存储的空闲容量——预算永远不够,混部是行业常态。技术:推理集群按峰值容量采购,但日均 QPS 通常远低于峰值,大部分时间 GPU 在「备而不用」;微调恰好能填这些谷。资源越紧张,混部的经济性越强。代价是调度复杂度上升——所以才需要前面整套「隔离 + 抢占 + 水位信号」把风险兜住;两套集群是另一个极端:运维简单但利用率难看,成本敏感的业务不会选。
Q:抢占的触发时机怎么定?会不会来回横跳?
人话:靠水位信号,不靠拍脑袋;而且不能等 P99 已经炸了才抢——那时已经晚了。类比:生产存储的自动限速:备份 IO 一抬升生产读的时延,就先压备份带宽,而不是等告警了才反应;同时阈值要有迟滞,防止在临界点反复开关。技术:信号取推理侧队列等待时间、QPS 预测曲线、显存余量;高/低双阈值中间留迟滞区间,流量在区间内晃不触发动作;再配最小运行时间片。更进阶的做法是按预测提前动作:预测 10 分钟后有高峰,现在就把微调安排到安全点,别等队列堆起来——抢占是兜底,不是常态手段。
术语卡
MIG:把一块 GPU 物理切成多个互相隔离的实例,像在阵列上划 LUN——硬隔离,谁也挤不到谁。
抢占式调度:高优先级任务挂起低优先级任务、收回资源的机制——微调被推理「请出去」全靠它。
QLoRA:基座 4-bit 量化 + 只训 LoRA 适配器,微调显存需求压 1~2 个数量级,「增量备份」式微调。
动态批处理:把并发请求攒成 batch 一起算提吞吐,配「超时发车」策略保时延。
Checkpoint:训练进度快照,抢占与恢复的底气——没有它,每次让路都等于从头再来。
SLA:服务等级协议,时延/可用性的对外承诺;本题的主线就是「推理的 SLA 一票否决」。
混部:在线、离线任务共摊同一批机器以提高利用率——本题的整个前提,也是资源紧张时的必然选择。
