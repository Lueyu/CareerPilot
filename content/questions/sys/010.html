Agent核心 · Q34

在多Agent系统中，如何保证异步任务执行的稳定性和结果一致性？

⭐⭐⭐⭐ #异步执行#一致性 字节(真题)
先说人话:这题问的是:任务丢给后台异步跑之后,Worker 崩了、消息重了、多个 Agent 并发改同一份数据,怎么保证任务不丢、不重复出事、账对得上。面试官爱考它,因为它专筛「真跑过分布式系统的人」——只会答「加重试、加个锁」的没挨过生产的毒打;能主动讲出「没有免费的 exactly-once」的才是老兵。
30秒电梯稿

"先把丑话讲在前面:异步 + 多机环境里没有免费的 exactly-once,工程上的标准答案是 at-least-once 投递 + 幂等消费,重复执行也无害,对外效果等价于恰好执行一次。稳定性四件套:消息队列(任务先落盘再执行)、租约 + 心跳(Worker 挂了自动重派)、超时 + 有限重试 + 指数退避(不卡死、不打爆下游)、死信队列 + 告警(反复失败有人兜底)。一致性四件套:幂等键(重复执行无副作用)、任务状态机(每次流转落库,可审计可回放)、单写者 / 乐观锁(防并发互相覆盖)、Saga 补偿(多步副作用中途失败就逆序回滚)。Agent 本身做成无状态、状态外置,进程挂了换台机器接着跑。"

通俗类比

先用容灾的思路想清楚难点在哪:单机代码里调一个函数,要么成功要么抛异常,状态都在一个进程里,天塌不下来;而「异步 + 多 Agent」等于把一条流程拆给一堆随时可能断电、还可能突然复活的节点去做——消息会重复投、Worker 会干到一半死掉、两个 Agent 会同时改同一份状态。这跟你熟悉的容灾是同一类问题:故障不是「会不会发生」,而是「什么时候发生」;设计目标也不是消灭故障,而是故障发生后系统能自动收敛回一致状态。你对 RTO/SLA 的职业直觉在这里完全适用——对外承诺的是恢复时间,内部所有机制都是为这个承诺兜底的。

整套机制像一套备份作业调度系统:消息队列 = 作业调度队列,任务先持久化登记(写 catalog)再派发,派发者和执行者解耦,高峰期任务排队而不是压垮服务器;租约 + 心跳 = 媒体服务器认领作业后的保活——领了作业要定期心跳续租,服务器宕机租约到期,作业自动重派,和容灾里备站靠心跳判断主站死活一模一样;幂等 = 去重,同一作业重跑一遍不该产生两份副作用,靠幂等键识别「这单干过了」;DLQ = 失败作业列表 + 告警,超限任务留给管理员,绝不静默丢弃;Saga = 流水线失败后的清理回滚——快照→复制→验证三步,第三步失败就把前两步占住的资源释放掉,不留半拉子状态。

哪里像:全是「先登记再执行、心跳保活、失败可重、超限上报」的作业系统套路,你做过备份调度就能秒懂骨架。哪里不像:备份作业大多重跑无害——源数据只读,重复备份顶多浪费点容量,去重一下就消掉了;而 Agent 任务经常带真实对外副作用(发消息、下单、改配置),重复执行会真出事故。所以在 Agent 这边,幂等不是性能优化,而是正确性前提——每一个写操作都要显式设计幂等,这是和备份系统思维方式最大的差异点。

详细拆解

这题在工程上等价于「把单机函数调用升级成跨机器的可靠执行」,分三块讲:稳定性(任务不丢、不卡死、不雪崩)、一致性(重复、并发、部分失败三个坑)、状态管理(前两者的地基)。

1. 稳定性:任务不丢、不卡死、不雪崩

稳定性的出发点是「故障必然发生」:节点会挂、消息会重、下游会抖,每种故障都要有对应兜底。先上对照表,下面逐条展开:

必然发生的故障没有机制时会怎样兜底机制
Worker 执行到一半宕机/假死任务永远卡在「进行中」,没人知道租约到期,自动重派给别的 Worker
消息重复投递 / 任务重派副作用执行两次(重复下单、重复发消息)幂等键去重
下游(LLM、业务 API)抖动限流大量任务同时失败,重试再砸一遍超时 + 指数退避 + 熔断限流
任务反复失败无限重试刷屏,或静默丢失死信队列 + 告警,人工兜底
  • 消息队列解耦:任务异步投递,生产者/消费者解耦,天然削峰;队列本身持久化,任务先落队再执行——和备份作业「先写 catalog 再派发」是同一条铁律。反面对照:生产者直接 RPC 调 Worker 等于裸奔,Worker 一重启任务就蒸发。
  • 租约(lease)+ 心跳:Worker 领任务时设租期(比如 60 秒),执行中定期续租(每 10 秒一次心跳);宕机、GC 长停顿、假死 → 租约到期 → 任务重派。这是「任务不丢」和「不双跑」之间的平衡:租约太短,重派太快,双跑概率高;太长,故障后任务悬空时间久。再补一道针对僵尸 Worker(老 Worker 停顿后复活继续写)的保险:租约每次续签配一个递增的 fencing token,存储侧只接受最新 token 的写入,老 token 的写入直接拒绝。
  • 超时 + 有限重试 + 指数退避:单步设超时(如 LLM 调用 30s);失败重试但设上限(如 3 次),退避 1s/2s/4s 加随机抖动,防止重试风暴打爆下游——下游刚喘口气,别再补一刀。超上限进死信队列告警,人工处理。
  • 熔断/限流:下游(LLM、业务 API)大面积异常时熔断快速失败,半开探测恢复,防止一个 Agent 的故障沿调用链拖垮整条链路——级联故障你在分布式系统里见过,Agent 系统一模一样。

2. 一致性:重复、并发、部分失败三个坑

  • 幂等(核心中的核心):给任务和写操作配幂等键,执行前查键去重,副作用操作(发消息、扣款、写单)按键认「这单干过了」。幂等键的来源很讲究:由生产者在投递时生成、随消息携带、重投也不变——类比备份作业的 job id,重派还是同一个 id,catalog 靠它识别重复;如果让消费者自己随机生成,一次重投就成了「新任务」,去重直接失效。实现手段按下表选型:
手段典型写法可靠性适用场景
DB 唯一索引UNIQUE(task_id),重复插入直接冲突最高,事务保证落库类副作用的首选
状态机条件更新UPDATE … WHERE status='pending',影响行数为 0 即已被处理高任务状态流转,天然防双跑
Redis SETNX + TTLSET idem:{task_id} NX EX 3600,抢不到即重复中,实例故障会丢键,需 DB 兜底短窗口去重、防抖
业务键去重(订单号, 操作类型) 设唯一约束高对外业务操作
  • 交付语义要主动讲清楚:at-most-once(发后即忘,可能丢,只适合可容忍丢失的埋点日志)、at-least-once(可能重,靠幂等兜底)、exactly-once(异步网络里无法免费达成,详见追问)。面试标准答案就是一句:「我选 at-least-once + 幂等」,这是工程界共识,主动说出来而不是等面试官逼问。为什么重派必然带来重复,看下面这个窗口:
为什么「恰好一次」做不到——ACK 丢失窗口必然产生重复执行:

  Worker ──→ ①执行任务,结果写库成功 ──→ ②回 ACK ──✕ 网络断了 / Worker 恰好崩溃,ACK 没到
                                                              ↓
  队列视角:「投出去的任务没有回音」= 失败 → 重派(不重派就要接受丢任务)
                                                              ↓
  新 Worker ──→ ③同一任务再执行一遍    ← 这就是 at-least-once 的代价:消息不丢,但可能重

  出路:不追「绝不重」,而是让「重也无害」:
  ③' 第二次执行 ──→ 查幂等键 task_id=42:已处理过 ──→ 跳过执行,直接返回上次结果
      → 对外效果 = 恰好执行一次(效果上的 exactly-once)
  • 并发写冲突:共享状态用单写者模式(同一任务/会话同一时刻只路由给一个 Worker 写,如按 session_id 哈希到固定队列)或乐观锁/版本号(CAS 更新,写入带 expected_version,版本不符说明有人抢先,重读重算再试;详见 乐观并发控制)。中间态合并建议用 reducer(列表追加、增量合并)而非整对象覆盖。
  • 部分失败 → Saga:跨 Agent 的多步副作用拆成本地小事务,每步成功就记录,并预先配好一个补偿动作;中途失败按逆序补偿回滚。例:Agent A 扣库存 → Agent B 创建订单 → Agent C 发通知;C 失败 → 撤 B(取消订单)→ 补 A(回库存)。补偿动作自己也要幂等可重试(下面追问展开)。保证要么全成、要么回到一致状态——和流水线失败后释放已分配资源是同一逻辑。

3. 状态管理是稳定性的地基

  • Agent 本身做成无状态,状态外置(Redis 放热数据:进行中的会话、中间产物;DB 放冷数据:历史、审计),进程挂了换台机器继续跑——和无状态计算节点随时可替换、状态靠外置 catalog/索引是同一个架构习惯。
  • 任务用状态机管理,每次变更落库,等价于作业日志:可审计、可回放、可恢复。同时它本身就是幂等手段——「只有 pending 能被领走」这一条约束,天然挡掉重复执行:
任务状态机(每次流转落库 = 作业日志):

            领取(租约生效)           执行成功
  pending ───────────────→ running ──────────→ succeeded
     ↑                        │ │
     │  租约到期/Worker 假死    │ └──重试耗尽──→ failed ──人工确认──→ dead
     └─────────重派────────────┘                  (进 DLQ,有人兜底)
  • 关键长任务做 checkpoint:每完成一个子步骤就落一个检查点,崩溃后从断点续跑而非从头再来——和备份断点续传、按块重跑是同一逻辑,LLM 长任务里尤其值钱,不然一次失败就烧掉前面全部 token。

把整条防线画出来,上半部分是单任务的稳定通路,下半部分是多步副作用的 Saga 补偿:

落地顺序(面试收尾用):①先做幂等键 + 状态机——这是地基,没有它,后面所有「重试/重派」都是危险动作;②再上队列 + 租约 + 超时重试;③补 DLQ + 告警 + 监控,让失败可见;④跨 Agent 多步副作用最后套 Saga。一句话点题:允许失败,但失败后状态不能烂在半路,也不能靠重复执行碰运气——能把「没有免费 exactly-once」主动讲清楚的候选人,面试官立刻知道你是真干过分布式的。

面试官追问
Q:为什么不能真正 exactly-once?
人话:因为「活干完了」和「汇报干完了」是两件事,中间隔着网络,汇报永远可能丢;汇报一丢,系统以为没干完就再派一次,活就干了两遍。类比:备份作业执行完、catalog 也更新了,但回报状态的那条消息丢了,调度器判定失败重派,第二个执行器又跑一遍——你在备份系统里见过这种「幽灵重跑」。技术:「执行」和「确认」之间存在不可消除的时间窗口,这是 两将军问题的变体,异步网络里理论上就做不到恰好一次;Kafka 等宣称的 exactly-once,本质也是把去重下沉到有状态消费端。所以工程答案不是追「绝不重」,而是让它重复也无害——幂等,对外效果等价 exactly-once。
Q:两个 Agent 同时写同一个会话状态,会覆盖吗?
人话:会的,后写的把先写的整个盖掉——两人都基于旧版本改,谁后保存谁赢,先改的那份凭空消失。类比:两个管理员同时改同一卷的备份策略,A、B 各自全量覆盖写回,B 的写回基于旧配置,A 的修改就丢了;存储元数据防这种事靠带版本号的更新,不会靠「祈祷没人并发」。技术:①乐观锁:表加 version 字段,UPDATE … SET version=version+1 WHERE id=? AND version=?,影响行数为 0 即并发冲突,重读重算再试;②串行化:按 session_id 哈希路由到同一队列,同一会话同一时刻只有一个写者,牺牲一点并发换正确性;③中间态合并用 reducer(列表追加、增量合并)而非整对象覆盖,把「覆盖」变成「合并」,冲突面天然缩小。
Q:Saga 补偿动作本身失败了怎么办?
人话:补偿也会失败,不能假装它不会。铁律是:补偿失败绝不静默吞掉,要显式挂账、告警、最后由人兜底。类比:容灾回切——切到备站后要回切,回切流程同样可能失败,那时不是硬切,而是冻结状态、挂起工单等人工介入;备份副本清理失败也一样,宁可留着待删记录,也不能假装删干净了。技术:补偿动作和正向动作同样做成幂等 + 可重试(失败进重试队列、指数退避);反复失败进人工补偿队列并告警;「补偿中/待人工」作为状态持久化进状态机,链路随时可从断点续跑,必要时重放 Saga 判断当前停在哪一步。宁可显式报「部分完成待人工」,不能悄悄不一致——静默不一致是最难排查的事故。
Q:任务延迟敏感,队列重试会不会拖太久?
人话:会,所以要分级:用户在线等的任务别扔进长重试队列,快失败、快降级;只有后台重任务才配得上慢慢重试的节奏。类比:备份分同步复制和离线批备:RPO/RTO 要求高的走同步快路径,其余进夜间窗口;交互式 Agent 调用等于「RTO 秒级」场景,套用离线作业的多轮重试节奏就是灾难。技术:实时交互类走同步路径 + 短超时(如 3s)+ 有限重试(如 1 次)+ 降级(返回缓存、切小模型、提示稍后送达),重试期间并行启动降级方案,谁先成功用谁;离线重任务才进队列做多轮退避重试;退避要封顶,DLQ 原则上只收离线任务——交互类任务失败直接降级给用户反馈,不该躺在死信队列里等人工。
Q:幂等键怎么设计?为什么不能让消费者自己生成?
人话:幂等键是每个任务/写操作的「唯一编号」,系统靠它认出「这单干过了」。好键三要素:业务上唯一、生成时机确定、重投也不变。类比:备份的 job id——作业重派一百次还是同一个 id,catalog 靠它识别重复,而不是每次比对内容;incarnation 换了才算新任务。技术:①键由生产者在投递时生成并随消息携带(task_id/message_id)——消费者随机生成的话,一次重投就成了「新任务」,去重直接失效;②业务操作可用业务键,如「订单号 + 操作类型」配 DB 唯一索引兜底,这比 Redis SETNX 更可靠(实例故障不丢);③注意键的粒度:同一键要覆盖「同一次业务意图的所有重试」,但不同请求绝不能误用同一个键,否则会把合法的两次操作错当成重复拒掉。
术语卡
幂等:同一操作执行多次,效果与一次相同——「把状态改为已发货」天生幂等,「计数器+1」天生不幂等,后者要靠幂等键改造成「set 绝对值」。
租约:带有效期的执行权,靠心跳续期,到期自动回收重派——既保任务不丢,又防死掉的 Worker 一直霸占任务。
Saga:长事务拆成若干本地小步,每步配一个补偿动作,中途失败就逆序补偿,把系统拉回一致状态。
At-least-once:投递语义中间档:消息绝不丢,但可能重;配上幂等消费后,对外效果等价 exactly-once。
DLQ:死信队列,反复失败任务的收容所——从这里进人工流程,而不是无限重试刷屏。
乐观锁:写入时带版本号做 CAS,版本不符说明有人抢先,重读重算再试——不加锁也能防并发覆盖。
Fencing token:随租约/锁发放的递增令牌,存储侧只认最新令牌的写入,专治「老 Worker 复活继续写」的僵尸双跑。
