系统设计 · Q5

设计一个分布式 Agent 调度系统

⭐⭐⭐⭐⭐ #分布式#调度#Agent
先说人话:一堆 Agent 任务散在一群机器上跑,怎么做到「不丢、不重、不乱、不过载」——这题问的就是这份施工方案。它是分布式老三样(队列、租约、幂等)在 AI 场景的落地,面试官拿它区分「背过八股的人」和「真扛过生产的人」:只画架构图、不主动讲「Worker 执行到一半挂了怎么办」,基本就露馅了。
30秒电梯稿

"经典生产者-消费者模型升级版:任务投递到消息队列(Kafka/RabbitMQ),Worker 池消费执行 Agent 任务;用心跳 + 租约检测 Worker 存活,宕机任务自动重派;任务设计成幂等的,重复执行无副作用;队列本身提供背压,按优先级分队列保证重要任务先跑;死信队列收集反复失败的任务供人工介入。主线就四句话:队列解耦削峰、租约保任务不丢、幂等保重跑无害、背压保系统不被打挂——外加指标驱动的扩缩容。"

通俗类比

把整个系统想成你天天见的「夜间备份窗口调度」:晚上窗口一开,几百个客户端的备份作业排队进池(任务队列);介质服务器池各自领作业干(Worker 池 + 负载均衡);每台介质服务器定时向主服务器报一次「我还活着」,连着几个周期收不到就把它踢出调度、发失联告警(心跳);领作业前先在登记表上把作业「锁」到自己名下,锁带有效期——机器炸了锁也不会永远卡着,到期自动释放、作业回队给别人(租约);一晚上塞太多全量备份会把客户端 IO 和网络打爆,所以要限并发、排优先级,关键库的日志备份先于归档文件(背压 + 优先级队列);反复失败的作业挂起进告警工单,等管理员人工排查后释放(DLQ)。

哪里像:排队、分派、失联检测、失败重试、过载限流、死信人工介入——六个环节一一对应,分布式调度的骨架完全同构。哪里不像(也是本题真正的考点):①备份作业大多天然幂等——同一份数据重跑一遍,顶多多花时间、再写一份副本,数据不会乱;Agent 任务的副作用多得很——发邮件、调外部 API、下单、改数据库,重跑一遍就是事故,所以「重试无害」在这里不是天生的,是要主动设计出来的(怎么设计见下面第 4 节)。②备份任务的时长和 IO 开销大致可预估,按「作业个数」排并发就行;Agent 任务里 LLM 调用一响几十秒、token 消耗忽大忽小,还共享同一个 LLM 网关,调度必须按 token/并发限流,不能光数任务个数。讲类比时把这两条「不像」主动说出来,面试官就知道你不是背的。

详细拆解

1. 整体架构

顺着图把一次任务的旅程走一遍:API 收到请求,生成全局唯一 task_id 和幂等键 → 按业务优先级投进对应队列 → 空闲 Worker 领取(先拿租约) → 执行中持续上报心跳与进度 → 完成后向队列 ACK → 状态落库。任何一环断掉,后面都有兜底机制接住——这句话就是整个设计的灵魂。

先回答一个容易被追问的问题:为什么中间要放队列,而不是上游直接 RPC 调 Worker?四个理由,每个都能在备份系统里找到原型:

  • 削峰:高峰期任务先排队,不把 Worker 池直接打挂——备份窗口里作业排队是常态而不是事故;
  • 解耦:上游不关心有多少 Worker、在哪台机器,加减机器不用改任何上游代码;
  • 重试缓冲:失败的任务重新入队,天然获得重试能力,不用上游自己实现;
  • 过载信号:队列积压长度是最直观的过载指标,后面的自动扩缩容和背压都盯它。

2. 任务生命周期(状态机)

pending → running → succeeded / failed / dead / cancelled。每次状态变更写 Redis + 异步落 DB。任务带唯一 task_id 和幂等键。

pending ──领取(抢到租约+SETNX 锁)──→ running ──执行成功──→ succeeded
   ↑                                  │
   │                                  ├──执行失败──→ failed ──重试<3次──→ 回 pending
   │                                  │                  └─重试≥3次──→ dead(进 DLQ)
   └────────租约到期/Worker 宕机(任务收回重派)────────┘

cancelled:任何状态都允许用户主动取消;succeeded/failed/dead/cancelled 是终态,不可逆

为什么状态先写 Redis 再异步落 DB?Redis 抗高频状态翻转(每秒成千上万次变更,还自带 TTL,天然适合做租约),但它终归是内存库;DB 落全量任务记录,负责审计、对账和故障后的恢复。这套「热数据管调度、冷数据管对账」的分工,和备份软件里内存作业表与落盘 catalog 的关系一模一样。

3. 容错三件套(核心考点)

机制管什么一句话原理关键参数
心跳Worker 死没死定时上报「我还活着」,连续失联判死每 5s 上报,连续 3 次未报 → 标记下线
租约任务归谁领任务先「租」,到期自动回收重派5 分钟租期,执行中定期续期
ACK消息删不删完成才确认;未确认的消息对其他消费者可见任务完成回执,无回执自动重投
  • 心跳:Worker 每 5s 向注册中心(etcd/Redis)上报;连续 3 次没报 → 标记下线,不再派新任务。注意心跳只能回答「机器死没死」,回答不了「它手上的任务怎么办」——那是租约的事。
  • 租约(lease):Worker 领任务先「租」(设定 5 分钟租期并续期),执行到一半宕机租约自动到期,任务回到队列被别人领走。租约解决的是「任务不丢」且「不双跑」的平衡(到期前不重派,可能慢一点但安全;要严格单跑就配幂等)。
  • ACK 机制:任务完成才向队列确认;处理中宕机未 ACK,消息对其他消费者可见,自动重派。

三个机制叠起来,得到的是 at-least-once(至少投递一次) 语义——系统保证任务一定被执行,但不保证只执行一次。重复执行的空隙就发生在「Worker 挂了到租约过期」这段窗口里,看时间线最直观:

t0        Worker-A 领任务 T42:写租约 key(lease:T42, TTL=5min),SETNX 抢执行锁
t0+30s    执行中,每 30s 续租一次(TTL 重置回 5min)
t0+4min   Worker-A 宕机 ⚠ 续租停止,但租约 key 还在(TTL 未到,任务不会立刻被抢走)
t0+9min   租约 key 自动过期 → 调度器发现 T42 无人持有 → 状态改回 pending 重新入队
t0+9min+ε Worker-B 领到 T42,抢锁成功 → 从头执行
                        ↑ 「重复执行」确实发生了(T42 被跑了两次)→ 只能靠幂等兜底

4. 幂等性(必须主动讲)

重派会导致任务被执行两次,所以任务必须幂等(同一操作执行多次,效果和执行一次相同,定义见维基)。三个手段,层层设防:

① 执行前抢执行锁(SETNX = 不存在才设置,抢到才有资格执行):
SET lock:task:T42 "worker-B" NX EX 300     → 抢到才执行;抢不到说明别人在跑,直接放弃

② 副作用操作带幂等键,下游按 key 去重:
POST /api/send  头部携带 Idempotency-Key: T42
                                           → 下游记录已处理的 key,重复请求返回首次结果

③ Agent 中间状态外置,重跑从断点恢复:
SET progress:T42 "step3"                   → 重跑时从 checkpoint 恢复,而非把状态叠加两遍
  • SETNX 锁:执行前用 task_id 在 Redis 抢锁,拿到才执行——挡住「同一时刻两个 Worker 都在跑同一任务」的双跑;
  • 幂等键去重:副作用操作(发消息、写库、调外部 API)带幂等键,下游去重——挡住「先后两次执行都发出了副作用」;
  • 中间状态外置:Agent 类任务的中间状态外置,重跑时从头初始化而非叠加——挡住「重跑把上一次的半成品状态叠加出新 bug」。

再补一个 Agent 场景特有的认知:幂等指的是「副作用幂等」,不是「结果相同」。LLM 调用本身有随机性,同一任务重跑两次,生成的文本大概率不一样——这没关系;要保证的是邮件只发一封、数据库只写一次、订单只下一个。分清这两件事,说明你真的趟过 Agent 的水。

5. 负载均衡与扩缩容

  • 消费者组天然分摊;同 hash key 进同队列保证局部有序(如同一会话的任务串行)。为什么串行很重要:Agent 会话是有状态的,上下文随任务顺序累积,同一会话的两个任务乱序执行会互相覆盖、上下文错乱——就像同一个客户端的增量备份必须排在全量之后,顺序错了链就断了。
  • 指标驱动扩缩容:队列积压长度 > 阈值 → 自动加 Worker(K8s HPA);连续空闲 → 缩容省钱。
  • Agent 任务耗 GPU/长时连接,扩缩容要考虑优雅下线:先摘流量、等在跑任务完成或迁移、再退场。直接 kill 缩容等于人工制造一批「Worker 宕机」,触发全量租约重派——省的钱不够填重跑的 GPU 账单。

6. 背压与过载保护

  • 队列满 → 拒绝新任务并返回「排队中」凭证(削峰);或上游降级(如把 Agent 任务降级为简单 RAG 直答)。
  • Worker 内部再限并发(信号量控制同时在跑的 LLM 调用数),防止把 LLM 网关打挂。
  • 一个关键洞察:过载时无脑扩 Worker 救不了 LLM 网关——瓶颈在下游共享资源(网关的 QPS/token 配额),多加 Worker 只是把排队从队列挪到网关前面,还更容易触发限流。这和「备份客户端进程开再多也没用,因为瓶颈是介质服务器的 IO」是同一个道理:先找瓶颈在哪一层,再决定扩哪一层。

7. 死信队列:重试 3 次仍失败的任务进 DLQ,告警 + 人工排查 + 修复后可重新投递。为什么重试要有上限而不是无限重试?因为存在毒丸任务(poison message)——比如任务体本身非法、Prompt 把模型必挂,重试一百次也一样失败,还每次占住一个 Worker 白烧 GPU。让它留在正常队列里循环重试,等于让一个永远跑不完的坏作业夜夜堵死备份窗口;正确做法就是三次之后踢出去、告警、等人来——和你处理反复失败的坏文件备份作业(跳过 + 挂起 + 工单)一模一样。

面试官追问
Q:选 Kafka 还是 RabbitMQ?
人话:两个都能用,但性格完全不同——一个像日志流,一个像调度台,选谁取决于你要什么。类比:Kafka 像磁带库的顺序归档流:海量写入、可从头重放(重放备份日志排查问题就是这么干的);RabbitMQ 像调度台:路由规则灵活、原生支持优先级队列、任务完成有确认回执,天生为「派活」设计。技术:Kafka 吞吐高、日志型、重放方便,适合海量任务流;RabbitMQ 延迟低、路由灵活、优先级队列原生支持。Agent 调度一般任务量级不大但需要优先级和灵活路由,RabbitMQ/Redis Stream 更常用;要和大数据链路打通选 Kafka。
Q:Worker 执行到一半挂了,任务会重复执行吗?
人话:先直接答「会」——租约到期后任务必然重派,重复执行躲不掉;然后立刻补上「所以靠幂等保证重复无副作用」。先认账再给方案,显得考虑周全,这题面试官就是在钓你敢不敢承认。类比:介质服务器跑到一半断电,作业重新排队在另一台上重跑——备份重跑只是多花时间,因为它的副作用天然无害。技术:时间线是:宕机 → 续租停止 → 租约 key TTL 到期自动失效 → 任务回 pending 重派。防御靠三层:执行前 task_id 抢 SETNX 锁防「同时双跑」;副作用带幂等键防「先后两次都生效」;中间状态外置、重跑从头初始化防「状态叠加」。注意幂等保证的是副作用唯一,不是两次生成结果一样——LLM 有随机性,文本不同没关系,邮件只发一封才是关键。
Q:长任务(几小时)怎么办?
人话:几小时的任务不能靠一次租约赌命,要拆着跑、存进度、按进度续命。类比:超大库的全量备份从不指望一口气跑完——分阶段执行,每个阶段落 checkpoint,断了从断点续传,而不是从头再来。技术:任务拆阶段 + 定期 checkpoint 上报进度;租约按进度续期(只要还在上报进度就持续续租,不设死板上限);支持暂停/恢复/取消;这类任务单独放大超时队列,避免和秒级小任务混在一起互相污染超时参数。重派时从最近 checkpoint 恢复而不是重跑全程,把重复执行的代价压到最低。
Q:任务状态为什么写 Redis 又要落 DB,留一个不行吗?
人话:Redis 管「快」,DB 管「稳」,俩是分工不是冗余,只留任何一个都会出事。类比:备份软件里内存作业表负责实时调度,catalog 落盘负责审计和事后扯皮——重启恢复靠热数据,月底对账靠冷数据,缺一个都玩不转。技术:调度热路径每秒可能上千次状态翻转,还依赖 TTL 做租约,这是 Redis 的主场;但它是内存库,有淘汰和丢数据风险,绝不能当唯一事实源。所以状态变更先写 Redis(保调度低延迟),异步批量刷 DB(保审计与故障恢复),再配一个对账任务定期比对两边差异、不一致就告警。答这题时点出「Redis 不是事实源」,是加分位。
Q:控制面/调度器自己挂了,整个系统怎么办?
人话:设计目标是「变笨但不瘫痪」——新任务进不来或只能排队,但在跑的任务必须继续跑完,绝不能控制面一挂全场任务全停。类比:备份主服务器重启时,各介质服务器上正在跑的作业并不中断,恢复后重新接管调度——控制面是大脑,不是心脏,大脑短暂离线不该心跳骤停。技术:①控制面无状态化,全部状态放 etcd/Redis(本身多副本高可用),控制面实例随便重启;②多实例部署 + 选主(或全对等);③Worker 的执行权来自租约而非控制面的在线祝福,租约存在共享存储里,控制面挂了 Worker 照常续租、照常跑;④恢复后靠心跳和租约对账,把失主持有的任务收回重派。能讲出「执行权下放到租约」这一层,说明你真理解控制面和数据面的边界。
术语卡
租约:带 TTL 的任务执行权,持有者宕机后到期自动回收重派——比心跳强一级的容错机制。
幂等:同一任务跑一次和跑 N 次副作用相同;at-least-once 队列的黄金搭档,Agent 场景必须主动设计。
心跳:Worker 定期喊「我还活着」;失联判定全靠它,但它只能判死机器,保不住任务。
ACK:消费完成回执;没回执的消息会被重投,是「任务不丢」的最后一道保险。
DLQ:死信队列,反复失败任务的收容所 + 告警工单,防毒丸任务无限重试拖垮全局。
消费者组:一组 Worker 自动分摊队列消息,天然负载均衡,扩容不用改代码。
HPA:K8s 水平自动扩缩容,按队列积压等指标自动加减 Worker。
背压:过载时向上游「顶回去」的信号——排队、拒绝、降级三选一,总比系统崩了强。
