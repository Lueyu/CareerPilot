系统设计 · Q5

设计一个分布式 Agent 调度系统

⭐⭐⭐⭐⭐ #分布式#调度#Agent
先说人话:一堆 Agent 任务散在一群机器上跑,怎么做到「不丢、不重、不乱、不过载」——这题问的就是这份施工方案。它是分布式老三样(队列、租约、幂等)在 AI 场景的落地,面试官拿它区分「背过八股的人」和「真扛过生产的人」:只画架构图、不主动讲「Worker 执行到一半挂了怎么办」,基本就露馅了。
30秒电梯稿

“队列按优先级交给 Worker 执行，心跳报告存活，租约协调任务归属。Worker 先把结果和终态持久化，再确认消息。重投时先查任务表，已有终态就读回结果并确认。需要恢复外部动作时按原操作号查回执，满足下游幂等契约才安全重放。背压保护下游，反复失败的任务进死信队列。”

通俗类比

把整个系统想成你天天见的「夜间备份窗口调度」:晚上窗口一开,几百个客户端的备份作业排队进池(任务队列);介质服务器池各自领作业干(Worker 池 + 负载均衡);每台介质服务器定时向主服务器报一次「我还活着」,连着几个周期收不到就把它踢出调度、发失联告警(心跳);领作业前先在登记表上把作业「锁」到自己名下,锁带有效期——机器炸了锁也不会永远卡着,到期自动释放、作业回队给别人(租约);一晚上塞太多全量备份会把客户端 IO 和网络打爆,所以要限并发、排优先级,关键库的日志备份先于归档文件(背压 + 优先级队列);反复失败的作业挂起进告警工单,等管理员人工排查后释放(DLQ)。

哪里像:排队、分派、失联检测、失败重试、过载限流、死信人工介入——六个环节一一对应,分布式调度的骨架完全同构。哪里不像(也是本题真正的考点):①备份作业大多天然幂等——同一份数据重跑一遍,顶多多花时间、再写一份副本,数据不会乱;Agent 任务的副作用多得很——发邮件、调外部 API、下单、改数据库,重跑一遍就是事故,所以「重试无害」在这里不是天生的,是要主动设计出来的(怎么设计见下面第 4 节)。②备份任务的时长和 IO 开销大致可预估,按「作业个数」排并发就行;Agent 任务里 LLM 调用一响几十秒、token 消耗忽大忽小,还共享同一个 LLM 网关,调度必须按 token/并发限流,不能光数任务个数。讲类比时把这两条「不像」主动说出来,面试官就知道你不是背的。

详细拆解

1. 整体架构

一次任务的顺序是：API 登记 task_id 和幂等键 → 按优先级投递 → Worker 领取并拿租约 → 执行中上报心跳和进度 → 将结果和终态一起提交到数据库 → ACK。如果在提交后、ACK 前断电，消息重投时按 task_id 读回原结果并确认。若外部动作可能已生效而本地尚无终态，先按原操作号查外部回执。

先回答一个容易被追问的问题:为什么中间要放队列,而不是上游直接 RPC 调 Worker?四个理由,每个都能在备份系统里找到原型:

  • 削峰:高峰期任务先排队,不把 Worker 池直接打挂——备份窗口里作业排队是常态而不是事故;
  • 解耦:上游不关心有多少 Worker、在哪台机器,加减机器不用改任何上游代码;
  • 重试缓冲:失败的任务重新入队,天然获得重试能力,不用上游自己实现;
  • 过载信号:队列积压长度是最直观的过载指标,后面的自动扩缩容和背压都盯它。

2. 任务生命周期(状态机)

每个任务保存唯一 task_id 与幂等键。成功时在同一事务提交结果与终态，终止失败时保存原因与终态。可重试失败时先持久化重试计划，例如在同一事务写入待投递表，再确认原消息。

pending ──拿到租约──→ running ──提交结果和终态──→ succeeded ──ACK
  ↑                      ├──可重试失败──→ 持久化重试计划 ──ACK 原消息
  │                      └──重试耗尽──→ 保存失败原因和终态，登记 DLQ ──ACK
  └────按重试计划投递，或租约到期后核对持久状态再接管───────┘

pending 或 running 可请求取消。确认停止并核对在途副作用后，持久化 cancelled。
succeeded、dead 和 cancelled 是终态。重投时读取终态及已保存信息后 ACK。

Redis 可保存高频心跳、租约和进度视图。任务表及其持久检查点提供恢复依据。Worker 在 ACK 前等待数据库事务提交，Redis 视图可以在提交后异步刷新。

3. 容错三件套(核心考点)

机制管什么一句话原理关键参数
心跳Worker 死没死定时上报「我还活着」,连续失联判死每 5s 上报,连续 3 次未报 → 标记下线
租约任务归谁领任务先「租」,到期自动回收重派5 分钟租期,执行中定期续期
ACK何时确认本次投递结果和终态持久化后确认，或等重试计划持久化后确认原消息确认前断连可触发重投，重投先查任务表
  • 心跳:Worker 每 5s 向注册中心(etcd/Redis)上报;连续 3 次没报 → 标记下线,不再派新任务。注意心跳只能回答「机器死没死」,回答不了「它手上的任务怎么办」——那是租约的事。
  • 租约（lease）。Worker 定期续约，租约到期后由新 Worker 接管。接管前读持久状态，并用递增执行代数阻止旧 Worker 覆盖本地结果。旧 Worker 可能仍在运行，外部动作还需要下游按操作号防重。
  • ACK 机制。以 RabbitMQ 为例，消费通道关闭后未确认的消息可以重新投递。Worker 收到重投时先读任务表，已有终态就复用结果并 ACK。同一次失败的重试已登记时，确认原消息，由待投递记录派发新的尝试。

按 at-least-once（至少投递一次） 来设计消费者：同一消息可能投递多次，租约也可能在旧 Worker 仍运行时过期。要演练数据库提交前后两处故障。

T42：Worker A 领取 → 执行 → 数据库提交结果和 succeeded → ACK
故障点 A（提交前）：A 断电 → 消息重投，B 接管 → 查检查点与外部回执后恢复
故障点 B（提交后、ACK 前）：A 断电 → 消息重投 → B 读回原结果 → ACK

4. 幂等性(必须主动讲)

重派会导致任务被执行两次,所以任务必须幂等(同一操作执行多次,效果和执行一次相同,定义见维基)。三个手段,层层设防:

① 接管前读取任务表。有终态时复用原结果。仍需执行时取得新租约和执行代数。
② 外部动作使用持久保存的稳定操作号，例如任务 T42 的通知步骤使用 T42:notify。
   已成功就补记回执，仍在途就等待。确认可安全重放且下游按原号原子去重时才重发。
   状态不明且没有去重保障时转对账。
③ 从最近的有效持久检查点恢复。本地写入时校验执行代数，避免迟到写入覆盖新结果。
  • 执行权。拿租约时分配执行代数，提交结果时用该代数做条件更新，拒绝旧持有者的写入。
  • 幂等键去重。每个副作用使用独立的稳定操作号，确认下游支持同号同参数原子去重，并保留外部回执供恢复查询。
  • 中间状态外置。记录有效检查点，恢复时继续未完成步骤，同时核对尚未记录结果的外部动作。

已提交的任务结果在重投时应原样读回。提交前若确实需要重跑模型，生成文本可能不同。邮件、订单等副作用按独立操作号和下游回执确定是否已经生效。

5. 负载均衡与扩缩容

  • 消费者组天然分摊;同 hash key 进同队列保证局部有序(如同一会话的任务串行)。为什么串行很重要:Agent 会话是有状态的,上下文随任务顺序累积,同一会话的两个任务乱序执行会互相覆盖、上下文错乱——就像同一个客户端的增量备份必须排在全量之后,顺序错了链就断了。
  • 指标驱动扩缩容:队列积压长度 > 阈值 → 自动加 Worker(K8s HPA);连续空闲 → 缩容省钱。
  • Agent 任务耗 GPU/长时连接,扩缩容要考虑优雅下线:先摘流量、等在跑任务完成或迁移、再退场。直接 kill 缩容等于人工制造一批「Worker 宕机」,触发全量租约重派——省的钱不够填重跑的 GPU 账单。

6. 背压与过载保护

  • 队列满 → 拒绝新任务并返回「排队中」凭证(削峰);或上游降级(如把 Agent 任务降级为简单 RAG 直答)。
  • Worker 内部再限并发(信号量控制同时在跑的 LLM 调用数),防止把 LLM 网关打挂。
  • 一个关键洞察:过载时无脑扩 Worker 救不了 LLM 网关——瓶颈在下游共享资源(网关的 QPS/token 配额),多加 Worker 只是把排队从队列挪到网关前面,还更容易触发限流。这和「备份客户端进程开再多也没用,因为瓶颈是介质服务器的 IO」是同一个道理:先找瓶颈在哪一层,再决定扩哪一层。

7. 死信队列。例如重试 3 次仍失败时，在同一数据库事务中提交失败原因与 dead 终态，并登记待投递的死信记录，然后 ACK 原消息。待投递记录负责把死信送到 DLQ 供告警和排查。修复后若需重试，先核对原操作回执与安全重放条件，再登记新的执行。

面试官追问
Q:选 Kafka 还是 RabbitMQ?
人话:两个都能用,但性格完全不同——一个像日志流,一个像调度台,选谁取决于你要什么。类比:Kafka 像磁带库的顺序归档流:海量写入、可从头重放(重放备份日志排查问题就是这么干的);RabbitMQ 像调度台:路由规则灵活、原生支持优先级队列、任务完成有确认回执,天生为「派活」设计。技术:Kafka 吞吐高、日志型、重放方便,适合海量任务流;RabbitMQ 延迟低、路由灵活、优先级队列原生支持。Agent 调度一般任务量级不大但需要优先级和灵活路由,RabbitMQ/Redis Stream 更常用;要和大数据链路打通选 Kafka。
Q:Worker 断电后，重投一定要重跑任务吗？
先查持久任务表。若结果和终态已经提交，直接复用原结果再 ACK。若尚未提交，等租约可接管后，按最近的有效检查点恢复。外部动作可能已完成时，按原操作号查回执。查到成功就补记，仍在途就等待，确认可安全重放且下游按原号去重时才重发。状态未知又缺少去重保障时转对账。
Q:长任务(几小时)怎么办?
人话:几小时的任务不能靠一次租约赌命,要拆着跑、存进度、按进度续命。类比:超大库的全量备份从不指望一口气跑完——分阶段执行,每个阶段落 checkpoint,断了从断点续传,而不是从头再来。技术:任务拆阶段 + 定期 checkpoint 上报进度;租约按进度续期(只要还在上报进度就持续续租,不设死板上限);支持暂停/恢复/取消;这类任务单独放大超时队列,避免和秒级小任务混在一起互相污染超时参数。重派时从最近 checkpoint 恢复而不是重跑全程,把重复执行的代价压到最低。
Q:任务状态为什么写 Redis 又要落 DB？
Redis 适合做高频调度视图和带 TTL 的租约，数据库保存任务结果、终态及恢复用检查点。进度视图可以异步刷新。ACK 要等待持久事务提交，重投和重启后从任务表恢复。
Q:控制面/调度器自己挂了,整个系统怎么办?
人话:设计目标是「变笨但不瘫痪」——新任务进不来或只能排队,但在跑的任务必须继续跑完,绝不能控制面一挂全场任务全停。类比:备份主服务器重启时,各介质服务器上正在跑的作业并不中断,恢复后重新接管调度——控制面是大脑,不是心脏,大脑短暂离线不该心跳骤停。技术:①控制面无状态化,调度状态放高可用的 etcd/Redis，任务结果和终态持久化到数据库,控制面实例随便重启;②多实例部署 + 选主(或全对等);③Worker 的执行权来自租约而非控制面的在线祝福,租约存在共享存储里,控制面挂了 Worker 照常续租、照常跑;④恢复后结合心跳、租约和持久任务表，只接管失去持有者且未完结的任务。能讲出「执行权下放到租约」这一层,说明你真理解控制面和数据面的边界。
术语卡
租约:带 TTL 的任务执行权,持有者宕机后到期自动回收重派——比心跳强一级的容错机制。
幂等:同一任务跑一次和跑 N 次副作用相同;at-least-once 队列的黄金搭档,Agent 场景必须主动设计。
心跳:Worker 定期喊「我还活着」;失联判定全靠它,但它只能判死机器,保不住任务。
ACK：确认本次投递。先提交结果与终态，或持久化后续重试的交接，再确认原消息。
DLQ:死信队列,反复失败任务的收容所 + 告警工单,防毒丸任务无限重试拖垮全局。
消费者组:一组 Worker 自动分摊队列消息,天然负载均衡,扩容不用改代码。
HPA:K8s 水平自动扩缩容,按队列积压等指标自动加减 Worker。
背压:过载时向上游「顶回去」的信号——排队、拒绝、降级三选一,总比系统崩了强。
