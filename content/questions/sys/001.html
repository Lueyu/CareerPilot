系统设计 · Q5

设计一个分布式 Agent 调度系统

⭐⭐⭐⭐⭐ #分布式#调度#Agent
30秒电梯稿

"经典生产者-消费者模型升级版:任务投递到消息队列(Kafka/RabbitMQ),Worker 池消费执行 Agent 任务;用心跳 + 租约检测 Worker 存活,宕机任务自动重派;任务设计成幂等的,重复执行无副作用;队列本身提供背压,按优先级分队列保证重要任务先跑;死信队列收集反复失败的任务供人工介入。"

通俗类比

就是外卖平台调度骑手:订单进池(任务队列),系统派给顺路的骑手(负载均衡),骑手手机每几秒报一次位置(心跳),骑手失联超时就把订单转给别人(租约到期重派),高峰期接不过来就提示"高峰排队"(背压),同一个订单不会派给两个骑手各送一份(幂等),骑手三番五次送失败的订单进人工客服处理(死信队列)。

详细拆解

1. 整体架构

2. 任务生命周期(状态机)

pending → running → succeeded / failed / dead / cancelled。每次状态变更写 Redis + 异步落 DB。任务带唯一 task_id 和幂等键。

3. 容错三件套(核心考点)

  • 心跳:Worker 每 5s 向注册中心(etcd/Redis)上报;连续 3 次没报 → 标记下线,不再派新任务。
  • 租约(lease):Worker 领任务先"租"(设定 5 分钟租期并续期),执行到一半宕机租约自动到期,任务回到队列被别人领走。租约解决的是"任务不丢"且"不双跑"的平衡(到期前不重派,可能慢一点但安全;要严格单跑就配幂等)。
  • ACK 机制:任务完成才向队列确认;处理中宕机未 ACK,消息对其他消费者可见,自动重派。

4. 幂等性(必须主动讲)

重派会导致任务被执行两次,所以任务必须幂等:① 执行前用 task_id 在 Redis 抢 SETNX 锁,拿到才执行;② 副作用操作(发消息、写库)带幂等键去重;③ Agent 类任务的中间状态外置,重跑时从头初始化而非叠加。

5. 负载均衡与扩缩容

  • 消费者组天然分摊;同 hash key 进同队列保证局部有序(如同一会话的任务串行)。
  • 指标驱动扩缩容:队列积压长度 > 阈值 → 自动加 Worker(K8s HPA);连续空闲 → 缩容省钱。
  • Agent 任务耗 GPU/长时连接,扩缩容要考虑优雅下线:先摘流量、等在跑任务完成或迁移、再退场。

6. 背压与过载保护

  • 队列满 → 拒绝新任务并返回"排队中"凭证(削峰);或上游降级(如把 Agent 任务降级为简单 RAG 直答)。
  • Worker 内部再限并发(信号量控制同时在跑的 LLM 调用数),防止把 LLM 网关打挂。

7. 死信队列:重试 3 次仍失败的任务进 DLQ,告警 + 人工排查 + 修复后可重新投递。

面试官追问
Q:选 Kafka 还是 RabbitMQ?
Kafka:吞吐高、日志型、重放方便,适合海量任务流;RabbitMQ:延迟低、路由灵活、优先级队列原生支持,适合任务调度场景。Agent 调度一般任务量级不大但需要优先级和灵活路由,RabbitMQ/Redis Stream 更常用;要和大数据链路打通选 Kafka。
Q:Worker 执行到一半挂了,任务会重复执行吗?
会重派(租约到期),所以靠幂等保证重复执行无副作用——先答"会",再答"怎么防",显得考虑周全。
Q:长任务(几小时)怎么办?
任务拆阶段 + 定期 checkpoint 上报进度;租约按进度续期;支持暂停/恢复/取消;这类任务单独放大超时队列。
术语卡
租约:带有效期的执行权,到期自动回收重派。
幂等:同一操作执行多次效果和一次相同。
ACK:消费完成确认,未确认可被重投。
DLQ:死信队列,反复失败任务的收容所。
消费者组:一组消费者分摊队列消息。
HPA:K8s 水平自动扩缩容。
