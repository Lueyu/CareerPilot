系统设计 · Q12

设计一个支持语音交互的 Agent

⭐⭐⭐⭐ #语音交互#多模态#Agent
先说人话:这题问的是:把一个会打字聊天的 Agent,改造成「能打电话」的那种——用户开口说话,它听懂、想好、开口答,全程要快到像真人。面试官爱考,是因为它同时验两件事:你懂不懂流式流水线,以及知不知道语音特有的两个灵魂难题(用户说完没有?用户插嘴怎么办)。答错的暴露点:只会报一串模型名、没有延迟预算概念,或者压根没想过「静音多久算说完」这种问题——那就是没真做过语音链路。
30秒电梯稿

"全链路是 音频流 → VAD(检测说没说话)→ 流式 ASR(边说边出字)→ Agent(文本/多模态推理)→ 流式 TTS(边生成边合成播报)。设计的第一件事是亮延迟预算表:真人对话的回应间隔是 200ms~1s,我们必须把端到端响应延迟压到 < 1.5s 才不尬——所以每一环都必须流式化、流水线重叠执行,像流式备份一样边读边处理边下发,谁也不许攒大招。另外两个语音特有的难题必须主动讲:断句判定(静音多久算说完)和打断处理(barge-in,用户插嘴 Agent 要立刻闭嘴听)。讲出这两个人,面试官就知道你踩过语音的坑。"

通俗类比

先搞懂「流式化」(用流式备份想):老式备份是一根筋——把整个文件读进内存,再算去重,再复制,最后写远端,四个阶段首尾相接,备份窗口全耗在「白等」上。流式备份改成数据块像传送带一样流动:读到第 100 块时,第 1 块已经在写远端了,读、算、传、写四段重叠执行,窗口时间从「四段之和」变成「四段最大值+尾差」。语音 Agent 完全同理:ASR 不等用户说完才出字(partial 结果),LLM 不等整句定稿就开始预热,TTS 不等全文生成完就按句合成播放——哪里像:都是流水线重叠、都在和「总时长预算」搏斗。哪里不像:备份流水线算错了顶多重传一块(数据落盘前有校验兜底),语音流水线是「抢跑」——用户话还没说完就预热,赌错了要能干净地扔掉,所以要多一层「投机执行可能白干」的容错设计。

整个对话像同声传译:译员不等演讲者讲完整段才动笔(流式 ASR,边听边出文字);脑子里边组织译文(Agent 推理);译出一句立刻说出口,不用憋到最后一个字(TTS 按句合成,边生成边播);台下突然有人插话提问,译员立刻停下听着(barge-in 打断),还要记住自己刚才说到哪、被打断的语境是什么(写进对话历史,不然失忆)。再加一个分布式人熟悉的视角:断句判定本质是超时判活——「静音超过 500ms 判定说完了」和「心跳超时判定节点挂了」是同一类难题:阈值调小,误判多(把「嗯……让我想想」当成说完了,抢答打断用户);阈值调大,反应慢(冷场三秒,用户怀疑对面死机了)。你在容灾演练里怎么权衡 RTO 和误切换率,这里就怎么权衡。

详细拆解

第 0 步:整体链路与延迟预算(先亮预算表,非常加分)

和优化备份窗口一样,先做分解:端到端延迟 = 各环节之和,哪些能压、哪些能重叠,全靠这张表说话。真人对话的自然回应间隔在 200ms~1s 之间——超过 1.5s 用户就开始怀疑「对面卡了」,超过 3s 就会重说一遍(然后引发更糟的双向打断)。预算表如下:

环节耗时说明与压法
VAD 检测~30ms逐帧检测,基本不构成瓶颈
ASR 尾包~200ms说完后补最后一段音频的识别,流式模型决定它的下限
断句等待(静音 500~700ms)500~700ms预算表里最大的一笔——这就是为什么要与 Agent 预热重叠执行
Agent 首 token~300mspartial 置信度高就先预热检索,不等最终文本
TTS 首音~150msLLM 凑满一个短句就送去合成,不等全文
用户听到回应≈ 1.2~1.8s串行则是 2~4s+,重叠执行是本题的生死线
笨办法(串行,每一步都在白等上一步):
  用户说完 ──→ 等静音判定 0.6s ──→ ASR 定稿 0.2s ──→ LLM 全文生成完 2s ──→ TTS 全文合成完 1s ──→ 播放
  用户干等 ≈ 4s,已经想挂电话了

流水线(重叠,像流式备份一样让数据块流动起来):
  用户说话中 ── partial 已出「帮我查订单」──→ 预热检索/参数(投机执行,赌错就丢弃)
       └→ 静音到 0.6s 判定说完 → ASR 定稿 0.2s → LLM 首句吐出 → TTS 首句合成 → 用户听到
  用户听到 ≈ 1.2~1.8s:LLM 第 2 句还在生成时,第 1 句已经在播放了

1. 流式 ASR(耳朵)

  • 选支持 partial hypotheses 的流式模型(如 Whisper 的流式化方案、专用实时 ASR 引擎或厂商实时接口):边收音频边出「暂定文本」,每 100ms 刷新一次,说完后出最终定稿。partial 和最终文本之间可能变(「帮我查订」→「帮我查订单」),下游所有投机预热都必须抱着「随时会作废」的心态。
  • ASR 纠错:数字、专有名词、中英混杂是重灾区——用 LLM 上下文做后处理重写(把「幺零零八六」规范成「10086」)。这一步很像数据入库前的清洗管道:识别是「采」,纠错是「洗」,别让脏数据直接进 Agent。

2. VAD 与断句(语音交互的灵魂难题)

  • 静音 500~700ms 判定说完(可按场景调:客服场景用户说得慢、爱停顿,就放宽到 800ms;指令场景「开灯」这种短口令,可以收紧)。本质是超时判活:和心跳超时一样,没有完美值,只有按误判代价调的权衡值。
  • 防误断:用户说「嗯……让我想想」这种带思考停顿的,纯静音门限必挂;加一道 LLM 语义完整性判定——partial 文本像不像一个说完整的句子?像就提前提交,不像就继续等。这是在「超时」之外加的「一致性校验才放行」。
  • 对话式填充:判定期间 Agent 先回一句「嗯,我查一下」——这是语音体验版的 loading 动画。用户对 3 秒沉默会恐慌,但对一句「稍等」能容忍 10 秒,延迟预算不够就用心理预算补。

3. 打断(barge-in,语音交互的成人礼)

  • Agent 播报期间 VAD 持续开着,检测到用户语音(能量 + 语义双确认:既有音量又通过一个小分类器确认是人声而不是键盘声/电视声,防环境音误触发)→ 立即停止 TTS 播放。这像抢占式调度里的「取消传播」:取消信号要沿流水线往下游推——丢弃未播的合成音频、暂停生成、清空播放队列,哪一段漏了取消,就会出现「用户都插完话了,Agent 还在自己念」的灵异现场。
  • 被打断的上下文要写进对话历史(「Agent 说到一半被用户打断,用户说了 X」)。这像作业被杀也要留审计日志:不记录,Agent 下一轮就失忆,答非所问。打断不是异常,是语音对话的常态交互方式——真人聊天 40% 的轮次都是打断,不支持 barge-in 的语音 Agent 就是个自说自话的复读机。

4. 流水线重叠(压延迟的关键)

  • Agent 的首 token 不等最终 ASR 文本——partial 置信度高就开始预热检索。这是标准的投机执行:赌用户后半句不改口,赌赢省下几百毫秒,赌错就把预热结果丢弃重来。你的预算表里断句等待占 500~700ms,不靠重叠把它吃掉,端到端根本进不了 1.5s。
  • LLM 输出按句子切分喂 TTS:凑满一个短句就送去合成播放,生成/合成/播放三级流水线并行——第 3 句在生成时,第 1 句在播放,第 2 句在合成。注意 TTS 不能按 token 切(会播得结结巴巴),要按标点/语义断句切,这是实践中最常见的坑。

5. 工程细节(这些不讲,面试官默认你没做过)

  • 回声消除(AEC):Agent 自己的声音从喇叭出来、又被麦克风收进去,不消掉就会「自己打断自己」甚至无限循环——和网络里的广播风暴是同一类问题,解法思路也一样:把已知是自己的信号减掉/过滤掉,只放行外来输入。
  • 丢包补偿(PLC):弱网下音频包丢了,做补偿插值防识别断崖,别让 20% 丢包直接毁掉整句识别。
  • TTS 音色/语速可配(品牌一致性 + 不同场景语速不同)。
  • 全链路 trace 打点:把延迟分解到 VAD/ASR/断句/推理/TTS 每一环——和优化备份窗口先分段计时是同一个职业习惯,没有测量就没有优化。
面试官追问
Q:为什么不直接用语音到语音的端到端模型(如 GPT-4o realtime)?
人话:端到端确实更快、更有感情,但贵、不可控、没法插业务,所以主流工程还是级联。类比:像「存储一体机」和「自建分布式存储」之争——一体机开箱即用、路径短,但你插不进自己的去重/加密逻辑;自建链路每一层都可替换、可审计,代价是自己扛运维。技术:端到端 语音到语音模型延迟更低、保留语气情绪,但难插工具调用/检索、成本高、行为不好做业务约束(比如风控话术必须逐字审核)。当前主流仍是 ASR→LLM→TTS 级联:可插拔、可观测、每层独立优化;实时多模态模型演进很快,值得持续跟进。答出这个 trade-off 很加分——说明你不是只看模型排行榜。
Q:怎么进一步把 1.5s 压到 1s 以内?
人话:预算表里最大一笔是「等静音判说完」,所以先消灭等待,再给高频问题开绿色通道。类比:像压 RTO:先把串行恢复步骤改成并行,再对最常恢复的那几类业务做预置快照,一键秒回。技术:① 断句与 Agent 重叠执行(LLM 判定语义完整即预热,不等静音超时);② 高频问题预合成音频缓存,命中直接播放(语义缓存思路);③ TTS 换低延迟神经 vocoder,压首音;④ 简单问题走小模型旁路(意图识别+模板回答 < 500ms),复杂问题才进大模型主路。核心还是那句:每压一项都要有 trace 数据证明压到位了。
Q:ASR 识别错了,Agent 就答错了怎么办?
人话:耳朵听错字,回答必然跑偏——能纠就纠,纠不动就确认,千万别硬答。类比:像从损坏介质里读数据:先纠错码自纠(ECC),纠不动就报错让上层重试(向源端重新发起请求),而不是拿着疑似损坏的数据直接跑恢复。技术:① 上下文纠错:LLM 拿对话历史重写 ASR 输出(数字/专名按上下文修正);② 低置信度时 Agent 主动复述确认:「您是想查 10086 的订单吗?」——一次确认的代价远小于答错重来;③ 线上统计纠错前后的一致率,把 ASR 错误率当一级监控指标,高了换模型/加领域词表,而不是等客诉。
Q:你用 partial 结果投机预热,用户后半句改口了,怎么办?
人话:抢跑赌错很正常,关键是丢弃要干净、代价要小到愿意赌。类比:分布式系统里的经典权衡——用缓存先答、被标记失效后回源;投机执行赌错就回滚,只要赌对时省的时间远大于赌错时浪费的,期望就是赚的。技术:① 预热只做「只读、可丢弃」的事:检索结果、会话上下文组装、Prompt 骨架,不做任何落盘/外发副作用;② 定稿文本一到,和 partial 做一致性比对,一致就复用预热成果,不一致整体丢弃重来——预热成本是几百毫秒检索,不是一次生成,赌错不肉疼;③ 别对「高代价动作」投机:涉及下单、改配置的意图,必须等 ASR 定稿+置信度达标才执行。
术语卡
VAD:Voice Activity Detection,逐帧检测「有没有人声」,是断句判定和打断检测共同的底座。
Partial 结果:流式 ASR 的暂定识别文本,会随音频继续到达到而自我修正,下游用它投机预热必须能随时作废。
Barge-in:用户插嘴打断,Agent 立刻停播、清队列、转收听态——语音对话的常态而非异常。
AEC:回声消除,把 Agent 自己播出去又被收回来的声音减掉,防「自己打断自己」的死循环。
断句判定(端点检测):静音持续多久算「说完了」的判定,本质是超时判活的权衡题,没有完美值。
投机执行:不等输入定稿就提前预热,赌对了省延迟,赌错了干净丢弃——语音链路压延迟的核心手法。
