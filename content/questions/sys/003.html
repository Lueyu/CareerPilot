系统设计 · Q12

设计一个支持语音交互的 Agent

⭐⭐⭐⭐ #语音交互#多模态#Agent
30秒电梯稿

"全链路是 音频流 → VAD(检测说没说话)→ 流式 ASR(边说边出字)→ Agent(文本/多模态推理)→ 流式 TTS(边生成边合成播报)。核心指标是端到端响应延迟 < 1.5s 才像真人对话,所以每一环都必须流式化、流水线重叠执行;另外两个语音特有的难题:断句判定(静音多久算说完)和打断处理(barge-in,用户插嘴要立刻闭嘴听)。"

通俗类比

就是同声传译:译员不等演讲者说完一句才开始(流式 ASR,边听边出文字);脑子里边组织译文(Agent 推理);译出一句就立刻说,不用憋到最后(TTS 分句流式);台下听众突然插话提问,译员立刻停下来听(barge-in 打断)。任何一环憋着攒大招,对话就尬住了。

详细拆解

1. 整体链路与延迟预算(先亮预算表,非常加分)

2. 流式 ASR

  • 选支持 partial hypotheses 的流式模型(Whisper 流式化方案或专用实时 ASR 如 FunASR/Paraformer 流式、厂商实时接口),边收音频边出"暂定文本",说完出最终文本。
  • ASR 纠错:数字、专有名词、中英混杂是重灾区——用 LLM 上下文做后处理重写(把"幺零零八六"规范成"10086")。

3. VAD 与断句(语音交互的灵魂难题)

  • 静音 500~700ms 判定说完(可按场景调:客服场景用户说得慢就放宽)。
  • 防误断:说"嗯……让我想想"这种停顿;用 LLM 判断"句子是否语义完整"再决定是否提交。
  • 对话式填充:判定期间 Agent 先回"嗯,我查一下"(语音体验版 loading 动画)。

4. 打断(barge-in)

  • Agent 播报期间 VAD 持续开着,检测到用户语音(能量+语义双确认,防环境音误触发)→ 立即停止 TTS 播放,丢弃未播的合成音频,进入收听态。
  • 被打断的上下文要记进对话历史("Agent 说到一半被用户打断,说了 X"),不然 Agent 会失忆。

5. 流水线重叠(压延迟的关键)

  • Agent 的首 token 不等最终 ASR 文本——partial 置信度高就开始预热检索。
  • LLM 输出按句子切分喂 TTS:凑满一个短句就送去合成播放,生成/合成/播放三级流水线并行。

6. 工程细节:回声消除(AEC,防 Agent 自己的声音被当作用户说话);丢包补偿(弱网音频 PLC);TTS 音色/语速可配;全链路 trace(把延迟分解到每一环,不然没法优化)。

面试官追问
Q:为什么不直接用语音到语音的端到端模型(如 GPT-4o realtime)?
端到端延迟更低、保留语气情绪,但可控性差(难插工具/检索)、贵、不好做业务逻辑。当前主流工程仍是 ASR→LLM→TTS 级联,可插拔可控;实时多模态模型在快速演进,值得跟进——答出这个 trade-off 很加分。
Q:怎么进一步把 1.5s 压到 1s 以内?
① 断句与 Agent 重叠执行(语义完整即预热);② 高频问题预合成音频缓存;③ TTS 用低延迟神经 vocoder;④ 简单问题走小模型旁路(意图识别+模板回答 < 500ms)。
Q:ASR 识别错了,Agent 就答错了怎么办?
低置信度时 Agent 主动复述确认("您是想查 10086 的订单吗?");上下文纠错重写;线上统计 ASR 纠错前后的一致率。
术语卡
VAD:Voice Activity Detection,检测有没有人声。
Partial 结果:流式 ASR 的暂定识别文本。
Barge-in:用户打断,Agent 立刻闭嘴。
AEC:回声消除,防自言自语循环。
