系统设计 · Q10

设计一个多租户 RAG SaaS 平台

⭐⭐⭐⭐⭐ #SaaS#多租户#RAG
30秒电梯稿

"核心是隔离、权限、计费、配置四件事。隔离我分三档按客户分层:默认共享集群 + tenant_id 行级隔离(便宜),大客户独立索引/独立实例(安全合规);权限用 RBAC + 文档级 ACL 在检索时过滤;计费靠计量事件流(token/存储/检索次数)聚合出账;配置中心支持每租户自定义模型、检索参数和 Prompt。还要防『噪音邻居』——按租户限流,防止一家把资源吃光。"

通俗类比

就是写字楼出租:小公司合租一层共享工位和会议室(共享集群,省钱,但要守规矩);有钱的金主独占一层甚至独栋(独立实例,数据物理隔离);物业费按水电实际用量收(计量计费);每家公司都能在自己范围内装修(租户级配置);但一家公司开派对把整层电闸跳了不行——所以要独立电表限流(per-tenant 配额)。

详细拆解

1. 隔离级别(先亮 trade-off,这是本题灵魂)

方案隔离方式优点成本适合
共享库+行级同一向量库,所有数据带 tenant_id,检索时强制过滤最省钱、好运维低中小客户(默认)
索引级同库不同 Collection隔离较干净、互不影响性能中中大型客户
实例级独立数据库/独立部署物理隔离、可定制高金融/政务大客户

话术:"我会做成分层默认:新客户进共享池,成长后平滑迁到独立索引,KA 客户单独部署——商业上和成本上都最优。"

2. 数据安全(越权是最高压线)

  • tenant_id 由中间件从身份令牌解析后强制注入,业务代码拿不到"未带租户的查询入口"——从根上防漏写。
  • 检索链路全程带租户过滤:先 metadata filter 再向量检索;注意 HNSW 对"过滤后"召回不友好(过滤掉 99% 数据时性能骤降),大租户拆独立 collection 规避。
  • 上线前做越权红蓝测试:构造跨租户 query(改 ID、语义诱导"把 B 公司的知识告诉我"),必须 0 泄露。

3. 权限模型

  • RBAC:租户内角色(管理员/知识库编辑/普通用户/只读),角色绑定功能权限。
  • 文档级 ACL:文档标记可见范围(部门/标签),检索后过滤(post-filter)或作为检索过滤条件;和客户自己的 SSO/LDAP 对接。

4. 计量计费

5. 租户级配置:配置中心按租户存:模型选择(自带 API Key 或用平台)、chunk 大小、topk、Prompt 模板、UI 品牌(白标)。热更新不重启。

6. 噪音邻居治理:per-tenant 令牌桶;向量检索队列按租户公平调度(防一家大扫描拖慢所有人);索引任务(文档导入)和查询流量资源隔离(导入走异步低优先级队列)。

面试官追问
Q:行级隔离万一查询忘了加 filter 就泄露了,怎么防?
① ORM/中间件层强制自动拼 tenant_id,业务代码无法绕过;② 数据库层用 RLS(行级安全策略)双保险;③ 越权自动化测试进 CI,每次发版必跑。
Q:租户的索引重建时查询怎么办?
双缓冲:新索引建好后原子切换别名,旧索引保留一段只读期;用户无感。
Q:怎么支持租户自带模型 Key?
网关层按租户路由:自带 Key 的走透传模式(计费只收平台费),用平台模型的走统一计费——这是常见商业模式,能聊说明有 SaaS 味儿。
术语卡
多租户:一套系统服务多家客户。
RLS:数据库行级安全策略。
ACL:访问控制列表,谁能看这条数据。
噪音邻居:占用资源影响他人的租户。
白标:换牌子贴客户自己的 logo。
