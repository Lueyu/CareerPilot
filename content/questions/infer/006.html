Agent核心 · Q24

你怎么处理响应速度与推理精度之间的tradeoff？是先召回再精排，还是单次生成？

⭐⭐⭐ #性能优化#权衡 字节(真题)
先说人话:这题问的是:当「答得快」和「答得对」打架,你怎么排兵布阵——所有问题都先查资料再答(慢但稳),还是都张口就答(快但易错)?面试官爱考,因为它考的是工程权衡而非背参数;答「永远检索」或「永远直答」,都暴露同一个问题:没扛过真实流量。
30秒电梯稿

"这题的答案不是二选一,而是分级路由:先判断问题难不难——简单问题走'单次生成'直接答,复杂问题走'先召回再精排'的漏斗。检索链路上,召回要宽(保证查全)、精排要准(保证查准),用粗筛精排把昂贵的精排只压在少量候选上;分类器拿不准的一律走完整链路——宁可慢一点,不可翻车。响应速度再叠加语义缓存、流式输出(TTFT)、模型分级、并行四招;所有提速都带质量护栏——每动一个参数就跑黄金集回归,拿 Recall 和答案质量说话。一句话:用最便宜的一步先砍掉 90% 的候选,再用最贵的一步精挑最后的 10%。"

通俗类比

先把三个主角认清楚(用你天天干的活想)。「单次生成」就是你凭经验直接回答——像被问「备份机房在几号楼」,张口就来;「先召回再精排」是先查作业日志、翻告警记录,把证据拼齐了再下结论——快问快答靠记忆,查证回答靠证据链。难就难在你事先不知道这题属于哪类,所以需要一个路由。路由像容灾预案分级:核心库配两地三中心、秒级切换,边缘系统冷备几小时恢复。哪里像:都是按「事情的重要程度」决定投入多重的资源,不让小事占用大预案。哪里不像:容灾分级是按系统静态规划的,一年审一次;Agent 的路由是每个请求在线判断、毫秒级出结论,判错的代价不是「恢复慢了」,而是「答非所问」——所以它必须保守。

「召回+精排」你天天在用它的孪生兄弟——块级去重:先算数据块指纹,在索引里粗筛出「可能重复」的候选块(快,可能有误报,但绝不漏报);再对少量候选做逐字节比对,给最终裁决(慢但准)。召回扮演指纹筛查:和 布隆过滤器 是同一种哲学——宁可多报,绝不漏报;精排扮演逐字节比对:贵,所以只压在十来条候选上。哪里像:两把工具成本差着数量级,便宜的做海选、贵的做终审。哪里不像:去重的比对只回答「同/不同」,是二值判决;精排输出的是「按相关度排好序的清单」,是个排序问题。

提速的两招也有你地里的影子。语义缓存像恢复时直接挂已有快照:同样的恢复请求不重跑整条数据流,挂载即用——但快照认「完全相同的请求」,语义缓存认「意思相近的问题」,所以它比快照多一种风险:把相似但不同的题答串了。流式输出像恢复进度条:用户看到「恢复中 37%」就不焦虑了——他心里的计时器从「等多久才有结果」变成「等多久才开始出结果」,这个「开始」的时刻就是 TTFT。

详细拆解

1. 先讲清 trade-off 的本质

  • 响应速度:用户感知的是 TTFT(首字时间)加总时长,不是链路内部有多复杂;每多一跳检索、多一步精排,都会直接堆到延迟上。
  • 推理精度:三个来源——检索充分(证据找齐)、模型够强、上下文完整(该拼的都拼进去);每加一层,都更慢更贵。
  • 串行叠加的坑:这条链路是串行的,各段的长尾请求会互相叠加——三段各自 P95 都还行的流程,串起来 P95 就不好看了,和备份流水线「读盘→压缩→写带」各阶段超时叠加是同一个教训。
  • 正确姿势是按难度把请求分流,而不是给所有请求套同一套最重/最轻的链路——让 70% 的简单问题为 30% 的复杂问题陪跑,和让 30% 的复杂问题裸奔,都是浪费。

2. 先召回再精排 vs 单次生成(怎么选)

维度先召回再精排(两阶段)单次生成(无检索)
适用需要外部知识/多步推理的复杂问题简单问答、闲聊、通用常识
精度高(有事实支撑,幻觉低)一般(纯靠模型记忆,易幻觉)
延迟多一跳检索 + 重排,略慢最快,直接生成
成本检索便宜,但上下文可能更长无检索开销
可控性可追溯来源、可审计黑盒,难引用
典型流量占比约 30%(知识密集型问题)约 70%(多数请求其实很简单)

结论:不该全链路都检索,也不该全都不检索——用难度分类器/规则路由,拿不准时走完整链路(宁可慢一点,不可翻车)。

为什么默认值必须偏保守?因为两类错误的代价不对称:误走重链路,代价是白慢几十毫秒(挨句吐槽);误走轻链路,代价是幻觉答案直达用户(砸信任)。这和容灾切换决策一模一样——误切换是白忙一场,漏切换是真故障裸奔,两边代价不对称,默认值就没有第二种选法。

3. 漏斗式检索(速度和精度的平衡点)

路由 + 漏斗的全景(数字为量级示意,体会分工即可):

              query 进来
                │
                ├─ 语义缓存命中(约 30%):≈50ms 返回,后面整条链路都不用走
                │
                ├─ 判定「简单」(约 70% 流量:闲聊/常识/单点事实)
                │     └→ 小模型直接生成 + 流式输出 → TTFT ≈ 200ms   [单次生成路线]
                │
                └─ 判定「复杂」(约 30% 流量:要外部知识/时效/可引用)
                      │  (难度判断与检索预热并行,判断耗时基本白送)
                      ├→ 召回:向量 + BM25 多路并行,取 top50~100   ~50ms   [宽进·宁多勿漏]
                      ├→ 粗排:轻量打分,收到 top20~50             ~20ms   [收口]
                      ├→ 精排:Cross-Encoder 只算 top5~10           ~80ms   [贵刀·只切小块]
                      └→ 注入生成:top3~5 拼进 Prompt,流式输出 → TTFT ≈ 400ms
  • 召回要查全(宁多勿漏),精排要查准(宁精勿多)——两者的优化目标不同,所以要分开调。
  • 精排模型最贵,所以要把它压在最少候选项上:召回 100 条里只精排 10 条,延迟和精度都能顾住。

为什么非得两把刀?因为两类打分器的成本差着两三个数量级。召回用的双塔模型(代表作是 Sentence-BERT)把文档侧 Embedding 全部离线预计算、提前入库,查询时只算一次 query 向量再做 ANN 近邻搜索,毫秒级扫完百万级语料;而 Cross-Encoder 要把「query + 文档」拼在一起送进模型逐对打分,候选有 100 条就是 100 次前向推理,百毫秒起步、还不能预计算。所以工程解永远一样:便宜的刀做海选(全库扫一遍),贵的刀做终审(只看前十)——两阶段不是设计美学,是成本结构逼出来的必然解,正如去重流程里指纹比对永远排在逐字节比对前面。

召回这一层还要多路并联:向量检索抓「意思像」,BM25 抓「术语一字不差」,两路各取所需再用 RRF 融合——单一通道都有盲区:向量可能漏掉专有名词精确匹配的文档,词法可能漏掉换了说法的同义问题,所以重要场景都上混合检索。

4. 响应速度的四招(叠加在路由之上)

  • 语义缓存:对 query 算 Embedding,与已缓存问题相似度过阈值就直接复用答案,命中的流量整体 50ms 内返回——单点 ROI 最高,先做它。但要防「相似但不是同一个问题」的错配:只缓存高确定性、无个性化、无时效的答案,带用户信息/实时数据的不进缓存,源文档更新时主动失效。快照回挂的思路,但比快照多了一层「意思相近」的模糊匹配,风险也藏在这。
  • 流式输出:用户感知的是首字时间而不是总时长——TTFT 一达标,后面慢慢吐字,用户体感就是「一直在干活」。再配合 Prompt 里「先给结论,再给依据」,结论几百毫秒内就流出来了。
  • 模型分级:分类器把约 70% 的简单流量路由到小模型,TTFT 快 2~4 倍;难度判断本身要够快(小分类器,且与检索预热并行),别让「判断要不要快」这件事本身变慢。
  • 并行:向量与 BM25 多路并行、检索与 Prompt 骨架准备并行、query 改写与「用原始 query 先检索一轮」并行——串行改并行是白捡的延迟,一行硬件不加。

5. 质量护栏(提速的底线)

每次调参(降 ef_search、砍重排、缩 top-k)都跑黄金集回归(Recall@k + 答案质量),质量掉超阈值就回退;线上走 A/B 实验看最终指标。性能优化必须带着精度护栏做,否则就是用精度换速度的假优化。

用你地里的老规矩收尾:没演练过恢复的备份不算备份——同理,没跑过黄金集的提速不算提速,它只是把错误答案答得更快了。面试时能开口就讲「先分流再漏斗:贵的模型只碰少量候选,拿不准默认全链路,每个旋钮都带 Recall 护栏」,面试官就知道你真扛过线上流量。

面试官追问
Q:单次生成不是更快更简单吗,为什么还要检索?
人话:该单次生成的确实该单次生成,所以答案从来不是二选一,是分流;但需要外部知识的问题必须检索,因为单次生成有三个致命伤。类比:运维问题同理——「备份机房在几号楼」你直接答,「周三的全量作业为什么失败」你必须先查作业日志、再查存储侧告警,拼齐证据才敢开口;不查就答就是瞎猜。技术:三个致命伤——幻觉(模型编造)、知识过时(训练截止日之后的事一无所知)、无法引用(黑盒,答了也难审计)。时效、专有、精确事实类问题必须走检索,慢几十毫秒换正确性,这笔账怎么算都划算。
Q:召回和精排的延迟怎么压?
人话:各自对症下药——召回靠「少算」,精排靠「少喂」。类比:像压备份窗口:全量扫描先靠指纹索引跳过重复块,确认比对只挑可疑块细看;没人对全库逐字节。技术:召回侧:HNSW 降 ef_search、向量量化、缩小 top-k、向量与 BM25 多路并行;精排侧:只重排 top 10 而非 top 50、换轻量 Rerank 模型、或先粗排收量再精排。原则不变:最贵的模型只见最少的候选,延迟和成本一起降。
Q:怎么判断一个 query 该走哪条链路?
人话:规则兜底 + 小模型分类,拿不准的一律默认完整链路。类比:像告警分级:明确的低危告警自动闭环,明确的高危立刻拉群处理,分不清的按高危走——宁可虚惊一场,不可漏报一次。技术:规则先兜底:问候/闲聊直接单次生成;含时间敏感词、专有名词、数值类问题强制检索;剩余灰区交小分类器,置信度低于阈值默认完整链路。上线后盯两类错误率:直答后被用户改写重问的(该检索没检索,伤信任),和检索了却答非所问的(浪费但可控)。
Q:两阶段有个死穴——正确答案在召回阶段就被漏掉了,精排再强也救不回来,怎么兜底?
人话:对,这是两阶段检索的天花板:精排只会在召回给的候选里挑,海选漏了,终审再准也没用,所以召回必须重点保护。类比:像恢复时备份目录索引不全:没登记的备份集,校验做得再严也找不到它——所以目录条目宁滥勿缺,海选也要同样保守。技术:① 召回放宽 top-k、宁多勿漏,延迟预算优先留给召回;② 多路召回(向量+BM25+规则)用 RRF 融合,一路漏了另一路兜;③ 黄金集盯 Recall@k,召回调参优先保查全率;④ 线上监控「检索后仍答不出」的负反馈(点踩/重问),反推召回盲区、补语料或加召回通道。
术语卡
召回:用便宜的向量/BM25 从百万候选里快速海选,求全不求精——宁多勿漏,它是整条链路精度的天花板。
精排:用昂贵的 Cross-Encoder 对少量候选精算排序,求准不求快——贵刀只切小块。
两阶段检索:先粗筛后精排,本质是成本差两三个数量级的两把刀,各干各的活。
双塔模型:文档向量离线预计算、查询时只算一次 query 向量,便宜,天生适合做召回。
路由:按问题难度把请求分到不同链路——速度与精度权衡的第一道闸门。
语义缓存:按「意思像不像」复用旧答案,单点 ROI 最高的提速招,但要配阈值与失效策略防错配。
黄金集回归:一组人工标注的标准问答对,每次提速调参后跑一遍,质量掉线就回退参数。
TTFT:首 token 时间,流式时代用户真正感知的「开始回答」。
Recall@k:前 k 结果的查全率,每个提速旋钮的精度护栏。
