工程实践 · Q10

如何实现跨模型的统一 API?

⭐⭐⭐⭐ #API设计#适配器模式#统一接口
30秒电梯稿

"标准适配器模式:定义统一抽象层(chat/ stream/ embed/ 工具调用接口),每个供应商一个 Adapter 做参数翻译、响应翻译和错误码归一化;OpenAI 的请求格式当事实标准(业内通用,新供应商基本都兼容它,适配成本最低);能力差异不做'假统一'而是能力协商——不支持 function calling 的模型自动降级 ReAct 文本协议;加健康检查和路由,新模型接入≈写一个 Adapter + 注册配置。"

通俗类比

就是万能转接头(出国旅行插头转换器):你的电器插头(业务代码)永远是中国标准(统一接口),到不同国家插不同转接头(Adapter)——回国不用换电器,新去一个国家只要新买一个转接头。最忌讳每个国家单独买一套电器(每个供应商写一套业务代码)。

详细拆解

1. 抽象层设计(接口定义)

class LLMClient(ABC):
    def chat(messages, tools=None, **params) -> LLMResponse     # 同步
    def stream(messages, tools=None, **params) -> Iterator[LLMDelta] # 流式
    def embed(texts) -> list[Vector]
    # 统一返回:content / tool_calls / usage{in,out} / finish_reason
  • 统一参数:通用的直接传,特有的放 extra(如某家的 top_k)——别为了统一丢掉特色能力。
  • 以 OpenAI 格式为基准的好处:绝大多数国产模型/推理框架(vLLM、Ollama)都提供 OpenAI 兼容端点,一层 Adapter 通吃,甚至很多供应商零成本接入。

2. 错误码归一化(比参数映射更容易被漏掉,却更重要)

统一错误枚举OpenAIClaude处理建议
RATE_LIMITED429429退避重试
CONTEXT_OVERFLOW400 (max tokens)400 (prompt too long)截断/压缩后重发
CONTENT_FILTEREDcontent_policyrefusal不重试,改写或降级
AUTH_FAILED401401告警,不重试

把"上下文超长"归一化特别有价值:上层可以统一实现"自动摘要压缩后重试"的通用逻辑。

3. 能力协商与降级兼容

  • 每个 Adapter 声明能力矩阵:支持 system role?支持 tools?最大上下文?支持 JSON mode?
  • 运行时按能力自动降级:不支持 system → 拼进首条 user;不支持 FC → 切换 ReAct 文本协议(Prompt 里教模型输出工具调用格式,正则解析);不支持 JSON mode → 修复性解析+重试。
  • 能力变化只改 Adapter 声明,业务代码零改动。

4. 工厂 + 配置路由

  • 注册表:model_name → Adapter 实例(带连接池);新增供应商 = 实现 Adapter + 配置注册,业务代码一行不动。
  • 路由策略挂在工厂之上:按用途/成本/可用性选实例(和 LLM Gateway 配合,见第一部分 Q6)。

5. 测试与质量

  • 契约测试:同一批请求过所有 Adapter,断言统一响应结构一致(字段齐全、语义一致)。
  • 黄金用例集:工具调用、多轮、长文本、中文等各一,新 Adapter 必须全绿。
面试官追问
Q:统一会不会抹平各家优势功能?
核心接口统一,特色能力通过 extra 参数和能力协商暴露(比如 Claude 的 prefill、思考模式),不搞"削足适履"的假统一;判断标准:80% 场景纯统一,20% 高级能力可按模型寻址。
Q:流式响应的适配有什么坑?
各家的 chunk 结构差异大:增量内容字段不同、工具调用可能跨多个 chunk 分片(要聚合)、finish_reason 语义不一;统一 LLMDelta 结构 + Adapter 内做聚合缓冲,坑基本都能填。
术语卡
Adapter 模式:接口翻译层,桥接不同实现。
ReAct:用文本协议模拟工具调用,兼容无 FC 模型。
契约测试:验证所有实现符合同一契约。
