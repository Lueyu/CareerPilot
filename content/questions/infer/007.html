Agent核心 · Q31

如果Agent推理API需要低延迟响应，你会从哪些方面做系统级优化？

⭐⭐⭐ #性能优化#系统设计 字节(真题)
30秒电梯稿

"我会先把延迟拆成 TTFT(首 token)和 TPOT(每 token)分别治理,再分四层优化:① 模型服务层——上 vLLM/TensorRT-LLM 做连续批处理和 PagedAttention,配 INT8/INT4 量化、投机解码;② 缓存层——KV cache 复用 + prompt 前缀缓存 + 语义缓存,把重复计算省掉;③ 网络层——流式输出 + 长连接复用 + gRPC,把首字时间压到几百毫秒;④ 调度层——模型分级路由,简单请求走小模型。核心心法:延迟和吞吐是 trade-off,低延迟场景宁可牺牲一点吞吐。"

通俗类比

把 LLM 推理想成一个打字员打字:首字时间 TTFT 是"你按下开始后他多久打出第一个字",每 token 时间 TPOT 是"之后每个字间隔多久"。要让他"快"起来,要么打字更快(量化、换更快的硬件/算子)、要么把已经打过的草稿直接复用别重打(KV cache / 前缀缓存)、要么同一个问题只打一次,后面的人直接抄答案(语义缓存)、要么简单问题派给打字快的实习打字员(模型分级)。

详细拆解

1. 先拆延迟构成(面试第一句,立刻显专业)

  • TTFT(Time To First Token):请求到首 token 的时间,受 prefill(预填充)阶段主导——要把整个 prompt 一次性算完 KV 才能开始解码。prompt 越长、首字越慢。
  • TPOT(Time Per Output Token):之后每个 token 的间隔,受 decode(解码)阶段主导——每生成一个 token 都要读一次整个 KV cache,是访存密集型。
  • 总延迟 ≈ TTFT + 输出 token 数 × TPOT。优化要先搞清楚你的瓶颈在 prefill 还是 decode。

2. 模型服务层(最核心)

  • 连续批处理(Continuous Batching):传统静态批处理要等整批都做完才释放;连续批处理是"边生成边插新请求",GPU 空出来一个位置就补一个,吞吐提升几倍,也间接降低排队延迟。
  • PagedAttention:把 KV cache 切成固定大小的"页",按需分配、复用(类似操作系统分页),消除显存碎片,能塞进更大的 batch。
  • 量化(INT8/INT4):权重/激活从 FP16 压到低精度,显存和带宽都省,延迟明显下降;代价是精度轻微损失,可用 GPTQ/AWQ 等方案把损失压到很小。
  • 投机解码(Speculative Decoding):用一个小模型"草稿"先快速猜一串 token,再用大模型一次性验证——猜对的直接采纳,延迟大幅下降且不影响输出质量。
  • 张量并行 / 流水线并行:超大模型切到多卡,但要注意跨卡通信本身有开销,小模型未必划算。

3. 缓存层(省掉重复计算)

缓存类型缓存什么效果
KV cache 复用同一会话多轮对话的前缀 KV多轮对话只算新增部分,TTFT 大降
Prompt 前缀缓存公共系统提示词/长上下文所有请求共享,prefill 快一大截
语义缓存相似问题→现成答案直接短路,连推理都不做

4. 网络与 IO 层

  • 流式输出:首 token 一到就推给前端,用户感知延迟 = TTFT 而不是总时长。
  • 长连接复用:复用 HTTP 连接或走 gRPC 双向流,省掉反复握手。
  • 就近部署 / 减少跳数:网关和应用尽量贴近推理集群,省网络 RTT。

5. 调度与路由层

  • 模型分级路由:简单请求(意图识别、分类、抽取)走小模型,只有复杂推理才上大模型——小模型延迟往往低一个数量级。
  • 请求优先级队列:实时交互请求优先,离线批处理任务让路。
  • 超时与降级:大模型超时自动切备胎模型,保证可用性。

6. 提示词 / token 压缩

  • 缩短 prompt、历史对话做摘要、只传必要上下文——token 少了,prefill 和 decode 都快。
  • 约束输出长度(max_tokens)、用结构化输出减少无谓生成。
面试官追问
Q:连续批处理为什么能降延迟,不是反而要攒一批吗?
关键在不等整批结束:传统方案里一个 batch 里只要有请求没生成完,新请求就得排队等;连续批处理是迭代级的——每生成一个 token 就检查有没有新请求可以插进来、有没有请求已经结束,GPU 永远保持"满员但不堵塞"。它的主要收益是吞吐,延迟受益于"少排队";真正为了单请求延迟,还要靠投机解码、前缀缓存这些"算得更少"的手段。
Q:投机解码会不会反而变慢?
在decode 阶段、显存带宽受限时通常能加速:一次验证多个草稿 token 是"大矩阵运算",比一个个 token 串行读 KV 更高效;草稿命中率越高收益越大。但如果草稿模型选得太差、接受率极低,多算的部分就是纯开销,会变慢——所以要选对草稿模型,一般经验接受率 50%+ 才有正收益。
Q:量化会不会影响 Agent 的工具调用准确率?
会有一定风险。INT8 对多数任务损失很小;INT4 在复杂推理、精确格式(JSON 工具调用)上更容易出错。实践上通常让量化模型只承接简单任务,复杂推理和工具调用路由到全精度/高精度模型,分级处理。
术语卡
TTFT:首 token 时间,用户感知延迟的核心。
TPOT:每输出 token 时间,反映 decode 效率。
PagedAttention:KV cache 分页管理,消除显存碎片。
连续批处理:迭代级动态插拔请求,GPU 不空等。
投机解码:小模型猜草稿、大模型一次验证。
量化:低精度存储计算,省显存省带宽换少量精度。
