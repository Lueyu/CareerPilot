系统设计 · Q6

设计一个 LLM Gateway(API 网关)

⭐⭐⭐⭐ #网关#限流#负载均衡
先说人话:这题在问:全公司的模型调用都要过一扇统一大门,这扇门怎么修——协议翻译、故障切换、限流、记账、缓存一把抓。面试官爱考它,是因为一题就能验分布式基本功:答成"就是个反向代理转发请求"的人,暴露的是没做过入口层/平台层服务,追问两句限流和熔断细节就露馅。
30秒电梯稿

"LLM 网关是所有模型调用的统一入口,解决五个问题:① 协议统一——用适配器把 OpenAI、Claude、国产模型统一成一套 API,错误码也统一翻译;② 高可用——主供应商超时/限流时自动 failover 到备胎,配熔断器防止雪崩;③ 限流——按应用/租户用令牌桶控并发,满了排队而不是直接拒绝;④ 成本治理——按调用方记账、配额、预算告警;⑤ 缓存与观测——语义缓存省钱,全链路 trace。这五件事在备份接入层、多路径存储里都有老熟人。开源参考 LiteLLM、OneAPI。"

通俗类比

整个网关,就是你修过的「备份统一接入层」换了张皮。备份系统里,客户端从来不直接怼各种后端(磁带库、对象存储、异地站点),统统过一层介质服务器/接入网关:它做协议翻译(NFS/S3/FC 各说各话,接入层负责翻译)、资源调度(驱动器就那么几台,作业排队上)、故障切换(主存储坏了改投备用)、按租户记账(谁占了多少容量,月底一张账单)。LLM 网关一模一样:上游"存储介质"换成了"模型供应商","客户端"换成了"业务应用"。哪里像:统一入口、协议翻译、资源治理、租户记账四件事完全同构,你的经验全部平移。哪里不像:备份后端是固定硬件,坏了是硬故障、好诊断;模型供应商是弹性云服务,故障大头是软故障——限流(429)、内容审核拒绝、余额不足、偶尔抽风变慢,形态碎得多,所以网关的熔断和 failover 逻辑比存储接入层密集得多。

网关部件你舒适区里的老熟人哪里像哪里不像
协议适配器S3 兼容层(Ceph/MinIO 都说 S3 方言)生态认事实标准,不认"更优雅的自定协议"翻译的不只是 API 形状,还有错误码和各家模型的能力差异
Failover容灾主备切换主坏了自动换备,对上层透明粒度是单个请求、毫秒级,不需要人工仲裁
熔断器多路径 IO 把坏路径摘除快速失败,不让请求挂死在超时上会"半开"自动试探恢复,不用等运维介入
限流与排队备份作业调度/带宽 QoS匀速放行、允许小突发、满了排队限的维度多了"钱":供应商按 RPM/TPM 收配额
记账租户容量报表事件流水进队列,聚合出账单计价单位是 token,不同模型单价差几十倍且调用量无法容量规划
缓存备份去重相同内容直接复用旧结果语义缓存放宽到"意思相近也复用",要防错配串答案

一句话总结:这题考的不是新知识,而是你能不能把分布式老三样(限流/熔断/failover)正确搬进 LLM 新场景——搬对了,再补上 LLM 特有的三件事:token 记账、流式透传、语义缓存。

详细拆解

0. 总架构:一眼看全

调用方(业务App / Agent / 内部脚本)
   │   统一用 OpenAI 格式调 /chat/completions
   ▼
┌────────────── LLM Gateway(无状态集群)──────────────┐
│ 鉴权 → 入口限流(app/租户令牌桶) → 路由决策        │
│      → 缓存查询 → 适配器 Adapter(每供应商一个)    │
│      → 出口限流(供应商 RPM/TPM 配额) → 计费事件  │
│ 熔断器 ×N(每供应商一个)      全链路 trace 打点     │
└──────────┬───────────────┬───────────────┬────────┘
       OpenAI(主)      Claude(备胎)    国产模型(兜底,最便宜)

1. 统一协议(适配器层)

  • 以 OpenAI 的 /chat/completions 格式为事实标准(业内都是这么做的),内部每个供应商一个 Adapter:请求翻译出去、响应翻译回来、错误码统一映射。为什么选 OpenAI 格式不自建协议?——网络效应。就像对象存储世界的 S3 API:它未必最优雅,但 MinIO、Ceph 全都提供 S3 兼容层,因为客户端生态(SDK/工具/监控面板/教材)都长在它上面。自定义协议的成本不在协议本身,在于让整个下游生态重学一遍。
  • 错误码翻译是适配器最容易被忽略、面试最容易被追问的部分——各家的"429"含义和后续动作完全不同:
供应商返回翻译成统一枚举网关接下来的动作
OpenAI/Claude 的 429(限流)RATE_LIMITEDfailover 切备供应商,不重试主
连接超时/读超时UPSTREAM_TIMEOUT指数退避重试,仍失败切备用
内容审核拒绝CONTENT_REJECTED原样返回调用方——重试没有意义
余额不足/配额耗尽QUOTA_EXHAUSTED熔断该供应商(短期不会自愈),切备用
  • 能力差异处理:有的供应商不支持 system role、没有 function calling——降级模拟:system 拼进 user 第一轮;FC 用 ReAct 文本协议模拟。这等于网关对外承诺"能力拉齐":下游按最强协议写代码,弱供应商由 Adapter 翻译兜底——换模型不改业务代码,这是网关的第一价值。

2. 路由与高可用

  • 路由策略可配:成本优先(同类问题走便宜模型)、质量优先、延迟优先;支持按百分比灰度切流量(新模型先切 5% 观察)。类比存储分层:热数据放贵快的介质、冷数据放便宜慢的介质——成本优先路由就是"按问题难度分层放模型"。
Failover 链(对调用方完全透明,拿到的仍是正常响应):
  请求 ─→ 路由决策(策略 + 灰度比例)
          主选 OpenAI ──超时3s / 连续429──→ 备选 Claude ──也挂──→ 兜底国产模型
                                                        (永远留一个最便宜最稳的兜底)
  • 熔断器(三态,经典模式):闭合(正常)→ 错误率超 50% 打开(直接拒绝,快速失败不再打上游)→ 30s 后半开(放一个探测请求,成功则闭合)。防的是雪崩:没有熔断时,上游一挂,网关所有在途请求都挂满 3s 超时,线程和连接池被占满,网关自己先死,再传染所有调用方——和多路径存储里"坏路径必须立刻标记 down,而不是让每个 IO 都去等 30s 超时"是同一条铁律。
         ┌────── 成功 ──────┐
         ▲                  │
      闭合(正常)      半开(放1个探测请求)
         │                  ▲ 30s冷却后
   错误率>50%(窗口统计)      │
         ▼                  │
      打开:新请求不再发上游、不再白等超时,直接快速失败/切备胎
  • 重试与熔断配合:先重试(最多 2 次指数退避),重试都失败才计入熔断统计(免得一次网络抖动就触发熔断);只重试幂等的读式调用——纯文本生成不改上游状态,可安全重试;但 Agent 场景里带副作用的工具调用(下单、发消息)绝不盲目重试。

3. 限流(保护自己和上游)

  • 令牌桶:桶里匀速发令牌,请求拿到才走,允许小突发——比固定窗口平滑。固定窗口的坑:窗口边界瞬间双倍流量(第 59 秒末放 100 个 + 第 61 秒开头又放 100 个,两秒内 200 个直接打穿下游);令牌桶"匀速发 + 攒下的令牌允许小突发",就像带宽 QoS 给租户限 50MB/s 但允许短时冲一下把攒的额度用掉。
                ┌──────────────────────┐
 匀速投放 ───→  │ ● ● ● ● ● ● (容量100) │   速率:50 个/s
                └──────────┬───────────┘
 请求到达 → 桶里有令牌? ──是→ 放行,扣 1 个
                     └──否→ 排队(告知预计等待)或 429
  • 双层限流:入口按 app_key/租户限(保护自己),出口按供应商配额限(如 OpenAI 的 RPM/TPM)。类比备份调度:入口按客户端限并发保护介质服务器,出口按后端吞吐限保护磁带库——两头都要护,只护一头另一头必炸。
限流层按什么限保护谁
入口app_key/租户(RPM、并发数)网关自身 + 租户间公平性
出口供应商配额(RPM/TPM)上游供应商,避免全公司共享配额被打爆
  • 并发信号量:LLM 是长连接(一次生成几秒到几十秒),必须限制同时在途请求数;超了排队而非拒绝,排队给个预计时间。类比:磁带驱动器就 4 台,第 5 个备份作业不是报错,而是进队列,系统告诉你"预计排队 12 分钟"——直接拒绝是体验事故,排队+预计时间才是平台该有的样子。

4. 成本治理

  • 每次调用记录:调用方、模型、输入/输出 token、单价 → 事件流(Kafka)→ 聚合 → 按天/租户/应用出账。和"备份作业产生记录、月底按租户出容量账单"一个套路。哪里不一样:计价单位是 token,单价随模型差几十倍,调用量完全无法容量规划——所以预算检查必须实时,月底看账单才发现某 Agent 一晚上烧掉一个月预算,就是事故了。
  • 配额与预算:软限制(用量 80% 告警)、硬限制(超限 429 或自动降级到便宜模型)。
每次调用 → 网关发计费事件(调用方,模型,in/out token,单价) → Kafka
             → 流式聚合 → 按天/租户/应用账单
             → 实时配额检查: 80% → 告警(软)   100% → 429 或降级便宜模型(硬)

5. 缓存

  • 精确缓存(相同 prompt+参数 hash 命中)+ 语义缓存(相似问题命中);缓存必须按租户隔离,防止串答案。类比备份去重:精确缓存 = hash 完全一致直接引用旧块(零风险);语义缓存 = 放宽到"意思相近也复用"(收益大得多,但会错配——把别的问题的答案发给用户是静默错误)。所以语义缓存要高相似度阈值 + 租户隔离 + 可主动失效。

6. 可观测

  • 每次调用一条 trace:入参出参、路由决策(这次为什么走了 Claude)、耗时分段、重试次数、是否命中缓存;接 LangFuse / Prometheus。看板四件套:QPS、P99、每供应商错误率与熔断状态、token 成本曲线。类比备份作业日志:出了事必须能回答"这次为什么慢/为什么切了供应商/花了多少钱"——没有 trace 的网关就是个黑盒,只能靠猜。
  • 落地收尾(面试加分):不要从零造轮子,开源 LiteLLM、OneAPI 已把适配器、限流、failover 做了;答题时点一句"对标 LiteLLM,我们在此基础上补租户强隔离、语义缓存和成本预算"——说明你既见过生态、又知道真实差距在哪。
面试官追问
Q:熔断打开了,正在排队的请求怎么办?
人话:熔断只拦"新打到这家上游"的请求,排队里已经等着的那些必须给个交代,不能让它们无限挂下去。类比:备份作业正在排队时后端磁带库突然故障——正确做法是给队列设最大等待时长,到点自动改投备用存储或快速失败退出,绝不让几百个作业一起挂死等超时。技术:排队请求设最大排队时长,超时返回统一错误码并携带 Retry-After;同时路由层把熔断中的供应商从可用列表摘除,新请求直接走备供应商;若已切到备胎,排队请求可继续放行,对调用方返回兜底结果保持透明,响应头带背压信号提示客户端降速。
Q:怎么防止一个业务方把全公司配额吃光?
人话:配额必须按调用方切分,不能所有 App 共享一口锅——共享池里嗓门最大的人吃穷所有人。类比:备份系统防止一个部门的作业把驱动器和带宽全占走:按客户端隔离并发数,关键业务(核心库备份)预留专属资源,非关键作业靠后。技术:per-app 令牌桶隔离,每个 App 独立的 RPM/TPM/并发额度;大调用方单独通道甚至专属供应商配额;全局限流之上再为关键业务白名单预留约 20% 供应商配额;配 80% 用量告警提前通知,避免等某个 App 突发流量把共享池打穿了才发现。
Q:流式响应经过网关怎么处理?
人话:网关不能当"攒齐整包再转发"的文件服务器,要当"边收边转"的管道,顺便在管道上把账记了。类比:像流式备份/复制——数据边读边写,不需要在本地先落盘整个镜像;哪里不像:网关转发的同时还要增量数 token,这是流式备份没有的"过路记账"。技术:网关透传 SSE 分块,每块到达立刻转发、不缓存整个响应体;增量解析统计 token(同时供 TTFT 打点和成本记账);超时分两级——首包超时(迟迟不吐首字就触发 failover)和流空闲超时(流中途断掉要检测),熔断统计对流式同样生效,首包持续失败也计入错误率。
Q:网关自己不会成为单点/瓶颈吗?你们怎么部署?
人话:会——入口层天然是单点风险,答案是把它做成无状态集群,让状态尽量少、尽量外置。类比:介质服务器集群化一个道理:介质服务器自身无状态(状态在元数据库里),所以可以横向扩;网关的状态(限流计数、熔断状态)要么集中放 Redis,要么允许各实例独立统计。技术:多实例无状态部署 + 前置 LB;令牌桶计数放 Redis 用原子操作保证全局一致;熔断状态可以各实例本地维护——允许实例间略有偏差,保守侧顶多多切一次备用,无害;健康检查自动摘除坏实例;网关只做控制面逻辑和转发、不缓存大响应体,吞吐瓶颈在出口连接数,靠连接池和多实例解决。
Q:为什么统一成 OpenAI 格式?自定义一套更干净的协议不行吗?
人话:不行,或者说不值——协议之战拼的是生态,不是优雅。类比:对象存储的 S3 API 并不完美,但 Ceph、MinIO 全都做 S3 兼容层,因为客户端 SDK、工具链、运维经验都长在它上面;自造协议等于强迫整个下游生态重学一遍,成本转嫁给所有人。技术:OpenAI 的 /chat/completions 已是 LLM 领域的事实标准,各家供应商甚至主动提供兼容模式,适配成本最低;网关对外暴露兼容格式,内部用 Adapter 翻译差异即可。真有私有需求(如成本标头、租户标识)用可选扩展字段挂在标准协议上,绝不另起炉灶替换协议本身。
术语卡
Failover:故障自动切换备用,LLM 网关里是单请求毫秒级的切换,对调用方完全透明。
熔断器:上游错误率过高时直接快速失败,不再白等超时,防止把网关自己拖死的雪崩保护器。
令牌桶:匀速发令牌的限流算法,攒下的令牌允许小突发,比固定窗口平滑。
RPM/TPM:每分钟请求数/每分钟 token 数,模型供应商配额的计量单位。
背压:下游过载时向上游回传"降速"信号,让生产端主动收油门而不是硬灌。
语义缓存:按"问题意思像不像"复用旧答案,省钱但怕错配,必须配高阈值、租户隔离和失效策略。
