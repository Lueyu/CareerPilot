设计 Prompt Engineering 的 A/B 测试

⭐⭐⭐ #Prompt#ABTest#实验设计
30秒电梯稿

"按标准 A/B 五要素走:① 单一变量——只改 Prompt 策略(如 zero-shot vs few-shot、加不加 CoT);② 随机分流——用户/请求 hash 分成同质两组;③ 预设指标——主指标准确率(程序化优先,其次 judge 分),护栏指标延迟、成本、拒答率;④ 样本量——按最小可检测效应事前算好;⑤ 固定观察期+ 统计显著性(p<0.05)。Prompt 特有两点:多 seed 采样消除 LLM 随机性,judge 校准位置/长度偏差。"

通俗类比

就像比菜谱:同一道菜,一份写"放盐、炒熟"(直接),另一份写"先热锅、下油、最后放盐"(分步 CoT)。要证明哪份更好,得让很多厨师随机各拿一份、同一批评委盲评、每个人多炒几次取平均——不能只看一个厨神的一次超常发挥,也不能偷看结果后提前喊赢。

详细拆解

1. 五要素(背这个框架)

  • ① 单一变量:一次只改一个维度——few-shot 的例数、是否加 CoT、角色设定、输出格式;改多了不知道提升归谁。
  • ② 随机分流:user_id / 请求 hash 分桶,同用户始终同组,保证两组同质可比。
  • ③ 指标预注册(动手前写死):主指标 = 任务准确率(能程序化就程序化,其次 LLM-as-judge);护栏 = 输出 token、P99 延迟、成本、拒答率、格式合规率。
  • ④ 样本量:按 MDE(最小可检测效应)和基线方差反推,别"跑几天感觉差不多就下结论"。
  • ⑤ 固定观察期:覆盖工作日/周末完整周期,到点才开盲;中途只看护栏止损,不看主指标(防 peeking)。

2. Prompt 实验特有的两个坑

  • LLM 随机性:温度 > 0 时同一 Prompt 结果会漂。对策:固定 temperature/seed,或同一输入采样多次取均值+方差报告,否则"提升"可能只是采样噪声。
  • judge 偏差:裁判有位置/长度/自我偏好——A/B 答案随机打乱顺序、固定裁判模型版本、rubric 写"长度不加分",再抽 5% 人工对齐(judge 与人工一致率 ≥85% 才可信)。

3. 离线先筛,线上终审

  • 先用黄金集(离线评估集)快速筛掉明显更差的 Prompt——便宜、快、可复现;有希望的再上线上 A/B——真实、贵、慢。
  • 离线是漏斗,线上是终审;只信线上的统计显著性,离线只做"别退化"的回归门禁。

4. 结论怎么写

  • 报主指标 + 置信区间 + p 值,同时亮护栏指标:若质量 +2% 但成本 +30%,要把 trade-off 交给业务方决策。
  • 注意结论的外推边界:Prompt 效果和模型强耦合,换模型结论可能失效,报告里要注明"在模型 X 上成立"。
面试官追问
Q:不同温度下结论会变吗?
会。所以要么固定温度做实验(结论只在固定设置下成立),要么在同一温度下多 seed 采样取均值并报告方差。温度越高噪声越大,需要的样本量也越大。
Q:离线分数高、线上没差别怎么解释?
多半是测试集分布和线上真实请求不像(黄金集太"干净")。用线上真实 query 重采样离线集、定期轮换;同时做 A/A 测试排除"线上本来就测不出差异"的噪声底。
Q:只有几百用户流量不够做 A/B 怎么办?
退而求其次:交替时间窗(本周 A 下周 B,多轮交叉)或用户内交叉;再小就老实承认"流量不足做统计",改用离线评估+人工评审,别假装在做 A/B。
术语卡
单一变量:一次只改一个因素,否则无法归因。
随机分流:用 hash 把用户均匀分成同质两组。
MDE:最小可检测效应,决定样本量要多大。
Peeking:中途偷看主指标提前下结论的作弊行为。
多 seed 采样:同输入多次采样取均值,压 LLM 随机噪声。
A/A 测试:同版本对打,校验系统本身噪声底。
