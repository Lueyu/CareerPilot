Agent算法 · Q33

设计 Prompt Engineering 的 A/B 测试

⭐⭐⭐ #Prompt#ABTest#实验设计
先说人话:这题问的是——你改了一版 Prompt,凭什么说它比旧版好?答案要拿一套对照实验证明,而不是「我觉得」。面试官爱考它,因为太多人把「跑几条样例、看着顺眼」当结论,一追问样本量、随机分流就露馅——暴露的是只会玄学调 Prompt,没做过严谨实验。
30秒电梯稿

"按标准 A/B 测试五要素走:① 单一变量——一次只改 Prompt 策略这一处(如 zero-shot 换 few-shot、加不加 CoT);② 随机分流——按 user_id/请求 hash 分成同质两组,同一用户始终同组;③ 预设指标——主指标任务准确率(能程序化判分优先,其次 judge 分),护栏盯 P99 延迟、成本、拒答率;④ 样本量——按最小可检测效应事前算好,不跑到点不开盲;⑤ 固定观察期 + 统计显著性(p<0.05)。Prompt 特有两点:多 seed 采样消除 LLM 随机性,judge 校准位置/长度偏差。整体节奏:离线黄金集先筛,线上 A/B 终审。"

通俗类比

整件事像「验证一个新备份调度策略」:你写了新版调度,想证明它比旧版好。第一步绝不是全网切换,而是灰度分流——把业务系统随机分成两半,一半跑旧版、一半跑新版。必须随机分,因为「A 组全是小库、B 组全是大库」的对比就是耍赖,随机才能保证两组天生同质,这和灰度发布按用户分桶是同一件事。一次只换一个东西:如果同时换了调度器和压缩算法,备份窗口缩短 20%,你说不清功劳归谁——这和你遵守的变更管理纪律「一次变更只动一处」一模一样。达标线先写进方案:演练前定死「成功 = 备份窗口 < 4 小时」,跑完不能回头翻指标,挑一个碰巧好看的说事。

哪里像、哪里不像:像的部分——两组同质环境、单一变量、预设达标线、满一个完整周期(含周末高峰)才下结论,这套纪律你闭眼能默写。最不像的一点:备份作业是确定性的,LLM 天生是骰子——同一份输入跑两次,备份结果基本一致,而 LLM 在温度 > 0 时两次输出就是不一样。所以 Prompt 实验多一道必备工序:同一输入采样多次取均值——这反而更像你测 SSD 的 4K 随机读,单次延迟抖得离谱,必须跑够轮数看均值,单次读数毫无意义。还有,裁判会偏心:让人或模型盲评两版答案,它天然偏爱「先看到的」和「写得更长的」——像故障复盘会上先发言的根因分析总更容易被采信,所以答案顺序要随机打乱、评分标准要写死「长度不加分」。

详细拆解

第 0 步:先给这题定性——A/B 测试就是线上化的随机对照实验

它的骨架你在分布式系统里天天见:灰度发布本身就是一次生产环境对照实验,区别只是灰度回答「新代码炸不炸」,A/B 回答「新 Prompt 好不好」。动手前先承认一个物理事实:LLM 是带随机性的系统——温度 > 0 时,同一输入跑两次输出可以不同。所以你比的不是「两个确定函数谁强」,而是「两个随机分布谁强」,这句话决定了后面每一道工序。

1. 五要素(背这个框架)

要素干什么不守的后果映射到你的老本行
① 单一变量一次只改 Prompt 策略这一个维度:few-shot 例数、加不加 CoT、角色设定、输出格式改了两处,B 好 3 分说不清归功给谁变更管理:一次变更只动一处,否则故障排查两眼一摸黑
② 随机分流user_id/请求 hash 分桶,同一用户永远同组两组不同质(比如 A 组全撞高峰流量),比了白比灰度按用户分桶,sticky 保证同人同桶
③ 指标预注册动手前写死:主指标一个 + 护栏一批事后从 20 个指标挑 3 个好看的,纯自欺(p-hacking)演练方案先定死 RTO 达标线,验收照单执行
④ 样本量按 MDE(最小可检测效应)和基线方差事前反推「跑几天感觉差不多」——感觉不是统计要测出 10% 提升,基准必须跑够轮次
⑤ 固定观察期覆盖工作日/周末完整周期,到点才开盲,中途只看护栏中途偷看主指标提前下结论,假阳性翻倍变更观察期未满,不许宣布成功或回滚
  • ① 单一变量:先把「改什么」定义清楚——是 zero-shot 换 few-shot(给不给示例),还是加不加 CoT(让不让它一步步推理)。确实想同时验证多个改动,可以升级成多臂实验,但每个臂都要能单独归因;面试答「一次只拧一个旋钮」最稳。
  • ② 随机分流:按 hash(user_id) 分桶而不是按时间切——早晚高峰流量天然不同质;同一用户固定同组:一是体验一致,二是同用户行为互相污染会让统计失真。分流单元选用户而不是请求,原因同上。
  • ③ 指标预注册:主指标只能有一个决胜。判分方式优先级:能程序化(答案对错机器可判,如分类、抽取、选择题)> LLM-as-judge > 人工(贵,只做抽检校准)。护栏:输出 token 成本、P99 延迟、拒答率、格式合规率——主指标赢了但护栏破了,照样不能上。
  • ④ 样本量:给个量级直觉——基线准确率 70%,想可靠测出 +5 个百分点,每组要 1200 条以上;想测 +2 个百分点,每组近 8000 条(方法见 样本量计算,惯例 80% 统计功效:差异真存在时有八成把握测出来)。MDE 定得越小实验越贵——先问业务「小到多少的提升才值得上线」,再定 MDE,别反过来。
  • ⑤ 固定观察期 + 防 peeking:观察期要覆盖完整业务周期,防止只看到某类流量;到点一次开盲。中途只允许看护栏指标(成本炸了、延迟炸了就止损),不看主指标。

2. Prompt 实验特有的两个坑(和传统 A/B 拉开差距的地方)

坑一:LLM 是骰子。传统 A/B 里,同一用户看到同一版本,行为基本稳定;LLM 在温度 > 0 时,同一 Prompt 自己跟自己都不一致。对策分两层:能固定就固定(temperature=0 + 固定 seed,代价是牺牲多样性、结论只在固定设置下成立);线上必须高温的场景,同一输入采样 k 次取均值 + 报告方差,别让单次骰子决定命运。

同一条输入、同一版 Prompt、温度 0.7,独立采样 4 次:
  run1 对 │ run2 错 │ run3 对 │ run4 对   →  均值 0.75
  只看 run2:「这版 Prompt 不行」 —— 被骰子骗了
对策:离线集每条样本跑 k 次(k=3~5)取均值,均值再进统计检验
代价:评测成本 ×k,黄金集规模和 k 要一起规划

坑二:裁判会偏心。用模型当裁判省人力,但它有三张偏心牌:位置偏差(A/B 答案顺序固定时偏爱某个位置)、长度偏差(偏爱啰嗦答案)、自我偏好(偏爱和自己风格同族的输出)。对策四件套:① A/B 顺序随机打乱、双向各评一次;② 固定裁判模型版本——裁判偷偷升级等于实验中断;③ rubric 写死「长度不加分、只看要点命中」;④ 抽 5% 人工对齐,judge 与人工一致率 ≥85% 才可信,达不到就换裁判或改评分标准,而不是硬信。

3. 离线先筛,线上终审

别一上来就烧线上流量。先用黄金集(固定题目 + 标准答案的离线评测集,定位等同你的回归测试集:便宜、快、可复现)批量筛掉明显更差的候选;有希望的再上线上 A/B——真实、贵、慢。职责分工要咬死:离线是漏斗(粗排 + 「别退化」门禁),线上是终审(唯一有权宣布「用户真的受益」的环节)。

新 Prompt 想法(往往有多个候选)
   │
   ▼
[第 1 关:离线黄金集快筛]  便宜 · 快 · 可复现,一批候选一起跑
   │  明显更差 ──→ 淘汰,不配消耗线上流量
   ▼  有希望的
[第 2 关:线上 A/B 终审]  真实 · 贵 · 慢
   ├─ hash 分桶 ──→ A 组:旧 Prompt(对照)
   └─ hash 分桶 ──→ B 组:新 Prompt(实验)
   │
   ▼
固定观察期满才开盲:
   主指标显著 + 护栏全过 ──→ 全量上线
   否则 ──→ 回滚,带数据复盘(失败实验也是资产)

4. 结论怎么写(体现工程素养的地方)

  • 报全套而不是只报一个数:主指标 + 95% 置信区间 + p 值 + 护栏全套。示范:「准确率 71.3% vs 68.9%,+2.4pp,95% CI [+0.9, +3.9],p<0.01;P99 延迟 +8%(护栏内);成本每答 +31 token(需业务决策)」。
  • trade-off 交给业务方:质量 +2% 但成本 +30%,算法工程师的任务是把账算清楚摆上桌,上不上让业务定——别替业务拍板。
  • 写清外推边界:Prompt 效果和模型强耦合,换模型、大版本升级,旧结论可能清零。报告注明「在模型 X、温度 Y、判分方式 Z 下成立」——就像换了代存储硬件,老基准必须全部重跑,没有「沿用」这一说。
面试官追问
Q:不同温度下结论会变吗?
人话:会。温度是实验设置的一部分,不绑定温度的结论等于没说清适用条件。类比:像给新压缩算法出基准——低负载下 A 快、高峰期 B 稳,拿 A 的峰值成绩满世界宣传就是误导;温度就是 LLM 的「负载档位」,档位不同,结论可以反转。技术:要么固定温度,声明结论仅在固定设置下成立;要么高低温各跑一轮,报告结论随温度的稳定性;温度越高采样噪声越大,同样 MDE 下需要的样本量和每组采样次数 k 都要往上加。
Q:离线分数高、线上没差别怎么解释?
人话:多半是黄金集和真实请求长得不像——考试卷太干净,真实用户不按考纲出牌,离线分数自然高估。类比:测试环境压测全绿、一上生产就露馅,是同一个病:构造的负载和数据分布都太「理想」。技术:①从线上真实 query 抽样(脱敏)定期回灌、轮换黄金集,防分布漂移;②先做 A/A 测试测出线上噪声底——连 A 对 A 都频繁出现「假显著」,说明实验平台灵敏度不够,先修平台再谈谁好。
Q:只有几百用户流量不够做 A/B 怎么办?
人话:别硬做。样本量不够时统计测不出差异,假装做 A/B 等于用随机数生成结论。类比:小集群比性能:两台机器各跑一次,谁快纯看运气;正确姿势是同一台机器上交替跑两种配置、多轮交叉,让时间效应互相抵消。技术:①交替时间窗:本周 A 下周 B、多轮交叉,用成对设计抵消节假日等时间混杂;②用户内交叉:同一用户先后体验两版,注意顺序效应;③流量再小就老实退回离线评估 + 人工评审,明说「样本不足,结论是方向性的」——面试里敢承认这点反而加分。
Q:实验跑到第 5 天,B 组领先 4%,能不能提前宣布胜利停实验?
人话:不能。中途偷看、看到领先就停,会把「没有差异」测成「有差异」,这是实验作弊里最常见的一种。类比:变更观察期没满就想宣布稳定——灰度第三天指标好看,周末高峰还没扛过你敢承诺吗?观察期就是防「只看了好日子」。技术:每次开盲都是一次独立检验,反复偷看再挑最早显著的时刻,属于多重比较,5% 的假阳性会被刷到 20% 以上;要么按预定样本量到点一次开盲,要么动手前写死序贯检验/贝叶斯的提前停止规则——规则不能边跑边改。
术语卡
单一变量:一次只改一个因素,否则提升无法归因——变更管理纪律的实验版。
随机分流:用 hash 把用户均匀分成同质两组,随机对照试验的线上版。
MDE:最小可检测效应,你想可靠测出的最小差距——MDE 定得越小,样本量烧得越多。
Peeking:中途偷看主指标提前下结论——反复偷看会刷高假阳性,实验作弊第一名。
多 seed 采样:同一输入多次采样取均值,把 LLM 的骰子噪声平均掉。
A/A 测试:同版本对打,校验实验平台自己的噪声底——连 A 对 A 都频繁「显著」,平台先送修。
LLM-as-judge:用模型当裁判打分,省人工,但要防位置/长度/自我偏好三类偏差。
p 值:差异纯属噪声的概率;p<0.05 意思是「白高兴的可能性不到 5%」。
