评估讨论 · Q5

评估一个 Agent 为什么比评估一个基础 LLM 更加困难和复杂？评估的维度有哪些不同？

⭐⭐⭐ #Agent评估#评估难度 字节 / 阿里（高频）
先说人话:这题问的是:为什么给 Agent 打分不能像给 LLM 打分那样只看「答得对不对」,得看整条做事的过程。面试官爱考它,是因为一秒就能分出「只跑过 benchmark 的人」和「真搭过验收体系的人」——答错的通常只会喊「更难」,却列不出差在哪些维度、每维怎么量化。
30秒电梯稿

"难度主要来自四点:① 多步轨迹——LLM 只评一个最终答案,Agent 要评一整条'思考→调工具→观察→再决策'的轨迹,中间任何一步错都可能让后面全部白费;② 环境交互——要和沙箱、浏览器、API 等外部环境互动,环境有随机性、有副作用,评估需要真实或可控的环境;③ 结果定义复杂——'任务成功'不等于'答案正确',还存在部分完成;④ 维度更多——除效果外,还要看工具调用准确率、效率(步数/延迟/成本)、鲁棒性(错误恢复)、安全合规。再加上非确定性:同一任务要多次采样看方差。所以 Agent 评估必须是轨迹级 + 任务级 + 环境执行式的组合,而 LLM 评估基本只是答案级判定。"

通俗类比

评估基础 LLM,像「验证一次单文件恢复」:取一个恢复点,把某个关键文件拉出来,打开、比对、打勾——一次交互,一个结果,对或不对,五分钟出验收结论。评估 Agent,像「验收一整场容灾演练」:RTO 只是最后那个数字,但你验收时绝不会只看它——你要看编排流程每一步走得对不对(先断流、再切流、再验证,顺序错了全盘皆输,这就是轨迹)、应急工具用得熟不熟(该用扳手不会抡锤子,这就是工具调用)、该 30 分钟的事有没有磨蹭成 3 小时(RTO,这就是效率)、中途注入的模拟故障有没有救回来(这就是鲁棒性),以及最要命的一条——演练有没有误伤生产(这就是安全合规)。维度从「一个文件的正确性」变成「一次完整任务执行的全过程」。

哪里像:两者都要先回答「什么叫成功」——演练里是 RTO/RPO 达标线,Agent 里是任务成功标准;都得多跑几场看波动;都怕只盯单一指标交差。哪里不像:容灾演练是写死的脚本,跑一百次路径都一样,波动只来自基础设施;Agent 是自主决策,同一个任务它可能今天三步做完、明天绕十步还失败——方差来自被测对象本身。所以演练验收可以按「一次跑通」设计,Agent 评估必须按「多次采样的统计」设计,这是两套方法论的分水岭。

详细拆解

0. 先把差距画出来

基础 LLM 的评估对象是「一次输入→一次输出」,单点判定;Agent 的评估对象是「一条会自己拐弯的执行轨迹 + 它留下的环境终态」。规模差一个量级:

基础 LLM 评估:
  问题 ──→ 模型 ──→ 答案 ──→ 对/错(一次判定,完事)

Agent 评估:
  任务 ──→ [思考 → 调工具 → 观察] × N 步 ──→ 环境最终状态
              │                        │
              ├ 轨迹级判定:每步工具对不对?参数对不对?这步该不该做?
              └ 任务级判定:数据库里订单真的建了吗?代码真的过测试了吗?
  额外要求:沙箱隔离(副作用不伤生产)、可重置(每场评估从同一快照开始)、
           多次采样(同题多跑,报均值±方差)、全程记录(出问题能回放是哪步拐的)

1. 为什么更难(五个根本差异)

  • ① 从"单点答案"到"多步轨迹":Agent 的执行是 ReAct 式的循环(推理→行动→观察→…),要评估每一步决策是否合理。中间选错工具、用错参数、提前终止,都会让"最终答案"失去意义。用备份链想:Agent 的多步轨迹像一条增量备份链,前一步是后一步的依赖,链中间坏了一块,后面所有增量全部挂不上去——所以不能只验收「最后一份备份在不在」,必须逐块校验。
  • ② 环境交互带来随机性与副作用:Agent 操作真实/仿真环境(数据库、浏览器、文件系统、API),环境状态会变、有随机因素(搜索结果顺序、网络抖动),还有不可逆副作用(真的下了单、删了文件)——评估要考虑隔离和可重置。用容灾想:这就像演练不带隔离直接往生产切流,评估本身变成了事故源。所以 Agent 评估必须跑在沙箱里,每场评估从同一份「环境快照」重新拉起——和你平时做恢复演练前先打快照是同一个职业习惯。
  • ③ 成功标准模糊 + 部分正确:很多任务没有唯一答案("帮我订个性价比高的酒店"),存在部分完成(查到了但没下单)。要给"部分正确"设计分数,不能简单 0/1。用容灾想:演练 RTO 达标但 RPO 超了、核心业务切过去了但报表系统没跟上——验收单从来不是一个勾,是一张按子项打分的表,Agent 评估同理。
  • ④ 非确定性与方差:同一任务跑多次,轨迹和结果都可能不同,评估要多次采样 + 报告方差,不能只看一次。方差大的样本要单独拉出来立案分析——是模型不稳还是环境不稳,思路和治理长尾请求一模一样。
  • ⑤ 成本与时长:Agent 一次任务几十上百步、烧大量 token,评估集大一点就很贵很慢,需要控制规模和采样次数。用容灾想:全量演练太贵,所以平时做抽样演练、季度才做一次全量——Agent 评估的采样预算也要花在刀刃上,稳定基线任务少跑几遍,高方差任务多跑几遍。

2. 维度差异(核心对比)

维度基础 LLM 评估Agent 评估
评估对象单次输入→输出完整任务轨迹(多步、多轮)
核心指标答案正确性、相关性任务成功率、轨迹正确率
工具/行动一般不涉及工具选择/调用/参数准确率
效率延迟、成本步数、延迟、token/金额成本、绕路率
鲁棒性几乎不看错误检测与恢复、失败重试
安全合规内容安全越权操作、危险副作用、约束遵循

面试时这张表就是你的主答骨架:先报「左列是单点、右列是过程加终态」这个总括,再逐行展开——顺序感和体系感本身就是加分项。每一行的右列都值得追问一句「怎么量化」,所以下面把它们落成可执行的指标。

3. 评估维度拆解(可落地)

  • 效果类:任务成功率(端到端)、轨迹正确率(中间步骤判定)、部分完成度。任务成功率是北极星指标,但它太粗——失败要能归因,才知道该修检索还是修规划,所以必须配合轨迹级指标一起看。
  • 交互类:工具选择准确率(该用哪个工具)、参数准确率(调用的参数对不对)、无效调用率。这三个是纯结构化校验——拿期望的工具名和参数 schema 逐字段比对,可程序化、可自动化,是所有过程指标里性价比最高的一组。
  • 效率类:平均步数、工具调用次数、P50/P99 延迟、单任务成本(按 token 折算成钱)。两个成功率相同的 Agent,一个 5 步完成、一个 30 步绕路,对用户是天壤之别——「绕路率」就是 Agent 版的「RTO 超标」。
  • 鲁棒类:遇到失败后的恢复率、重试后成功率、对无关扰动的稳定性。测法上要主动注入故障(工具超时、返回报错、脏数据)——思路就是 Agent 版的混沌工程:不主动搞破坏,你永远不知道系统崩了是什么样。
  • 安全类:越权/危险操作数、是否遵循约束(如"不得改动数据库")。这是唯一「一票否决」的维度:任务成功率 99%,但偶发一次真的删了生产表,这个 Agent 就不能上线——和你做备份系统时「删数据操作必须白名单」是同一条红线。

4. 评估方式的三层组合

  • 执行式(最可信):在沙箱/仿真环境里真跑,用"结果状态"判定(代码是否过测试、订单是否创建成功)。行业基准都走这条路:SWE-bench 用「单元测试是否全绿」判定,不看模型解释得多漂亮;AgentBench、WebArena 在真实环境里查终态。τ-bench 还引入了 pass^k 口径:同一任务连跑 k 次全部通过才算过——专治「偶尔成功靠运气」,这是刻画 Agent 可靠性最严苛的指标,面试里能主动提它,基本就是「真研究过」的信号。
  • 轨迹判定:用规则/模型逐步检查轨迹是否合理,给"过程分"。规则层管硬性项(工具名、参数 schema、禁区操作),模型层管软性项(这步是否必要、有没有绕路)。
  • LLM-judge + 人工:对开放目标、部分完成做综合打分——用 LLM-as-a-Judge 按评分细则(rubric)自动判,再人工抽检校准。黄金轨迹(人工标注的标准执行路径)在这里起「校准基准」的作用——相当于你的 golden 副本:judge 偏没偏,拿它和黄金轨迹的偏差一量就知道。
面试官追问
Q:中间步骤怎么自动评估？
人话:过程分不能靠人肉盯回放,得有自动化的三层办法,可靠程度递减、覆盖范围递增。类比:像演练验收不靠全程看直播,而是每步一张检查单、关键节点安排旁站,最后再抽几段录像复核。技术:① 对工具调用做结构化校验——对比期望的工具名、参数 schema,逐字段判,纯程序化,最可靠;② 对轨迹合理性用 LLM-judge 按 rubric 逐步判(这一步是否必要、是否走弯路);③ 关键任务保留人工标注的黄金轨迹做对齐校准。实践里"工具/参数准确率"性价比最高,先把它做扎实。
Q:环境有随机性,同一个任务跑一次分不准,怎么办？
人话:一场定不了输赢——单次成功可能纯靠运气,得多跑几场看成绩单的均值和波动。类比:容灾演练一次切换成功说明不了可靠性,验收看的是连续 N 次演练的达标率和抖动幅度。技术:多次采样取平均 + 报告方差:固定 temperature 多次运行,报"平均成功率 ± 标准差";尽量控制环境随机源(固定种子、固定数据集版本、每场从同一快照起跑);高方差样本单独立案,分清是模型不稳还是环境不稳。预算有限时,稳定基线任务少采样,高方差子集加采样;严苛场景直接用 pass^k 口径——k 次全过才算过。
Q:Agent 评估里"部分正确"怎么打分？
人话:不能用 0/1 一刀切,要设计阶梯分,让"差一步"和"全没做"拉开差距。类比:恢复演练里 RTO 达标但 RPO 超了,不能算全过也不能记零分——验收单按子项逐条给分,哪项丢分一眼可见。技术:定义分级的成功函数:例如酒店预订任务分成"查到了→选对了→下单成功→回传了凭证"四级,给 0/0.33/0.66/1 的阶梯分;或按"关键子目标完成数"给分。这比 0/1 更细,能看出模型是"差一点"还是"完全没做对",也为优化指路——卡在同一级上不去的样本,就是下一个版本的修复清单。
Q:让 LLM 给 LLM 打分(LLM-judge)靠谱吗？
人话:能用,但绝不能盲信——裁判自己也会看走眼,而且偏爱「像自己的人」。类比:相当于请一位资深运维替你验收演练:快、便宜、覆盖广,但他有自己的偏好,关键项目必须抽检复核,否则验收报告本身就是新的风险点。技术:① judge 和被测模型避免同源,降低LLM-as-a-Judge 论文里说的自我偏好/位置偏好等偏差;② rubric 要具体可操作("每步是否必要"优于"整体是否合理");③ 定期人工抽检,持续监控 judge 与人的一致率,一致率掉线就修 rubric;④ 高风险任务不用 judge 兜底,用执行式结果判定——跑不过测试就是不过,没有解释空间。
术语卡
轨迹(Trajectory):Agent 从开始到结束"思考→行动→观察"的完整序列,Agent 评估的第一现场。
任务成功率:端到端完成任务的比例,北极星指标,但太粗,必须配合轨迹级指标定位失败原因。
工具调用准确率:选对工具且参数正确的比例——纯结构化校验,最可靠、性价比最高的过程指标。
分级成功函数:给"部分正确"发阶梯分(如 0/0.33/0.66/1),把"差一步"和"全没做"区分开。
沙箱:隔离且可重置的执行环境,Agent 版的"演练环境"——副作用不伤生产,每场评估从同一快照起跑。
LLM-as-a-Judge:用模型按评分细则自动打分的裁判,快但要防偏差,需人工抽检校准。
pass^k:同一任务连跑 k 次全过才算过的严苛口径,专治"偶尔成功靠运气",τ-bench 提出。
