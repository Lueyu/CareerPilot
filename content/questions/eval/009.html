Agent核心 · Q47

如果用户连续追问"为什么选这家酒店？"，Agent如何回溯决策链并给出可解释理由？

⭐⭐⭐ #可解释性#决策追溯 字节(真题)
先说人话:用户连问三遍「为什么选这家酒店」，考的是 Agent 能不能把当时的决策依据原样端出来，而不是事后现编一套听上去合理的说辞。面试官爱问它，是因为一开口就能分出「做过 Agent 工程的人」和「只会说『让 LLM 解释一下』的人」——答错的暴露点恰恰是后者：把可解释性做成了「事后找借口」。
30秒电梯稿

"核心是把决策过程全程留痕：Agent 每做一次选择，就把'选了谁、依据什么、排除了哪些、权重是多少'写进一条结构化的决策链（trace），随会话持久化保存。用户追问时分三步走：①定位——把'为什么选这家'解析到'选酒店'这个决策节点（'这家'要先做指代消解）；②取数——从 trace 里拿出当时的输入约束、候选打分、排除原因；③翻译——正反两面说人话：正面给'它在预算内、离西湖 800 米、评分 4.7'，反面给'A 超预算、B 距离超标'，必要时补一句反事实'预算放宽到 800，A 会更合适'。分水岭一句话：解释只能来自真实记录，模型不许现编理由——查不到记录就老实说'我记不清当时的完整依据了'。"

通俗类比

决策链，就是 Agent 世界的链路追踪。你在分布式系统里天天见它：一次请求扇出几十个服务，分布式追踪把每一步记成一个 span，串成一条 trace，出问题才「说得清」。Agent 跑一趟任务要经过几十次工具调用、十几次选择，每个决策节点就是 trace 里的一个 span——记下「输入是什么、算出了什么、为什么这么算」，用会话 ID 串起来。用户问「为什么」，等价于 SRE 点开慢请求的瀑布图逐段看。而「先留痕、后解释」的次序，就是预写式日志（WAL）的思想——先落盘，再干活；没有当时的记录，就没有事后可信的说法。哪里像：都是旁路记录、都按请求/会话 ID 关联、都为「事后说得清」服务。哪里不像：分布式 trace 的读者是工程师，字段晦涩无妨；Agent trace 的读者是终端用户本人，要把字段翻译成人话，还要经得起用户当场逐条质疑——所以 trace 必须结构化、可查询，不能是一坨自由文本日志。

用户追问，等于你查备份 catalog 出恢复报告。备份软件敢承诺「能恢复到周三 14:00 那个时间点」，靠的不是管理员的记忆，是 catalog 里每一条元数据：哪个卷、哪个时间点、落在哪块介质。Agent 敢说「选 C 是因为 560/晚在预算内」，同样必须靠当时落下的字段——而不是让模型「回忆」，LLM 的回忆其实是重新算一遍，两次结果还未必一样，这在审计意义上等于伪证。至于反事实解释（「预算放到 800，A 就赢了」），它像容灾里的 what-if 演练：不动生产环境，在沙盘里改一个参数重推一遍，让你看清哪个条件才是决定性的。

最后是那条红线：事后合理化。事故复盘时，运维不查操作日志、凭印象写一份「当时是这么决策的」，那叫伪造审计记录——LLM 天生爱干这件事：它会顺着结论流畅地补一套「合理」理由，哪怕当时根本不是这么算的。可解释性工程的全部要义，就是把模型按在真实 trace 上：只准翻译，不准补充。

详细拆解

1. 决策链的数据结构（先设计"留痕"，没有留痕一切免谈）

留痕不是「把对话存下来」——对话只是决策的结论，可解释要的是决策的过程。每个关键决策落一条结构化记录：

翻译成你熟悉的备份语言：节点 ID 像作业 ID，输入约束像备份策略（哪些卷、什么保留期），「可回滚标记」像可恢复点——记录的可查询性决定了解释的精确性。多个决策节点用「因果箭头」串起来，就得到整条决策链：

会话 S-1024 的决策链（自上而下，箭头 = 因果影响）

[节点1 选景点] 依据: 用户要"安静的湖边"+当天天气 → 西湖(置信0.86)
      │ 产出下游约束: "距西湖≤3km"
      ▼
[节点2 选酒店] ◄── 用户追问的正是这个节点
  输入: 预算≤600/晚 · 距西湖≤3km · 评分≥4.5
  候选: A(1200/晚,1.2km,4.8)  B(480/晚,6km,4.6)  C(560/晚,0.8km,4.7)
  打分: 距离40% + 价格30% + 评分30%   (权重来自用户偏好设置)
  结果: 选中C(综合0.81) · 排除A(超预算) · 排除B(6km超出3km约束)
      │ 住宿锚点: 以C为中心
      ▼
[节点3 排行程] 两天路线围绕C展开
  • 记录要结构化、可查询：不是存一段自由文本，而是存字段，追问时可按维度精确检索——就像你排查恢复失败时能按 catalog 字段查，而不是 grep 一大坨日志。
  • 留痕粒度分级：关键决策（选酒店、排行程）细记录到字段；琐碎步骤（单次查询）粗记一条摘要——平衡存储成本与解释需求。
  • 写入旁路化：trace 先 append 到内存队列、异步落库，主流程不等它——审计日志不能挡业务事务，这个原则原样搬过来。

2. 回溯定位（用户问"为什么"时，先找准是哪个决策）

  • 把追问解析成"针对哪个决策、哪个维度"：连续追问"为什么选这家"→ 定位"选酒店"节点；"为什么不是 A"→ 定位到"排除项"字段。这一步是查询 trace，不是让模型自由发挥。
  • 用指代消解 + 上下文："这家""它""那个"要回指到上一轮提到的实体——追问到第三轮时，"它"指的到底是酒店 C 还是景点，搞错了整条解释就全错。
  • 沿因果箭头向上取相邻节点：选酒店受前面"选了哪个景点"影响。定位节点 2 之后，把节点 1 也拉出来，才能答出"因为你坚持去西湖，所以选了离它最近的 C"——多步任务的解释靠的是链，不是孤立的点。
  • 找不到决策记录（如历史会话丢失、旧版本系统没留痕）时诚实降级："我记不清当时的完整依据了，能帮你重新评估一次"——绝不编理由。宁可承认留痕缺口，也不能伪造审计依据。

3. 生成自然语言解释（分层回答，LLM 只当翻译）

定位到节点、取出字段之后，剩下的事才是 LLM 的：把结构化字段翻译成人话。不同追问给不同层次的答案：

追问类型回答策略示例
为什么选 X正面依据(打分)"因为它距西湖 800m、600/晚在预算内、评分 4.7"
为什么不选 Y排除项 + 反事实"A 价格 1200 超预算，B 距景点 6km 超出你 3km 的要求"
X 和 Y 比呢并排对比表按价格/距离/评分三列对比
凭什么信这个数据数据来源 + 时效"评分来自 OTA 平台、价格是今天实时查询"
  • 解释要贴合用户当时的约束（预算、位置、偏好），而不是泛泛说"综合最优"——"综合最优"在用户耳朵里等于"没说"。
  • 必要时给反事实解释："如果你把预算放宽到 800，A 会更合适"——让用户理解并自行调整，解释从单向陈述变成交互。

翻译环节最大的风险是 LLM 的「合理补全」本能——它会顺手添上 trace 里根本不存在的好处。所以要把约束写进 Prompt，并加一道出口校验：

解释生成的 Prompt 模板（核心：LLM 只当翻译，不当辩手）

【决策记录】(来自 trace, 结构化注入)
decision: 选酒店
chosen: C — 560/晚, 距西湖800m, 评分4.7
rejected: A — 1200/晚, 超出预算600; B — 距离6km, 超出3km约束
scored_by: 距离40% 价格30% 评分30% (来源: 用户偏好设置, 可修改)
missing: 当天实时房态未查询

【生成规则】
1. 只允许引用【决策记录】里的字段组织解释;
2. 记录里没有的信息, 必须回答"当时没查到", 不许推断;
3. 输出顺序: 先正面依据, 再排除项, 被追问时才给反事实。
  • 出口校验层：解释生成后，把里面的数字与事实逐条和 trace 比对，对不上就重新生成或降级为模板拼接——像出报告前先对一遍 catalog。

4. 难点与边界（面试加分点）

  • 真实依据 vs 模型脑补：这是本题的灵魂。LLM 天然会"合理补全"理由，必须强制"解释只能引用 trace 里的字段"，缺失就承认缺失。能主动讲出「我加了引用校验层防止解释器幻觉」，面试官就知道你真踩过坑。
  • 多步决策的因果链：选酒店受前面"选了哪个景点"影响，要能沿链回溯："因为你坚持去 X 景点，所以选了离它最近的 C"。单点解释容易，链式解释才见 trace 设计功力——节点间的因果引用关系要在留痕时就建好，事后补不出来。
  • 权重本身可质疑：把权重明示给用户（"距离权重 40% 是你之前设置的"），用户可改权重 → 重新排序 → 展示前后变化——这就是可交互的可解释性系统：从"解释给你听"升级到"你自己动手调"。
  • 留痕的生命周期：trace 按会话 TTL 归档清理，但涉及订单、投诉的会话延长保留——和备份保留策略同款思路：平时省成本，争议期留证据。
面试官追问
Q:如果 Agent 其实是 LLM 直接"拍脑袋"推荐的，没有结构化打分怎么办？
人话:那要做的就不是「补个解释功能」，而是把决策流程改造成可留痕的——没有当时的记录，解释只能靠编。类比:某个应用的写入从来没进过快照，你就没法把它恢复到任意时间点；想可恢复，得先把写路径纳入保护，存量没记录的数据谁也变不出来。技术:把「LLM 直接出结果」改成「LLM 生成候选 → 结构化打分函数排序 → LLM 只负责把排序依据说人话」，即决策用确定性逻辑（可解释），表达用 LLM（可读）。对无法结构化的主观判断，至少记录"模型当时的判断摘要 + 置信度 + 时间"，解释时明示"这是模型判断，非规则打分"；新会话从第一天起留痕。
Q:决策链很长，用户追问很多轮会不会上下文爆炸？
人话:会，所以上下文里只放摘要，全量日志外置在存储里按需拉。类比:恢复某台虚拟机时你不会把整个备份 catalog 载进内存，只取该 VM 的恢复点索引，介质按需挂载——解释也一样，按「这次追问命中哪个节点」来取。技术:解释用决策链摘要（结构化精简版）而非全量日志：上下文只注入当前追问相关的节点 + 相邻因果节点，多轮追问滚动淘汰已答过的节点；trace 本体外置（DB/向量库），并按节点字段建索引，让「取哪一段」变成查询而不是全量塞入，token 成本随追问数线性而非链长增长。
Q:用户质疑权重不合理，系统怎么回应？
人话:不辩护，把权重的来源亮出来，并让用户当场能改——可解释的最高形态是可干预。类比:容灾里的 RPO/RTO 不是拍脑袋写死的，业务方质疑就改参数重演一遍演练给他看前后差异。技术:把权重的来源和可调整性暴露出来并分层标注：系统默认 / 用户此前设置 / 模型建议，提供修改入口，改完即时重排并展示对比（"预算权重提到 50% 后 B 会上位"）。用户改参数 → 系统重算 → 看到结果变化，这条闭环本身就是最强的解释，也把"可解释"升级成了"可干预"。
Q:解释本身也是 LLM 生成的，怎么保证它不添油加醋？
人话:解释器自己也会幻觉，得用硬约束加校验把它的自由度锁死。类比:备份报告应该由脚本从 catalog 读字段生成报表，而不是让管理员凭印象手写——哪怕手写的文笔更好，审计也不认。技术:① trace 字段结构化注入 Prompt，规则写死"只准引用、缺了就说没查到"；② 出口加引用核对层——把解释中的数字与事实逐条和 trace 比对，对不上就重生成或降级为模板拼接；③ 高风险场景（客诉、审计追溯）干脆放弃自由生成，纯模板拼字段，牺牲一点流畅换零幻觉。
术语卡
决策链:Agent 世界的链路追踪,每个决策记成一个节点、串成一条链,事后才答得出「当时为什么」。
预写式日志(WAL):先落盘、后干活;「先留痕、后解释」和它同一个祖师。
反事实解释:说明"改了什么条件、结果会怎样变",像容灾的 what-if 演练。
指代消解:搞清"这家/它/那个"指的是哪个实体,追问多轮时的第一道定位工序。
可解释性:让决策依据可被人类理解的能力;最高形态是可干预——用户能改参数看重算。
事后合理化:模型顺着结论现编理由而非还原真实依据,本质是伪造审计记录,必须用"只准引用 trace"的约束堵死。
