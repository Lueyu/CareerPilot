系统设计 · Q11

设计一个 Agent 调试与可观测性系统

⭐⭐⭐⭐ #调试#监控#可观测性
30秒电梯稿

"标准三支柱:Trace(每次请求的全链路树,LLM 特有的要记录 prompt/输出/token/成本)+ Metrics(延迟、错误率、token 成本、缓存命中)+ Logs(结构化聚合)。Agent 场景的独有需求是把"答错了"归因到具体环节——是检索没召回、还是 Prompt 不好、还是工具返回错了,所以 trace 里每个 span 要能回放。方案上 OpenTelemetry 做标准,LangFuse 做展示分析,告警分级带 trace 直达链接。"

通俗类比

给 Agent 装一套行车记录仪 + 仪表盘 + 保养手册:仪表盘(Metrics)让你开车时随时看车速、水温、油量——系统健康不健康一眼便知;行车记录仪(Trace)出了事故能逐秒回放——这个回答为什么错,把每一步调出来看;保养手册(Logs)记录所有历史细节备查。没有这三样,出了问题就只能"我觉得可能是模型不行"。

详细拆解

1. Trace:Agent 排障的灵魂

  • 每个 span 记录:入参出参(敏感字段脱敏)、耗时、重试次数、token 数、折算成本、模型名。出错标记:哪个 span 抛了异常一目了然。
  • 跨服务传播:trace_id 放请求头,网关/检索/生成各微服务全链路透传(OpenTelemetry 标准,别自己造轮子)。
  • 采样策略:LLM 调用全量采集(贵且重要),健康高频请求按 1~10% 采样;出错请求自动提升为全采。

2. Metrics:四层看板

层级关键指标
业务层问题解决率、用户点踩率、转人工率
应用层QPS、P50/P95/P99、错误率、缓存命中率
模型层TTFT、吞吐(token/s)、每请求成本、各模型调用量分布
资源层GPU 利用率、队列深度、Worker 饱和度

3. 告警分级(带一键现场)

  • P0:服务不可用 / 错误率 > 20% → 电话叫醒。
  • P1:错误率 > 5% 持续 5 分钟、P99 翻倍 → 群消息。
  • P2:token 成本环比 +50%、缓存命中率跌破 20% → 工单。
  • 每条告警附 trace 样本链接,点进去就是案发现场,不用再捞日志。

4. 排障工作流(讲这个=有实战经验)

用户反馈"答错了" → 按 trace_id 拉全轨迹 → 依次检查:① 检索召回里有没有正确文档(没有=检索问题,看 chunk/索引);② 有但没排进 top5(重排问题);③ Prompt 渲染是否异常(模板变量错了?);④ 工具返回值对不对 → 十分钟内定位环节,而不是玄学调模型。

5. 选型:LangFuse(开源、LLM trace 专精、可自部署、 prompt 版本管理)/ LangSmith(LangChain 官方 SaaS)/ OTel + Prometheus + Grafana(通用底座)。典型组合:Prometheus+Grafana 管机器和接口,LangFuse 管 LLM 语义层。

面试官追问
Q:Trace 数据量很大,存得起吗?
分级存储:全量 trace 放对象存储(便宜),最近 7 天热数据进 ClickHouse/ES;prompt 全文只存摘要+可回放原文(压缩);采样 + TTL 自动过期。
Q:每次调用的成本怎么精确算?
网关层统一计量:输入/输出 token 分开计数 × 该模型单价,写进 span;聚合到租户/天级成本表。注意供应商批量折扣和缓存命中的价格差异。
Q:幻觉率能监控吗?
在线近似指标:引用存在率(答案引用是否真实)、用户点踩聚类、judge 抽样跑分;真正的幻觉率靠定期离线评估集。
术语卡
Trace/Span:一次请求的链路/链路中的一个步骤。
OTel:OpenTelemetry,可观测性数据标准协议。
采样:只采部分 trace 省存储。
P0/P1/P2:告警严重级别。
