评估讨论 · Q10

如何持续监控和评估一个已经部署上线的 LLM 应用或 Agent 服务的表现，以应对可能出现的性能衰退或行为漂移？

⭐⭐⭐ #线上监控#性能监控 字节、阿里、腾讯（工程重点）
先说人话:这道题问的是:模型上线只是开始——怎么装仪表盘、设告警、建演练机制,在用户炸锅之前发现它悄悄变笨、变慢、变味。面试官爱考它,因为它专筛「只会离线调模型」和「真守过线上系统」的人——答不出「模型一行没动、质量也可能掉」,就暴露没扛过生产。
30秒电梯稿

"上线后的监控我分三层,像给系统装三个仪表盘:模型质量层——输出对不对,黄金集持续回归 + 线上流量抽样用 LLM-as-judge 打分;服务质量层——延迟、错误率、token 成本、QPS;业务质量层——问题解决率、转人工率、用户满意度。应对漂移两板斧:一是漂移检测,输入分布用 PSI / embedding 聚类监测,输出质量用黄金集回归分数监测;二是版本化 + 金丝雀发布 + 秒级回滚,发现衰退立刻切回。关键认知:漂移不只是「模型变了」——输入分布变、知识库更新、下游工具/API 改动、供应商静默升级,都会让一个「没动过」的系统行为漂移。"

通俗类比

先搞懂「漂移」(用静默数据损坏想):LLM 应用变差,大多数时候不是「崩了」——接口照样返回、延迟照样正常,只是答案在悄悄变笨、变味。这和存储领域最怕的 静默数据损坏 是同一种脾气:监控绿灯全亮,数据早就坏了。备份工程师有条铁律——「没验证过的备份等于没有备份」,作业成功率 100% 证明不了可恢复。平移过来就是:没有持续评估的线上服务等于裸奔,错误率 0% 证明不了答得对。这道题考的,就是怎么把「恢复验证」这套机制装到一个概率系统上。

整个体系像备份系统的日常运维闭环:上线当天先拍基线快照——各层指标 + 评估分存档,相当于给系统打一张「全量备份」;之后每天看仪表盘(服务质量层,就是作业成功率监控那一层);定期拿固定的黄金集做回归跑分(就是定期恢复演练——剧本固定,才能区分「系统退化」和「需求变化」);再看用户侧的解决率、转人工率(业务层,等于业务方审计 RTO/RPO 是否达标);发现异常先回滚到上一个稳定版本(就是容灾里的「回切」);上新版本先切 5%~10% 流量观察(就是先在一个租户、一个机房试点再放量)。

哪里像、哪里不像:像——都是「先建基线、盯偏离、定期演练、快速回滚」的闭环,手段几乎可以一一对应。不像——传统运维的指标大多是确定性的:作业成功就是成功、字节数校验对就是对,天然有「对错位」;LLM 的输出是概率性的、质量是连续的,没有天然的「成功位」,必须靠黄金集回归和抽样打分人为造出一个质量信号。而且 LLM 的漂移来源更广:模型权重一行没动,知识库、检索、下游 API 任何一个环节变了,整个系统就算变了——所以监控对象必须是整条链路,而不只是模型。

详细拆解

1. 为什么必须持续监控(漂移从哪来)

LLM/Agent 是概率系统:没有固定输出,也不存在「一次测试通过就永远稳定」。上线评估通过,只证明「当时的模型 + 当时的 Prompt + 当时的知识库 + 当时的流量」这个组合是好的——四个要素任何一个变了,结论就作废。这和「备份策略当年验证通过,不代表今天还能在窗口内恢复成功」是同一个道理:数据涨了、固件升了、拓扑改了。更麻烦的是,下表四类漂移,有三类都发生在「模型权重一行没动」的情况下:

漂移来源表现第一排查动作
输入分布漂移用户问法变了、新话题涌入、季节性需求看 embedding 聚类/类别占比,确认新需求
知识/数据变化知识库更新、政策变更，旧答案过时对齐知识库版本号与变更单
下游依赖变化检索库、工具 API、第三方模型静默升级拉下游版本记录,问供应商
自身变更Prompt、模型版本、参数的改动引入回归查发布记录,用黄金集回归定位

其中最阴的一类是「下游依赖静默升级」:供应商把 API 背后的模型从 v2 悄悄换成 v2.1,不会给你发变更单,但你精心调好的输出格式、few-shot 示例可能一夜之间全不灵。做存储的同学对这一幕太熟了——阵列固件自动升级导致备份窗口悄悄变长,没人通知你,直到作业超时告警炸了,你才知道环境早就变了。

逐层说透:

  • 服务质量层(秒级,最快,但也最浅):错误率、延迟、token 成本、QPS——就是你熟悉的基础设施监控,Prometheus/Grafana 那套直接平移,上线第一天就能建好。但要清楚它的边界:它只能证明「服务活着」,证明不了「答得对」。
  • 模型质量层(分钟~小时级,LLM 特有的核心层):两个抓手。①黄金集回归:几十到几百条核心问答,带标准答案和评分标准,每次发版前全量跑,分数跌破基线就拦截——模型世界的「恢复演练」,跑分不稳不许放量。②线上流量抽样:每天从真实流量抽 1%~5%,用 LLM-as-judge(拿一个强模型当阅卷老师、给输出自动打分)得到「线上真实质量」的代理指标,再人工抽检其中一小部分,校准阅卷老师的可信度。RAG/Agent 场景还要盯「引用忠实度」——答案里引用的片段是不是真的支持结论,这是幻觉的专用探测器。
  • 业务质量层(日级,最慢,但也最真):问题解决率、转人工率、留存、点踩率、NPS。转人工率上升往往是最早的真实告警——用户用脚投票,比任何离线分数都诚实,而且是唯一没法被「朝指标优化」造假的信号。

3. 漂移检测怎么做

  • 数据漂移(盯输入):可量化的结构化特征——问题类别占比、query 长度分布、语言、渠道——用 PSI(群体稳定指数,风控行业监测客群分布的标准工具,与 KL 散度同族)逐日对比,PSI 超过 0.25 通常判为显著漂移。文本没法直接算分布,做法是:对每天进来的 query 算 Embedding 后聚类,盯「簇占比变化」——原来 80% 的请求集中在售后政策类,某天冒出一个占 20% 的新话题簇,就是新需求涌进来了,而你的知识库和评估集多半还没准备好。
  • 性能漂移(盯输出):定期把黄金集 + 最新线上样本喂回去跑分,分数跌破基线阈值就报警。它是数据漂移的对照组,两者合起来才能回答「是需求变了,还是系统坏了」。
  • 概念漂移(盯尺子):同一问题的「正确答案」本身变了——典型如政策更新,模型答旧答案答得再流畅也是错。它最隐蔽:模型、输入、分数可能都没变,是评分标准过时了;必须靠业务方定期同步修订评估集,否则监控在用歪尺子量东西——演练跑满分,也可能是假安全。
线上质量下滑,先跑一轮「黄金集对照」,按结果三路分流:

  黄金集(固定输入)重新回归,分数掉了吗?
   │
   ├─ 没掉,掉的是线上抽样/业务指标 ──▶ 数据漂移:新需求、新人群进来了
   │                                  → 对策:补评估集、补知识覆盖,别急着动模型
   │
   ├─ 黄金集也掉了 ──▶ 系统退化:查变更记录(自己的 Prompt/参数,
   │                    或下游 API、供应商模型静默升级)→ 对策:回滚,再定位
   │
   └─ 复核发现是「老答案本身过时」──▶ 概念漂移:尺子歪了
                                      → 对策:业务方先修订标准答案,再重跑

4. 持续评估管线(把评估变成日常动作,而不是年终考试)

  • 黄金集持续回归:核心评估集接入 CI/CD,每次发版自动跑,回归测试分数低于基线自动拦截发布——相当于把「每次变更先过恢复演练」写成机器卡点,不靠人自觉。
  • 线上流量抽样:每天抽样、judge 打分、人工抽检,输出「质量日报」。注意 judge 自己也是模型、也会错(偏爱长答案、打分有位置偏见),所以人工抽检不是可选项,而是给阅卷老师做一致性校准的必需项。
  • Bad case 回流:用户点踩、转人工、投诉的样本自动进待标注池,清洗、补标准答案后编入黄金集——线上 bad case 是最值钱的评估数据来源,就像每次恢复失败都要写进演练手册,下个季度必考。
日常闭环(评估不是一次考试,是每天巡检):

  线上流量 ──每日抽样──▶ LLM-as-judge 打分 ──人工抽检校准──▶ 质量日报(vs 基线)
      │                                                        │
      └─ 点踩/转人工/投诉 ──▶ bad case 池 ──清洗+定标准答案──▶ 编入黄金集(越养越准)

  发版卡点:改动 ─▶ CI 自动跑黄金集回归 ─┬ 分数≥基线 ─▶ 金丝雀 5%~10% ─▶ 全量
                                        └ 跌破基线 ─▶ 自动拦截发布

5. 发现衰退怎么快速止损

  • 版本化一切:Prompt、模型版本、参数、知识库版本、下游 API 版本,全部带版本号记录,任何变更可定位、可回滚。没有版本化,「回滚」就是空话——出了问题连「滚回哪」都不知道。
  • 金丝雀发布(工程模式见 Canary Release):新版本先切 5%~10% 流量,新旧对照组各自对比基线,指标异常自动回滚、正常则逐步放量。和容灾切换「先切一个机房、观察、再扩大」是同一套手法。
  • 告警分级:服务质量层(错误率、延迟)秒级告警;模型质量层(回归分数、judge 分)分钟/小时级——因为要跑批;业务层日级复盘——信号天然滞后。分级不是因为哪层次要,而是三层信号的产生节奏本来就不同。
面试加分句："性能衰退"要看的是"相对基线的偏离"，而不是绝对值——先建立上线时的基线快照（各指标 + 评估分），之后一切监控都是"偏离基线多少就告警"。没有基线的监控只是看数字，不叫监控。基线快照就是上线当天给系统打的那张「全量备份」，之后每天的巡检，都是在拿现状和这张快照做差异比对。
面试官追问
Q:模型根本没动，为什么质量会下降？
人话:因为决定输出的远不止模型权重——Prompt、知识库、检索结果、下游 API、用户问法全是变量,任何一个动了,「系统」就变了。类比:备份策略一行配置没改,恢复成功率照样掉:数据量悄悄涨了、应用改了文件布局、阵列固件静默升级——「配置没动」从来不等于「环境没变」。技术:典型来源:供应商静默升级底层模型(输出风格、格式突变)、知识库或检索库更新改变引用质量、工具 API 改返回格式、输入分布随运营活动漂移。所以监控对象是整条链路,且 Prompt hash、模型版本、知识库版本、API 版本都要记录在案,出问题才对得上时间线。
Q:怎么区分是"模型变差"还是"用户需求变了"？
人话:拿固定的黄金集当对照组——同一批题重考一遍,看分数掉没掉,掉的层面决定结论。类比:恢复演练用固定剧本跑:剧本成功率没掉、只是线上新业务涌入导致排队变长,那是需求变化,要扩容;固定剧本成功率掉了才是系统退化,要修系统——两者动作完全不同,混着排查会白忙。技术:黄金集稳定 + 线上抽样/业务指标下滑 ⇒ 数据漂移,对策是补评估集、补知识覆盖;黄金集同掉 ⇒ 系统退化,对策是查变更记录、回滚;还要识别第三态——标准答案本身过时(概念漂移),先让业务方改尺子再重测。
Q:黄金集怎么维护？会不会自己就过时了？
人话:会,而且是最隐蔽的坑——监控用的尺子自己歪了,监控就成了自我安慰。类比:恢复演练剧本多年不更新,业务早迁到新应用了还在演练老系统,演练满分也是假安全;评估集必须跟着业务一起活着。技术:① 线上 bad case(点踩/转人工/投诉)定期清洗、定标准答案后编入;② 政策、知识变更由业务方同步修订答案;③ 控制题目分布,防止评估集过度集中于某类问题、团队朝它「应试优化」;④ 黄金集本身版本化,改动时新旧两版对照跑,避免把尺子的变化误判成系统衰退。维护评估集是持续投入,要当「活资产」管理。
Q:告警了但一时半会儿修不好，怎么兜底？
人话:先止血、后排查——别让有问题的版本继续伤害用户,而止血动作必须平时就演练好。类比:容灾第一原则:主站异常先切备站,不是原地 debug;回滚就是「回切到上一个验证过的恢复点」。技术:① 秒级回滚最近一次变更(前提:版本化 + 回滚预案平时就绪);② 无旧版可回就降级——Agent 退化为简单 RAG 直答或 FAQ 检索,高风险类请求转人工;③ 业务侧限流/熔断,控制坏体验扩散面;④ 事后把本次 bad case 回流进评估集防复发。原则:止损手段要像容灾预案,平时演练过,事故时才敢按。
Q:LLM-as-judge 自己也是模型，凭什么信它的打分？
人话:不能全信——阅卷老师本身也是概率系统,所以自动打分必须配「人工抽检」这双眼睛。类比:校验和只能证明比特没坏,证明不了内容正确;备份验证最终要靠真恢复抽检。judge 是自动校验,人工抽检才是终审。技术:① 定期用人工标注算 judge 一致率(如 kappa 或简单一致百分比),一致率跌破阈值先查 judge 自己;② judge 的 Prompt 和模型版本也纳入版本化与监控清单——它本身就是一条「下游依赖」,同样会静默漂移;③ 优先用成对比较(新旧答案谁更好)代替绝对打分,减少打分漂移;④ 安全合规等高风险场景保留人工必审。
术语卡
数据漂移:输入分布随时间变化(新话题涌入、问法迁移),模型没坏,但在新输入上开始失效。
概念漂移:同一问题的「正确答案」本身变了(如政策更新),监控用的尺子会自己过时。
PSI:群体稳定指数,衡量两个时期分布差异的风控标准工具,常以 0.25 为显著漂移警戒线。
黄金集:每次变更必跑的固定核心评估样本,模型的「恢复演练剧本」,防回归、做对照。
金丝雀发布:新版本先切 5%~10% 流量对照基线,异常自动回滚、正常逐步放量。
基线快照:上线当天拍下的全套指标 + 评估分,之后一切告警都看「偏离它多少」。
LLM-as-judge:用一个强模型当阅卷老师自动打分,线上质量的代理指标,需人工抽检定期校准。
