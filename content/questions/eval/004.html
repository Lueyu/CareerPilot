业务落地 · Q2

如何设计 Agent 的灰度发布策略?

⭐⭐⭐⭐ #灰度发布#上线策略
先说人话:这题问的是——一个改完的 Agent 怎么放出去才不炸线上：放多少、放给谁、出事了怎么收、谁来盯。面试官爱考，因为它一秒分清「扛过生产」和「只跑过 demo」:说不出回滚和护栏的，基本没发过版。最大的暴露点是把它当运维流程背，讲不出 Agent 特有的静默出错和统计验证。
30秒电梯稿

"四个要素：梯度(1%→5%→20%→50%→100% 阶梯放量，每档观察期)、维度(按用户 hash 稳定分流，同一用户体验一致；先内部员工后真实用户)、护栏(每档设自动回滚阈值：解决率下降、投诉率上升、P99 翻倍，触发即秒级回滚)、观测(核心指标看板实时化，客服团队提前知会、随时待命)。Agent 特别点：LLM 输出不确定性高，灰度时长要覆盖足够多的真实场景,不是过 24 小时就放量。"

通俗类比

灰度发布的本质：把「上线」当成一次可控的容灾切换来做。你做过机房迁移或核心系统大版本升级，没人敢一个维护窗口全量切，都是先切只读的边缘业务 → 观察一天 → 切一个业务域 → 再切核心交易；而且切换方案里最重要的从来不是「切过去」，是「怎么切回来」。灰度是完全同一套思路用在软件放量上：1% 相当于「先切一个边缘业务」，100% 相当于「全量切换」，回滚相当于回切方案。哪里像:爆炸半径可控、每步留观察窗、回退路径先于前进路径验证、切换期间值班就是半个事故态。哪里不像:容灾切换面对的是确定性系统——同样的流量打到新机房，行为可以预测；Agent 背后是 LLM 这个概率系统，同一个用户问题，新版今天答对、明天可能答歪。所以灰度在这里不是「验证一次通过」，而是「统计意义上验证通过」——更接近你靠定期的抽样恢复演练来证明备份体系可靠，而不是靠某一次恢复成功就签字。这也是为什么每档要的不只是「观察时长」，而是「足够的真实场景样本量」。

回滚和护栏，用备份体系想:旧版本保持热备，等于「最近一次全量备份绝不能删」——回滚就是从它恢复。护栏指标等于 RPO/RTO 那种预先定义的红线：不是出了事再翻日志找原因，而是先约定「解决率跌到哪条线、点踩涨到哪条线，就自动触发动作」。而 Agent 灰度最阴险的一点，可以用你最熟的场景体会：传统服务故障像备份任务失败——有告警、有错误码、好发现；Agent 答错(比如幻觉)像静默数据损坏——任务全绿、内容是错的，默认监控根本抓不到，必须主动抽样校验。所以 Agent 的护栏不能只盯技术指标(P99、错误率)，必须加「业务质检」指标(解决率、点踩率、judge 抽检)——这是它和传统后端灰度最大的分岔口。

详细拆解

第 0 步：发布前置三问(灰度不是从 1% 开始，是从这里开始)

  • 回滚路径演练过吗？没演练过的回滚方案不算方案——和容灾里「没演练过回切的切换预案等于没有预案」一个道理。演练内容：开关真的能秒级拨回、旧版本实例真的还热着、回滚后老版本真的能服务当前流量。
  • 评估集回归过了吗？新版先在离线评估集(带标准答案的测试集)上跑分，分数不达标连 1% 都不配进——线上灰度是最后防线，不是第一道质检。
  • 监控、值班、客服就位了吗？看板实时化、值班群拉好、客服话术发下去。这三个没到位，灰度就只是「裸奔的新版本」。

1. 灰度梯度与观察期

梯度的设计逻辑只有一条：爆炸半径从小到大，每一步的信息增量要配得上风险。小流量档抓的是「明显的坑」(报错、点踩暴增)；大流量档验证的是「统计意义上的质量」(解决率、成本)。每档时长不是拍脑袋：

  • 内部试用 1~2 周:员工用自己的真实工作流打磨，零外部风险，又叫「吃狗粮」。为什么这么久？因为要等到员工问出各种刁钻真实问题，而不是头两三天的新鲜劲。
  • 20% 档必须覆盖一个周末:周末的用户 query 分布和工作日完全不同——闲聊、模糊问题、长尾意图占比飙升，恰恰是最容易翻车的样本。
  • 50% 双版本并存 2~3 天:这是黄金对比期——新旧各吃一半流量，天然的 A/B 对照,新版到底比旧版好多少，这里出结论最干净。

2. 分流维度(比梯度更容易答错的地方)

  • 用户维度 hash:同一用户永远同版本——A 版答一次 B 版答一次，人设不连贯，体验灾难。实现上是网关/服务层的粘性分流，和蓝绿、金丝雀发布的路由层是同一层东西：
def pick_version(uid, cfg):
    if uid in cfg.pin_old:                   ← 白名单/VIP/大客户:钉死旧版
        return "old"
    if uid in cfg.dogfood:                   ← 内部员工:永远先行吃狗粮
        return "new"
    bucket = stable_hash(uid + cfg.salt) % 100
    return "new" if bucket < cfg.ratio else "old"

三个坑:
1) 必须是稳定 hash,不能用随机数——否则同一用户两次请求换版本
2) salt 换一次,全网用户的桶全部重洗,等于全体重新洗牌——没充分理由不动它
3) 会话开始时锁定版本,会话内不再变(会话 sticky)
  • 场景维度:可以先对低风险意图灰度(查订单先行)，高风险意图(退款)晚开放——按风险分层放量是 Agent 灰度的特色。传统后端没有这层，因为「接口」没有风险高低，「让 Agent 替用户做有后果的动作」才有。
  • 白名单：VIP/大客户最后放量，或干脆钉死旧版本直到充分验证。

3. 护栏与自动回滚(量化写出来)

护栏分两级：硬阈值(技术指标，机器自动回滚不等人)和软阈值(业务指标，告警后人工 10 分钟内决策)——分级是因为业务指标有波动，全自动回滚会被误触发打爆；技术指标(报错、超时)没有歧义，等人工就是浪费爆炸半径。

指标回滚阈值(示例)
解决率/CSAT较基线下降 > 5pct
投诉/点踩率环比上升 > 50%
转人工率突然飙升(用户被惹毛的先兆)
幻觉/引用失败抽样 judge 分下降 > 10%
技术面(P99/错误率)P99 > 2×基线，错误率 > 2%
平均轮次/复访率环比上升 > 30%(用户反复追问 = 其实没解决)
护栏巡检(每 1 分钟):
  采集新版本指标 ──→ 与基线对比 ──┬─ 硬阈值(错误率/P99)触发 → 自动回滚,不等人
                                 ├─ 软阈值(解决率/点踩)触发 → 告警,人工 10 分钟内决策
                                 └─ 全绿 → 本档样本量+场景覆盖够了吗?
                                             ├─ 不够 → 继续观察(不是看天数,看会话数)
                                             └─ 够了 → 放下一档

回滚 = 特征开关拨回旧版本(秒级)，旧版本保持热备——资源不释放，谁先摘谁背锅。另有一个最容易漏的点：状态兼容。灰度期间产生的会话/数据，回滚后旧版本要能接住——这是向前兼容问题：新版灰度期写入的数据格式，老代码要读得懂。用你熟的领域讲：和备份软件升级前必须确认「新版本写的 catalog,回滚后的老版本能解析」是同一件事，升级方案里没这条，回滚就是二次事故。

4. 组织配套(说出来了 = 落地过)

  • 客服/运营提前培训：用户问"你们机器人怎么变了"，一线要有标准话术——客服不知情，用户就会用最坏的猜测填空。
  • 值班响应：灰度期 = 半个事故态，群里有专人盯，出问题 10 分钟内决策回滚。关键设计：决策授权要前置——一线值班就有权按回滚按钮，不用层层审批。这和容灾预案里「谁有权触发切换」必须写进文档是一个道理：爆炸半径在分钟级扩大时，审批链就是助燃剂。

5. 放量到 100% 不是终点

全量后再盯一周，期间发现的 badcase 逐条归因、修复后回流进评估集——成为下次回归的测试用例。评估集和灰度就这样滚动闭环：灰度帮评估集发现盲区，评估集帮下次灰度前移风险。能讲出这个闭环，面试官就知道你不是「发完版就散会」的人。

面试官追问
Q:灰度期间两个版本的数据会互相污染吗？
人话：会有交叠，但管得住——三板斧：按用户隔离、会话内不换版本、数据全量打标，让两版数据像两个独立的备份集，分析时能干净拆开。类比：像你做备份系统升级：新旧并存期间写的元数据必须带版本号，catalog 查询按版本过滤；「转人工」这类后续动作，要像增量备份归到所属全量一样，归因到用户最先接触的那个版本。技术：① 分流按 uid 粘性 hash,同一用户始终同版本；② 会话开始锁定版本，会话内路由不变；③ 所有落库记录(会话、点踩、转人工)带 version 标签，报表按标签拆；④ 跨天归因按「首触版本 + 首触后 N 天」定义清楚；⑤ 50% 双版本并存档反而是最干净的 A/B 对比期——前提就是打标纪律不破。
Q:Prompt 级的小改动也要走灰度吗？
人话：要，但不是同一套重流程——按影响面分级走；而且别被「小改动」骗了，Prompt 就是 Agent 的源代码，改一句话可能让行为大变。类比：像变更管理里区分配置变更、代码变更、架构变更：改个备份窗口时间走快速通道，换存储格式就得全流程评审——判据是影响面，不是改了几行。技术：三级：① 调参数/温度 = 快速通道，评估集回归 + 1% 影子抽样；② 改 Prompt 主逻辑 = 标准灰度；③ 换模型/改架构 = 重灰度 + 双跑对比。所有级别强制过评估集回归，回归的自动化程度直接决定发布速度;Prompt 改动额外要人肉看 badcase 样本，因为评估集永远覆盖不全真实说法。
Q:Agent 的灰度和传统后端服务的灰度，本质区别在哪？
人话：三个根本不同——输出不确定(同一问题两次答案不同，bug 难复现)、好坏是统计量(解决率是百分比，不是报错的布尔值)、伤害是静默的(错误率一点不涨、答案却可能错一片)。类比：传统服务故障像备份任务失败——有告警好发现；Agent 幻觉像静默数据损坏——任务全绿、内容是错的，默认监控抓不到，必须主动抽样校验。技术：① 指标体系从「错误率/延迟」扩展到「解决率/点踩/judge 抽检」；② 观察期按样本量而非天数定；③ 多出「场景维度分层放量」——低风险意图先行，高风险动作后放；④ 回滚救不回已经发给用户的错答案，所以质量护栏必须前移到评估集，不能只靠线上兜底。
Q:观察期多长才算够？放量判据是什么？
人话：判据不是「没炸」，是「指标不但好，而且置信」。观察期由两个东西决定：样本量够不够、场景覆盖全不全——按会话数说话，不按天数。类比：像验证备份可恢复性：不能靠「任务显示成功」，要抽样真恢复；也不能只恢复一种应用，要覆盖关键应用类型——周一早高峰的订单 query 和周末深夜的闲聊，对 Agent 就是两种负载。技术：① 每档预设最小会话数(比如 1% 档 ≥ 5000 会话)，天数只是兜底；② 场景覆盖检查表：工作日/周末、高峰/深夜、高频意图/长尾意图逐项打勾；③ 指标做显著性检验，置信区间和基线不重叠才下结论，防止把正常波动当成「新版更好」；④ 一旦回滚，修复后从 1% 重新爬梯，不允许跳档——和容灾演练失败要重走流程是同一个纪律。
术语卡
吃狗粮:内部员工先用自己的产品——零外部风险的第一个灰度档。
金丝雀发布:灰度发布的英文名，源自矿工带金丝雀下井探毒气——小鸟先下去，人再下去。
特征开关:配置中心里的版本开关，回滚 = 拨开关，秒级生效。
热备:不摘流量、随时可切回的旧版本实例——「最近一次全量备份不能删」。
向前兼容:回滚后的旧版本要能读灰度期间新版本写下的数据——回滚方案里最容易漏的一条。
CSAT:用户满意度评分，和解决率一起构成 Agent 灰度的核心业务护栏。
护栏指标:预先定义、跌破即触发回滚的量化红线——分硬阈值(自动)和软阈值(人工决策)。
