业务落地 · Q3

如何设计 RAG 系统的 A/B 测试?

⭐⭐⭐⭐ #ABTest#RAG#实验
先说人话:这道题在问：你把 chunk 从 512 改成 256,怎么用数据证明系统真的变好了，而不是自我感觉良好？业务方天天要这种证据，所以它是落地岗的高频题。答错的暴露点很典型——把 A/B 测试说成「灰度上线看看反馈」的，暴露压根没做过实验(灰度是发布手段，A/B 是统计实验)；只说「跑一段时间对比一下」的，暴露没有统计素养。
30秒电梯稿

"这题答的是一张施工单：五步流程打底，三个 RAG 特有的坑拉开差距。五步——单一变量(一次只改一个东西：chunk 策略、Rerank、生成模型三选一，否则提升不知道归谁)、随机分流(用户 ID hash 进桶，同一用户永远同组，两组同质才可比)、预设指标(主指标：回答质量 judge 打分或解决率；护栏指标：延迟 P99、单次成本、点踩率——动手前白纸黑字)、样本量(按预期效应量事前算，不够就别开跑)、固定观察期(覆盖工作日和周末，到期才开盲，中途只看护栏做止损)。结论只认统计显著性(p<0.05),而 RAG 最大的坑是裁判本身要校准——LLM 当 judge 有位置/长度/自我偏好，不校准的裁判会把烂版本判成好版本。"

通俗类比

主类比：新版备份引擎上线前的「对打实验」。假设你写了个新版备份引擎，想证明它比旧引擎更快、成功率更高。你不会在演练环境拿几条测试作业跑一下就宣布胜利——演练数据不代表真实负载；你也不会直接全量切换——万一更差就是生产事故。成熟做法是：把生产作业按 hash 随机分成两半,同一时段、同一批存储、同样的真实负载，一半走新引擎、一半走旧引擎，跑满两周，按事先盖章的验收单(成功率、备份窗口耗时、介质消耗)到期对账。A/B 测试的每个动作都能在这个场景里找到影子：随机分流防的是「新引擎恰好接走了容易的作业」；同用户同组防的是同一客户今天快明天慢、体验割裂；验收单先定防的是对账完再挑一个好看的指标宣布达标；到期对账防的是跑到一半看见领先就提前报捷。

哪里像:都是「别全量赌、别拍脑袋，拿对照实验说话」；都要求实验之外的一切变量冻结不动；都强调看事先定死的验收线，而不是事后找角度。哪里不像(也是本题的题眼):备份对打的指标全是客观秒表——作业成功就是成功，窗口耗时掐表可测；而 RAG 的主指标是「答案好不好」,世界上没有秒表能量它，只能请一个 LLM 当裁判打分，而裁判自己还带偏见(偏爱长答案、偏爱自家模型)。于是 RAG 的 A/B 比经典 A/B 多出一整层工作：先证明裁判靠谱，再让裁判评卷。临床界的随机对照试验把这套规矩做到了极致——随机分组、双盲、不许中途偷看数据，对应过来就是：随机分流、用户不知道自己在哪组、不许 peeking(中途偷看)。

详细拆解

第 1 部分：实验设计五步(背这个框架)

先把五步的总览表立起来，再逐步展开——面试时按这个顺序讲，条理分就到手了：

步骤做什么不做会怎样备份世界的对应
① 单一变量一次只改一个东西提升无法归因，回滚都不知道回滚谁对比新引擎时别顺手把介质也换了
② 随机分组用户 ID hash % 100 < 10 → 实验组；同用户同组两组用户不同质，「提升」可能只是分组的运气一致性哈希：同一客户永远路由到同一节点
③ 指标预注册主指标+护栏指标+分析方法，动手前白纸黑字写死事后挑好看指标 = 作弊演练前定死 RTO/RPO 验收线
④ 样本量按 MDE(最小可检测效应)事前算跑三天「感觉差不多」就下结论采样监控：样本不够，1% 的差异和噪声分不开
⑤ 固定观察期覆盖完整周期，到期才开盲中途偷看主指标，假阳性翻倍备份窗口没跑完，成功率不算数

import hashlib

def ab_group(user_id: str, exp_id: str = "chunk256") -> str:
    # exp_id 拼进哈希:不同实验的分流互相独立,不会互相"撞桶"
    h = hashlib.md5(f"{exp_id}:{user_id}".encode()).hexdigest()
    bucket = int(h[:8], 16) % 100
    return "treatment" if bucket < 10 else "control"   # 10% 流量先行
  • ① 假设单一变量:把假设写成规范句式——“把 chunk 从 512 改 256 会提升回答质量”。一次只动一个变量的原因是归因:三个变量捆着改、指标涨了 2%,你答不上预算该投给谁、出了事故该回滚谁——就像同时换了备份引擎、磁带介质和网络带宽，窗口缩短 20% 是真的，但下一季度钱该花在哪一项，没人知道。真要并行验证多个改动，用分层实验(见追问)。
  • ② 随机分组:hash 分流等于负载均衡里的确定性路由——同 user_id 必落同桶，体验一致且分组不泄漏。必须随机而不是「愿意尝鲜的用户进实验组」：愿意尝鲜的用户本来就偏爱新东西，两组天然不同质，这叫自选择偏差。流量比例不必 50/50:10% 先行像灰度放量的节奏，但统计功效按较小的一组算，10/90 的分法需要更多总样本才能补回功效，能 50/50 就 50/50。另外留意新用户：老用户对两版本都有历史预期，新用户没有，混在一起会稀释差异。
  • ③ 指标预注册(动手前白纸黑字)：主指标两种实现——回答质量(LLM-as-judge 按固定 rubric 打 1~5 分)或解决率(用户行为：重问率、点踩率、采纳率；真实行为比打分硬)；护栏指标 = 延迟 P99、单次成本、引用率(防编造)。分析方法也要预写：怎么算显著、按哪几层切分——不然数据到手后有无数种切法，每种切法都能切出好看的故事，这在统计上叫 data dredging。
  • ④ 样本量:按 MDE 算，给个手感——基线解决率 60%,预期提升 3 个百分点(60%→63%),显著性水平 0.05、统计功效 0.8,每组约 4100 个请求。MDE 的直觉是：想测的差异越小，噪声越容易盖住它，样本量按平方级涨——测 1 个百分点的提升，所需样本是测 3 个百分点的 9 倍。所以「预期提升多大」直接决定「要跑多久」；流量不够时，小效应的改动干脆别做实验。记住一句话：测不出 ≠ 没效果，可能只是样本不够。
  • ⑤ 固定观察期:覆盖完整周期——工作日和周末用户问的问题类型都不一样，只跑工作日等于拿半个周期下结论。到时间才开盲；中途只看护栏指标做止损(成本炸了、延迟崩了立刻停)，不看主指标——为什么偷看是作弊，追问里有专门一问。

第 2 部分：RAG 特有的实验坑(拉开差距的细节)

  • judge 校准:LLM 裁判自带三大偏差——位置偏差(先读的答案容易得高分)、长度偏差(长答案显得更可信)、自我偏好(裁判偏爱自己模型家族的文风)。对策：对比时随机打乱 A/B 呈现顺序、交换顺序各判一遍、固定裁判模型版本和 temperature=0、抽 5% 样本人工对齐——judge 与人的一致率 ≥85% 才允许上岗。能讲出「先校准裁判、再信裁判的打分」这句话，面试官就知道你真干过 RAG 的实验。这和你用自动巡检脚本判断备份健康度是同一个职业习惯：脚本本身有 bug 时会把烂版本判成好版本，而且是静默错误——所以脚本上线前，必须先拿一批人工确认过好坏的作业验证脚本自己判得准不准。
  • 新奇效应(novelty effect):新版本因为“回答更详细、界面更花哨”短期点踩偏少，两三周后新鲜感消退、数据回落——观察期太短，就会把新鲜感红利误读成真实提升。这也是固定观察期不能太短的第二个理由。
  • 变量泄漏:A/B 之外的东西悄悄变了——最典型的是模型供应商那天升级了后端、或上游团队动了共享服务，你的对照组已经不是你以为的对照组了。对策：把实验之外的所有组件版本钉死；并且定期跑 A/A 测试(同版本对同版本)校验系统噪声底——A/A 两边理应打平，如果"测出了显著差异"，说明分流系统或测量系统本身有病，先修测量再谈实验。
  • 长尾问题:整体均值好看，但长尾场景(罕见问题、超长文档)变差被平均掉了——均值会稀释最差体验，和盯 P99 是同一个道理。对策：按问题类型/难度分层看指标分布，不只看总均值；上线后单独监控长尾请求的负反馈。

第 3 部分：离线/在线的配合(高频追问点)

  • 离线评估集先筛:改动先过黄金集(便宜、快、可复现)，有希望再上线上 AB(真实、贵、慢)。这和生产发布的顺序一模一样：先在演练环境全量回归，过了再上生产灰度。离线是漏斗，在线是终审——离线筛掉八成明显不行的想法，省下宝贵的线上流量。
  • bad case 回流:线上实验同时回收新 bad case → 回流测试集。实验不但是验收，还是采集新测试用例的管道——生产事故复盘出来的案例要进回归集，这是你做了多年备份的老习惯，平移过来就行。
面试官追问
Q:流量小(内部系统几百人)怎么做 AB?
人话:几百人跑不出统计功效，别硬做 AB——换方法，并且坦然承认「这个量级做不了严格统计」，这句话本身就是加分项。类比：机房里就两台机器，撑不起「100 台灰度对打」的实验设计；硬跑出来的“显著差异”大概率是噪声，拿它拍板比不拍板更危险。技术：三档降级：①交替时间窗——本周全量 A、下周全量 B,多轮交叉，缓解“这一周作业恰好简单”的时间趋势；②用户内交叉——每人交替体验两版本，自己当自己的对照，方差大幅减小；③再小就干脆离线评估+人工评审，给定性证据。核心姿态：不假装在做 AB。
Q:质量提升了但成本也涨了，怎么决策？
人话:没有免费的午餐，把 trade-off 摆上桌面，用事先定好的规则或业务方拍板，工程师不做独裁。类比：容灾方案想把 RTO 从 4 小时压到 30 分钟，得上双活机房、成本翻倍——你不会自己拍板上双活，而是给业务方摆一条「每快一分钟花多少钱」的曲线，让他们选点。技术：两条路：①复合决策函数——决策分 = 质量分 − λ×成本，λ 反映「一分质量值多少钱」，同样要在实验前预注册；②约束式——先定死「成本不得超基线 10%」,在此约束下最大化质量。最终把各方案的帕累托前沿亮给业务方拍板；避免数据到手后临时挑一条对自己有利的算法。
Q:实验中途能不能看数据？看到领先能提前宣布吗？
人话:护栏随便看(那是保命的)，主指标到期才看(那是防作弊的)。类比：容灾演练中途发现设备冒烟，必须立刻中止——这是止损；但“切换成功率”的最终验收要等全部演练跑完对账——窗口没跑完就宣布成功，等于考试没交卷先给自己打分。技术：peeking 的问题是假阳性膨胀：每偷看一次都是一次新的“摸奖”，粗算偷看 20 次、至少一次“显著”的概率从 5% 涨到 64% 上下(1−0.95²⁰)。正确姿势：止损线预注册——护栏指标崩了(成本超线、P99 翻倍)立即停；主指标要么不看，要么用序贯检验这类多次查看有校正的方法。
Q:一次上线同时改了 chunk 策略、Rerank 和 Prompt,指标涨了 2%,能说有效吗？
人话:能说“这一捆改动整体有效”，不能说“其中哪个有效”——归因丢了，而工程上最需要的恰恰是归因。类比：备份引擎、介质、带宽同时升级，窗口缩短 20% 是真的，但下季度预算只够投一项时，你答不出投哪项最值。技术：规范做法是拆实验：多个实验用分层实验框架(Google 的 Overlapping Experiment Infrastructure 是奠基之作)在不同流量层并行，互不干扰；或上全因子设计——2³=8 个组合，贵但能量出交互效应。至少保底：捆包上线前，留一个只改单变量的对照。
Q:LLM 裁判可信吗？怎么校准？
人话:能用，但先给裁判做岗前体检，体检不过不许上岗——不校准的裁判可能把烂版本判成好版本，而且是静默错误。类比：自动巡检脚本判断备份作业健康度，脚本自己有 bug 时会把坏作业标成好的，用户未必发现，发现时已是信任事故——所以脚本上线前要拿人工确认过的作业验证它的判准率。技术：校准三板斧：①控偏差——随机打乱答案呈现顺序、交换后各判一遍(治位置偏差)、固定裁判模型版本和 temperature=0;②对齐——抽 5% 人工双评，人机一致率 ≥85% 才上岗；③持续——上线后定期抽检，裁判模型一升级必须重新校准。细节见 LLM-as-a-Judge 论文。
术语卡
MDE:最小可检测效应，你想稳稳测出的最小提升幅度；它决定样本量，样本量随它缩小按平方级暴涨。
A/A 测试:同版本对同版本，理应打平；若“测出显著差异”，说明分流或测量系统有病——先修测量，再谈实验。
Peeking:中途偷看主指标、看到领先就停；每偷看一次都在增加假阳性，20 次偷看能把 5% 膨胀到六成上下。
p 值:假设“改动其实没用”成立时，出现当前这么大差异的概率;p<0.05 才敢说这提升“不太像碰巧”。
LLM-as-judge:用 LLM 给答案打分的主指标实现，省人力但自带位置/长度/自我偏好，必须先校准再上岗。
新奇效应:用户对新版本的新鲜感红利，几周后消退；观察期太短会把红利误读成真实提升。
