设计 Multi-Agent 协作效率实验

⭐⭐⭐⭐ #MultiAgent#实验设计#效率评估
30秒电梯稿

"我会设计一个受控对比实验回答『多 Agent 到底值不值』:① 数据集用可分解的复杂任务(多跳问答、多工具规划),带标准答案和可并行子任务标注;② 对照组给单 Agent 同样的模型、工具和同等 token 预算,保证公平;③ 指标三层——成功率(效果)、步数/延迟/token(效率)、judge 分(质量);④ 消融拆 Agent 数量、拓扑、通信方式;⑤ 结论重点报告协作收益 vs 通信开销的拐点,而不是只报一个成功率。"

通俗类比

就像大厨房做年夜饭:一个人(单 Agent)锅碗瓢盆全自己来,菜一多就手忙脚乱、容易糊;分成洗菜、切配、掌勺三个人(多 Agent)各司其职,但多了一道『传菜』的沟通成本。实验就是要回答:任务复杂到什么程度,『多雇几个人』省下的力才超过『来回喊话』浪费的力。

详细拆解

1. 先想清楚要回答的问题:不是"谁成功率高",而是"每单位成本的成功率"

  • 多 Agent 天然比单 Agent 多消耗 token(角色分工、多轮通信),所以只比成功率是耍流氓,必须把成功率归一化到单位 token/单位延迟上再比。
  • 公平性三同:同基座模型、同工具集、同预算上限(步数/token/墙钟时间)。任何一条不同,结论都会被"模型更强/工具更多"污染。

2. 数据集:选"可分解的复杂任务",难度分层

  • 三类任务:多跳问答(信息散在多个来源)、多工具规划(订票+订酒店+查天气一条龙)、带约束的长任务(改代码+补文档)。
  • 标注不止标准答案,还要标子任务分解与可并行性,这样能算出"理论最优效率"当上界。
  • 难度分层:简单(线性串行)/中等(子任务可并行)/难(子任务有依赖+动态信息)。任务太简单会出现天花板效应,单 Agent 稳赢,实验结论失真。

3. 指标:效果 / 效率 / 质量三层

维度指标说明
效果任务成功率、子任务完成率核心,但别只报这个
效率平均步数、墙钟时间、总 token、单位成功率成本多 Agent 的命门在这
质量LLM-as-judge rubric 分、人工抽检一致率judge 要校准位置/长度偏差

4. 对照组与消融(实验骨架)

  • 上界是"天花板",下界是"单 Agent",多 Agent 的价值要落在两者之间才算有意义。
  • 消融重点是回答"多少个 Agent 最优、要不要 Supervisor、并行到底省不省时间"。

5. 高频翻车点

  • 错误级联:一个子 Agent 错了,后续全错——要记录错误源头,区分"单点错"和"级联错"。
  • 上下文漂移:多轮传递后信息丢失/扭曲,单独测"关键信息在多轮通信后的保留率"。
  • 多 Agent 输出往往更长,judge 有长度偏好 → 校准或改用程序化校验。
面试官追问
Q:多 Agent 一定比单 Agent 好吗?
不一定。简单线性任务单 Agent 通常更稳更便宜;多 Agent 的优势只在"任务可分解、子任务可并行、且单 Agent 上下文过载"时显现。所以结论要按难度分层给,而不是一句"多 Agent 更好"。
Q:怎么保证单 Agent 对照组是"公平"的?
同基座模型、同工具集、同预算上限(步数/token/墙钟);单 Agent 也必须拿到多 Agent 会拿到的所有工具,否则多 Agent 赢在"工具多"而不是"分工好"。若担心单 Agent 上下文过长,给它同等长度的摘要上下文。
Q:成功率一样但成本翻倍,你怎么写结论?
结论就是"多 Agent 无增益,有负增益"。用单位成本成功率做主排序指标,把质量-成本画成 Pareto 曲线,让业务方在"要不要多花一倍钱换可能的质量提升"上拍板,工程师只给证据不给主观偏好。
Q:Agent 之间通信方式会不会影响结论?
会,而且很大。共享黑板(写状态+读状态)比自由对话更可控、token 更省,但对并行冲突要处理;消息传递更灵活但更贵。所以通信方式要作为消融变量单独测,否则你测的可能是"通信协议",不是"多 Agent 架构"。
术语卡
消融实验:逐个关掉/改变某组件,看指标变化定位其价值。
天花板效应:任务太简单,大家分数都顶格,差异测不出来。
Oracle 上界:理想最优解,用来量化方法离理论最好还差多少。
错误级联:上游出错导致下游连环错,评估要追溯到第一环。
单位成本成功率:成功率除以 token/延迟,衡量"性价比"。
LLM-as-judge:用强模型按 rubric 打分,需校准位置/长度偏差。
