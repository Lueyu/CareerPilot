项目上线后，你是如何收集bad case并迭代模型/策略的？有做在线学习吗？

⭐⭐⭐ #迭代优化#在线学习 字节 / 阿里
30秒电梯稿

"我搭的是数据闭环:收集 → 归因 → 修复 → 回归 → 上线。① 收集:bad case 来自用户点踩、转人工、评价文本、模型低置信、内部抽检,其中用户点踩最值钱;② 归因:用 trace 回放定位错在意图/检索/生成/工具哪一环;③ 修复:从便宜到贵——补 few-shot、改 prompt、调检索参数、补知识、加工具,最后才上 SFT/RLHF 微调;④ 回归:进测试集跑离线评估 + 灰度。关于在线学习,我没做实时版——风险是毒数据、灾难性遗忘、概念漂移、不可回滚,实际做法是'准实时回流 + 定期离线训练 + 灰度上线'。"

通俗类比

像餐厅改菜单:把顾客差评、退菜、服务员观察(点踩/转人工)收集起来,后厨归因是"太咸还是食材不新鲜"(归因),对症改配方(修复),先在小桌试菜(灰度回归),好了才全面换。所谓在线学习相当于"顾客边吃边自动改配方"——听着酷,但可能被一两个奇葩顾客带偏,把好好的菜改砸,还改不回来;所以一般攒一批再统一改,而不是实时自动改。

详细拆解

1. bad case 从哪来(六类来源)

  • 用户点踩/差评:最直接的负反馈,含金量最高。
  • 转人工:AI 接不住才转人工,是能力边界的最佳样本。
  • 评价文本/投诉:带原因,比单纯点踩信息量大。
  • 模型低置信/自检失败:主动暴露"我不确定"的样本。
  • 用户修正行为:用户反复改述/重问,说明首答没解决问题。
  • 内部抽检:每天抽 N 条人工复核,补自动监控的盲区。

2. 归因(定位错在链路哪一环)

  • 归因错了,修复就白搭——所以全链路 trace 落库 + 可回放是迭代的地基。
  • 同类型 case 自动聚类,优先修高频高影响的。

3. 修复手段(从便宜到贵,别一上来就微调)

层级手段成本/风险
Prompt补 few-shot、改指令、加约束最低,改完即生效
规则/检索调召回、改重排、补知识库、加工具低
小模型意图/工具选择分类器重训中
基座模型SFT 微调 / RLHF / DPO最高,周期长、要评测

4. 迭代流程(数据闭环)

  • 收集 → 去重/标注/聚类 → 修复 → 把 case 写进回归测试集 → 离线评估 → 灰度 → 全量。
  • 度量迭代效果:新 bad case 率、点踩率、转人工率、解决率,配合 AB 对比,并确认"没把好 case 改坏"。

5. 在线学习(考点:为什么不轻易做)

  • 什么是在线学习:用线上流式数据持续更新模型参数。
  • 风险:① 毒数据——个别恶意/噪声样本直接带偏;② 灾难性遗忘——学了新忘旧;③ 概念漂移——分布变了模型过拟合当下;④ 不可回滚/难评测——出问题难定位是哪个样本害的。
  • 折中做法(我实际用的):'准实时回流 + 定期离线 SFT/DPO + 灰度'——数据实时收集,训练周期化,上线走灰度;非参数层面可做轻量在线选择(如 MAB 调工具/模型路由),风险可控。
面试官追问
Q:为什么不直接做在线学习,技术难点具体是什么?
难点不在"能不能实时更新",而在安全与稳定:① 线上反馈噪声大、还有恶意注入,单个样本可能是毒;② 流式微调容易灾难性遗忘和概念漂移;③ 出了问题难回滚、难复现定位。工程上"实时数据 + 周期训练 + 灰度"几乎能拿到在线学习 90% 的收益,风险却小一个量级,所以更常用。
Q:bad case 量大,怎么高效标注?
先聚类(按错误类型/意图),再按影响力排序(高频优先),人工只标代表性样本;用 LLM 半自动打标 + 人工抽检;很多归因可以自动化(工具调用失败、检索空、格式错误都不用人工看)。
Q:修复后怎么证明没把好 case 改坏?
把历史 good case 也放进回归集,修完同时跑"bad 集要变好 + good 集不能退化";再做灰度 AB,看整体点踩率/解决率,而不是只看个别 case 有没有修好。
Q:做过 RLHF 或 DPO 这类对齐吗?
做过 DPO:把点踩/点赞样本构造成偏好对(win/lose),在 SFT 后做偏好对齐;成本比 RLHF 低、更稳定。关键前置是偏好数据质量——点踩不一定代表"回答错",要先归因筛选出真正的偏好信号。
术语卡
Bad case:线上表现不佳的样本,迭代的燃料。
数据闭环:收集→归因→修复→回归→上线的循环。
在线学习:用流式数据持续更新模型的训练方式。
灾难性遗忘:学新任务时忘了旧能力。
概念漂移:数据分布随时间变化导致模型过时。
DPO:直接偏好优化,用偏好对做对齐,比 RLHF 稳定。
