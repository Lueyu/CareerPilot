Agent算法 · Q32

设计 Memory 压缩算法的评估实验

⭐⭐⭐⭐ #Memory#压缩#实验设计
先说人话:这题在问:Agent 的记忆被压小之后,信息到底丢了多少,你打算用什么实验把它量出来。压缩率好算,保留率难测,难就难在「有损」二字。面试官爱考它,是因为只会答「测一下准确率」的人,一开口就暴露出缺对照组、缺相对化、缺净损失归因——实验设计没入门。
30秒电梯稿

"我会画一条『压缩率—保留率』权衡曲线:① 数据集用长对话/长文档 + 问答对,并针对早期信息专门出题——答案必须只能从被压缩的记忆里找出来,不靠常识能猜到;② 压缩率=1−压缩后 token/原始 token,保留率=压缩后答对率/用全量记忆的答对率,相对化之后才能跨方法公平比;③ 对照组:全量记忆(上界)、滑动窗口只留最近几轮(下界);④ 横向对比摘要、关键事实抽取、向量检索按需回源等压缩法,加做压缩粒度和长度档位的消融;⑤ 在 (压缩率, 保留率) 坐标系里找『花最少 token 保住最多信息』的拐点,并同时报压缩耗时、查询延迟和 token 总账——省的 token 和摘要烧掉的 token 要算净值。"

通俗类比

把 Memory 压缩想成你天天在做的备份重删/压缩。Agent 的对话长期记忆会越滚越长,全部塞进 大语言模型的上下文既塞不下也烧钱,所以要压——这和备份系统对备份数据做重复数据删除、压缩来省空间省带宽,是同一类动作。哪里像:压缩率的定义一模一样(压掉的比例);好不好都不能看压缩环节自己,要看下游任务——备份压缩得好不好,最终看恢复行不行;记忆压缩得好不好,最终看问答答不答得对;而且都面临同一条铁律:压得越狠风险越大,都得给业务方一条「压到多小还能用」的承诺线。

哪里不像——这正是这道题存在的原因:你熟悉的备份压缩是无损的——zstd、LZ4 解压回来逐字节还原,所以存储行业从来不需要「评估压缩后的信息保留率」,解压加个哈希校验就够了;而 Agent 记忆压缩是有损的——让 LLM 把八十轮对话写成一段摘要,细节丢失是必然的,丢多少却谁也说不清,只能靠实验测量。所以这道题的本质:备份界用算法性质保证的保真度,你要换成用「评测集 + 对照组」量出来。

再把几个主角一并映射掉:滑动窗口(只留最近 N 轮)= 只保留最近 N 天备份、更早的过期淘汰的备份轮转策略——省是真省,但早期的账查不到了;全量塞上下文 = 不做任何优化、每次全量恢复,信息零损失但谁也养不起;摘要+检索混合 = 生产备份的标准形态:平时只留 catalog(目录),要用哪个文件按目录精确恢复——Agent 记忆的最优解往往也是这个长相:常态强压缩,碰到高价值事实再按需回源。

详细拆解

开场:这套实验和容灾演练是同一个套路

容灾演练怎么做的?先写剧本(造可控的故障场景),再定判据(哪些业务多长时间内恢复算成功),然后跑不同预案对比,最后出选型对比表。记忆压缩实验一模一样:剧本=评测集,判据=指标,预案=各压缩算法,对比表=权衡曲线。总流程如下,再按五步拆细。

① 造数据:长对话/长文档 + 问答对(答案只藏在记忆里,靠常识猜不到)
② 定判据:压缩率 CR / 保留率 / 效率(压缩耗时、检索延迟、token 总账)
③ 跑方案:全量(上界)、滑动窗口(下界)、分层摘要、槽位表、向量检索按需回源…
④ 出结论:每个方法一个 (CR, 保留率) 点 → 画前沿 → 找拐点 → 给工程推荐

第 1 步:先把两个核心量定义死(否则没法比)

  • 压缩率 CR= 1 − token(压缩后) / token(原始),范围 [0,1],越大越狠。例:10 万 token 的对话史压到 1 万,CR = 0.9,省下九成注入成本;CR=0 表示没压(全量),CR 趋近 1 表示几乎全丢(只剩一句「我们聊过」)。
  • 保留率(保真度)= 用压缩后记忆的下游任务成绩 / 用全量记忆的成绩。必须相对化:绝对分受模型本身能力影响太大——有的题模型闭着眼也能蒙对,有的题给它原文也答不出;除以全量基准后,模型自身能力在分子分母同时出现、大体抵消,这样才能跨方法、跨任务比较。
  • 二者天然打架:压得越狠,保留率越低。这正是它和备份压缩最大的不同——备份压缩无损,省多少都不伤恢复;记忆压缩有损,省得越狠伤得越重。所以实验目标不是评出一个「最好的算法」,而是精确量化这条 trade-off 曲线,让业务方在曲线上选点。这个定位先说对,后面才不跑偏。

第 2 步:数据集——让「信息是否被压丢」可判定

出题的总原则:答案必须只能从被压缩的记忆里来。凭常识就能答对的题,测的是模型不是压缩——好比演练恢复时,不能拿「应用自带本地缓存也能起来」充数。

  • 长对话史(几十到上百轮)+ 针对「早期信息」的问答:如「我第 3 轮说过的名字是什么」。为什么专打早期?因为不同压缩法的丢法是有方向性的——滑动窗口系统性丢头部;如果题目均匀分布,大量题落在「反正都留着的最近几轮」上,所有方法都接近满分,实验白做。题目要往最容易丢的位置打。
  • 长文档 + 跨段落事实问答:答案要综合前后多段才能答对,专测压缩是否打断了跨段关联——逐段摘要的典型病是「每段摘要都对,合起来答不出」。
  • 关键信息分层埋点:在 head/middle/tail 各埋若干关键事实,像演练前故意放进系统的金丝雀数据——演练后逐一核对,丢没丢一目了然。
把 80 轮对话当成 80 个时间点的备份链,三个区段各埋「金丝雀事实」:

  [ 轮1~10  head ][ 轮11~50 middle ][ 轮51~80 tail ]
      ▲名字/约束        ▲改期的数字        ▲最新偏好

  滑动窗口(只留最近10轮):head、middle 全截掉 → head 埋点题几乎全错(下界的丢法)
  分层摘要:               每层留一份压缩版   → 埋点可能「摘要时没带上」
  全量记忆:               原文全在           → 埋点全对(上界)

第 3 步:指标三层

维度指标说明
压缩效果压缩率 CR越小越好,但要看保留率配比
信息保留下游问答准确率、事实召回率、关键槽位准确率核心,相对化报告
效率压缩耗时、单次检索/注入延迟、token 成本在线系统最敏感

表里那行「越小越好」要会读:它是信息风险视角——CR 越小(压得越保守),丢信息风险越小;但换成 token 成本视角恰恰相反,CR 越大越省。所以 CR 单独看没有绝对好坏,必须和保留率配成 (CR, 保留率) 的点才有意义——这正是表里特意写「要看保留率配比」的原因。

「信息保留」一行给了三个粒度,各有分工:下游问答准确率是端到端黑盒分,最贴近真实体验,但会漏「碰巧答对」;事实召回率对着埋点清单逐条核(算法口径同 Recall@k,只是对象换成事实点),能定位丢的是哪一层——head 丢得多还是 tail 丢得多,直接指向该换哪种压缩法;关键槽位准确率单独盯人名/数字/日期这类错一个就翻车的字段——像备份系统里 catalog 必须零错,正文数据才谈得上有损容忍。

「效率」一行是三笔账:压缩耗时像备份作业里压缩阶段吃 CPU——LLM 摘要同样要花时间花 token,离线压还是边写边压,就是「后处理重删 vs 在线重删」的同款取舍;单次检索/注入延迟是因为向量化方案把成本转嫁到查询路径上,用户多等的就是这一段;token 成本要算总账——压缩省的是生成侧注入的 token,摘要和检索本身也在烧 token,结论里要报净值而不是只报省了多少。

第 4 步:对照组与待比方法

  • 上界:全量记忆。不做压缩直接塞上下文,信息零损失,保留率的分母就是它。两个附加作用:① sanity check——全量都答不对的题是模型能力问题,从统计里剔除;② 顺带验证全量是不是真上界:上下文塞太长,模型对中部信息的利用率反而下降(见 Lost in the Middle 论文),超长场景下全量未必真无损——发现这一点本身就是实验洞察。
  • 下界:滑动窗口只留最近 N 轮,经典「丢早期信息」基线。最便宜,系统性丢头部,head 埋点题几乎全错。设下界的意义是给所有花哨方法一条及格线:赢不过无脑截断,再高级也白搭——就像任何容灾方案至少要赢过「手动拷贝」。
  • 待比方法:分层摘要(LLM 逐段压缩再拼接——保住时间局部性,丢跨段关联)、关键事实抽取/槽位表(像 catalog:结构化字段准,但语气和上下文全丢)、向量化+按需检索(原文不压,每次查询只注入 top-k 相关片段——省的是注入 token 而非存储,CR 按注入量算)、LLM 整段摘要(一次压到底,最省也最暴力)。
  • 消融:压缩粒度(整段 vs 逐轮——粒度越细局部信息越保、跨段关联越碎)、目标压缩长度档位(比如压到 50%/25%/10% 三档,让每个方法自己画出一条曲线)、是否强制保留「人物/数字/日期」等关键槽位——这组消融往往能证明:保哪些信息,比压多狠更影响保留率。

第 5 步:权衡如何呈现与下结论

  • 每个方法在 (CR, 保留率) 坐标系画一个点,连出Pareto 前沿:前沿上的方法=没有任何别的方法在两个指标上都更优;前沿右下方的点被「支配」,直接淘汰不讨论——就像选型会上「又贵恢复又慢」的方案,根本不用上会。
  • 找 knee point(拐点):过了它再压,token 收益变小、保留率却陡降——工程上就停在这。类比:保留策略从 90 天砍到 30 天,省的是真金白银;30 天再砍到 7 天,砍掉的就不是存储,是业务真要用的数据了。压缩同理:拐点之后再压,压掉的就不是冗余,是信息本身。
  • 常见最优解是摘要+检索混合:常态用强压缩把历史对话滚动压成摘要(像备份轮转把日备份合并成月备份——粒度变粗但覆盖还在),关键槽位和原文单独留库,查询时用向量检索「按需回源」,而不是把所有记忆都硬压。混合方案要额外报回源命中率和它带来的查询延迟,别只报 CR。
  • 统计纪律:每个配置多跑几遍(不同采样、不同题目顺序),题目量要够(几百条起步),报均值——保留率差 2% 可能只是抽样噪声;容灾演练也不会只跑一次就下结论。
保留率
 100% ● 全量记忆(上界,CR=0)
      │ ╲
  90% │  ● 摘要+检索混合 ← 拐点常在这附近:再往右压,省得少、掉得快
      │    ╲

      │       ╲   ● 分层摘要(不保护槽位)

  这串点就是 Pareto 前沿:每个点都是「同一档压缩率下保留率最高」的解;
  落在它右下方的方案被支配,直接淘汰。(各点位置仅为示意)
面试官追问
Q:信息保留率怎么定义才不会被「猜对」污染?
人话:保留率最大的坑是「模型蒙对的题」混进分子——题不用记忆也能答对,丢信息的方法照样测出高分。类比:像演练恢复时,有的应用自带本地缓存,不靠备份也能起来,这种「成功」证明不了备份有效;必须专挑只有备份里才有的数据来验。技术:两个办法:① 用相对保留率(压缩后/全量),模型自身能力在分子分母同时出现,基本抵消;② 出题时构造「答案只存在于被压缩记忆里」的题——生僻事实、虚构实体、人工改写,答对一定是因为记得,不是因为蒙的。
Q:压缩后答错,怎么区分是「压缩丢信息」还是「模型本来就不会」?
人话:得先给模型做个体检,把它「本来就不会」的题剔掉,剩下的错才能记到压缩头上。类比:像恢复失败先分锅:用一次全量恢复做基准,全量也起不来的应用是应用自己的问题,不算备份的账;「全量能起、压缩后起不来」的才是压缩的净损失。技术:消融对照:同一批题先让模型带全量记忆作答,答错的从压缩实验里剔除(模型能力问题);只统计「全量答对、压缩后答错」的题。这同时要求评测集全量答对率不能太低,否则有效样本太少,差几个点全是噪声。
Q:压缩率是唯一的成本吗?
人话:不是——压缩本身要花钱花时间,查询侧还可能变慢,最后要算总账。类比:重删给备份省了存储,但重删计算吃 CPU、可能拖长备份窗口;按需恢复省了恢复量,但要维护 catalog。存储的账从来是双边的,记忆压缩是同款账。技术:成本三块:① 压缩耗时与调用成本,LLM 摘要按 token 计费;② 查询侧延迟,向量检索按需回源把延迟加在用户每次提问上;③ token 总账——压缩省的是生成时注入的 token,摘要和检索注入本身也在烧 token,要报净值。所以效率层指标必须和 CR 一起上桌。
Q:怎么保证测试集没被模型「背过」?
人话:公开题集模型训练时可能见过原题,成绩虚高,相当于考场泄题。类比:用 demo 数据测备份恢复能力没有意义,必须拿生产真实数据测;杀毒软件也得用没见过的新样本,测出来的才是「查杀」不是「背题」。技术:① 用私有/新构造数据:人工改写、领域专属长文档、虚构实体名;② 做污染检测——让模型不注入任何记忆直接作答,答对率应接近零,若它能凭空答出被压掉的信息,说明题目泄漏了(同类问题见数据泄漏),相关题作废重造。
Q:为什么不直接给一张排行榜,说哪个压缩方法最好?
人话:因为两个指标天然打架,不存在「综合分最高的方法」,只存在「按你的预算挑哪个点」。类比:像容灾方案选型:RPO 越小成本越高,没有全面最优的方案,只有一条「花多少钱买多少数据安全」的前沿——你把前沿给业务方,让他按预算选,而不是替他拍板。技术:(CR, 保留率) 是多目标问题:高频闲聊场景能接受高 CR 低保留;金融、医疗场景关键槽位错一个就是事故,要低 CR 高保留。所以交付物是 Pareto 前沿 + 拐点(默认推荐)+ 按业务权重选点的说明,而不是一张单指标排行榜。
术语卡
压缩率:1−压缩后大小/原始大小,越大压得越狠、省得越多。
信息保留率:压缩后成绩/全量成绩,衡量信息丢了多少;相对化后才可跨方法比较。
Pareto 前沿:没有哪个点在两个指标上都更优的解集;前沿之外的点直接淘汰。
Knee point:权衡曲线拐点,过了它边际收益骤降,工程默认停在这。
滑动窗口:只留最近 N 轮记忆,最省但系统性丢早期信息,实验里的下界。
槽位:结构化关键字段(人名/日期/数字),压缩时须强制保护的高价值信息。
有损压缩:解压不还原原样的压缩——记忆压缩属于此类,所以才需要实验测保留率,这点与备份界的无损压缩根本不同。
