Agent核心 · Q37

Agent怎么评估效果？

⭐⭐⭐ #Agent评估#效果评价 字节 / 阿里(高频)
先说人话:这题问的是:你做的 Agent 到底好不好用,你拿什么证据说服面试官。它高频,因为答「跑跑测试集看对错」的人一抓一大把——暴露的是只会调模型、没搭过质量体系。评估之于 Agent,就像恢复演练之于备份:没验证过的能力,等于没有能力。
30秒电梯稿

"分三层说。第一,指标多维:Agent 是多步系统,不能只看『答对没』——任务成功率、工具选择/参数准确率是效果分;平均步数和延迟看有没有绕路;单任务 token 成本老板必看;幻觉率是安全红线。结果对了但绕了三次远路,照样算不合格。第二,离线评估:固定测试集 + 三级自动打分(规则 → 程序化校验 → LLM-as-judge),接进 CI,每次发版跑回归,专门防退化。第三,在线评估:AB 实验看解决率、点踩率、转人工率,用户的负反馈自动回流成新测试样本。核心思想一句话:离线是门禁防退化,在线是真相定胜负,两层必须闭环。"

通俗类比

先对齐一个你最熟的常识:备份行业有条铁律——没做过恢复演练的备份,等于没有备份。Agent 评估就是这同一条铁律在 AI 系统上的翻版:离线评估是演练,在线评估是真实故障。离线=拿固定剧本在演练环境反复测,便宜、可重复、能进 CI 门禁;在线=让真实流量和真实用户当考官,贵、噪声大,但只有它说真话。哪里像:演练年年全绿不代表真故障顶得住,离线高分同样不代表线上好用——因为剧本永远编不全生产的意外。哪里不像:容灾演练可以主动注入故障、把系统故意打挂来看表现;Agent 的线上评估不能故意坑用户,只能靠小流量灰度、AB 分流一点点试探真相。

LLM-as-judge 相当于请第三方审计。开放性任务(写方案、查资料)没有唯一正确答案,『好不好』得有人判,但不能让开发自己验自己的活——就像备份验收要拉独立团队签字,Agent 判卷要拉一个更强的模型当裁判,拿着评分细则(rubric)逐项打分。哪里像:真人审计员有偏好(报告厚的显得工作量大、先看到的标书占便宜),LLM 裁判也有系统性偏差——偏爱长答案、偏爱先出现的答案、偏爱自家家族的模型。哪里不像:真人审计员你没法「洗牌」,LLM 裁判可以随机换打分顺序、换裁判家族来消除偏差,成本也只是几次模型调用的钱。

bad case 回流就是故障复盘回灌演练库:线上发现一起点踩,复盘后写成新剧本进测试集,下次发版这条 case 就在门禁里候着。你的测试集因此越来越像真实世界,而不是越来越像你以为的世界。

详细拆解

1. 为什么 Agent 评估比普通模型难

普通 QA 模型一问一答,对就是对、错就是错。Agent 是多步、有交互、有副作用的系统——这个体验你其实早就有了:一条备份作业也是多阶段的(快照 → 去重 → 上传 → 校验),「作业状态=成功」根本不等于过程健康,你得翻各阶段日志看重试了几次、校验过没过。Agent 的麻烦更进一步:中间一步错了,最后可能碰巧对,也可能被后面的自我纠正救回来:

用户任务: "查这批订单里哪些还没开发票"
Agent 轨迹:
  ① 选工具: 查订单列表        ✓
  ② 传参:   status=已开票     ✗ ← 参数传反了
  ③ 自我纠正: 换条件重查        ✓
  ④ 组织答案输出               ✓  → 最终答案正确

只看结果: 成功 ✓
看过程:   一次无效调用,多花 1 倍 token 和 1 倍延迟
          下次环境稍变,②的错可能就救不回来了(稳定性隐患)
  • 多步有交互:中间工具调错了,最终答案可能「碰巧」对或错,单看最终答案会误判——就像只看作业成功标志不看阶段日志。
  • 任务开放:很多 Agent 任务(写方案、查信息、操作订单)没有唯一标准答案,只能靠评分细则+裁判来判。
  • 有副作用:Agent 会真调工具、真改数据,评错了不是丢分,是线上事故——所以越权操作数是红线指标。
  • 结论:评估要过程 + 结果 + 成本三本账一起看,缺一本都是盲人摸象。

2. 指标体系(别只会说"准确率")

维度指标说明
效果任务成功率、工具选择准确率、参数准确率核心指标,离线可测
效率平均步数、工具调用次数、P50/P99 延迟步数多=绕路,费钱费时
成本单任务 token、折算金额老板最关心
安全幻觉率、越权操作数、拒答合理率红线指标
过程轨迹步准确率、有效步占比、无效调用数多步任务的中间质量账,和结果分分开记

这张表的价值在「多维」两个字。只报成功率 95% 是不够的——如果单任务成本 ¥1、平均绕路 3 次,业务根本用不起;反过来,幻觉率0.5% 在客服场景可能可容忍,在操作订单的场景就是一次事故的种子。指标要按业务风险配权重,不是一列了事。

3. 离线评估:测试集 + 三级自动评分

三级打分按「可靠、便宜优先」排序,能低级别解决的绝不用高级别——这和恢复验证能用校验和自动跑就不上人肉的道理一样:

  • L1 规则评分:关键词/精确匹配,快而便宜,但死板——「答对了但没出现关键词」会冤枉好人,只适合 FAQ 类封闭场景。
  • L2 程序化校验:代码题跑单测、工具调用比 Schema、数学题验算、SQL 题比对结果集。能程序化的尽量程序化,最可靠——恢复后自动 checksum 校验永远比人肉翻日志靠谱,同一个道理。
  • L3 LLM-as-judge:给 rubric(维度+分值+示例)让强模型打分,专治开放性任务。三个已实证的坑及对策:位置偏差(对比打分偏爱先出现的答案 → 随机顺序,两个顺序都打、不一致就送人工)、自我偏好(偏爱自己家族的模型 → 换裁判家族)、长度偏差(偏爱长答案 → rubric 明写「长度不加分」)。这些偏差的实证研究见 MT-Bench 论文。
[rubric 示例: 退款政策问答 的评分细则]
- 事实准确(0-4): 数字、政策条款与知识库一致? 任一处引错 → 直接 0
- 完整性(0-3): 用户问的三点是否都答到
- 合规性(0-3): 不承诺知识库之外的政策;越权承诺 → 整题 0
- 表达(0-2): 写明"长度不加分,冗长不扣分"——堵长度偏差
附样例: 2 分答案 / 4 分答案各一份,先给裁判看再打分(锚定分数感)
  • 测试集要版本化、分层:核心集(几百条,每次 CI 门禁必跑,单次成本控制在几块钱)/ 全量集(几千条,发版日跑)/ 专项集(bad case 回流区、新场景),和被测系统版本绑定,保证可复现。这就是 回归测试在 Agent 上的落地形态:改一个 prompt、换一个模型版本,跑分一对比,退化立刻拦在上线前。

4. 在线评估:AB 实验 + 用户反馈

  • 同期同流量随机分流的 AB 实验:新旧版本各接一部分真实流量,看任务完成率、点踩率、转人工率、CSAT;跑够样本量、确认统计显著性再下结论——「新版本点踩率 3.2% vs 老版本 3.5%,样本 500」这种差异多半是噪声。
  • 「任务解决」要埋点定义,不能拍脑袋:比如「用户 24 小时内未就同一问题重问、未转人工」记为解决。定义本身要和业务方对齐。
  • 用户点踩/修正行为是最值钱的评估信号:不花钱、来自真实分布,自动回流成新测试样本进专项集。上线后还要人工抽检一部分对话,用来校准裁判模型的可信度。

5. 评估闭环(加分点)

离线分数高只说明「在已知剧本上没退化」,只有闭环能把「未知剧本」源源不断变成已知——和演练剧本必须来自真实故障报告是同一个进化逻辑:

这条闭环里,离线回归是门禁(拦住 80% 的退化,成本极低),在线 AB 是终审(效果决策以它为准),反馈回流是进化引擎(测试集跟着真实分布走)。面试能把这三句讲全,基本就赢了大多数人。

面试官追问
Q:离线分数高、线上反馈差,怎么办?
人话:说明你的「演练剧本」和真实战场脱节了——剧本越跑越像表演,真实故障一来全露馅。类比:备份演练年年全绿,真切换那天手忙脚乱,因为剧本只覆盖「演练过的那种故障」,得拿真实故障报告去改剧本。技术:用线上真实 query 重采样测试集并定期轮换(注意脱敏);核心集保持稳定守住回归可比性,全量集定期换血对齐线上分布;重新校准指标权重,让它对齐线上目标(如转人工率、解决率)。原则不变:离线只负责防退化,效果好坏以在线 AB + 统计显著性为准。
Q:Agent 是多步的,中间对最后错、中间错最后对,分别怎么算分?
人话:拆开记账——过程分和结果分各记各的,别让「碰巧对」蒙混过关,也别让「绕路但到了」显得十全十美。类比:备份作业不能只看「作业状态=成功」,要翻各阶段日志:哪步重试了三次、校验返工了几回——状态绿不代表过程健康。技术:轨迹级逐步判(工具选择是否合理、参数是否正确——参数可以直接和执行结果比对,选择靠 judge 按 rubric 判)+ 结果级判最终答案,再统计有效步占比、无效调用数。发版门禁两个都卡:防止「结果对但成本翻倍」这种隐性退化悄悄混上线。
Q:开放性问题没有标准答案,怎么评?
人话:没有标准答案,但有验收标准——把「好不好」拆成一条条可打分的验收项。类比:容灾方案没有唯一正确写法,但 RTO 达标、演练通过、文档齐全这些验收项可以逐项勾——勾完就敢签字。技术:把开放任务拆成可校验子项(引用来源对不对、用户约束满足没、格式合规没),写进 rubric 交给 LLM-as-jjudge 按 0-4 分逐维打;同时人工抽检约 5% 校准裁判可信度,judge 与人的一致率 > 85% 才敢信;高价值、易分歧的题进人工金标集,长期沉淀。
Q:评估本身要花多少 LLM 成本?会不会比开发还贵?
人话:评估也烧真金白银,思路是「便宜方法覆盖大流量,贵的只抽查」——别用旗舰模型当日常门禁。类比:和备份校验一样:全量数据每次都人肉核验谁也养不起,所以自动校验和天天跑、深度核查按周期抽查。技术:三级打分本身就把 judge 留给 L2 解决不了的题;裁判选便宜但靠谱的模型(先用强裁判算一致率验证过再上岗);同题同答案的裁判结果做缓存不重复打分;核心集控制在几百条进 CI,单次回归几块钱量级;全量集按发版周期跑,不进日常门禁。
Q:测试集从哪来?要多少条才够?
人话:别一上来追求大而全,先手工攒百来条核心场景,再靠线上回流滚雪球——测试集是养出来的,不是一次性建出来的。类比:演练剧本不是拍脑袋一次写完,是每年复盘真实故障、一条条攒出来的;只出过书的「学院派剧本」打不了实战。技术:三个来源:人工构造核心场景(覆盖高频+高危路径)、线上真实 query 抽样脱敏、bad case 回流专项集。分层使用:核心集几百条进 CI 门禁,全量集几千条发版跑。够不够的检验标准是「区分度」:拿两个已知优劣的版本跑分,分不开就说明要么加题、要么加难度,而不是无脑堆量。
术语卡
任务成功率:完成用户目标的任务占比,核心效果指标——埋点定义「完成」本身就是设计活。
LLM-as-judge:用强模型按 rubric 给开放性回答打分,要防位置/自我/长度三类偏差。
Rubric:评分细则(维度+标准+示例),裁判可靠的前提——没有它,judge 就是凭感觉。
回归测试:发版前防退化的自动化验证,Agent 版即测试集跑分门禁。
幻觉率:答案中无依据内容占比,安全红线——指标,按业务风险定阈值。
CSAT:客户满意度评分,在线评估的用户侧指标之一。
统计显著性:AB 实验下结论的门槛——差异没过这条线,再多热闹也是噪声。
有效步占比:轨迹里真正推进任务的步数占比,衡量「绕路程度」的过程指标。
