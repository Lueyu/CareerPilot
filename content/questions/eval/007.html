Agent核心 · Q37

Agent怎么评估效果？

⭐⭐⭐ #Agent评估#效果评价 字节 / 阿里(高频)
30秒电梯稿

"评估分指标、离线、在线三层:第一,指标多维——不能只看'答对没',要看任务成功率、工具/参数准确率、平均步数、延迟、单任务成本、幻觉率;第二,离线评估——固定测试集 + 自动评分,规则/程序化校验/LLM-as-judge 三级打分,接进 CI 每次发版跑回归;第三,在线评估——AB 实验 + 用户反馈(点踩、转人工、修正行为),bad case 回流成新的测试样本。核心思想:离线防退化、在线看真相,两层必须结合。"

通俗类比

像教练评估运动员:不能只看"这场比赛赢没赢",要看训练成绩(离线测试集)、正式比赛成绩(线上 AB 实验)、比赛录像复盘(bad case 回流),还要综合体能、伤病、训练成本这些指标。只看训练成绩会选出"训练型选手"(应试过拟合),只看一两场比赛又太慢噪声大——所以两层都要,指标要全面。

详细拆解

1. 为什么 Agent 评估比普通模型难

  • Agent 是多步、有交互、有副作用的:中间一步工具调错了,最后答案可能"碰巧"对或错,单看最终答案会误判。
  • 任务开放:很多 Agent 任务(写方案、查信息、操作订单)没有唯一标准答案,需要人工或裁判模型来判。
  • 所以评估要过程 + 结果 + 成本一起看。

2. 指标体系(别只会说"准确率")

维度指标说明
效果任务成功率、工具选择准确率、参数准确率核心指标,离线可测
效率平均步数、工具调用次数、P50/P99 延迟步数多=绕路,费钱费时
成本单任务 token、折算金额老板最关心
安全幻觉率、越权操作数、拒答合理率红线指标

3. 离线评估:测试集 + 三级自动评分

  • L1 规则评分:关键词/精确匹配,快而便宜但死板。
  • L2 程序化校验:代码题跑单测、工具调用比 Schema、数学题验算——能程序化的尽量程序化,最可靠。
  • L3 LLM-as-judge:给 rubric(维度+分值+示例)让强模型打分。三个坑:位置偏差(对比时偏爱先出现的)、自我偏好(偏爱自己家族)、长度偏差(偏爱长答案)——对策:随机顺序、换裁判模型家族、rubric 明确"长度不加分"。
  • 测试集要版本化、分层(核心集/全量集/专项集),和被测系统版本绑定保证可复现。

4. 在线评估:AB 实验 + 用户反馈

  • 同期同流量随机分流,看解决率、点踩率、转人工率、CSAT,跑够样本量看统计显著性。
  • 用户点踩/修正行为是最值钱的评估信号,自动回流成新测试样本。

5. 评估闭环(加分点)

面试官追问
Q:离线分数高、线上反馈差,怎么办?
说明测试集分布和真实用户偏了。用线上真实 query 重采样测试集、定期轮换;离线指标只用来防退化,效果决策以在线为准。
Q:Agent 是多步的,中间对最后错怎么算分?
过程分和结果分分开:轨迹级(每步工具选择是否合理、参数是否对)+ 结果级(最终答案),再统计"有效步占比"看有多少调用是白干的。
Q:开放性问题没有标准答案,怎么评?
用 LLM-as-judge 按 rubric 打分 + 人工抽检 5% 校准 judge 可信度(judge 与人的一致率 > 85% 才敢信);或把开放任务拆成可校验子项(引用了正确来源吗、满足了用户要求吗)。
Q:评估本身要花多少 LLM 成本?
裁判用便宜但靠谱的模型 + 缓存裁判结果;核心集控制在几百条,一次回归几块钱以内。
术语卡
任务成功率:完成用户目标的任务占比,核心效果指标。
LLM-as-judge:用强模型按 rubric 给回答打分。
Rubric:评分细则(维度+标准+示例)。
回归测试:发版前防退化的自动化验证。
幻觉率:答案中无依据内容占比,安全红线。
CSAT:客户满意度评分。
