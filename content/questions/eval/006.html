Agent核心 · Q33

你做Prompt优化时，是如何判断优化后的Prompt在Agent推理链路中性能提升的？用什么指标来衡量？

⭐⭐⭐ #Prompt评估#性能指标 字节(真题)
先说人话:这题问的不是「你 Prompt 写得多漂亮」,而是「你说新版更好,凭什么是它好?」——考的是有没有评测体系。面试官爱考它,因为一句「我调了一版,感觉效果挺好」追问一句「好多少、怎么量的」就露馅:等于做备份从来不做恢复演练,全凭自信。
30秒电梯稿

"核心是先建评测集、再量化对比,而不是凭感觉——没有固定考卷,一切'我觉得变好了'都是盲改。我会分三层:① 离线评测——用带标准答案的回归测试集,比优化前后的准确率/任务成功率/工具调用正确率,配上 LLM-as-judge 打分和人工抽检;② 效率指标——token 消耗、延迟、重试次数(好的 Prompt 应该更省);③ 在线 AB 实验——小流量灰度看端到端指标和成本。结论看四个维度:质量、成本、延迟、稳定性——都涨才叫优化成功。"

通俗类比

改 Prompt,就是改 Agent 的「作业配置脚本」。你在备份领域改作业逻辑时肯定有肌肉记忆:改一行调度脚本,从来不敢直接上生产——必须拿同一批固定的样本数据,在测试环境把备份、恢复整条链路跑一遍,比对结果才敢发布。Prompt 也是同一个道理:它是 Agent 这套「备份软件」的配置,模型是执行引擎;引擎没换、配置换了,凭什么说新配置更好?必须出同一套考卷,让新旧两版各跑一遍,对账。

逐项映射你熟悉的场景:回归测试集 = 固定的恢复演练清单——每次改动拿同一批 case 重跑,专防「今天修好 A、明天改坏 B 都不知道」;golden answer = 演练的预期基线(RPO/RTO 达标线),自动对账全靠它;LLM-as-judge + 人工抽检 = 校验工具自动比对 + 季度人工抽查;AB 灰度 = 双活机房切 5% 流量先验证,而不是全量切换。哪里像:都是「自动先筛、人工终审、灰度上线、留回滚」的工程习惯,底层纪律完全一致。

哪里不像:备份校验是确定性比对——checksum 对就是对、恢复成功就是成功,二值、精确、可复现;LLM 评分是概率性的——同一个 judge 跑两遍可能给不同分,judge 自己还会偏心(偏爱长答案、偏自己的风格)。所以 LLM 评测必须多一层备份领域没有的工序:给 judge 定 rubric(评分细则)、用人工抽检给 judge 做「校准」。另外,备份作业成败是二值的,而开放生成的质量是多维连续的(相关性/完整性/语气),所以要把「好不好」拆成维度打分,而不是像看恢复日志那样只看通过/失败。

详细拆解

先看全景:一次合格的 Prompt 优化,是一场受控实验

一次 Prompt 优化 = 一场受控实验(离线部分):

  分层评测集(几十~几百条真实 case,带 golden answer/标准动作序列)
        │
        ├─ 旧 Prompt ─→ Agent 全链路跑一遍 ─→ 记录: 答案、动作序列、token、时延、重试
        └─ 新 Prompt ─→ Agent 全链路跑一遍 ─→ 记录: 同上
                          │
   控制变量: 同一考卷、同模型、同温度,唯一变量是 Prompt
                          │
        ┌─────────────────┼───────────────────┐
        ▼                 ▼                   ▼
  有标准答案→自动算分   开放题→LLM-as-judge    人工抽检 10~20%
  (准确率/成功率)      (rubric+成对比较)      (给 judge 校准偏差)
        └─────────────────┼───────────────────┘
                          ▼
              四维成绩单: 质量 | 成本 | 延迟 | 稳定性
                          │
              离线全绿 → 在线 5% 灰度 AB(1~2 周)+ 回滚开关

1. 第一步:没有评测集就别谈优化(最重要的意识)

  • Prompt 优化必须有固定的回归测试集(几十到几百条真实 case),否则每次改动都在"盲改"——今天修好 A 明天改坏 B 都不知道。这和备份系统升级后必须重跑回归测试是一个纪律:考卷固定,分数才可比。
  • 测试集要分层覆盖:正常场景 + 边界场景 + 对抗/刁钻场景;Agent 场景还要包含"该调用哪个工具"的判定。类比:演练清单不能全是"单文件恢复"的送分题,必须混着断点续传、源端变更、并发超限这些刁钻 case——只考简单题的分数没有意义。
  • 理想情况带标准答案(golden answer)或标准动作序列,才能自动算分——有了它,评测才能像恢复演练一样无人值守地批量跑、每天跑。

2. 离线指标(质量维度)

指标含义适用
准确率/正确率答案与标准答案匹配比例有明确对错的任务(数学/代码/抽取)
任务成功率端到端把任务做成的比例Agent 多步任务
工具调用正确率选对工具 + 参数正确 + 调用顺序对Agent 链路,最该盯的指标之一
格式合规率输出 JSON/结构化格式的合法率要求结构化输出的场景
LLM-as-judge 分强模型按 rubric 打分(相关性/完整性/流畅性)开放生成、难自动判分的任务

特别说工具调用正确率,Agent 链路里它的地位相当于备份链路的「作业配置正确性」,可以拆成三段分别统计,定位问题最快:

  • 选对工具:类比选对存储池/备份方式——Agent 该查数据库却去调了网页搜索,一步错全错;
  • 参数正确:类比挂对参数——工具选对了但时间范围、过滤条件传错,等于备份了错误的目录;
  • 调用顺序对:类比作业依赖顺序——先改数据再备份就备份了个寂寞;Agent 先写文件再读需求也是同类事故。

3. 效率与成本指标(很多人漏掉)

  • token 消耗:同样效果下,输入/输出 token 越少越省。好的 Prompt 常能砍掉冗余上下文——类比做了重删:内容一个字不少,占的空间小一半。
  • 延迟:TTFT / 总时长。加长 Prompt 可能提升质量却拖慢首字,要一起看——质量预算是有延迟代价的,就像备份窗口是有限的。
  • 重试/反思次数:Prompt 写得清晰,Agent 反复重试、走弯路的概率会下降——这是"链路性能"的直接体现,相当于备份作业的失败重跑率:一次成功和重试三次才成功,稳定性天差地别。
  • 成本:token × 单价,直接换算成钱——像「每 TB 备份成本」一样,是能汇报给管理层的语言。

4. 评判方法怎么落地

  • LLM-as-judge(经典方法见 MT-Bench 论文):用强模型 + 明确评分标准(rubric),给新旧两版回答打 1~5 分或对打分,批量跑。注意:judge 也是模型,会有偏见(偏长答案、偏自家的风格),要抽 10~20% 做人工复核——它只能当初筛,人工是终审。
  • 人工评估:抽样看质量,尤其看"模型判不出来、但用户会不爽"的细节(语气、格式、幻觉)。
  • AB 对比原则:同测试集、同模型、同温度,只改 Prompt 变量,否则归因不清——就是存储升级时「一次只动一个变量」的变更纪律。

5. 在线验证

  • 小流量灰度(如 5%)跑 1~2 周,对比任务成功率、用户满意度/留存、转人工率、成本——离线考卷只是预演,真实流量才是故障现场。
  • Prompt 优化上线也要留回滚开关,指标变差一键退回旧版——和新策略上线必须能切回旧版本是同一个容灾思维:能上就能退。

6. 汇总:一张可直接抄的成绩单模板

维度核心指标备份领域的对应物红线示例
质量准确率、任务成功率、工具调用正确率恢复演练通过率任何一项下跌即回退
成本token 消耗、每任务成本每 TB 备份成本涨幅超预算 20% 需评审
延迟TTFT、总时长备份窗口 / RTOTTFT 超过 SLA 即回退
稳定性重试次数、格式合规率、失败率作业失败重跑率重试率翻倍即回退

汇报口径建议:四个维度各给一个数字、新旧对比、加上一句结论——「质量 +x%,成本持平,延迟持平,稳定性 +y%,建议上线」。能拿出这张表的人,和只会说「感觉更好了」的人,在面试官眼里是两个物种。

面试官追问
Q:LLM-as-judge 不可靠怎么办?
人话:judge 自己也是个模型,会偷懒、偏心长答案、偏好自己的风格,所以别把它当真理,要当成一个「初级质检员」来管理。类比:自动校验工具再好用也有盲区——checksum 只能告诉你「比特没变」,回答不了「恢复出来的数据业务上对不对」;所以制度上必须有人工终审,并且定期反向校验工具本身。技术:四个手段:① 用明确 rubric(分维度、给分值锚点)代替"打几分";② 让 judge 做成对比较(A 比 B 好吗)而非独立打分,成对判断更稳定;③ 调低温度、多次采样取平均;④ 关键结论抽 10~20% 人工复核,量化 judge 和人工的一致率、持续校准。judge 是初筛,人是终审。
Q:优化后质量升了但 token 翻倍,算成功吗?
人话:要算账——质量是花钱买的,值不值看「单位成本的质量」,不看裸质量。类比:为了把 RTO 从 4 小时压到 30 分钟,把介质全换全闪——没有绝对对错:核心业务库值,归档库就不值;正确做法是分层,不是一刀切。技术:若成本是硬约束,这就叫「不划算」,继续做压缩(砍冗余示例、收紧上下文);更常见的解法是分级 Prompt:高价值/复杂请求用长版保质量,简单请求路由到精简版保成本。汇报时给「每任务成本」和「单位成本质量」两条曲线,让业务方在明确的价签下选档位。
Q:Agent 链路里,Prompt 效果怎么和"工具/流程改动"区分归因?
人话:一次只准动一个变量,不然涨了分不清功劳、出了锅甩不清责任。类比:存储升级同一个窗口既换了盘又升了固件,性能上去了说不清是谁的功劳,坏了也查不到根因——变更管理的基本功就是单变量推进。技术:评测时冻结工具集与流程,只切 Prompt,同一考卷跑出的差值就是 Prompt 的净贡献;之后再跑全链路 AB 看叠加效果。工程上给所有请求日志打上 prompt 版本号、工具版本号,事后能按版本拆出归因报表——这套玩法和你熟悉的「按变更单拆监控指标」完全同构。
Q:评测集分数涨了,会不会只是 Prompt「押中考题」?怎么防过拟合?
人话:这是最隐蔽的坑——Prompt 就是照着这几百条考题调出来的,考卷分数涨可能只是「刷题刷出来的」,真实流量一来现原形。类比:备份策略只在精心挑的样本数据上调优过,真实的增量数据、异常文件一来就露馅;演练考卷和真实故障必须分开准备。技术:① 评测集切成两部分:调优时只看训练份,验收汇报用从没参与调优的 holdout 留出集;② 按难度分桶看涨分分布,别只涨简单题;③ 线上 badcase 定期回流扩充评测集,考卷常换常新;④ 团队约定:只报 holdout 分数,刷训练集分数不算业绩。
术语卡
LLM-as-judge:让强模型按评分标准替人工批量打分;省人力但有偏见,必须配人工抽检校准。
Rubric:评分细则,把「好不好」拆成维度 + 分值锚点,让打分可复现——对应备份领域的验收标准。
回归测试集:固定不变的考卷,每次改动重跑一遍,专防「修好 A 改坏 B」。
AB 实验:把流量随机分组对比新旧版本,在线指标归因唯一可靠的手段。
Golden answer:评测集里人工标注的标准答案/标准动作序列,自动算分的对照基线。
Holdout 留出集:从不参与调优、只用来最终验收的题库——防 Prompt 对评测集「刷题」。
