Agent核心 · Q33

你做Prompt优化时，是如何判断优化后的Prompt在Agent推理链路中性能提升的？用什么指标来衡量？

⭐⭐⭐ #Prompt评估#性能指标 字节(真题)
30秒电梯稿

"核心是先建评测集、再量化对比,而不是凭感觉。我会分三层:① 离线评测——用带标准答案的回归测试集,比优化前后的准确率/任务成功率/工具调用正确率,配上 LLM-as-judge 打分和人工抽检;② 效率指标——token 消耗、延迟、重试次数(好的 Prompt 应该更省);③ 在线 AB 实验——小流量灰度看端到端指标和成本。结论看四个维度:质量、成本、延迟、稳定性,都涨才叫优化成功。"

通俗类比

改 Prompt 就像改一份发给员工的作业指导书:不能只凭"感觉新版本更好",要出同一套考卷让新老两版指导书下的员工都做一遍,对答案打分(回归测试集);光看分数不够,还要看谁更快交卷、谁用了更少纸(延迟、token 成本);个别拿不准的卷子请资深老师复核(LLM-as-judge + 人工抽检);最后小范围试运行一周再全面推广(AB 实验)。

详细拆解

1. 第一步:没有评测集就别谈优化(最重要的意识)

  • Prompt 优化必须有固定的回归测试集(几十到几百条真实 case),否则每次改动都在"盲改",今天修好 A 明天改坏 B 都不知道。
  • 测试集要分层覆盖:正常场景 + 边界场景 + 对抗/刁钻场景;Agent 场景还要包含"该调用哪个工具"的判定。
  • 理想情况带标准答案(golden answer)或标准动作序列,才能自动算分。

2. 离线指标(质量维度)

指标含义适用
准确率/正确率答案与标准答案匹配比例有明确对错的任务(数学/代码/抽取)
任务成功率端到端把任务做成的比例Agent 多步任务
工具调用正确率选对工具 + 参数正确 + 调用顺序对Agent 链路,最该盯的指标之一
格式合规率输出 JSON/结构化格式的合法率要求结构化输出的场景
LLM-as-judge 分强模型按 rubric 打分(相关性/完整性/流畅性)开放生成、难自动判分的任务

3. 效率与成本指标(很多人漏掉)

  • token 消耗:同样效果下,输入/输出 token 越少越省。好的 Prompt 常能砍掉冗余上下文。
  • 延迟:TTFT / 总时长。加长 Prompt 可能提升质量却拖慢首字,要一起看。
  • 重试/反思次数:Prompt 写得清晰,Agent 反复重试、走弯路的概率会下降——这是"链路性能"的直接体现。
  • 成本:token × 单价,直接换算成钱。

4. 评判方法怎么落地

  • LLM-as-judge:用强模型 + 明确评分标准(rubric),给新旧两版回答打 1~5 分或对打分,批量跑。注意:judge 也可能有偏见,要抽 10~20% 做人工复核。
  • 人工评估:抽样看质量,尤其看"模型判不出来、但用户会不爽"的细节(语气、格式、幻觉)。
  • AB 对比原则:同测试集、同模型、同温度,只改 Prompt 变量,否则归因不清。

5. 在线验证

  • 小流量灰度(如 5%)跑 1~2 周,对比任务成功率、用户满意度/留存、转人工率、成本。
  • Promp 优化上线也要留回滚开关,指标变差一键退回旧版。
面试官追问
Q:LLM-as-judge 不可靠怎么办?
四个手段:① 用明确 rubric(分维度、给锚点)而不是"打几分";② 让 judge 做成对比较(A 比 B 好吗)而非独立打分,成对判断更稳定;③ 调低温度、多次采样取平均;④ 关键结论人工抽检校准 judge 偏差。把 judge 当成"初筛",人工做"终审"。
Q:优化后质量升了但 token 翻倍,算成功吗?
看业务约束。若成本是硬指标,可以算"不划算",需要继续压缩;更常见的做法是分级:高价值/复杂请求用长 Prompt 保质量,简单请求用精简版保成本。优化的目标是"单位成本的质量",不是单看质量。
Q:Agent 链路里,Prompt 效果怎么和"工具/流程改动"区分归因?
控制变量:评测时固定工具与流程不变,只切 Prompt,对比差值就是 Prompt 的净贡献;再做全链路 AB 看叠加效果。日志里记录版本号,事后能按版本拆指标。
术语卡
Golden answer:评测集里人工标注的标准答案。
LLM-as-judge:用强模型按标准给生成结果打分。
Rubric:评分标准,分维度给锚点。
回归测试集:固定不变的评测集,防止改坏旧能力。
AB 实验:小流量灰度对比新老版本指标。
