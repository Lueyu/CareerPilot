评估讨论 · Q7

在评估一个 Agent 的任务完成情况时，除了最终结果的正确性，还有哪些过程指标是值得关注的？（例如：效率、成本、鲁棒性）

⭐⭐ #过程评估#效率指标 所有公司
先说人话:这题在问：验收一个 Agent，除了「任务做成了没」，还要盯哪些过程账——走了几步、烧了多少 token、出岔子能不能自己爬起来、事后查不查得清。面试官爱考它，是因为只会背「准确率」的人多半没真正上线过 Agent；能分维度、带数字、讲权衡的，才是背过线上锅的人。
30秒电梯稿

"只看『答对了没』远远不够，我按四类过程指标验收：效率——完成率之外看平均步数、总延迟、有没有绕路和重复调用；成本——单任务 token 和调用费用，Agent 是多步串行、上下文步步重传，步数一多成本平方级上涨；鲁棒性——工具报错能不能自恢复、重试收不收敛、换个问法成功率掉不掉；过程质量——工具选得对不对、轨迹留得全不全、有没有危险动作。核心观点：最终正确 ≠ 过程可靠——一个靠运气蒙对、一半时间在乱调工具的 Agent，上线必翻车。过程指标就是用来区分『真会』和『蒙对』的。"

通俗类比

用备份体系验收来想这道题：老板问"这套备份行不行"，你绝不会只答"昨晚那单作业绿了"。你会掏出整套过程账：恢复演练平均耗时多少、RTO 达不达标（效率）；备份窗口占多长、存储配额吃了多少（成本）；故意拔一块介质、断一条复制链路，补跑能不能自动成功（鲁棒性）；作业日志全不全、出了事能不能复盘（可观测）。Agent 评估一模一样：最终正确性就是那单"绿了的作业"，过程指标才是让你敢对外承诺 SLA 的整套验收——一次恢复成功只说明这次运气好，敢签字靠的是过程账。

再换个更扎心的对照：老预案脚本 vs 新值班工程师。哪里像：两者都不能只看一次结果——容灾演练从不做一次就签字，Agent 评估也要多次重放看方差，单次成功什么也证明不了。哪里不像：备份流程是写死的 playbook，第 100 次执行和第 1 次走的是同一条路；而 Agent 每一步都是模型现场重新决策，天生带随机性——今天 4 步干净利落，明天同一道题绕 30 步还可能失败。所以传统运维不太需要操心"这次路径对不对"，Agent 评估却必须把轨迹、扰动、稳定性当一等公民——这正是本题想考的认知：过程指标不是加分项，是这种「现场决策型系统」的体检必检项。

详细拆解

1. 为什么只看最终正确性不够（先立论）

  • LLM 是概率系统：同一个任务、同一份输入，这次对、下次可能就错。只跑一次看结果，等于拿一次容灾演练的手气当体系能力——单次成功 ≠ 稳定成功，评估至少要多次重放看方差。
  • 最终正确性是滞后且稀疏的信号：选错工具、重复调用、陷入循环，这些病根在过程里早就露头了。等结果错了才发现，就像备份作业显示"成功"、但日志里早就刷满了重试告警——等恢复失败那天才翻日志，太晚了。
  • 过程指标直接回答三个工程问题：能不能规模化（单任务成本、延迟）、能不能扛压（鲁棒性）、好不好排查（可观测性）。这三问和备份验收的"窗口/成本、演练成功率、日志完备度"一一对应。

先看一个直观例子——同一个任务，两个 Agent 的结果分完全一样，过程账天差地别：

任务：「查这个用户三个月的订单，算出应退金额」

Agent A（真会）                        Agent B（碰运气）
──────────────────────                ──────────────────────
1. 查用户(id)        ✓                1. 查用户(id)          ✗ 参数写错
2. 查订单(user)      ✓                2. 全表拉用户           ✗ 拖回 10 万行
3. 算退款(订单)       ✓                3. 查用户(id)           ← 重来一遍
4. 汇总答复          ✓                4. 查订单(user)         ✓
                                      5. 算退款(订单)         ✗ 公式用错
                                      6. 算退款(订单)         ✓ 第 3 次才对
                                      7. 汇总答复             ✓

结果分：A = B（都答对了）              过程账：步数 4 vs 7
                                      token 1.8k vs 9.4k
                                      总时长 12s vs 48s
                                      过程分：A 全程无废步，B 一路磕绊

只看结果分，这俩 Agent "一样好"；打开过程账，B 根本不该上线。这就是过程指标存在的意义。

2. 四类过程指标（可背下来的框架）

维度指标怎么测揭示的问题
效率任务完成率、平均步数、TTFT/总延迟、重复调用次数从执行轨迹统计走弯路、低效规划
成本单任务 token 数、调用费用、模型调用次数网关/计费日志聚合烧钱、过度调用
鲁棒性失败后自恢复率、扰动下成功率、重试是否收敛注入故障、扰动重放脆弱、不可靠
过程质量工具选择准确率、轨迹可审计性、是否有越权/误操作LLM-as-judge + 人工抽检选错工具、行为异常

注意"怎么测"这一列：四类指标几乎全都从执行轨迹里统计出来——轨迹本身就是过程评估的数据源，后面第 6 点会展开。

3. 效率类指标怎么落地

  • 任务完成率（task success rate）：离线评估集上跑 N 次（比如 100 次），统计最终达成目标的占比——报"完成率 85%，N=100"比报"做对了"专业得多，这和演练成功率要报次数是一个道理。注意要和"过程分"分开看——同样完成，10 步完成的和 30 步完成的是两个 Agent。
  • 步数（step count）：完成一个任务 Agent 平均走多少步、调用多少次工具（ReAct 这类「推理→行动」交替范式的 Agent，一步 = 一次模型决策 + 一次工具调用）。步数暴增通常意味着规划失效或工具不匹配。再配一个灵敏的细分指标——重复调用次数：同一工具、同一参数连续调两次以上，基本就是"陷入循环"的报警器，相当于作业日志里同一告警反复刷屏。
  • 延迟：拆成 TTFT（首动作时间，用户感知"它动起来了"）和总时长（用户感知"多久能用上结果"）。Agent 是多步串行，总延迟 ≈ Σ（每步 LLM 往返 1~3 秒 + 工具执行耗时），30 步轻松破 2 分钟——和备份窗口一样，窗口是各阶段串行加出来的总和，每省一步都是真金白银。排查时别只报平均值：把每步耗时拉出 P99 看，总延迟的天花板往往卡在一两个长尾请求般的慢步骤上（某个慢工具、某次超时），先治它，别笼统甩锅"模型慢"。

4. 成本类指标：token 消耗 = 上下文（每次调用都要重传历史）× 步数。关键在于 LLM 本身无状态——历史每一步都要整段重发，相当于"每次同步都发全量，而不是增量"：

第 k 步发给模型的内容 = 系统提示 + 前 k-1 步的完整轨迹 + 新观察

设每步新增轨迹约 800 token，一个 20 步的任务：
  第 1 步输入  ≈  0.8k token
  第 2 步输入  ≈  1.6k token
  第 k 步输入  ≈  0.8k × k
  总输入      ≈  0.8k × (1+2+…+20) = 0.8k × 210 ≈ 168k token
                                      ↑ 等差数列求和：步数对成本是平方级放大器

结论：一次 20 步的任务，token 开销 ≈ 170 次单轮问答。
所以砍步数、压上下文、加缓存，本质全是成本优化——不是锦上添花。
（即使推理引擎有 KV Cache 这类优化，按 token 计费时重传的历史照样计入账单；
 高 QPS 下单任务贵一块钱，月底账单就是事故。）

5. 鲁棒性类指标（最容易被忽略，但对备份/容灾背景的工程师最亲切）——本质就是把"拔线演练"搬到 Agent 上，手法来自混沌工程：

  • 扰动鲁棒性：把输入做轻微改写、同义替换、注入噪声，看完成率是否跳水。跳水说明它在"背题"而不是"理解题"——就像预案只覆盖"拔网线"这一种故障，换成断电就傻眼。
  • 故障恢复：故意让某次工具调用返回错误（超时、500、空结果），统计自恢复率——注入 1 次故障后仍能完成任务的比率。看它是换策略继续（换工具、改参数、向用户澄清），还是摆烂（原样硬重试、直接放弃）。
  • 收敛性：失败后的重试是越来越接近答案，还是越陷越深？有的 Agent 会把报错原文塞回上下文继续试，历史越滚越大、错误越积越多，活脱脱一场"重试风暴"。解法同分布式老三样：设最大步数熔断、对工具调用失败做指数退避，别让 Agent 无限打转。
  • 重放稳定性（鲁棒性的孪生指标）：同一任务跑 10 次，10 次全成 vs 7 成 3 败——就算平均完成率一样，方差大的那个也不可托付。

6. 过程质量与可观测：

  • 全量留轨迹：每一步的输入、模型决策与工具选择、调用参数、中间产出、耗时、token 消耗，一个不落。这就是 Agent 版的"作业日志 + 审计"——没留轨迹的 Agent 就是一张只写着"成功"两个字的作业单，你敢在它上面签 SLA 吗？
  • LLM-as-judge + 人工抽检：用强模型当裁判，给"工具选得对不对、这一步是否必要"打分，再人工抽检争议样本。这和备份验证的老思路同构：校验和自动打底 + 定期抽样做真实恢复演练——既不能全靠人，也不能全信机器。
  • 行为红线：Agent 手里握着真实工具权限（发邮件、写数据库、跑脚本），过程评估必须盯有没有越权/误操作——就像演练环境必须权限最小化、操作留审计。
加分表达：最终正确性是必要条件，过程指标才是上线决策条件——正确率高但步数/成本翻倍、鲁棒性差的 Agent，不该上线；过程干净利落、偶尔结果错的，往往调一版 Prompt 就能救回来，不必推倒重来。这跟"演练一次成功 ≠ 敢对外签 RTO 承诺"是同一张验收单。
面试官追问
Q:过程指标这么多，哪个最重要？为什么？
人话:没有唯一答案，按业务阶段排优先级——上线前先证明"能稳定做对"，铺量期抠"贵不贵"，运营期盯"出了事查不查得清"。类比:跟备份体系排优先级一个道理：新建系统先保"数据真能恢复"，业务上量后开始抠备份窗口和存储成本，稳定运行后最怕"恢复失败还查不出原因"。技术:上线前看任务完成率 + 鲁棒性（入场券，不稳定一切白搭）；规模化阶段看单任务成本和步数（决定毛利能不能覆盖）；持续运营看轨迹可观测性（决定故障定位时长和用户口碑）。一句话：正确性是入场券，成本决定赚不赚钱，鲁棒性决定会不会被用户骂下架。
Q:怎么区分 Agent 是"真会"还是"蒙对"的？
人话:别看单次结果，看它重放——同一道题做 10 遍，路径稳、工具选择一致的是真会，时对时错、路径乱飘的是蒙。类比:容灾演练从不做一次就签字：10 次演练 10 次成功、且每次走同一套预案，才敢签 RTO；如果 10 次里 6 次靠值班同学现场手工救场，这预案就不可签——哪怕最后都显示"恢复成功"。技术:① 看多次重放的成功率和路径相似度，方差大即不可复现；② 过程分与结果分交叉验证——结果对但轨迹乱（重复调用、绕路、废步多），大概率碰运气；③ 扰动测试——同一任务换说法、加干扰条件再跑，真会的依然对，蒙的立刻现形。
Q:这些过程指标能全自动测吗？还要不要人？
人话:八成指标能全自动，剩下一两成必须留人，因为裁判自己也会犯错。类比:备份验证的老思路：校验和自动打底，再定期抽样做真实恢复演练——既不能每次全量演练，也不能只信校验和；LLM 裁判就是那个"校验和"，快、便宜、但会漏。技术:完成率、步数、延迟、token 成本从轨迹直接统计，零人工；工具选择是否合理先用 LLM-as-judge 粗筛；"这步有没有必要、轨迹是否合规"这类开放判断，judge 的评分会漂，必须人工抽检争议样本（约 5%~10%）。原则：自动化打底 + 人工仲裁，并且 judge 本身要定期用人工标注做校准。
Q:成本和成功率打架了怎么办？比如砍步数、换小模型省钱，任务会不会跟着砍坏？
人话:经常打架，正确姿势是拿数据画权衡曲线，不拍脑袋二选一。类比:备份窗口 vs RPO 的经典权衡：全量备份恢复链短但窗口爆，增量省窗口但恢复链长——真正的解法是重删、合成备份这类技术把两个指标一起改善，而不是永远在两个烂选项里挑一个。技术:把每个版本（步数上限、检索 top-k、模型分级路由）跑出（单任务成本，完成率）坐标，画帕累托前沿，只保留不被支配的方案；给成本设硬护栏（单任务 token 超限即熔断告警），完成率掉点超阈值自动回滚。优化的目标不是在前沿上赌，而是靠上下文压缩、缓存把整条前沿往前推——让"便宜"和"准"不再互斥。
术语卡
任务完成率:评估集上最终达成目标的比例，只看结果不看过程——相当于"演练成功次数 / 总次数"，报的时候要带 N。
轨迹 Trace:Agent 版的分布式追踪——每一步的输入/工具/产出/耗时全记录，过程评估的唯一数据源。
步数 Step Count:完成任务走的步数/工具调用次数，过程效率的第一信号——对延迟是线性放大，对成本是平方级放大。
鲁棒性 Robustness:面对扰动、噪声、故障时表现不跳水的程度——Agent 版"拔了线还能不能切换成功"。
LLM-as-judge:用强模型当裁判给输出/过程打分，快但会漂，必须配人工抽检做校准。
单任务成本:一次任务的总 token/费用——上下文每步重传，所以步数越多越贵，规模化前的硬指标。
混沌工程:主动往系统注入故障看它挂不挂，Agent 鲁棒性测试的思想源头。
帕累托前沿:多个指标互相牵制时，标出所有"不被全面碾压"的方案，让权衡看得见、可决策。
