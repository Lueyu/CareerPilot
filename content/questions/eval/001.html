系统设计 · Q9

设计一个 Agent 评估平台

⭐⭐⭐⭐ #评估#平台#Agent
先说人话:这题问的是「你凭什么说你的 Agent 这次发版变好了而不是变坏了」——考的是评估体系怎么搭。面试官爱问它,是因为答「跑跑看效果、问问用户」的人一抓一大把,一张口就暴露没搭过体系:指标只有一维、评分全靠人肉、离线在线不分、评估不进 CI。答好这题,展示的不是调参手感,是平台思维。
30秒电梯稿

"评估分离线和在线两层:离线是固定测试集+自动评分(规则/程序化校验/LLM-as-judge 三级打分),在线是 AB 实验和用户反馈。平台核心模块:任务与数据集管理(版本化)、多维度指标(任务成功率、工具选择准确率、平均步数、延迟、单任务成本)、对比实验(消融分析)、可视化报告。关键设计是把评估接进 CI,每次发版跑回归,分数掉了自动拦截合并——让 Agent 团队像工程团队一样,凭数据发版而不是凭感觉发版。"

通俗类比

整体像给 Agent 办一套学校考试体系:模拟考(离线评估)——固定卷子、自动改卷,天天能考、便宜、可重复,但模拟考高分不代表实战能打;高考(线上 AB 实验)——真实用户当考官,成绩作数,但考试昂贵、变量不可控、不能天天考;老师抽查(人工评估)——机器改卷不放心,抽 5% 人工复核,顺便校验「机器阅卷员」本身靠不靠谱。只看模拟考容易养出「应试选手」(测试集刷得飞起,真实问题一塌糊涂),只看高考又太慢太贵——所以要两层结合,互相校准、互相兜底。

换成你熟悉的世界:备份系统的「演练 vs 真实故障」。离线评估 = 定期恢复演练:剧本固定、环境可控、每天可跑、出量化报告,但它测的是「按剧本演时行不行」;在线评估 = 真实故障:不挑时间、不讲剧本,才是 RTO 的最终裁决。哪里像:都强调固定剧本、可重复、指标可量化,都是「平时练兵、战时见真章」的双层结构——离线分数用于防退化,效果裁决看线上,这和你汇报演练成绩与真实 RTO 是同一套话语体系。哪里不像:恢复演练的剧本基本能覆盖真实故障的主要路径,所以演练成绩和实战表现强相关;而 Agent 的离线测试集很难逼近真实用户问题的分布,离线分天然容易「虚高」——这正是这题必须专门设计「用线上真实 query 轮换测试集」「judge 校准」这些兜底机制的原因,也是面试官最爱追问的地方。

详细拆解

第 0 步:先把平台骨架画出来

整体数据流(评估平台四大件:考题仓 + 跑分引擎 + 评分引擎 + 报告/门禁):

  被测对象(Prompt/模型/工具配置,带版本号)        数据集仓库(版本化)
            │                                            │
            └──────────────────┬─────────────────────────┘
                               ▼
                        评估调度器 ── 发版跑核心集 / 每周跑全量集 / bug修复后跑专项集
                               ▼
              三级自动评分(L1 规则 → L2 程序化 → L3 LLM-as-judge)+ 5% 人工抽检
                               ▼
              指标聚合 → 与基线对比 → 可视化报告 + CI 门禁(掉分阻断合并)
                               ▲
              线上 bad case / 用户点踩 ── 标注后回流数据集(形成闭环)

1. 任务定义与管理

  • 评估单元 = 数据集(输入 + 期望输出:参考答案/期望的工具调用轨迹/校验程序)+ 评分配置。期望输出给到什么程度,决定了能用哪一级评分:只给参考答案,最多用到 judge;给了校验程序,就能用最可靠的程序化判定——所以出题时多花一分钟写校验程序,评估就少花一辈子冤枉钱。
  • 版本化:数据集打版本号,和被测系统版本(Prompt/模型/配置)绑定,保证任何历史分数可复现。这和备份要支持「任意时间点恢复」是同一个道理:半年后有人质疑「当时为什么这么发版」,你要能一比一复现当时的考卷和考生配置。
  • 分层集:核心集(每次发版必跑,~100 条)+ 全量集(每周跑)+ 专项集(bug 修复后针对性验证)。这是备份的分级保护策略思维——每日增量、每周全量、关键变更前加强校验,不可能每条 PR 都跑全量集,成本撑不住。

2. 多维度指标(别只会说"准确率")

为什么一个「准确率」盖不住?因为 Agent 的失败姿势五花八门:有的办砸了还理直气壮(幻觉),有的办成了但绕了 20 步(费时费钱),有的把能干的事直接拒答了。这和监控系统不能只看一个 CPU 利用率是同一个道理——多维面板才能定位「哪种病」。

维度指标说明
效果任务成功率、工具选择准确率、参数准确率核心,离线可测
效率平均步数、工具调用次数、P50/P99 延迟步数多=绕路,费钱费时
成本单任务 token 消耗、折算金额老板最关心
安全幻觉率、越权操作数、拒答合理率红线指标

汇报口径建议:每个维度定一个主指标(如任务成功率),其余做护栏指标(只许持平不许恶化)——「成功率 +4% 但成本翻倍」这种事,护栏指标会在报告里当场拦住。

3. 自动评分三级火箭

一套数据集里客观题、程序题、主观题混着,没有一种评分方法通吃,所以按「可靠性优先、成本递增」分级:

每条样本的评分流水线(先便宜后贵,逐级兜底):
  L1 规则匹配(毫秒级,≈0 成本)──判得动──→ 出分
        └─ 判不了 → L2 程序化校验(跑单测/比 Schema/验算,秒级)──→ 出分
                └─ 判不了(主观题)→ L3 LLM-as-judge(按 rubric 打分)→ 出分
                        └─ 再抽 5% 人工复核,校准 judge 与人的一致率(>85% 才算可信)
  • L1 规则评分:精确匹配、关键词包含 —— 快、便宜,但死板,答案换个同义词就误判;只适合封闭类任务(分类、选择题、固定命令词)。
  • L2 程序化校验:代码类任务直接跑单测;工具调用直接比 Schema(该调哪个工具、参数对不对,结构化数据逐一比对即可);数学题验算 —— 最可靠,能程序化的尽量程序化。因为程序的判断是确定性的、免费的、可解释的——校验能自动就绝不用人眼,和备份校验的思维一模一样。
  • L3 LLM-as-judge:给评分 rubric(维度+分值+正反例),让强模型打分。要注意三个坑:位置偏差(对比时偏好先出现的,系统性研究见这篇论文)、自我偏好(偏爱自己风格的模型)、长度偏差(偏爱长答案)—— 对策:随机顺序、换不同家族模型当裁判、rubric 里明确"长度不加分"、用正反例锚定分数段防「给熟人打高分」。
  • 人工抽检 5% 校准 judge 的可信度(judge 和人的一致率 > 85% 才敢信)——这是 L3 能否商用的前置条件,跳过这步的 judge 就是玄学。

4. 对比实验

  • 支持 A/B 配置(模型、Prompt、检索参数、架构)同数据集跑分,出对比表。单独一个分数没有意义,分数永远在对比中产生:和上一版比、和关掉某模块的自己比。
  • 消融实验:逐个关掉模块(rerank / memory / 多轮改写),看指标掉多少,证明每个组件的价值——每个组件都要用消融证明自己「没在吃空饷」,不然架构就是玄学堆料。
同一数据集、四个配置的对比报告(示例数据):
配置                 成功率   平均步数   单任务成本   幻觉率
v1 基线               72%      8.2      ¥0.31       4.1%
v2 +rerank            76%      7.5      ¥0.38       3.2%   ← +4 分,多花 7 分钱,值不值?
v3 +rerank+memory    77%      6.1      ¥0.44       3.0%   ← memory 只 +1 分,要砍吗?
v4 全开+换小模型      74%      6.8      ¥0.21       3.5%   ← 成本砍半、掉 2 分,业务能接受吗?

5. 工程化:接进 CI/CD

  • Prompt 或配置变更 → PR 触发跑核心集 → 分数对比基线,下降超阈值(如成功率 -2%)自动阻断合并。
  • 失败案例自动聚类(按错误类型),展示典型 bad case 全轨迹回放——和备份失败作业按错误码聚类定位是同一个习惯。
一次 PR 的评估门禁流程:
开发者提 PR(改 Prompt/换模型/调检索参数)
   │
   ▼ 自动触发
跑核心集(~100 条,每条重复 3 次取均值──因为 LLM 有随机性,单次跑分不可信)
   │
   ▼ 与基线对比
任务成功率 ≥ 基线-2% ?──是──→ 允许合并
        │否
        ▼
  自动阻断合并 + 失败样本按错误类型聚类 + 全轨迹回放,定位到步

两个工程细节别漏:① LLM 的 temperature > 0 意味着同一考卷跑一次 74%、再跑一次 71% 都是正常波动,所以门禁阈值要给随机性留余量(这就是 -2% 而不是 -0.2% 的原因),重要对比跑 3 次取均值;② 门禁只看核心集,别把全量集塞进 PR 流水线,开发会等死。

6. 在线评估:线上小流量 A/B 测试(详见第四部分 A/B 测试题),看的是业务指标(任务完成率、用户修正率、点踩率);用户点踩/改写重问/人工接管等负反馈行为回流为新的评估样本 —— bad case 是最值钱的评估数据来源,因为它天然是「真实分布 + 真实失败」的现成考砸真题。回流后人工标注(错在哪一步、正确该是什么),先进专项集,能稳定复现的升入核心集——评估数据集是活资产,不是一次性题库。

面试官追问
Q:离线分数高、线上反馈差,怎么办?
人话:卷子出偏了——测试集和真实用户的问题长得不像,离线分成了「自嗨分」。类比:恢复演练一直在理想机房里做,真出事才发现真实故障的姿势和剧本完全对不上,演练满分毫无安慰效果。技术:① 用线上真实 query 定期重采样、轮换测试集,对抗分布漂移;② 持续监控「离线分 vs 在线指标」的相关性,相关性掉了就是测试集过期的报警;③ 重新定位离线指标的职责:只用于回归防退化(保证没变坏),效果决策一律以在线 AB 为准。
Q:Agent 是多步的,中间对了最后错了怎么算分?
人话:过程分和结果分分开设账,别一锅端,否则永远定位不了问题出在第几步。类比:备份作业链的多段任务——快照成功、上传成功、索引校验失败,作业整体算失败,但每段状态单独落盘,你才知道该修哪段。技术:轨迹级(每步工具选择/参数是否合理,按 rubric 逐步判)+ 结果级(最终答案用 L2/judge 判)分开统计;再加「有效步占比」指标(多少调用是白干的、有没有死循环);由此聚出两类高价值坏例——「过程对结果错」(多半是收尾失手)和「过程错结果对」(多半是侥幸通过),前者上线会翻车,后者更危险,都要单独立项修。
Q:评估本身要花多少 LLM 成本?
人话:三招:考卷控规模、裁判用便宜模型、判过的不再判。类比:备份的分级存储思维——不是所有数据都配黄金双副本,核心数据每天校验,全量每周扫一次。技术:① 优先 L2 程序化,零 token 成本,能覆盖的绝对不走 judge;② judge 用中等价位模型 + few-shot 示例校准到与强 judge 结论一致,不必非用旗舰模型;③ 裁判结果缓存,同一 (题目, 答案) 组合不重复判;④ 核心集控制在几百条、每条 3 次重复,一次回归的成本控制在几块钱量级;全量集才配强模型裁判,每周跑一次,别进 PR 流水线。
Q:团队天天盯着测试集分数改 Prompt,分数越调越高却越来越虚,怎么办?
人话:学生把卷子背下来了,再用这张卷子给他打分就是自欺欺人——评估集被「应试」了。类比:容灾演练提前把剧本塞给值班团队,演练成绩虚高,可真实故障不按剧本走。技术:① 留一块私有的 holdout 集,不进日常回归、不展示逐条明细,只在关键节点评估用;② 定期轮换、用新题替换旧题,线上 bad case 优先补进测试集;③ 监控离线-在线相关性漂移——「离线一直涨、在线不涨」就是过拟合测试集最典型的信号;④ 评估集的管理权限和开发团队分离,和代码评审的权责分离是同一个道理。
术语卡
LLM-as-judge:用强模型代替人工按 rubric 批卷——便宜可扩展,但有位置/长度偏差,要用人工一致率(>85%)校准后才敢信。
Rubric:评分细则(维度+分值+正反例),给 judge 的「改卷标准」——写得越具体,打分越稳。
消融实验:逐个关掉模块看指标掉多少,用来证明每个组件「没在吃空饷」。
回归测试:发版前用固定用例集自动验证「没改坏旧功能」;Agent 版把它升级成「没改坏旧能力」。
黄金集:精心标注、每次发版必跑的核心考题集——测试集里的「特级保护对象」,只进不出、逐版对比。
轨迹评估:不只判最终答案,还逐步判工具选择和参数是否合理——多步 Agent 的「过程分」,定位问题在第几步全靠它。
