系统设计 · Q9

设计一个 Agent 评估平台

⭐⭐⭐⭐ #评估#平台#Agent
30秒电梯稿

"评估分离线和在线两层:离线是固定测试集+自动评分(规则/程序化校验/LLM-as-judge 三级打分),在线是 AB 实验和用户反馈。平台核心模块:任务与数据集管理(版本化)、多维度指标(任务成功率、工具选择准确率、平均步数、延迟、单任务成本)、对比实验(消融分析)、可视化报告。关键设计是把评估接进 CI,每次发版跑回归,分数掉了自动拦截。"

通俗类比

就是给 Agent 办一套学校考试体系:模拟考(离线评估)——固定卷子、自动改卷,天天能考,但考好不代表实战;高考(线上 AB 实验)——真实用户是考官,成绩作数;老师抽查(人工评估)——机器改卷不放心,抽一部分人工复核。只看模拟考容易"应试选手",只看高考又太慢——所以要两层结合。

详细拆解

1. 任务定义与管理

  • 评估单元 = 数据集(输入 + 期望输出:参考答案/期望的工具调用轨迹/校验程序)+ 评分配置。
  • 版本化:数据集打版本号,和被测系统版本(Prompt/模型/配置)绑定,保证任何历史分数可复现。
  • 分层集:核心集(每次发版必跑,~100 条)+ 全量集(每周跑)+ 专项集(bug 修复后针对性验证)。

2. 多维度指标(别只会说"准确率")

维度指标说明
效果任务成功率、工具选择准确率、参数准确率核心,离线可测
效率平均步数、工具调用次数、P50/P99 延迟步数多=绕路,费钱费时
成本单任务 token 消耗、折算金额老板最关心
安全幻觉率、越权操作数、拒答合理率红线指标

3. 自动评分三级火箭

  • L1 规则评分:精确匹配、关键词包含 —— 快、便宜,但死板。
  • L2 程序化校验:代码类任务直接跑单测;工具调用直接比 Schema;数学题验算 —— 最可靠,能程序化的尽量程序化。
  • L3 LLM-as-judge:给评分 rubric(维度+分值+例子),让强模型打分。要注意三个坑:位置偏差(对比时偏好先出现的)、自我偏好(偏爱自己风格的模型)、长度偏差(偏爱长答案)—— 对策:随机顺序、换不同家族模型当裁判、rubric 里明确"长度不加分"。
  • 人工抽检 5% 校准 judge 的可信度(judge 和人的一致率 > 85% 才敢信)。

4. 对比实验

  • 支持 A/B 配置(模型、Prompt、检索参数、架构)同数据集跑分,出对比表。
  • 消融实验:逐个关掉模块(rerank / memory / 多轮改写),看指标掉多少,证明每个组件的价值。

5. 工程化:接进 CI/CD

  • Prompt 或配置变更 → PR 触发跑核心集 → 分数对比基线,下降超阈值(如成功率 -2%)自动阻断合并。
  • 失败案例自动聚类(按错误类型),展示典型 bad case 全轨迹回放。

6. 在线评估:线上小流量 AB(详见第四部分 A/B 测试题)、用户点踩/修正行为回流为新的评估样本 —— bad case 是最值钱的评估数据来源。

面试官追问
Q:离线分数高、线上反馈差,怎么办?
说明测试集分布偏了(和真实用户问题不像)。用线上真实 query 重采样测试集,定期轮换;离线指标只用于回归防退化,效果决策以在线为准。
Q:Agent 是多步的,中间对了最后错了怎么算分?
过程分+结果分分开统计:轨迹级(工具选择是否合理,逐步判)+ 结果级(最终答案),还要看"有效步占比"(多少调用是白干的)。
Q:评估本身要花多少 LLM 成本?
judge 用便宜但靠谱的模型+缓存裁判结果;核心集控制在几百条,一次回归几块钱以内。
术语卡
LLM-as-judge:用强模型按 rubric 打分。
消融实验:关掉某组件看指标变化。
回归测试:发版前防退化的自动化验证。
Rubric:评分细则(维度+标准+示例)。
