Agent核心 · Q51

问Agent的工具tool的设计，是否是workflow形式？

⭐⭐ #工具设计#Workflow 字节（真题）
30秒电梯稿

"我分两层回答：工具怎么设计、流程怎么组织。工具设计上，每个工具是一份 JSON Schema——名称、一句话描述（重点写清什么时候该用/不该用）、参数（类型/必填/枚举）、返回值结构；粒度遵循『一次干成一件事』，读/写分离，写操作做成幂等 + 两段式（预览 → 执行）。流程组织上不是非此即彼，而是一条光谱：一端是 Workflow（确定性编排）——步骤固定、代码编排、LLM 只填空；另一端是自主 Agent——LLM 自由决定调哪个工具、调几次。我的做法：能确定的部分用 workflow 固化成图，需要模型判断的部分才交给 Agent 自主选工具——确定性优先，不确定性交给模型。"

通俗类比

像做菜：Workflow 是标准化菜谱——先放油、再放菜、炒三分钟，步骤写死，照着做就行（可预期、稳定）；自主 Agent 是让厨师自由发挥——看冰箱里有什么、客人什么口味，自己决定切什么、炒什么（灵活、但可能翻车）。工具就是厨房里的设备——锅、刀、烤箱，每个都要标清"能干嘛、怎么用、什么时候别用"，标得越清楚，厨师越不容易用错。聪明做法是把熟练的菜写成菜谱（workflow），把新菜让厨师即兴发挥（Agent），两者混搭。

详细拆解

1. 工具怎么设计（Tool 设计五原则）

  • Schema 清晰：name / description / parameters（JSON Schema）/ 返回值结构。description 里一定要写"什么时候该用、什么时候不该用"——这直接决定模型选对工具的概率。
  • 粒度适中：一次一个原子动作（"查订单"而非"查订单顺便改地址"）。太粗（瑞士军刀式巨型工具）参数多、模型易选错/漏参；太细一次任务调用几十次，延迟和 token 暴涨。
  • 读/写分离：读操作无副作用、可安全重试；写操作（下单、退款、改配置）要有幂等键 + 两段式（先预览、再确认/审批执行），并做权限最小化。
  • 返回值精简：把底层返回的大 JSON 裁剪成模型真正需要的字段 + 明确的错误码，省 token、少幻觉。
  • 错误可回喂：工具报错要结构化返回给模型，让 Agent 能"看着错误自我纠正"（换参数、换工具、或承认失败）。

2. 是 workflow 形式吗？——一条光谱，不是二选一

维度Workflow（确定性编排）自主 Agent（工具自主选择）
步骤固定 DAG/状态机，代码定死LLM 在 ReAct 循环里自主决定
谁做决策代码（条件分支）LLM（工具路由）
可控/可测强（可预期、可回归）弱（不确定、可能死循环）
成本低高（多步多次 LLM 调用）
适用流程明确的标准化业务开放、长尾、路径不固定的任务

3. 生产主流是"中间态"：Agent + 护栏

  • 用状态机/LangGraph把合法流程固化，但节点内部可以是"自主 Agent 子图"，让模型在受限范围内选工具。
  • 护栏四件套：工具白名单/路由、最大步数 + token 预算、输出校验、失败转人工——把 Agent 的"自由"关进确定性的笼子。

4. 决策标准（什么时候用哪个）

  • 步骤确定、工具少且固定、容错要求高 → Workflow，别为"看起来高级"硬上 Agent。
  • 路径不固定、工具多且动态、需要模型临场判断 → Agent，但要配护栏。
  • 落地策略：高频主流程先用 workflow 固化（约 80%），开放长尾问题再交给 Agent 承接，共用同一套原子工具层，兜底转人工。
面试官追问
Q:工具切太细会有什么问题？太粗呢？
太细：一次任务要连续调几十次，延迟和 token 线性累积，中间结果还会把上下文塞满、淹没关键信息。太粗（巨型工具）：参数太多，模型容易选错工具或漏传参数，且一个工具承担多个副作用、难做权限隔离。平衡点是"一次一个原子动作"，复杂动作靠编排（workflow 串起来）或 Agent 多次调用组合实现。
Q:写操作工具怎么做才安全？
三件套：① 幂等键——同一操作重复执行无副作用（防重试/重派导致重复下单）；② 两段式——先返回 preview（将要做什么、影响什么），用户或人工确认后再 execute；③ 权限最小化——敏感接口只给"起草"权限，真正执行走审批。目标是让 Agent 永远只能"提议"，不能"直接越权执行"。
Q:同一个工具既在 workflow 里又在 Agent 里用，有冲突吗？
不冲突，这是推荐做法：工具是"原子能力"，workflow 是"固定编排"，Agent 是"自主编排"，两者共享同一套工具层。区别在于——对 workflow 来说工具描述只是文档，对 Agent 来说 description 是模型选对工具的关键信号，所以工具的 description 要按"服务 Agent 的视角"写清楚（何时用/不用、参数含义），这样两个场景都能吃。
Q:怎么判断一个需求该用 workflow 还是 Agent？
看三点：① 步骤确定性——流程固定选 workflow，路径发散选 Agent；② 工具集合大小——工具少且固定选 workflow，工具多且动态选 Agent；③ 容错/成本要求——强容错低成本选 workflow。经验法则是"能用 workflow 别上 Agent"，Agent 只兜开放长尾，最后用端到端成功率做 AB 验证，别凭感觉。
术语卡
Tool Schema:工具的名称/描述/参数/返回值的结构化定义。
ReAct:推理 + 行动的循环，Agent 自主选工具的范式。
Workflow:步骤固定的确定性编排，代码主导。
幂等:同一操作执行多次效果和一次相同。
两段式执行:先预览再执行，防误操作的写保护。
LangGraph:能把 workflow 与 Agent 节点混合编排的图引擎。
