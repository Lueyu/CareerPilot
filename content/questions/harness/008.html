Agent核心 · Q5

Tool Use 是扩展 Agent 能力的有效途径。请解释 LLM 是如何学会调用外部 API 或工具的？（可以从 Function Calling 的角度解释）

⭐⭐⭐ #Agent#ToolUse#FunctionCalling 所有公司（高频）
先说人话:LLM 本质是个「接话机器」，没手、没网、没 shell，凭什么能替你查天气、查订单、触发备份？这题问的就是这条「指挥链」怎么搭。面试官爱考，是因为一句「模型自己执行了 API」就能筛掉一批人——干过的人都知道：模型只出工单，干活的一直是你的代码；答不出这层，暴露的就是没亲手写过 Agent 执行循环。
30秒电梯稿

"关键认知：模型并不真正「执行」工具，它只「生成调用意图」——这句话是整道题的题眼。Function Calling 的流程：把每个工具用 JSON Schema 描述(名称、作用、参数类型)随请求传给模型 → 模型判断「要不要调、调哪个、参数填什么」，输出一个结构化的 tool_call → 由程序解析校验后执行真实函数/API，并把结果作为新消息回填 → 模型基于结果继续生成，可能再来一轮，直到给出最终回答。能力来自训练阶段的 instruction tuning(指令微调：教它何时调用、格式如何)，推理阶段靠 schema + 执行循环保证稳定。相比 ReAct 的纯文本约定，FC 结构化、可校验、支持并行多工具，是生产首选。"

通俗类比

Function Calling(用备份系统里「中央调度器 + 执行代理」的分工想):把 LLM 想成那个只下工单、从不亲手碰存储的中央调度器。作业模板库就是工具的 JSON Schema(每张模板写死作业名、必填字段、取值范围)；它读一眼需求(用户问题)，挑一张合适的模板，把卷名、时间窗填进去——开出的那张作业单就是 tool_call;真正挂卷、读写数据的是各节点的执行代理，也就是你的程序 + 真实 API;执行完的回执(工具结果)交回调度器，它看一眼：要追加作业就再开单，信息够了就出排障报告(最终回答)。整个 Function Calling,就是这套「调度 → 执行 → 回执 → 再决策」循环的 LLM 版。教科书里更常见的讲法是餐厅点菜：顾客(模型)照菜单(schema)点菜但不进后厨，服务员(程序)下单传菜，顾客尝一口再决定加不加菜——同一套循环，换个行业皮肤而已。

哪里像:① 调度器只决策不执行，LLM 也只生成 tool_call、从不真正调 API——这是最重要的对应关系；② 作业模板必须预先注册、字段写死，工具 schema 也是提前声明、随请求传入，模型填不出 schema 之外的字段；③ 拿到回执决定下一步(备份失败 → 追加一张「查日志」的作业单)，对应模型看到工具结果后决定是否再调用；④ 模板库里没有的作业类型，调度器想下也下不出来——模型同样只能在 tools 列表里选。哪里不像:① 传统调度器的决策是人写死的规则/状态机，永远确定；LLM 的决策是从海量样本学出来的统计模式，同一个问题两次填单可能不一样，所以执行前必须校验;② 传统系统里模板只是注册信息，FC 里 schema 的 description 会直接拼进模型输入——说明书写得糊，选错率立刻上升,「文档质量影响系统行为」在这里是字面成立的；③ 传统调度器不会越权，LLM 却可能幻觉出模板里没有的参数值(编一个不存在的卷名)，所以要白名单校验 + 最小权限。

详细拆解

1. 本质澄清：模型是「出单的」，不是「干活的」

先把最容易答错的一点钉死：LLM 无法直接执行任何东西，它只会预测 token。给它一段对话，它续写一段文本，仅此而已——没有网络权限、没有 shell、没有文件系统，就像调度器没有手。所谓"调用工具"，实际是模型生成一段符合约定的调用指令(JSON)，由应用层解析后去执行真实函数/API，再把执行结果作为新消息回填。整条链路里，模型的位置永远是「出单」，「干活」的始终是你的代码。

  • 所以"学会调用工具" = 学会两件事：① 什么时候该调、调哪个(意图判断);② 参数怎么填、格式对不对(结构化生成)。这两件事都是训练阶段练出来的肌肉记忆，不是推理时的魔法。
  • 反过来，模型不会做的事也记牢：它不会执行任何代码、不会自己上网、调不到你没在 tools 里声明的工具(幻觉除外，见追问)。
常见误解实际机制
「模型自己执行了 API」模型只生成 tool_call(一张 JSON 工单)，解析和执行都发生在你的程序里
「开了 FC 模型就联网了」推理过程没有任何网络/磁盘权限，外部信息只能由你执行后回填
「每接一个新工具都要重新训练」FC 是通用能力，接新工具只需写一份 schema，零训练零微调
「FC 是个开关，一开就稳」稳定性来自 instruction tuning 的功底，弱模型开了 FC 也照样频繁吐坏 JSON

2. 三步循环：出单 → 干活 → 回执，循环往复

流程上记住五个动作：带单进(请求里带上 tools schema)→ 模型出单(tool_call)→ 程序干活(解析、校验、执行)→ 回执进单(tool 结果回填)→ 模型看回执，决定出下一张单还是收工。下面这张图是单轮视图，真正值得注意的是图上那条虚线回环——它才是生产环境的常态：

再落到消息序列上看一遍(OpenAI 风格，各家字段大同小异)。重点是：模型返回 tool_call 时并不认为自己「答完了」，它只是在等回执:

【第 1 轮:你发给模型的】
messages = [
  {"role": "user", "content": "vol-7f3a 昨天的备份为什么失败?"}
]
tools = [query_backup_status 的 schema]      ← 工具说明书随请求一起给

【模型返回:注意不是答案,是一张工单】
{
  "role": "assistant",
  "finish_reason": "tool_calls",
  "tool_calls": [{
      "id": "call_001",
      "function": {"name": "query_backup_status",
                   "arguments": "{\"volume_id\": \"vol-7f3a\", \"date\": \"yesterday\"}"}
  }]
}

【你的程序执行完,把回执追加进历史,发起第 2 轮】
messages += [
  {"role": "assistant", "tool_calls": [ ...上面那张工单原样追加... ]},
  {"role": "tool", "tool_call_id": "call_001",
   "content": "{\"status\": \"failed\", \"error\": \"snapshot timeout\"}"}
]

【第 2 轮模型返回:信息够了,给出最终回答】
{"role": "assistant", "content": "vol-7f3a 昨天备份失败,原因是快照超时…"}
  • finish_reason 是 "tool_calls" 而不是 "stop":程序靠这个标记区分「该去执行工具」和「该把回答吐给用户」。
  • assistant 的 tool_calls 要原样追加进历史:回执靠 tool_call_id 对回工单，否则模型不知道这条结果对应哪次调用。
  • 循环不是一趟跑完:用户问「vol-7f3a 昨天的备份为什么失败」——第 1 轮模型调 query_backup_status 查到 status=failed;第 2 轮它自己决定再调 get_backup_log 拿错误详情，发现「快照超时」；第 3 轮不再出单，输出结论。执行循环的价值就在这：模型能基于中间结果决定下一步，像运维排障一样迭代。
消息角色谁写入装什么调度系统类比
user用户/上游系统原始问题故障工单
assistant(tool_calls)模型要调哪个工具、参数是什么调度器开出的作业单
tool你的程序执行结果或报错，靠 tool_call_id 对回工单作业回执
assistant(最终)模型面向用户的自然语言回答排障报告

3. 能力从哪来(训练)：教出来的，不是推理时悟出来的

  • 闭源 API(OpenAI/Claude/国产)：厂商在 instruction tuning 阶段用大量 (query → tool_call → tool_result → answer) 样本训练，把「何时调、调哪个、参数怎么填、结果怎么用」整套行为压进权重；推理时你只需在请求的 tools 字段传入 schema。一条训练样本长这样：

——本质是教模型「在正确时机填出正确的标准工单」
{
  "messages": [
    {"role": "user",      "content": "帮我看看订单 8899 发了没"},
    {"role": "assistant", "tool_calls": [{
        "function": {"name": "query_order",
                     "arguments": "{\"order_id\": \"8899\"}"}}]},
    {"role": "tool",      "name": "query_order",
     "content": "{\"status\": \"已发货\", \"eta\": \"明天送达\"}"},
    {"role": "assistant", "content": "订单 8899 已发货,预计明天送达。"}
  ]

何时调 / 调哪个 / 参数怎么填 / 结果怎么组织成回答
  • 开源模型(Qwen / Hermes / Llama 3.1 等)：各家 chat template 里约定了 FC 的特殊格式，能力内置；能力弱的模型可以用 FC 数据做 SFT 增强。把开源模型的 FC 输出打出来看，它其实也是「特殊标记包起来的文本生成」：

  • 推理侧零成本的关键是 schema 写得好:描述里写清“何时该用/何时不该用”，直接决定选工具的准确率——工具说明书本身就是 prompt 的一部分。

4. Schema 设计要点：说明书就是半个 prompt

  • 名称 + 描述(含正反例：什么时候用、什么时候别用)、参数 JSON Schema(类型/必填/枚举/默认值)。
  • 允许模型一次返回多个 tool_call 实现并行(如同时查天气 + 查订单)。
  • 权限最小化：只给任务需要的工具，减少选错面——给调度器的作业模板库越精简，开错单的概率越低。

一份合格的 schema 长这样(拿备份域举例，注意 description 里那句「何时不用」往往比「何时用」更值钱)：

{
  "type": "function",
  "function": {
    "name": "query_backup_status",
    "description": "查询指定卷某天的备份状态与耗时。当用户问'某卷备份成功没/最近备份时间/为什么失败'时使用;查恢复任务请改用 get_restore_job,不要用本工具。",
    "parameters": {
      "type": "object",
      "properties": {
        "volume_id": {"type": "string",
                      "description": "卷唯一标识,如 vol-7f3a"},
        "date":      {"type": "string",
                      "enum": ["latest", "yesterday"],
                      "description": "查哪一天的备份,默认 latest"}
      },
      "required": ["volume_id"]
    }
  }
}

5. 工程细节：把「出单-干活」当分布式依赖治理来做

  • JSON 解析容错:模型偶发非法 JSON → 重试、带纠错提示重问、或宽松解析(修引号/尾逗号/截断)，兜底是降级为不调工具直接回答。这套分层降级跟容灾设计一个思路：主路径 → 重试 → 纠错重放 → 降级服务 → 人工兜底。
  • 超时/限流:工具是外部依赖，防慢调用拖垮链路。每个工具设独立超时和并发上限，再加熔断——否则一个 P95 都正常、却被工具超时拖出长尾请求的接口，P99 直接打穿 SLA。治理方式跟备份系统防介质库雪崩完全同构。
  • 结果截断:工具返回超长(全量日志、大 JSON)要截断/摘要，或 chunk 化分批处理，否则挤爆上下文——等价于告警里只放日志摘要，而不是把全量日志塞进短信。
  • 流式 + FC:先等 tool_call 完整、执行完再继续流式输出，处理好衔接：首包别傻等(保护 TTFT),执行期间可以先把「正在查询…」推给用户。
  • 灰度接工具:新工具上线先灰度发布小流量，观察选中率、准确率、耗时再全量——工具也是一种「发布」。

6. 为什么优于文本 ReAct:结构化带来的确定性

ReAct 是「用纯文本约定 Thought/Action/Observation」的早期方案，FC 可以理解为它的结构化升级版：

维度ReAct(文本协议)Function Calling(结构化)
调用表达自由文本 "Action: search[...]",靠正则抽原生 JSON tool_call,天然可解析
校验几乎没法校验，格式漂移只能整段重试schema 约束，参数可逐字段校验
并行难(文本里塞多个 Action 很脆)一次声明多个 tool_call,应用层并发执行
模型要求任何会写文本的模型都能跑需要模型经过 FC 训练/模板适配
适用场景快速原型、弱模型兜底生产环境首选

一句话:FC 用结构化换来了可校验、可并行、可观测，代价是协议更「刚性」、对模型有要求；ReAct 胜在万能通用。生产上主用 FC、文本协议留兜底是常见组合。至于 N 个 Agent × M 个工具的接入爆炸，由 MCP 标准化解决，追问里展开。

面试官追问
Q:模型真的"理解"工具吗？还是只背了格式？
人话：它学会的是「看到什么话、该填什么单」的统计规律，不是真懂工具原理。热门工具、清晰需求，它填得很准；冷门工具、含糊的 schema，它就开始瞎猜。类比：像一个把作业手册背得滚瓜烂熟的值班调度员：手册覆盖的工单秒填，手册没写的新型故障只能凭感觉填单。跟传统备份系统里人写死的调度规则最大的不同是——这位值班员会联想，也会想歪。技术：FC 能力来自 instruction tuning 的海量样本，学到的是「语言→调用格式」的条件映射，并没有真正的语义理解。工程上要靠三件事把它摁住：schema 写清正反例、few-shot 示范、必要时 FC 数据微调；没见过的专有工具，别指望零样本就稳。
Q:模型返回的 JSON 不合法怎么办？
人话：偶发坏 JSON 很正常，备一套降级链：先重试，再带着报错让它重写，再宽松修复，最后放弃调工具、直接回答或转人工。类比：这就是容灾设计的多级降级：主路径失败 → 原地重试 → 纠错重放 → 降级服务 → 人工兜底；备份作业失败也是先重试、再换介质、最后告警人工，同一个哲学。技术：① 同参数重试一次；② 把坏输出和报错一起回填，让模型自纠错，成功率不低；③ 宽松解析，修引号/尾逗号/截断；④ 仍失败则降级为不调工具直接回答。根治靠约束解码(JSON mode/结构化输出),从采样层面保证合法。某模型非法率持续高，说明它 FC 底子不行，该换模型或微调。
Q:需要并行调多个工具时怎么处理？
人话：让模型一次吐出多张互不依赖的工单，程序并发执行，结果凑齐后一起回填；如果 B 要用 A 的结果，必须排队。类比：备份调度器同时把多个卷的作业分发到不同代理并行跑，但「先查卷列表、再按列表下发」这种有依赖的步骤天然串行——本质就是分布式任务调度的 DAG。技术：① 开启 parallel tool call;② 模型返回 tool_calls 数组，应用层用线程池/异步并发执行；③ 按依赖关系建调用图，独立节点并行、依赖节点等前置完成；④ 全部回填后再进下一轮。注意失败隔离：单个工具挂了只回填错误信息，别让一个慢工具把整批的 SLA 拖成长尾请求。
Q:工具太多(几十上百个)模型会选错吗？
人话：会，这是真实痛点：选项一多，模型就「挑花眼」，选错、漏选都常见。核心思路是别让它一次看全仓库。类比：把几百个运维脚本一次性拍在新值班员桌上，他必然懵；按场景分组、每次只给相关的十来个，准确率立刻回来。技术：① 按场景/路由拆 Agent，每个只挂 5~15 个工具；② schema 写清「何时用/何时不用」；③ 检索式工具选择：对工具名+描述建索引(BM25、向量检索皆可)，按用户意图召回 top-k、必要时 Rerank 再交给模型——本质是「先检索后选择」，和 RAG 同构；④ 高频场景用 FC 数据微调。经验值：单请求挂 20+ 工具，选择准确率明显下滑。
Q:Function Calling 和 MCP 是什么关系？
人话：FC 管「模型怎么表达要调工具」，MCP 管「工具那一侧怎么统一接入」。一个是点单语言，一个是后厨标准插座，互补不互斥。类比：过去每接一个新工具，Agent 都要为它写一遍胶水代码——像每接一种新存储阵列就要写一遍适配层。MCP 把工具接口标准化：工具方实现一次，所有支持协议的 Agent 都能挂载，消掉 N×M 的适配爆炸。技术：MCP(Model Context Protocol)是 2024 年开放的协议，规范了工具的发现、描述与调用报文。落到链路：MCP server 暴露工具 → 宿主把 schema 转成模型的 tools 参数 → 模型照常生成 tool_call → 宿主经 MCP 执行。MCP 不取代 FC，它标准化的是 FC 下游的工具接入层。
Q:模型会不会编造不存在的工具或参数？怎么防？
人话：会。它可能编一个你没注册的工具名，或者瞎填参数(比如一个根本不存在的卷 ID)。防线就一句话：执行前校验、执行时鉴权、全程留痕——它说什么都别直接信。类比：调度单上写了个卷名，你不能拿着单子直接去挂载生产卷：先查配置库里有没有这个卷、这位值班员有没有权限，单子不合法就打回重填。技术：① 白名单校验：工具名+参数先过 schema/枚举校验，不合法就把报错作为 tool 消息回填，让模型重出单；② ID 类参数先查存在性再执行；③ 权限最小化，删除类危险操作加二次确认或人工审批；④ 全链路审计日志。幻觉没法根除，只能用校验把风险挡在产生真实副作用之前。
术语卡
Function Calling:模型输出结构化调用指令、由程序代为执行的能力，是 Agent 使用工具的主流机制。
JSON Schema:用 JSON 描述「一份合法 JSON 长什么样」的规范，FC 里用来声明工具的参数结构。
tool_call:模型生成的「工具名 + 参数」结构化工单，模型只出单、不执行。
Instruction Tuning:用「指令 → 期望输出」数据微调，教模型遵循约定的时机与格式。
ReAct:用纯文本 Thought/Action/Observation 约定实现工具调用的早期方案，FC 的前身。
Parallel Tool Call:一次生成多个互不依赖的 tool_call，由应用层并发执行。
MCP:把工具的发现/描述/调用标准化的开放协议，解决 N 个 Agent × M 个工具的适配爆炸。
执行循环:生成 → 执行 → 回填 → 再生成的闭环，Agent 迭代排障的骨架。
