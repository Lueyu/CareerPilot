Agent核心 · Q36

如果子agent回复不对怎么办？反思？跳不出去怎么办？限制次数？

⭐⭐⭐ #错误处理#反思机制 字节(真题)
先说人话:主 Agent 把活儿外包给子 Agent,收上来的结果不对——这题问的就是一整套出错处置预案:怎么发现错、怎么让它改、改不动了怎么收场。面试官爱问它,是因为答「反思到对为止」直接暴露没踩过坑;真救过火的人,开口就是「检测→带反馈重试→上限→兜底」这条闭环。
30秒电梯稿

"分三步:① 先发现错误——别信子 Agent 的自报,过四层校验:规则/格式、工具结果、置信度阈值、Critic 复查;② 再反思纠正——把“错在哪、为什么错、怎么改”作为反馈喂回去,让它带反馈重试,修复手段逐级升级(改提示→换工具/检索→换模型/拆任务),最多 2~3 轮;③ 防跳不出去——三重闸门:轮次上限、总 token/时间/成本预算、无进展检测(连续两轮输出无实质变化即强制退出),任一超限就走兜底策略:取历史最优、降级直答、转人工。核心原则:允许失败，但必须有退出机制和兜底，不能让用户卡死。"

通俗类比

整道题(用“实习生交作业 + 带教老师”想):先立全局图景——主 Agent 是派活的调度者，子 Agent 是被派去干具体活(检索、写代码、调工具)的实习生。实习生交上来的作业，老师不直接签收：先检查(校验)，发现不对就圈出错误让他重做(带反馈反思)，但最多改 2~3 次；再不行老师自己上手(降级直答)或上报领导(转人工)。哪里像:检查→返工→限次→兜底，和任务失败处置完全同构。哪里不像:实习生被指出错误后通常能稳定改对，LLM 带反馈重试仍有随机性，所以下面每个环节都格外强调“独立校验、全程存档、硬上限”。

校验器(用“备份成功 ≠ 恢复成功”想):干容灾的人有句行话：日志里的 "job succeeded" 不算数，真做过恢复演练才算数。子 Agent 的输出同理——它“自信地说自己做对了”和“真的做对了”之间，隔着一次独立校验，第一反应永远是别信自报，上校验。哪里像:都是“不信当事人，信第三方复核”，执行和验收分离。哪里不像:备份校验是确定性的，校验和对就是对、错就是错；Agent 的校验器很多时候也是 LLM(自己也会看走眼)，所以要分层:能用程序判的(格式、数值)交给程序，判不了的才交给裁判模型——“裁判不靠谱怎么办”在追问环节单独拆。

反思重试(用“带日志修复重提，不是原样重提”想):备份作业因为挂载路径配错而失败，把作业原封不动重提一百次，还是同一个错；正确姿势是看报错日志、改配置、再重提。Agent 的反思同理——原样重跑大概率原样错,必须把“错在哪、为什么、怎么改”作为新输入喂回去，这套思路在学术上就是 Reflexion 和 Self-Refine。哪里像:都是“诊断→修复→再执行”，错误信息本身就是修复的输入。哪里不像:备份作业修对配置后就稳定收敛(行为幂等)，LLM 带反馈重试仍带随机性——这轮可能改好了，也可能把原本对的地方改坏，所以要每轮结果都存档打分,退出时挑最优，而不是默认取最后一版。

跳不出去(用“无上限重试 + 熔断器”想):无限反思就是无限重试。分布式系统的老教训：无上限的重试不但修不好故障，还会把它放大成雪崩——所以你的工具箱里早就有指数退避、重试预算和熔断器。哪里像:都是用硬上限防止下游和用户被一个修不好的故障拖死。哪里不像:HTTP 重试配上退避之后大概率收敛，LLM 有一种更阴的失败——活锁:每轮都“忙忙碌碌”地给出新的错误答案，看起来在反思，实际原地打转。所以光数轮次不够，还要做无进展检测:连续几轮输出没有实质变化，就按死循环熔断。

兜底(用“容灾预案分级”想):熔断之后去哪，容灾早就给了模板。取历史最优 = 回滚到最近一次验证通过的副本(last known good);降级直答 = 服务降级,主链路不可用时用兜底链路先把业务撑住；转人工 = 升级 on-call。哪里像:每条失败路径都有预案，而且预案是事先写好、演练过的，不是出事才现想。哪里不像:容灾预案执行出来的结果基本是确定的，Agent 的降级输出本身还带不确定性，所以降级直答必须向用户声明置信度、明说“未经完整验证”，不能装作一切正常。

详细拆解

整条处置链按「检测 → 修复 → 熔断 → 兜底」四步走，正好对应你熟悉的四板斧：校验、带日志修复重跑、超窗强杀、预案切换。面试官这题一口气问了四件事——怎么发现错、怎么改、跳不出去怎么办、要不要限次数——恰好就是下面四步，一步步看。

1. 先解决“怎么知道它错了”(没有检测，反思无从谈起)

这一步最容易被一句话带过，却是整套机制的地基。干备份的人都懂：日志说成功，不等于成功——"job succeeded" 和“能恢复出来”之间隔着一次校验。子 Agent 的输出同理，它“自信地说自己对”和“真的对”之间，隔着下面四层检查，按从便宜到贵排成漏斗。

  • 规则/格式校验:输出必须是合法 JSON、必须引用来源、数值必须在合理区间——可程序化判定，最可靠。落地三件事：① 用 JSON Schema 把结构钉死——必填字段、类型、枚举值，不合法直接打回，连一次模型调用都不用花；② 引用的来源链接要真实可达，防“幻觉引用”；③ 数值做 sanity check:折扣率不可能大于 100%,库存不可能为负。这一层就是你的老朋友校验和：几乎零成本，先挡掉一大类低级错误。
  • 工具结果校验:子 Agent 调工具拿回的结果是否符合预期(为空、报错、类型不对)。典型疑点：查询接口返回空列表——是真没数据，还是参数传错了？返回码非零、超时、返回类型和声明不符，统统算可疑信号，绝不能默认“拿到返回就是成功”。介质服务器退出码非零时备份系统不会把作业标成功，Agent 也不能装没看见。
  • 置信度阈值:让子 Agent 附带 self-confidence 分数，低于阈值视为不可信。注意坑：LLM 的自评普遍偏乐观、没校准(calibration)——自称 0.9 的把握，实测正确率可能只有六成，所以阈值要先用标注数据统计“自评 vs 实际对错”的分布再定，不能拍脑袋给个 0.8。
  • Critic/Verifier 复查:另一个 Agent 或强模型对结果打分/找茬，不通过即判错，工程上叫 LLM-as-judge(拿模型当裁判)。两条纪律：① 生成者与校验者分离——自己不能给自己签收，就像开发不能 approve 自己的 MR;② 打分标准写成具体的 rubric(维度、分档、正反例)，否则裁判自由发挥，同一份答案两次打分能差出一档。
校验层谁来判成本确定性抓什么错
规则/格式校验程序≈0100%结构错、越界值、幻觉引用
工具结果校验程序≈0100%空结果、报错、类型不符
置信度阈值子 Agent 自评≈0(顺带产出)低明显“心虚”的输出
Critic 复查另一个模型+1 次模型调用中程序判不了的语义错误

四层是漏斗关系：便宜的在下、贵的在上，能用 if-else 解决的事，绝不留给裁判模型烧钱——就像备份校验先跑 checksum,过不了的不会进入昂贵的恢复演练环节。

2. 反思纠正：怎么“修”而不是“重试”

发现错误后，最大的坑是“原样重跑”。原理一句话：LLM 的输出是从一个由输入决定的概率分布里采样出来的，输入一个字没变，分布就没变——重跑或许换个说法，但大概率还是落在同一个错误模式里；要改变结果，先改变输入。

  • 带反馈重试(关键):把“错在哪、为什么错、怎么改”作为新上下文喂回子 Agent,而不是原样重跑(原样重跑大概率还是错)。反馈要来自第 1 步的校验结果，而不是让子 Agent 自己“再想想”——自己检查自己，自己的盲点很难翻出来。反馈除了指向最终答案，也建议指向执行轨迹(“你在第 3 步选错了工具”比“答案错了”好定位得多);Reflexion 一脉的做法，就是把校验反馈写成一段“语言记忆”注入下一轮上下文。
  • 渐进升级:第一轮改提示重试 → 仍错则换工具/换检索 → 再错则换更强模型或换策略(如拆更小的子任务)。这就是备份排障的顺序：先查配置(最便宜)，再换介质/通道，最后才动硬件方案——修复手段按成本递增排，不一步到位上重炮。前两级都失败，往往说明问题不在“怎么做”而在“做什么”，所以最后一级换的是策略本身。
  • 反思要落地到具体动作:让模型输出“我上一步哪里错了 + 下一步改做什么”，而非空泛的“我会更小心”。反例——“下次我会更仔细”，零可执行信息，下一轮和这一轮不会有任何区别；正例——“上一步把日期按 '2027-3-1' 传给了接口，接口要求 ISO 8601 格式，这次先调 format_date 工具再调用”，直接可执行。就像工单里写“系统很慢”和写“P99 从 200ms 涨到 5s、始于 14:00 的那次变更”，处理效率天差地别。

两种重试的差别，落到伪代码上一目了然：

── 盲重试(✗): 上下文一个字没变, 大概率复现同一个错 ──
answer2 = sub_agent.run(task)              # 原任务原样再问一遍

── 带反馈重试(✓): 把校验结果注入上下文, 改变采样条件 ──
answer2 = sub_agent.run(
    task,
    prev_output = answer1,                 # 上一轮的输出
    verify_err  = "字段 price 类型错误: 期望数字, 得到字符串 '免费'",
    fix_rule    = "只修正上述问题, 其余部分保持原样",
)

顺带一提，反思不是唯一解法。答案空间离散的任务(选择题、代码生成)可以用自一致性替代：同一任务独立采样 k 次直接投票，把“修一个错的”变成“从多个里挑对的”。反思适合“能定位到具体错误”的场景，投票适合“错误随机出现”的场景，两者常组合使用。

3. 防“跳不出去”：三重硬约束

反思是循环，循环就要防死循环。分布式系统的教训直接适用：无上限的重试不但修不好，还会自我放大成故障。三重闸门，各自回答一个“凭什么停”。

  • 限制反思轮次:通常 2~3 轮，超限强制退出——这是最直接的闸门。依据是收益曲线：头两轮修的是“反馈一给就能改”的浅层错误，收益最大；两三轮还修不动的，多半超出子 Agent 的能力边界，或者任务拆分本身有问题——再刷轮次只是烧钱。类比：重试三次还失败，说明不是抖动是故障，继续重提只会烧穿备份窗口。
  • 预算上限:总 token / 时间 / 成本预算，任一超限即停，防烧钱(token 是模型计量输入输出的基本单位，上下文长度和费用都按它算)。再补一个容易被忽略的视角——延迟：一轮反思 = 校验 + 生成反馈 + 重跑，少则两次、多则五六次模型调用，天然制造长尾请求，直接威胁对外的 SLA 和 P99。类比：整个任务必须在备份窗口内完成，超窗影响生产业务——预算一到就停，不能陪它耗。
  • 无进展检测:连续两轮输出无实质变化(哈希/关键字段比对)，判定陷入死循环，熔断。它抓的是最阴险的死法——活锁：每轮都“认真反思”、每轮都有产出，内容却在原地打转。类比：看门狗只确认“进程还活着”是不够的，还得确认“在干活”；同理，只看“它还在输出”不算进展，要看输出有没有实质变化。实现细节：别只比对全文哈希——模型每轮会换措辞，更稳的做法是抽取关键字段/结论做规范化后再比对。

三重闸门加兜底，整条控制流写出来是这样(闸门位置就是关键设计：在“决定是否再试”之前检查):

MAX_RETRY  = 3      # 闸门①: 轮次上限, 经验值 2~3 轮
BUDGET     = 50000  # 闸门②: 本任务总 token 预算, 超窗即停

retry_count = 0
best        = None               # 历史最优: 每轮存档打分(备份保留策略)
last_output = None               # 上一轮输出, 供无进展检测比对
feedback    = None

while True:
    output = sub_agent.run(task, feedback)      # 带反馈重试(第 2 步)
    score  = verify(output)                     # 四层校验(第 1 步)
    best   = better_of(best, output, score)     # 更新历史最优

    if score >= PASS:                           # 修好了 → 正常出口
        return output

    feedback = diagnose(output)                 # 错在哪 / 为什么 / 怎么改

    if retry_count >= MAX_RETRY:           break   # 闸门①: 轮次超限
    if tokens_used() > BUDGET:             break   # 闸门②: 预算烧完
    if same_as_last(output, last_output):  break   # 闸门③: 无进展(活锁)

    last_output  = output
    retry_count += 1

return fallback(best)    # 第 4 步: 历史最优 / 降级直答 / 转人工

三个闸门各管一件事：轮次管“别无限”，预算管“别烧穿”，无进展管“别空转”——少任何一个，循环都有一种对应的死法。

4. 兜底策略(退出之后去哪)

熔断不是终点，是切换点。三条出路按“手里还剩什么”选，和容灾预案一个逻辑：

策略做法适用
取历史最优反思全程保留各轮结果，退出时选评分最高的一版已有“不完美但可用”的结果
降级直答放弃多步 Agent,单模型基于已有信息直接给答案并说明不确定性用户等不起、答案可接受部分偏差
转人工明确告知 + 提交工单/人工接管高风险、敏感、用户已不耐烦

四个工程细节，决定兜底是“预案”还是“装饰”:① 历史最优的前提是全程存档——每轮输出和评分都要留底，这和“新备份未验证通过前不删旧副本”是同一条纪律；② 降级直答要声明不确定性——明说“此答案未经完整验证，仅供参考”，这是和传统服务降级最大的不同：降级产物本身也可能错，不能装作一切正常；③ 兜底路径要提前演练——上线前故意构造失败用例，把“超限→兜底→用户体验”整条链路走一遍，没演练过的预案等于没有；④ 兜底要有监控和上报——熔断率、兜底率、转人工率都是核心指标，兜底率突然升高，八成是新版本引入了新故障模式，该回滚回滚。

面试官追问
Q:反思会不会越改越差，甚至改坏本来对的部分？
人话:会，反思不是只赚不赔的买卖，它有「越改越糟」的真实风险，所以永远不能默认「最后一版就是最好的」。类比:备份保留策略——新副本没验证通过前，绝不删上一晚的成功副本；反思期间每轮产出都要存档打分，退出时挑最优，而不是闭眼取最后一版。技术:① 全程保留各版本和校验分，退出取最优；② 反馈聚焦具体错误，并明确「只修正上述问题，其余保持不变」；③ 硬上限防恶性循环；④ 上线前用测试集对比「开/不开反思」的正确率，确认有净收益再灰度发布——反思是配置项，不是默认美德。
Q:子 Agent 一直“自信地说对”，但其实错了(高置信度错误)怎么办？
人话:模型的自信和正确是两回事，自评分只能当线索，不能当证据，更不能当验收单。类比:备份日志写着 job succeeded,不等于能恢复成功——干过容灾的人只信恢复演练；同理，自评置信再高，也只认独立校验的结果。技术:① 有硬标准的交给程序：格式、数值区间、工具返回码；② 开放性结果上独立 Critic 做 LLM-as-judge 交叉检查，生成者与校验者分离；③ 对置信度做校准：在标注集上统计「自评分布 vs 实际正确率」，按校准曲线定阈值；④ 高危动作(写库、扣款、删数据)再叠一层人工二次确认，像生产变更必须走审批。
Q:反思轮次设多少合适，依据是什么？
人话:经验值 2~3 轮，但别拍脑袋，要拿测试集画「轮次-正确率-成本」曲线，找收益拐点。类比:备份重试策略——重试三次还不成，说明不是抖动是故障，再重提只会烧穿备份窗口；反思两三轮还错，说明错不在表面，而在任务拆分或能力边界。技术:头 1~2 轮修的是「反馈一给就能改」的浅层错误，收益最大；之后边际递减、成本线性上涨，还容易发散，Reflexion、Self-Refine 这些代表工作也都在个位数轮次内拿到主要收益。再按任务分级：简单任务不开反思，复杂、高风险任务才开，轮次随任务等级配置。
Q:转人工前，怎么避免让用户觉得“机器很蠢、白等了”？
人话:核心是「早转 + 带着上下文转」，别把转人工拖成最后一刻的认输。类比:容灾升级——等主备全挂才打 on-call 电话，黄金恢复时间早烧完了；高风险信号一出现就该升级，且工单里带全现场信息，别让接手的人从头排查。技术:① 设提前转触发条件：连续两轮同类错误、识别到用户负面情绪、任务命中高危清单；② 转接时打包已收集信息、已执行步骤、已排除方向，用户不用复述；③ 等待期话术给明确进度(「已升级至专员，预计 30 秒接入」)，不给白屏；④ 把「转人工」包装成服务能力而不是失败标志——体面的升级好过硬撑的沉默。
Q:校验器/Critic 自己也会看走眼，怎么保证“裁判”靠谱？
人话:会错，所以原则是：能用程序判的绝不用模型判；必须用模型判的，要「多人陪审、标准成文」。类比:备份质检从不靠一个人肉眼看日志，而是 checksum、沙箱恢复、抽检层层独立——单点裁判就是单点故障。技术:① 校验分层，程序规则打底，Critic 只兜语义层；② 把打分标准写成具体 rubric(维度、分档、反例)，压缩裁判自由发挥空间；③ 多评委投票或跨模型交叉评审，降低单模型偏差；④ 生成者与校验者用不同模型，防自己给自己放水；⑤ 定期用标注集回归测试裁判，翻车率超标就降权重、修 rubric。
术语卡
Reflection(反思):让模型审视并修正自己输出的机制，代表工作有 Reflexion、Self-Refine。
Self-confidence(自评置信度):模型对自身答案的口头打分，普遍偏乐观，只能参考、不能当验收单。
Critic/Verifier(校验者):独立于生成者的校验/评审角色，自己不能给自己签收。
兜底:主路径失败后的降级出口，思想同工程里的 fail-safe,让系统「失败也体面」。
熔断:异常反复时强制中断当前路径，防止故障自我放大。
活锁:一直在动却无实质进展的循环，反思机制最阴险的死法，靠无进展检测抓获。
看门狗:独立盯着「有没有在干活」、超时即强制干预的机制，无进展检测的精神原型。
