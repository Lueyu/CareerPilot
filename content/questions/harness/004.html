工程实践 · Q11

如何实现 Agent 的状态持久化?

⭐⭐⭐⭐ #状态管理#持久化#Agent
30秒电梯稿

"状态 = 执行位置(跑到图哪个节点)+ 共享 State(对话/中间产物)+ 外部引用(大对象指针)。每个节点执行完做一次序列化快照(JSON/protobuf),热存 Redis(亚毫秒恢复,给断点续传用)、冷存数据库(审计回放);恢复流程:定位最后 checkpoint → 反序列化 → 从该节点继续;两个必聊的深水区:状态 schema 版本化(代码升级后老状态还能恢复)和LLM 的不确定性(重放时生成内容会变,恢复策略要幂等)。"

通俗类比

游戏存档:每过一关自动存档(checkpoint);游戏崩了,读档从最近关卡继续(断点续传),不用从第一关重打;存档文件格式升级了,老存档也得能读(schema 兼容);换台电脑(另一个 Worker 实例)登录,进度照样在(状态外置);只是重新打时,关卡里的敌人随机刷新可能不太一样(LLM 重放的不确定性)。

详细拆解

1. 存什么:状态的三部分

2. 存储选型

存储存什么理由
Redis最新 checkpoint(热)亚毫秒读写,断点续传秒级;TTL 24h~7天
PostgreSQL/MongoDB历史 checkpoint(冷)审计、回放、时间旅行调试;按 thread_id 索引
对象存储大对象原文状态本体保持小,序列化快

3. 何时存 & 恢复流程

  • 写入时机:每个节点执行完、副作用提交前(WAL 思想:先记状态再执行副作用,顺序要对,防"做了事但没记档")。
  • 恢复:load 最新 checkpoint → 反序列化 → 校验 schema 版本 → 从记录的 next_step 重新调度。人工审批流:节点挂起 = 存档 + 计时器,批完 invoke 恢复。

4. 序列化细节

  • JSON 人类可读易调试,但要注意:datetime/枚举/自定义对象的编码约定;protobuf 性能好但要维护 schema。进阶做法:状态 schema 用 Pydantic 定义,序列化和校验一步到位。

5. 两个深水区(拉开差距)

  • Schema 演化:checkpoint 带版本号,加载时跑迁移函数(v1→v2 补默认值);反序列化用宽容模式(未知字段忽略不炸,缺字段给默认值)。
  • 恢复的不确定性:从 checkpoint 重放,LLM 重新生成的内容和之前不会完全一样。策略:① 恢复点选择"最后完成的节点"而非"生成到一半的 token";② 已成功的工具调用(副作用已发生)标记为"跳过重执行"(结果直接引用),只重跑未完成部分——配合幂等,双保险。
面试官追问
Q:状态很大(几 MB),每个节点存一次开销不小?
增量 checkpoint:只存和上次的 diff + 基线指针,恢复时回放合并;高频小状态全量存,低频大状态增量存,按对象大小自适应。
Q:为什么不用直接把状态塞进对话历史交给模型?
① 状态是给程序用的(结构化、确定性),历史是给模型用的(自然语言);② 塞历史费 token 且模型可能不忠实执行;③ 结构化状态才能做校验、迁移和审计。LangGraph 的 State 独立于 messages 的设计正是这个思路。
术语卡
Checkpoint:状态快照,恢复依据。
WAL:先写日志再执行,崩溃可恢复。
时间旅行调试:回放历史状态重跑。
