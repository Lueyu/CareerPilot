Agent核心 · Q45

你的Agent如何处理工具调用失败(如API超时、返回空)？有设计重试、降级或用户澄清机制吗？

⭐⭐⭐ #容错机制#降级策略 字节(真题)
先说人话:你的 Agent 调工具，就像备份系统调下游存储——超时、返回空是家常便饭，这题问的是翻车之后的「应急预案」怎么排：重试、降级、澄清、兜底各管一段。面试官爱考它，因为容错最能分清「背八股的」和「救过火的」——把重试当万能药、不知道写操作超时后不能闭眼重发的人，一句「超时到底成没成功」就能问露馅。
30秒电梯稿

我会按「先分类→再重试→后降级→必要时澄清→最终兜底」的链条处理。第一步先给失败分类：超时、限流这类瞬时错误才值得重试，无权限、参数非法重试一百次也不会变好，而“查无结果”根本不是错误；第二步只对可重试错误做指数退避重试，上限 2~3 次，写操作必须先有幂等保障；重试不成就走降级链：换备用工具、读缓存、给部分结果，并向用户声明降级的代价；信息不足或需要用户拍板时一次问清，不挤牙膏；所有路径最终收敛到明确告知原因 + 建议，或转人工，绝不让用户干等。一句话总结：重试有上限、降级有预案、澄清一次问清、兜底必有交代。

通俗类比

整套容错链(用你熟悉的容灾预案想):Agent 每次调用工具，等于生产系统依赖了一条下游链路。工具失败的处理，本质上就是给这条链路写一份容灾(DR)预案：瞬时故障重试、下游半死熔断、主路不通逐级降级、业务取舍升级问人、最坏情况按 RTO 给交代。唯一根本差异：容灾保护的是数据面，可以慢慢磨；Agent 容错保护的是正在盯屏幕的用户体验，每一步都有耐心预算，后台任务能重试十分钟，对话多等十秒用户就想关窗口。

重试(用备份任务错峰重跑想):网络抖了一下没连上，等 0.5s、1s、2s 再试，次数封顶——和备份任务失败后错峰重跑一模一样。哪里像：只针对瞬时故障、间隔递增、次数封顶、加抖动防止大家一起冲。哪里不像：普通重试是“原样重发”，Agent 多一个杀手锏模型自纠——把报错原文喂回模型让它修好参数再发，相当于运维看着 stderr 改命令而不是闭眼重跑；另外备份系统靠 job ID 去重防重复备份，Agent 写操作对应的就是幂等键，第 2 步细讲。

熔断(用微服务熔断想):下游连续超时说明它已经过载，继续调用是雪上加霜，不如跳闸。哪里像：和微服务里的熔断器完全同构——失败计数、阈值、打开短路、半开探测、恢复，一套直接搬过来用。哪里不像：Agent 的下游常是第三方 API，你熔断保护的不只是自家服务，还有对方的配额、你方的时间预算和 token(大模型按字计费的账单)。

降级链(用多级容退想):同城双活挂了退异地灾备，再不行退冷备——Agent 同构：备用工具→本地缓存→部分结果→能力降级直答。哪里像：都是“能服务多少先服务多少”，先保可用性再谈完整性，这是优雅降级的核心思想。哪里不像：容灾切换力求对用户透明，Agent 的缓存降级却必须向用户声明“非实时”——把昨天的快照当今天的准信交出去，那不叫容灾，叫事故。

澄清与兜底(用值班升级想):进程挂了自动拉起，但“要不要切异地”是业务决策，得打电话找领导批；Agent 里这个“领导”就是用户，该问的别让机器瞎猜。兜底对应 RTO：灾难再大，也必须在承诺时间内给出说法。哪里像：技术能拍板的自动做，业务取舍升级到人，最坏情况有时限承诺。哪里不像：容灾升级对象是内部值班人，沟通可以糙；Agent 升级对象是终端用户，话术必须是带选项的一次性提问，不能来回踢皮球。

详细拆解

0. 全景图：先把架子搭对。整套机制的决策顺序不能乱——先分类、再重试、后降级、必要时澄清、最终兜底，和容灾预案“先判故障域→自动恢复→按预案降级→重大决策升级人工→对外给交代”是同一个模子。先看整条链路长什么样：

下面按五步逐个拆。

1. 失败分类（先分清楚，才谈得上策略）

为什么第一步是分类？因为不同故障的处理动作完全不同——这和存储排障一个道理：介质坏块、链路抖动、配置错误，三类故障的恢复动作天差地别，混着处理要么空转、要么误伤。落到工具调用上，分四类：

失败类型示例策略
可重试·瞬时超时、网络抖动、429 限流指数退避重试 + 熔断
可重试·语义参数格式错、返回空可换参模型自纠参数后重试 1~2 次
不可重试无权限、资源不存在、非法参数直接降级/澄清，不空转
业务空结果查无此人、酒店满房换条件、给替代、反问澄清
  • 可重试·瞬时：错不在你，是环境抖了一下，原样重发就有概率成功。429 是下游在喊“我限流了”，正确姿势是按它给的 Retry-After 节奏来，而不是硬闯。
  • 可重试·语义：请求“差一点就对”——日期格式错了、参数名拼错了。原样重发不会好，但把报错喂回模型改参数后有机会好，这是 Agent 特有的重试姿势（第 2 步细讲）。
  • 不可重试：没权限就是没权限，重试一百次结果一样。继续试纯属烧时间烧 token，正确动作是快速失败，把时间预算省下来给降级和澄清。
  • 业务空结果：再强调一次，空不是错。“查无此人”是下游认真查过之后的正常答复，属于业务事实。它需要的不是重试，是换条件、给替代、或者问用户。
  • 工程上把这套判断做成错误码映射表（错误类型→处置策略），类似 errno 归类：接入新工具时先把它的错误语义登记进来，分类逻辑不散落在业务代码里。

2. 重试机制（要点：可重试性 + 退避 + 上限 + 幂等）

重试是整套容错里最容易被滥用的环节——它本质是给正在故障中的下游追加流量，所以四条军规一条不能少：

  • 指数退避 + 抖动：如 0.5s → 1s → 2s，加随机抖动避免惊群；总重试上限 2~3 次、总预算限时。展开讲两个为什么：退避解决“隔多久再试”——下游过载时，你越快重试它死得越透；抖动解决“别一齐上”——想象 200 个请求同一毫秒超时，又在同一毫秒集体重试，下游瞬间再挨一记惊群。预算烧完立刻转降级，宁可降级，不能让用户干等。
  • 只重试幂等操作：查询可以安全重试；写操作（下单/扣款）必须幂等，否则“超时其实已成功”会造成重复执行——用幂等键/两段式防重。这里藏着重试最大的坑：超时 ≠ 失败，请求可能早已到达并执行成功，只是响应没回来，这时闭眼重发就是重复扣款事故。三道防线任选其一：① 幂等键——写请求带唯一 ID，下游按 ID 去重，和备份系统按 job ID 去重防重复备份完全同构；② 查询确认——重试前先调读接口，看上一笔到底落地没有；③ 两段式——先建“待执行单据”再确认执行，每一步可查询、可撤销。
  • 熔断：某工具连续失败（如 5 次），短时间内直接短路不再调用，保护下游 + 快速失败。它有三态：闭合（正常放行）→打开（全拒，直接走降级）→半开（冷却期满放 1 个探测请求，成功才闭合）。价值双重：护住下游，也护住自己的时间预算——熔断打开意味着“这工具眼下靠不住”，可以立刻切预案，而不是每次都陪它等满超时。
  • 模型自纠：参数类错误把工具返回的错误信息回填给模型，让它修正参数重试，这是 Agent 相对普通重试特有的能力。比如第一次传 "2027-3-1" 被报“日期格式应为 YYYY/MM/DD”，模型读完报错自改自重发。但要限次 1~2 次并计入总重试预算：模型也可能越改越错，无限自纠就是拿 token 和时间打水漂。

落到时间轴上长这样，注意写操作多了一道“先查证”的闸门：

退避时间轴 (0.5s 起步, 2倍指数, 3次封顶):

t=0.0s   首次调用: 超时 (注意: 此时不能断定失败, 可能已成功落地)
t=0.5s   重试#1  ← 0.5s + 随机抖动 (如 ±40%)
t=1.5s   重试#2  ← 1.0s + 随机抖动
t=3.5s   重试#3  ← 2.0s + 随机抖动   ← 次数到顶, 停止
t=3.5s+  无缝转入降级链, 不再干等

写操作的前置闸门:
重试前先查"上一笔落地没有" (幂等键查重 / 读接口确认)
确认没落地, 才允许发出重试#1

工程上把这些约定收进配置，而不是硬编码在调用点里：

retry_policy = {
    "max_retries":    3,          # 重试上限, 防流量放大
    "backoff_base":   0.5,        # 首次退避(秒)
    "backoff_factor": 2,          # 指数因子: 0.5s→1s→2s
    "jitter":         "full",     # 全抖动, 防重试惊群
    "retryable":      ["TIMEOUT", "CONN_RESET", "HTTP_429"],
    "budget_ms":      5000,       # 总预算: 烧完立刻降级, 不再等
    "write_op":       "require_idempotency_key",  # 写操作无幂等键禁止重试
}
circuit_breaker = {
    "fail_threshold":  5,         # 连续失败 5 次 → 打开(短路)
    "open_seconds":   30,        # 打开 30s 后进半开
    "half_open_probe": 1,        # 半开只放 1 个探测请求, 成功才闭合
}

3. 降级机制（体现工程成熟度）

重试救不回来，不代表任务死透——能服务多少先服务多少，和容灾的“降级运行”同一思路：主库挂了走只读副本，同城挂了退异地。Agent 的降级链按代价从低到高排：

  • ① 备用工具：同一能力常有多条实现（官方 API 挂了换聚合网关、主搜索挂了换备用索引），对应容灾的同城双活——换个机房接着干，数据新鲜度几乎不掉。
  • ② 本地缓存：拿最近一次成功结果顶上，对应拿昨天的快照恢复——能用，但要向用户声明“非实时”；价格、库存、余额这类强一致场景慎用。
  • ③ 部分结果：5 个数据源挂了 2 个，把另外 3 个先交付，并注明缺了哪块——对应挂载部分卷继续跑，业务先活下来。
  • ④ 能力降级：工具链整体不可用时，退回纯模型直答（基于自身知识，或 RAG：先从知识库检索相关材料再作答），并明说“工具暂不可用，以下仅供参考”，绝不冒充实时结果。
  • 降级也要讲清代价：比如缓存结果要提示“非实时”，不能让用户把过期数据当准信。
  • 降级链可配置化（策略表），不同工具不同预案；降级本身也要有监控指标（降级率、降级后满意度）。
  • 降级链要演练：和容灾演练一个道理——不能等真挂了才第一次跑备用工具。定期用混沌测试验证备用路径真的通、缓存真的可读，否则降级链就是纸面预案。

4. 用户澄清（信息/权限不足时）

有一类失败重试和降级都救不了，因为缺的信息在用户脑子里。硬猜就是把用户的钱和时间拿来掷骰子（满房了给你订错城市），这时该“升级人工”——只不过 Agent 的“人工”就是用户本人。

  • 触发时机：缺必要参数（“哪天出发？”）、结果有歧义（多个同名地点）、失败后需要用户拍板（“改期还是换航班？”）。判断口诀：机器能查到的别问用户，只有用户知道的才问。
  • 一次问清：把澄清项做成选择题/结构化追问，避免多轮挤牙膏；带上下文说明“为什么问这个”。每多一轮就是多一次往返延迟，用户耐心是有限资源；“这家酒店满房了，换附近同价位的，还是改日期？”这种问法，用户一眼就能答。
  • 澄清不是万能：能合理默认的（有唯一高置信答案）就默认并告知“已按 X 处理，可改”，减少打断。边界和容灾升级同构：进程挂了自动拉起（自动做），切异地灾备找领导批（问人）——技术能拍板的自动做，业务取舍问用户。

5. 兜底与可观测（收尾）

链条最后一环是底线：不管前面怎么折腾，用户最后必须拿到一个明确交代。这一步做得好不好，决定用户对 Agent 的信任是一次故障归零，还是还能挽回。

  • 最终失败：明确告知“当前无法完成，原因 + 建议”或转人工，附上失败上下文方便接手。转人工不是甩锅：要带上“我试过什么、各卡在哪、已排除什么”，让人工从第 80 步接手而不是从零排查——和故障工单转交必须附完整排查记录是同一件事。
  • 全链路记录每次工具调用的入参/结果/耗时/重试次数，失败归因可查；把重试率、降级率、澄清率、最终失败率纳入健康度看板。四个率怎么读：重试率、降级率抬升，说明下游质量或模型产参质量在恶化；澄清率抬升，说明任务设计在消耗用户耐心；最终失败率直接对应 SLA 达成。耗时分布要单独盯长尾请求——重试链最长的那批，就是 SLA 的杀手。
  • 指标要设告警，策略要走灰度：最终失败率越阈值、熔断频繁打开，应当像备份成功率掉线一样触发告警，而不是等用户投诉才发现；重试/降级策略的调整也要走灰度发布，小流量验证再全量，别让“优化容错”本身变成一次故障。
面试官追问
Q:重试会不会放大流量，把下游打挂？
人话:会，重试本质是给正在故障的下游追加流量，所以必须戴枷锁：限次数、拉间隔、会熔断、有总预算，四样缺一不可。类比:凌晨全量备份任务集体失败，如果全体立刻原地重跑，瞬间能把存储集群压垮——成熟备份系统的做法就是并发上限加错峰重跑，和这里完全同构。技术:① 重试上限 2~3 次，指数退避 0.5s→1s→2s 叠加抖动防惊群；② 熔断器连续 5 次失败即打开，期内直接短路走降级；③ 客户端令牌桶限流，按下游配额压住 Agent 侧 QPS；④ 设总时间预算，烧完立即降级。下游返回 429 时按 Retry-After 头对齐节奏，不自作主张。
Q:写操作超时了，怎么知道到底成功没有？
人话:超时不等于失败——先查证、再重试，绝不闭眼重发。类比:备份任务界面上超时了，第一反应是查 job 状态，而不是再建一个同名任务；真备份系统按 job ID 去重，重跑一万次也只落一份备份。技术:写操作重试的前提是幂等：① 幂等键——请求带唯一 ID，下游按 ID 去重，重发也只执行一次；② 查询确认——重试前先调读接口，看上一笔是否已落地；③ 两段式——先建待执行单据、再确认执行，每步可查询。三选一兜住；一样都没有就禁止自动重试，否则“超时其实已成功”加重试就是重复扣款事故。
Q:怎么决定"重试"还是"直接问用户"？
人话:确定性错误自动修，涉及用户取舍的问人。类比:容灾里进程挂了自动拉起，但要不要切异地灾备是业务决策，必须升级到人拍板；Agent 里这个“拍板的人”就是用户。技术:看失败类型和修复成本：瞬时错误（超时/429）和参数格式错，自动重试或模型自纠即可，用户无感；涉及用户偏好、业务取舍的（满房换哪家、预算超了怎么办），重试一万次也没答案，直接澄清。中间地带：存在唯一高置信默认值就默认执行并告知“已按 X 处理，可改”；置信度不够才打断用户——确定性错误靠重试，不确定性错误靠澄清。
Q:工具没报错、但查出来是空的，这算失败吗？怎么处理？
人话:空结果是“认真查过、确实没有”，不是故障——不能重试，更不能装作成功。类比:查某个时间点的恢复点列表返回空：可能是真没做过备份，也可能是查询时间窗口填错了。前者要告知并给建议，后者要自纠参数再查一次，处理完全不同。技术:① 先自检：参数是否合理（拼写、时间窗、过滤条件），修正或放宽后重查一次；② 确认真为空：明确告知“查无结果”，并给替代建议（相近选项、相似内容）；③ 拿不准是“真没有”还是“查错了”就向用户澄清。红线：绝不硬编数据去填空结果，宁可信其无。
Q:熔断打开之后，什么时候恢复？怎么恢复？
人话:不能一直关死——冷却一会儿放个探针，试好了再逐步放行。类比:容灾切流后回切，不能一把全量切回生产，先灰度一小部分流量观察，稳了再逐步扩大，熔断恢复同理。技术:熔断器三态轮转：打开（全拒绝）→ 冷却期（如 30s）后进半开 → 半开状态只放 1 个探测请求（或先打一次 health check）：成功则闭合、恢复正常调用；失败则重新打开计时。恢复后也别立刻放量，按比例逐步放行，配合监控看下游真实水位，避免“半开→闭合→再打挂”的振荡循环。
Q:模型自纠参数，会不会越改越错、烧 token 死循环？
人话:会，所以自纠要限次、限成本，改不好就换路走。类比:运维改脚本连改三遍还报错，就该停下来翻文档或求助，而不是无限改下去——无限自纠烧的是 token 和用户的时间预算。技术:① 硬上限 1~2 次，超了直接转降级或澄清；② 每次自纠把“上次参数+报错原文”一起喂给模型，避免它改回老样子；③ 连续自纠失败往往说明工具的 description 或 JSON Schema 和模型理解不匹配，记录下来改工具定义才是根治；④ 自纠计入总重试预算，和普通重试共享上限，不搞特权。
术语卡
指数退避：重试间隔按 2^n 增长（如 0.5s→1s→2s），叠加随机抖动防止集体扎堆。
熔断：连续失败达阈值后“跳闸”，短期内直接拒绝调用，防止故障雪崩。
幂等：同一操作执行多次效果等同一次，是写操作能安全重试的前提。
降级链：主路径失败后逐级退让的备用方案序列，如备用工具→缓存→部分结果→直答。
澄清：信息不足或结果有歧义时向用户结构化反问，而非让模型瞎猜。
优雅降级：主能力不可用时退到次优方案，先保可用性再谈完整性。
惊群：大量请求同一时刻集中重试，瞬间形成流量尖峰，是抖动要解决的问题。
幂等键：写请求携带的唯一标识，下游按它去重，防“超时其实已成功”后重试造成重复执行。
