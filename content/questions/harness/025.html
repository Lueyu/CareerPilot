Agent核心 · Q45

你的Agent如何处理工具调用失败(如API超时、返回空)？有设计重试、降级或用户澄清机制吗？

⭐⭐⭐ #容错机制#降级策略 字节(真题)
30秒电梯稿

我会按"先分类 → 再重试 → 后降级 → 必要时澄清 → 最终兜底"的链条处理：第一步区分失败类型（可重试的网络/超时 vs 不可重试的参数错/无权限），只对可重试错误做指数退避重试；重试仍失败就降级（换备用工具、用缓存、给部分结果）；信息不足导致无法执行时反问用户澄清；所有路径最终收敛到明确告知 + 转人工/给替代建议，绝不让用户卡死。核心原则：重试要有上限、降级要有预案、澄清要一次问清。

通俗类比

像餐厅点菜 + 骑手送餐：你点的菜后厨没食材了（工具返回空），服务员不是干等，而是先换一道类似菜（降级）或回来问你"换 A 还是 B"（澄清）；外卖超时了平台隔一会儿再催一次（重试），催三次还不行就退款 + 道歉（兜底）。关键在"服务员不能把客人晾在那儿"——每一步都有下一步，且最后一定给你一个说法。

详细拆解

1. 失败分类（先分清楚，才谈得上策略）

失败类型示例策略
可重试·瞬时超时、网络抖动、429 限流指数退避重试 + 熔断
可重试·语义参数格式错、返回空可换参模型自纠参数后重试 1~2 次
不可重试无权限、资源不存在、非法参数直接降级/澄清，不空转
业务空结果查无此人、酒店满房换条件、给替代、反问澄清

2. 重试机制（要点：可重试性 + 退避 + 上限 + 幂等）

  • 指数退避 + 抖动：如 0.5s → 1s → 2s，加随机抖动避免惊群；总重试上限 2~3 次、总预算限时。
  • 只重试幂等操作：查询可以安全重试；写操作（下单/扣款）必须幂等，否则"超时其实已成功"会造成重复执行——用幂等键/两段式防重。
  • 熔断：某工具连续失败（如 5 次），短时间内直接短路不再调用，保护下游 + 快速失败。
  • 模型自纠：参数类错误把工具返回的错误信息回填给模型，让它修正参数重试，这是 Agent 相对普通重试特有的能力。

3. 降级机制（体现工程成熟度）

  • 降级也要讲清代价：比如缓存结果要提示"非实时"，不能让用户把过期数据当准信。
  • 降级链可配置化（策略表），不同工具不同预案；降级本身也要有监控指标（降级率、降级后满意度）。

4. 用户澄清（信息/权限不足时）

  • 触发时机：缺必要参数（"哪天出发？"）、结果有歧义（多个同名地点）、失败后需要用户拍板（"改期还是换航班？"）。
  • 一次问清：把澄清项做成选择题/结构化追问，避免多轮挤牙膏；带上下文说明"为什么问这个"。
  • 澄清不是万能：能合理默认的（有唯一高置信答案）就默认并告知"已按 X 处理，可改"，减少打断。

5. 兜底与可观测（收尾）

  • 最终失败：明确告知"当前无法完成，原因 + 建议"或转人工，附上失败上下文方便接手。
  • 全链路记录每次工具调用的入参/结果/耗时/重试次数，失败归因可查；把重试率、降级率、澄清率、最终失败率纳入健康度看板。
面试官追问
Q:重试会不会放大流量，把下游打挂？
会，所以要三件套：① 重试上限小（2~3 次）+ 指数退避拉长时间；② 熔断，连续失败直接短路；③ 对下游做限流/令牌桶，压住 Agent 侧的并发。还可以在超时后先探测一次（health check）再决定是否真重试。
Q:写操作超时了，怎么知道到底成功没有？
靠幂等键：每次写操作带唯一 id，重试时下游按 id 去重；或者用"查询确认"（调一个读接口看结果落地没有）再决定重试还是补偿。设计原则：写操作要么幂等，要么两段式 + 状态可查询，否则重试就是制造事故。
Q:怎么决定"重试"还是"直接问用户"？
看失败类型和成本：瞬时性、自动可修复的（超时、参数格式）优先自动重试；涉及用户偏好/业务取舍的（满房换哪家、预算超了怎么办）重试无意义，直接澄清。简单说：确定性错误靠重试，不确定性错误靠澄清。
术语卡
指数退避:重试间隔按 2^n 增长，加随机抖动。
熔断:连续失败后短期拒绝调用，防止雪崩。
幂等:同一操作执行多次，效果等同一次。
降级链:主路径失败后逐级退到的备用方案序列。
澄清:信息不足时向用户反问，而非瞎猜。
