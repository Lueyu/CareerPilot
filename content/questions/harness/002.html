系统设计 · Q4

设计一个 Agent 工作流引擎(类似 LangGraph)

⭐⭐⭐⭐⭐ #Agent#工作流#状态机
先说人话：这题让你造 Agent 系统的“调度内核”：理解、检索、生成、审查这些步骤串成一张有向图，要跑得稳、挂得起、断了能续。面试官爱考它，是因为一题就能分出“会演示的人”和“能上线的人”：前者满嘴 prompt,后者必须答得出持久化、防环、失败补偿。有备份/容灾底子更是主场——按“自带快照与容灾的引擎”来答就对了。
30秒电梯稿

"本质是把流程图变成可执行、可恢复的程序。节点是函数或 LLM 调用，边分固定边和条件边，全图共享一个 State 对象像接力棒一样在节点间流转。核心设计四件事：① State 每步落库做 checkpoint,支持断点恢复和人工审批挂起；② 条件边实现分支，循环用最大迭代次数 + 状态变化检测双保险防死循环；③ 节点级重试 + 指数退避 + 双层超时；④ 支持 fan-out/fan-in 并行节点。LangGraph 就是这套思路的标杆实现。"

通俗类比

整个引擎(用你天天维护的备份策略引擎想):一条备份策略天生就是张流程图——发现资源、打快照、复制到远端、校验、归档；Agent 工作流引擎只是把执行单元换成 LLM 调用：节点是策略里的各步骤，边是调度顺序，State 是任务元数据表，checkpoint 是任务进度快照。俩系统是同一套老四样：流程图 + 调度器 + 状态持久化 + 失败处理。

哪里像:都靠“从断点续跑、失败重试”吃饭，都强调留痕可审计、可回放。哪里不像:备份策略的分支在策略创建时就定死(变化率超阈值 → 转全量)，而 Agent 的条件边是运行中被模型输出动态决定的——流程图自己会“思考”，所以防环和预算兜底得比备份域做得更硬。

State 与 checkpoint(用快照 + 增量 + 冷热分层想):State 是任务的全量状态，每个节点跑完写一次 checkpoint,相当于“每步一份增量备份”；热副本放 Redis 供毫秒级恢复，冷副本放 DB 供审计回放——副本供恢复、归档供审计，一个都不能少。

哪里像:崩溃恢复就是容灾切换的语义，RPO 等于 checkpoint 间隔——每步都写，RPO 趋近于零。哪里不像:保护对象是状态字典不是数据块，体量小但每步都变，必须做 diff 和去重；而且“等人审批一等几天”这种挂起，比普通崩溃恢复对持久化的要求更苛刻。

循环防护(用看门狗 + 熔断想):max_iterations 是看门狗——“N 步没跑完就杀”；“同节点连续 N 次状态不变 → 熔断”是熔断器的“连续失败 N 次就跳闸”。

哪里像:都不信任“它自己会停”，都用外部硬顶来框住爆炸半径。哪里不像:熔断对象不是网络调用而是“模型原地打转”，判断信号是“状态变没变”而不是错误率。

失败处理(用作业重试 + 残留清理想):瞬时失败(网络超时、限流)带着指数退避重试，就像复制中断自动重拉；补偿(compensation)像“远端副本写了一半失败 → 清理碎片，不留不一致残留”。

哪里像:重试都区分瞬时与确定性(策略配错了，重试一万次也没用)；补偿都是对副作用做善后。哪里不像:失败源多了“模型”这一路——除了网络错，还有“生成质量不达标”“拒答”这类语义失败，得靠条件边打回重做，而不是傻重试。

fan-out/fan-in 与 HITL(用 scatter-gather + 变更审批想):一条条件边返回多个目标，就是一个读请求拆 N 个分片、汇总后返回——scatter-gather;人工节点是变更审批闸口——机器跑流程，人握按钮，图一挂几小时几天，批完从 checkpoint 续跑。

哪里像:并行都是“拆分 → 执行 → 汇合”，汇合都可以“谁先完成用谁”；审批流同样是“存状态、等人、继续”。哪里不像:这里的“分片”常是异构任务(检索走一路、写代码走另一路)，不是同构副本；审批按钮也不在运维平台上，而是图里的一个节点。

详细拆解

先定调：这个引擎 = 一台允许带环的状态机(比 Airflow 这类调度系统的 DAG 更放宽，环必须带防护)+ 一层持久化 + 一个并行调度器。下面按“定义图 → 存状态 → 防循环 → 处理错误 → 跑并行”推进，先用一张组件总览搭心智模型：

组件职责备份域对应物
图 DSL声明节点与边策略配置文件
调度器选出下一批可执行节点调度框架
State + reducer共享状态与合并策略任务元数据库
Checkpointer每步持久化状态与位置快照 + 增量备份
错误处理重试 / 超时 / 补偿作业重试 + 残留清理
HITL 人工节点挂起等人拍板变更审批

再背一个事实，后面所有设计都由它推导而来：节点分两种——普通函数节点(格式化、查库，毫秒级、稳定)和 LLM 节点(把当前 State 交给大模型，让它生成内容或做判断)。LLM 节点慢(百毫秒到几十秒)、不稳(会超时、会输出不合规内容)、贵(按 token 计费)。重试、超时、预算、打回重做，全是给这三个特性兜底的。

1. 图定义(DSL 设计)

为什么要把控制流从代码里搬进图？写在 Python 里，if/else 埋在函数体内，引擎看不见全貌；搬进图里，引擎才能做 checkpoint 路由、静态环检测、并行调度——就像备份策略写成配置而不是 shell 脚本：配置才能被静态校验、可视化、审计。

  • 节点 = 一个函数:输入 State,输出 State 的增量更新(只返回变化的字段，由引擎合并)。开发者用代码注册：graph.add_node("retrieve", fn)。只返回增量的好处：节点无权篡改全量状态，并行写入时由合并策略兜底。
  • 边 = 跳转规则,分两种：固定边(A 完了一定去 B)和条件边(一个函数读当前 State,返回下一个节点名，可返回多个实现并行)。与传统调度最关键的区别：条件函数可以引用模型的运行时输出——“下一步去哪”由内容决定，而不只由成败决定。
  • 入口/出口:START → … → END;图对象编译后生成可执行单元(compile() 时顺带做静态检查：悬空节点、不可达节点、无出口环)。
边的类型注册方式下一站由谁决定并行支持
固定边add_edge(A, B)定义期写死：A 完必去 B否
条件边add_conditional_edges(A, fn)运行期：fn 读 State 返回节点名是，返回列表即扇出
编译期静态检查抓什么问题备份域类比
悬空节点没有入边或没有出边的节点任务没挂进任何计划——要么永不执行，要么成孤儿
不可达节点从 START 出发到不了的节点任何数据都命中不了的策略分支
无出口环环上所有边都指回环内没有成功判据的死循环，只能靠人杀
# 用户侧 API 大致长这样
g = Graph()
g.add_node("understand", understand_fn)     # 意图理解
g.add_node("retrieve", retrieve_fn)         # 检索
g.add_node("generate", generate_fn)         # 生成
g.add_node("review", review_fn)             # 质量审查
g.add_edge(START, "understand")
g.add_edge("understand", "retrieve")
g.add_edge("retrieve", "generate")
g.add_conditional_edges("generate", # 条件边:不合格打回重做
    lambda s: "retrieve" if s.need_retry else END)
app = g.compile(checkpointer=RedisSaver())  # 带持久化编译

代码里三个细节值得咂摸：① 条件边是个 lambda,读 s.need_retry——这是 generate 节点写进 State 的字段，“下一步去哪”和模型产出质量挂了钩；② compile(checkpointer=RedisSaver()) 把持久化做成引擎的可插拔组件，业务节点保持干净；③ 顺带一提，review 注册了却没接任何边——真编译时会被静态检查当场拦下(悬空节点)，这个例子恰好演示了编译期检查在干活。这张图画出来是：

2. 状态设计与持久化

State 是全图共享的“单一事实来源”，设计核心两个字：分区 + 合并。分区让不同类信息互不踩踏，合并让并行节点写同一字段时不丢数据。

  • State 是一个带 schema 的字典:输入、中间产物、迭代计数、错误信息分区存放，避免互相覆盖(可用 reducer 函数定义合并策略，如追加列表)。一种合理的分区：
分区放什么例子谁写
input原始输入，只读question, user_id入口一次性写入
artifacts中间产物retrieved_chunks, draft各节点追加
counters循环与预算计数loop_count, tokens_used引擎自增
errors错误记录last_error, retry_count引擎 / 节点

为什么需要 reducer?fan-out 的并行节点会同时写同一字段(比如三路检索各写一份结果)，直接覆盖只剩最后一份，追加式合并(append)则全保得住——这就像多路备份流并发写同一份索引：按策略合并，不许互相覆盖。

  • Checkpoint 策略:每个超节点(superstep:一轮 fan-out 节点组)执行完写一次，内容 = State + 图位置 + 版本号,双写 Redis(热，供快速恢复)/ DB(冷，供审计回放)。
存储层Redis(热)DB(冷)
角色快速恢复路径审计、回放、时间旅行
保留最近 N 个版本全版本，按合规 TTL
恢复速度毫秒级百毫秒级
备份域类比本地副本 / 快照异地归档
  • 恢复:进程重启或人工审批通过后，load 最新 checkpoint,从记录的节点继续执行。写序必须是“checkpoint 落库成功，节点副作用才对外生效”——WAL 先写日志再做事的语义；恢复按 at-least-once 执行，有副作用的节点必须幂等。
  • 时间旅行调试:回放任意历史 checkpoint 重跑(fork 出新线程重跑更稳，不惊动原线程)，定位问题神器——相当于从任意恢复点还原重放。checkpoint 链还天然支持分叉，是“同一轨迹上 A/B 对比两个模型版本”的基础设施。

       │                 │                 │
       ▼                 ▼                 ▼
    ckpt_1            ckpt_2          (未产生)
       │                 │
       └────────┬────────┘
                ▼
  重启后:load 该线程最新的 ckpt_2
                │  state = retrieve 完成后的快照
                │  position = 下一站 generate
                ▼
  重跑 generate ──▶ 继续后半程 (at-least-once → 节点须幂等)

频率上再做一笔权衡：每步都写，RPO 趋近于零，代价是每节点一次落库——和“备份频率 vs 存储成本”的权衡一模一样，解法也是同一套：增量 diff、大对象外置(追问里细聊)。

3. 分支与循环的安全

为什么 Agent 图特别需要防护？因为条件边由模型输出驱动，模型完全可能永远判 need_retry=True——这不是 bug,是模型行为的固有怪癖。防护必须按“它自己永远不会停”来设计。

  • 循环必须配 max_iterations(如 5 次)和预算上限(token/时间)，超限强制走降级出口——注意是“降级出口”，不是抛异常暴毙：路由到兜底节点，产出安全答案(如“暂时无法核实，请补充信息”)，并把 loop_count、last_error 写进 State 供排查。
  • 环检测:同一节点连续执行 N 次而 State 关键字段无变化 → 判定死循环，熔断。它抓的是“每圈都很快、预算也烧不到，但状态在原地打转”的那类死循环。
防护封顶什么备份域类比
max_iterations循环圈数看门狗：N 步没完就杀
预算上限(token/时间)成本天花板策略配额：窗口超了就终止
状态变化检测“无进展”死循环熔断：连续 N 次无效果就跳闸
循环防护伪代码:
if loop_count >= max_iterations:        → 降级出口(强制)
if tokens_used >= token_budget:         → 降级出口
if 同节点连续 N 次且关键字段哈希不变:    → 熔断 → 降级出口

再补一刀成本视角：打回重做的每一圈都是完整的 LLM 调用，token 预算必须全图共享而不是按节点各自为政，否则每个节点都“合规”，加起来整体爆炸。

4. 错误处理

原则先行：先分类，再处置——确定性失败重试是浪费，瞬时失败不重试是白白丢可用性。

  • 节点级重试:可配置(次数、指数退避、哪些异常类型可重试——网络错误可重试，参数错误重试也没用)。
  • 超时:节点级 + 全图级双层。节点级管单步上限(如一次 LLM 调用 30 秒)，全图级管整条链路(如 120 秒)——防止“每个节点都只慢一点，加起来没完没了”。
  • 补偿:已产生副作用的节点(如已扣款)失败时执行补偿动作(退款)——参考 Saga 模式。备份域类比：远端副本写一半失败 → 清理碎片、不留不一致残留。补偿节点自身也要幂等、要可靠可达，别让善后变成新的故障源。
  • 最终失败:状态标记 failed + 保留完整 trace 供排查——每个节点的输入输出摘要、token 消耗、每次分支决策依据。生产事故基本靠这份 trace 定位。
异常类别例子可重试？处置
瞬时网络超时、限流、模型 5xx是指数退避重试(1s→2s→4s)
确定性参数错误、鉴权失败否快速失败 + 告警
语义输出解析失败、拒答、质量不达标部分解析失败可带错误信息重试；质量不达标走条件边打回(进第 3 节的循环防护)

5. 并行执行

  • 条件边返回多个目标 = fan-out 并行执行，全部完成(或任一完成，可配)后再 fan-in。两种汇合模式对应两类业务：多源检索要全量(全部完成)，竞速取快可用任一。
  • 子图支持:节点本身可以是另一张图，实现分层编排——像策略里嵌子策略；子图的执行位置是父图 checkpoint 的一部分，嵌套挂起/恢复天然成立。
  • 人工节点(HITL):执行到审批节点时图挂起，状态入库，人批完再 invoke 恢复——这是和普通工作流引擎最大的差异点之一。挂起时长不可控(几分钟到几天)，checkpoint 必须落在持久存储而非进程内存。

          │
          ├────▶ web_search ─────┐
          ├────▶ code_search ─────┼────▶ merge (fan-in) ───▶ 继续执行
          └────▶ doc_lookup ─────┘
          fan-out:三路并发            汇合策略:全部完成 / 任一完成(可配)

两个值得在面试里点破的设计洞察：① HITL 挂起和崩溃恢复共用同一套机制——都是“load checkpoint,继续执行”，区别只是触发方是人还是进程重启，机制统一是这套设计的优雅之处；② 审批/驳回的结果由人写进 State,再由条件边路由——人本质上是一个“慢但权威的节点”。

6. 上线检查单(加分项)

  • 可观测:每个节点执行留一条 trace——输入输出摘要、token 消耗、时延、分支决策依据；图级 trace_id 串起全程日志。
  • 流式与延迟:交互场景要支持流式输出——generate 的第一个 token 就推给用户，体感 TTFT 不必等全图跑完。
  • 限流与预算:全局 token 预算 + QPS 上限，防止图的循环与并行放大流量，把下游打穿。
  • 幂等与沙箱:副作用节点全部上幂等键；工具调用走白名单，文件/网络进沙箱。
  • 版本与演练:checkpoint 带 schema 版本，新图版本先灰度发布再全量；定期故障注入杀进程验证可恢复性(混沌工程)。
面试官追问
Q:和 Airflow 这类传统工作流引擎有什么区别？
人话：Airflow 是跑夜间批处理的引擎，我们要造的是交互式实时决策引擎；最本质的区别是它的流程提交时就定死，我们的流程是运行中被模型一步步决定的。类比：Airflow 像备份软件的 nightly 批调度——作业挂了明早重跑，没人盯着；Agent 引擎像同步复制——用户就在屏幕另一头等，必须快、必须经得起循环、必须容得下人。技术：① 调度：时间触发 DAG vs 事件驱动、带环的状态机；② 时延：分钟/小时级批窗口 vs 秒级交互 SLA;③ 分支：静态配置 vs 模型输出动态决定；④ HITL 挂起恢复、时间旅行调试，Airflow 里几乎不存在。
Q:状态很大(几 MB 对话历史)每步都存吗？
人话：首次全量、之后增量，大对象放外面、State 里只留指针，去重省不回来的才考虑降频。类比：就是全量 + 增量 + 去重那套：首跑全量，后续节点只存 diff;没变的字段靠内容哈希去重；原始文档“下沉”到对象存储，State 只留引用地址。技术：checkpoint 内容 = 位置 + State diff + 大对象指针；value 哈希去重；Redis 热 / DB 冷双写，滚动全量控制 diff 链长度；对话历史还可做窗口化与摘要压缩，防 State 无界增长。
Q:怎么保证同一张图不被并发执行出问题？
人话：同一线程加锁串行，谁抢到谁执行；不同线程天然隔离。类比：就像同一卷并发写要抢分布式锁：一条备份策略(线程)同时只能有一个在跑的作业，抢到锁才执行、跑完或超时释放；不同策略写不同的卷，互不打扰。技术：以 thread_id 为锁键，Redis SET NX EX 互斥，或把同线程 invoke 收进队列串行消费；checkpoint 带版本号做乐观并发控制；节点幂等做兜底——就算意外双跑，也不产生多余副作用。
Q:崩溃恢复时，怎么避免半途的节点重复执行造成重复扣款？
人话：恢复按“至少一次”来：从最新 checkpoint 之后全部重跑，所以有副作用的节点必须幂等。类比：checkpoint 间隔就是这条工作流的 RPO——切换后重做快照之后的一切；“重放复制任务没关系，只要目标端按 seq 去重”就是节点幂等。技术：checkpoint 记录图位置 + 状态，重启后 load 最新者续跑；扣款、下单类节点用幂等键(唯一约束/去重表)，“做事”与“写 checkpoint”放同一事务边界，消除“扣了钱没记账”的窗口。
Q:图改版了，老 checkpoint 的 schema 不兼容，怎么恢复？
人话：checkpoint 带版本号，恢复时做 schema 迁移；真不兼容的，用原始输入在新图上重放。类比：就是备份格式升级：新版本软件必须能读老备份集，恢复时一键转换；时间旅行重放也等于“任意恢复点一键还原”。技术：checkpoint 存 state 版本号，load 时按版本路由：兼容字段直通、缺失字段补默认、破坏性变更走迁移函数；最坏情况从初始输入在新图 replay(重跑)，幂等键防重复副作用。新图先灰度发布、老 case 回放验证后再全量。
Q:这样的引擎，你怎么测试才能放心上线？
人话：两层：引擎层打桩求确定性，业务层重放真实轨迹。类比：就是备份容灾演练：定期拿生产数据在隔离环境还原跑一遍，真出事时才有底气；时间旅行调试就是演练里的“任意恢复点还原”。技术：依赖注入把 LLM 换成 record-replay 桩，老 case 变回归用例；故障注入中途杀进程验证 checkpoint 恢复(混沌工程)；断言分支决策(条件边该返回什么)而不只断言最终答案；图一改，CI 全量回放。
术语卡
DAG:有向无环图；Airflow 等调度系统的基础，Agent 工作流刻意放宽了无环约束，允许带防护的环。
状态机:状态与迁移规则均为有限的模型，工作流引擎是它的图状扩展(多活跃状态 + 条件边)。
Checkpoint:执行进度快照(状态 + 图位置)，断点恢复、审计回放、时间旅行调试的依据。
Saga 模式:把长事务拆成小步，每步配一个补偿动作，失败时逆序补偿。
Fan-out/Fan-in:并行发散/汇聚，即 fork-join 模型，分布式存储里的 scatter-gather 同款。
HITL:Human-in-the-Loop,机器跑流程、人握最终决策按钮的人工节点。
指数退避:重试间隔按指数增长(1s→2s→4s),给还在挣扎的下游留喘息时间。
WAL(预写日志):先记日志再做事；“checkpoint 落库先于副作用生效”的纪律与它同宗。
