Agent算法 · Q4

如何优化 Agent 的规划效率？

⭐⭐⭐⭐ #Agent#规划#优化 所有公司（通用）
30秒电梯稿

"把 ReAct 从 8 步减到 5 步,核心是减少无效往返,三招:第一,事前规划——Plan-and-Execute,先出一份全局子目标计划再执行,别每走一步才想下一步;第二,步骤合并与并行——把多个可并行的工具调用放进同一步,把『观察→思考→行动』合成一轮,少一次 LLM 往返就少一步;第三,精简观察——工具结果只保留决策需要的字段(截断/摘要),减少"信息过载导致的犹豫",反思只在失败时触发而非每步都反思。目标是步数下降,成功率不降——如果只砍步数丢了成功率,那是伪优化。"

通俗类比

ReAct 像边走边问路的司机:开 500 米停一次、打开地图看一眼、再开 500 米——总共停 8 次(8 步)。优化后像出发前先看全局导航:规划好整条路线(plan),一口气开几段,能同时办的两件事(比如加油 + 买水)顺路一起办了(并行合并);只有真正走错路才停下来重新规划(条件反思)。停的次数从 8 次降到 5 次,路程就短了、人也轻松了。

详细拆解

1. 先搞清 ReAct 为什么步数多(才能对症下药)

  • ReAct 每步都是"观察 → 思考(Thought)→ 行动(Action)→ 再观察"一个完整 LLM 往返,步数 = LLM 调用次数,直接决定延迟和成本。
  • 步数多的三个来源:① 无全局计划,每步都在局部决策,容易绕路;② 串行工具调用,本可并行的也一个接一个;③ 观察信息过载,工具吐一堆无关字段,模型要花额外步骤去"消化"和澄清。
  • 先量化:8 步里哪几步是"必要的动作",哪几步是"消化信息/试错/空转"。优化目标是对准后者的。

2. 事前规划:Plan-and-Execute(把"边想边走"改成"先想好再走")

  • 规划器先分解任务为目标列表,执行器照单执行,省掉"每步重新决策下一步"的往返。
  • 动态重规划:计划不是死的,执行中发现偏差(某步失败、环境变化)才重新规划,而不是每步都反思。

3. 步骤合并与并行(一箭多雕)

  • 并行工具调用:一次返回多个 function_call("同时查订单 + 查物流"),把 N 个串行步骤压成 1 步。前提是工具间无依赖;有依赖的用"DAG 依赖图"先算可并行层。
  • 动作聚合:把"连续的小动作"合并成一个复合动作,或让模型一次规划出"接下来 k 个动作"批量执行。
  • 减少元步骤:把纯"确认/复述/我已收到"这类不产生信息增量的步骤砍掉,用提示词引导模型"结果拿到了就直接下一步"。

4. 精简观察(治"信息过载")

  • 工具返回往往是完整 JSON/整页 HTML,几万字符;模型被噪音淹没会多花步骤去定位关键字段,甚至看漏。
  • 做法:① 截断 + 字段白名单(只回传决策需要的字段);② 工具结果摘要(LLM 先压缩再进上下文);③ 结构化展示(表格/列表)降低理解成本。观察干净了,模型"想一步就够"。

5. 条件反思(不每步都反思)

  • 反思(Reflexion)很贵,每步都反思会把步数翻倍;改为事件触发:工具报错、结果明显异常、连续两步无进展、最终答案质量自检不过——才触发一次反思。
  • 自我纠错只解决"真出错了",不解决"本来没出错还要停下来自省",后者是步数虚高的常见原因。

6. 模型侧与评估

  • 提示词引导"果断决策":明确"不确定时用已有信息给最优答案 + 说明不确定性",减少反复试探;可选地对规划器做微调,让"出计划"更准更少重规划。
  • 评估三件套:平均步数(效率)、任务成功率(不能掉)、总 token/成本与端到端延迟(步数省了但每步变贵也可能亏)。三者一起看,单独报"步数降了"没有意义。
面试官追问
Q:减少步数会不会牺牲成功率?怎么保证?
会有一组 trade-off,所以要"分场景优化 + 双指标验收":对简单、流程固定的任务激进合并(收益大、风险小);对高风险任务(下单、写库)保留必要的确认步骤,不为了省步数而跳过安全动作。上线用 AB 实验同时看步数和成功率,成功率掉超阈值就回滚。砍掉的是"无效步骤",不是"关键步骤"。
Q:Plan 一开始就错了,怎么办?
Plan-and-Execute 不是"计划一次执行到底",而是"计划 + 偏差检测 + 重规划":执行中监控子目标是否达成、结果是否与预期一致,偏差大到阈值就只重规划剩余部分(不是全部推倒)。比 ReAct 省步数,又保留了对错误的响应能力。
Q:并行工具调用有依赖关系怎么办?
先做静态依赖分析:工具间是否有数据依赖(输出喂输入)。无依赖的同一批并行发;有依赖的按依赖 DAG 分层,层内并行、层间串行。同时让规划器显式输出"哪些可并行",把依赖判断交给模型而不是盲发。
Q:步数降了但每步 token 暴涨,怎么权衡?
看总成本 + 总延迟而不是只看步数:并行合并会让单步 token 变大,但只要总 token 和端到端延迟下降就是赚。真正要优化的是"LLM 往返次数 × 每次成本"的总和。汇报时用"端到端延迟 + 总 token"做主指标,步数做辅助指标。
术语卡
ReAct:Reason+Act,交替"思考-行动-观察"的推理范式。
Plan-and-Execute:先出全局计划再执行的规划范式。
Reflexion:让 Agent 基于反馈反思并改进下一次尝试。
并行工具调用:一次 LLM 往返同时发起多个无依赖工具。
条件反思:只在出错/无进展时反思,而非每步反思。
