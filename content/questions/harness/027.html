Agent算法 · Q4

如何优化 Agent 的规划效率？

⭐⭐⭐⭐ #Agent#规划#优化 所有公司（通用）
先说人话:这题问的是:Agent 干一件事要来回调 8 次大模型,怎么压到 5 次还不把事办砸。面试官爱考它,因为这是「真优化过还是背名词」的分水岭——只会背 Plan-and-Execute 的,追问一句「哪几步最该省」就露馅;真干过的人先讲测量归因再谈手段,这个顺序反不了。
30秒电梯稿

"这题的靶心:步数 = LLM 往返次数,把 ReAct 的 8 步压到 5 步,本质是砍掉无效往返,且成功率不能掉。三招:①事前规划——用 Plan-and-Execute 先出全局子目标计划再照单执行,别每走一步才现想下一步;②合并与并行——无依赖的工具调用放进同一次往返批量发出,顺手砍掉『复述确认』这类零信息步骤;③精简观察——工具结果只回传决策要用的字段,别让模型被几万字符淹没后绕路。反思改成事件触发:出错才反思,不每步自省。验收看步数、成功率、总 token 与端到端延迟三件套——只报步数下降,是伪优化。"

通俗类比

ReAct 的步数(用分布式系统里的同步 RPC 往返想):Agent 每走一步,就是一次完整的 LLM 调用——请求发出去、模型生成完、结果送回来,和一次同步 RPC 没有本质区别;8 步 = 8 次串行往返,端到端延迟 ≈ 步数 × 单步耗时,还直接制造长尾请求。哪里像:都是串行 RTT 堆出来的延迟,解法也同款——批处理、并行、减少往返。哪里不像:RPC 的响应是确定性的,LLM 每次返回的「思考」带随机性;而且单次 LLM 调用的大头是生成内容的秒级耗时,不是毫秒级网络 RTT——省一步省的是秒,不是毫秒。

Plan-and-Execute(用 SQL 查询优化器想):数据库收到 SQL 不是边扫边想下一步,而是先由优化器生成完整执行计划(先过滤还是先 join、走不走索引),再交给执行器照单跑。Plan-and-Execute 就是给 Agent 装了个「优化器」:先让 LLM 把任务拆成子目标列表,执行器依次或并行执行。哪里像:都是把「逐条决策」换成「一次出计划」,省掉中间的决策往返;计划错了都能重新规划。哪里不像:SQL 优化器有代价模型和统计信息撑腰,LLM 规划器是凭语言先验在猜,计划错误率高得多——所以必须配「偏差检测 + 重规划」兜底,这是它和数据库最大的差别。

并行工具调用(用备份系统的多流并发想):备份软件从不串行地「备完一个 LUN 再问调度器下一步」,而是按依赖分层:互不依赖的备份流并发拉起,有硬依赖的(先快照、再复制、后校验)按 DAG 排序。Agent 同理:一次 LLM 往返同时发出多个无依赖的 function_call(模型结构化输出的「调哪个工具、传什么参数」指令,比如同时查订单 + 查物流),N 个串行步骤压成 1 步。哪里像:都是「依赖 DAG 拓扑分层,层内并行、层间串行」。哪里不像:备份 DAG 是管理员显式声明的,Agent 的工具依赖是隐式的、要靠模型推断——依赖判错还硬并行,会拿到空结果甚至脏数据。

精简观察(用日志采集的字段裁剪想):没人会把全量 debug 日志原样塞进监控面板——按级别过滤、只采关键字段、聚合后再上报。工具返回也一样:整页 JSON/HTML 几万字符进上下文,模型要花额外步骤去「消化」,甚至看漏关键字段。哪里像:都是「生产端裁剪,消费端只看决策要用的信息」,省的是下游的处理成本。哪里不像:日志裁剪规则是人写的、稳定的;工具结果结构千差万别,裁剪只能靠字段白名单 + 摘要,存在「裁掉了后面才用得上的字段」的风险,白名单要随任务演化维护。

条件反思(用容灾的事件触发切换想):容灾系统不会每秒问一遍「要不要切备机房」,而是健康检查出问题、达到切换阈值才触发动作。条件反思同理:工具报错、结果明显异常、连续两步无进展,才触发一次反思;每步都自省,等于把步数翻倍。哪里像:都是事件驱动代替轮询,把昂贵动作留给真正需要的时刻。哪里不像:容灾切换是确定性规则触发,Agent 的「异常判断」本身也是模型做的——会误报(白反思一次)也会漏报(错了没发现),所以触发条件要偏保守。

详细拆解

1. 先搞清 ReAct 为什么步数多(才能对症下药)

  • ReAct 每步都是"观察 → 思考(Thought)→ 行动(Action)→ 再观察"一个完整 LLM 往返,步数 = LLM 调用次数,直接决定延迟和成本。
  • 再补两个工程事实,你就知道省一步值多少钱:① 单次往返的大头是输出 token 的生成(逐 token 解码,输出越长越慢),网络 RTT 反而是小头——省一步省的是秒,不是毫秒;② 上下文随步数越滚越长,后面每步都比前一步更贵,即使推理侧有 KV Cache 前缀复用,新增部分照样全额生成计费。步数堆出来的延迟,正是长尾请求的主要来源。
  • 步数多的三个来源:① 无全局计划,每步都在局部决策,容易绕路;② 串行工具调用,本可并行的也一个接一个;③ 观察信息过载,工具吐一堆无关字段,模型要花额外步骤去"消化"和澄清。
  • 先量化:8 步里哪几步是"必要的动作",哪几步是"消化信息/试错/空转"。优化目标是对准后者的。

抽象归因落不了地,拿一条典型轨迹演示怎么数——任务:用户问「订单 A-123 为什么还没到?」

原始 ReAct 轨迹(8 次往返):
──────────────────────────────────────────────────────
步1 [取数] 查订单状态    → 观察: 全量 JSON 约 8000 字符  ★ 过载从这开始
步2 [重复] 再查明细一遍  → 观察: 还是那坨 JSON          ★ 步1没看清(过载的代价)
步3 [取数] 查物流轨迹    → 观察: 运输中,预计后天到      ★ 与步4互不依赖,本可并行
步4 [取数] 查收货地址    → 观察: 地址正常               ★ 串行干等了一整轮
步5 [试探] 查目的地天气  → 观察: 晴                     ★ 犹豫「要不要提延误风险」
步6 [空转] 复述「信息已齐,现在组织答案」→ 观察: —      ★ 零信息步骤
步7 [生成] 起草回复
步8 [自检] 全量自我检查一遍再输出                       ★ 每步反思的代价
──────────────────────────────────────────────────────
归因: 真正干活的只有 4 步(1/3/4/7), 另外 4 步全是可压缩的浪费
步骤类型占哪些步病因对症手段(对应下文)
必要取数/生成步 1/3/4/7真活儿,不能省保留,但并行合并(第 3 节)
过载引发的重复查询步 2观察太脏,没看清精简观察(第 4 节)
犹豫试探步 5决策不果断提示词引导果断决策(第 6 节)
零信息复述步 6元步骤废话砍元步骤(第 3 节)
每步自检步 8反思滥用条件反思(第 5 节)

归因清楚,8 → 5 的路线图自然浮出来:砍 4 步浪费,花 1 步买全局规划。

优化后轨迹(5 轮, LLM 往返 8 → 5):
──────────────────────────────────────────────────────
新步1 [规划]   Plan: P1=并行查(订单|物流|地址) → P2=综合判断 → P3=回复
新步2 [并行批] 一次往返发出 3 个 function_call(白名单观察,各约 200 字符)
新步3 [综合]   执行器汇总观察 + 偏差校验(偏差大才重规划剩余子目标)
新步4 [生成]   综合判断 + 起草回复
新步5 [输出]   质量自检(事件触发,不过关才重写)→ 输出最终答案
──────────────────────────────────────────────────────
省账: 砍 4 步浪费(步2/5/6/8), 买 1 步全局规划(新步1), 8 - 4 + 1 = 5

2. 事前规划:Plan-and-Execute(把"边想边走"改成"先想好再走")

  • 规划器先分解任务为目标列表,执行器照单执行,省掉"每步重新决策下一步"的往返——上面例子里,原轨迹的步 6「复述 + 决定下一步」整段消失。
  • 动态重规划:计划不是死的,执行中发现偏差(某步失败、环境变化)才重新规划,而不是每步都反思。

三个工程细节,说出来就是加分项:

  • 延迟要算总账:事前规划省的是「重新决策」的往返,并行省的是「工具排队」的等待,两笔账合起来看:
端到端延迟 ≈ Σ(LLM 往返耗时) + Σ(工具执行耗时)

ReAct 8 步:   8 × T_llm + (t订单 + t明细 + t物流 + t地址 + t天气)   ← 工具也在串行排队
优化后 5 步:  5 × T_llm + max(t订单, t物流, t地址)                  ← 并行批内取最长
  • 规划器可以换小模型:出计划是结构化输出(一份子目标列表),不非要旗舰模型;贵模型留给执行与综合。控制面轻、数据面重——和系统设计里控制面/数据面分离是同一个思路。
  • 激进变体 ReWOO(Reasoning without Observation):规划时就把所有工具调用与参数定死,执行完一次性汇总,不再每步把观察喂回模型重新想——往返压到理论下限;代价是中途没有纠偏机会,更适合流程稳定的任务。

3. 步骤合并与并行(一箭多雕)

  • 并行工具调用:一次返回多个 function_call("同时查订单 + 查物流"),把 N 个串行步骤压成 1 步。前提是工具间无依赖;有依赖的用"DAG 依赖图"先算可并行层。
  • 动作聚合:把"连续的小动作"合并成一个复合动作,或让模型一次规划出"接下来 k 个动作"批量执行。
  • 减少元步骤:把纯"确认/复述/我已收到"这类不产生信息增量的步骤砍掉,用提示词引导模型"结果拿到了就直接下一步"。

「依赖判断」画出来,就是备份编排里天天见的那张图:

串行(ReAct 默认):  查订单 → 查物流 → 查地址 → 综合判断
                     4 次 LLM 往返, 工具耗时 = t1 + t2 + t3

DAG 分层并行:       层1 [查订单 | 查物流 | 查地址]    ← 互不依赖,同一批发出
                     层2  综合判断(依赖层1 全部结果)
                     1 次 LLM 往返(批量发起), 工具耗时 = max(t1, t2, t3)
方案LLM 往返工具耗时主要风险
纯串行(ReAct 默认)N 次Σti(逐个累加)慢;但每步都能纠偏
DAG 分层并行按层分批(常 1 批)每批 max(ti)依赖判错 → 空结果/脏数据
k 步批量规划约 N/k 次视依赖而定环境中途变化,后 k 步作废

还有个容易被忽略的细节:批内失败要隔离——并行批里某个工具失败,只单独重试或降级那一个,同批其余结果照常使用,就像备份集群里一条流失败不连坐其他流;若一失败就整批重发,浪费的 token 会把省下的步数又吃回去。

4. 精简观察(治"信息过载")

  • 工具返回往往是完整 JSON/整页 HTML,几万字符;模型被噪音淹没会多花步骤去定位关键字段,甚至看漏。
  • 做法:① 截断 + 字段白名单(只回传决策需要的字段);② 工具结果摘要(LLM 先压缩再进上下文);③ 结构化展示(表格/列表)降低理解成本。观察干净了,模型"想一步就够"。

白名单前后对比,感受一下信息密度的差别:

同一个「查订单」工具的返回:

原始(全量 JSON, 约 8000 字符):
  {"order_id":"A-123","status":"shipped","eta":"03-05",
   "items":[ 37 件商品的全量快照 ],"coupons":{...},"change_log":[...], ...}

字段白名单后(约 200 字符):
  {"status":"shipped","eta":"03-05","delay_reason":null}

  ↑ 只保留「要不要提示延误」这一决策真正用得上的 3 个字段
  • 按观察长度分级处理:短结果直接白名单(零额外成本),长结果(整页 HTML、大结果集)才值得花一次 LLM 摘要——按数据温度选介质,还是冷热分层那套思路。
  • 白名单有维护成本:任务变了、字段需求变了,清单要跟着改,否则只是把「模型消化」换成了「人肉消化」;拿不准的字段宁可保留,删错了比删少了贵。

5. 条件反思(不每步都反思)

  • 反思(Reflexion)很贵,每步都反思会把步数翻倍;改为事件触发:工具报错、结果明显异常、连续两步无进展、最终答案质量自检不过——才触发一次反思。
  • 自我纠错只解决"真出错了",不解决"本来没出错还要停下来自省",后者是步数虚高的常见原因。

触发条件做成一张表,你会发现全是分布式系统的老熟人:

触发事件触发后的动作分布式系统里的对应物
工具报错 / 超时反思原因,局部重试或换工具RPC 失败重试、熔断
结果明显异常(空值/越界)校验失败,补查或换参数重查健康检查异常告警
连续 2 步无进展触发重规划,换一条路线死锁检测、超时重启
最终答案自检不过重写答案(带重试上限)上线前验收门禁
  • 每次反思 = 额外一次 LLM 往返,触发条件宁缺毋滥;并给反思设重试上限,防止「反思失败 → 再反思」的循环把步数炸回去。

6. 模型侧与评估

  • 提示词引导"果断决策":明确"不确定时用已有信息给最优答案 + 说明不确定性",减少反复试探;可选地对规划器做微调,让"出计划"更准更少重规划。
  • 评估三件套:平均步数(效率)、任务成功率(不能掉)、总 token/成本与端到端延迟(步数省了但每步变贵也可能亏)。三者一起看,单独报"步数降了"没有意义。

三件套落成一张验收表:

指标量什么合格线
平均步数(含 P95/P50 分布)LLM 往返次数,效率下降,且不是只把简单任务做快
任务成功率答案/动作做没做对不降,这是红线
总 token / 成本往返次数 × 单次开销的总账总量降才算真省
端到端延迟 P99用户体感,对齐 SLA长尾请求明显收敛
  • 上线走灰度发布 + AB 实验:双指标(步数 × 成功率)同时验收,任一越线回滚,别裸切全量。
  • 体感和步数是两笔账:流式输出能让用户更早看到第一个字(改善 TTFT 体感),但一次 LLM 也没少调;汇报时把「体感优化」和「步数优化」分开说,别混着邀功。

收束一句:先归因(哪几步是浪费)、再合并(并行 + 砍元步骤)、观察瘦身(白名单)、反思改事件触发、验收看三件套——步数是过程指标,成功率和总账才是结果。

面试官追问
Q:减少步数会不会牺牲成功率?怎么保证?
人话:有这个风险,所以验收永远是双指标:步数降、成功率不掉,任一越线就回滚。类比:备份窗口优化同理——全量改增�能省一大截时间,但你不会不看恢复成功率就切生产;先在灰度环境跑恢复演练,达标再放量。技术:分场景施策:流程固定的简单任务激进合并;高风险动作(下单、写库、删数据)保留必要确认步骤——砍的是零信息步骤,不是安全步骤。上线走灰度发布 + AB 实验,双指标一起盯,成功率跌幅超阈值立即回滚。
Q:Plan 一开始就错了,怎么办?
人话:计划本来就不指望一次全对,靠「执行 + 偏差检测 + 重规划」闭环兜底:走偏了只重排剩余步骤,不推倒重来。类比:容灾预案也这样——演练或真实故障里发现某步走不通,只修订受影响的环节,不会把整份预案作废重写。技术:每个子目标执行完做校验:结果与预期比对、下游依赖是否满足;偏差超阈值触发重规划,只重新生成剩余子目标、保留已完成成果。比 ReAct 省往返,又没丢掉对错误的响应能力。
Q:并行工具调用有依赖关系怎么办?
人话:先分清哪些调用互相依赖、哪些互不相干:不相干的一批并发,有依赖的排好先后。类比:备份编排的老本行——先快照、再复制、后校验是硬依赖,而十个卷的备份互不依赖就并发拉流;本质是依赖 DAG 拓扑分层,层内并行、层间串行。技术:对工具做静态依赖分析(某工具输出是否喂另一个的输入),建 DAG 后按拓扑序分批发放;同时让规划器出计划时显式标注「哪些子目标可并行」,把依赖判断前置给模型,执行器照批执行,避免盲并行拿到空结果。
Q:步数降了但每步 token 暴涨,怎么权衡?
人话:算总账,不算单步账:总 token 和端到端延迟都降才是赚,只盯着步数会自我感动。类比:小 IO 合并成大 IO——单次请求变大了,但往返次数和总开销下降,吞吐反而上去;衡量的是「次数 × 单次成本」这个乘积。技术:主指标定为端到端延迟 P99 + 总 token 成本,步数只做过程指标。若单步膨胀到抵消收益,就把并行批拆小、回退部分合并,或对并行结果先做字段白名单压缩再进上下文。
Q:你怎么定位「这 8 步里哪几步是浪费的」?
人话:把每步轨迹日志拉出来打标签:取数、重复、试探、空转、自检各占几步,数完再动手砍。类比:性能优化先 profile 的老规矩——先看哪个接口吃掉了 P99、哪段日志在刷屏,再决定改哪里;跳过测量直接调参,是新手最典型的翻车姿势。技术:给执行 trace 加三类标注:动作类型(取数/确认/试探/反思)、观察长度、步骤间信息依赖。统计「零信息步骤」和「观察过载引发的重复查询」占比——通常这两类就是可压缩的大头,再分别对应合并、白名单、条件反思三招。
术语卡
ReAct:Reason+Act,让 LLM 交替「思考-行动-观察」的推理范式,每轮烧掉一次 LLM 往返。
Plan-and-Execute:先由规划器生成全局子目标计划、再交执行器照单执行的规划范式(学术近亲是 Plan-and-Solve 论文)。
Reflexion:让 Agent 基于失败反馈生成自我反思笔记、改进下一次尝试的机制。
并行工具调用:一次 LLM 往返同时发起多个无依赖的 function_call,把 N 步压成 1 步。
条件反思:只在出错、异常或无进展等事件触发时反思,而非每步自省。
DAG:有向无环图,刻画任务依赖、指导并行分层的老牌数据结构。
ReWOO:Reasoning without Observation,规划时定死全部调用、执行完一次性汇总的省步数变体。
