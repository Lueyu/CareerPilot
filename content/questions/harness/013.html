Agent核心 · Q18

如何让多个 agent 协同工作的？举个具体的协同机制例子。

⭐⭐⭐ #Multi-Agent#协作机制 字节 / 阿里(高频)
30秒电梯稿

"多 Agent 协同的本质是任务分解 + 结构化通信 + 状态共享 + 编排控制。常见四种机制:① Supervisor 编排——主管拆任务、分派、汇总;② 流水线——检索→分析→生成串行接力;③ 黑板/共享状态——大家读写同一个共享工作区;④ 群聊协商——AutoGen 式自由对话。我最常用 Supervisor:主管做意图理解和任务拆解,把"任务卡片"发给专业 Agent,子 Agent 各带最小工具集执行,结果写回共享状态,主管汇总。选型关键:流程可预测用编排,探索型任务才用自由协商。"

通俗类比

像项目组做方案:项目经理(Supervisor)接需求后拆成调研、设计、开发三块,发给对应同事(专业 Agent);大家把成果放进共享文件夹(共享状态);项目经理定期汇总、必要时开会对齐。另一种像流水线工厂:上一个工位做完传给下一个。自由群聊则像头脑风暴会:大家七嘴八舌讨论出结果——灵活但难控制、容易跑偏。

详细拆解

1. 协同要解决的三个问题

  • 分工:谁做什么——任务如何切分、路由给哪个 Agent。
  • 通信:怎么交流——直接对话还是共享状态,消息格式是什么。
  • 收敛:怎么结束——谁拍板、冲突怎么解决、如何防止无限循环。

2. 四种机制对比

机制控制点可控性适用场景
Supervisor 编排中心主管高流程清晰、需审计
流水线固定顺序最高步骤确定的批处理
黑板/共享状态共享工作区中多专家并行贡献
群聊协商无中心低探索、开放式问题

3. 具体例子:Supervisor 模式(电商智能客服)

4. 通信与状态(协同的"协议层")

  • 结构化消息:不用自然语言互聊(易歧义、难解析),而是传"任务卡片"这种结构化对象(角色、目标、已知字段、结果槽位),可靠且好调试。
  • 共享状态:会话状态放 Redis/内存,Agent 无状态,读写共享工作区完成交接——避免"两个 Agent 各记一份、数据打架"。
  • 上下文按需传递:每个子 Agent 只拿自己需要的字段,不塞整段历史,token 省、也少幻觉。

5. 收敛与冲突解决

  • 限定最大调度轮次和 token 预算,超了强制收敛(输出当前最优 + 转人工)。
  • 冲突由 Supervisor 仲裁(投票、置信度加权、规则兜底),而不是让 Agent 自己争。
  • 路由职责在 Supervisor,子 Agent 只执行不转发——从机制上杜绝互相踢皮球。
面试官追问
Q:什么时候用编排,什么时候用自由对话协商?
看任务的结构化程度和可逆性:流程可预测、有明确步骤、需要审计的(客服、工单、合规),用编排——可控、可测、可回放;探索型、开放式、路径事先未知的(头脑风暴、研究、代码架构讨论),用自由协商——灵活但代价是成本高、结果不稳定。实践铁律:能编排就不自由对话,自由对话先当"最后手段"。能主动说出这个取舍是加分点。
Q:多个 Agent 怎么避免互相踢皮球?
三点:① 路由权收在 Supervisor,子 Agent 无权说"这不归我管"再转手,只执行分配给它的任务;② 每个 Agent 职责边界清晰、不重叠,重叠区由 Supervisor 显式仲裁;③ 设兜底——Supervisor 连续 N 轮没进展、置信度低,就反问用户或转人工,不让 Agent 之间空转。核心是收敛责任落实到某一个节点。
Q:协同里共享状态的一致性怎么保证?
把状态做成"单一事实源"(single source of truth):统一放 Redis/DB,Agent 只读写它、不各自缓存;写操作加版本号或锁避免并发覆盖;关键状态(如退款单)走状态机,每次变更落库可审计。多 Agent 同时写同一字段时,用 reducer(合并策略,如追加、覆盖、投票)显式定义冲突如何收敛,而不是让写入顺序随机决定结果。
术语卡
Supervisor 模式:中心主管统一调度子 Agent。
黑板模式:多 Agent 读写共享工作区协作。
流水线:任务按固定顺序在 Agent 间接力。
结构化消息:用对象而非自然语言在 Agent 间传参。
共享状态:协作各方共用的单一事实源。
