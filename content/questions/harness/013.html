Agent核心 · Q18

如何让多个 agent 协同工作的？举个具体的协同机制例子。

⭐⭐⭐ #Multi-Agent#协作机制 字节 / 阿里(高频)
先说人话:这题问的是:一个 Agent 扛不动的活,怎么拆给一群 Agent 还不打架。面试官爱考,因为它专筛「看过 demo」和「上过生产」——追问一句「两个 Agent 同时写同一份状态怎么办」,只答「加个锁」的,说明没看透协同的本质就是分布式协调。你做备份编排那套「主控调度 + 无状态 worker + 元数据单一事实源」平移过来,就是高分答案。
30秒电梯稿

"多 Agent 协同的本质是任务分解 + 结构化通信 + 状态共享 + 编排控制。把复杂任务按领域拆开,分给带不同工具的专家 Agent,用结构化消息(任务卡片)而不是自然语言互聊,结果写回共享状态,由一个控制点负责调度与收敛。常见四种机制:① Supervisor 编排——主管拆任务、发任务卡、收结果、汇总;② 流水线——检索→分析→生成串行接力;③ 黑板/共享状态——大家读写同一个共享工作区;④ 群聊协商——AutoGen 式自由对话。我最常用 Supervisor:主管做意图理解和任务拆解,子 Agent 各带最小工具集执行,结果写回共享状态,主管汇总。选型铁律:流程可预测用编排,探索型任务才用自由协商——能编排就不群聊。"

通俗类比

先定个调:多 Agent 协同 ≈ 你天天在做的分布式协调。一个多智能体(Multi-Agent)系统要解决的三件事——谁干活、怎么通信、怎么收尾——恰好对应分布式系统的三大老问题:任务分片、消息传递 vs 共享内存、一致性与终止检测。所以下面每个机制,你都能在舒适区里找到原型。

Supervisor 编排(用备份软件的主控调度器想):主控节点接了备份策略,拆成快照、去重、复制、校验几个作业,派给无状态 worker,结果统一写回元数据库——Supervisor 编排(LangGraph 里的经典模式)就是这个结构。哪里像:主管握全局视图、子 Agent 无状态可水平扩、状态收敛到单一事实源,一模一样。哪里不像:传统 worker 是确定性代码,Agent 是"会理解任务、但可能理解错"的模型——它会幻觉、会自作主张,所以要多加轮次预算和输出校验,这是传统调度器不需要的防线。

流水线(用备份数据管道想):客户端→介质服务器→去重→落盘→校验,每个工位只干一件事,上下游靠固定格式交接——流水线同理:检索 Agent 取材、分析 Agent 提炼、写作 Agent 成稿。哪里像:顺序固定、职责单一、可控性最高,坏了就地停。哪里不像:管道传的是字节流,对错是确定的;Agent 间传的是带语义的对象,"理解错了"比"传错了"更隐蔽,所以每一环的输出要过 schema 校验。

黑板/共享状态(用共享存储想):多个专家进程并行读写同一块"黑板"——黑板模式是上世纪专家系统的遗产,如今变成共享 state 对象:任务目标、已确认事实、结论槽位都写在上面,谁有进展谁更新。哪里像:生产者消费者解耦、并行贡献、互不阻塞。哪里不像:写共享存储的是确定性代码,写黑板的是会出错的模型,同一个槽位可能被写成两个答案,所以必须显式定义合并策略,不能指望写入天然有序。

群聊协商(用无中心对等节点的 gossip 想):AutoGen 式多 Agent 自由对话,没有主管,靠互相说服收敛。哪里像:像 gossip——去中心、灵活、能碰撞出新东西。哪里不像:gossip 收敛的是确定性状态,群聊收敛的是"观点",可能越聊越偏、token 烧得飞快,所以只配当探索型任务的最后手段,而且必须挂轮数上限。

详细拆解

1. 先把问题翻译成分布式语言:协同要解决的三个问题

你做分布式出身,这题可以整段"降维"理解——多 Agent 协同 = 一群不可靠的智能进程 + 一套协调机制。三个核心问题:

  • 分工(= 任务分片):谁做什么——任务如何切分、路由给哪个 Agent。切法和分库分表一个逻辑:按领域垂直切(订单/物流/售后),每个 Agent 只带本领域的最小工具集——工具表越长,模型选错工具的概率越高,这是"单一职责"在 LLM 上的版本。
  • 通信(= 消息传递 vs 共享内存):怎么交流——直接对话还是共享状态,消息格式是什么。分布式系统的两条祖传路线,Agent 世界一条没少:对应"任务卡片"(像 RPC 请求体)和"黑板"(像共享存储)。
  • 收敛(= 终止检测 + 一致性):怎么结束——谁拍板、冲突怎么解决、如何防止无限循环。Agent 比普通进程多一个坑:它不崩溃挂掉,但会"体面地空转",所以轮次预算(像 TTL)和仲裁节点是刚需。

还有一个差异要刻在脑子里:传统 worker 的故障是诚实的——进程挂了、心跳断了,监控立刻知道;Agent 的故障是自信的——它不挂,它一本正经地返回一个编造的结果。所以 Agent 协同除了心跳式健康检查,还必须多一层传统分布式没有的防线:输出校验(schema 断言、关键结果抽查、置信度阈值)。能把这一点讲出来,面试层次感立刻不一样。

2. 四种机制对比(每种都能在舒适区找到原型)

机制控制点可控性适用场景像分布式里的
Supervisor 编排中心主管高流程清晰、需审计Master-Worker 调度(备份主控)
流水线固定顺序最高步骤确定的批处理ETL / 备份数据管道
黑板/共享状态共享工作区中多专家并行贡献共享存储 + 多进程协作
群聊协商无中心低探索、开放式问题无中心 gossip 协商

逐个过一遍:

① Supervisor 编排:主管统一拆解、分派、汇总,子 Agent 只执行。可控性高的代价是主管是单点——所以主管本身要有兜底(转人工)和降级路径(主管不可用时退回单 Agent 直答),这就是容灾思维直接平移。

② 流水线:固定顺序接力,最像你日常的备份管道(快照→传输→去重→落盘→校验),比如 RAG 三段式:

[检索 Agent] ──→ [分析 Agent] ──→ [写作 Agent] ──→ 交付
  取材:chunk 列表     提炼:结构化要点     成稿:自然语言答案

· 顺序固定,任何一环失败整条停摆(可控性最高,也最难并行)
· 每一环输出过 schema 校验:坏数据就地报错,不往下游传

③ 黑板/共享状态:没有主管传话,大家读写同一块黑板,谁先算完谁先写:

            ┌────────────────────────────────┐
            │        共享黑板(共享状态)          │
            │   任务目标 │ 已确认事实 │ 结论槽位   │
            └────▲──────────▲──────────▲─────┘
                 │读/写      │读/写      │读/写
           [订单 Agent]  [物流 Agent]  [风控 Agent]

· 并行贡献、互不阻塞,天然适合多专家同时上
· 隐患:同一槽位可能被写出两个答案 → 必须定义合并策略

④ 群聊协商:AutoGen 式自由对话,无固定流程,靠对话收敛:

   [策略 Agent] ⇄ [审校 Agent]
        ↕              ↕
   [检索 Agent] ⇄ [执行 Agent]

· 没有主管,谁想发言谁发言,靠互相说服收敛
· 终止条件:有人宣布"达成一致",或轮数/token 上限触顶(必须有)

一个实践细节:AutoGen 的群聊其实内嵌了一个负责"选下一个人发言"的 manager——纯无中心在真实系统里几乎不存在,最后总得有人拿槌子。这也是"能编排就不群聊"的又一证据。

3. 具体例子:Supervisor 模式(电商智能客服)

对着图走一遍流程(从上往下):

  • ① 用户一句"我买的还没到"进来——自然语言,无结构,没法直接路由;
  • ② Supervisor 做意图理解,判定是"查物流",再拆两步:先查订单拿运单号,再查轨迹;
  • ③ 把任务卡片发给订单 Agent——只带它需要的字段(订单号、用户 ID),不带整段聊天历史;如果意图是退款,第三张卡会发给售后 Agent——路由表按意图选人,子 Agent 之间永远不互相调用;
  • ④ 订单 Agent 调订单 API,结果写回共享状态(图最底下那个 Redis),不直接喊话别人;
  • ⑤ Supervisor 看到状态更新,再发第二张卡给物流 Agent;
  • ⑥ 物流 Agent 查轨迹、写回状态;
  • ⑦ Supervisor 汇总两个结果,生成自然语言回复;
  • ⑧ 全程兜底:置信度低或连续无进展,走右边那条"转人工"通道——协同系统的容灾出口。

把上面的过程画成时序图,一眼看懂谁在什么时候说话:

用户               Supervisor                订单 Agent       物流 Agent
 │                     │                       │                │
 │── "我买的还没到" ──→ │                       │                │
 │                     │ ① 意图: 查物流         │                │
 │                     │ ② 拆解: 查订单→查轨迹  │                │
 │                     │── ③ 任务卡{order_id} → │                │
 │                     │←── ④ 运单号+收货城市 ──│                │
 │                     │── ⑤ 任务卡{运单号} ───────────────────→ │
 │                     │←── ⑥ 轨迹: 已到同城 ────────────────────│
 │                     │ ⑦ 汇总生成回复          │                │
 │←─ "已到同城,预计今天送达" ─│                  │                │
 │                     │                                       │
 │   状态全程只写 Redis;Agent 本体无状态,可随时重启/扩容

任务卡片长什么样?本质上是一张"RPC 请求体":

{
  "task_id": "T-1024",                    // 全局唯一: 幂等键 + 追踪键
  "from": "supervisor",
  "to": "order_agent",
  "goal": "查询订单 O-8899 的运单号和收货城市",
  "context": {"order_id": "O-8899", "user_id": "U-3312"},  // 按需传字段
  "result_slot": {"waybill_no": null, "city": null},       // 槽位: 结果填这里
  "budget": {"max_tool_calls": 3, "max_rounds": 2}         // 轮次预算
}

from/to 是路由头,context 是请求参数,result_slot 是响应结构,budget 是超时与重试上限。子 Agent 拿到卡只需要:理解 goal → 调工具 → 填满槽位 → 写回状态。职责单一到想跑偏都难。

4. 通信与状态(协同的"协议层")

  • 结构化消息:不用自然语言互聊(易歧义、难解析、token 还贵),而是传"任务卡片"这种结构化对象(角色、目标、已知字段、结果槽位),可靠且好调试——就像服务间通信用 Protobuf 而不是发邮件;消息体可过 JSON Schema 校验。这套"只靠消息、不共享内存"的哲学,和 Actor 模型一脉相承。
  • 共享状态:会话状态放 Redis/内存,Agent 无状态,读写共享工作区完成交接——避免"两个 Agent 各记一份、数据打架"。这就是你熟悉的计算存储分离:worker 随便杀、随便扩,因为状态在"外面"。进阶做法:给关键状态做 checkpoint 落库,流程可从任意断点恢复——等于给 Agent 流程做"备份 + 断点续传",LangGraph 的 checkpointing 就是这个思路。并发写同一字段时用版本号兜底(乐观并发控制)。
  • 上下文按需传递:每个子 Agent 只拿自己需要的字段,不塞整段历史——RPC 只传参数、不传整个内存镜像,同理。token 省是其次,更关键的是无关上下文是幻觉的主要来源之一:给订单 Agent 看三页聊天记录,它就开始"发挥"了。

5. 收敛与冲突解决(协同的"治理层")

  • 限定最大调度轮次和 token 预算,超了强制收敛(输出当前最优 + 转人工)——就是给任务挂 TTL 加 watchdog:LLM 不会崩溃,但会体面地空转,必须有人能掐表。
  • 冲突由 Supervisor 仲裁(投票、置信度加权、规则兜底),而不是让 Agent 自己争——多个专家给出矛盾结论时,由控制点一次性收口,类似主节点裁决,不开现场辩论会。
  • 路由职责在 Supervisor,子 Agent 只执行不转发——从机制上杜绝互相踢皮球,等价于分布式里靠 TTL 递减防转发环。

6. 落地排坑清单(背下来,追问必中)

症状根因解药(分布式老朋友)
两个 Agent 互相转派,空转烧 token路由权下放给了子 Agent路由收归 Supervisor + 轮次预算(= TTL)
共享状态被并发写坏没有单一事实源和合并策略Redis 单一事实源 + 版本号 + reducer(= 乐观并发控制)
成本是单 Agent 的好几倍全量历史广播给每个子 Agent按需传字段,汇总只读结论槽
出错不知道是哪个 Agent 的锅没有全链路追踪task_id 贯穿所有消息与工具调用(= 作业日志)

一句话收束,面试时可以直接说:多 Agent 系统 = 一群不可靠的智能进程 + 你早就熟悉的那套分布式治理(分片、消息协议、单一事实源、TTL、熔断降级、全链路追踪)——多出来的新增量只有一个:对"自信地出错"的输出校验。

面试官追问
Q:什么时候用编排,什么时候用自由对话协商?
人话:流程能提前画出来的,用编排;画不出来、要边走边探的,才让 Agent 自由聊。铁律:能编排就不群聊。类比:备份域一模一样——策略驱动的定时备份永远走编排器,只有容灾演练这种路径未知的探索,才值得拉一屋子专家现场商量。技术:客服、工单、合规这类可预测、要审计的场景,用 Supervisor/流水线——可控、可测、可回放;头脑风暴、研究、架构讨论这类开放式任务,用 AutoGen 式自由协商——灵活但成本高、结果方差大,必须挂轮数和 token 上限,只当最后手段。
Q:多个 Agent 怎么避免互相踢皮球?
人话:把"派活"和"转活"分开:只有主管能派活,干活的只能干活,干不了就上报,不许再转手。类比:就是分布式里防请求转发环——每一跳 TTL 递减,归零就丢弃并上报,没人能把请求无限踢下去。技术:① 路由权收在 Supervisor,子 Agent 无权说"不归我管"再转手;② 职责边界不重叠,重叠区由 Supervisor 显式仲裁;③ 兜底:连续 N 轮无进展或置信度低,反问用户或转人工。核心是把收敛责任钉死在一个节点上。
Q:协同里共享状态的一致性怎么保证?
人话:状态只存一份,所有人读写它,谁都不许自己留小抄;写冲突的合并规则要提前定好。类比:就是备份系统的元数据库——worker 不落本地状态,进度全写元数据层并带版本号,任何变更可审计。技术:会话状态统一放 Redis 做单一事实源,Agent 无状态;写操作带版本号或锁防并发覆盖;关键单据(如退款单)走状态机;同一槽位并发写用 reducer 显式定义合并策略(追加/覆盖/投票),借 CRDT 的思路,而不是让写入顺序随机决定结果。
Q:为什么不直接用一个更大的 Agent,非要拆多个?
人话:大 Agent 会撞三堵墙:工具表太长选不准、上下文太长记不住、改一处 prompt 全链路回归。类比:为什么不造一台无限大的单体服务器,而要做分布式拆分?为了故障隔离(爆炸半径)、独立扩缩容和单一职责——Agent 拆分是同一逻辑在 LLM 上的复刻。技术:① 上下文隔离:子 Agent 只看任务卡,token 省、幻觉少;② 工具表最小化:工具一多,选择准确率明显下降;③ 子 Agent 可独立迭代、并行执行、单独灰度;④ Supervisor 可换小模型省成本。反过来,简单任务单 Agent 更优——别为了架构而架构。
Q:多 Agent 的延迟和成本明显比单 Agent 高,怎么压?
人话:三板斧:能并行就并行、能不叫就不叫、能小的就小。类比:和压备份窗口同一个思路:并行流拉满、冷数据别走高速通道、轻活别上重装备。技术:① 无依赖的子任务并行派发,查订单和查用户画像同时出发;② 按需唤起,单 Agent 能答就不拆;③ Supervisor 只干意图识别和路由,用小模型;④ 路由结果按意图缓存,命中直接走单 Agent;⑤ 全链路挂 P99 延迟和 token 成本监控,超 SLA 告警。
Q:出了错,怎么定位是哪个 Agent 的问题?
人话:给每张任务卡发全局 ID,所有消息、工具调用、状态变更都挂上它,出错按 ID 回放。类比:就是备份作业日志——一次备份失败,顺着 job id 逐阶段看是快照没拍成还是复制断了,Agent 链路一模一样。技术:① task_id/trace_id 贯穿 Supervisor、子 Agent、工具调用和状态写入;② 每步落结构化日志:输入摘要、输出、token 数、耗时;③ 关键节点做输入输出断言,失败当场定位环节;④ 支持按消息序列重放,复现问题。
术语卡
Multi-Agent 系统:多个能自主决策、互相通信的 Agent 协作完成单个 Agent 干不动的任务。
Supervisor 模式:中心主管负责拆解、分派、汇总,子 Agent 只执行,LangGraph 的经典编排结构。
黑板模式:多个 Agent 通过读写同一块共享工作区间接协作,无需直接对话。
流水线:任务按固定顺序在 Agent 间接力,每环只做一类变换,可控性最高。
AutoGen:微软开源的多 Agent 对话框架,群聊协商模式的代表实现。
结构化消息:Agent 间用带 schema 的对象(任务卡片)传参,而非自然语言对话。
共享状态:协作各方共用的单一事实源,Agent 本体保持无状态。
