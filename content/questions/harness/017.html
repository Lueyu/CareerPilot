Agent核心 · Q28

你做的 Agent 使用了多少个外部工具，在调用链条上如何保障故障容错和超时机制？

⭐⭐⭐ #工具调用#容错设计#超时 字节(真题)
30秒电梯稿

"工具数量我坚持少而精——核心 8~15 个,按领域分组,多了模型选错率上升。容错我按五层防线设计:① 超时——每个工具设 deadline(如 3~5s),全链路还有总预算;② 重试——只对幂等操作重试,指数退避+抖动,上限 2~3 次;③ 熔断——某工具连续失败就短路,不再无效调用;④ 降级——换备用工具/缓存结果/兜底话术;⑤ 超时预算——把剩余时间写进上下文,让 LLM 知道"该收敛了"。关键:失败信息要结构化回灌给 LLM 让它重新决策,而不是静默吞掉。"

通俗类比

就像项目经理带一群外包供应商:手上只留 10 家靠谱供应商(工具少而精),多了管不过来、还容易派错活。每次派活都签个"交付截止时间"(超时);供应商失联,再催一次、催的间隔越来越长(重试退避);某家连续三次放鸽子,先拉黑不再派活(熔断);工期不够就换备用供应商或先给客户一个"部分结果"(降级);整个项目还有一个总截止日期,快到点必须收尾(总预算)。供应商交回来的坏消息要如实转达,让经理重新安排(失败回灌),而不是装没发生。

详细拆解

1. 工具数量怎么定

  • 少而精:核心 8~15 个,按领域分组(订单/物流/售后/搜索),每个工具职责单一、描述清晰。
  • 数量与可靠性的关系:工具越多,模型选错/参数乱填概率越高;功能重叠的工具要先合并。
  • 命名与描述:工具名动词化、描述写明"何时用/入参/出参/错误",这本身就是容错的一部分(少选错)。

2. 五层容错防线(重点)

3. 超时机制细节

  • 分层超时:单工具 3~5s;整条链路 20~30s;LLM 调用单独超时。
  • deadline 传播:把剩余时间预算写进上下文("你还有 8 秒,请给出当前最优答案"),让模型主动收敛而不是被硬掐。
  • 超时不是失败:区分"慢但会成功"与"真失败"——能异步就异步(先回执,后台继续),交互场景则降级返回部分结果。

4. 重试与幂等(成败关键)

  • 只重试幂等操作:GET/查询可重试;下单/扣款/发消息必须带幂等键,否则重试造成重复副作用。
  • 指数退避+抖动防重试风暴;区分可重试错误(超时/429/5xx)与不可重试(参数错/权限/审核拒绝)。
  • 工具调用重试前,判断"这一步是否可能已执行"(先查后写)。

5. 熔断与降级

  • 熔断器三态:关闭 → 打开(连续失败 N 次/错误率超阈值)→ 半开(冷却后放一个试探)。
  • 降级链:主工具 → 备用工具 → 缓存/规则结果 → 兜底话术+转人工,逐级降。

6. 失败回灌 LLM(Agent 特有)

  • 把工具错误转成结构化描述(错误码+原因+建议下一步)塞回对话,让模型自我纠错(换参数/换工具/澄清用户)。
  • 限制纠错轮次(如 3 轮),防"失败-重试-再失败"死循环,超限走降级。

7. 可观测

  • 每个工具调用记录:耗时、成功率、重试次数、熔断状态;工具级 dashboard,哪个工具常超时一目了然。
面试官追问
Q:工具多了选错怎么办?
三层:① 从源头减——合并重叠工具、功能分组,控制在 15 个以内;② 描述质量——工具 description 写清"何时用/参数/返回/错误",很多选错是描述含糊导致;③ 选择辅助——用 function calling 的原生工具选择能力,必要时先过一层轻量路由(意图→工具组),让模型在组内选,缩小候选集。
Q:超时和熔断会不会把正常请求也误杀?
会,所以参数要调:超时按 P99 延迟的 2~3 倍设,别贴平均值;熔断阈值看"错误率"而非单次失败,半开状态放试探请求逐步恢复。误杀的本质是阈值太紧,用指标(熔断误伤率、超时占比)持续校准。
Q:工具返回超大结果怎么办?
工具侧先裁剪/分页(只返回 top N 或摘要),不要在 Agent 层硬塞;超大结果既拖慢又费 token,还容易让模型迷失重点。必要时工具返回"命中 M 条,已取前 N 条",把进一步筛选交给后续步骤。
术语卡
幂等(Idempotency):同一操作执行多次,效果与一次相同。
熔断器(Circuit Breaker):连续失败后短路,防止无效调用。
指数退避:重试等待时间按 1s→2s→4s 递增。
deadline 传播:把剩余时间预算传给下游,让其主动收敛。
function calling:模型输出结构化工具调用而非自由文本。
