工程实践 · Q8

如何实现 Agent 的并发控制?

⭐⭐⭐⭐ #并发控制#Agent#分布式
30秒电梯稿

"分层控制,每层管一类资源:入口令牌桶限流(保住系统不被打穿)→ 队列缓冲削峰(超量请求排队而非拒绝)→ Worker 信号量限并发(同时跑的 LLM/工具调用数)→ 下游按配额保护(向量库、LLM 网关、业务 API 各自设限额)。Agent 特有的坑:一个用户请求扇出十几个工具调用,放大效应必须在设计时就按'扇出系数'算容量;死锁靠无状态设计+超时释放根除,分布式并发用 Redis 原子操作实现信号量。"

通俗类比

景区管理:门口限售每小时 1000 张票(令牌桶限流);排队区让游客等而不是轰走(队列缓冲);每个导游最多带 30 人(信号量);溶洞一次只放 20 人进去(下游容量保护);黄金周人太多时提前发"请错峰"(背压提示上游);绝不能让 A 团等 B 团、B 团等 A 团(死锁)——景区管理靠"所有团队都朝一个方向走"(无状态、单向依赖)根除死锁。

详细拆解

1. 分层控制架构

2. 各层实现要点

  • 令牌桶 vs 漏桶:令牌桶允许突发(攒的令牌一次用),漏桶匀速出口;API 网关普遍用令牌桶。按用户隔离:单用户突发不能吃掉全局配额。
  • 有界队列 + 满了快速失败:队列不是越长越好——排 10 分钟队,不如立刻 429 让客户端稍后重试;返回建议等待时间。
  • 信号量(代码级):
sem = asyncio.Semaphore(20)  # 单实例最多 20 个在途 LLM 调用
async def call_llm(prompt):
    async with sem:            # 拿不到就等,自动排队
        return await llm.chat(prompt)
# 并发数经验值:LLM 是长时延IO,单实例并发几十~几百都行,
# 但要绑下游限制:20并发×扇出10 = 向量库200QPS,别把它打挂
  • 扇出放大系数(Agent 特有):一个用户请求可能触发 10+ 次工具/检索调用,容量估算按"请求 QPS × 平均扇出数"算下游压力——这是 Agent 并发和普通 Web 并发最大的差异点。

3. 死锁避免

  • Agent 任务大多无状态+单向依赖(Agent→工具),天然无环;要警惕的是循环等待:Agent A 等工具锁,工具等数据库连接池,连接池等一个被 A 占的资源——解法:所有资源获取设超时+失败释放,加锁顺序全局统一,连接池设上限并监控排队长度。

4. 分布式并发(多实例)

  • 信号量跨机器失效 → 用 Redis 原子操作实现分布式信号量/限流(Lua 脚本保证原子性),或网关统一限流;全局限流绝不能单机算。
  • 同一会话的任务串行(锁会话 key),不同会话并行——防状态竞争。

5. 背压传导:L3 排队变长 → 上游降低接收速率(或提示"当前繁忙")→ 一直传到客户端的"稍后再试"。优雅降速比硬崩好。

面试官追问
Q:并发数怎么定?
压测定:逐步加压,找到延迟 SLO 破线(如 P99>5s)或下游错误率抬升的拐点,拐点的 70~80% 作为日常上限;并留监控指标(信号量等待时长)指导动态调。
Q:多 Agent 并发调用同一工具产生写冲突?
写操作按资源 key 分布式锁串行化(同一订单的修改排队);或改设计:写操作收敛到单一 Coordinator,子 Agent 只产出"意图"。
术语卡
有界队列:有上限的排队区,满了就拒绝。
扇出系数:一个请求放大出的下游调用数。
背压:下游忙时向上游传导减速。
