Agent核心 · Q22

你们这种模块堆叠的架构是怎么设计视觉问答模块和动作模块的协同逻辑的？

⭐⭐⭐⭐ #模块设计#多模态Agent 字节(真题)
先说人话:这题问的是:多模态 Agent 里"眼睛"和"手"两个模块怎么分工、怎么对话——本质是模块接口设计题,只是战场从存储搬到了视觉场景。面试官爱考,因为它专筛设计过系统的人:常见翻车答法是"视觉模块输出一段文字、动作模块自己理解"——两模块之间没契约、全靠猜,一听就没踩过协同的坑。
30秒电梯稿

"我按感知 → 规划 → 动作三层堆叠,视觉问答模块是'眼睛',动作模块是'手',两者靠结构化观察 + 接口契约协同,而不是视觉模块吐一段自然语言、动作模块再猜一遍。关键三点:① 视觉模块输出任务相关的结构化观察——目标物体 ID、图像坐标、属性、置信度,不写小作文,像备份扫描交出的是变更块清单而不是一段读后感;② 规划模块读这套 schema 做决策,动作模块执行,各层还能看到共享状态里的历史;③ 走闭环:动作执行后再次观察,和目标比对,偏差就重新规划,重试有上限,超限转人工。这样拆的好处是可解释、可独立迭代、可单独替换,代价是模块间会有误差传递,所以靠置信度拦截加重观察兜底。"

通俗类比

先给零基础版(用人抓桌上的杯子想):眼睛先"看"——杯子在哪、手该伸多长;大脑算路径;手执行;伸偏了,眼睛再看一眼、大脑修正。这就是"感知 → 规划 → 动作 + 闭环"的全部直觉。下面换成你的主场,逐个概念对过去。

模块堆叠(用备份流水线想):一套备份软件从来不是一个进程包打天下——扫描器找变化、调度器排计划、执行器写介质、校验器验结果,四层各司其职。Agent 的模块堆叠同理:眼睛看、大脑想、手去做,层与层之间传的不是散文,是清单。

哪里像:每层只干一件事,层间靠标准数据结构衔接,坏了能定位到层,升级能只替换单层。哪里不像:备份流水线基本是单向跑完收工,Agent 是常驻循环——每做完一步要回头看世界变了没有;而且 Agent 面对的环境会自己动(杯子会被人挪走),备份介质可不会半夜自己改名。

结构化观察(用扫描器的变更块清单想):视觉模块的输出不是"一张木桌上有个红杯子"的图片描述小作文,而是像扫描器产出的 manifest——目标 ID、坐标、属性、置信度,字段固定、机器可读,动作模块拿到手直接执行,不需要二次猜测。

哪里像:都是"任务相关的最小信息集",无关信息不往下传。哪里不像:块清单来自确定性扫描,读元数据就有、不会"扫错";视觉观察是概率性预测,模型会看走眼——所以清单里多出一个置信度字段,相当于给每条记录配了校验和的连续版:上游自报把握,下游决定信不信。

接口契约(用存储 API 契约想):视觉输出和动作输入共用同一套 schema,像对象存储的 REST 接口——字段、类型、取值范围两边共同遵守,上游不许临场发挥,下游不做格式猜测,这正是契约式设计的核心。

哪里像:版本化、可校验、非法输入拒收。哪里不像:存储协议几年难得改一次,Agent 的契约会跟着任务长新字段(比如新增"是否可抓取"),所以必须带版本号、只做向后兼容的加法,升级节奏比存储协议快得多。

闭环校正(用备份后的 verify 想):写完介质不算作业完成,要读回来比对校验和,不一致就重写;Agent 的动作执行完也一样——再观察一次,和目标比偏差,超阈值就重新规划,是一个标准的反馈回路,"verify after write"的实时版。

哪里像:都是"执行后校验、偏差就重做",不信任任何一次写入。哪里不像:备份校验的是静态数据,坏就是坏、重写就好;Agent 面对的是动态世界——偏差可能不是自己做错,而是环境自己变了(目标被挡住了),这时盲目重试没用,得换策略。

误差传递(用增量备份链想):增量链里每一代都依赖上一代,任何一代静默损坏,后面整条链报废;模块堆叠的误差同样沿链下游传播——视觉框错 5 个像素,动作就抓偏 5 个像素,还可能被下游放大。

哪里像:上游的错会传给下游,链越长越危险,所以要层层设防。哪里不像:增量链的损坏是静默的,不校验根本发现不了;Agent 每层输出都显式带置信度,等于每一代增量都自带校验,坏数据在模块边界就能被拦下,而不是恢复时才爆雷。

详细拆解

1. 模块堆叠的总览:每层只干一件事,层间传结构化数据

"堆叠"就是流水线分层的意思:上游模块的输出,原样是下游模块的输入,像管道串联的一组进程。这套分工和你天天打的备份流水线是同构的——扫描器找变化、调度器排计划、执行器写介质、校验器验结果;Agent 这边则是眼睛看、大脑想、手去做:

Agent 这一层它干什么备份流水线里的对应物
视觉问答 VQA把像素翻译成结构化观察:目标是谁、在哪、什么状态扫描器:产出"变了哪些块"的变更清单
规划模块拿观察 + 任务目标,生成动作序列调度/策略引擎:按清单和 SLA 排作业计划
动作模块把动作序列翻译成可执行指令执行器:按计划真正写介质
执行 + 再观察落地后回看世界,与目标比对备份完成后的 verify:读回来比对校验和

输入: 图像/视频 + 指令
      |
      v
+------------------+
| ① 视觉问答 VQA   |   眼睛: 像素 -> 结构化观察
+------------------+
      |
      |  层间传递物: {object_id, 坐标, 属性, confidence}
      |  接口契约:   schema v2 · 字段校验 · 低置信拦截
      v
+------------------+
| ② 规划模块       |   大脑: 观察 + 目标 -> 动作序列
+------------------+
      |
      |  层间传递物: [动作1, 动作2, ...] 每个带参数/预算/重试次数
      v
+------------------+
| ③ 动作模块       |   手: 动作 -> 坐标/API/机械臂指令
+------------------+
      |
      v
   执行 --> 再观察(回到①) --> 有偏差? --> 回到②重新规划

注意箭头方向:主数据流是单向向下的(观察喂规划、规划喂动作),只有一条从"执行"绕回"视觉/规划"的回路,那是控制流,负责闭环。单向主链路 + 一条反馈回环,和你画备份系统数据流图是同一个套路:写入是主链路,校验是回环。

2. 视觉模块的输出设计(协同的关键)

协同成不成,九成取决于这一步。先给一句总纲:视觉模块的输出不是给人看的,是给下一模块执行的。展开成三条:

  • 核心原则:视觉模块的输出是"给下一模块的输入",必须结构化、任务相关。不是泛泛的图片描述("一张桌子的照片"),而是:{目标: "红色杯子", bbox: [x1,y1,x2,y2], 置信度: 0.92, 属性: {是否被遮挡: false}}。翻译成你的主场:扫描器交给下游的从来不是"我扫了一遍,文件挺多"的读后感,而是一张精确的变更块清单——哪些块、什么时间、什么校验值,字段个个能直接执行。
  • 带置信度:低置信度的观察,规划层可以选择"再看一次"或"换角度",而不是盲目执行。这条字段就是上游递给下游的"自检信号"——像备份里每块数据带的校验和,只是从"过/不过"的 0/1 判定,变成了连续的把握度分值,下游可以设阈值分级处置。
  • 按需调用:任务只需要定位,就输出坐标;需要语义,再输出属性/关系——避免冗余信息干扰动作决策。像扫描任务只开必要的过滤规则,不多碰一个无关目录:往下传的信息越少,被误读的概率越小。

把"结构化观察"的字段摊开,每个字段的下游用途一眼可见:

字段示例值下游(规划/动作)拿它干嘛
object_id"obj-07"唯一寻址"操作谁",多轮操作不会指错对象
bbox 坐标[120, 84, 260, 210]"在哪":换算成动作空间坐标——手往哪伸、光标往哪点

3. 协同逻辑:接口契约 + 共享状态

有了结构化观察,"协同"就有了底座。剩下两件事:让模块说同一种语言(接口契约),让模块看到同一份事实(共享状态)。

  • 接口契约(Schema 对齐):视觉输出和动作输入共用一套数据结构(物体 ID、坐标、类别、置信度),模块间不互相猜格式,这是能堆叠的前提。用备份的话说:上游定义 schema、下游做校验,非法数据在边界就被拒收——好比备份代理和服务器之间有 API 版本协商,谁也不靠"猜对端会发什么"写代码。
  • 共享状态:各模块的中间结果写进统一 State(当前观察、已完成动作、目标),动作模块不只依赖视觉单次输出,还能看到历史上下文。这就是全局备份 catalog 的角色:新作业不是只看本次扫描,还能查"上次备份到哪了、哪些已经成功"。
  • 同步 vs 异步:感知和规划可串行;多路观察(多视角/多帧)可并行,再汇总进规划。和多个扫描任务并行跑、结果归并进调度器是同一个路数。

接口契约具体长什么样,写成规格就是几行:

接口契约: 视觉模块 -> 规划模块 (schema v2)
------------------------------------------------------
必填字段 : object_id / bbox / confidence / frame_id
取值校验 : bbox 在图像范围内; confidence ∈ [0, 1]
拒收行为 : 缺字段 / 越界 / 类型错 -> 拒收 + 告警
           (错误停在模块边界,不向下游传播)
版本纪律 : 只加可选字段、不改旧字段语义 -> v2 升 v2.1
破坏变更 : 删字段 / 改语义 -> 升 v3,新旧并行,灰度切流

共享状态的读写关系:

          +---------- 共享状态 State ----------+
          |  current_obs     当前观察(带时间戳) |
          |  action_history  已完成的动作序列     |
          |  goal            任务目标            |
          |  retry_count     重试计数与预算       |
          +------+----------+----------+------+
             写 |        读写 |         读 |
                v            v           v
           [视觉VQA]       [规划]      [动作]

两个图合起来读:接口契约管"数据的形状",共享状态管"数据的时效与上下文"——动作模块执行的瞬间,读到的必须是带时间戳的最新观察,而不是三秒前的旧画面。世界会动,就像备份窗口里源数据还会被改写,所以每次决策都要锚定一个一致性时间点。

4. 闭环校正(体现"Agent"而非单次推理)

这一步是"Agent"和"单次推理"的分水岭:单次推理是开环——吐完结果就撒手;Agent 是闭环——执行完再看一眼世界,确认动作真的达成了目标。你在备份里天天干这件事:写完不算完成,读回来比对校验和,不一致就重写。Agent 的版本只是把"读回来比对"换成"再观察一次,和目标比偏差":

流程铺平了看更清楚,三个出口一目了然:

[观察] --> [规划] --> [动作] --> [执行] --> [再观察] --> [与目标比对]
   ^                                                     |
   |           偏差 ≥ 阈值: 重新规划,重试 + 1             |
   +-----------------------------------------------------+
                                                         |
                                      偏差 < 阈值 -------> 完成 ✔
                                      重试 > N 次 -------> 转人工 ✋
                                      (兜底: 自动化不许死循环烧钱)
  • 阈值怎么定:按任务容忍度定——抓杯子偏 1cm 无所谓,往机柜里插线偏 1cm 就是事故。不同动作不同阈值,和不同业务不同 SLA 一个道理:核心库恢复点苛刻,边缘数据放宽。
  • 重试上限 N:闭环不是无限循环,每一轮重试烧的是真实的推理费和延迟,超限就转人工——就像自动化容灾切换三次失败必须电话 oncall,自动化的尽头永远要有人工兜底。
  • 偏差归因:再观察发现偏差,先分清是"自己做偏了"(重试)还是"世界自己变了"(目标被挪走/挡住,换策略)——两种情况的分支完全不同,这是闭环比无脑重试聪明的地方。

5. 为什么堆叠而不是端到端(必答的 trade-off)

对面的方案是端到端 VLA(Vision-Language-Action) 模型:图像和指令直接进一个大模型,动作直接吐出来,中间不拆层。答完"怎么协同",面试官几乎必追"为什么不干脆端到端",先把对比摆出来:

维度模块堆叠端到端 VLA 单模型
可解释性每步都能看"看到了什么、为什么这么做"黑盒,难定位
可迭代换更好的 VQA 不动动作模块牵一发动全身
数据需求各模块分开训练,数据好造要大规模"图-指令-动作"配对
误差传递模块间会累积误差无显式接口,误差内隐
延迟串行多跳,略慢单次前向,更快
灰度与回滚单模块可灰度发布、独立回滚只能整体切流,回滚代价大

翻译一下:这张表就是"分层备份软件栈 vs 一体化备份一体机"的翻版——堆叠牺牲一点链路长度,换来可定位、可替换、可灰度;端到端赢在链路短,代价是黑盒和训练成本。选型标准也同构:数据少、要可解释、要快速迭代,选堆叠;数据管够、延迟极致敏感,才轮到端到端。业界常见的务实路线是:先用堆叠把系统跑通,靠它攒日志和配对数据,再把它当教师,把能力蒸馏进一个端到端小模型去吃低延迟场景——两者是演进关系,不是二选一。

6. 工程细节:把堆叠架构搬进生产要补的课

  • 误差传递控制:靠"置信度 + 重观察 + 人工兜底"三件套——上游每条输出自报把握度,中游敢拦,下游敢停,坏数据出不了模块边界。
  • 超时与重试:模块间用超时和重试防止卡死——每个模块调用设 deadline,一层卡住不能拖死整条链,和分布式调用的超时预算是同一个纪律。
  • 降级路径:视觉模块的失败(识别不出)要走降级路径——降低任务粒度、换任务、或转人工,而不是让动作模块瞎猜。容灾预案的思想:主路径不通必须有提前演练过的逃生通道。
  • 可观测性:每层的输入输出中间产物都记 trace——像备份作业日志(每步的源、目标、字节数、耗时、校验结果),出问题能回放到"哪一层哪一帧开始错"。
  • 幂等与预算:动作尽量可重试(点了没反应再点一次没有副作用),闭环重试设预算上限,防止个别长尾请求把算力烧穿。
面试官追问
Q:视觉模块看错了(误识别),动作模块会照做吗?
人话:不会。低置信度的观察在规划层就被拦下:先"再看一眼",还不过就拒执行、转人工——错误出不了模块边界。类比:像备份作业里源端数据校验和不过:绝不把坏数据写进介质,而是重读源端,重读仍错就让作业失败上报,绝不带病落盘。技术:视觉输出带 confidence 字段,规划层设阈值(如 0.7);低于阈值触发重观察——换帧、换视角,或调更高精度的模型二次确认;仍不达标则拒绝生成动作,带错误码走降级路径转人工。错误被拦截在模块边界而不是一路传到执行,这是堆叠相对端到端的核心优势。
Q:为什么不干脆用一个端到端的多模态大模型?
人话:不是不行,是现阶段三处吃亏:错了没法归因、配对数据造不起、升级牵一发动全身——先堆叠跑通,数据攒够再蒸馏。类比:就是"分层备份软件栈 vs 一体机"之争:一体机链路短,但换介质引擎要整机换代;分层栈慢半拍,可每层独立替换、独立监控,故障定位到层。技术:①归因:堆叠每层有中间产物和日志,可回放定位,端到端是黑盒;②数据:端到端要海量"图-指令-动作"配对样本,成本极高,堆叠各模块可用公开数据分开训练;③升级:堆叠能只换 VQA 单模块灰度发布,端到端要整体重训;④路线:数据攒够后把堆叠系统当教师,蒸馏出低延迟端到端小模型,两者是演进关系。
Q:模块之间怎么避免误差不断累积放大?
人话:三道闸:每层输出带置信度、执行后重新观察把误差拉回来、接口处做校验——坏数据出不了模块边界。类比:增量备份链最怕这个:每一代增量依赖上一代,一代静默损坏,后面整条链全废;所以每一代都带校验、写完就验,绝不让坏数据进链。Agent 的模块链同理,只是"校验"换成了置信度加再观察。技术:①每模块输出 confidence,下游对低置信输入有降级策略:重观察、换模型或拒收;②闭环校正:执行后再观察,用真实结果校准下一轮决策,把漂移的误差拉回来;③接口校验:字段缺失、坐标越界、类型不符直接拒收并告警,不让非法数据往下游传。
Q:接口契约要加字段、改版本,下游模块没跟上怎么办?
人话:只做加法不做减法:新字段一律可选、契约带版本号,新旧并行灰度,稳定后再收旧版本。类比:和存储系统改 API 同一个纪律:对象存储不敢随便删字段,只加新字段加版本协商;备份 catalog 的 schema 升级也是先双写、再灰度、最后切换,出问题秒回滚。技术:契约带 schema_version;新增字段必须 optional,旧版本忽略未知字段仍能运行;删字段或改语义才升 major 版本,并行期按版本路由,配合灰度发布小流量验证,盯下游消费成功率和错误率,指标异常立即回滚旧版本。
Q:每做一步都要"再观察"闭环,延迟和算力成本不会失控吗?
人话:不是每步都全量闭环——按风险分级:小动作放行,高危动作才强制再观察,并给闭环设预算上限。类比:备份也不是每个作业都全量 verify:核心库逐块校验,边缘业务抽查;校验强度按数据重要性和备份窗口分配,不是无差别全验。技术:①动作分级:只读、可逆动作(查询、点击)可省再观察,不可逆高危动作(删除、抓取)强制闭环;②流水线并行:执行的同时下一帧已在视觉模块推理,用并行掩盖串行延迟;③预算控制:闭环设延迟与重试上限,超预算降级成抽查或转人工,把算力留给长尾请求里的真问题。
术语卡
VQA:视觉问答——输入"图+问题"、输出答案;在 Agent 里被改造成吐结构化观察的"眼睛"。
VLA:Vision-Language-Action 端到端模型,图像+指令直接出动作,代表作 RT-2,是模块堆叠方案的"对面"。
结构化观察:视觉模块输出的机器可读清单——物体 ID、坐标、属性、置信度,下游直接消费、不用猜。
接口契约:模块间约定的数据 schema 与校验规则,上下游按同一份契约收发,靠校验不靠猜。
bbox:目标在图像中的矩形框坐标,结构化观察里"在哪"的载体。
感知-规划-动作:机器人与 Agent 的经典三层循环(Sense-Plan-Act),本方案的总骨架。
误差传递:上游错误沿模块链向下游传播并可能放大,堆叠架构最主要的代价。
闭环校正:执行后再观察、与目标比对的反馈回路,是 Agent 区别于单次推理的本质。
