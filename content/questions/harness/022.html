Agent核心 · Q38

你简历中的客服Agent项目，是如何判断用户意图是否需要调用外部API的？用了分类模型还是prompt判断？

⭐⭐ #意图识别#API调用 字节(真题)
30秒电梯稿

"我用的两层混合,不是二选一:第一层规则 + 轻量分类模型做快速分流——高频意图(查订单、查物流)先用关键词和 BERT 级别小模型判断'要不要调 API',又快又便宜;第二层LLM + 原生 function calling做最终决策和参数抽取——小模型置信度低、或需要从一句话里抽多字段时,升级到 LLM,靠工具 Schema 约束输出工具名和参数;最后兜底:实在拿不准就反问澄清,而不是乱调。核心 trade-off 是:分类模型快、省、可控,但泛化差、要训练;LLM 泛化强、免训练,但慢、贵、可能幻觉。"

通俗类比

像客服前台分流:顾客一开口,前台小妹先听关键词("我要退货"→售后),这是规则/分类模型——快但只会背手册;遇到"我上次那个订单,东西和描述不太一样,你看着办"这种话里有话的,前台小妹拿不准,交给有经验的店长(LLM)判断"这单到底该查订单系统还是直接进投诉流程",店长还翻着一本工具手册(工具 Schema)照着选。拿不准就回头问顾客,不瞎操作。

详细拆解

1. 问题的本质:这是一次"意图分类 + 触发判断"

  • 先把需求拆成两问:① 要不要调 API(查系统 vs 直接回答);② 要调的话调哪个、传什么参数。
  • 第①问是二分类/多分类问题,第②问是结构化抽取问题,两者最优解不同——所以分层处理。

2. 方案 A:分类模型

  • 用 BERT/RoBERTa 级别小模型做意图分类(查订单/查物流/退款/投诉/闲聊…),或直接二分类"需调API/不需调API"。
  • 优点:快(毫秒级)、便宜、可控可评测(有明确准确率)。
  • 缺点:要标注数据 + 训练 + 维护;意图边界模糊时硬分类会错;新增意图要重新训练。
  • 冷启动:先用线上日志 + 人工标注,或用 LLM 半自动打标再人工校验,先跑起来再迭代。

3. 方案 B:Prompt / LLM 判断

  • 用 function calling(或 ReAct 文本协议):把每个外部 API 写成工具描述(名称、参数、返回),让 LLM 自己判断该不该调、调哪个、填什么参数。
  • 优点:零样本泛化、免训练、能处理复杂/组合意图("帮我查单号顺便改地址")。
  • 缺点:慢、贵、可能幻觉出工具名;工具多了(>10 个)选错概率上升。
  • 加固:few-shot 示例 + 工具描述写清楚触发条件 + 明确"不需要工具就输出 none"。

4. 落地组合(我实际的做法)

层级手段负责
L1 兜底关键词/规则极高频意图秒判,零成本
L2 预分流小分类模型判断"是否需调 API"+粗意图
L3 终判LLM function calling置信度低/多字段时做最终决策+参数抽取
L4 兜底反问澄清都拿不准时问用户,不乱调

5. 关键设计:置信度阈值 + 升级机制

  • 分类模型输出概率,低于阈值(如 0.8)或落入"模糊区"就升级到 LLM;LLM 也拿不准就反问。
  • 这样既吃到小模型的快和省,又用 LLM 兜住了长尾和模糊意图。
面试官追问
Q:为什么不干脆全用分类模型接管,连参数也抽?
分类模型只能做"有限类别",参数抽取是开放式的(收货地址、订单号、时间范围五花八门),用 NER+分类也能抽但泛化差、要持续标注;LLM 抽参零样本就能做。所以分类管"要不要调",LLM 管"调什么、参数怎么填"。
Q:意图模糊(既像查单又像投诉)怎么办?
不硬分:分类模型输出多意图概率,若 top1 和 top2 接近(差 < 0.1)判定为模糊,升级 LLM 综合上下文判断,再不行反问一句"您是想查订单进度还是处理投诉?"。
Q:误判调用 API 的代价怎么控制?
工具层做幂等 + 只读优先:查询类 API 随便调无副作用;写操作(退款/改地址)走"预览→用户确认→执行"两段式,分类错了也只是多一次预览,不会直接造成损失。
Q:分类模型的训练数据从哪来?
冷启动用历史工单+规则自动打标、LLM 半自动打标再人工抽检;上线后把点踩、转人工、用户修正的样本回流,持续补进训练集,定期重训。
术语卡
意图识别:判断用户这句话想干什么。
Function calling:让 LLM 输出结构化工具调用而非纯文本。
ReAct:推理(Reason)+行动(Act)交替的调用范式。
Few-shot:给几个示例让模型照葫芦画瓢。
置信度阈值:低于阈值就升级/反问,不硬判。
