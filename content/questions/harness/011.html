Agent核心 · Q11

在构建一个复杂的 Agent 时，你认为最主要的挑战是什么？

30秒电梯稿

"如果只能选一个,我认为最主要挑战是可靠性——把不可靠的 LLM 决策变成可靠、可控、可预期的系统行为。复杂 Agent 是长链路,任何一环的幻觉、选错工具、格式不稳,都会沿链路放大,最终表现为"时不时抽风"。它派生出四个具体难题:评估难(没有单一标准答案)、上下文管理(信息多而乱)、可观测与调试(黑盒难定位)、成本与延迟(长链路堆 token)。工程解法都指向同一件事:用状态机、校验、重试、降级、HITL 这些确定性护栏把不确定性关进笼子——用存储人的话说:在会坏盘的介质上,做出企业级的可靠。"

通俗类比

先把两个词钉死:LLM(大语言模型)是那颗会推理、会聊天、但偶尔一本正经胡说的大脑;Agent(智能体)是拿这颗大脑当 CPU,配上工具当手脚、记忆当硬盘、循环规划当调度器,能自主连续决策多步的程序。所谓"复杂 Agent",就是这条决策链长达几十步。

复杂 Agent(用"在会坏盘的介质上做企业级存储"来想):你做存储时从没指望过单盘可靠——机械盘有年化故障率,SSD 有误码率,但你们照样敢对外承诺一长串 9 的持久性,靠的是 RAID、多副本、纠删码、校验和,把"部件级的不可靠"组合成"系统级的可靠"。复杂 Agent 是同一道题:LLM 就是那块"会随机出错、偶尔还静默坏数据"的盘;你的任务不是把这块盘修好(修不了,它出厂就这样),而是在它之上搭出可靠的系统。

哪里像:① 矛盾结构一样——部件不可靠,系统要可靠;② 数学一样——可靠性服从连乘律,"单点小概率 × 链路长度 = 系统大灾难",RAID 重建窗口里再坏一块盘是这个公式,Agent 十步只剩六成成功率也是这个公式;③ 解法同构——存储靠冗余+校验+巡检,Agent 靠校验+重试+护栏,没有谁是靠"消灭部件错误"取胜的。哪里不像:① 盘的错是诚实的——数据对不上校验和,一眼识破;LLM 的错是幻觉,格式全对、语气笃定、内容是错的,校验和式的检查抓不住语义错误;② 盘坏了就稳定地坏,LLM 这次错、下次可能就对——这让"重试"在 Agent 里的性价比远高于存储,但也让故障基本不可复现,只能事前埋点,没法事后复现。

给完全外行的版本:像招了个很聪明但偶尔走神的新员工,让他独立看一整条流水线——他九成时间干得漂亮,一成会看错单、填错表;而且他一错,下游全跟着错,还难查是哪一步错的。你要做的是既用上他的聪明,又给这条线定流程、加复核、留人工兜底。两个比喻说的是同一件事:个体不可靠,用制度补。

详细拆解

1. 为什么"可靠性"是核心挑战

先把对手看清楚。你写的 Python 后台活在确定性世界里:函数输入 x,永远输出 f(x),测试通过就一劳永逸。而 LLM 的输出是概率采样——同一个输入,这次答 A、下次答 B,等于每次决策都在掷骰子。麻烦在于:

  • LLM 输出本质是概率采样:同一个输入可能得到不同结果,而软件工程最怕"不确定"。复杂 Agent 又把几十次这样的不确定性串成一条链,误差随链路长度累积,整体可靠率是每一步可靠率的乘积——某一步 95% 看似不错,十步串起来就只剩约 60%。
  • 所以"复杂 Agent"的难度不是"让模型更聪明",而是"在不可靠的基座上搭出可靠的系统"。

这条"连乘律"画出来更直观(存储人应该觉得眼熟——这就是 RAID 重建窗口里"再坏一块盘就前功尽弃"的同款数学):

单步调用(普通 Chatbot):
  问题 ──► [ LLM ] ──► 答案                    单步可靠率 95%

多步链路(复杂 Agent):
  问题 ──► 规划 ──► 选工具 ──► 执行 ──► 观察 ──► 再规划 ──► ... ──► 答案
           0.95 ×   0.95  ×   0.95 ×  0.95  ×   0.95  × ...  ≈ 0.95^10 ≈ 60%

  ↑ 整体可靠率 ≈ 各步可靠率连乘
    任何一步掉链子,后面所有步骤都在错误的地基上继续盖楼
单步可靠率10 步链路整体(连乘)意味着什么
99%≈ 90%单步已经很优秀,链路仍在悄悄漏水
95%≈ 60%复杂 Agent 的现实处境:五分之二的请求会翻车
90%≈ 35%三次里两次翻车,根本不敢上生产

你在存储里还见过它的"无校验和"版本:静默数据损坏在层层拷贝里传播,每一级都笃信"我拿到的是对的"——Agent 链路里,一步幻觉被后续步骤忠实地继续加工,是同一个失败模式。结论就一句:模型迭代在把单步可靠率从 95% 往 99% 推,而你的工程任务,是把链路整体可用性从 60% 拉到 99% 以上——前者是算法的事,后者是你的事。这也是为什么最佳答案是"可靠性":它不是四个并列难点之一,而是把所有难点串起来的总纲。

2. 由此派生的四个具体难题

"可靠性"这个总纲,落到日常工程里会长成四张面孔。先上总表对齐(第四列是给你定制的主场翻译),再逐个展开:

难题为什么难应对思路用你的主场来想
评估难任务没有唯一正确答案,手工评测不可持续分层评估 + LLM-as-judge + 固定回归集 + 线上 AB灾备演练:没人等机房真失火才测容灾;没恢复过的备份不算备份
上下文管理信息塞多了又贵又吵,塞少了又丢关键背景分级记忆、按需检索注入、摘要压缩、上下文预算存储分层:上下文窗口是贵而小的高速层,该按需取数,不该全量灌入
可观测/调试多步推理是黑盒,失败难定位到具体一步全链路 trace、每步结构化日志、checkpoint 回放IO 全链路 trace + 快照回放:哪层慢/错,可定位、可复盘
成本/延迟多步调用让 token 和耗时线性放大模型分级、并行、缓存、提前终止预算备份窗口:窗口就这么大,靠增量、去重、并行、分层把量压下来

① 评估难——"没恢复过的备份,不算备份"。传统测试是断言"输出 == 期望值";Agent 的任务(排查故障、写周报、订机票)往往有多个可接受答案,还有过程好坏之分,组合起来 case 数爆炸。像的地方:备份领域早就教育过我们,验证只能主动演练,不能等真出事;不像的地方:恢复演练有干净的成功判据(数据逐字节一致),Agent 没有——所以要请 LLM-as-judge(让一个强模型按规则打分)来扩产能,但 judge 得先和人工标注对齐校准(抽一部分人机双评、算一致率),否则就是拿一个不确定的系统去测另一个不确定的系统。落地组合:分层评估(单步的工具选择准确率/格式通过率 → 轨迹级中间步骤 → 端到端任务成功率) + 固定回归集(像你每晚定时跑的验证任务) + 线上 A/B 测试与灰度发布兜底。

② 上下文管理——上下文窗口就是你的"高速缓存层"。LLM 每次调用只能看见窗口里塞进去的东西,而这个窗口又贵又有限。全量塞入等于把冷数据全放 NVMe:既贵,又"吵"——无关内容会稀释注意力,拖垮推理质量(有个专门的研究现象叫 Lost in the Middle:模型容易对窗口中间的内容视而不见)。像的地方:和容量规划同构,本质都是"稀缺资源 + 命中率"的分配问题,所以要设上下文预算;不像的地方:存储分层不命中只是慢一点,上下文塞错内容会直接把模型带偏、诱发幻觉——错比慢更致命,所以注入前必须做筛选与摘要压缩。落地套路:工作记忆(当前任务)/情景记忆(历史对话摘要)/长期记忆(外部知识库)三级分层,知识库切成 chunk、按 top-k 检索注入,历史对话定期摘要归档——本质是给"注意力"做一套冷热分层。

③ 可观测/调试——出事再开 trace 就晚了。多步链路失败后要回答"哪一步坏的",和你排查一个慢 IO 要定位到文件系统还是盘阵是同类问题,但有个要命的区别:故障基本不可复现——同一输入重跑,结果可能就对了(概率采样),你没法像复现盘问题那样复现 Agent 问题。所以纪律是"事前全量埋点、事后回放":全链路 trace,也就是你熟的分布式追踪,记下每次 LLM 调用的完整输入输出、工具参数、耗时与 token 数;每步 checkpoint 存档,能把 Agent 像恢复快照一样回放到第 N 步继续跑;错误按类目聚合(选错工具/格式错/幻觉/超预算)持续看趋势——相当于给 Agent 配一套 SMART 指标。

④ 成本/延迟——本质是"备份窗口"问题。十步链路意味着 token 消耗和耗时大约线性放大十倍(token 是模型处理和计费的基本单位,约半个到一个汉字),而用户对 Agent 响应的 SLA 期待和一个普通接口没区别。这是你的老战场:数据量涨十倍,备份窗口不会变长,只能靠工程手段压。模型分级 = 介质分层(难任务才上大模型,抽取/分类/路由这类日常流水用小模型);缓存 = 重删(相同或相似问题的命中率比想象高,连 KV Cache 都能直接复用);并行 = 并行流(无依赖的工具调用并发执行);提前终止 = 到预算就收口(带着已完成的部分结果加说明提前结束,别硬扛到超时,更别死循环烧钱);再配合流式输出把已生成的部分先递到用户眼前,体感延迟立刻下来。盯 P99 而不是平均值——决定半夜 pager 响不响的,从来是长尾请求。

3. 解法:确定性护栏(把不确定性关进笼子)

四个难题方向各异,解法却收敛到同一个设计哲学:概率的部分(LLM)只放在最小必要的环节,其余全用确定性代码包起来。就像你从不让"盘的读写错误"决定数据是否丢失,你也不该让"模型的自由发挥"决定系统是否可靠。整套结构长这样:

[用户请求]
    │
    ▼
┌────────────── 确定性护栏:普通代码,行为可预期 ──────────────
│
│  ① 状态机:只允许跳到"跳转表"里写明的下一步
│        │
│        ▼
│  ② LLM 产出 ──► Schema/参数校验
│        │              │
│        │    ✗ 不通过 ──► 报错原文喂回去,重试(≤ N 次)
│        │    ✓ 通过
│        │              │
│        │              ▼
│        │        执行工具 ──► 闭环检查(结果真的完成目标了吗)
│        │              │
│        │              ▼
│        └──────►  观察结果 ──► 回到 ①,进入下一轮
│
│  ③ 全程盯预算:最大轮次 / token 上限 / 死循环检测
│        │
│        ▼  超限
│  ④ 降级:模板兜底 / 缩小任务 ── 仍不行 ──► 转人工(HITL)
│
└──────────────────────────────────────────────────────────
    │
    ▼
[出口恒存在:正确答案 / 降级答案 / 工单,绝不卡死]
  • 状态机约束:把 Agent 流程固化成有限状态(如 规划 → 调用工具 → 观察 → 综合),而非让 LLM 自由漫游。经验法则:LLM 的自由度应该存在于状态内部(这一步怎么推理、怎么措辞),而不是状态之间(下一步跳去哪)——后者必须是白纸黑字的跳转表。类比你的主场:备份调度器和分布式共识(如 Raft)全是状态机,因为"自由发挥"不可审计、不可回放;状态机化之后,每步都能对账,出问题能定位到"哪次跳转违规"。
  • 输出校验:工具调用过 JSON Schema 校验、结果做闭环检查,格式错重试一次(带纠错提示)。关键细节:校验失败时,把报错原文拼回 prompt(prompt 就是发给模型的输入)再试——模型看着具体报错自纠的成功率,远高于盲目重试,相当于协议里"校验失败回 NAK 并附原因"。闭环检查则是结果层面:任务要查 3 条记录、返回了 0 条,不需要任何智能就能判定异常。
  • 预算与熔断:最大轮次、token 预算、死循环检测,超限降级。前半段是微服务那套超时/重试上限/熔断器的直系迁移;"死循环检测"是 Agent 特有——模型在两个状态间反复横跳、连调同一工具毫无进展,就该熔断。熔断后不是抛 500 完事,而是降级:模板答案、缩小任务、或转人工。原则同容灾:宁可降级服务,不可整体卡死。
  • HITL 兜底:关键/写操作留人工确认,所有失败路径收敛到"转人工 + 降级",绝不让用户卡死。这就是灾备切换分级的原样搬运:盘故障自动换热备、节点故障自动 failover,但机房级切换永远要人拍板——影响越大、越不可逆,自动化越保守。Agent 里同理:查询/总结类放开自动跑;删数据、对外发邮件、付款这类不可逆写操作,必须人工确认。
  • 副作用防护(加分项):重试的前提是幂等。每次工具调用生成幂等键透传到执行侧;高危工具先查后写;不可逆操作失败不自动重试,直接转 HITL——这套你在消息队列和存储写路径里玩得很熟,原样搬过来即可。

4. 一句话总结:复杂 Agent 的工程本质是"用确定性的流程设计,管理一个概率性的智能"——谁把这个平衡做得好,谁的系统才敢上生产。再给你一句主场翻译:这件事存储行业几十年前就干过一轮,"在不可靠的介质上,做可靠的系统";介质从机械盘换成了 LLM,方法论还是冗余、校验、分层、兜底那一套,只是"校验和"升级成了 Schema 校验 + 语义闭环检查。

面试官追问
Q:为什么不选"评估难"作为最主要挑战?
人话:评估难是症状,可靠性才是病根——正因为每步输出不确定、答案不唯一,才没法拿一个标准答案一刀切打分;把根立住,枝叶问题全都顺理成章。类比:你不会说"容灾的主要挑战是演练难做"——演练难,根子是故障形态和数据都在变、真正要保证的是 RTO/RPO;评估之于 Agent,正如演练之于容灾,是度量手段,不是问题本身。技术:四个难题都是可靠性的投影:评估=度量面,上下文=输入面,可观测=定位面,成本=约束面。面试先立根、再展枝,展示结构化思维;直接并列报四个难点,听着就像背清单。
Q:可靠性和"智能程度"怎么取舍?
人话:按"错了有多疼"分级:错了赔钱、赔信任的环节上枷锁;错了无伤大雅的环节放开跑,别在所有环节都赌模型发挥。类比:灾备切换分级的原样搬运:盘故障自动换热备、节点故障自动 failover,机房级切换必须人拍板——影响越大越不可逆,自动化越保守。技术:① 任务分级矩阵(读/写、可逆性、影响面);② 高危动作白名单 + HITL 确认;③ 允许模型弃权:不确定时输出澄清问题或直接 abstain,而不是硬猜;④ 计算查询类子任务用规则和检索兜底,把 LLM 留给真正需要模糊判断的环节。
Q:你怎么量度一个复杂 Agent 的可靠性?
人话:三层一起看:零件(单步)、整车(端到端任务)、路况(线上健康度),只盯任何一层都会被骗。类比:存储健康度的老套路:盘看 SMART,阵列看冗余和重建状态,业务看 IO 成功率和 P99,三层合起来才是整车体检;只报平均成功率,就像只报平均 IOPS 不看长尾请求——半夜 pager 响不响,从来由长尾决定。技术:① 单步:工具选择准确率、Schema 通过率;② 端到端:固定回归集任务成功率,按难度分层;③ 线上:失败率、重试率、转人工率、错误类目分布、P99 延迟与单任务成本;④ 长尾 bad case 持续回流进回归集,发版全量跑——可靠性是喂出来的。
Q:重试是护栏标配,但工具带副作用(下单、删数据)时,重试不会把操作执行两遍吗?
人话:会,所以重试必须配幂等——让执行一次和执行两次结果相同,否则护栏自己就会制造事故。类比:消息队列消费去重的老配方:请求带唯一幂等键,服务端记下"这个键处理过",重复请求直接返回上次结果——存储写路径和备份任务调度里你都见过同款。技术:① 每次工具调用生成幂等键,透传到执行侧;② 写操作先查后写,或带版本号做乐观锁;③ 高危不可逆操作失败不自动重试,直接转 HITL;④ 自动重试只留给读操作和显式声明幂等的工具。
Q:你说的重试、熔断、降级,跟微服务治理那套是不是一回事?
人话:骨架同源,但治理对象从"会超时的机器"换成了"会一本正经胡说的人"——失败模式变了,检测信号必须跟着变。类比:调下游微服务像调一台机器:超时、5xx,错得诚实;调 LLM 像问一个过度自信的同事:很少超时,但可能流畅地答错,而且这次错、下次对,"不可复现"是最大的新变量。技术:超时/重试/熔断/降级四件套直接迁移;新增三类信号:Schema 校验失败率、语义闭环检查失败率、预算消耗曲线;调试靠全链路 trace + 固定输入回放,类似用 IO trace 复现盘问题的思路。
Q:模型一直在升级,这些护栏会不会白做?
人话:不会。护栏是模型无关的资产,模型变好只是让护栏触发频率下降,不等于护栏失效。类比:盘从 HDD 换到 SSD 再换 NVMe,你的校验和、多副本、分层逻辑一行不用改——介质换代,可靠性框架照用;LLM 也一样,幻觉率会降,但降到 0 遥遥无期。技术:① 护栏尽量模型无关,别把补丁焊死在某个模型的行为癖好上;② 换模型先跑全量回归集,看错误分布怎么迁移;③ 轮次/token/幂等类护栏最稳,直接继承;④ 护栏拦截日志反而是雷达:新模型上线初期,它就是发现新 bad case 的第一现场。
术语卡
可靠性:系统在规定条件下、规定时间内持续正确履职的能力——要用指标量化,不能靠"感觉挺稳"。
误差累积:多步链路整体可靠率≈各步可靠率连乘,单步 95% 十步只剩约 60%——长链路的隐形杀手。
可观测性:不拆开黑盒,仅凭外部输出(trace/日志/指标)就能推断系统内部状态的能力。
护栏:包在模型外围的校验、熔断、流程约束,把概率性的输出圈进安全边界。
HITL:Human-in-the-loop,在关键或高危环节保留人工确认的兜底设计。
幂等:同一操作执行一次和执行多次,系统状态不变——重试安全的前提。
LLM-as-a-judge:用一个强模型按规则给被测输出自动打分,缓解人工评估不可扩展的问题。
有限状态机:只有有限个状态、按固定规则跳转的模型——把"自由发挥"变成"按流程走"。
token:模型处理文本的最小单位,也是计费单位,约等于半个到一个汉字。
