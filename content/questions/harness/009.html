Agent核心 · Q9

什么是多智能体系统？让多个 LLM Agent 协同工作相比于单个 Agent 有什么优势？又会引入哪些新的复杂性？

⭐⭐⭐⭐ #MultiAgent#协作#系统设计 字节、阿里（高频）
30秒电梯稿

"多智能体系统(MAS)是让多个各司其职的 LLM Agent 通过消息或共享状态协作完成任务的架构,典型是 Supervisor 调度多个专家 Agent。相对单 Agent 有四个优势:任务专注(每个 Agent 上下文小、工具少,准确率更高)、并行执行、独立迭代(模块化)、故障隔离。但代价也很明确:协作开销、状态一致性、误差级联、调试与成本都更复杂。结论:任务可拆、各子任务工具差异大才值得上多 Agent,简单线性任务单 Agent 更稳——能说出这个 trade-off 才是加分项。"

通俗类比

就是医院分诊台 vs 全科医生:分诊台(Supervisor)把病人派给各科专家,专家设备更精(工具更专)、看得更准(上下文更聚焦)、还能同时看几位病人(并行);但代价是挂号、转科、会诊这些协调成本,以及信息在科室间传递时可能传错、传丢。小毛病找全科医生反而又快又便宜——不是越拆越好。

详细拆解

1. 是什么:多 Agent 的典型结构

2. 相比单 Agent 的优势(为什么值得拆)

  • 上下文专注:单 Agent 要把所有工具说明、全部职责塞进一个 system prompt,工具一多(30+)选错率明显上升;拆开后每个 Agent 提示词更精、工具更少,单点准确率更高。
  • 并行执行:多个独立子任务同时跑,总延迟从"串行累加"变"取最长的一条"。
  • 独立迭代:各 Agent 独立开发、评估、回滚,团队也好分工。
  • 故障与权限隔离:某个 Agent 挂掉或被注入攻击,影响被限制在自己的职责和工具范围内。

3. 引入的新复杂性(必须主动讲,这是本题的"第二半")

  • 协作开销:多一次"调度→执行→汇总"就多几次 LLM 调用,token 成本和延迟都会上升。
  • 状态一致性:共享状态谁来改、怎么合并、并发时会不会互相覆盖——需要 reducer/锁/版本控制。
  • 误差级联:上游 Agent 输出错,下游基于错误输入继续,错误会逐级放大,比单 Agent 更难定位。
  • 通信协议设计:Agent 之间自由对话难以收敛(踢皮球、跑题),一般要靠 Supervisor 中转或强约束收敛。
  • 调试与可观测:链路变长,出问题要跨多个 Agent 追踪,单步埋点和 trace 是刚需。
  • 评估更复杂:除了端到端,还要拆到每个 Agent 单独评估,否则不知道是哪个环节掉链子。

4. 什么时候该用(决策标准)

  • 任务能自然切分成职责边界清晰的子任务,且各子任务需要的工具/知识差异大 → 适合多 Agent。
  • 任务线性、工具 < 10 个、流程简单 → 单 Agent 更简单可靠,别为了"看起来高级"硬拆。
面试官追问
Q:多个 Agent 之间怎么通信?是自由对话吗?
生产里不推荐自由对话式(易跑题、难收敛),更常用两种:① 共享状态 + Supervisor 中转——子 Agent 写结果到 State,Supervisor 决定下一步(可控、好调试);② 消息/任务协议——结构化消息(如 A2A 协议)显式传递任务。自由对话(AutoGen 风格)适合原型探索。
Q:怎么防止多 Agent 互相踢皮球或死循环?
路由职责集中在 Supervisor,子 Agent 只执行不转发;设最大调度轮次和 token 预算;Supervisor 路由置信度低时主动反问用户或转人工;状态无变化则判定死循环熔断。
Q:多 Agent 一定会比单 Agent 效果好吗?
不一定。多 Agent 的收益来自"职责切分",代价是协作开销和误差级联。如果任务本身是单一路径,拆开反而引入额外的调度误差和成本。正确做法是用任务特性决定架构,并用端到端指标做 AB 对照,而不是默认"越多越好"。
Q:怎么评估一个多 Agent 系统?
两层:端到端(任务成功率、延迟、成本、转人工率)+ 单 Agent(各自的任务成功率、工具调用准确率)。配合全链路 trace,把"整体失败"定位到"具体某个 Agent 的某一步",再针对性优化。
术语卡
MAS:Multi-Agent System,多智能体系统。
Supervisor 模式:主管 Agent 统一调度子 Agent 的星型架构。
误差级联:上游错误沿链路逐级放大。
共享状态:多个 Agent 通过同一 State 对象交换信息。
上下文隔离:各 Agent 只拿自己需要的上下文,更小更准。
