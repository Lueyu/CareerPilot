Agent核心 · Q25

如果要做电商agent，你会选择哪些模态的信息作为输入？比如文本评论、图像、视频、购买记录？

⭐⭐ #场景设计#多模态#电商Agent 字节(真题)
先说人话:这题问的不是"你认识几种数据",而是"你会不会做预算"——文本、图像、视频、购买记录,全都要还是挑着要?面试官爱考,因为它一眼分出"堆料型选手"和"做预算的工程师":张口就"全上多模态大模型"的,暴露没算过 token 账、没扛过延迟;能按收益/成本分层取舍的,才是干过活的人。
30秒电梯稿

"我的原则是按收益/成本比选模态,不是越多越好。电商 Agent 我选四层:① 结构化数据——购买记录、订单、价格、库存,这是决策主干,最便宜最可靠;② 文本——商品标题、评论、客服对话,是语义理解的主力,embedding 和检索成本可控;③ 图像——只在需要视觉判断时上,如商品主图、售后凭证 OCR、以图搜图;④ 视频——基本不作为实时输入,离线抽关键帧+摘要即可。一句话:能结构化就不上多模态,能文本就不上图像视频,每加一个模态都要回答'它带来什么增量、花多少成本'。"

通俗类比

多模态选型(用备份系统的介质分层来想):成熟的备份系统从不让在线恢复路径碰磁带——先查 catalog(元数据库),再读索引,万不得已才读数据块,归档介质只在离线批量任务里动。电商 Agent 的输入端是同一张地图:购买记录/订单是 catalog(最便宜、最可靠、毫秒级),文本是索引文件(便宜、量大),图像是磁盘上的数据块(按需读),视频是磁带库(在线永远不碰,只做离线批处理)。换成生活场景就是金牌导购:先翻你的购物小票和会员档案,再听你口头描述,拿不准才把商品拿起来端详,你发的开箱视频他只会快进扫两眼。

哪里像:都是"便宜介质先上、贵介质按需下沉"的分层经济学——加一层存储介质和加一种模态,都要拿访问频率与收益说话,不是"库里有磁带就什么任务都走磁带"。哪里不像:存储分层是同一份数据在介质间搬家,模态选型是决定给哪类信息源建管道——数据不搬家,是你在选"看不看它、什么时候看";而且介质分层看访问频率这种硬统计就够了,模态选型还要估"信息增益"这种软价值,更吃业务理解。

视频离线摘要(用备份时的重删+建 catalog 来想):备份引擎从不在查询现场解压整个备份集——重删、压缩、catalog 条目在备份完成时就做好了,查询只扫现成索引。视频同理:入库时就离线抽好关键帧、生成文字摘要,在线只查那几行"catalog 记录"。哪里像:都是"一次性重活,换在线轻查询"。哪里不像:重删压缩是无损的,视频摘要是有损压缩——信息必然丢,所以摘要策略要按业务定:带货视频的摘要必须保住价格、规格、卖点,不能只描述画面。

详细拆解

1. 为什么模态不是越多越好(先立观点)

先把直觉立住:在 AI Agent 里,每接一种模态,就是多养一条数据管道——和你接一种新数据库就要多写一个采集 agent、多测一轮兼容性,是同一种工程负担,只不过那边叫"备份 agent",这边叫"感知管道"。

  • 每个模态都对应一条独立管道:图像要视觉模型,视频要抽帧+时序建模,结构化要解析清洗——各配各的模型、监控和 badcase(失败案例)集,维护面是加一个模态多一整条。
  • 多模态 = 多一套模型 + 多一份延迟 + 多一份成本 + 多一个出错点,模态之间还要做对齐/融合——出错时的排查难度是乘法涨的。
  • 选型判据(定性):信息增益 ÷ (延迟 + 成本 + 复杂度),增益小成本高的模态坚决砍掉。

再算一笔token 成本账建立体感。图像进多模态模型前会被切成小方块(patch)、编码成视觉 token,一张图动辄几百上千个——这就是"图像比文本贵一个量级"的根源:

输入内容折算体量(数量级)类比备份世界
一条订单(序列化成 JSON)几十~几百 token查一次 catalog,毫秒级
十条评论的摘要几百 token读一段索引文件
一张商品图(视觉编码后)几百~上千视觉 token在线路径直接读数据块
60 秒视频(按 1fps 抽帧)数万视觉 token在线恢复时挂载整个备份集

结论不言自明:把所有模态一股脑丢给模型,等于每次查询都做"全量恢复"。备份系统从来不这么干——永远先查 catalog、再读索引、万不得已才碰数据块;Agent 的输入端照抄这个顺序就对了。

2. 四层模态定位

模态电商场景典型信息角色成本/延迟
结构化数据购买记录、浏览轨迹、订单、库存、价格决策主干极低,毫秒级
文本商品标题、评论、客服对话、搜索词语义主力低,embedding+检索
图像商品主图、售后凭证、用户上传图按需视觉判断中,视觉模型
视频开箱视频、直播切片、买家秀几乎不实时高,抽帧+摘要

这张表从上往下就是"从最便宜到最贵",也是你的消费顺序:第一行能解决的绝不动第三行。逐行展开:

  • 结构化数据是硬事实:买过什么、价格多少、有没有货——这些不需要模型"理解",只需要取准,一条查询毫秒级返回,可靠性接近 100%,永远让它先上场。
  • 文本是语义主力:评论情绪、商品卖点、用户意图都在文本里。工程上是文本 embedding 进向量检索(底层是 ANN 索引,常用 HNSW——动机和你在数据库里建 B 树一样:别全表扫,走索引,只是这里查"向量距离最近"而非"键值相等"),BM25 走关键词,两路混合检索用 RRF 融合,预算允许多加一层 Rerank 精排,取 top-k 片段——整套就是一个小型 RAG。延迟几十毫秒,成本可控。
  • 图像按需上场:只有"必须看一眼"的场景才值得花钱——售后凭证走 OCR,以图搜图走视觉 embedding,用一次付一次的钱。
  • 视频离线处理:在线路径几乎用不到它的原始形态,整体下沉到离线管道,第 4 节展开。

3. 具体怎么选(分任务对齐)

模态没有万能配方,跟着任务走:

  • 商品推荐/个性化:结构化购买记录 + 文本评论语义 + 图像风格特征(可选),视频基本不用——推荐的核心信号是行为(买过、看过、加购),行为天然结构化,图像最多补风格偏好,视频几乎零增量。
  • 售后客服:文本对话 + 图像凭证(破损照片 OCR/识别)+ 订单结构化数据——先用订单对上"是哪一单",再用照片定损,最后靠对话理解情绪,三种模态各司其职。
  • 以图搜图/找同款:图像 embedding 必须,文本辅助描述——这是图像唯一不可替代的主场。
  • 直播带货 Agent:视频只做离线理解(关键帧+字幕),在线输入仍是结构化+文本。
  • 商品审核/合规(补个反例):违禁品识别、图片违规检测,图像是主角且必上——可见"图像按需"的"需"由业务定,不是一刀切。

4. 融合方式(视频先"降维")

融合的总原则一句话:贵的模态先离线"降维"成便宜的模态,在线只消费降维产物——视频降成"关键帧+摘要",图像按需降成"OCR 文本/结构化描述",原样上在线的只有结构化数据和文本。先看主干道:

再补一张上面没画的在线/离线切分施工图,这是工程落地时真正要画的图——左边像你的备份作业(批处理、有窗口),右边像你的恢复作业(SLA 硬约束、只碰现成产物):

【离线管道(= 备份作业):批处理,提前把贵模态"降维"成便宜模态】
 视频 ──抽关键帧──> 关键帧图集 ──视觉模型──> 文字描述
 视频 ──语音转写──> 字幕文本
      └──两条汇合──> LLM 摘要──> "几句话+几张图" 存入索引
 商品主图 ──视觉 embedding──> 向量入库(供以图搜图)
 评论/标题 ──分 chunk+文本 embedding──> 向量库+倒排索引

【在线管道(= 恢复作业):SLA 内必须回,只碰便宜模态】
 用户请求
   ├─ 结构化:查订单/库存/价格 ───────────── 毫秒级
   ├─ 文本:query 向量化+向量检索 ─────────── 几十毫秒
   ├─ 图像:按需触发(售后凭证/找同款) ─────── 百毫秒级
   └─ 视频:不碰原始视频,只读离线摘要 ──────── 毫秒级
        │
        ▼
 组装上下文(结构化 JSON+检索片段+离线摘要)
        │
        ▼
 文本 LLM 推理 ──流式输出──> 用户

对照着读:离线管道把重活全干完,在线管道一根"贵模态"的毛都不碰——恢复路径从不现场做重删压缩,在线 Agent 从不现场解码视频,是同一条铁律。最后由便宜的文本 LLM 推理并流式输出,TTFT 也不会被视觉编码拖累。

5. 关键 trade-off

  • 端到端多模态大模型(GPT-4V/Qwen-VL)能直接吃图,但贵且慢;工程上常用"视觉模型抽取成结构化描述 → 再喂便宜文本 LLM"的分层方案——贵的视觉模型小范围按需触发,便宜的文本模型承担海量推理,这正是备份系统的花钱哲学:重活(重删/压缩)做在备份时,恢复时只读现成块。
  • 在线 vs 离线:能离线预处理的(视频摘要、图像特征入库)绝不放到在线实时算——在线 SLA 就像容灾的 RTO,是倒逼架构的硬约束;大促 QPS 翻十倍时,在线路径里每多一个视觉调用,长尾请求就多一批。
  • 可解释与可回滚(补):分层方案的每个中间产物——OCR 结果、抽取描述、视频摘要——都能落库、能审计、能单独重跑;端到端一锅炖,坏了只能整锅换。

6. 落地节奏(加分项)

如果面试官追问"那你打算怎么排期",给出三步走:

  • Phase 1:结构化 + 文本,先覆盖 80% 高频场景,把决策链路和评测基线跑通;
  • Phase 2:图像按需接入,挑售后凭证、以图搜图这类"非它不可"的点先上;
  • Phase 3:视频离线摘要入库,在线只读索引。

每期上线前都做 badcase 归因 + 小流量灰度验证,收益测不出来就停在这一期——不是所有数据都配得上 SSD,也不是所有场景都配得上多模态。

面试官追问
Q:为什么不直接上一个多模态大模型,把图、文、视频都丢进去?
人话:不是不行,是不划算——除非场景真的离不开细粒度视觉,否则别让一个模型包打天下。类比:恢复一封误删邮件,你不会挂载整个备份集去翻——有 catalog 查 catalog,有索引走索引;端到端多模态等于"每次请求都全量挂载",贵、慢、还难排障。技术:三个代价:①贵——一张图编码后是几百到上千视觉 token,比等量信息的文本贵一个量级;②慢——TTFT 和吞吐一起被拖累,P99 变难看;③不可控——一个模型管所有模态,坏一处全链路遭殃。工程折中是"多模态感知+文本决策":视觉模型只做抽取,转成文本再交给便宜的文本 LLM;只有看复杂表格截图这类强视觉场景才值得端到端。
Q:购买记录这类隐私敏感数据,作为输入要注意什么?
人话:三条红线——少拿、脱敏、留痕;能走规则的不走模型。类比:和备份系统同一条军规:备份集里有全盘数据,不代表每次恢复都该把全盘吐出去——恢复结果按最小权限交付,敏感字段该遮蔽就遮蔽,审计日志必须答得出"谁、何时、动了哪些数据"。技术:①最小化——只取与当前意图相关的字段,不全量塞进上下文;②脱敏——手机号、地址、卡号等 PII 进模型前掩码/泛化,输出侧再加一道敏感信息拦截;③权限与审计——用户授权、访问可回溯。另外结构化数据尽量走确定性逻辑(规则/检索)而非 LLM 自由发挥——进了上下文的东西,都存在被模型复述出去的可能。
Q:视频为什么基本不作为实时输入?
人话:视频的单位信息密度太低,在线实时算它,等于花 SSD 的钱养冷数据,延迟和成本都扛不住。类比:在线路径碰原始视频,等于在线恢复时去磁带库扫全量备份——不是做不到,是 SLA 不答应;正确姿势是平时就给"磁带"建好索引和摘要,在线只查 catalog。技术:一条 60 秒视频按 1fps 抽帧就是 60 张图、数万视觉 token,再叠加解码与时序建模,在线算不动。常规做法是离线管道:抽关键帧→图文识别→LLM 摘要,把视频压成"几张图+几句话"入库,在线只用摘要。只有必须理解动态过程的垂直场景(如动作质检)才做在线视频,且用专用小模型。
Q:不同模态的信息打架了怎么办?比如评论一片好评,退货率却居高不下。
人话:别让模型私下和稀泥——定一套显式的"证据可信度排序",冲突时让更硬的证据赢,并要求 Agent 把分歧说出来。类比:就是告警仲裁:采集 agent 上报和存储侧直采告警打架时,你按数据源可靠度定优先级,工单里两条都留痕,而不是静默吃掉一条。技术:可信度大致排序:客观行为数据(退货率、订单)高于主观文本(评论),评论又高于模型对图像的推断(有幻觉风险)。实现上,结构化数据当硬约束/校验项,文本与视觉抽取结果当上下文证据,prompt 要求输出标注依据,冲突时明说(如"评论好评,但近 30 天退货率 18%"),让仲裁逻辑可审计。
Q:你的第一步会做什么——怎么判断某个模态值不值得上?
人话:先测量,后上模态——收益是测出来的,不是觉得出来的。类比:扩容存储集群前你先看容量水位和增长曲线,而不是先下单买盘;上模态前也得先看"现在的输入缺了什么、导致多少请求答不好"。技术:①离线归因:抽样 badcase,统计"缺图像/缺视频/缺字段"各自占比——若 500 条里只有 3% 是"没看到图"导致的,图像优先级直接后置;②在线验证:新模态走灰度发布小流量,盯任务完成率、人工接管率、P99 延迟、单请求成本四个指标,收益盖不住成本就停在这一期。
术语卡
多模态(Multimodal):同时处理文本、图像、音频等多种信息形态。
结构化数据:有固定 schema 的记录型数据(订单、库存),可直接程序处理。
视觉 embedding:把图像编码成向量,用于以图搜图/相似度计算。
CLIP:用图文对比学习把图像和文本编进同一向量空间的模型,以图搜图的地基。
关键帧抽取:从视频里挑出代表性画面,降低后续处理量。
收益/成本比:选型判据——新增模态的价值是否盖过它的成本。
OCR:把图片里的文字转成机器可读文本,售后凭证识别的标配。
视觉 token:图像切成 patch 后编码出的 token,一张图几百上千个,是图像贵的主因。
PII:个人身份信息(手机号/地址/卡号),进模型上下文前必须脱敏。
