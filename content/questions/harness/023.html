Agent核心 · Q40

当多个工具都能完成子任务时，你的Agent如何做选择？有没有引入打分或排序模块？

⭐⭐⭐ #工具选择#决策机制 字节(真题)
30秒电梯稿

"有的,我用'LLM 粗筛 + 打分精排'两层:第一层,把每个工具写成带描述和触发条件的 Schema,靠 LLM 的 function calling 按语义做粗筛,从一堆工具里捞出候选;第二层,当候选多于 1 个、且确实存在选择空间时,引入打分/排序模块——对每个候选算一个匹配分,特征包括语义相似度、任务所需能力、工具历史成功率、成本/延迟、权限与前置条件,选最高分。打分模块的价值是把 LLM 的黑盒决策变成可观测、可调权重的显式排序;分数接近时反问用户或给候选让用户确认,误选后允许自我纠正换工具。"

通俗类比

像外卖平台派单:用户点单后不是随机喊个骑手,而是先在附近圈一批候选人(LLM 粗筛),再给每个骑手打分——距离近不近、好评率高不高、手上单多不多、配送费贵不贵(打分特征),综合分最高的接单(精排)。两个骑手分数差不多时,让用户自己挑;骑手接错单了还能改派(自我纠正)。

详细拆解

1. 为什么需要显式的选择机制

  • 工具一多(>10 个),LLM 靠纯文本判断选错概率上升;不同工具还有成本、延迟、权限、副作用差异,选错代价不一。
  • 多个工具"都能干"时,单靠 LLM 容易挑到"名字像但最贵"的那个——需要一个统一的打分标准。

2. 方案一:纯 LLM function calling(简单场景)

  • 工具描述写好触发条件,让模型自己选。优点是零额外模块;缺点是工具多了准确率下降、不可观测、难调优。

3. 方案二:打分/排序模块(多工具场景)

4. 打分特征(可解释、可调)

特征来源作用
语义相似度任务 embedding vs 工具描述 embedding基础匹配度
能力覆盖任务所需能力 vs 工具能力标签判断"干得了吗"
历史成功率线上日志统计/用户反馈越用越准,冷启动给先验
成本/延迟工具自身画像同等匹配选便宜的
权限/前置条件规则表没权限的候选直接过滤
  • 精排可以用交叉编码器(cross-encoder)对候选两两打分,或直接加权线性公式(可解释、好调);历史成功率可以像"多臂老虎机(MAB)"那样边用边更新。

5. 消歧与纠错

  • 候选分数接近(差 < 阈值)→ 反问用户或列出候选让用户确认。
  • 执行后结果不对,允许 Agent换一个工具重试,并把"这次选错"记进历史成功率。
  • 打分不一致时,以规则/业务约束为最高优先(如涉及钱的操作强制走审批),再谈分数。
面试官追问
Q:打分模块会不会反而增加延迟和成本?
会有,所以要省着用:先用规则/LLM 把候选压到 2~3 个,再打分;特征里 embedding 相似度可以预计算缓存;只有"确实存在选择空间"时才走精排,单一明确工具直接跳过。延迟换准确率,值不值看工具选错代价。
Q:没有历史成功率数据时怎么冷启动?
给每个工具一个中性先验(如 0.5),主要靠语义匹配分跑起来;上线后用反馈逐渐更新;也可以先用规则/专家经验预设权重,等数据积累再调。
Q:打分模块和 LLM 决策不一致,听谁的?
分情况:硬约束(权限、必填前置)打分模块一票否决;软偏好(成本、历史)以打分为主;LLM 有额外上下文理解(如用户语气暗示)时可覆盖打分结果,但要把"覆盖"记日志,事后复盘谁对,反哺权重。
Q:两个工具语义几乎一样(两个查天气的 API)怎么区分?
语义分区分不开,就靠非语义特征:成本、限流额度、可用性、数据覆盖范围、SLA。把这些做成工具画像,语义分打平后由画像分决定;再不行就按"主备"配置:主用挂了 failover 到备用。
术语卡
工具路由:把任务分派给最合适工具的过程。
召回+精排:先粗筛候选,再精确排序。
交叉编码器:拼接两段文本一起打分,精度高。
工具画像:描述工具能力/成本/权限的元信息。
MAB:多臂老虎机,边用边学选哪个。
