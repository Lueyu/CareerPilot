Agent核心 · Q44

如果让你设计一个能行程规划的旅行Agent，你会如何拆解任务？各子Agent职责怎么划分？

⭐⭐⭐ #场景设计#任务分解 字节(真题)
先说人话:这题问的是:把"五天行程、卡预算、带娃"这类麻烦事，拆成职责清楚、互不踩脚的子Agent，再由总控统一调度——本质是分布式架构的"服务拆分+调度编排"换了张业务皮。面试官爱考它，因为它一秒区分"喊口号上多Agent"和"真拆过系统"的人;最大翻车点:按流程步骤切子Agent，切完互相打架。
30秒电梯稿

我会用「总控规划 + 专业子Agent + 约束求解」三层拆解：第一步，总控Agent先过需求澄清关——去哪儿、几天、几人、预算、偏好忌口，信息不齐不往下走；第二步，任务按数据源拆给交通、住宿、景点、餐饮四个领域子Agent，各带最小工具集，并行去拉候选；第三步，所有候选汇入约束求解层，由它统一校验时间窗、预算、地理距离这些硬约束，做冲突检测和择优，总控再把top-k行程拼装出来；预订一律两段式——只出方案，用户点头才真下单。核心原则一句话：子Agent按"数据源/工具"边界切，绝不按"步骤"切——就像微服务按业务域拆、从不按调用顺序拆，这样职责才清晰、才能并行、才能独立替换。

通俗类比

整套系统(用你天天在做的"备份平台任务编排"想):表面看这是一家定制旅行社——行程顾问问清预算偏好，机票组、酒店组、景点组各查各的资源，还有个调度员盯冲突；但骨架完全是分布式系统的老三样:Orchestrator 编排器(总控Agent，只拆单不干活，像调度中心里从不碰数据、只发任务单的主节点)+ 执行代理(四个领域子Agent，像各管一种介质的备份代理——磁带代理不操心云存储怎么传，交通Agent也不操心酒店房态)+ 全局校验器(约束层，像quota校验服务，谁的结果都必须过它这一关才能拼进行程)。

总控Agent(用K8s的控制器想):读全局、拆任务、盯进度，自己一个航班都不查。哪里像:都是"控制面不下场干活"——职责是让正确的事发生，不是亲手做完每件事。哪里不像:K8s控制面对接的是确定性API，总控面对的是"都行、随便"的真人，所以它比传统编排器多一项灵魂任务——需求澄清:把模糊意图逼问成结构化参数。答这题漏了这一步，后面切得再漂亮也是白切。

领域子Agent(用按业务域拆分的微服务想):交通、住宿、景点、餐饮各持私有工具集，互不越界。哪里像:单一职责、可独立部署替换、故障隔离——景点Agent超时不拖垮交通Agent，正如订单服务挂了不牵连库存服务。哪里不像:微服务之间可以信任对方的返回值，子Agent的输出是LLM生成的、天然带不确定性，所以只能当"候选"，必须送约束层校验后才能当事实用——相当于每个下游响应都要多过一道schema加语义校验，这是微服务时代没有的额外保险。

约束求解层(用中心quota/容量校验服务想):时间窗、预算、距离这些跨领域的账，谁都不许自己算，统一到它这儿结。哪里像:中心配额服务——各服务自己报价，全局账本只有一个人管，超限只有它有权拒。哪里不像:quota只有"批/拒"两个按钮，约束层还得给出"怎么改"的修复建议——换顺序、换替代、降档，更像一个带自愈建议的巡检校验器。

详细拆解

1. 为什么不做一个大 Agent 全干？（先讲拆分的理由）

先把"为什么要拆"答清楚，后面的切法才立得住。三条理由，条条都能在你过去的设计文档里找到原型:

  • 工具太多，模型会选错:Agent 挑工具，对LLM来说是一道"选择题"——航班、酒店、地图、点评、天气全塞给一个Agent，选项一多、语义一近(比如"查酒店位置"和"查地图坐标"长得几乎一样)，选错工具的概率就会上升。和你把两百条命令塞进一个巨型运维脚本是同一种病:人都会翻错行，模型更会。
  • 上下文互相污染:各子领域上下文差异大，查酒店返回的几百行JSON会挤占查航班需要的注意力；拆开后每个系统提示词只描述自己领域，更聚焦，还能可独立评估与迭代——给每个子Agent单独跑评测集，谁弱补谁，支持灰度发布新版本，互不牵连。
  • 问题结构本身就是"并行收集 + 集中求解":行程规划是多目标约束问题，航班/酒店/景点/餐厅四路数据互不依赖，天然适合先并行收、再集中解——结构上就是MapReduce的形状:map=四个子Agent各拉各的候选，reduce=约束层统一组合择优。

顺手把拆分的代价也说出口(这是加分项，显得你真拆过系统而不是画过PPT):Agent之间每多一条消息，就多一次语义损耗和延迟，和微服务拆分一模一样——拆太碎就是过度工程。4~6个领域Agent够用，别为了架构图好看拆出30个。

2. 拓扑：总控 + 专业子 Agent + 约束层（控制面/数据面分离）

分层的依据是"谁碰真实世界":总控和约束层属于控制面——读全局、算账、做决策，本身无副作用；四个领域子Agent是数据面——真正去调外部API、产生预订动作。这正是你天天画的那种分离:总控在顶上只拆单不下场，四个子Agent居中各查各的数据源，成果全部沉到最底部的约束求解层统一校验。约束层为什么不并进总控？因为它是纯计算、无状态、可重放——单独一层才能离线跑评测、才能水平扩容，动机和"把校验逻辑从调度器里拆出来"完全相同。

静态拓扑回答"谁是谁"，再看一张动态流程——一次真实请求从头到尾怎么跑。重点盯②③两步:派发是并行的，汇总是有主的:

3. 各子 Agent 职责与工具边界（表格画清楚）

表里补了一列"类比"，把每个角色对到分布式系统里的老朋友——你会发现它和"调度器+各介质代理+校验服务"的职责划分其实是同一张表，只是介质从磁带/云存储换成了航班/酒店。顺带解释表里两个缩写:POI指地图上的兴趣点(一个个可去的地点)，OTA指在线旅游平台(订房订票的那类网站)。

子 Agent职责读/写典型工具类比:它在分布式系统里像谁
总控澄清需求、拆任务、拼行程、处理用户调整只读为主意图理解、需求抽取任务编排器:读全局、发任务单，自己不IO
交通给出时刻、价格、换乘方案只读 + 预订(两段式)航班/高铁查询 API对接外部专线的适配服务，写操作走两段式事务
住宿给出位置、评分、价位的酒店候选只读 + 预订(两段式)酒店/OTA API预订事务的prepare/commit参与方
景点推荐景点、串出游览顺序只读POI、门票、点评 API只读查询服务，结果可缓存、可重放
餐饮按口味/位置/人均推荐餐厅只读点评/餐厅 API只读查询服务，结果可缓存、可重放
约束层时间窗、预算、距离约束的冲突检测与择优无副作用地图距离矩阵、规划求解器无状态纯计算服务(像quota校验器)，可重放、可离线跑
  • 读写边界铁律:默认全部只读；全系统唯一的写操作是"预订"，必须走两段式(先出方案并锁定，用户确认才真正下单)——等价于生产系统的"高危操作二次确认"。
  • 工具最小集:每个子Agent 3~5个工具为宜，工具描述当接口文档写——入参、出参、失败时返回什么，一个字段不许含糊。模型是照着描述选工具的，描述糊，它就糊。
  • 消息即契约:总控与子Agent之间传结构化消息(候选ID、价格、时刻、数据时间戳)，不传大段散文。时间戳的意义同备份集的快照时间点:不标时间的数据，你分不清它是"现在满房"还是"昨天满房"。

4. 关键设计：约束怎么传播与求解（这道题的加分点）

到这里骨架都搭完了，面试官真正在等的，是你把"多个Agent凑一块儿"推进到"约束求解系统"的那一步。拆三层讲:

4.1 约束分两种，待遇天差地别

类别违反的后果行程规划里的典型项类比(备份系统)
硬约束一票否决:违反=方案不可行航班起降时刻、入住14:00/退房12:00、景点闭馆日与停止入园时间、餐厅营业时间、预算上限、同行人数备份SLA:错过备份窗口=任务失败，没商量
软约束只扣分:影响排序，不影响可行顺路程度、口味/忌口偏好、评分高低、单日景点数上限(体力)、单程通勤时长压缩比/去重率:尽力而为，能高则高

先分类的收益巨大:硬约束一把筛掉不可行解，软约束只负责在剩下的解里排座次——求解从"大海捞针"变成"小池子里挑好的"。

4.2 两阶段求解:先广后深

  • 阶段一(广度):先让子Agent各自生成候选集——只要量，不做全局判断。这一步就是map阶段:各worker互不通信，谁慢了单独重试，不拖累别人。
  • 阶段二(深度):约束层再用"时间窗 + 距离矩阵 + 预算"对候选做组合搜索/打分，输出top-k行程。规模小(几天×每类几个候选)直接穷举+剪枝；规模一大，退化为贪心 + 局部搜索:贪心=按时间就近填充，局部搜索=在邻域内交换两个景点、换一家同类酒店再算一次分——不必硬上精确求解。
  • 串当天的游览顺序，本质是个小型旅行商问题；真要较真，可以上约束求解求解器(如OR-Tools的CP-SAT)。但面试要讲清"什么时候才值得上":候选规模小时，手写的剪枝逻辑更可调试、更好解释。把"可解释的次优解"优先于"不可解释的最优解"——用户问"为什么没排上熊猫基地"，你必须答得出来。

4.3 冲突检测与修复:拿真实数字算一遍

题面里的经典冲突:"景点 A 和酒店相距 2 小时车程，但当天时间窗只剩 1 小时"——这就是触发调整(换酒店/删景点/改顺序)并回写原因的信号。落到具体数字更直观，以带娃的成都行为例:

5月1日下午的"时间账"——硬约束全部画到轴上, 冲突一眼可见

   12:00              14:00                16:00              21:00
     │                  │                    │                 │
  ───┼──────────────────┼────────────────────┼─────────────────┼────▶
  航班落地          酒店可入住          熊猫基地停止入园      回酒店歇了

  算账: 12:00落地 → 取行李进城吃午饭 ≈ 2h → 14:00到酒店放行李再出发 ≈ 0.5h
        酒店到熊猫基地单程 ≈ 1h(在郊区) ⇒ 15:30才进园, 16:00就停止入园
        而官方建议游览 3h ⇒ 硬约束打架, 这天排不下!

  修复选项按代价排(同备份系统的降级策略):
    ① 改顺序: 熊猫基地挪到5月2日一早, 1日下午改市区宽窄巷子 —— 零成本, 默认选它
    ② 换替代: 换成2小时能逛完的同类景点 —— 低成本
    ③ 有损项: 删熊猫基地 / 加一天 / 加预算 —— 必须用户点头

修复策略按代价排序，同备份系统的降级策略同构:①改顺序(零成本)→②换同类替代(低成本)→③删项/加天数/加预算(有损，必须用户点头)。每次修复都回写原因，让总控能向用户解释"为什么这么排"，而不是默默吞掉——沉默的调整，会在用户心里透支信用。

5. 交互与兜底（工程味最重的一段，最能露怯，也最能加分）

  • 迭代式生成:先出框架让用户确认，再逐段细化，避免一次性生成 7 天行程全部返工。这正是备份软件"恢复向导"的交互:先预览待恢复的文件清单，点确认才真正执行恢复。先小步确认，后续修改都落在增量上，不做全量重算。
  • 预订类写操作一律两段式(Agent 只出方案，用户确认才下单):prepare=锁价、留房、给保留时限；commit=用户点头后真正下单。思想上就是两阶段提交——哪里像:两段确认，prepare阶段可回滚，失败不留半个事务；哪里不像:2PC的commit由协调者自动触发，这里必须人工点头，因为下单花钱是真实世界里不可逆的副作用。下单请求带幂等键，防手抖双击重复订。
  • 查询失败降级:查询失败降级为"给建议 + 让用户自查"，别让整单卡死；某个子Agent持续超时，按断路器熔断，输出"部分行程"并标注缺失环节——单个数据源抽风，没理由拖死整张行程单。
  • 所有推荐留依据(价格、评分、距离，外加数据时间戳)，支撑"为什么选这家"的追问(见 Q47)——等价于审计日志:可回放、可对账，出了投诉能自证清白。

6. 收个尾:这套设计里，LLM到底站在哪

并行派发、约束校验、超时重试、两段式下单——这些确定性流程全部交给工程组件，便宜、稳定、可回归测试；LLM只配出现在两个位置:入口把"都行/随便"澄清成结构化参数，出口把脏数据(自由文本的点评、退改政策)归一成决策信号。能写成状态机的环节，绝不让模型拍板——这句话说完，面试官立刻知道你是系统工程师出身，不是套壳爱好者。

面试官追问
Q:为什么按"数据源"切子 Agent，而不是按"步骤"（查→排→出）切？
人话:按步骤切，每个Agent都揣着全套工具瞎摸；按数据源切，每个Agent兵器库最小、最专业，出了错也好定位是谁的锅。类比:这就是微服务按业务能力垂直拆——订单服务、库存服务各一个；没人按"接收请求→处理→返回"水平切，那样每个服务都得懂全部业务，改一处动全身。技术:工具列表对LLM是道选择题，选项越多、语义越近，误选率越高；按领域切让系统提示聚焦、可独立评估与灰度发布，同层子Agent还天然并行(像map阶段各自独立跑)；折中做法:领域切Agent，内部仍按查→筛→出的流程组织。
Q:预算约束是全局的，分散在各子 Agent 怎么保证不超？
人话:子Agent只许报价，不许替用户做预算决定；总账只有约束层一个人算，超了就降档，或者把选择题抛回给用户。类比:分布式存储的配额:每个卷各自用，局部谁也看不住总额，必须由中心quota服务统一记账、超限就拒——各Agent各自揣摩预算，总和必然失控。技术:子Agent输出结构化候选(带单项成本)，约束层做组合校验；超预算触发剪枝或降档(经济舱/快捷酒店)，降无可降就把"加预算还是降档"抛给用户；建议双档管理:硬上限必拒，软上限(±10%)提示后放行，别让一块钱卡死整单。
Q:两个子 Agent 给出矛盾信息（如酒店满房但交通按它排）怎么办？
人话:数据在流动，过期是常态不是bug；关键是别让旧信息毒害下游，发现就只重排受影响的局部。类比:增量备份链:全量失效，依赖它的增量全部作废，但也只重做这一条链，不会推倒整个备份策略；行程同理，酒店满房只回滚依赖该酒店的安排。技术:①锚点优先:先锁确定性强的(航班)，再围绕锚点查浮动项(酒店)；②关键结果带时间戳，下单前实时复验；③把"满房/售罄"建成结构化一等事件，不是文本里捎带的一句话；④冲突时按依赖图找受影响子图回滚重排，其余结论原样保留。
Q:子 Agent 之间要互相通信吗，还是都走总控中转？
人话:不许私聊，统一走总控中转——星型拓扑。类比:备份域里各备份代理从不直接互传任务，全由调度器统一下发、归集；P2P私聊很快会长出环形依赖，排查起来就是分布式死锁现场。技术:直接通信会让上下文两两污染、消息通道按n²膨胀、审计断链；星型让总控成为唯一事实汇聚点，可统一限流、回放、调试；子Agent确有协作需要(比如景点想参考酒店位置)时，由总控派单时把约束摘要注入任务参数，而不是让两个Agent自己开小会。
Q:用户确认完 5 天行程后，临时要改第 3 天，需要全部重排吗？
人话:不用，行程天生是"改哪补哪"的结构，只重跑受影响的局部。类比:恢复任务里只恢复单个文件，不是整卷重跑；缓存失效只evict对应的key，不是清全缓存。技术:行程建模为DAG(天→时段→活动)，每个活动记录依赖(住宿位置↔景点车程、航班时刻↔首日安排)；改第3天只重跑该天加前后衔接点的约束校验；若波及已下单项，进入两段式的退改流程，先算清退改费、给用户确认，绝不静默改单。
Q:这套设计和传统工作流引擎（如 Camunda、Temporal）有什么区别？哪些环节根本不需要 LLM？
人话:骨架部分——并行派发、约束校验、超时重试、两段式下单——用工作流引擎写死就行，更便宜、更确定、可回归测试；LLM只配出现在两个位置:入口理解模糊需求，出口归一化脏数据。类比:等于在传统备份流水线前面雇了个"听得懂人话的表单填写员"——表单之后怎么流转，还是老系统的事，没人让填写员去管理道。技术:能枚举成状态机的环节绝不让LLM拍板；LLM负责自然语言→结构化参数的需求抽取，以及把自由文本(点评/退改政策)变成决策信号；答"全靠LLM规划"是硬伤，答"LLM只在边界出力"才显功力。
术语卡
Multi-Agent 系统:多个各有工具与职责的Agent协作，完成单个Agent扛不动的复杂任务。
总控 Agent(Orchestrator):负责澄清、编排、汇总的调度者，只拆单、不下场IO。
约束求解:在硬/软约束下找"可行且较优"方案的组合优化问题。
候选集:各子Agent并行产出的备选结果集合——只算候选不算事实，必须过约束层校验。
两段式执行:先prepare出方案(锁价/留房)，用户确认后才commit下单，借自两阶段提交。
依赖回滚:上游事实(如满房)失效时，只重排依赖它的下游环节，同失效一条增量备份链。
贪心 + 局部搜索:组合爆炸时的近似解法——先就近填充，再在邻域内交换元素找更优。
断路器模式:下游持续失败就快速熔断，防止一个数据源拖死整张行程。
