Agent核心 · Q44

如果让你设计一个能行程规划的旅行Agent，你会如何拆解任务？各子Agent职责怎么划分？

⭐⭐⭐ #场景设计#任务分解 字节(真题)
30秒电梯稿

我会用"总控规划 + 专业子 Agent + 约束求解"三层拆解：总控 Agent 负责需求澄清（去哪儿、几天、几人、预算、偏好）并生成整体框架；下面挂交通、住宿、景点、餐饮四个专业子 Agent 各管一摊、各自带最小工具集；再有一个约束/编排层负责把时间窗、预算、地理距离这些硬约束做传播和冲突检测，最后汇总出可执行行程。核心原则：子 Agent 按"数据源/工具"边界切，不按"步骤"切，这样职责清晰、可独立替换。

通俗类比

就像一家定制旅行社的后台团队：先有一个行程顾问（总控）反复问清你的预算和喜好；然后他安排机票组、酒店组、景点组、餐饮组分别去查各自资源；中间有一个调度员（约束层）盯着"你中午 12 点落地，酒店 14 点才能入住、景点离酒店 40 分钟"这类冲突；最后顾问把所有方案拼成一张时间表交给你，你哪里不满意，他回到对应的组去改。

详细拆解

1. 为什么不做一个大 Agent 全干？（先讲拆分的理由）

  • 工具太多（航班、酒店、地图、点评、天气…）会让模型选错工具的概率上升；
  • 各子领域上下文差异大，拆开后系统提示词更聚焦、可独立评估与迭代；
  • 行程规划是多目标约束问题，天然需要并行收集 + 集中求解的结构。

2. 拓扑：总控 + 专业子 Agent + 约束层

3. 各子 Agent 职责与工具边界（表格画清楚）

子 Agent职责读/写典型工具
总控澄清需求、拆任务、拼行程、处理用户调整只读为主意图理解、需求抽取
交通给出时刻、价格、换乘方案只读 + 预订(两段式)航班/高铁查询 API
住宿给出位置、评分、价位的酒店候选只读 + 预订(两段式)酒店/OTA API
景点推荐景点、串出游览顺序只读POI、门票、点评 API
餐饮按口味/位置/人均推荐餐厅只读点评/餐厅 API
约束层时间窗、预算、距离约束的冲突检测与择优无副作用地图距离矩阵、规划求解器

4. 关键设计：约束怎么传播与求解（这道题的加分点）

  • 约束分类：硬约束（航班时间、酒店入住/退房、景点闭馆日、预算上限）必须满足；软约束（顺路、口味、评分）作为打分项参与择优。
  • 两阶段求解：先让子 Agent 各自生成候选集（广度），约束层再用"时间窗 + 距离矩阵 + 预算"做组合搜索/打分，输出 top-k 行程（深度）。
  • 冲突检测：如"景点 A 和酒店相距 2 小时但当天时间窗只剩 1 小时"→ 触发调整（换酒店/删景点/改顺序），并回写原因。
  • 复杂组合问题可退化为"贪心 + 局部搜索"，不必硬上精确求解；把"可解释的次优解"优先于"不可解释的最优解"。

5. 交互与兜底

  • 迭代式生成：先出框架让用户确认，再逐段细化，避免一次性生成 7 天行程全部返工。
  • 预订类写操作一律两段式（Agent 只出方案，用户确认才下单）；查询失败降级为"给建议 + 让用户自查"。
  • 所有推荐留依据（价格、评分、距离），支撑"为什么选这家"的追问（见 Q47）。
面试官追问
Q:为什么按"数据源"切子 Agent，而不是按"步骤"（查→排→出）切？
按步骤切会把"查航班""查酒店"都挤进一个"查询 Agent"，工具又杂又多；按领域切让每个 Agent 的上下文和工具高度内聚、系统提示更专业，也方便并行收集和独立升级。折中做法是"领域切 Agent，内部仍按查 → 排 → 出的流程组织"。
Q:预算约束是全局的，分散在各子 Agent 怎么保证不超？
子 Agent 只负责产出候选和单项成本，预算在约束层统一计算：约束层拿到各候选成本后做组合校验，超预算则触发剪枝或提示用户"加预算/降档"。不要让每个 Agent 各自揣摩预算，否则各算各的、总和失控。
Q:两个子 Agent 给出矛盾信息（如酒店满房但交通按它排）怎么办？
这是数据新鲜度 + 依赖顺序问题：先定"锚点"（如必去景点/固定航班），再围绕锚点查住宿；关键结果（满房/售罄）要实时校验并带时间戳；发现冲突时约束层按依赖图回滚相关部分重排，而不是全局重来。
术语卡
总控 Agent:负责澄清、编排、汇总的调度者。
约束求解:在硬/软约束下找可行且较优的方案。
候选集:各子 Agent 生成的备选结果集合。
两段式执行:先出方案、确认后再真正下单。
依赖回滚:上游结论失效时只重排受影响的环节。
