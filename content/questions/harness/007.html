Agent核心 · Q3

在 Agent 的设计中，"规划能力"至关重要。请谈谈目前有哪些主流方法可以赋予 LLM 规划能力？（例如 CoT, ToT, GoT等）

先说人话:LLM 天生只会「一口气把话吐完」，没有步骤、没有回头路，这题问的就是怎么给它装上「先拆解、再选路、错了能退」的规划骨架。面试官爱考，因为规划是 Agent 的脑——答成名词罗列暴露只会背论文，追问一句「你实际用哪个、为什么」，没落过地的立刻现形。

"这题按三条主线答，别按论文时间线背。① 推理路径增强——CoT 让模型逐步推理打底，Self-Consistency 采样多条路径投票求稳，要探索回溯就上 ToT 把推理变成树做搜索，GoT 进一步升级成图，支持分支合并汇聚；② 反思修正——Reflexion 让模型失败后自我批评，把教训写进记忆带着重试；③ 任务分解执行——Plan-and-Execute 先列步骤清单再逐步执行，ReWOO 把规划和观察解耦、一次出全量计划批量跑，省 token 又好并行。收尾给选型：线性任务 CoT 就够，答案抖就加投票，搜索型难题才配 ToT/GoT，长流程执行用先规划后执行——按任务结构选方法，这句是加分项。"

通俗类比

主框架(拿你最熟的运维世界想):LLM 本体像一台「无状态的一次性函数服务」——张嘴就是完整输出，没有步骤、没有重试、没有回滚。所谓「规划能力」，就是在外面给它包一层编排，让它像老运维干活：先出 runbook，再执行，错了复盘。下面每个方法，都能在你的舒适区里找到亲戚：

方法运维世界的亲戚一句话
CoT把心算改成写 runbook一步一检查点，别一口气算到底
Self-Consistency三副本 + 多数派投票用冗余对抗单路径偶发错误
ToT带剪枝的路径探索 + 死路回滚多方案并行评估，不行就回头
GoTSpark/Airflow 那种 DAG多路结果汇聚进下游节点
Reflexion故障复盘入库失败写教训，重试时带着
Plan-and-Execute先评审变更单再逐步执行长流程有主线，不迷路
ReWOO把逐条交互攒成批处理减少往返，天然好并行

CoT(用「心算改 runbook」想):把一长串心算改成带检查点的书面步骤。哪里像:都是把长流程拆成显式的中间步骤，每步结果看得见、可检查。哪里不像:runbook 每步有 exit code 可以失败即停，CoT 的中间步骤是自然语言，没有强校验，一步写歪它照样面不改色往下写。

Self-Consistency(用「三副本 quorum」想):k 条推理路径就是 k 个「副本」，多数投票就是 quorum。哪里像:都是拿冗余换可靠、投票收敛。哪里不像:存储副本是确定性复制、故障近似独立；这 k 条路径出自同一个模型的采样，撞上系统性盲区会一起错——相关故障，quorum 的前提就不成立了。

ToT / GoT(用「路径探索 + DAG 编排」想):ToT 就是迁移前把多条候选路径各自小流量验证、打分、死路回滚，活脱脱带剪枝的搜索；GoT 就是你天天看的任务 DAG,fan-out 并行探索、fan-in 汇聚进下游。哪里像:节点=状态、边=决策、评估=打分、回溯=回滚，机制同构。哪里不像:分布式系统里算子是确定性的、回滚有快照、指标客观;ToT/GoT 的「状态」是自然语言，评估器还是个会抖的 LLM,merge 这步本身可能产出幻觉，没有事务兜底。

Reflexion(用「postmortem 入库」想):任务失败查「日志」(执行轨迹)、写复盘、沉淀进记忆，下次带着教训重跑。哪里像:失败驱动学习、经验入库、重试携带，工作流一模一样。哪里不像:你的复盘改进的是 runbook 和告警规则，永久沉淀;Reflexion 不改模型权重，教训只活在上下文/记忆里，像打热补丁而不是升级固件，换个会话可能就忘了。

Plan-and-Execute / ReWOO(用「变更管理 + 攒批执行」想):先出完整操作序列、评审、再逐步执行，出岔子重新规划，就是标准变更流程；ReWOO 把「问一句-等结果-再问一句」攒成一次规划 + 批量执行，和你把 N 次同步往返改成 pipeline 是同一个念头。哪里像:计划与执行分离、减少往返、无依赖步骤可并行。哪里不像:变更单的步骤是确定性命令，P&E 每步是 LLM 现生成的动作，环境一变计划可能整体作废；ReWOO 省了往返，也牺牲了「边看边调」的适应性。

做题的直觉版也留一份:CoT 是写解题过程，SC 是同一题算三遍投票，ToT 是草稿纸上留分支、死路划掉回头，GoT 是把两页草稿合并成一页。

详细拆解

1. 为什么需要规划

  • 先看 LLM 的出厂形态：它是「自回归逐 token 生成」的一次性函数——从第一个字吐到最后一个字，像一条没有 checkpoint 的长事务:中途任何一步跑偏都会无声传导到结尾，没有中间落盘点、没有回滚点。复杂任务(多步推理、多工具协作、长流程)无法一步到位，LLM 一次性生成容易遗漏、跑偏、幻觉。
  • 它还像一台无状态服务:所谓「记忆」全在请求体(上下文窗口)里，请求结束什么都不留——单次请求内的 KV Cache 只是会话级加速，跨请求想要状态得靠外挂记忆。所以要像给无状态服务配编排层一样，给 LLM 配一层规划。
  • 规划 = 把任务分解 + 选择执行路径 + 依据反馈调整。这三个动词正好框住下面全部方法：路径增强类管「选路」(CoT/SC/ToT/GoT),任务分解类管「拆」(Plan-and-Execute/ReWOO),反思类管「调整」(Reflexion)。

2. CoT 与 Self-Consistency:线性推理的两次升级

  • CoT(Chain-of-Thought):在 prompt 里给 few-shot 的「逐步推理」示例，或零样本直接说 "Let's think step by step",把中间推理显式化(零样本版来自 Kojima 等;few-shot 版来自 Wei 等)。机制：把「一步出答案」拆成「多步出答案」，每个中间 token 都是白送的额外计算空间。工程直觉：这就是把黑盒脚本改成带日志输出的版本——推理从模型内部一闪而过，变成你能看见、能检查的文本。免费午餐：不改模型、不训练，只改问法。
  • Self-Consistency:同一问题带温度采样 k 条推理路径，对最终答案多数投票。用「多路径」对抗单条路径的偶然错误，代价是调用次数 ×k——串行做延迟直接翻 k 倍、P99 会难看，工程上通常并行采样摊回来。前提记住：投票治「偶发错」，治不了「系统性错」，模型集体盲区时 k 条一起栽。
  • 两者的结构区别，一张图记牢：
CoT(单链, 一口气推到底):
  问题 ──▶ 想一步 ──▶ 再想一步 ──▶ 再想一步 ──▶ 答案
              └─ 中途写歪? 没有回滚点, 错误一路传导到底

Self-Consistency(多链 + 多数投票):
                问题
                 │  同一道题, 带温度采样 k 次
     ┌───────────┼───────────┐
     ▼           ▼           ▼
   路径1        路径2        路径3
  想…想…想    想…想…想    想…想…想
     │           │           │
    42          42          17
     └───────────┴─────┬─────┘
                       ▼
                多数投票 → 42 ✅
             (17 那条的偶发错误被多数派淹没)
  • 适用边界：投票要求答案可比较——数学题、选择题这类有离散答案的可以；开放式生成(写文案)没有可投票的对象，得换「LLM 当裁判打分」。别把 SC 硬套到写周报的活上。

3. ToT(树状思维):把推理变成搜索问题

  • 把推理建模成树:每个节点 = 一个「思考状态」(到目前为止的推理进展);每一轮做三件事——① 用 LLM 从当前状态生成 k 个候选下一步；② 用一个评估器(LLM 打分/启发式)给节点打分；③ 用 BFS/DFS 搜索 + 剪枝，沿高分分支深入、回溯低分分支，一般只保留 top-k 条活分支。浅而宽的任务(如 24 点)用 BFS,深而窄的任务(如长文写作)用 DFS。
  • 这就是你熟悉的「探索 + 回滚」：多条恢复路径各先小规模验证(打分)，可行的才全量执行(深入)，失败的回滚(回溯)。区别：你的回滚有快照、评估有硬指标;ToT 的状态是自然语言，评估器本身是个会抖的 LLM——「打分」这步的噪声直接决定搜索质量。
  • 适合：需要探索多方案、可回溯的任务(24 点游戏、创意写作、解谜)。ToT 论文的名场面：24 点游戏上 GPT-4 用 CoT 成功率只有 4%,ToT 拉到 74%。
  • 代价：调用次数随深度指数级增长(深度 d、每层宽度 b,最坏约 O(b^d)),贵且慢——它只配用在「单路径成功率低、且任务值这个钱」的地方。

      ▼               ▼               ▼

4. GoT(图状思维):允许把两页草稿合并

  • 把树进一步泛化成图:多个想法可以汇聚(combine/merge)成一个新想法，支持聚合、循环、引用。树里信息只能从父到子单向流；图里 A 分支和 B 分支的结果可以一起喂给一个新节点，产出「1+1 大于 2」的综合结论，还能对某个节点做 refine(自我改进)再往下走，甚至循环迭代。
  • 结构上就是你天天打交道的任务 DAG:fan-out 并行探索、fan-in 汇聚进下游。哪里不一样:DAG 调度器里的算子是确定性函数，reduce 一万次结果都一致；GoT 的 merge 是让 LLM 读几段推理融合出新结论，这一步本身可能引入幻觉，没有事务兜底。论文用归并式排序、多文档合并这类任务演示 merge 的威力。
  • 比 ToT 更灵活，适合需要「综合多个线索」的推理；但编排复杂度更高——树只要记父亲，图要维护任意拓扑和消息传递，排错也更费劲。

                            ├── merge ──▶ [融合 A+B 的新结论] ──┐
[子问题2] ─推理─▶ [结论B] ──┘                                 │
                                                              ▼
[子问题3] ─推理─▶ [结论C] ── refine 自我改进 ──▶ [结论C+] ──▶ [最终答案]
     ▲                                                        │
     └────────── loop: 结果不满意, 再迭代一轮 ◀────────────────┘

5. 反思修正类：给失败装一个学习回路

  • Reflexion:执行失败 → 模型生成「语言化反思」(我哪里错了、为什么)→ 存进记忆(episodic memory)→ 带反思重试，类似「口头强化学习」——不更新权重，把教训当文本存着，下一轮拼进上下文。工作流和你写 postmortem 一模一样：任务挂了查日志(执行轨迹)、写复盘入库、下次 runbook 多一条 guard 再重跑。
  • 像与不像：复盘改进的是文档和告警规则，永久沉淀在知识库;Reflexion 的反思通常活在会话/记忆里，上下文一翻篇可能就丢——是热补丁，不是固件升级。真要固化，得走 SFT/RL 去改参数。
  • 配套还有 Self-Refine(自我纠错：生成→自评→改写循环)、CRITIC(用外部工具校验：让代码执行器、搜索器当裁判，不只听模型自己给自己打分)等。
     ┌─────────▶ [执行任务] ──▶ 评估 ──通过──▶ 输出结果, 收工
     │                │
     │             不通过(失败 / 不达标)
     │                ▼
     │    [生成语言化反思: 哪一步错了? 为什么?]
     │                │
     │                ▼
     │    [反思写入记忆, 下一轮拼进上下文]
     │                │
     └── 带着教训重试 ◀┘

6. 任务分解执行类：Agent 真正干活的两件套

  • Plan-and-Execute(思想同 Plan-and-Solve,LangChain 有现成实现):先让 Planner 输出一份「计划步骤列表」，再由 Executor 逐步执行，执行中可 Replan——某步结果和预期不符，把新观察喂回 Planner 重出计划。好处：长任务不丢目标(计划钉在上下文里，像 runbook 钉在工单上)、上下文更聚焦(每步只喂当前步需要的，而不是把混乱的完整历史全塞给模型)。
  • ReWOO:把「规划」与「观察」解耦——先一次性生成完整计划(含工具调用占位)，再批量执行、最后由 Solver 汇总，减少与环境反复交互的轮次。省在哪：ReAct 式交互里每步都要把「计划 + 全部历史观察」重发一遍，观察越长越贵；ReWOO 规划只做一次、观察不回灌，论文报告 token 效率约为 ReAct 的 5 倍、精度还略有提升。且无依赖步骤天然可并行——这本身就是个 DAG 调度问题。
  • 取舍：ReWOO 快且省，但计划先于观察生成，环境一变计划里的假设可能过时(像提前生成的执行计划撞上统计信息变化)，适应性不如边看边走的 ReAct。
Plan-and-Execute(先规划, 边执行边修正):
  [Planner] ──▶ 计划: ①查库存 → ②查单价 → ③算总价 → ④写报告
      ▲                                           │
      │           逐步执行, 每步产生观察反馈         │
      └── Replan: 第②步结果异常, 重出计划再继续 ◀─────┘

ReWOO(一次规划, 批量执行):
  第1步  一次性生成全量计划(带占位符):
           E1 = 查库存(物料X)
           E2 = 查单价(物料X)
           E3 = 总价 = #E1 × #E2        ← "#E1"是占位符, 执行后回填
  第2步  批量执行: E1、E2 无依赖可并行, 再算 E3
  第3步  [Solver] 汇总全部结果 ──▶ 答案

7. 方法对比与选型

方法结构核心机制代价 / 适用
CoT线性链逐步推理便宜,通用
Self-Consistency多条链采样 + 投票×k 调用,提升稳定性
ToT树分支 + 评估 + 回溯搜索指数级,探索型任务
GoT图分支 + 汇聚 + 循环更灵活,编排复杂
Reflexion循环 + 记忆失败反思重试迭代提升,需评估器
Plan-and-Execute计划 + 步骤先规划后执行长流程,可重规划
ReWOO计划 + 占位批量执行规划与观察解耦省 token、可并行,计划易过时
  • 调用成本心里要有把尺:CoT 1 次 → Self-Consistency k 次 → Plan-and-Execute 约等于步骤数 → ToT/GoT 指数级再加编排开销。
  • 选型不背名词，按任务结构走决策路径：
拿到任务, 按顺序问自己:

 ① 线性推理能搞定吗? ──── 能 ───▶ CoT(1 次调用, 先跑基线)
        │ 不能, 或答案不稳
        ▼
 ② 同题多跑几次答案抖吗? ── 抖 ──▶ 加 Self-Consistency(k 次采样换稳定)
        │ 需要探索多方案, 可能走死要回头
        ▼
 ③ 是搜索型难题吗? ─────── 是 ───▶ ToT(要回溯) / GoT(还要多路汇聚)
        │ 是长流程、多工具的执行任务
        ▼
 ④ 要按步骤执行吗? ─────── 是 ───▶ Plan-and-Execute(要边看边调)
                                     / ReWOO(要省 token、好并行)
        │ 失败率高, 要自我修正
        ▼
 ⑤ 会反复失败吗? ──────── 会 ───▶ 叠加 Reflexion(复盘入库, 带教训重试)
  • 落地提醒：新方法别一把梭全量，先灰度发布小流量，盯任务成功率和 token 成本两条曲线，再决定放量还是回退——和你上任何编排改动是同一套纪律。
面试官追问
Q:CoT 为什么有效？有共识的解释吗？
人话:学界没有定论，但有三条主流解释撑住场面：多出计算空间、贴合训练分布、显式中间结论防丢失。类比:像把一条没有 checkpoint 的长事务拆成多个带落盘的小事务——每步有中间结果可依赖，错误暴露在更小的粒度上，不至于无声传导到结尾。技术:① 自回归生成下，中间 token 相当于额外计算步骤，把「一步出答案」的急转弯拉平；② 预训练语料里海量带推导过程的文本，CoT 让模型回到熟悉的分布；③ 多跳问题中显式写下中间结论，减少远距离信息被注意力稀释。诚实的说法是「经验上有效 + 机制仍在研究」，别硬编一个错误理论。
Q:ToT 调用成本这么高，什么时候才值得用？
人话:任务「有明确中间状态、候选可评估、单路径容易卡死需要回头」才值得，比如解谜、数学搜索、创意规划；日常问答、摘要、翻译这种线性活，ToT 纯属高射炮打蚊子。类比:像跨机房大迁移才值得先小流量灰度验证多条路径再全量执行；日常备份任务一条脚本跑完就完了，没人给每个 job 搞全量演练。技术:看成本量级:CoT 1 次、SC k 次、ToT 随深度指数级。判断式是「单路径成功率低到值得搜索」：论文里 24 点游戏 GPT-4 用 CoT 成功率 4%,ToT 到 74%——这种量级的差距才配得上指数成本，讲出这个权衡比背方法名重要。
Q:规划能力靠 prompt 就够了，还是需要微调？
人话:先 prompt 后微调：prompt 验证可行性，微调把验证过的东西内化成稳定能力，两条腿走路。类比:先用脚本加现成工具拼一版自动化，跑稳了再固化成产品代码——prompt 是运维脚本，灵活但每次现拼；SFT 是固化成服务，稳定、便宜、扛并发。技术:① 短平快场景 CoT/ToT/ReAct 纯 prompt 即可，零训练成本、快速迭代；② 当小模型规划格式不稳、工具选择错率高、QPS 上来成本扛不住时，用规划轨迹和 FC 数据做 SFT;③ 常见路线是强模型生成轨迹蒸馏给小模型上线，两头的好处都要。
Q:Self-Consistency 投票是不是就像多副本，一定能纠错吗？
人话:能纠「偶然错」，纠不了「系统性错」——投票的前提是错误彼此独立。类比:quorum 假设副本故障独立，但三副本同批盘、同一个固件 bug 会一起挂；k 条路径来自同一个模型、同一套偏见，撞上知识盲区就集体翻车——相关故障，多数派救不了。技术:SC 依赖 temperature 大于 0 让路径有差异，只在「路径错误近似独立 + 答案可比较」时有效；开放式生成没有可投票的离散答案，要换 LLM-as-judge 打分；还要防「自信地错」的多数派，k 加大收益边际递减。
Q:ReAct 算不算规划？它和 Plan-and-Execute 什么区别？
人话:ReAct 是「走一步看一步」，Plan-and-Execute 是「先画路线图再上路」，一个响应式，一个先规划式。类比:ReAct 像交互式排障，敲一条命令看输出再敲下一条；P&E 像先写完整 runbook 再批量执行——前者灵活但容易走着走着忘了目标，后者有主线但环境突变时计划容易过时。技术:ReAct 每轮 Thought→Action→Observation,观察实时进上下文，适应性强、轮次多、token 贵;P&E 由 Planner 一次出步骤列表，Executor 逐步执行，必要时 Replan。工程上按任务长度选：短交互 ReAct,长流程 P&E/ReWOO。
Q:这些方法在一个真实 Agent 里怎么组合使用？
人话:不是五选一，是分层叠加：骨架用 Plan-and-Execute,单步用 ReAct 调工具，关键判断用 SC 投票，失败叠 Reflexion,全程写记忆。类比:备份体系从来不是单一技术，是调度器 + 分层存储 + 重试策略 + 复盘机制的组合拳；规划方法同理，按职责组合，各管一段。技术:典型链路:Planner 出步骤列表 → Executor 逐步 ReAct 执行 → 难点子任务上 ToT/SC → 失败触发反思重试 → 结果与反思沉淀进记忆供下次检索。上线先灰度发布小流量，盯成功率与 token 成本两条曲线再放量。
术语卡
CoT:Chain-of-Thought,让模型把中间推理一步步写出来再给答案的提示方法。
Self-Consistency:同一问题采样多条推理路径、对最终答案做多数投票的稳定化技巧。
ToT:Tree of Thoughts,把推理组织成树，靠「生成候选 + 评估打分 + 剪枝回溯」做搜索。
GoT:Graph of Thoughts,把树泛化成图，支持多路想法的汇聚、精炼与循环。
Reflexion:失败后生成语言化反思存入记忆、带着教训重试的自我改进框架。
Plan-and-Execute:Planner 先出步骤清单、Executor 逐步执行、必要时 Replan 的执行范式。
ReWOO:Reasoning WithOut Observation,把规划与观察解耦、一次生成全量计划批量执行，主打省 token。
BFS / DFS:广度/深度优先搜索，ToT 做树搜索的两把基本工具。
DAG:有向无环图，GoT 的结构基础，也是你熟悉的任务编排拓扑。
