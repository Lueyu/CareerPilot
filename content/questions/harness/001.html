系统设计 · Q2

设计一个 Multi-Agent 协作系统(电商智能客服场景)

⭐⭐⭐⭐⭐ #MultiAgent#系统设计#协作 字节 / 阿里(真题)
30秒电梯稿

"我用 Supervisor 模式:一个主管 Agent 负责理解意图、拆任务、分诊,三个专业 Agent(订单/物流/售后)各管一摊、各自带最小化的工具集;会话状态统一放 Redis,Agent 本身无状态、可水平扩展;并发场景下主管可以并行调度多个 Agent;异常方面做超时控制、死循环防护、敏感操作审批和转人工兜底。选多 Agent 而不是单 Agent 的核心原因是每个 Agent 上下文更专注、工具更少,准确率更高、更好独立迭代。"

通俗类比

就是医院分诊台模式:病人描述症状(用户问题)→ 分诊台判断挂哪科(Supervisor 路由)→ 各科医生用自己科室的设备问诊(专业 Agent 调用各自的工具)→ 复杂病情请多科室会诊(多 Agent 协作)→ 最后分诊台汇总结果给你。如果只有一个"全科医生"(单 Agent)包治百病,他要么啥都会一点但都不精,要么设备太多手忙脚乱——这就是拆分 Agent 的意义。

详细拆解

1. 拓扑结构:Supervisor(星型)

路由方式:轻量意图分类器(小模型或规则)先粗分,拿不准的交给 Supervisor 用 LLM 判断;支持并行调度——"我的货到哪了顺便把发票改一下"这类复合请求,订单 Agent 和物流 Agent 同时干活。

2. 状态管理(关键考点)

  • Agent 无状态:所有会话状态(用户信息、对话历史、各 Agent 中间产出)存 Redis(热数据,带 TTL)+ 持久化数据库(冷备)。这样任何一个 Agent 实例挂了,请求换一台机器照样跑——这是高并发的的前提。
  • 上下文按需传递:不要把整个对话历史塞给每个 Agent,而是 Supervisor 生成"任务卡片"(用户是谁、要办什么、已知哪些字段),每个 Agent 只拿自己需要的——上下文又小又准,token 也省。
  • 关键业务状态(如退款单状态)用状态机管理,每次变更落库,可审计可回放。

3. 并发处理

  • 用户间并发:请求级隔离,Agent 无状态 + 水平扩展天然支持。
  • 请求内并发:asyncio / 线程池并行调用多个 Agent,用 asyncio.gather 汇聚结果。
  • 下游保护:对订单系统等内部 API 做限流 + 熔断,防止 Agent 流量打挂业务系统(面试官很爱问这一点:AI 系统不能成为压垮业务系统的元凶)。

4. 异常处理(体现工程成熟度)

  • 超时:单 Agent 调用限时(如 5s),超时降级。
  • 死循环防护:限制 Supervisor 最大调度轮次(如 8 轮)和总 token 预算,超了直接转人工。
  • 意图不清:反问用户澄清,而不是瞎猜。
  • 情绪检测:用户发火 / 连续不满意 → 无条件转人工。
  • 敏感操作:退款、改地址这类写操作,Agent 只能"起草",需要用户二次确认或人工审批后执行(工具层面做成两段式:预览 → 执行)。
  • 兜底:所有失败路径最终收敛到"转人工 + 道歉话术",绝不能让用户卡死在机器上。

5. 工具权限最小化:每个 Agent 只能访问自己领域的 API,售后 Agent 摸不到订单修改接口——就算被 Prompt 注入攻击,损失也被限制在最小范围。

面试官追问
Q:为什么要拆 3 个 Agent,一个大 Agent 加全部工具不行吗?
三个原因:① 工具一多(30+),模型选错工具的概率显著上升;② 每个 Agent 的系统提示词可以写得更专业、上下文更聚焦;③ 各 Agent 可独立迭代、独立评估、独立回滚,团队协作也好分工。反过来说,如果场景简单(工具 < 10 个、流程线性),单 Agent 更简单可靠——能说出这个 trade-off 才是加分项。
Q:Agent 之间怎么通信?
不直接对话,通过共享状态 + Supervisor 中转:子 Agent 写结果到会话状态,Supervisor 决定下一步。这比自由对话式(AutoGen 风格)更可控、好调试。
Q:怎么防止两个 Agent 互相踢皮球?
路由职责在 Supervisor 而不是子 Agent 自己声明"这不归我管";子 Agent 只执行不转发;Supervisor 路由置信度低时主动反问或转人工。
Q:怎么评估这个系统?
分 Agent 评估(各自的任务成功率、工具调用准确率)+ 端到端评估(问题解决率、转人工率、用户满意度),线上做 AB 实验,离线用 LLM-as-judge 批量回归测试集。
术语卡
Supervisor 模式:主管 Agent 统一调度子 Agent 的架构。
无状态服务:请求不依赖服务器内存,随便扩容。
HITL:Human-in-the-loop,关键环节人工介入。
两段式工具:先预览再执行,防误操作。
LLM-as-judge:用强模型给回答打分做自动评估。
