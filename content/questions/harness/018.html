Agent核心 · Q29

有没有做过工具调用失败后的feedback策略设计？

⭐⭐⭐ #错误恢复#反馈机制#反思 字节(真题)
先说人话:Agent 调工具就像备份作业调下游存储,失败是常态。这题问的是失败之后那套流程——错误怎么回灌、哪些能自愈、何时止损转人工——你有没有真设计过。面试官爱考它,因为它最容易分清「调过 API 的」和「做过容错链路的」:只会答『重试一下』,暴露的就是没碰过带副作用的线上系统。
30秒电梯稿

"做过,整条链路分两层反馈。① 机器侧自纠错:把工具失败转成结构化 observation(错误码+原因+建议下一步)回灌给 LLM,让它改参数、换工具、或向用户澄清——这是 ReAct 的循环;进阶是 Reflexion 式反思:失败后先写一段「失败归因+改进策略」,带着反思重试。② 人侧沉淀:失败先分类——瞬态的退避重试、副作用的走幂等+补偿、权限的直接转人工;失败样本回流评测集和 few-shot 库,反哺后续优化。两条铁律:错误先分类再处置、自纠错设预算上限(2~3 轮),防死循环。"

通俗类比

整条 feedback 链(拿备份作业的容错链路想):Agent 调一次工具,约等于备份作业去碰一次下游存储——失败是家常便饭,而成熟的备份系统从不把异常一抛了之:错误被编成结构化事件回给调度器,调度器按错误类型决定重试、换介质、跳过、还是升级人工。Agent 的 feedback 设计干的是同一件事,区别只有一个:「调度器」换成了一位读自然语言的 LLM,你喂给它的错误描述,就是它下一步动作的全部依据。

哪里像:失败先分类(瞬态/永久/逻辑)、重试有预算、连续失败熔断、副作用走补偿、兜底靠人工——五个环节一一对应,你分布式里攒下的直觉全部成立。哪里不像:调度器是确定性代码,if-else 写死即可;LLM 是概率系统,错误描述含糊它就归因错,恶意的工具返回甚至能反过来操纵它(提示注入)。于是多出两条传统容错里没有的纪律:错误信息要模板化生成,高危操作执行层要二次确认。

静默失败(拿静默数据损坏想):备份行业最怕的不是报错,而是「作业绿灯、恢复那一刻才发现数据是坏的」。哪里像:Agent 有同款灾难——工具挂了但没人告诉 LLM,它拿着空结果一本正经编答案,用户拿到错的还以为是对的;两者都是「不报错的错」,危害都大于显式失败。哪里不像:兜底手段不同——SDC 靠校验和+后台巡检,Agent 靠「失败必须显式回灌」+ 返回值 schema 校验,没有校验和这种数学工具可用了。

Reflexion 反思(拿故障复盘想):一次恢复失败后,工程师写 RCA 报告(根因/影响/改进措施)存进知识库,下次同类故障先查报告再动手。Reflexion 就是让 LLM 在重试前自己产出这段「归因+改进」文本,作为记忆带进下一轮。哪里像:都是把一次性失败沉淀成可复用经验,且经验能跨任务复用——反思文本可以进长期记忆,相当于 runbook。哪里不像:RCA 是人写的、质量可控;LLM 的反思是现场生成的,可能归因跑偏、可能车轱辘话,所以必须限轮数、控 token,还要拿评测集验证「反思真的提升了成功率」,没验证过的反思可能纯粹在烧钱。

补偿与幂等(拿你的老本行想):这条几乎不用翻译——副作用工具失败走补偿,就是分布式事务里的 补偿事务/Saga 模式。哪里像:查状态、幂等键、反向操作三件套原样照搬,一件不用改。哪里不像:传统 Saga 里「走哪条路」是代码判断,Agent 里可能交给 LLM 判断——所以幂等和审批必须由执行层代码兜死,不能信模型的自觉。

详细拆解

路线图:先讲为什么必须有 feedback(第 1 节),再讲机器怎么自纠错(第 2~3 节),然后人怎么分类处置、兜底和沉淀(第 4~6 节),最后给一张面试可背的清单(第 7 节)。

1. 为什么需要 feedback 设计(先讲价值)

  • 失败是常态而非异常:工具调用失败率不低——参数幻觉(LLM 编了个不存在/不合法的参数值)、下游抖动(超时、429 限流)、权限不足、上游接口 schema 变了没打招呼,每一类在线上天天发生。假定工具永远成功来设计 Agent,等于假定磁盘永不损坏来设计存储。
  • 最危险的不是失败,是静默失败:没有 feedback 的 Agent 会"静默失败"——LLM 不知道工具挂了,可能拿错误/空结果继续编答案,这是最危险的。备份行业对这种「作业绿灯、数据是坏的」有切身记忆:发现时已是恢复那一刻。对策也同源——把「成功与否」从隐式变成显式,强制回灌、强制校验。
  • 好的 feedback 让失败变成"可恢复"而非"直接崩":思路和容灾里的 RTO 分级同构——不追求消灭失败,而是控制失败的爆炸半径:能自愈的自愈、不能自愈的优雅降级、都兜不住的转人工。

2. 机器侧反馈:observation 循环

  • ReAct 模式:Thought(模型想一步)→ Action(调哪个工具、传什么参数)→ Observation(工具返回了什么),循环往复;工具结果(含失败)作为 observation 回灌,模型据其决定下一步。
  • Observation 是 LLM 感知外界的唯一通道:模型看不到工具内部、看不到网络、看不到日志,它只看得到你回灌的这段文本。整个多轮消息历史像一份只追加的作业日志,和 WAL 一个脾气——LLM 每一步都基于这份日志做决策,日志里没写的,对它来说就没发生。
  • 失败信息要结构化:{工具名, 错误码, 原因, 建议下一步},而不是只给一个异常字符串。一段 Python traceback 里 90% 是模型不需要关心的调用栈,而结构化字段能把「哪里错、为什么、怎么办」直接递到它手里。
  • 错误码语义直接抄 HTTP 的作业:HTTP 状态码的分法——参数错≈4xx(请求方的锅,改请求才有用)、下游挂≈5xx(可以试探重试)、429/超时≈瞬态(退避后再来)。照这套语义设计错误码,LLM「猜对下一步」的概率会明显上升,毕竟这些语义模式在它的训练语料里出现过无数次。
  • 让模型"知道失败"是自纠错的前提——错误处理第一原则:先把失败送到决策者眼前。

3. 进阶:Reflexion 式反思

  • Reflexion 核心:把"反思"作为一段文本记忆存下来,跨步骤复用;相比盲目重试,带反思的重试成功率高得多。
  • 这段记忆的三个去向(对应 RCA 的三种沉淀):① 只在本任务内用——反思附在下轮上下文里;② 存入跨会话的长期记忆,同类失败先查旧反思,相当于故障知识库;③ 高频失败模式沉淀成工具描述/系统提示词的修正,相当于把 RCA 结论写进 runbook。
  • 什么时候不用 Reflexion:瞬态错误(超时/429)直接退避重试就行,反思纯属浪费 token(token 是 LLM 的计长计费单位,约等于一两个汉字)——反思是给「上次做法本身有问题」的失败用的。

适用的失败类型瞬态错误(超时/429)参数错、工具选错、步骤拆分不当

4. 失败分类与处置(错误要先分类)

先说为什么「先分类」是铁律——这正是分布式系统的老常识:瞬态错误(网络抖动)用指数退避重试就能好;永久错误(介质坏了)重试一万次也是失败,得换副本;逻辑错误(配置错)得先改配置。分类错了,后面所有动作都是白费力气。Agent 侧一模一样,只是「分类器」从代码换成了错误码映射+LLM 的理解:

失败类型例子策略分布式老熟人
参数错误订单号格式错、缺必填回灌校验信息,让模型修正参数重试4xx:请求方的锅,改请求才有用
工具选错想查物流却调了比价反馈"无此工具+可用工具列表",重选路由错了,重新做服务发现
权限不足越权改地址不重试,转人工/要求用户授权403:鉴权不过,重试无意义
下游超时/限流429、超时幂等重试+退避;连续失败熔断504/429:教科书级可重试错误
返回空/异常搜不到结果反馈"无结果+换关键词建议",或降级话术查无此数据是「业务空」,不是故障
副作用失败扣款失败补偿/回滚,不盲目重试半提交事务,走补偿/Saga

表里第四行值得展开:「幂等重试+退避」——重试间隔按 1s/2s/4s 翻倍,给下游喘息窗口;「连续失败熔断」——短窗口内失败次数到阈值,就打开熔断器让后续请求直接走降级,别拿头去撞已经倒下的服务。这俩你在微服务里天天见,搬到 Agent 里一字不改。

5. 人侧反馈与沉淀

  • 转人工:预算耗尽、权限、敏感操作、用户情绪不满时收敛到人工。触发条件必须写死在代码里,不能指望 LLM「自己觉得该转了」——止损线和容灾预案里「什么条件触发主备切换」一样,由确定性逻辑拍板,不由手感拍板。
  • 补偿:已产生副作用的失败走补偿(退款/回滚),用幂等键保证不重复。就是分布式里的补偿事务/Saga:失败后先查实际状态——已生效走反向操作,未生效才带幂等键重试;「走哪条路」可以由 LLM 判断,但幂等与审批必须由执行层代码兜底。
  • 样本回流:失败样本 + 最终成功路径 → 进评测集(专门攒起来给 Agent 考试的题集)、few-shot 示例库(在 prompt 里放几个成功案例给模型当教材)、甚至用 DSPy 反优化 Prompt,形成闭环。等价于把每起故障沉淀成回归用例:下次改 prompt、换模型、调分类器,先在这批「历史上的失败」上跑一遍,不过不上线——这是 feedback 策略能持续变好的发动机。

6. 预算与兜底

  • 自纠错设上限:最多反思重试 2~3 轮,超过直接降级(兜底话术/转人工),防"反思-失败-再反思"死循环烧 token。
  • 为什么是 2~3 这个量级:经验规律是第一轮反思挽回率最高、第二轮边际收益骤降、第三轮后多为同义反复;预算的本质是止损线,和重试预算一样,要拿「每轮挽回率 × 单轮成本」算出来,不是拍脑袋。
  • 熔断与兜底联动:同一工具短窗口连续失败,先怀疑工具本身挂了——打开熔断器,后续请求直接走降级话术/备选工具,别让所有会话陪葬,窗口过后半开探测恢复。线上盯三个数:失败恢复率、平均反思轮数、降级转人工率;兜底率持续上涨说明策略在变保守,该回头修分类器,而不是继续加预算。

7. 收尾:一张面试可背的落地清单

  • 失败显式化:错误必须作为结构化 observation 回灌,杜绝静默失败;
  • 先分类再处置:错误码按 4xx/5xx 语义设计,瞬态/参数/权限/空结果/副作用五路分走;
  • 自纠错有预算:反思重试 ≤3 轮,瞬态错误走指数退避而不是反思;
  • 副作用有兜底:幂等键 + 查状态 + 补偿事务,执行层代码做最终裁决;
  • 失败有沉淀:样本回流评测集/few-shot 库,任何改动先跑失败注入回归,再小流量灰度发布。
面试官追问
Q:Reflexion 和普通重试的本质区别?
人话:普通重试是原样再来一遍,输入没变多半死在同一处;Reflexion 是重试前先让模型写一段「失败归因+改进策略」,把诊断带进下一轮——带着改动重做。类比:备份作业失败后盲目重跑 vs 先看作业日志归因:介质坏、网络抖、参数错,归因不同动作不同;不归因的重跑,十次还是十次失败。技术:Reflexion 把反思存成 episodic memory 注入下轮上下文;代价是每轮多一次 LLM 调用和 token,所以限 2~3 轮,只对参数错/选型错这类「值得反思」的失败启用,瞬态错误直接退避重试更划算。
Q:feedback 里给模型的错误信息,会不会被模型误解甚至被注入攻击?
人话:会。工具返回本质是外部输入,恶意内容可以借「错误信息」冒充指令操纵模型,这是真实攻击面。类比:和备份系统绝不裸信下游返回一个道理——恢复结果必须校验通过才敢标成功;提示注入就是 SQL 注入的 LLM 版:外部数据混进了指令通道。技术:① 错误信息由服务端模板化生成,不透传第三方原文;② 工具返回做 schema 校验+长度截断;③ 高危操作(退款/改地址)在执行层二次审批,不把「是否执行」交给被反馈影响的模型;④ 回灌前敏感字段脱敏。
Q:怎么衡量 feedback 策略有没有效?
人话:盯三个数:失败恢复率(失败后最终救回的比例,核心,要升)、平均反思/重试轮数(要降)、降级转人工率(兜底是否过重,直接影响 SLA)。类比:备份报表上的成功率不作数,定期真做一次恢复演练才算数——离线靠「失败注入」测试集回归,线上看三个指标的走势。技术:恢复率=feedback 后成功数/失败总数;轮数看均值和 P99,P99 高说明长尾请求在空转烧 token;兜底率持续涨说明策略保守,该修分类器;每次改 prompt/换模型先跑失败注入回归,再小流量灰度发布。
Q:这套东西和微服务里的重试/熔断/补偿有什么区别?
人话:骨架一样,差别在决策者:微服务里是确定性代码,Agent 里是 LLM,所以错误要转成它读得懂的结构化 observation,由它改参数、换工具、拆步骤。类比:把 LLM 当值班工程师:熔断器只会拉闸,工程师还会看报错换方案、判断要不要升级;设计 feedback 等于给这位值班工程师配告警模板、操作手册和止损红线。技术:复用指数退避、幂等键、熔断器三件套;新增 observation 回灌与反思预算两个组件;最大的坑是 LLM 可能错误归因甚至被注入,所以执行层的鉴权、幂等、二次确认一样都不能省。
Q:扣款这类有副作用的工具失败了,怎么处理?
人话:先查副作用到底发生没有,再决定补偿还是重试,绝不盲目重跑。类比:和恢复任务半途失败的处置一致:先盘点哪些卷已经写脏,再决定回滚还是断点续传;重试前先拿幂等键对账,否则就是双倍扣款事故。技术:① 副作用调用带唯一幂等键(订单ID+操作+版本),下游据此去重;② 失败后先调查询接口确认实际状态:已扣款走补偿事务(退款/逆向单),未扣款才允许重试;③ 补偿自身也可能失败,要有重试队列+日终对账兜底;④ 超出补偿预算转人工,并全链路留痕。
术语卡
ReAct:让 LLM 按 Thought→Action→Observation 循环「边想边调工具」的经典范式。
Reflexion:失败后先生成「归因+改进策略」文本、作为记忆带入下次重试的自我反思机制。
Observation:工具结果(含失败信息)回灌给模型的那条消息,是 LLM 感知外部世界的唯一通道。
幂等性:同一操作执行一次与多次效果相同,靠幂等键实现,是副作用工具敢重试的前提。
指数退避:重试间隔按 1s/2s/4s…翻倍拉长,给下游喘息窗口,专治超时与限流。
熔断器:短窗口连续失败后直接拒绝请求、过段时间半开探测恢复,防止整条链路陪葬。
补偿事务:副作用已发生时用反向操作(退款/回滚)恢复一致性,是 Saga 模式的核心构件。
提示注入:外部文本混进上下文冒充指令操纵模型,工具返回内容是最常见的攻击面。
DSPy:把 prompt 当可优化程序、按评测指标自动搜索最优提示的框架,失败样本可喂给它。
few-shot 库:精选示例的集合,放进 prompt 给模型当教材,失败到成功的样本是最好的教材。
