Agent核心 · Q29

有没有做过工具调用失败后的feedback策略设计？

⭐⭐⭐ #错误恢复#反馈机制#反思 字节(真题)
30秒电梯稿

"做过,分两层反馈:① 机器侧自纠错——把工具失败转成结构化 observation 回灌给 LLM(错误码+原因+建议),让它换参数/换工具/向用户澄清,这是 ReAct 的 observation 循环,进阶是 Reflexion 式的反思:失败后先"反思错在哪"再重试;② 人侧沉淀——失败分类后触发补偿(幂等/回滚)、转人工,并把失败样本回流进评测集和 few-shot 库,反哺后续优化。核心原则:错误先分类再处置,且给自纠错设预算上限,防死循环。"

通俗类比

就像学生做题对答案:做错一道题,先不看答案,自己反思"哪一步错了、为什么错"(Reflexion),带着反思重做一遍(重试),对了好;还不对就查错题本里有没有同类题的解法(检索经验),再不行就问老师(转人工)。做完把这道错题抄进错题本(失败样本回流),下次同类题就不会错。关键是:不能无限重做,错三次就停下来求助——这就是"自纠错预算"。

详细拆解

1. 为什么需要 feedback 设计(先讲价值)

  • 工具调用失败率不低:参数幻觉、下游抖动、权限不足、schema 变化都会导致失败。
  • 没有 feedback 的 Agent 会"静默失败"——LLM 不知道工具挂了,可能拿错误/空结果继续编答案,这是最危险的。
  • 好的 feedback 让失败变成"可恢复"而非"直接崩"。

2. 机器侧反馈:observation 循环

  • ReAct 模式:Thought → Action → Observation,工具结果(含失败)作为 observation 回灌,模型据其决定下一步。
  • 失败信息要结构化:{工具名, 错误码, 原因, 建议下一步},而不是只给一个异常字符串。
  • 让模型"知道失败"是自纠错的前提。

3. 进阶:Reflexion 式反思

  • Reflexion 核心:把"反思"作为一段文本记忆存下来,跨步骤复用;相比盲目重试,带反思的重试成功率高得多。

4. 失败分类与处置(错误要先分类)

失败类型例子策略
参数错误订单号格式错、缺必填回灌校验信息,让模型修正参数重试
工具选错想查物流却调了比价反馈"无此工具+可用工具列表",重选
权限不足越权改地址不重试,转人工/要求用户授权
下游超时/限流429、超时幂等重试+退避;连续失败熔断
返回空/异常搜不到结果反馈"无结果+换关键词建议",或降级话术
副作用失败扣款失败补偿/回滚,不盲目重试

5. 人侧反馈与沉淀

  • 转人工:预算耗尽、权限、敏感操作、用户情绪不满时收敛到人工。
  • 补偿:已产生副作用的失败走补偿(退款/回滚),用幂等键保证不重复。
  • 样本回流:失败样本 + 最终成功路径 → 进评测集、few-shot 示例库、甚至用 DSPy 反优化 Prompt,形成闭环。

6. 预算与兜底

  • 自纠错设上限:最多反思重试 2~3 轮,超过直接降级(兜底话术/转人工),防"反思-失败-再反思"死循环烧 token。
面试官追问
Q:Reflexion 和普通重试的本质区别?
普通重试是"原样再来一遍",问题不变多半还是失败;Reflexion 在重试前先让模型生成一段"失败归因 + 改进策略"的反思文本,把它带进下一次尝试,等于"带着诊断重做"。代价是每轮多一次 LLM 调用和 token,所以要限轮次,且只对"值得反思"的失败用。
Q:feedback 里给模型的错误信息,会不会被模型误解甚至被注入攻击?
有风险——工具返回的内容本质是外部数据,恶意返回可能诱导模型。防御:① 错误信息走"服务端模板化"而非原样透传第三方原文;② 对工具返回做 schema 校验和长度截断;③ 敏感操作(退款等)无论模型怎么被诱导,最终执行层都要二次确认/审批,不把"是否执行"完全交给被反馈影响的模型。
Q:怎么衡量 feedback 策略有没有效?
指标三个:① 失败恢复率——失败后经 feedback 最终成功的占比(核心);② 平均重试/反思轮数——越低越好;③ 降级/转人工率——兜底是否过重。离线用构造的失败注入测试集回归,线上监控这三个指标的走势。
术语卡
ReAct:Thought-Action-Observation 交替的推理-行动循环。
Reflexion:先反思失败原因、再带反思重试的机制。
Observation:工具调用返回的结果/反馈,回灌给模型。
补偿(Compensation):副作用已发生后的回滚/补救。
few-shot 库:可复用的示例集合,用于提示与优化。
