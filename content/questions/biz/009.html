框架选型 · Q9

API 框架选型:FastAPI vs Flask vs Django

⭐⭐⭐ #API框架#后端开发
先说人话:这题考选型判断:给你一个场景,能不能从 IO 模型出发推出该用哪个框架、为什么。AI Agent 岗爱考它,是因为 LLM 服务"重 IO+流式"正好踩在三个框架的分水岭上。答错的暴露点:只背"FastAPI 快",被追问"为什么快、什么时候不快"就卡壳——那是背参数,不是干过活。
30秒电梯稿

"AI/LLM 服务我无脑选 FastAPI:异步原生(长时 LLM 调用/SSE 流式的刚需)、Pydantic 数据校验(Prompt 参数防呆)、自动 OpenAPI 文档;Flask 适合小工具和存量系统,同步模型在 IO 密集下要靠多进程硬扛;Django 是全家桶,适合'后台管理+业务模型'的传统 Web 产品。选型核心依据是 IO 模型:LLM 应用是重 IO+流式场景,async 亲和度决定一切。"

通俗类比

三个框架(用餐厅运营模式想):Flask 是一个服务员盯一桌(同步:一个请求占一个 worker,客人聊一小时天=服务员站一小时);FastAPI 是一个服务员管全场(异步:点完菜就去服务别桌,菜好了再回来上)——客人越多差距越大;Django 则是连锁餐厅整套体系——后厨、收银、会员全带,开小饭馆用它反而束手束脚。

再压一层存储视角,更接近本质:Flask 默认是 thread-per-request 的阻塞 IO——一个请求独占一个线程,线程等回包时整段睡死,像每笔读盘都独占一次同步 read() 干等的老服务;FastAPI 是 epoll/io_uring 那套事件驱动——一个事件循环线程盯住全部连接,谁就绪推谁;挂起的请求只是内存里躺着一个协程,由 asyncio 调度,切换成本是用户态函数调用级别,近似零。Django 则像成熟存储套件:元数据目录(ORM)、管理控制台(Admin)、权限体系(Auth)全都自带,交付的是整套系统而不是零件。

哪里像:事件循环之于海量连接,等于 IO 多路复用之于海量 fd——灵魂都是"一个执行流看住一大片等待者,谁就绪服务谁",把等待从成本变成挂起。哪里不像:epoll 由内核回调,你只收就绪列表;asyncio 的让出必须靠代码显式写 await,谁忘写谁就堵死全场(这个坑追问里会考)。服务员类比也有边界:服务员若亲自进后厨炒菜(CPU 密集),全场没人端茶——这正是异步框架的死穴。

详细拆解

1. 一张表定基调:三个框架逐维度对齐

看表前先垫三个词,表才读得顺:WSGI 是 Python Web 应用与服务器之间的同步接口标准,Flask/Django 都出生在这个年代;ASGI 是它的异步继任者,FastAPI 从第一天就长在它上面;DI(依赖注入)指你声明需要什么(数据库连接、配置、客户端),框架自动装配塞给你。好,上主表:

维度FastAPIFlaskDjango
IO 模型asyncio 原生同步为主(异步需 patch)同步为主(ASGI 逐步支持)
数据校验Pydantic 深度集成手动/扩展Form/Serializer
文档自动 Swagger扩展生成扩展生成
自带路由+DI,轻路由,极轻ORM/Admin/Auth 全家桶
适合AI API/微服务/流式小工具、存量维护内容型网站、后台系统
部署形态uvicorn(ASGI)多 workergunicorn 多进程/多线程(WSGI)WSGI 或 ASGI 服务器均可

这张表怎么用:第一行 IO 模型是"基因"级差异,决定并发上限;其余行都是"体验"级差异——校验是手写还是注解、文档是手工维护还是自动生成、零件自己拼还是精装交付。选型永远先看基因(场景负载形态),再看体验(团队效率)。

2. 分水岭细看:同步与异步,到底差在哪个瞬间

把"FastAPI 快"讲到让人点头,得精确到瞬间。AI 接口的时间轴是:收请求 → 校验参数 → 发起 LLM/检索/工具调用 → 等回包 → 组装返回。实测"等回包"常占全程 90% 以上——LLM 一次推理动辄数秒,校验和组装只有毫秒级。三个框架在 CPU 环节没有本质差距,胜负全在"等"字上:

【同步:一个请求占一个工人,工人等的时候睡觉】

时间 ──────────────────────────────────────────►
线程1 [收请求A][发LLM][░░░ 等回包 3s,线程睡死 ░░░][回包→组装→响应]
线程2          [收请求B][发LLM][░░░ 等回包 3s,线程睡死 ░░░][回包→响应]
线程3                  [收请求C][发LLM][░░░ 等回包 3s,线程睡死 ░░░][...]

10 路并发 = 10 个线程各睡各的:内存 ×10,线程切换 ×10
而 ░ 区间里一件活都没干——资源被占着,纯属浪费

【异步:一个事件循环看全场,等待的时间拿去干别的】

时间 ──────────────────────────────────────────►
loop [收A][发A→挂起][收B][发B→挂起][收C][发C→挂起]…[谁的回包到,唤醒谁]
                                              │
        A 先回包 → 唤醒协程A → 组装 → 流式吐字 ◄┘

10 路并发 = 1 个线程 + 10 个协程(单个协程内存开销 KB 级)
等待从"占用资源的罪",变成几乎免费的挂起

主角是那个永远不睡的事件循环:协程跑到 await 处主动交权,loop 立刻切去推进下一个请求;回包一到,再把对应协程捞回来续跑。一个线程支撑成百上千路并发,这就是"服务员管全场"的工程真相。

补一刀边界:异步只救"等 IO",救不了"算得慢"。CPython 有 GIL,同一进程同一时刻只有一个线程在执行字节码,多线程算不动 CPU 任务,事件循环更算不动。真碰上 CPU 密集(本地推理、大文件解析),三个框架一个命:丢进程池,或者干脆独立服务,Python 只当薄网关。这道边界说出来,面试官就知道你不是背的。

3. AI 场景点名 FastAPI 的三个硬理由,逐个展开

  • 并发 LLM 调用:一个 Agent 请求动辄扇出 10 个工具/模型调用,asyncio.gather 并行等结果,总耗时=最慢一路;同步框架得开线程池硬扛,一路占一个线程,资源开销大得多。放到你熟的领域,这就是备份调度器并行跑 N 个备份流,与一条流水线串行跑 N 个任务的差距。
  • SSE 流式:LLM 是逐 token 出字的,体验由 TTFT(首字时间)和"持续有字吐"决定。StreamingResponse + 异步生成器天然契合 token 流(见第二部分 Q9);Flask 实现流式是能用,但别扭。真正的"卡"多半不是模型慢,而是服务端攒一大段才吐——异步生成器让"模型吐一个、接口转一个"成为一行代码的事,这是 LLM 流式输出的标准链路。
  • Pydantic:请求/响应/工具参数的 schema 校验一行注解搞定——Prompt 参数、工具入参的防呆层,还能复用模型生成 JSON Schema 喂给 Function Calling(约定 LLM 按给定格式产出工具调用参数的机制),一份定义两处用(这个细节说出来很加分)。Agent 场景里这层校验格外要命:LLM 生成的参数是"不可信输入",性质等同外部提交的表单——top-k 传成 500、日期传成字符串、必填项缺失,都要在这一层拦下,而不是等下游工具炸了才发现。

先给理由①算笔时间账,数字最有说服力:

一次 Agent 推理要发 3 路(检索 2s、查库 1s、LLM 3s)

同步(排队等): 发检索──等2s──发查库──等1s──发LLM──等3s   总耗时 6s
异步(齐发等): 三路同时发出去,一起等最慢的那路回来          总耗时 3s
                                                    (LLM 这路 3s 到点,其它早好了)

路数越多、单路越慢,异步省下的越多——"并行扇出"的全部秘密就这一句

三个理由落到代码上就是一段骨架(用异步 HTTP 客户端 httpx 演示,箭头行是讲解,读一遍就能感到"为什么顺"):

并发扇出:同步写法要开线程池(或串行三次等待),异步是三路齐发

@app.post("/agent/run")
async def run_agent(req: AgentRequest):              ← AgentRequest 是 Pydantic 模型,入参自动校验
    async with httpx.AsyncClient(timeout=30) as cli:
        llm_res, docs, db_rows = await asyncio.gather(    ← 三路同时发,总耗时 ≈ 最慢一路
            cli.post(LLM_URL,       json={"messages": req.messages}),
            cli.post(RETRIEVAL_URL, json={"query": req.query, "top_k": 5}),
            cli.post(DB_URL,        json={"sql": req.safe_sql}),
        )
    return {"answer": merge(llm_res, docs, db_rows)}

SSE 流式:模型吐一个 token,接口就转发一个

@app.post("/chat/stream")
async def chat_stream(req: ChatRequest):
    async def token_gen():                          ← 异步生成器
        async for chunk in llm.astream(req.messages):
            yield f"data: {chunk}\n\n"              ← SSE 帧格式,客户端逐段收到增量
    return StreamingResponse(token_gen(), media_type="text/event-stream")

4. 反过来说:什么时候不该选 FastAPI

反过来什么时候不用 FastAPI:纯 CPU 密集的推理服务(Python 本来就不合适,走 gRPC/独立服务);需要完整后台管理的运营系统(Django Admin 真香);团队全是 Flask 老手且无性能瓶颈(技术栈连续性 > 纸面先进性)。这三条其实是三种不同性质的"否":第一条否的是 Python 这门语言,第二条否的是重复造轮子,第三条否的是"为新而新"。现场推演可以走这棵决策树:

拿到需求,按顺序问三句:

① 时间主要花在哪?
   ├─ 等 IO(LLM 回包 / 检索 / 下游服务)────► FastAPI 优先
   └─ 烧 CPU(本地推理 / 加解密 / 解析大文件)─► 独立服务 + gRPC,
                                               Python 只当薄网关
② 要不要现成的后台管理界面?
   └─ 要 ──► 认真考虑 Django:Admin+ORM+Auth 是白送的
③ 有没有存量与团队惯性?
   └─ 有,且没碰到性能瓶颈 ──► 别为迁移而迁移,做增量

收个尾:选型没有"最好的框架",只有"负载形态匹配+迁移代价最小"的答案。面试时把这棵树的推演过程讲出来,比背十个框架特性值钱。

面试官追问
Q:FastAPI 部署有什么讲究?
人话:三件事:worker 怎么配、停机怎么停得体面、容量按什么算。类比:备份集群上下线节点的老规矩——先把节点从调度器摘掉,让在跑的备份流收完尾再退出,绝不一刀 kill 把任务挂半路;健康检查就是节点心跳。技术:生产用 gunicorn+uvicorn worker 起多进程,每进程一个事件循环;SIGTERM 触发优雅停机,drain 在途请求和 SSE 长连接;Kubernetes 里 readinessProbe 摘流、preStop 兜底;容量第一参数是单实例最大长连接数(SSE 场景 QPS 反而不是核心),副本按它算,SLA 才守得住。
Q:FastAPI 到底"快"在哪?单个请求也会变快吗?
人话:快在"等的时候不闲着"——涨的是吞吐量和并发容量;单个请求的耗时基本不变,瓶颈本来在 LLM 那侧。类比:同步 read() 换成 epoll/io_uring:盘没变快,是"等盘的姿势"变了,一个线程盯一万路 fd,等待不再占用执行资源。技术:async 路由是协程,在 await 点让出事件循环(uvloop 实现可再提速),loop 单线程轮流推进所有在途请求;收益是同配置下扛住更高 QPS、更稳的 P99,不是某次请求提前返回。CPU 密集时三者一个命:GIL 在头顶,异步救不了计算。
Q:在 async 路由里写了同步阻塞的代码(CPU 密集、同步 HTTP 库),会发生什么?
人话:全场卡死:事件循环被这段代码独占,所有并发请求一起干等——FastAPI 第一大坑,代码评审要专门盯。类比:备份进程做全量比对时占满 CPU 不让出,调度队列里所有任务全堵着;重活必须丢独立进程池,主循环只干轻量收发调度。技术:loop 单线程,协程只在 await 处让出,同步代码没有让出点,loop 直接停转。解法按代价排:整条路由写普通 def(FastAPI 自动丢线程池);局部用 asyncio.to_thread;真 CPU 密集丢进程池或独立服务;同步 HTTP 库换 httpx.AsyncClient。
Q:团队有一堆 Flask 存量服务,你会为了 AI 场景把它们全重写成 FastAPI 吗?
人话:不会全重写:新 AI 网关直接用 FastAPI 起,存量按收益挑着迁,其余原地不动。类比:灾备演练里的"按优先级恢复"——先把关键路径(LLM 网关)切到新架构,老 CRUD 接口原地继续跑,两个域并行一段时间再收尾。技术:先测量再动手:压测拿 QPS、P95/P50 和长尾请求画像,只迁重 IO、高并发的路由;网关层按路由做灰度发布,5%→50%→100% 逐步放量、随时回滚;Flask 侧没瓶颈就别动——技术栈连续性是资产,不为迁移而迁移。
术语卡
asyncio:Python 官方异步编程框架,提供事件循环与协程调度,async/await 是它的门面。
Pydantic:基于类型注解做数据校验与解析的库,FastAPI 的地基。
ASGI/uvicorn:ASGI 是异步网关接口协议(WSGI 的异步继任者),uvicorn 是它的高性能实现服务器。
WSGI:同步时代的 Python 网关协议,Flask/Django 的默认接口标准。
GIL:CPython 全局解释器锁,同进程同一时刻只允许一个线程执行字节码,多线程救不了 CPU 密集。
SSE:服务器向客户端单向推流的事件协议,LLM 吐 token 的主流通道。
OpenAPI:描述 REST API 的规范,FastAPI 自动生成的交互文档建立在它之上。
uvloop:用 libuv 实现的 asyncio 事件循环,性能显著高于默认实现,uvicorn 可直接启用。
