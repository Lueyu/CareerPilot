API 框架选型:FastAPI vs Flask vs Django

⭐⭐⭐ #API框架#后端开发
30秒电梯稿

"AI/LLM 服务我无脑选 FastAPI:异步原生(长时 LLM 调用/SSE 流式的刚需)、Pydantic 数据校验(Prompt 参数防呆)、自动 OpenAPI 文档;Flask 适合小工具和存量系统,同步模型在 IO 密集下要靠多进程硬扛;Django 是全家桶,适合'后台管理+业务模型'的传统 Web 产品。选型核心依据是 IO 模型:LLM 应用是重 IO+流式场景,async 亲和度决定一切。"

通俗类比

像餐厅运营模式:Flask 是一个服务员盯一桌(同步:一个请求占一个 worker,客人聊一小时天=服务员站一小时);FastAPI 是一个服务员管全场(异步:点完菜就去服务别桌,菜好了再回来上)——客人越多差距越大;Django 则是连锁餐厅整套体系——后厨、收银、会员全带,开小饭馆用它反而束手束脚。

AI 场景的三个硬理由(展开说)

  • 并发 LLM 调用:一个 Agent 请求扇出 10 个工具/模型调用,asyncio.gather 并行等结果,总耗时=最慢一路;同步框架得开线程池,资源开销大得多。
  • SSE 流式:StreamingResponse + 异步生成器天然契合 token 流(见第二部分 Q9);Flask 实现流式是能用,但别扭。
  • Pydantic:请求/响应/工具参数的 schema 校验一行注解搞定——Prompt 参数、工具入参的防呆层,还能复用模型生成 JSON Schema 喂给 Function Calling,一份定义两处用(这个细节说出来很加分)。

反过来什么时候不用 FastAPI:纯 CPU 密集的推理服务(Python 本来就不合适,走 gRPC/独立服务);需要完整后台管理的运营系统(Django Admin 真香);团队全是 Flask 老手且无性能瓶颈(技术栈连续性 > 纸面先进性)。

面试官追问
Q:FastAPI 部署有什么讲究?
uvicorn/gunicorn+uvicorn worker;容器健康检查/优雅停机( draining 长连接);多实例水平扩展,SSE 长连接数是容量规划的核心参数。
