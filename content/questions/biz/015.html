Agent核心 · Q7

请比较一下两个流行的 Agent 开发框架，如 LangChain 和 LlamaIndex。它们的核心应用场景有何不同？

⭐⭐ #Agent#框架#选型 所有公司（通用）
30秒电梯稿

"这两个不是二选一的竞品,而是定位不同:LangChain 是通用 LLM 应用框架——链条、工具调用、多步编排的"全家桶";LlamaIndex 是数据/RAG 专精框架——文档接入、索引、检索最细。一句话结论:要做带工具调用、多步推理的对话/Agent 应用选 LangChain(复杂编排直接用它的内核 LangGraph);要围绕私有知识库做检索问答、把检索做到极致选 LlamaIndex。生产里常见的是组合:用 LlamaIndex 搭数据管道,用 LangGraph 做编排。"

通俗类比

LangChain 像瑞士军刀——刀、剪、锯一应俱全,啥都能干一点;LlamaIndex 像专业图书馆管理系统——只专注一件事:把海量书分类、编目、快速查到。你要野营带军刀,你要经营图书馆就上专业系统;真要开大型图书馆,往往是"军刀开路、专业系统管书"——两者配合用,不是二选一。

详细拆解
维度LangChainLlamaIndex
定位通用 LLM 应用开发框架数据框架 / RAG 专精
核心强项Chain/Agent/Tool/Memory 抽象全、集成最多、生态最大;配套 LangSmith 观测、LangGraph 图编排数据连接器(上百种)、索引结构(向量/关键词/树/知识图谱)、检索器抽象最丰富,RAG 天花板高
典型场景带工具调用的对话机器人、多步推理 Agent、复杂工作流编排文档问答、企业知识库检索、结构化数据查询、复杂检索策略(路由/子问题/混合)
弱项抽象层多、Debug 像剥洋葱;版本破坏性变更多非 RAG 的通用编排能力弱;Agent 能力是后来补的
一句话选型以"对话/工具/流程"为中心以"数据/检索"为中心

核心场景差异(面试要讲到点子上)

  • LangChain 的回答单元是"链/Agent":LLM 决策 + 工具调用 + 步骤编排,关键词是 orchestration。
  • LlamaIndex 的回答单元是"索引 + 查询引擎":先把数据建索引,再对索引做检索与合成,关键词是 retrieval。
  • 两者其实有交集且会互相渗透:LlamaIndex 现在也有 Agent/Workflow,LangChain 也能做 RAG,只是"看家本领"不同——能说出"框架边界在模糊"比背表格更显水平。
面试官追问
Q:两个都用过吗?实际项目里你选哪个、为什么?
给一个具体场景佐证立场。例:做一个"企业制度问答"产品,核心是私有文档检索,我先用 LlamaIndex 的 Data Connector + 索引快速出效果;后来加了"多步审批/查多系统"的 Agent 需求,编排层就换到 LangGraph,检索仍复用 LlamaIndex 的组件。结论:按"链路里谁占主导"来定主力框架,而不是认死一家。
Q:它们底层有本质区别吗,还是只是 API 风格不同?
底层调用的是同一个 LLM,真正的差异在抽象视角:LangChain 把问题抽象成"节点和边组成的执行图",LlamaIndex 把问题抽象成"数据怎么被索引、怎么被查询"。视角决定了一整套组件设计方向,所以不是换个 API 那么简单。
Q:能直接说"我们生产不用框架"吗?
可以说,但要补上理由和平衡点:核心链路(检索→拼 Prompt→调模型)其实很短,自研可控;但完全不用框架也会重复造轮子。更稳的说法是"用它的组件(数据连接器、向量库封装),不用它的编排",并准备一个真实踩坑故事支撑。
术语卡
LangChain:通用 LLM 应用框架,重编排与生态。
LlamaIndex:数据/RAG 框架,重索引与检索。
LangGraph:LangChain 家的图编排引擎,做复杂 Agent 流程。
Data Connector:LlamaIndex 的数据接入组件。
Query Engine:LlamaIndex 里"检索+生成"的封装单元。
