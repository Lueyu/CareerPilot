Agent核心 · Q26

你的 Agent 系统Prompt 是怎么设计和迭代的？有没有做过 Prompt 自动优化？当用户提出不完整的请求时，如何补全用户意图的？

⭐⭐⭐ #Prompt工程#意图理解#自动优化 字节(真题)
先说人话:这题一题三问:系统 Prompt 怎么搭骨架、改完怎么证明没改坏、用户话说一半怎么接住。面试官爱考,是因为人人都能背一句「你是 xx 助手」,但追问一句「改完怎么知道变好了」,答「感觉更流畅」的当场露馅——暴露的是没有度量意识、把调 Prompt 当玄学,这在工程团队眼里是硬伤。
30秒电梯稿

"这题我按三问顺序答。系统 Prompt 用四段式:①角色与目标(你是谁、服务谁、边界在哪);②能力与工具清单(能用什么、何时用);③行为规范(何时澄清、何时拒绝、格式要求);④输出契约(JSON schema、引用来源等)。迭代靠评测集驱动:固定一批任务,用 LLM-as-judge 加人工抽检打分,每次改动看分数 diff 而非感觉,涨了才灰度。自动优化做过两层:DSPy 式签名优化,以及「LLM 生成候选 + 评测筛选」的进化搜索。意图补全用槽位填充:先抽已有槽位,历史能默认的静默补,只对缺失的关键槽位主动澄清一次,一次最多问一两个,不搞连环审问。"

通俗类比

系统 Prompt(用备份策略模板来想):每个备份作业都是从策略模板实例化出来的——几点起、保留多久、走哪个介质池,模板定死、作业照办。系统 Prompt 就是每次对话的「策略模板」:新会话一开,模型照它干活。这是 Prompt 工程里最该先稳住的一份基线。常见的「新员工手册」类比也对,但策略模板更贴你:手册是给会成长的员工看的,模板是给一次次全新实例化的作业用的——会话之间不共享记忆,这点和模板一模一样。

哪里像:稳定不变、所有实例共享、改一处全局生效;同样讲究「稳定的进模板,易变的当参数传」。哪里不像:配置文件是确定性解析,写错当场报错;Prompt 是概率性的「说服」,模型可能不照办且不报错——所以输出契约必须在代码层再校验一道。写配置的心态是「默认被执行」,写 Prompt 的心态是「默认会被违反」。

评测集驱动迭代(用回归测试套件来想):改一行 Prompt 和改一行代码一样危险——改好一处、悄悄坏三处的概率不低。所以每次改动都跑固定评测集看分数,相当于 CI 门禁;LLM-as-judge(让一个强模型当裁判、按评分标准打分)就是你的自动化断言。

哪里像:小步提交、跑套件、看通过率 diff、防回归;歧义/越权/工具失败这些边界样本,就是异常路径测试。哪里不像:传统断言精确匹配、对错确定;judge 给自然语言打分,自己会看走眼——偏好长答案、爱给中庸分。所以断言器本身也需要「测试」(人工抽检校准),这在传统 CI 里不是问题。

Prompt 自动优化(用数据库自动调参来想):自动调参工具拿真实负载当目标函数,在参数空间里搜;Prompt 自动优化同构——拿评测集当目标函数,把 Prompt 当参数去搜。DSPy 就是把这套路子框架化了。

哪里像:都是把「老师傅手调」变成「机器搜索」,都以固定基准负载为参照,都收敛到「够用解」而非理论最优。哪里不像:数据库参数改坏了,行为仍可预期;Prompt 优化器优化的是「评测分数」而不是你的真实意图——它会过拟合评测集、钻评分标准的空子,甚至改出绕过安全约束的措辞。所以关键段落必须锁死,人工兜底。

意图补全(用恢复工单的必填字段来想):网上常用的类比是服务员面对「我就要那个」——先看常点的猜,只问缺的。换到你的世界更清楚:用户说「帮我恢复一下数据」,值班工程师不会瞎开工单——恢复源(哪个备份集)、时间点(RPO 口径)、目标位置、恢复范围,缺哪项补哪项。Agent 的槽位填充一模一样:先识别意图,再拆必填字段,缺的才问。

哪里像:都是把模糊请求结构化;都能用历史默认值预填(上次恢复的目标位置=这次的默认);都只追问关键字段。哪里不像:工单是人填的,人明确知道缺什么;Agent 要先「猜」意图再算槽位缺失度,意图猜错后面全错——所以多一道置信度阈值:意图都拿不准时,先澄清意图,别急着问字段。

详细拆解

这题按「骨架 → 设计要点 → 迭代闭环 → 自动优化 → 意图补全」五步走,对应面试三问:第一问考有没有结构,第二问考是不是工程化地改,第三问考产品策略。每一步都给出能直接抄走的东西。

1. 系统 Prompt 四段式结构(给出骨架)

四段式不是排版玄学,是把不确定性逐段关进笼子:角色段关掉越界,工具段关掉瞎编,规范段关掉乱来,契约段关掉格式漂移。逐段拆开,看每段回答什么问题、怎么写才算数:

段落回答的问题写什么没用的写法可验证的写法
① 角色与目标你是谁、对谁负责、边界在哪角色定位+服务对象+明确「不做什么」「你是一个智能助手」「你是订单客服,只管售后,不聊股价」
② 能力与工具能用什么、何时用工具清单+调用时机+参数含义只列工具名,不写使用时机「查订单用 query_order;没有单号先追问」
③ 行为规范遇到 X 情况怎么办何时澄清、何时拒绝、何时转人工「要礼貌、要专业」「用户情绪激烈,直接 transfer_human」
④ 输出契约交作业长什么样JSON schema、字段枚举、引用来源散文一句「请输出 JSON」附完整 schema,逐字段给枚举值

落到纸上,一份能跑的四段式骨架长这样(节选):

【① 角色与目标】
你是 xx 商城的订单客服 Agent,只处理订单、售后类问题;
医疗、法律、投资类问题一律礼貌拒答。

【② 能力与工具】
query_order(order_id)         查订单状态;用户没给单号,先追问
create_refund(order_id, reason, type)
                              发起退款;type 只能是 {仅退款, 退货退款}
transfer_human(reason)        转人工;用户明确要求或情绪激烈时使用

【③ 行为规范】
意图不明确:给选项式澄清,一次最多问 2 个问题
涉及资金的操作:执行前必须复述关键信息,等用户确认
工具调用失败:如实告知并给下一步建议,不许假装成功

【④ 输出契约】
所有回复输出合法 JSON,含字段:
reply(给用户的话) / tool_calls(要调的工具) /
need_clarify(是否在澄清) / sources(引用的订单号等)

第④段多啰嗦一句:格式约束别写完 Prompt 就撒手——附上 JSON Schema 定义,解析层再校验一道:解析失败自动重试一次,仍失败就降级成纯文本回复。Prompt 是概率性说服,契约的最后一道闸必须留在代码层。

2. 设计要点(区别于单轮 Prompt)

单轮 Prompt 是一次性脚本,跑完就扔;系统 Prompt 是常驻基线,要扛住你预料不到的所有输入。套路完全不同,三个要点:

  • 分层:系统 Prompt 放「稳定不变」的规则,任务 Prompt 放「本次任务」指令,用户消息放「具体输入」。改任务不改系统,改系统不动全局——这就是配置管理里「基线与 override」的老规矩,别把每单的临时参数写进基线。
  • 少样本:关键分支(澄清、拒绝、多工具协同)各给 1~2 个高质量示例,比长篇说明更有效。原因是模型会照着示例「抄」格式和风格——一个坏示例能带偏整个行为,所以示例要当代码过 review,不是随手贴。
  • 约束要具体可验证:「要礼貌」没用,「价格一律带货币单位和来源」才有用。自检标准:这条约束能不能写成代码断言、能不能进 judge 的评分 rubric——两条都进不去,等于没写。
层备份世界的对应物改动频率放什么怎么审
系统 Prompt策略模板/基线配置季度级角色、工具、规范、输出契约评审+回归评测+灰度
任务 Prompt某次作业的 override 参数按任务本次任务指令、少样本示例代码 review
用户消息运行时输入的数据流每轮用户原话、上下文不需要审

3. 迭代方法(评测集驱动,别凭感觉)

改 Prompt 和改代码一样危险:改好一处、悄悄坏三处的概率不低,而且坏得悄无声息——没有编译器替你报错。所以迭代必须走闭环,整条流水线长这样:

改 Prompt(当次提交)
   │
   ▼
┌─────────────────────────────────────┐
│ 跑回归评测集:100~300 条固定任务        │
│ (真实样本 + 歧义/越权/工具失败边界样本) │
└──────────────────┬──────────────────┘
                   ▼
┌─────────────────────────────────────┐
│ LLM-as-judge 按 rubric 打分          │
│ + 每月人工抽检 5%~10% 校准 judge      │
└──────────────────┬──────────────────┘
          ┌────────┴────────┐
          ▼                 ▼
      分数掉了           分数涨了
          │                 │
          ▼                 ▼
   拉 badcase 定位      灰度发布 5%→20%→50%
   原因,回炉重改        看任务成功率/澄清率/满意度
                            │
                 ┌──────────┴──────────┐
                 ▼                     ▼
           线上指标同涨            指标异常
           全量上线+记入基线        一键回滚(旧版留档)
  • 建回归集:100~300 条任务,真实线上样本为主(约七成)、构造的边界样本为辅(约三成)——歧义请求、越权请求、工具调用失败,对应测试里的异常路径,最容易被漏。集合要版本管理,只加不改,否则分数没法跨版本对比。
  • 打分双轨:LLM-as-judge(带 rubric,每个任务写清「什么算成功」)自动打分;每月人工抽检 5%~10%,校准 judge 的可信度。每次改动记录「改了什么 → 分数 diff」,像 commit log 一样可回溯。
  • 灰度:线上 AB 测试,看任务成功率/澄清率/用户满意度——离线分数好不等于线上好,评测集再像也替代不了真实分布。走灰度发布 5%→20%→50%,指标异常一键回滚,旧 Prompt 像备份一样留档,随时可回。
迭代动作后端世界的对应物关键差异
回归评测集回归测试套件/CI 门禁断言从「精确匹配」变「打分」,自带噪声
LLM-as-judge + rubric自动化断言断言器本身会错,需要人工抽检校准
每月人工抽检 5%~10%code review 抽查抽样控成本,顺便校准 judge 可信度
灰度发布 + AB金丝雀发布看业务指标(成功率/澄清率),不只看离线分
分数 diff 记录CI 通过率 + commit log每次改动可回溯「改了什么、涨跌多少」

一句话:Prompt 迭代 = 代码迭代,评测集就是 CI——没过 CI 的改动,不许上线。

4. Prompt 自动优化(做过的两层)

手写调 Prompt 本质是「人肉梯度下降」:改一版、看眼分数、再改一版。自动优化是把这趟搜索交给机器,我们落地过两层:

方法思路类比适用前提主要坑
A · DSPy 签名优化任务写成「输入→输出」签名,指令与示例当参数搜索声明式配置,编译器替你选实现结构稳定+百条级标注优化的是评测分,不是你的真实意图
B · 进化搜索LLM 生成 N 个候选,评测集排序,高分交叉变异,迭代几轮像生物进化:高分「存活」,低分淘汰冷启动、无框架依赖过拟合评测集;轮数多时 token 成本高
初始种群(5~10 个候选:手写版 + LLM 生成的变体)
   │
   ▼
┌──────────────────────────────────┐
│ ① 全体候选上评测集跑分              │◄──────────┐
│   (同一 rubric,LLM-as-judge)      │           │

人工审查(安全段、契约段逐字过) → 灰度 AB → 上线
  • 方法 A · DSPy 思路:把 Prompt 变成可调参模块,用少量标注对「指令/示例」做搜索式优化,而非手写。更具体:先声明任务签名——像写函数签名 refund_agent(user_msg: str) → Action——框架拿标注当目标函数,替你搜出最优的指令措辞+示例组合。相当于「声明要什么,编译器替你选实现」。
  • 方法 B · 进化搜索:LLM 生成 N 个候选 Prompt,在评测集上排序,保留高分交叉变异再迭代几轮——本质是遗传算法:Prompt 当个体,评测分当适应度。
  • 结论(面试官爱听这条):自动优化能收敛出「过得去」的起点,把冷启动从三天压到三小时;但关键语义(安全边界、格式契约)仍需人工兜底审查,防优化器「过拟合评测集」钻空子——它优化的是分数,不是你的意图。我们的规矩:安全段、契约段锁死,优化器只准动指令和示例段。

5. 意图补全(不完整请求的处理)

先定义两个词:意图=用户想干什么(退款/查物流/改地址);槽位=干成这件事必须收集的字段(订单号、退款类型)。用户的话天然残缺——「帮我退一下」缺订单号、缺类型、缺金额口径。处理框架就一个词:槽位填充,流程长这样:

用户: "帮我退一下"
   │
   ▼
① 意图识别: intent=refund, 置信度 0.62 (低于阈值 0.7)
   │
   ▼
② 置信度不够 → 选项式澄清一次: "退货退款,还是仅退款?"
   │                            (用户答: 退货退款)
   ▼
③ 槽位抽取 (意图已确定)
   ├── 已有槽位:   商品=冲锋衣, 原因=质量问题
   ├── 可默认槽位: 金额=按实付金额 → 静默补全, 不打扰用户
   └── 缺关键槽位: 订单号 → 追问一次 (澄清预算 1/2)
   │
   ▼
④ 槽位齐全 → 涉及资金,先复述确认 → 调 create_refund → 按契约输出
   │
   └── 若第 2 次澄清仍拿不全 → 按最可能假设执行,并明说假设可纠正

槽位抽取这步的内部产物,本身也是输出契约的一部分——机器可校验,缺字段、越枚举当场拦截:

{
  "intent": "refund",
  "confidence": 0.62,
  "slots_known":   { "product": "冲锋衣", "reason": "质量问题" },
  "slots_default": { "amount": "按实付金额" },
  "missing_critical": ["order_id", "refund_type"],
  "action": "clarify",
  "clarify": {
    "question": "您是要退货退款,还是仅退款?",
    "options": ["退货退款", "仅退款"]
  }
}

// action 枚举: execute | clarify | transfer_human
// 这份 JSON 能被代码直接校验,不合规的输出进不了下游

不同意图的关键槽位和可默认槽位不一样,举三个例子:

意图关键槽位(缺了必问)可默认槽位(静默补全)澄清话术
退款订单号、退款类型金额(按实付)、地址(用历史)「退货退款还是仅退款?」(选项式)
查物流订单号(名下多单时)默认最新一单「是昨天那单还是上周那单?」
改收货地址新地址订单号(仅一单在途时)开放式问新地址(没有选项可给)
  • 槽位填充:intent + 槽位集合。先抽取已有槽位,计算缺失槽位的「关键度」——影响决策、资金、安全的算关键,其余都可默认或后补。这套结构化思路,和恢复工单的必填字段一模一样。
  • 只问关键槽位:缺的槽位影响决策才问(如「退款」必须知道订单号);能用默认值/历史上下文补的就补(收货地址用历史默认)——目标是把「显式提问」的比例压到最低。
  • 澄清话术:给选项式澄清(「您是要退货还是换货?」),比开放式「请详细描述」更高效——选择题点一下就走,问答题要打一段字,交互成本差一个量级。
  • 置信度阈值:意图置信度低于阈值才澄清,否则直接给「最可能解读 + 一句确认」,减少来回。阈值不拍脑袋:拿评测集画「澄清率 vs 误执行率」曲线选平衡点,跟选告警阈值是同一个 trade-off 套路。
  • 澄清预算:一次最多问 1~2 个缺失槽位,一个会话累计主动澄清不超过 2 次,避免连环追问激怒用户;第 2 次仍拿不全,就按最可能假设执行,并明说假设、欢迎纠正。

一句话收尾:意图补全的目标是「大部分静默补全,极少显式提问」——提问是成本,不是服务。

面试官追问
Q:自动优化有没有翻过车?怎么防?
人话:翻过。优化器为了刷评测分,把 Prompt 改成「只在评测集上灵」,上线就拉胯;还改出过绕过安全约束的措辞——它优化的是分数,不是你的意图。类比:像拿 TPC-C 跑分调数据库参数,基准分数起飞,真实负载一上来自动回档;也像去重率在合成数据上调到 5:1、生产只有 2:1——按基准优化,不等于按真实负载优化。技术:三条防线:①评测集持续混入线上真实样本,防过拟合;②候选 Prompt 必须过人工/规则审查,安全段与格式契约段禁止自动改动;③离线分数只作参考,上线走灰度 AB,指标异常秒回滚。
Q:系统 Prompt 太长会被模型忽略怎么办?
人话:真事。指令越长,排在中间和靠后的越容易被模型「略读」——不是它偷懒,是长上下文的已知弱点,叫 lost in the middle。类比:500 页的容灾 runbook 没人逐页读:开头结尾仔细看,中间扫一眼就翻过去——模型读长 Prompt 也一样,埋在中间的约束最容易被漏。技术:①精简+分层,能固化到代码/工具层的约束(JSON schema 校验、工具参数校验)就不写进 Prompt;②关键约束前置,或在首尾各出现一次;③用列表、XML 标签这类结构化格式代替大段散文;④定期删减,控制系统 Prompt 占总 token 预算的比例,超了就下沉到工具层。
Q:用户请求不完整,但澄清次数太多体验差,怎么权衡?
人话:设「澄清预算」:一个会话最多主动问 2 次。第二次还问不清,就按最可能的假设执行,并明说「我按 xx 假设办了,不对随时纠正」。类比:像容灾切换:探活两次还拿不到明确信号,就按预案切,切完广播声明——宁可带假设行动,不停机干等。技术:第一次只问最关键槽位,且给选项(选择题好过问答题);用历史上下文和用户画像预填可默认槽位,把需要澄清的比例压到很低;每次澄清都记进 badcase,反哺槽位默认值。好的意图补全是「大部分静默补全,极少显式提问」。
Q:怎么衡量一个系统 Prompt 的好坏?看哪些指标?
人话:别答「更流畅了」,要报数:离线看评测集分数,线上看四个核心指标,每次改动对比基线报 diff。类比:跟备份系统一个道理:好不好不看作业日志多漂亮,看恢复成功率、RPO 达成率——Prompt 好不好不看文案,看任务最后成没成。技术:①任务成功率(端到端完成比例);②澄清率(过高=意图理解差,过低=瞎猜);③格式合规率(输出 JSON 可解析、字段齐);④越权/幻觉率(该拒的拒了没、该引用的引用了没)。四个指标都有基线,离线+灰度双达标才全量。
Q:什么时候值得上 DSPy 这类自动优化,手写什么时候就够了?
人话:三个条件凑齐才上:任务稳定、有百条级标注、迭代频繁到人工跟不上。冷启动或一次性任务,手写+评测集性价比更高。类比:跟数据库自动调参一样:负载稳定又重要的库,值得上自动调优工具;一年跑三次的归档库,DBA 手调一次就完事——工具本身有成本,别为自动而自动。技术:①标注是优化器的「训练集」,没有 100+ 条高质量样本别搜,搜出来的是噪声;②任务 schema 三天一变的,搜完就过期;③DSPy 适合固定「结构」、搜索「措辞」,安全边界和输出契约锁死不许优化器碰。
术语卡
系统 Prompt:给模型定角色、规则、工具、输出格式的持久指令,每次对话的「基线配置」。
LLM-as-judge:用强模型按评分标准给输出打分的自动评估法,一个会看走眼的「自动化断言」。
DSPy:把 Prompt 当可优化参数、用少量标注自动搜出指令与示例的编程框架。
槽位填充:任务型对话中把用户话语拆成「意图+关键字段」并逐项补齐的技术。
少样本:在 Prompt 里放少量「输入→输出」示例,引导模型照着做。
Lost in the Middle:长上下文中间位置的信息最容易被模型忽略的已知现象。
过拟合评测集:优化结果只对评测样本生效、线上泛化差,与机器学习过拟合同源。
遗传算法:保留高分个体、交叉变异生成下一代的搜索算法,进化搜索的底层套路。
