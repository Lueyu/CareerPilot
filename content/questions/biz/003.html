框架选型 · Q1

LangChain vs LlamaIndex vs AutoGen,如何选择?

⭐⭐⭐⭐ #框架选型#对比分析 所有公司(通用题)
30秒电梯稿

"三个框架定位根本不同:LangChain 是 LLM 应用全家桶(工具、链、生态最全,但重、抽象多);LlamaIndex 是数据/RAG 专精(文档接入、索引、检索器设计最细);AutoGen 是多 Agent 对话编排(微软出品,偏研究风格)。我的原则:原型期用框架快速验证,生产期自研轻量核心、只复用框架里经过考验的组件抽象——因为框架的抽象泄漏和版本不稳定在生产里都是成本。"

通俗类比

像买车:LangChain 是 SUV——啥路况都能跑,配置全,但油耗高;LlamaIndex 是房车——专门为"带一堆行李出门"(数据管道)设计;AutoGen 是多人巴士——专为"一群人协作"(多 Agent 对话)设计。而很多团队最后发现:真正上赛道(生产),自己攒一台轻量化赛车反而最快——零件(检索、LLM 调用)单买就行。

详细拆解
维度LangChainLlamaIndexAutoGen
定位通用 LLM 应用框架数据框架/RAG 专精多 Agent 对话编排
强项生态最大:工具/集成/模板最多,LangSmith 配套数据连接器、索引结构、检索器抽象最丰富;RAG 天花板高多 Agent 会话模式灵活,研究原型快
弱项抽象层多,Debug 像剥洋葱;版本迭代破坏性变更多非 RAG 场景能力弱(通用编排一般)对话式控制流难调试;生产工程化偏弱
适合快速原型、全栈小团队以 RAG 为核心的产品多 Agent 策略探索、研究实验

我的选法(要有立场)

  • 做 RAG 产品:LlamaIndex 的检索抽象(或直接拿它的数据连接器)+ 自研编排。
  • 做 复杂 Agent 工作流:其实首选是 LangGraph(LangChain 家的图编排,见 Q6),而不是裸 LangChain。
  • 做多 Agent 协作原型:AutoGen/ CrewAI 起步,验证交互模式后把稳定的模式固化到自研编排里。

"生产为什么不直接全家桶"(必被追问,提前备好)

  • 依赖树大:一个简单功能引入上百个传递依赖,安全审计和升级成本高。
  • 抽象泄漏:出问题时得翻框架源码,排障路径变长;LLM 应用的核心链路其实很短(检索→拼 Prompt→调用),自研 500 行就能覆盖且完全可控。
  • 版本不稳:框架 API 频繁破坏性变更,生产系统升级是持续税。
  • 平衡点:用它的"组件"(数据连接器、向量库封装),不用它的"编排"——这话面试说出来非常加分。
面试官追问
Q:你实际用过哪个?踩过什么坑?
(准备一个真实小故事)例:原型用 LangChain 的 RetrievalQA 一天上线 demo;生产遇到:中间步骤不可观测(埋点是黑盒)、版本升级 break 两处。最终方案:保留其 VectorStore 封装,链路自研,trace 接 LangFuse。
Q:不用框架,自研不是重复造轮子吗?
LLM 应用的核心轮子(检索、调用、工具执行)各大厂 SDK 已经提供;框架真正增值在"胶水",而胶水恰恰是业务最该自己掌控的部分。造的是薄胶水,不是轮子。
术语卡
抽象泄漏:底层细节穿透抽象层暴露出来。
Data Connector:LlamaIndex 的文档接入组件。
编排:把各步骤串起来的控制流层。
