Agent核心 · Q8

你用过哪些 Agent 框架？选型是如何选的？你最终场景的评价指标是什么？

⭐⭐⭐ #Agent#框架选型#评估
先说人话:这题是三连问:框架真上手过没有、选型有没有方法论、上线后拿什么证明它行。面试官爱考,是因为一句「为什么选它」就能分出「跑过 demo 的」和「上过生产的」——只报名字、或答「选 GitHub 星最多的」当场出局;报不出自家指标基线的,基本没碰过真系统。
30秒电梯稿

"我用过的分三类:编排用 LangChain + LangGraph(生产主力),数据/RAG用 LlamaIndex,多 Agent原型试过 AutoGen 和 CrewAI。选型走四步:定需求边界 → 列硬约束(部署/合规/团队栈)→ 用自家数据做 PoC 实测 → 评可维护性;原则是「用它的组件、不锁死它的编排」,关键链路自研。最终场景(智能客服 Agent)的评价指标分四层:可靠性(任务成功率、工具调用准确率)、体验(P95 延迟、TTFT)、成本(单次对话 token 成本)、业务(问题解决率、转人工率),外加离线 LLM-as-judge 回归和线上灰度 AB 对照兜底。"

通俗类比

Agent 框架(用「一体化备份套件」想):LangChain、LangGraph 这类框架,就是把「调模型、接工具、管状态、做RAG(检索增强生成:先查资料、再回答)」这些通用零件打包成套,让你少造轮子、专注业务逻辑。哪里像:都是平台替你干脏活、你只写策略;哪里不像:备份软件的接口十年稳定,Agent 框架半年就可能来一次破坏性变更——成熟度像早年的虚拟化平台,买回来还得天天自己拧螺丝。

选型 PoC(用「恢复演练」想):厂商 demo 跑得再漂亮都不算数,必须拿自家真实数据、真实量级跑一遍才作数。哪里像:都是「演练不过关、不上生产」,验证负载必须来自真实业务;哪里不像:备份演练的结果是二值且可复现的(恢复成/不成),Agent 的输出带随机性——同一个用例要跑多次看统计通过率,一次运气好就拍板,必踩坑。

「用组件、不用编排」(用「防厂商锁定」想):成熟的零件(检索封装、向量库接入)可以买,但控制面——编排逻辑、评估体系、数据格式——必须握在自己手里,就像备份系统绝不把编目和备份格式交给设备厂商。哪里像:都是保住「可替换性」,任何一层都不能私有化到换不动;哪里不像:存储界的锁定靠私有格式,一眼能看穿;Agent 界的锁定更隐蔽——是业务代码里长出来的几百个框架 API 调用点,散在四处,想换时哪儿都得改。

评价指标(用「备份监控大盘 + 年度容灾演练」想):成功率、延迟、成本这些技术指标,对应备份里的作业成功率、RTO(恢复时间目标)、介质成本;问题解决率、转人工率对应年度容灾演练通过率——平时大盘全绿,不代表真出事时扛得住。哪里像:都是「技术指标 + 端到端演练」的双层验证;哪里不像:备份成没成,状态码自己会说话;Agent「办成没办成」是语义判断,机器不报状态,得靠规则断言 + LLM-as-judge 组合来判——这是 Agent 评估里最花功夫的一块。

详细拆解

1. 用过哪些(按用途分,别只报名字)

面试官要听的不是报名字大赛,而是「这个框架你放在系统哪一层、解决什么问题、踩过什么坑」。先看全景图,四个框架各守一层:

一个生产级 Agent 系统的分层(框架各守哪层)

业务层    客服工单 · 售前问答 · 内部提效          ← 指标在这里产生
  │
编排层    状态图 · 循环 · 重试 · checkpoint       ← LangGraph 主战场(关键链路建议自研)
  │
能力层    工具调用 · RAG 管道 · 记忆 · 观测       ← LangChain / LlamaIndex 的组件可复用
  │
模型层    LLM API · Embedding · 向量检索          ← 所有框架最终都落到这一层
  • LangChain:最早入门的一套,链/工具/记忆的抽象最全,快速搭原型最快;代价是抽象层多,排障经常要一层层翻进源码——生产上我只取它的工具封装和观测组件。
  • LangGraph:复杂工作流的主力。它把 Agent 建模成一张图(节点=一步动作,边=流转条件),自带 checkpoint(每步落一个状态快照,失败从上个快照续跑——就是备份作业的断点续传思想)和人工介入(高危操作先审后放),可控性最好。
  • LlamaIndex:RAG 数据管道最细——文档接入、切分、建索引、检索一整套,几十种数据源到向量库的适配它做得最全,检索这层的轮子不用自己造。
  • AutoGen / CrewAI:多 Agent 协作(给几个角色分工、互相对话把活干完)的原型验证很快;交互模式跑通后固化进自研编排,不直接带进生产。

2. 选型四步(要有方法论,不是凭感觉)

四步是一条单向漏斗,前一步不过关就不进下一步:

  • ① 需求边界先钉死:纯 RAG(一问一答、无状态)、单 Agent 多步(ReAct 式「想一步、做一步、看结果、再想」)、多 Agent 协作,复杂度差着量级——先分清「要一个备份脚本还是一整套容灾平台」,采购清单完全不同;纯 RAG 的需求上多 Agent 框架,是杀鸡用了数据中心。
  • ② 硬约束先于偏好:数据能不能出域(决定能不能调外部 LLM API)、是否强制私有化部署、团队技术栈(Python 后台用 LangChain 系最顺,不让团队现学新生态)、框架维护活跃度(issue 响应、发版节奏)。硬约束不过关的候选,再流行也直接划掉——采购先过合规,一个道理。
  • ③ PoC 用自家数据:挑 3~5 个真实场景、固定一份评估集(比如 200 条历史工单,人工标好「什么叫办成」),候选框架同题同测,比成功率、延迟、成本,踩坑全部记进选型报告。官方 quickstart 的 demo 数据永远跑得顺——那是为它量身调好的。
  • ④ 可维护性看三样:依赖树多大(一个「简单功能」带进上百个传递依赖的要慎重)、抽象泄漏重不重(排障要不要读框架源码)、升级历史(changelog 里破坏性变更的频率,半年 break 一次的框架长期持有成本极高)。
  • 判断标准一句话:能少一个抽象就少一个抽象——核心链路其实很短,自研 500 行可控、可测、可排障;框架只在「确实省事」的组件上引入(检索封装、观测、工具 schema)。

3. 评价指标(分层讲,面试官最想听这个)

系统上线不是终点,「你怎么知道它行不行」才是这题的高分点。先钉口径:任务成功率 = 固定测试集里「端到端办成」的条数占比,测试集从历史工单分层抽样约 200 条、人工标注预期结果——像备份验证要覆盖全类型作业,不能只挑最容易的文件备份刷分;工具调用准确率(工具选对 + 参数 JSON 对)可以 100% 用规则自动判,是可靠性里最先自动化的一项。指标分四层,每层在备份域都有对应物:

层级指标怎么测 / 为什么重要拿备份域对照
可靠性任务成功率、工具调用准确率构造固定测试集,统计"最终把事办成"的占比;工具选对+参数对才叫准作业状态绿 ≠ 备份有效,要做恢复演练才算数
体验P50/P95 延迟、TTFT(首字)Agent 多步调用延迟会累积,要压到用户可接受(P95 看长尾)像 RTO:业务能容忍的恢复用时上限,看长尾不看平均
成本单任务 token / 单次对话成本多步 Agent 一次任务多次 LLM 调用,成本是软件 Agent 的隐形瓶颈每次 LLM 调用都像写一次介质,一个任务写 N 次,必须记账
业务问题解决率、转人工率、用户满意度端到端才反映"有没有真的帮到人",内部指标再漂亮也要业务兜底像年度容灾演练:平时大盘全绿 ≠ 真出事扛得住
  • 体验的两个抓手:TTFT 靠流式输出撑住体感(首字快,用户就愿意等下去);端到端 P95 靠砍步数(合并 LLM 调用、缓存中间结果、并行无关步骤)。
  • 评估体系 = 离线 + 在线:离线用 LLM-as-judge 对固定集批量回归(每次改动都跑,像每次变更前必跑备份验证作业);上线做灰度发布的 A/B 对照,看业务指标是否变好、成本是否可控。
  • 基线先行:所有指标先给 v1 钉一条基线(比如成功率 72%、P95 8 秒、单次 0.03 元),此后每次改动对着基线看回归——没有基线的「感觉变好了」是玄学,就像没有历史监控的存储集群,出了问题都不知道是不是新引入的。
  • 北极星与护栏分开:问题解决率是目标函数(北极星),延迟、成本是护栏(约束)——护栏达标即可,不为压延迟牺牲成功率;这和「备份窗口是约束、RPO(恢复点目标)是目标」的取舍一模一样。

面试官追问
Q:为什么最终没选择纯用某个框架?
人话:账算下来不划算——依赖太重、排障太深、升级太疼,所以只买它的零件,发动机舱自己开。类比:备份软件不会把整条数据链路押给一家存储厂商:传递依赖等于一堆私有接口,每次升级都是全量兼容性回归;抽象泄漏等于排障先读厂商私有日志,MTTR 攥在别人手里。技术:①依赖树大,一个简单功能带进上百个传递依赖,安全审计和升级都是税;②抽象泄漏,出问题要翻框架源码,排障路径变长;③版本不稳,破坏性变更是持续成本。结论:复用经过考验的组件,编排这层"胶水"自研、版本钉死。
Q:任务成功率怎么定义?会不会定义得太松?
人话:定义成「端到端把用户的事办成、且没有错误副作用」,不是「模型回了一句像样的话」;判定走双通道、两边取严,专防放水。类比:备份不能只看作业状态码是绿,必须真做恢复演练——「表面成功、恢复时才发现数据损坏」的备份,在容灾里就等于失败。技术:规则通道查工具调用与参数对不对、查最终状态(订单真改没改);LLM-as-judge 通道判语义是否满足用户意图;两通道取较严者。测试集固定、按难度分层,防止拿简单用例刷分。
Q:框架升级破坏生产,你怎么办?
人话:三道闸:钉版本锁依赖、升级先过全量回归、灰度放量;再给框架套一层薄适配,让它只待在边缘、随时可换。类比:等于升级存储固件:先在演练环境跑全量恢复测试,再灰度切流量,异常秒回滚到快照;适配层就像统一的块设备接口,后端换了阵列、上层无感。技术:锁死依赖树、冻结大版本(语义化版本里主版本号一变即破坏性变更,必须单独评审);升级 PR 必附离线评估集回归报告,成功率/延迟/成本三项不许回退;线上按 5%→25%→100% 放量,盯 P95 和转人工率,异常自动回切。
Q:Agent 的评估和传统软件测试有什么不一样?
人话:传统测试是确定性的——同样输入必得同样输出,断言一次就够;Agent 输出带随机性,只能统计地评:固定测试集、多次采样、看通过率。类比:备份作业跑一万遍结果都可复现;Agent 更像在丢包率 2% 的链路上测质量——没人拿一次 ping 判链路好坏,得靠探针长跑出统计结论。技术:temperature 设 0 也只降低、不消除随机;用 n 次采样看成功率和置信区间,不押单条 case;评估集要覆盖长尾请求场景;版本对比看统计显著性,不看一两个极端例子。
Q:指标打架怎么办?比如延迟压下来了,成功率却掉了。
人话:先分清北极星和护栏:问题解决率是北极星,延迟是护栏;护栏达标就行,绝不为它牺牲北极星。类比:备份窗口和 RPO 天天打架,但没人会为缩窗口牺牲保护等级——窗口是约束,RPO 是目标,二者地位天然不平等。技术:指标分级写进 SLA:成功率/解决率是目标函数,P95/成本是约束;先做无损优化(合并 LLM 调用、缓存中间结果、并行无关步骤),护栏真扛不住了才考虑降级模型,且每次取舍都要有 A/B 数据背书。
术语卡
PoC:概念验证,拿真实场景小范围跑通再决策,不看广告看演练。
任务成功率:端到端"把事办成"的比例,不是"回复像不像样"的比例。
P95 延迟:95% 的请求比它快,看长尾不看平均。
转人工率:机器没搞定、转给人的比例,越低越好,但该转不转更伤体验。
LLM-as-judge:用强模型当裁判给回答打分做自动评估,要防裁判自己的偏差。
抽象泄漏:底层细节穿透封装漏到上层,逼你读懂框架内部才能排障。
依赖地狱:传递依赖滚雪球导致的版本冲突与升级泥潭。
RTO:恢复时间目标,容灾里"多久能恢复业务"的量化上限。
checkpoint:工作流每一步的状态快照,失败后从最近的快照续跑,不必从头再来。
