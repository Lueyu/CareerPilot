30秒电梯稿

"我用过的分三类:编排用 LangChain + LangGraph(生产主力),数据/RAG用 LlamaIndex,多 Agent原型试过 AutoGen 和 CrewAI。选型我走四步:先定需求边界 → 列硬约束(部署/合规/团队栈)→ 用自家数据做 PoC 实测 → 评可维护性;原则是"用它的组件、不锁死它的编排",关键链路自研。最终场景(智能客服 Agent)的评价指标分三层:可靠性指标(任务成功率、工具调用准确率、P95 延迟、单次成本)+ 业务指标(问题解决率、转人工率),再加离线 LLM-as-judge 回归和线上 AB 对照。"

通俗类比

像装修选施工队:不能光看广告词(文档漂亮),要看它做过你家这种户型的活(用自家数据做 PoC),再掂量工人手艺和后期维修成本(可维护性);哪怕选了大品牌,也只买它的主材、自己盯关键工序("用组件不用编排")。验收不看"师傅多努力",看工期、质量、返工率、总花费——这四样就是评价指标。

详细拆解

1. 用过哪些(按用途分,别只报名字)

  • LangChain:入门最早,链/工具/记忆抽象全,适合快速原型;但生产里抽象多、排障深。
  • LangGraph:复杂 Agent 工作流的主力,图编排 + checkpoint + 人工介入,可控性好。
  • LlamaIndex:RAG 数据管道,连接器与检索抽象最细。
  • AutoGen / CrewAI:多 Agent 协作原型验证,交互模式跑通后再固化进自研编排。

2. 选型四步(要有方法论,不是凭感觉)

  • 判断标准一句话:能少一个抽象就少一个抽象——核心链路其实很短,自研 500 行可控,框架只在"确实省事"的组件上引入。

3. 评价指标(分层讲,面试官最想听这个)

层级指标怎么测 / 为什么重要
可靠性任务成功率、工具调用准确率构造固定测试集,统计"最终把事办成"的占比;工具选对+参数对才叫准
体验P50/P95 延迟、TTFT(首字)Agent 多步调用延迟会累积,要压到用户可接受(P95 看长尾)
成本单任务 token / 单次对话成本多步 Agent 一次任务多次 LLM 调用,成本是软件 Agent 的隐形瓶颈
业务问题解决率、转人工率、用户满意度端到端才反映"有没有真的帮到人",内部指标再漂亮也要业务兜底
  • 评估体系 = 离线 + 在线:离线用 LLM-as-judge 对固定集批量回归(每次改动都跑);上线做灰度 AB,看业务指标是否变好、成本是否可控。
面试官追问
Q:为什么最终没选择纯用某个框架?
三点:① 依赖树大,一个简单功能引入上百个传递依赖,安全审计和升级都是税;② 抽象泄漏,出问题要翻框架源码,排障路径变长;③ 版本不稳,破坏性变更是持续成本。所以只复用经过考验的组件,把编排这层"胶水"掌握在自己手里。
Q:任务成功率怎么定义?会不会定义得太松?
定义成"端到端把用户请求办成、且无错误副作用",不是"LLM 给了一句合理回复"。严格的判定最好用判定规则 + LLM-as-judge 双通道:规则查工具调用和结果对不对,LLM 判语义是否达标,两者取"较严"的那个,避免模型互相放水。
Q:框架升级破坏生产,你怎么办?
把框架依赖钉版本 + 锁依赖树,升级走"先在测试集回归 → 灰度 → 全量";同时在自研层做一层薄适配,让框架只在边缘可替换,升级风险就不伤核心链路。
术语卡
PoC:概念验证,拿真实场景小范围跑通再决策。
任务成功率:端到端"把事办成"的比例。
P95 延迟:95% 请求比它快,看长尾不看平均。
转人工率:机器没搞定、转人工的比例,越低越好。
LLM-as-judge:用强模型给回答打分做自动评估。
