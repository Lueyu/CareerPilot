评估讨论 · Q18

平常使用AI吗，都用来干嘛？如果我想使用AI，比如coding领域，你有何建议给我？

⭐ #实际应用#工具使用 所有公司
30秒电梯稿

"我几乎每天都用,分三类:写代码(补全、写单测、解释陌生代码、重构)、查资料与写作(研究、翻译、润色、总结长文)、头脑风暴(当 sparring partner,先让它给思路、再让它批判思路)。给 coding 领域三条建议:一是把它当『结对同事』而不是『自动驾驶』——你写规格和 review,它写初稿;二是小步快跑、每步都跑测试,别让它一次生成几百行再慢慢调;三是先把上下文喂清楚——项目背景、约束、代码风格,喂得越准,产出越靠谱。"

通俗类比

把 AI 编程助手当成一个反应极快、但偶尔会瞎编的初级搭档:它能帮你把搬砖的活干得飞快(样板代码、单测、重命名、查文档),但它的产出你必须 review,就像你不能把实习生的代码不审核直接上线。你越把它当"替你思考的大脑",越容易踩坑;越把它当"替你打字的快手 + 一起讨论的同事",越值回票价。

详细拆解

1. 我日常怎么用(给具体场景,不空谈)

  • 写代码:样板代码、SQL、正则、单元测试、重构命名、解释一段看不懂的旧代码、把报错贴进去让它定位。注意:写测试和解释代码是我最推荐的用法,因为这两件事有客观对错、容易验证。
  • 查资料与写作:总结长文档、翻译技术文章、润色邮件、把一个术语用浅显的话解释清楚、生成初稿再自己改。
  • 头脑风暴:让它先给 5 个方案,再让它逐个挑毛病,我用它来"找反方",避免自己钻进单一思路。

2. coding 领域的核心工作流(重点讲)

  • 小步快跑是关键:一次让它写 300 行,错了要 debug 半小时;一次写 30 行,错了一秒就发现。大模型的错误率乘以代码量,是翻车的概率。
  • 先让它解释再让它改:遇到报错不要只说"修一下",而是先问"这段报错是什么意思、可能原因是什么",让它给出推理,你再判断它是不是真懂——这同时是在训练你自己的排查能力。

3. 三条边界(防止被反噬)

  • 别跳过理解:AI 写的代码你看不懂也照搬,就是在积累技术债。底线是:上线的每一行你都要能讲出它在干什么。
  • 别信它的"幻觉":它会一本正经地编一个不存在的库函数/参数。凡是它给出的 API,顺手点进文档或让编译器/测试验证一遍。
  • 别让它替你定架构:它可以给建议,但"该用哪种设计、为什么"的判断要自己扛——这是工程师的核心价值,别外包出去。

4. 给新手的上手建议:从 Cursor 或 GitHub Copilot + 一个好模型 开始,先做"写单测、解释代码、查 API"这类低风险用法,养成"每步验证"的习惯,再逐步放开到"生成模块、重构"。工具本身不重要,"把上下文说清楚 + 把产出验证清楚"的习惯才重要。

面试官追问
Q:AI 生成的代码有 bug / 幻觉怎么办?
把它当"待验证的候选"而非"答案":① 让 AI 生成的代码必须有测试覆盖,写完先跑测试;② 对它引用的 API/参数保持警惕,拿不准就查文档或让编译器确认;③ bug 定位时,把完整报错 + 最小复现代码 + 你的预期行为一起贴给它,命中率会高很多;④ 它改了几次还不行,就果断换思路自己上,别和它死磕。
Q:用 AI 会不会让自己变笨、基础变差?
取决于你怎么用。如果用它"替你跳过思考",基础一定会退;如果用它"帮你把低价值重复劳动提速,把省下的时间用来啃原理、做更难的设计",反而会进步更快。我的检验标准很简单:离开 AI 你还能不能独立完成这件事?能,AI 就是杠杆;不能,你已经被它绑住了。所以我坚持"AI 写、我 review、我讲得清每一行"。
Q:你推荐哪些具体工具/模型组合?
日常写代码我用 Cursor(Copilot) + 一线旗舰模型:补全、重构、写测试、解释代码交给 IDE 内置助手;复杂架构讨论和跨文件的大改动,我会把上下文整理好再交给更强的模型。关键是选一个稳定顺手的主工具,而不是同时开五个——工具堆得多不如把一个用得深。另外建议备一个不同家的模型做交叉验证,避免单一模型的系统性盲区。
术语卡
Copilot:AI 结对编程助手,内嵌 IDE 做补全与问答。
上下文工程:把背景、约束、风格组织好喂给模型。
结对编程:一人写一人 review,AI 承担"写初稿"的角色。
代码审查(Review):对 AI 产出的人工把关环节,不可省略。
最小复现:把 bug 压缩成最小可稳定触发的样例。
