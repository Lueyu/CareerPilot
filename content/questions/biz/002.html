工程实践 · Q2

如何将 Agent 系统的 API 成本降低 70%?

⭐⭐⭐⭐ #成本优化#Agent#API
30秒电梯稿

"先建立每请求成本账单(按环节归因 token),然后组合拳:语义缓存省 30%、模型分级把 70% 简单流量切到便宜 10 倍的小模型、Prompt 压缩(LLMLingua + 检索内容精简 + 历史摘要)再省 20%、离线任务走 Batch API 半价、输出限长防废话。数学上:0.7 × 0.4 × 0.8 ≈ 0.22,降幅 78%,超额完成。关键是每招都配质量护栏,省钱不能省出事故。"

通俗类比

像家庭省钱:常做的菜周末做好冻起来,吃的时候微波炉一热(缓存);日常采购去平价超市,只有宴客才去高档超市(模型分级);按菜谱精确买菜不囤积(Prompt 压缩);大件集中采购等折扣(Batch API);先记账才知道钱花哪了(成本归因)——不记账就省钱,省的都不是大头。

详细拆解

第 0 步:成本归因(和延迟优化同理,先测量)

网关给每次调用记流水:系统提示词 1.2K + 检索注入 2.5K + 历史 1K + 输出 0.8K,按单价折算。典型发现:60% 成本在输入侧,其中检索注入占大头——这就指明了优化方向。

招式一:语义缓存(-30%)

  • 问题 embedding 相似度 > 0.95 直接返回缓存答案;企业场景命中率 30%+ 很常见。
  • 进阶:FAQ 预生成(Top 1000 高频问题离线生成好)。
  • 护栏:缓存 key 绑定知识库版本(内容更新缓存失效);抽样监控缓存答案质量。

招式二:模型分级(-40%)

  • 轻量分类器(或规则)判断难度:简单事实问答/格式转换 → 小模型;复杂推理/多工具编排 → 旗舰模型。
  • 成本差 10~50 倍,70% 流量是小模型后:整体成本 × (0.7×0.1 + 0.3×1) ≈ ×0.4。
  • 护栏:分级错误率监控;小模型回答置信度低时自动升级重答(escalation)。

招式三:Prompt 压缩(-20%)

  • 系统提示词减肥:删掉装饰性文字,指令合并(实测能砍 30~50%)。
  • LLMLingua 类工具:算法压缩提示词,语义基本不损。
  • 检索注入精简:top3 而不是 top5;文档段落做"相关句抽取"而不是整段塞。
  • 历史对话摘要化(见 Q4)。

招式四:输出与调度

  • max_tokens 限制 + Prompt 要求"直接给结论";输出 token 通常比输入贵 3~5 倍,少废话是最便宜的优化。
  • 离线任务(文档摘要、评估)走 Batch API(半价,24h 内返回)。
  • 网关比价路由:同一档位的模型按当前单价/延迟动态选。

算总账(面试时主动展示数学)

防劣化:每招上线跑黄金集;线上监控点踩率/解决率,省钱但质量掉了要立刻回滚——成本优化是"在质量约束下的优化问题",这句话说出来很加分。

面试官追问
Q:语义缓存返回了过时/错误的答案怎么办?
三个防线:① TTL(24~48h);② 知识库版本绑定强制失效;③ 缓存答案带"生成于 X 时"和反馈入口,点踩率超阈值自动下架该缓存。
Q:模型分级怎么判断"简单/复杂"?
冷启动用规则(query 长度、是否命中 FAQ、历史同类问题准确率);积累数据后训练小分类器;运行时用"小模型置信度/自检"动态升级。
Q:为什么不直接全换便宜模型?
可以更便宜但质量崩——Agent 的多步任务对模型能力敏感,一步错步步错。分级策略保住了复杂任务的质量下限。
术语卡
LLMLingua:微软的提示词压缩工具。
Batch API:批量异步接口,约半价。
Escalation:小模型不行自动升级大模型。
