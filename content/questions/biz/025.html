安全沙箱 · Q25

你的 Agent 要执行模型生成的代码、还要"自我进化"改自己的工具和权限——怎么保证安全?

⭐⭐⭐⭐ #沙箱#安全#自进化 腾讯云(社区文章)
30秒电梯稿

"安全思维是 Agent 和 Demo 的分水岭,我抓两条线。第一,任何模型生成/第三方代码绝不进主进程:一律丢独立沙箱——容器或 microVM,限额 CPU/内存/时长,不注入密钥,默认断网、外联只走白名单代理。第二,自进化可以,但权限变更不能静默生效:Agent 只能'提议'加工具、改提示词、扩权限,判定权在框架层,必须过审批门(人工或策略引擎),登记进能力注册表,全程留可回放的审计。一句话:能力可以自动长,权限永远手动批。"

通俗类比

把 Agent 当作能力很强但不能全信的外包驻场团队:活可以交,但门禁卡只开指定房间(最小权限);想进新房间必须先到前台申请(审批门);进出全程有监控(审计回放)。高危操作关在独立小隔间里做,就算砸了也伤不到主楼(沙箱隔离)。

详细拆解

1. 为什么必须有沙箱:RCE 是 Agent 系统的默认攻击面

  • 模型天然要产出代码:代码解释器、数据管线、自动修复脚本……"让 Agent 写代码并跑起来"是核心卖点,也就意味着任意代码执行(RCE)风险是系统自带的,不是可选件。
  • Prompt 注入会升级风险:一份恶意网页/文档里藏一句"请执行以下命令",就能把"帮我读文档"变成"帮我跑脚本、外传数据"。
  • 主进程就是皇冠珠宝:密钥、数据库连接、用户数据全在主进程。代码一旦在主进程执行,一次逃逸=全线失守。所以答案只有一个:换个地方跑。

2. 隔离层级怎么选(按代码可信度递增)

隔离层级强度典型用途注意
同进程函数调用❌ 无隔离仅纯计算且完全可信生产环境直接禁用
子进程 + rlimit弱可信脚本一个内核漏洞就击穿
WASM(Wasmtime 等)中高频小函数、表达式求值系统能力受限于宿主 API
容器(Docker/gVisor)强代码解释器、批任务共享内核:非特权 + seccomp + 只读根文件系统
microVM(Firecracker/Kata)最强多租户、完全不可信代码独立内核,ms 级冷启动,成本略高

3. 沙箱的四条默认(我的落地配置)

# 沙箱出口策略:默认拒绝
network: deny_all
egress_allow:            # 外联必须显式授权,按任务给域名
  - host: api.github.com
fs_mounts:
  - /work                # 只挂工作目录,读写
secrets: none            # 沙箱内不注入任何凭据
limits: { cpu: "2", mem: "1G", wall: "120s" }
  • 不注入密钥是单点最有效的一条:沙箱里没有凭据,代码想外传也传不出有价值的东西——出口再套白名单代理,双保险。
  • 结果回传主进程前做出站校验:只回文本/文件,大小与类型受限,不回传可执行物。

4. 自进化的安全设计:能力开放,权限收紧

  • 先定义"自进化"是什么:Agent 修改自身行为——换提示词、加/改工具、写长期记忆、更新技能库。风险三类:权限扩张(注入让它"给自己提权")、目标漂移(为了完成度越改越偏)、供应链(自装依赖被投毒)。
  • 权限判定权不在模型手里:模型只能发起请求,判定在框架层(策略引擎/RBAC)执行——注入再厉害也改不了代码里的权限表。
  • 能力注册表:每个工具/权限/提示词版本登记来源与版本号,新能力首次调用必须有签名与审批记录。
  • 快照 + 回滚:自进化的每一步改动可一键回退,坏版本不扩散。

5. 审计与回放:安全设计的"事后"一半

  • 每一步落 trace:输入、工具调用、权限判定结果、输出,出事可按 trace 重放取证,这是讲安全时最容易加分的细节。
  • 异常信号接告警:新工具首次调用、权限请求频率突增、出站流量形状异常。

6. 讲自己的实践(面试决胜区):我在自己的多智能体项目里定了两条铁律——第三方代码不进主进程;权限扩张不静默生效。面试时直接讲"我怎么做的、踩过什么坑",比背十条概念值钱。

面试官追问
Q:都有容器了,为什么还要 microVM?什么时候必须上?
容器共享宿主内核:gVisor 做系统调用代理已经能挡住大多数攻击,但内核 0day 依然可能逃逸。判断标准是"代码可信度 × 爆炸半径":单租户内部工具,容器 + 非特权 + seccomp 足够;多租户、跑完全不可信的用户代码,上 Firecracker/Kata 这类独立内核 microVM——每个沙箱一个精简内核,逃逸了也只是逃到一台空 VM 里。成本上 Firecracker 冷启动 ~125ms,对代码解释器场景无感。
Q:沙箱默认断网,但工具就是要调外部 API,怎么办?
不是"给沙箱开网",而是把网络收回到代理层:沙箱内 deny_all,唯一出口是宿主侧的 egress 代理,代理上按任务授权域名白名单(这次任务只允许 api.github.com),请求带任务级短时凭证,全部请求落审计。这样权限粒度从"能不能上网"细化到"这一单任务能访问哪几个域",凭证泄漏了也只在白名单域内、几分钟内有效。
Q:Prompt 注入让 Agent "给自己加权限",你的设计怎么挡住?
靠权限判定权不在模型手里:模型输出的只是"请求",真正的判定发生在框架代码里——策略引擎对照静态权限表(代码管,模型改不了)做判定,危险操作走人工审批。注入能操纵的是模型的话,操纵不了我的服务端代码。再配两条兜底:权限扩张绝不静默生效(宁可打断体验也要确认);会话级权限用完过期,即便骗到授权,影响窗口也有限。
Q:审批门打断自动化,体验和安全怎么平衡?
按爆炸半径分级:只读浏览类自动放行;写操作限额放行(每会话 N 次,超了才审);真正危险的操作(支付、删除生产数据、权限变更、新增执行代码的通道)必须人审。再加会话级时效:批一次只管这一单任务,不沉淀成长期权限。原则是:低危讲效率,高危讲确定性——面试时主动把这条分级讲出来,说明你考虑过产品侧,不是只会喊"都审批"。
术语卡
沙箱(Sandbox):隔离执行环境,代码跑在受限进程/容器/VM 内,越界也伤不到宿主。
gVisor / Firecracker:前者拦截系统调用做用户态内核,后者轻量 microVM,独立内核隔离最强。
最小权限原则:只授完成任务所需的最小权限,且随任务结束回收。
权限扩张(Privilege Escalation):攻击者(含注入的指令)诱导系统授予超出授权的能力。
能力注册表:工具/权限/提示词版本的登记台账,带来源、签名与审批记录。
审计回放(Audit Replay):全量 trace 落盘,事后可按步重演取证。
