框架选型 · Q10

监控方案选型:Prometheus + Grafana vs LangSmith vs LangFuse

⭐⭐⭐⭐ #监控#可观测性
先说人话:这题问的是:Agent 上线之后拿什么盯着它——机器扛不扛得住、答得对不对、token 烧了多少钱。面试官爱考选型,因为它照得出思维框架:张口就"三选一、逐个比参数"的,暴露的是没分清监控层次;而做过基础设施的人赢面极大——这题有一半,就是你天天在干的事。
30秒电梯稿

"先纠偏:这不是三选一,是两个层次。Prometheus+Grafana 管基础设施层——QPS、P99、错误率、GPU 水位,什么系统都需要,这套我平时就在维护;LangSmith/LangFuse 管LLM 语义层——每次回答的完整 trace、Prompt 版本、效果评估、token 成本,这是 Agent 特有的新账本。两者互不可替代:P+G 看不懂'这次回答为什么胡说',Lang 系看不到'显卡快冒烟了'。语义层二选一的判据:要开源自部署、多框架中立,选 LangFuse;重度 LangChain 生态、接受 SaaS,选 LangSmith。我的典型组合:P+G + 自部署 LangFuse,两套用 trace_id 串联。"

通俗类比

Prometheus+Grafana(用你机房的硬件监控面板想):就是你天天盯的那块大屏——节点存活、磁盘水位、IOPS 曲线、告警短信。它回答"系统活着吗、还剩多少余量",跟跑的是什么业务完全无关;给它的采集器加上 GPU 指标,它顺手就把推理集群也管了。这一半对你是送分题。

LangSmith/LangFuse(用备份软件的作业目录+任务日志想):每条记录都写清楚——这次任务输入是什么、走了哪几步、每步耗时多少、用的哪个策略(Prompt)版本、花了多少钱、用户最后满不满意。其中最核心的 trace,就是你熟的分布式链路追踪:微服务里一个请求拆成一棵 span 树,Agent 这里一模一样,只是 span 从"调了一个服务"换成"调了一次模型/检索/工具",再顺手多记一笔 token。

哪里像:两者都是"采集→存储→看板→告警"的观测闭环,套路同源,而且 P+G 那一半你闭着眼都会配。哪里不像:备份任务的步骤是写死的(扫描→传输→校验),Agent 每次的执行路径是模型现场决定的——先检索还是先调工具、要不要回头重来,每次都不同;所以语义层的 trace 除了耗时,还得存 Prompt 全文、模型输出、token 账单这些"文本+金额"型字段——只存数字的时序监控天生装不下。两套只留一套,就等于机房只有监控大屏、没有作业日志:着火了可能不知道,或者知道着火了却查不出哪次备份坏了。

详细拆解

1. 动手比较之前,先把题目掰正

先统一名词:本文说的 Agent,指会自主调用大模型(LLM)、检索知识库、执行工具来完成任务的程序。选型题最忌上来就逐个比参数,先问一句:这三个东西各自回答什么问题?Prometheus+Grafana 回答"系统活着吗、快不快、资源够不够"——所有后端系统的公共课;LangSmith/LangFuse 回答"这次回答怎么生成的、质量好不好、花了多少钱"——LLM 应用新增的必修课。一个盯机器,一个盯内容,先把层次分开,比较才有意义——面试官从这一句就开始给分。

  • 「层次/典型数据」两行是根子:P+G 的底座是时序数据库,存的是"每隔几秒聚合一次的数字",天生不存长文本;Lang 系存的是"每一次调用的全文记录"。存的东西不同,注定互补,不是竞争。
  • 「核心能力」行别只看 trace:Lang 系还带两样 P+G 完全没有的东西——评估闭环(攒一批标注好的测试集,新 Prompt 上线前先跑回归,像发版前的恢复演练)和 Prompt 版本管理(线上跑的是哪个版本、各自表现如何,像备份策略的版本表)。这俩是 Agent 迭代的命根子。
  • 「形态/隐私」两行经常一票定音:LangSmith 以 SaaS 为主、闭源;LangFuse 开源、可自部署。Agent 的 trace 里躺着用户对话和业务 Prompt,"数据不出境"在不少公司是红线——对做惯容灾合规的人,这是肌肉记忆。
  • 「生态」行是双刃剑:LangSmith 与 LangChain 深度集成,LangChain 团队近乎零接入成本;LangFuse 模型/框架中立,换个 base_url 就能把 OpenAI SDK 的流量导进来,不绑死任何一家。

3. 我的标准架构(组合拳):两层都要,一条 trace_id 串起来

下层 P+G 盯"机器和流量",上层自部署 LangFuse 盯"每一次回答"。用户请求在入口生成一个 trace_id,同时写进两边——就像备份作业 ID 既出现在存储系统的日志里、又出现在备份软件的作业目录里,排障时两边对得上号。

语义层到底长什么样?把一次用户提问的 trace 拆开看(LangFuse 里每次点开就是这么一棵树):

一次用户提问的 trace(在 LangFuse 里点开就是这么一棵树)
trace_id=7f3a…  用户问题:"帮我查一下上个月备份失败的任务"
├─ 检索(RAG)                     120ms   知识库命中 5 条
│   ├─ 向量检索                    80ms   top-k=5
│   └─ Rerank 精排                 40ms
├─ LLM 调用 [gpt-4o-mini]         2.1s    入 1.2k tok / 出 300 tok
├─ 工具调用 [查作业数据库]          350ms   SQL 返回 14 行
└─ LLM 调用 [生成最终回答]         1.8s    入 2.0k tok / 出 450 tok
──────────────────────────────────────────────────────
总耗时 4.4s · 总成本 $0.011 · 用户反馈 👎 → 回流进评估数据集

读法和你排障微服务时看 Jaeger 完全一致:整棵是 span 树,一行一个环节,自带耗时;Agent 这里新出来的字段只有两样——入/出 token和成本(token 是模型计费单位,1 个汉字约 1~2 个 token,相当于每次调用自带账单)。树根第一步"检索(RAG)"——先去知识库捞资料再回答——是 Agent 应用的常规起手式。最要紧的是末行:用户点踩回流进评估数据集,质量闭环由此转动——只有机器层监控,你永远知道"慢不慢",不知道"对不对"。

4. 用一场故障把"两套都要"焊死

设想深夜出了一次推理集群故障,两套监控在同一分钟各自看到的东西:

深夜 22:14 的一次推理集群故障,两套监控各自看到什么
────────────────────────────────────────────────────
LangFuse(语义层)  22:14
  · LLM 调用失败率 40%↑,超时 span 成片
  · 受影响的 317 个会话、白烧的 42 万 token,一屏列出
Prometheus+Grafana(基础设施层)  22:15
  · 3 号推理节点显存水位 95%
  · TTFT(首字延迟)从 0.8s 飙到 4s,P99 告警电话打出
────────────────────────────────────────────────────
P+G 告诉你"哪里坏了"  →  摘节点、扩容、止血
Lang 系告诉你"伤到谁" →  哪些会话要重跑、要不要给用户道歉

一句话收束:P+G 负责"哪里坏了",Lang 系负责"伤到谁了"。只有前者,机器修好了你却不知道有多少对话烂在半路;只有后者,你看着满屏红 trace 却找不到是哪个节点着火。能把这组对照讲出来,这题的分基本就稳了。

5. LangSmith vs LangFuse 的具体取舍

  • 选 LangSmith:团队重度使用 LangChain/LangGraph,要它的数据集-评估-回放闭环和 Playground 调试;接受 SaaS 和出境合规评估。还有一条隐性代价:按用量计费,trace 涨、账单涨,上线前要测算。
  • 选 LangFuse:要开源自部署(国内企业常态)、多框架混用(模型中立)、成本可控;它的 Prompt 管理和成本看板开箱即用。代价是自己背运维,评估能力比 LangSmith 轻一档。
  • 共同底线:两者都支持 OpenTelemetry 语义约定——选谁都要留好数据导出路径,别把观测数据变成新的供应商锁定。和你选备份介质时坚持开放格式是同一条原则:数据是自己的,工具永远可换。

6. 加分收尾:把"选型"答成"落地节奏"

  • 上线当天:P+G 挂 QPS / P99 / 错误率三件套加 GPU 水位告警;Lang 系接入 trace,第一周全量,看清分布再谈采样。
  • 第一周:token 成本看板上线;用户点踩/采纳信号回流。
  • 第一个月:攒评估数据集,新 Prompt 上线先跑回归;Prompt 版本与灰度发布绑定,一次只放 10% 流量观察。

答到这一步,面试官听到的就不是"我背过这三个产品",而是"我上过线、值过班"。

面试官追问
Q:已经有 Prometheus+Grafana 了,为什么还要再上一套 Lang 系?
人话:P+G 只认数字不认内容:它能报"这十分钟错误率 40%",但答不出"用户问了什么、模型回了什么、从哪一步开始胡说"。类比:就像你想从集群级容量报表里查出"上周三那次备份为什么跳过了某个卷"——聚合指标天生抹掉单任务细节,这种问题只能翻作业日志。技术:指标监控只存聚合后的时间序列,不落请求原文;而 LLM 应用排障恰恰要 trace 里的 Prompt 全文、检索命中、工具返回、token 消耗。反过来,Lang 系也看不到 GPU 水位——所以是互补,不是替代。
Q:两个体系的告警怎么不打架?
人话:按层次分家:机器和流量的告警归 P+G,质量和成本的归 Lang 系,别让两边为同一件事各喊一遍。类比:备份机房本来就这么干的:磁带库硬件告警走存储团队,备份失败率超阈值走备份软件的业务告警——同一机房两套通道,收件人和处理动作不同。技术:影响 SLA 的可用性/延迟告警(P99 超标、错误率、GPU 水位)走 P+G,P0 电话拉人;质量/成本异常(点踩率环比涨、单请求 token 翻倍)走 Lang 系,P2 工单;两边告警统一带 trace_id 跳转链接,值班同学一套工作流处理到底。
Q:自部署 LangFuse 的运维负担?
人话:负担很小:Docker Compose 一条命令拉起全家桶,中小规模一台虚机够用;相比它省下的人力,这点运维是零头。类比:像备份软件内嵌的元数据库——不用为它单独立项建集群;真到海量规模,再按老办法做容量规划。技术:组件就 Postgres + ClickHouse 两个;trace 量上来后做采样和 TTL(热 30 天,冷数据导出到对象存储);升级跟版本走。对比自研一套 trace 管道(采集、传输、存储、查询全自己造),省一个数量级的人力——这钱花得值。
Q:trace 越积越多,采样和留存策略怎么定?
人话:全量存是烧钱,一条不存是裸奔;按价值分层——出错的、被点踩的全存,正常的抽样存。类比:这就是你天天做的冷热分层:热数据放 SSD 随查,冷数据下沉磁带/对象存储,介质按访问价值分配——trace 一模一样。技术:常见策略:报错/负反馈 trace 100% 留,成功 trace 采样 1%~10%;TTL 设热数据 30 天,之后归档对象存储;再用成本分析看板盯住每月 token 开销。这套"采样+TTL+分层"是存储人的主场,面试里值得主动亮出来。
Q:为什么不把 trace 直接写进 ELK,自己在 Grafana 上画面板?
人话:能做,但坑很多:token 计费、Prompt 版本、评估数据集、会话回放……每块都要开发排期,最后等于自研半个 LangFuse。类比:就像有了通用文件系统,你仍然买备份软件而不是写 cp 脚本——目录、重试、校验、报表这些"胶水"才是真正的工作量。技术:ELK 存的是非结构化日志,缺 span 树模型(父子关系、嵌套耗时)和 LLM 语义字段的开箱支持;Lang 系把语义约定、成本计算、评估闭环都做好了。除非有极强的定制需求,自研性价比不划算。
术语卡
时序数据库:按时间戳存指标的库,Prometheus 自带的存储引擎就是,你的老熟人。
链路追踪:把一次请求拆成一棵 span 树记录全链路耗时,微服务排障标配;LLM trace 是同款思想。
Playground:在线改 Prompt、立刻试跑对比效果的交互界面,相当于策略的"试运行"模式。
OTel 语义约定:trace 字段的标准命名规范,换了观测平台数据仍能互认,防供应商锁定的关键。
ClickHouse:列式分析数据库,Langfuse 拿它存海量 trace,聚合查询快。
可观测性三支柱:指标、日志、链路追踪三条数据通道,本题讨论的是"指标+追踪"这两条。
