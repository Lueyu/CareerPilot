工程实践 · Q3

如何优化向量检索的召回速度?

⭐⭐⭐⭐ #向量检索#优化#RAG
先说人话:这题问的是:库里躺着几百万条向量,怎么让每次查询又快又不漏。面试官爱考它,因为这是 RAG 链路里最"工程"的一环,最能分清「背过名词的人」和「真扛过向量库线上流量的人」——答不出 Recall 与 QPS 的取舍、只会报菜名式罗列索引,就暴露了。
30秒电梯稿

"第 0 步先建基线,然后四板斧按序上:① 索引调优(HNSW 的 ef_search / IVF 的 nprobe,精度换速度要有 Recall 曲线依据);② 量化(SQ 内存 1/4、PQ 1/16,可两阶段"量化粗筛+精读重排");③ 分片并行(亿级向量 scatter-gather);④ 缓存热点 query。再往上还有 GPU 索引(如 CAGRA)和降维(768→256 的 Matryoshka)。核心原则:每一步优化都对着 Recall-QPS 曲线做 trade-off,不做无测量的玄学调参。"

通俗类比

先把场景对齐:你平时查备份,是拿备份 ID 去 B+ 树精确命中一条;而向量检索要的是「找出和这句 query 语义最像的前 k 条」——没有唯一正确答案,只有「更像/更不像」。数学上,想 100% 不漏,就得把 query 的 Embedding 和库里每一条向量的距离都算一遍(这就是 Flat 暴力检索),百万条规模下注定慢。所以这道题所有手段,本质都在回答同一件事:「能不能少算几条,还基本不漏?」哪里像:和你熟悉的 CAP 取舍一样,都是放弃一样东西换另一样;哪里不像:CAP 放弃的是一致性保证,近似检索放弃的是 Recall@10——它可测量、可回归,拿测试集就能把损失算成数字,比 CAP 温柔多了。

图书馆找书速度的进化(经典类比,顺手翻译成存储界的话):暴力检索=一本本翻(最准但 100 万本翻到明年)——等价于无索引的全量扫描,几万条以内它反而简单可靠;IVF=先按分类号走到正确书架,只翻这一架(快但可能放错架的书漏了)——等价于先用 k-means 聚类做「分区」,查询时只扫最近的几个桶,思想就是分布式数据库的分区裁剪;HNSW=老图书管理员,凭经验直接走近路,几步就到(又快又准但「经验」要花时间建)——等价于多级路由:顶层稀疏大步跳、底层稠密小步找;量化=目录卡片只记书的摘要特征,比对更快但偶尔看走眼——等价于有损压缩,把向量压小再比;分片=开 8 个借阅窗口同时查——这就是你天天做的 fan-out 并行扫描 + 归并,零新知识。

哪里像:整套优化都遵循存储/分布式界的老规矩——索引哲学(用离线预处理换在线延迟)、冷热分层(内存贵就下沉)、分治并行(数据大了就拆)。哪里不像:传统索引的查询结果是确定性的,哈希命中就是命中;近似索引返回的是「大概率对」,Recall 是个统计值,每调一个参数它都会变——所以第一步永远是建基线测试集,而不是动参数。顺序答反了,就是面试官在等的那个破绽。

详细拆解

1. 先建立基线(老规矩)

固定一份「黄金测试集」——几百上千条真实 query,每条标注好「正确答案应是哪几条文档」——然后测三样:QPS、P99 延迟、Recall@10(前 10 条结果里含正确答案的比率:标准答案是 doc#42,返回的 top10 里有它,这条就算命中)。这份测试集是后面所有调参的「秤」:之后每个优化都汇报"QPS +80%,Recall 从 0.97 → 0.95"——有数字才有说服力,也防止你优化着优化着把召回优化没了。另:拿 Flat(全量精确比对)当对照组,它是 Recall=100% 的天花板,所有近似手段的精度损失都拿它做参照系。

2. 索引选型与调参(第一优先级)

索引原理(一句话)速度/内存/精度适用
Flat(暴力)全部算一遍距离慢/小/100% 准< 10 万条,追求极致精度
IVF聚类分桶,查最近的几个桶快/小/中内存紧张、数据量大
HNSW多层贪心图导航最快/大(内存怪兽)/高默认选择,内存够就上
GPU(CAGRA)GPU 并行图检索极快/需 GPU/高超高 QPS 场景

把表格翻译成人话:Flat 不建任何索引,来一个 query 就和全库逐条算距离——十万条以内它是最优解(简单、精确、零维护),再往上延迟就顶不住。IVF(倒排文件,Inverted File)建索引时把全库聚成 nlist 个「桶」,查询时算 query 到各桶中心的距离、只进最近的 nprobe 个桶逐条精算——「先定位再扫描」的分区裁剪思想;选型经验可参考 Faiss 官方索引选择指南。HNSW 建图时每个点连若干近邻、图分多层,查询从顶层「大步跳」快速逼近目标区域、逐层下潜到底层「小步微调」——像地图导航先上高速、再下国道省道。CAGRA(论文)是 GPU 上的图索引,把海量距离计算丢给几千个核心并行,超高 QPS 场景的暴力解法。

  • HNSW 调参:M(图的连接度,建索引时定)和 ef_search(搜索广度,运行时可调)——ef_search 是最常用的速度旋钮。机制:搜索时维护一个长度为 ef_search 的候选队列,队列越长探索的分支越多、结果越接近全量最优;调小它,QPS 上去、Recall 下来,参数含义见 HNSW 论文。实操:ef_search 从 512 逐档减半(512→256→128→64),每档记录 QPS 和 Recall@10,选「Recall 贴着业务底线」的那档。
  • IVF:nlist(桶数)≈ √N 起调,nprobe(查几个桶)调小立刻变快——它和 ef_search 是同一性质的速度旋钮,只是作用对象从「图上的候选队列」换成「要进几个桶」。
调参 = 在这条曲线上选点;每动一个旋钮,要能报出"从哪个点挪到了哪个点":

Recall@10
 1.00 ┤ ● Flat(全量精确,对照组/天花板)
      │    ● ef_search=512
 0.95 ┤         ● ef_search=128   ← 业务底线 0.95,取这一档
      │              ● ef_search=64
 0.90 ┤                   ● 再叠 PQ(更激进的压缩)
      └────────────────────────→ QPS

3. 量化(省内存+提速)

  • SQ 标量量化(标量量化的原理):float32 → int8,每条 768 维向量从 3KB 压到 0.75KB,内存 1/4,int8 的 SIMD 距离计算也更快,精度损失很小——性价比之王,默认开。
  • PQ 乘积量化:向量切段编码——768 维切成 8 段,每段用码本里 256 个「中心」中最像的一个编号(1 字节)代替,单条向量压到 8 字节、内存 1/16+,精度损失明显,适合超大规模。思路很像块级去重:每个「块」只存指纹库里最像那条的编号;哪里像:都是用码本/指纹编号代替原始内容换空间;哪里不像:去重是精确等价替换,量化是近似替换,所以要付 Recall 代价(选型见 Faiss 指南)。
  • 两阶段策略:PQ 粗筛 top200 → 原始向量精读重排 top50——大规模场景速度精度兼得的经典组合(Faiss 里的 IVF-PQ + refine)。

4. 分片并行

  • 1 亿向量 → 16 个分片,各 600 万(单分片保持 HNSW 高效区间),并行查询 scatter-gather 合并。为什么不建一张 1 亿点的巨型 HNSW?图太大搜索路径变长、构建时间爆炸——分而治之,和把备份目录拆到多个存储池是同一个决策。
  • 分片数 = QPS 需求 × 副本扩展;热点分片再拆(「热 key 再拆」同款);跨分片合并用归并(各分片已排好序)——合并不需要重算任何距离:距离分数全局可比,k 路归并直接出全局 top-k。

这一段对分布式背景的人是零门槛:协调节点 fan-out、各分片本地 top-k、gather 端归并——和并行扫描多个存储池再合并结果列表完全同构,唯一区别是排序键从时间戳换成了距离。

5. 其他加速项

  • 热点缓存:高频 query 的结果直接缓存(embedding 相似度匹配)。注意和 RAG 的语义缓存区分:这里缓存的是「检索结果 top-k 列表」而非生成的答案,错配风险小得多,放心上。
  • 降维:Matryoshka(MRL) 训练的 embedding 可以只用前 256 维(768 维的 1/3 计算),精度小降——BGE 系列有支持。类比:训练时就把「缩略图」嵌进了「原图」的前几维,平时拿缩略图比对,要精确时再上原图。
  • metadata 预过滤:先按过滤条件缩小候选集再向量检索(注意 HNSW 对高选择率过滤的性能坑:过滤条件会把图上的节点「遮住」,导航被迫绕路,极端情况退化成近似全扫——见多租户题)。
优化后,一次查询在 1 亿向量 / 16 分片系统里的完整走位:

  query(768 维)
    │
    ├─ 热点缓存命中? ──是──→ 直接返回 top10(≈ 5ms,后续全免)
    │否
    ├─ scatter:并发扇出到 16 个分片
    │     每分片内部: PQ 量化粗筛 top200 → 原始向量精读 → 本地 top10(按距离排序)
    ├─ gather:16 路归并(不重算距离) ──→ 全局 top10
    └─ 交给下游:Rerank / 生成

为什么每一步都在「少算」:
  Flat 全量比对  = 1 亿次距离计算,慢
  PQ 粗筛        = 还是比 1 亿条,但每条便宜 16 倍,只留 200 条
  原始向量精读   = 只对 200 条精算,贵但量极小
  —— 分层过滤,和备份时先比对指纹、再比对全量数据是同一招
面试官追问
Q:量化导致 Recall 掉了,怎么找补?
人话:量化是有损压缩,压缩必然失真——先守住「别把真结果挤出候选门」,再靠后置环节把精度补回来。类比:像先用压缩缩略图粗筛监控录像,锁定嫌疑片段后回放原始录像确认——粗筛快但糙,精读准但只对小范围做。技术:① 两阶段:量化粗筛扩大候选(top50→top200),再用原始向量精读重排;② 靠下游 rerank 找回排序精度;③ 混合精度:热数据留原始向量、冷数据量化,按业务重要性分配精度;④ 每次改动跑黄金集回归,Recall 曲线达标才算数。
Q:HNSW 内存不够怎么办?
人话:三条路按代价排:先压缩,再分层,最后加机器。类比:这就是备份系统的经典冷热分层——热数据放内存/SSD,冷数据下沉磁盘/对象存储,介质按访问频率分配,没有一条数据天生配得上 SSD。技术:① 量化:SQ 起步(内存 1/4),仍紧再上 IVF-PQ(1/16);② 数据分层:热数据驻内存 HNSW,冷数据放磁盘索引(如 DiskANN 类方案)或 Milvus/Elasticsearch 的磁盘友好索引;③ 都不行就加机器——最诚实的选择,HNSW 是内存怪兽,没有银弹。
Q:IVF 和 HNSW 到底怎么选?
人话:内存够、要极致速度和精度选 HNSW;数据量特别大、内存紧张、能接受中等精度选 IVF(常配 PQ);十万级以下直接 Flat,别折腾。类比:像选 RAID/存储介质——HNSW 是全闪阵列,性能最好但每 GB 都贵(内存);IVF-PQ 是大容量机械盘阵列,便宜能装但慢一些,偶尔要靠校验(重排)兜底。技术:IVF 构建快、内存小、可落盘;HNSW 查询快、Recall 高,但内存开销是向量本身的好几倍(图结构+全量向量驻留)。正确姿势:同一数据集两种都建,画 Recall-QPS 曲线,按业务底线(如 Recall@10 ≥ 0.95)选满足要求的更便宜者。
Q:ef_search 调小,系统里到底发生了什么?为什么快了但可能漏?
人话:它控制搜索时候选名单的长度——名单越长越不漏但越慢,越短走得越快但可能半路错过更近的点。类比:像容灾切换时问「哪个站点状态最好」:问的范围大就稳,只问两三个就快但可能漏掉状态更好的站点。技术:HNSW 贪心图导航时维护一个大小为 ef_search 的候选优先队列,队列越长探索的分支越多、结果越接近全局最优;调小 = 收窄搜索波束,QPS 上升、Recall 下降。它运行时可调、不用重建索引,所以是线上压测最好用的旋钮——每档调整都记录 Recall@10,拿数据说话。
术语卡
ef_search:HNSW 运行时旋钮,搜索候选队列长度——调小提速但可能漏,线上压测第一选择。
nprobe:IVF 查询时访问的桶数,桶数越少越快、漏得越多。
SQ/PQ:标量/乘积量化,把向量有损压缩成 int8 或码本编号,内存 1/4 到 1/16。
Scatter-gather:分散并行查询各分片再归并聚合——分布式系统的老朋友。
MRL:套娃表示,训练时让向量「前几维就能用」,截断使用省算力省内存。
CAGRA:GPU 图索引,超高 QPS 场景把海量距离计算丢给几千个核心并行。
