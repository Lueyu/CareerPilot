工程实践 · Q12

如何实现 RAG 的多语言支持?

⭐⭐⭐⭐ #多语言#RAG#国际化
30秒电梯稿

"两条路线:跨语言检索——用多语言 Embedding(BGE-M3 这类)让中文 query 直接命中英文文档,零翻译成本、实时性好,是默认选择;翻译管道——query 翻译成索引语言再检索,适合 embedding 模型多语言能力不足的语种。工程上:入口语言检测路由(含中英混杂处理),检索可双路并行(原 query + 翻译版各查一遍 RRF 融合),生成侧跟随用户语言输出;效果必须分语言评估,小语种单独建回归集。"

通俗类比

联合国图书馆:方案一:图书管理员懂 100 种语言,你用中文描述"关于气候变化的书",他直接把英文书、阿拉伯文书都抱过来(跨语言 embedding——向量空间里"意思相近"不分语言);方案二:先把你中文的需求翻成英文,再按英文书名找(翻译管道——多一道工序,翻译不好就找错书);最后都请一位同声传译把找到的内容讲回中文给你听(生成跟随用户语言)。

详细拆解

1. Embedding 选型(地基)

  • 首选多语言模型:BGE-M3(100+ 语言,还同时支持稠密/稀疏/多向量三种检索)、multilingual-e5、jina 多语言版;验证方法:用自己的中英平行 query-文档对测跨语言 Recall,别只信榜单。
  • 坑:单语模型(如纯中文训练的)的向量空间里,中英文"同义"距离很远——跨语言检索直接失效,这是多语言 RAG 第一大坑。

2. 语言检测与路由

  • 入口轻量检测(fastText/规则,毫秒级);按语言路由到对应策略和分词器(BM25 分词对语言敏感:中文要 IK 分词,英文空格切分)。
  • 中英夹杂是中文场景日常:"帮我看看这个 PR 的 review 意见"——检测主语言即可,不用强行翻译;BM25 混合索引 + embedding 天然处理。

3. 检索策略(双路并行,兼得)

  • 翻译质量用便宜模型即可(检索对翻译噪声不敏感);高频 query 的翻译结果缓存。
  • 文档侧:保持原文索引(存原语言,检索后按需翻译展示),不做全量预翻译——预翻译有损且维护成本高,除非检索质量实在不行。

4. 生成语言控制

  • 规则一:Prompt 明确"始终用用户的语言回答"+把检索到的外文片段标注"以下是英文参考资料";强模型基本遵守。
  • 兜底:输出语言检测不对,带"用 X 语言重写"轻量重试一次。
  • 注意"答案语种"与"引用原文":引用块保持原语言并给出翻译,可信度和可读性都要。

5. 评估必须分语言(很多人栽在这)

  • 每种支持的语言建独立评估集;常见结果:英语 95 分、中文 90 分、小语种 70 分——小语种差主要差在 embedding 和分词,针对性补数据或加翻译路。
  • 线上监控分语言的满意度/点踩率。
面试官追问
Q:小语种(泰语/越南语)检索很差,怎么办?
① 翻译管道保底(query 翻成英文检索,效果好但加延迟);② 小语种文档额外建"英文影子索引"(离线翻译入库);③ 评估收益后决定,别为 1% 流量的语种做 30% 的复杂度。
Q:跨语言 embedding 的原理是什么?
训练时用了大规模平行语料(同义多语言对齐),把"同义不同语"的文本拉到向量空间的相近位置——所以语义检索能跨语言;但它的单语言内精度通常略低于专用单语模型,是 trade-off。
术语卡
跨语言检索:一种语言的 query 检索另一种语言的文档。
平行语料:同一内容的多语言对照文本。
影子索引:为同一内容建的另一语言索引。
