Agent算法 · Q1

如何提升 GraphRAG 的多跳推理召回率？

⭐⭐⭐⭐ #GraphRAG#多跳推理#算法优化 字节 / 阿里（真题）
30秒电梯稿

"GraphRAG 多跳召回率低的根因不在检索那一下,而在前置的图建得不准、切得不对、查得不对路。我从四层提升:第一,建图质量——实体抽取和关系抽取用强模型 + Schema 约束 + few-shot,别名合并、共指消解,图不准后面全白搭;第二,索引粒度——社区检测(Leiden)做分层,局部问题走实体级子图、全局问题走社区摘要,别一刀切;第三,查询策略——Query 改写(别名扩展、子问题分解)+ 多路检索(实体检索 + 向量 + BM25 + 图邻居扩展)融合;第四,评估闭环——用 HotpotQA / MuSiQue 这类多跳基准逐层定位是抽取、链接还是检索哪一环漏了。"

通俗类比

多跳推理就像侦探连证据链:要答"A 的导师的机构是哪家",得先找到 A,再顺着"师生关系"找到导师,最后查导师的任职机构——一环断了整条链就断。GraphRAG 相当于先把所有书拆成一张人物关系网(知识图谱),侦探在网里定位起点再顺藤摸瓜。召回率低 = 证据链断掉,通常三种原因:① 关系网里根本没把这个人画进去(抽取漏了);② 同名同姓画错了人(链接错了);③ 侦探只翻了局部没翻全(检索范围不对)。提升召回率就是修这三个环节。

详细拆解

1. 先定位漏在哪里(别上来就调参)

  • 多跳召回率是级联乘积:第 k 跳的召回 ≈ (实体抽取率 × 链接准确率 × 关系抽取率 × 每跳检索命中率)^k。任何一环 90%,三跳后只剩约 0.73;所以多跳对每一环的精度都极度敏感——这是多跳比单跳难得多的根本原因。
  • 先做分层归因:把失败 case 分到"实体没抽取到 / 链接错 / 关系缺失 / 检索没命中 / Query 表达不对"五类,哪类占比高就优先打哪。

2. 建图质量(召回率的地基)

  • 实体抽取:定义目标 Schema(人物/机构/概念/事件等),用强模型 + few-shot + 结构化输出(JSON),提示词里明确"哪些算实体、哪些算属性";低置信度实体用阈值过滤或人工抽检。
  • 关系抽取:对每对候选实体判断关系类型;关系本体不能无限膨胀,先按业务收敛到几十类核心关系。
  • 实体对齐 / 共指消解:这是多跳最常见漏点——"OpenAI"和"OpenAI Inc"、"乔布斯"和"Steve Jobs"本是一体,不合并就断链。做法:同义词典 + 向量相似度聚类 + 规则(缩写、大小写)。
  • 别名与多义:同一实体多个别名建别名索引;同名不同实体靠上下文消歧(LLM 判或实体类型 + 邻居结构辅助)。

3. 社区检测与分层索引(粒度是核心 trade-off)

  • 社区切太粗:一个社区塞进上千实体,摘要变成"大杂烩",目标信息被稀释;切太细:社区碎片化,跨社区的桥接边(多跳的"跳"就靠这个)被切断。经验上是分层存储、按查询动态选层,而不是只留一层。
  • Leiden 算法(比 Louvain 更优,避免"坏连接"社区)的分辨率参数决定粒度;可以按领域数据做网格搜索,用下游 recall 做指标。
  • GraphRAG 原版主打全局性问题("总结全文主题")靠社区摘要;而多跳事实查询更像局部问题,直接对实体子图做邻居扩展往往比摘要更准——能说出"GraphRAG 的社区摘要不是多跳事实问答的银弹"是加分点。

4. 查询策略(检索那一层怎么提召回)

  • Query 改写:先做子问题分解(把"X 和 Y 的共同投资者"拆成"X 的投资者""Y 的投资者"再求交),多跳查询直接拆成多个单跳子查询分别检索再汇合,比直接喂整句更容易命中。
  • 别名扩展 + 实体链接:Query 里识别的实体先链接到图谱节点(而非只匹配字符串),再把该节点的所有别名展开参与检索。
  • 多路检索融合:实体/关系结构化检索(精确)+ 向量检索(语义近似)+ BM25(关键词)+ 图谱邻居扩展(BFS 1~2 跳)并行,用 RRF 融合。单一路线在多跳场景几乎必漏。
  • 迭代检索 / 自我反思:首轮结果不足以支撑答案时,根据已命中实体再扩展下一跳,最多 N 轮;这是多跳检索的标准做法。

5. 评估与闭环

  • 多跳基准:HotpotQA(2 跳)、2WikiMultihopQA(2~4 跳)、MuSiQue(可组合多跳、更难)。
  • 指标别只看端到端 recall,要分抽取 recall / 链接准确率 / 每跳命中率 / 端到端 F1 逐层看,才能定位瓶颈。
  • 成本 trade-off:GraphRAG 建图 + 社区摘要很贵(token 消耗大),在线时把社区摘要预生成缓存;增量更新只重建受影响的社区而非全图。
面试官追问
Q:社区切分的粒度到底怎么定?有客观方法吗?
以"下游指标"为准做搜索:固定抽取质量后,扫不同分辨率参数,看在多跳评测集上的端到端 recall;经验上"社区内实体数十到数百、跨社区桥接边足够"是合理区间。也可以分层保留——粗层管全局摘要、细层管局部检索,查询时动态选层,避免二选一。
Q:实体链接错了/漏了怎么办?尤其同名多义和别名。
三层兜底:① 建别名索引,Query 实体先展开全部别名再检索;② 用向量相似度 + 类型约束做候选链接,再让 LLM 结合上下文消歧(看句子语境指哪个);③ 链接置信度低时不硬链,而是把多个候选都带进检索、由后续推理消歧。链接错一次,后面全错,所以低置信度宁多勿错。
Q:GraphRAG 建图成本很高,怎么平衡成本与召回?
分场景:① 全局/主题级问答才需要社区摘要,事实多跳只要实体-关系子图,可以只建图不做社区摘要,省掉一大块 token;② 社区摘要离线预生成并缓存,增量更新走"局部社区重建"而非全量重跑;③ 抽取用便宜模型 + 强模型抽检,高频冷门实体用规则兜底。核心是"按查询类型决定用图的哪一层"。
Q:多跳问题怎么判断该走图,而不是普通向量检索就够?
用轻量分类器/规则判断查询是否含关系推理词("…的…的…"、比较、桥接实体),或先跑一次单跳向量检索,看能否直接命中答案;命中不了且查询含多个实体 → 升级走图。判断本身要便宜,否则自适应省下来的被路由开销吃掉了。
术语卡
GraphRAG:微软提出的图增强 RAG,用实体-关系图 + 社区摘要回答全局问题。
Leiden:社区检测算法,比 Louvain 更能保证社区连通性。
共指消解:把指向同一实体的不同说法合并成一个节点。
RRF:倒数排名融合,把多路检索结果合成一个榜单。
多跳推理:需要跨多个事实/实体串联才能回答的推理。
MuSiQue:可组合的多跳问答基准,比 HotpotQA 更难。
