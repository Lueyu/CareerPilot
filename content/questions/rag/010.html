Agent算法 · Q1

如何提升 GraphRAG 的多跳推理召回率？

⭐⭐⭐⭐ #GraphRAG#多跳推理#算法优化 字节 / 阿里（真题）
先说人话:这道题在问:你的图谱问答系统里,那些要"连着跳好几步"才能答的问题老是答不上来——不是模型不会算,是证据链上的证据没被检索到,怎么系统性修。面试官爱考它,因为多跳是 RAG 的深水区,一开口就能分清"只会调 top-k 的人"和"真从建图修到查询的人"。答错的典型暴露点:张口就"换更强的 embedding",说明没看懂多跳的损耗是级联的,根子多半在建图和实体链接。
30秒电梯稿

"GraphRAG 多跳召回率低的根因不在检索那一下,而在前置的图建得不准、切得不对、查得不对路。我从四层提升:第一,建图质量——实体抽取和关系抽取用强模型 + Schema 约束 + few-shot,别名合并、共指消解,图不准后面全白搭;第二,索引粒度——社区检测(Leiden)做分层,局部问题走实体级子图、全局问题走社区摘要,别一刀切;第三,查询策略——Query 改写(别名扩展、子问题分解)+ 多路检索(实体检索 + 向量 + BM25 + 图邻居扩展)融合;第四,评估闭环——用 HotpotQA / MuSiQue 这类多跳基准先做分层归因,搞清楚是抽取、链接还是检索哪一环漏了,再对症下药——这一步其实应该排第一,先归因、再动手。"

通俗类比

多跳推理 = 连元数据链。拿备份系统里天天发生的事举例:查"这台虚拟机去年 3 月那份归档副本,现在落在哪个介质池?"没有一个现成字段直接存着答案,你得顺着链跳:VM → 快照 → 备份集 → 复制副本 → 归档介质——每一步都要拿上一步的结果当下一步的查询键,哪一环元数据缺失或映射断了,这条链就答不出来。GraphRAG 干的事,是提前把语料拆成一张实体-关系网(知识图谱)——像 CMDB:把"谁依赖谁、谁连接谁"预先登记成拓扑图,查询时先定位起点节点,再顺着边一跳一跳摸过去。多跳召回率低 = 证据链断了,断因通常三类:① 图里根本没把这个实体画进去(抽取漏了);② 画进去了,但中途某环没对上号(链接错了——同一块盘在阵列侧叫 WWN、在主机侧叫 /dev/sdb、在备份系统里叫资源 ID,三处不做映射,追溯链必断);③ 图是对的,但侦探只翻了局部没翻全(检索范围不对)。提升召回率,就是按顺序修这三层。

为什么多跳格外难修:成功率是连乘的。每一跳要"抽取对 × 链接对 × 关系在 × 检索命中",四环各 90%,一跳就只剩约 0.65;三跳连乘下来惨不忍睹——这和备份域"端到端可恢复率 = 快照成功率 × 备份成功率 × 复制成功率 × 归档成功率"是同一个数学,所以备份验收从来只认端到端演练,单看某一环的健康度会自我感觉良好。哪里像:都是链式系统、都吃最弱一环;单环节 90% 听着还行,端到端就崩;修法都是"全链路逐环抠 + 端到端指标验收"。哪里不像:备份链的拓扑是固定的——几级、每级拿什么键查,上线时就定死了;多跳推理的"跳"是动态的,建图时不知道哪条边将来会被问到,所以建图必须"宁滥勿缺",把可抽的关系尽量登记全,精筛留给检索阶段;另一个区别是推理链断了可以换路(A 到 C 走不通 A→B→C,还能绕 A→D→C),备份链基本没有备路——这决定了多跳除了修每一环,还能在查询侧玩多路、迭代这些"绕路"策略。

详细拆解

1. 先定位漏在哪里(别上来就调参)

  • 多跳召回率是级联乘积:第 k 跳的召回 ≈ (实体抽取率 × 链接准确率 × 关系抽取率 × 每跳检索命中率)^k。任何一环 90%,三跳后只剩约 0.73;所以多跳对每一环的精度都极度敏感——这是多跳比单跳难得多的根本原因。把这条算术摆给面试官,是最快建立"我懂为什么"的方式:
每环质量1 跳2 跳3 跳4 跳
90%0.900.810.730.66
95%0.950.900.860.81
98%0.980.960.940.92

看第四行和第一行的差距:4 跳问题把每环从 90% 抠到 98%,端到端从 0.66 提到 0.92——答错率从"三分之一答不上"压到"不到十分之一"。单跳场景里 90% 和 98% 只是锦上添花,多跳场景里是生死线。这就是为什么这题的标准解法是全链路逐环工程,而不是单点调参。

  • 先做分层归因:把失败 case 分到"实体没抽取到 / 链接错 / 关系缺失 / 检索没命中 / Query 表达不对"五类,哪类占比高就优先打哪。落到操作上就是这张排查表——和排备份故障先分"作业没起 / 起了没跑完 / 跑完了数据不对"是同一个职业习惯:
失败类型典型症状怎么确认对应修法
实体没抽取到图里根本没有这个节点回去看原文,实体明明在文中第 2 步:加强抽取
链接错了检索到同名但错误的实体看命中节点的邻居对不对别名索引 + 消歧
关系缺失两个节点都在,但没有边查邻居列表,对方不在关系抽取补全
检索没命中节点边都在,就是没被召回单独查该子图,能查到第 4 步:多路 + 改写
Query 表达不对用户问法和文档说法差太远人工换个问法能查到Query 改写 + 分解

2. 建图质量(召回率的地基)

这层出的问题,在检索侧永远修不回来——元数据登记错了,查询引擎再强也只能在错的目录里打转。四个子环节逐个抠:

  • 实体抽取:先定义目标 Schema(人物/机构/产品/技术概念/事件等,几十类封顶),用强模型 + few-shot + 结构化输出(JSON),提示词里明确"哪些算实体、哪些算属性"——这一步就是给抽取器发"登记模板",没模板它自由发挥,抽出来的东西千奇百怪。低置信度实体用阈值过滤或人工抽检,别让脏节点污染图。
  • 关系抽取:对每对候选实体(通常同句/同段共现的)判断关系类型;关系本体不能无限膨胀——开放抽取会抽出几百种花式关系,图没法用。先按业务收敛到几十类核心关系(投资/任职/属于/依赖/参与……),抽不进本体的先进"其他"待审。
  • 实体对齐 / 共指消解:这是多跳最常见漏点——"OpenAI"和"OpenAI Inc"、"乔布斯"和"Steve Jobs"本是一体,不合并就断链。这和存储域的痛完全同构:同一块盘在阵列侧是 WWN、在主机侧是设备名、在备份系统里是资源 ID,不做统一映射,跨系统追溯必断。做法三层:同义词典(显式规则)+ 向量相似度聚类(embedding 距离小于阈值聚成簇,再人工确认)+ 规则(缩写展开、大小写、全半角)。
  • 别名与多义:同一实体多个别名,在节点上挂别名索引——像 DNS 一条 A 记录挂若干 CNAME,哪个名字来查都能解析到同一节点;同名不同实体(两个"张伟")靠上下文消歧:LLM 看句子语境指哪个,再用实体类型和邻居结构辅助——"这个张伟的邻居全是影视节点,那个全是学术节点,显然不是一个人"。

3. 社区检测与分层索引(粒度是核心 trade-off)

社区 = 把图聚成一个个"主题圈",相当于把机房资产聚成故障域、把监控聚成聚合层级——园区、机柜、节点各管一层。粗层适合"整体怎么样"的问题,细层适合"这一台怎么了"的问题;只留一个粒度,必然有一类人没法干活:

  • 社区切太粗:一个社区塞进上千实体,摘要变成"大杂烩",目标信息被稀释——像一份把整个园区所有备份作业混在一起的周报,"整体成功率 97%"看着挺好,你关心的那次失败被平均得看不见;切太细:社区碎片化,跨社区的桥接边(多跳的"跳"就靠这个)被切断——像每台设备单独出一张日报,没人能看出园区级趋势。经验上是分层存储、按查询动态选层,而不是只留一层,把"选粒度"从建图时一次性决定,变成查询时按问题决定。
  • Leiden 算法(比 Louvain 更优,避免"坏连接"社区——Louvain 会产出名义上一个社区、实际内部断成两截的社区,连通性没保证)的分辨率参数决定粒度;可以按领域数据做网格搜索,用下游 recall 做指标——不拿"看着舒服"定参数,拿评测集说话。
  • GraphRAG 原版(微软论文)主打全局性问题("总结全文主题")靠社区摘要;而多跳事实查询更像局部问题,直接对实体子图做邻居扩展往往比摘要更准。为什么?社区摘要是一次 map-reduce 压缩出来的"平均信息",多跳要的却是精确的两三条边——压缩本身就是信息损失,拿周报查单笔交易,当然查不到。能说出"GraphRAG 的社区摘要不是多跳事实问答的银弹"是加分点。

4. 查询策略(检索那一层怎么提召回)

  • Query 改写:先做子问题分解——多跳查询直接拆成多个单跳子查询分别检索再汇合,比直接喂整句更容易命中。拆的道理:整句一把梭,两个实体在句子里互相干扰,哪一边都搜不全;拆开各搜各的,把一个"双实体联合检索"的难题变成两个"单实体检索"的简单题:
问:"A 公司和 B 公司的共同投资者是谁?"

整句直接检索(容易漏):"A公司 B公司 共同投资者"一把梭 → 两边都没搜全,链断

子问题分解 + 汇合:
  Q1 = "A 公司的投资者有哪些?" → 图上命中 {红杉, 高瓴}
  Q2 = "B 公司的投资者有哪些?" → 图上命中 {红杉, 腾讯}
  汇合(求交): {红杉, 高瓴} ∩ {红杉, 腾讯} = {红杉}
  返回:红杉 + 两条"投资"边,作为完整证据链一起给模型
  • 别名扩展 + 实体链接:Query 里识别的实体先链接到图谱节点(拿到节点 ID),而非只匹配字符串——这一步的差别,像"把主机名解析成 IP 再操作"和"拿主机名子串到处 grep"的差别,前者精确、后者看运气。链接成功后,再把该节点挂的所有别名展开参与检索,让 BM25 和向量两侧的命中面都变大。
  • 多路检索融合:四路并行、各管一段,用 RRF 融合。单一路线在多跳场景几乎必漏——因为每路都有自己看不见的角落:
检索路强项弱项多跳里的角色
实体/关系结构化检索精确、零漏检地定位符号依赖实体先链对定位起点锚点
向量检索换个说法也能命中只有单跳视野找"意思相近"的入口
BM25专名/型号精确不懂同义改写兜住专名和缩写
图邻居扩展(BFS 1~2 跳)正是"跳"的执行者起点错则全错负责跨步串联

RRF 融合的好处:各路只交排名、不比绝对分——像三个副本各自返回榜单,按"在各家榜单里的名次"合成一张总榜,不用调分数权重,天然规避"向量分数和 BM25 分数量纲不同没法比"的问题。

  • 迭代检索 / 自我反思:首轮结果不足以支撑答案时,根据已命中实体再扩展下一跳,最多 N 轮;每轮拿"当前证据够不够回答"当停止条件。这就是查归档位置的老套路:先查备份集拿到 job ID,发现介质字段为空,再拿 job ID 去介质库查——不是一次查完,是"查一步、看一步、再查下一步"。这是多跳检索的标准做法。

5. 评估与闭环

  • 多跳基准:HotpotQA(2 跳)、2WikiMultihopQA(2~4 跳)、MuSiQue(可组合多跳、更难——专门构造了"伪多跳"干扰,防止模型靠单跳答案蒙混过关,是三件套里最能试出真本事的)。
  • 指标别只看端到端 recall,要分抽取 recall / 链接准确率 / 每跳命中率 / 端到端 F1 逐层看,才能定位瓶颈——和备份健康度分层看(单作业成功率、复制成功率、端到端演练通过率)是同一个逻辑:端到端指标掉了,先看是哪一层掉的,别猜。
  • 成本 trade-off:GraphRAG 建图 + 社区摘要很贵(token 消耗大),在线时把社区摘要预生成缓存;增量更新只重建受影响的社区而非全图——注意"重写放大":改一份文档,牵连它所在社区及其上层社区摘要一起重算,增量策略要按社区边界裁剪影响面,这和增量备份要算"改动扩散范围"是一个意识。
面试官追问
Q:社区切分的粒度到底怎么定?有客观方法吗?
人话:粒度没有"正确答案",只有"和你的问题分布匹配的答案"——别拍脑袋定,拿下游指标扫出来。类比:像备份域的聚合层级——机房、机柜、节点哪层出报表,取决于看的人是园区主管还是值班工程师;一刀切只留一层,必然有一类人没法干活。技术:固定抽取质量后,对 Leiden 分辨率参数做网格搜索,以多跳评测集上的端到端 recall 为选型指标;经验区间是"社区内实体数十到数百、跨社区桥接边保留充分"。更稳的做法是分层保留:粗层管全局摘要、细层管局部检索,查询时动态选层,不做二选一。
Q:实体链接错了/漏了怎么办?尤其同名多义和别名。
人话:链接是链条上的单点,错一次后面全错——所以修它的总原则是"低置信度宁多勿错"。类比:像存储里把多路径设备的 WWN 映射到错的 LUN——不是"慢一点"的问题,是 I/O 静默写错盘;比"操作失败"更危险的是"操作成功但对象错了"。技术:三层兜底:① 建别名索引,Query 实体先展开全部别名再检索;② 用向量相似度 + 类型约束出候选链接,再让 LLM 结合上下文消歧;③ 链接置信度低时不硬链,把多个候选都带进检索、由后续推理消歧。同时把链接错误率单列为指标进评估闭环,别让它混在端到端指标里看不见。
Q:GraphRAG 建图成本很高,怎么平衡成本与召回?
人话:不是每类查询都值得全套图索引——按查询类型决定建图的哪一层,钱花在刀刃上。类比:不是每份数据都值得全量备份——核心库全量+增量,冷数据只归档;索引建设同理,按查询价值和频率分级投入。技术:① 全局/主题级问答才需要社区摘要,事实多跳只要实体-关系子图,可以只建图不做社区摘要,省掉一大块 token;② 社区摘要离线预生成并缓存,在线只读;③ 增量更新走"局部社区重建"而非全量重跑;④ 抽取用便宜模型 + 强模型抽检,高频冷门实体用规则兜底。核心一句:按查询类型决定用图的哪一层。
Q:多跳问题怎么判断该走图,而不是普通向量检索就够?
人话:先用小成本判断问题的"跳数",单跳直接向量检索,多跳才升级走图——路由本身就是道性价比题。类比:像读请求先打缓存、miss 才回源数据库——路由的开销必须远小于省下的成本,否则判断本身就吃掉收益。技术:轻量做法两条:① 规则/小分类器看查询形态——含"…的…的…"链式指代、比较词、多个专名,判为多跳候选;② 试探法:先跑一次单跳向量检索,能直接命中答案就返回,命中不了且查询含多个实体再升级走图。判断逻辑用纯规则或小模型,控制在毫秒级,别让路由成为新的延迟大头。
术语卡
GraphRAG:微软提出的图增强 RAG,用实体-关系图 + 社区摘要回答全局问题。
Leiden:社区检测算法,比 Louvain 更能保证社区内部连通,分辨率参数控制粒度。
共指消解:把指向同一实体的不同说法合并成一个节点——不做这一步,多跳链必断。
RRF:倒数排名融合,只看各路排名不比绝对分,把多路检索结果合成一个榜单。
多跳推理:需要跨多个事实/实体串联才能回答的推理,端到端召回是各环成功率的连乘。
MuSiQue:可组合的多跳问答基准,比 HotpotQA 更难,专门防"伪多跳"蒙混。
