工程实践 · Q1

如何将 RAG 系统的 P99 延迟从 2s 降低到 300ms?

⭐⭐⭐⭐ #性能优化#延迟#RAG 字节(真题)
30秒电梯稿

"第一步永远不是改代码,而是分段打点测量——把 2s 拆到每个环节,看钱花在哪。典型构成:检索 800ms + 生成 1200ms。检索侧:语义缓存直接让 30% 请求变 50ms、HNSW 调参和向量量化、重排砍量或降级;生成侧:用户感知的是首字时间,流式输出 + 限制输出长度 + 模型分级;最后治理长尾——P99 差就是那 1% 最慢的请求,逐类专项消灭。每一步都拿 Recall 和质量指标护航,防止优化延迟把准确率优化没了。"

通俗类比

像治理高速堵车:先查清堵点在哪(分段计时,是收费站还是隧道),收费口(检索)改 ETC(缓存+量化),主干道(生成)放开限速减少车距(流式+限长);最堵的那几个特殊时段(长尾请求:超长文档、怪异 query)单独治理。不测量就动手,等于闭着眼修路。

详细拆解

第 0 步:建立延迟画像(没有这步都是瞎优化)

环节现状目标主要手段
Query 理解150ms砍掉/并行简单 query 跳过改写;改写与检索预热并行
向量检索300ms100msHNSW 调参、量化、topk 缩小

合计(感知)~2s~300ms语义缓存命中时 < 50ms

检索优化(800 → 200ms)

  • 语义缓存:命中率 30%,命中请求整体变 50ms——单点 ROI 最高的优化,先做这个。
  • HNSW 调参:ef_search 从 256 降到 64,查询快 3 倍,Recall@10 从 0.98 降到 0.95(通常可接受——拿 Recall 曲线说话,不做无依据的牺牲)。
  • 向量量化:SQ/ PQ 压缩,内存降、缓存命中升、距离计算变快。
  • 重排降级:Cross-Encoder 重排 top50 最贵;降到重排 top10,或换两阶段(量化粗筛→精读小模型)。
  • topk 全链路收紧:召回 50 → 20,注入生成 5 → 3,又快又省 token。

生成优化(1050 → 感知 300ms)

  • 流式输出:核心思想——用户感知的是首字时间,不是总时长。TTFT 300ms 达标,后面慢慢吐字用户觉得"一直在干活"。
  • 限制输出:max_tokens 500;Prompt 里要求"先给结论,再给依据"(结论 100ms 内就流出来了)。
  • 模型分级:难度分类器把 70% 简单问题路由到小模型,TTFT 快 2~4 倍。
  • 前缀缓存:系统提示词相同的部分,网关/推理引擎复用 KV(见 Q5),首 token 显著加速。

并行化(白捡的延迟)

  • Query 改写和"用原 query 先检索第一轮"并行,改写完补充第二轮;多路检索(向量/BM25)并行;重排和生成的 Prompt 骨架准备并行。

长尾治理(P99 专项)

P99 = 最慢的 1% 请求。把它们拉出来聚类分析:① 超长文档类 → chunk 预过滤/摘要化;② 缓存全 miss 的冷门 query → 无解但占比小;③ 下游抖动(向量库 GC)→ 超时+重试+多副本。能讲出"看最慢 1% 的请求构成"这句话,面试官就知道你真干过。

面试官追问
Q:砍重排、降 ef_search 都牺牲了精度,怎么保证答案质量不掉?
所有调参改动跑黄金集回归(答案质量 + Recall@k),质量掉超阈值就回退参数;A/B 实验兜底。性能优化必须带着质量护栏做。
Q:只有一周时间,先做哪个?
优先级:语义缓存 > 流式输出 > topk 收紧 > 模型分级 > 索引调参。前两个改动小、无质量风险、收益直接覆盖大部分流量。
术语卡
ef_search:HNSW 搜索深度参数,精度换速度的旋钮。
长尾请求:最慢的那一小撮,决定 P99。
Recall@k:前 k 结果的查全率。
