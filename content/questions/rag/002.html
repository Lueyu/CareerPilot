系统设计 · Q3

设计一个支持流式输出的 RAG 系统

⭐⭐⭐⭐ #RAG#流式输出#系统设计
30秒电梯稿

"核心思路是把『等全部生成完再返回』改成『边检索边反馈、边生成边推送』:用 SSE 长连接,检索阶段先推送状态事件(正在查什么、命中哪些文档),生成阶段 LLM 的 token 一到就转发给前端;核心指标是 TTFT(首字时间),通过检索/生成流水线并行把它压到 500ms 内;同时要处理客户端断连中止生成、断线重连续传这些工程细节。"

通俗类比

差别就像请客吃饭:非流式是"后厨把十道菜全做完一起上",客人饿等 20 分钟;流式是"凉菜先上,热菜一道道端"——菜的总时长没变,但客人 2 分钟就有东西吃,感知上快了 10 倍。首字时间 TTFT 就是"第一盘凉菜多久上桌"。

详细拆解

1. 为什么要流式(先讲清价值)

生成一段 500 token 的答案要 3~5 秒。用户盯着白屏 3 秒就会觉得"卡死了";而首字 300ms 出现、后面每秒吐 50 字,总时长没变,但感知延迟从 3 秒降到 0.3 秒。这就是为什么所有主流 AI 产品(ChatGPT、Kimi、豆包)都是流式。

2. 协议选型:SSE 优先

SSE(推荐)WebSocket
方向服务器→客户端单向双向
底层普通 HTTP独立协议,需升级握手
基础设施CDN/网关/代理天然兼容可能被中间件断长连接
断线重连浏览器原生自动重连 + Last-Event-ID 续传要自己实现
适用AI 回答推送,95% 的场景语音全双工、协同编辑

3. 流水线并行(降低 TTFT 的关键)

细节:① 引用来源先推,用户在等首字时已经在读文档标题,焦虑感大幅下降;② 生成和重排可重叠——rerank 完成前就可以让 LLM 基于 top 文档先开写(激进策略,适合超低延迟场景);③ SSE 事件设计成类型化(status/sources/delta/done/error),前端好编排。

4. 工程细节(拉开差距的地方)

  • 客户端断连必须中止生成:用户关页面了还继续生成就是白烧钱。监听连接断开事件,向上游 LLM 发 cancel。
  • 背压:客户端网络慢,发送缓冲区堆积时要暂停从 LLM 读取(暂停拉取即可,SSE 场景 rarely 需要)。
  • 断线重连:事件带序号,客户端带 Last-Event-ID 回来,服务端从 Redis 里补发缺失的事件。
  • 代理配置:Nginx 要关 buffering(proxy_buffering off),否则 SSE 会被攒着一起发,流式失效——这是最常见的上线翻车点。

5. 前端展示优化

  • 打字机效果 + 平滑滚动跟随;光标闪烁指示生成中。
  • Markdown 渐进渲染:token 流随时渲染,但要注意不完整的代码块/表格(常见做法:边收边渲染,未闭合的块等闭合后再格式化)。
  • 生成中途提供"停止"按钮 → 触发 cancel。
面试官追问
Q:生成到一半断线了怎么办?
服务端把已生成内容暂存 Redis(带会话 ID),客户端重连带 Last-Event-ID,补发缺失 delta;若 LLM 调用已断,展示半截答案 + "重新生成"按钮。
Q:多个用户同时流式,服务器连接数会不会爆?
SSE 是长连接,3000 并发就要 3000 连接——用异步框架(FastAPI + asyncio)单机可撑上万连接;更大规模靠网关层水平扩展 + 连接粘性(同一会话路由回同一节点,或状态外置 Redis 解耦)。
Q:Token 是一个个到吗?网络开销会不会大?
LLM 上游本来就是 chunk 到达;服务端可以攒 20~50ms 或若干 token 再 flush,平衡流畅度和包数量。
术语卡
TTFT:Time To First Token,首字时间。
SSE:Server-Sent Events,HTTP 长连接单向推送。
背压:下游消费慢时向上游反压减速。
Nginx buffering:代理攒响应,流式场景必须关闭。
