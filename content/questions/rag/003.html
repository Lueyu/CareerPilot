系统设计 · Q13

设计一个 Agent 知识库更新系统

⭐⭐⭐⭐ #知识库#增量更新#RAG
30秒电梯稿

"原则是增量优先、更新不停服:变更检测用文档哈希指纹比对(或 CMS webhook 推送),只处理变化部分;增量向量化写入双缓冲索引,建好后原子切换别名,查询全程走旧索引无感;冷热分离按检索日志的访问频率调度;每次更新生成版本快照,可一键回滚。最容易被忽略但必须主动讲的:更新后缓存要跟着失效(缓存 key 带版本号)。"

通俗类比

就是图书馆上新书:绝不能"闭馆三天重新整理所有书架"(全量重建),而是新到的书直接上架(增量);常被借的书放门口展示区(热数据,SSD/多副本),没人借的搬地下室(冷归档);每次大批上架前先拍照存档(版本快照),发现一批书分类错了,整批撤回重摆(回滚);读者正在看的书不从他手里抢走(查询无感切换)。

详细拆解

1. 变更检测(三档灵敏度)

  • 推送式:CMS/网盘 webhook 实时通知——最快,首选。
  • 轮询比对:定时拉文件列表,比内容哈希(MD5)(不能只比 mtime,有人只是重新保存了一下)。
  • 删除检测:源里消失的文档要从索引下架——最容易被忘记的 bug 来源。

2. 增量处理管道

3. 双缓冲(蓝绿)切换

  • 增量写入影子 collection,build 完成 + 抽检质量后,alias 原子切换(毫秒级,查询无缝)。
  • 旧索引保留 3~7 天只读:出问题把别名切回去 = 秒级回滚;长期审计需求留每日快照。
  • 大重构(换了 chunk 策略/ embedding 模型)才走全量重建,安排在深夜低峰。

4. 冷热分离

  • 统计检索日志:近 30 天被命中的 chunk = 热数据(多副本、常驻内存);未命中 = 冷数据(降副本、HDD/归档),查询时按需唤醒。
  • 典型比例:5% 的热文档承接 80% 的检索(员工手册、产品 FAQ 就是永远的热点)。

5. 版本管理与回滚

  • 版本 = 索引快照 + manifest(文档 ID 清单 + 源版本 + embedding 模型版本)。embedding 模型升级必须全量重建且新旧索引隔离(向量空间不可混)。
  • 支持"时间点视图":回答"这个答案基于哪一版制度生成的"(合规审计刚需)。

6. 缓存一致性:语义缓存/FAQ 预生成答案的 key 绑定知识库版本号,切换即旧缓存全部失效,防止"新政策出了还答旧的"。

7. 任务编排:增量任务走实时低优先队列;批量重建走深夜批处理;失败任务死信队列人工介入。

面试官追问
Q:文档改了一句话,要重嵌入整个文档吗?
不用。结构化 chunk 锚点定位到受影响的 chunk 重切重嵌入;但若改动影响语义连贯(章节标题变更),向上扩一层(整章)重切——用"最小受影响范围"策略平衡成本和正确性。
Q:更新很频繁(分钟级)怎么办?
小增量实时入主索引(向量库支持 upsert);双缓冲只用于大批量;配合"延迟合并"——高频小写先攒批再合并,减少索引碎片。
Q:怎么发现"该更新没更新"?
对账任务:定期全量比源和索引的文档哈希清单;差异告警——把"索引和源不一致"当成 P1 故障对待。
术语卡
双缓冲/蓝绿:新旧两套并行,原子切换。
Manifest:索引内容清单,用于对账。
Chunk 锚点:按文档结构定位切块,变更可局部化。
Upsert:存在则更新不存在则插入。
