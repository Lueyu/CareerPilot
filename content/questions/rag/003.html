系统设计 · Q13

设计一个 Agent 知识库更新系统

⭐⭐⭐⭐ #知识库#增量更新#RAG
先说人话:这题其实是把你天天干的活换了件马甲:源端文档天天变,下游那份可查询的「语义副本」(向量索引)怎么跟着变、还不能停服。面试官用它筛掉只会「定时全量重建」的人——那等于只会用停机窗口干活;答出增量检测、无感切换、可回滚,才证明你有在线系统的工程感。
30秒电梯稿

"原则是增量优先、更新不停服:变更检测用文档哈希指纹比对(或 CMS webhook 推送),只处理变化部分;增量向量化写入双缓冲索引,建好后原子切换别名,查询全程走旧索引无感;冷热分离按检索日志的访问频率调度;每次更新生成版本快照,可一键回滚;最后用定期对账兜住一切漏网之鱼。最容易被忽略但必须主动讲的:更新后缓存要跟着失效(缓存 key 带版本号)——否则新政策上线,Agent 还在流畅自信地背旧政策。"

通俗类比

整道题翻译成你的母语:一套「带服务连续性要求的增量同步 + 可回滚发布」系统。源文档=生产数据,向量索引=下游只读副本。变更检测=备份软件扫增量时算内容指纹(只认哈希,不认 mtime);增量向量化=数据去重后只传变化块——没动的块一个字节都不重算;双缓冲索引+别名切换=主备两个卷,新卷在后台 build 好,再原子地切一次挂载点:正在跑的查询在旧卷上做完,新查询落新卷——就是一次不停机的容灾切换;版本快照+manifest=快照链+备份 catalog,manifest 这份清单告诉你"这一版索引里装了什么",对账、审计、回滚全查它;冷热分离=存储分层(SSD→HDD→归档),按访问频率决定放置。

哪里像:只处理变化、新旧并存留观察期、改坏了秒级回滚、靠一致性对账兜底——四个职业习惯原封不动搬过来就能用。哪里不像:①备份副本只要求"留着能恢复",这份副本要求"秒级可查",所以冷数据不能像取归档介质那样提工单,必须按需自动唤醒;②向量索引不是逐字节副本,是"语义表示"——去重的块之间互不影响,RAG 的 chunk 之间有语义传染,改一句话可能牵连整章的连贯性;③备份窗口可以约在深夜,RAG 查询是 7×24,任何切换必须用户无感。想通这三条差异,下面每个设计决策都是顺理成章的。

详细拆解

先给全景:这个系统就是备份领域的四个老朋友组队

子系统要解决的问题备份系统里的对应物
变更检测文档变了,第一时间知道且不误报增量扫描:内容指纹比对 / CBT
增量管道只处理变化部分,成本与变更量成正比分块 + 去重,只传变化块
双缓冲索引新索引上线,查询一毫秒都不停克隆卷 + 原子切换挂载点
版本与回滚改坏了能退回上一版,能审计到任意时点快照链 + 备份 catalog

1. 变更检测(三档灵敏度)

  • 推送式:CMS/网盘 webhook 实时通知——最快,首选。相当于源端主动做变更块推送,下游不用反复扫。但要清楚:推送消息会丢(网络抖、重试逻辑有洞),所以推送只能当"加速器",不能当唯一真相——第 7 条的对账作业是它的安全网。
  • 轮询比对:定时拉文件列表,比内容哈希(MD5 等),不能只比 mtime——有人只是重新保存了一下,内容没变,比 mtime 会白白触发全文档重嵌入;反过来,某些复制管道会保留源的 mtime,内容变了时间戳却没动,比 mtime 又会漏。指纹比对本身极便宜:算个哈希,比"解析+切块+调 embedding 接口"便宜几个数量级,所以永远先比指纹再谈处理。
  • 删除检测:源里消失的文档要从索引下架——最容易被忘记的 bug 来源。类比备份里的孤儿数据:源目录早删了,备份作业从不感知,多年后恢复出一堆已下线文件。在 RAG 里后果更糟:已废止的政策文档还在被检索、被写进答案,这是合规事故,不是性能问题。
对账清单比对(比哈希指纹,不比 mtime):
  源端 manifest              索引端 manifest             判定
  doc_001 hash=a1b2…        doc_001 hash=a1b2…        一致 → 跳过,一分钱不花
  doc_002 hash=c3d4…        doc_002 hash=e5f6…        指纹不同 → 重新处理(mtime 相同也不行)
  doc_003 hash=9e8f…        (缺失)                    源有索引无 → 漏更新,告警+自动补数
  (缺失)                    doc_004 hash=77aa…        源无索引有 → 该删没删,下架+告警

2. 增量处理管道

  • 解析:PDF/HTML/表格各配解析器,产出统一中间格式——像备份前先给异构应用装代理,把不同数据源规范成同一种"可备份格式"。
  • chunk 对齐(锚点·重切变化区):切块必须按文档结构锚点(章节标题、编号)定位。这里有个和去重一模一样的坑:如果用固定长度滑窗切块,文档开头插入一句话,后面所有块边界集体错位,增量直接退化成全量;结构锚点相当于内容定义分块,给每块一个稳定的"内容地址",改动只波及局部。这一步是整个增量方案成立的地基。
  • 增量向量化(只算变化 chunk):对受影响 chunk 调 embedding 接口,成本严格与变更量成正比——改 1% 的文档只付 1% 的嵌入成本,而不是 100%。
  • 影子索引:带版本、时间、来源元数据写入新 collection,主索引一个字节不动——在克隆卷上做重构,主卷继续服务。

3. 双缓冲(蓝绿)切换

  • 增量写入影子 collection,build 完成 + 抽检质量后,alias 原子切换(毫秒级,查询无缝)。alias 就是一个软链/挂载点名:查询端只认别名不认物理 collection,切换=改一次指针。进行中的查询在旧索引上跑完,新查询落新索引,不存在"停服瞬间"。
  • 旧索引保留 3~7 天只读:出问题把别名切回去 = 秒级回滚;长期审计需求留每日快照。观察期就是容灾切换后"旧机房再顶几天电"的冷静期——切换最忌讳的旧资源秒删。
  • 大重构(换了 chunk 策略 / embedding 模型)才走全量重建,安排在深夜低峰。注意:双缓冲是给大批量用的;单文档小改用后述 upsert 直写即可,别小题大做。
一次大批量更新的时间线:
T0  索引 v37 正常服务 ←──── 所有查询打在这(全程不停)
T1  影子索引 v38 开始 build(后台进行,不影响线上)
T2  build 完成 → 抽检:抽 chunk 验嵌入质量、抽 query 验检索效果
T3  alias: kb → v38 原子切换(改一次指针,毫秒级)
      进行中的查询在 v37 上做完,新查询落 v38 → 用户无感
T4  v37 转只读,保留 3~7 天(观察期)
T5  若 v38 质量翻车 → alias 切回 v37 = 秒级回滚
T6  观察期过 → v37 归档/删除(有审计需求则留快照)

4. 冷热分离

  • 统计检索日志:近 30 天被命中的 chunk = 热数据(多副本、常驻内存);未命中 = 冷数据(降副本、HDD/归档),查询时按需唤醒。统计来源从存储系统的"IO 热度"换成"检索日志命中",其余思路与分层存储完全同构。
  • 典型比例:5% 的热文档承接 80% 的检索(员工手册、产品 FAQ 就是永远的热点)。
层级判定放置副本检索表现
热(~5%)近 30 天命中过内存 / NVMe3 副本全速
温90 天内命中过SSD / HDD2 副本略慢
冷(~95%)长期未命中对象存储 / 归档介质1 副本或纠删码按需唤醒,百毫秒级

和备份介质分层唯一的实质差异:冷 chunk 一旦被检索到必须自动唤醒并快速返回,不能像取归档磁带那样提工单等人工。所以常见做法是冷层仍保留向量本身(向量很小,贵的是原文和常驻内存索引),或对冷层做定期预热。

5. 版本管理与回滚

  • 版本 = 索引快照 + manifest(文档 ID 清单 + 源版本 + embedding 模型版本 + chunk 策略版本)。manifest 之于索引,如同备份 catalog 之于备份集:回滚时不用翻数据本身,查清单就知道这一版装了什么、对应源的哪个版本。embedding 模型升级必须全量重建且新旧索引隔离(向量空间不可混)——像备份格式升级:新旧格式不能拼在同一卷里,要么全转要么别动;技术原因:余弦相似度只在同一向量空间内才有意义。
  • 支持"时间点视图":回答"这个答案基于哪一版制度生成的"(合规审计刚需)。这正是 时间点恢复(PITR) 的查询语义:答案落库时带上知识库版本号,审计时按版本号还原"当时那一版"的索引视图。

6. 缓存一致性

  • 语义缓存 / FAQ 预生成答案的 key 绑定知识库版本号,切换即旧缓存全部失效,防止"新政策出了还答旧的"。类比:源端变更后 CDN/元数据缓存必须主动失效,否则用户看到旧页面;这里更危险——旧答案是静默错误,一段流畅自信的过期答案,没有任何报错。
  • 工程注意:版本切换会让缓存命中率短期跳水(瞬间全 miss),对热点 FAQ 提前预热,避免切换后出现延迟尖刺。

7. 任务编排(和对账兜底)

  • 增量任务走实时低优先队列;批量重建走深夜批处理;失败任务进死信队列人工介入。和备份作业调度同构:增量日志类作业实时跑,全备挑周末低峰,失败作业挂起等人工处理。
  • 对账兜底:webhook 会丢消息、轮询会漏文件、删除逻辑会有 bug——所以每日/每周一次全量对账(第 1 条的哈希清单比对),差异告警并自动补数。这层是所有检测机制共用的保险丝:检测手段可以又快又省,但"一致性"永远由独立的对账作业最终背书。
面试官追问
Q:文档改了一句话,要重嵌入整个文档吗?
人话:不用整篇重来,但"改一句"的实际影响范围要先定位再决定——改一句话就重嵌全文档,等于一次增量都没省的伪增量。类比:这是数据去重的块边界问题:固定窗口切割时开头插入一个字符,后面所有块边界集体错位,去重直接失效;所以要用"稳定边界"——这里就是结构锚点。技术:结构化 chunk 锚点(章节标题、编号)定位受影响的 chunk,只重切重嵌入这些块;若改动影响语义连贯(章节标题变了、前后指代断了),向上扩一层按整章重切。"最小受影响范围"策略就是靠锚点才可控的——若用无锚点的固定滑窗,一次插入会让边界漂移,增量退化成近似全量。
Q:更新很频繁(分钟级)怎么办?
人话:小步快走,大动作才兴师动众——不是所有更新都配得上蓝绿切换。类比:和备份策略分级一个道理:日志/增量备份分钟级实时跑,全量备份才挑周末;每次分钟级小改都做双缓冲,等于天天做全备,运维上不成立。技术:小增量(单文档)实时 upsert 进主索引,向量库原生支持,双缓冲影子索引只留给大批量导入和策略变更;高频小写配合"延迟合并"——先攒批再合并,减少索引碎片(和 LSM 的 compaction 一个思路);upsert 并发冲突用版本号做乐观锁,避免乱序到达的旧版本覆盖新数据。
Q:怎么发现"该更新没更新"?
人话:任何检测机制都会漏,而且漏得无声无息,所以必须有独立的对账作业兜底。类比:就是备份系统的数据校验/一致性巡检:备份作业全绿不等于数据真的可恢复,得定期比对抽查;这里同样,把"索引和源不一致"当 P1 故障对待。技术:定期(如每日)全量比对源端与索引端的文档哈希清单,差异即告警并自动触发补数;webhook 丢消息、更新任务挂死、删除逻辑漏分支,全都能被对账兜住。定级 P1 的理由:RAG 答错是静默故障——用户拿到一段流畅自信的过期答案,没有任何报错,不主动对账永远发现不了。
Q:为什么 embedding 模型升级必须全量重建、新旧索引不能混?
人话:新旧模型算出的向量不在同一个"坐标系"里,混用后相似度全是噪音,而且错得不报警。类比:像备份介质换了新格式,新带子和旧带子不能拼在同一卷里恢复——格式不兼容就是全有或全无,不存在"一半新一半旧"。技术:向量相似度成立的前提是所有向量由同一模型映射到同一空间;换模型后新旧向量之间的余弦距离失去意义,检索结果错乱且难以察觉。正确做法:全量重嵌入→建新索引→灰度发布切流量对比质量→确认后旧索引下线;manifest 必须记录模型版本,检索按版本路由到对应索引,保证任一时刻查询只落在一个"纯版本"上。
术语卡
双缓冲/蓝绿:新旧两套索引并存,别名原子切换,查询无感——和主备卷切换同一个思路。
Manifest:这一版索引"装了什么"的清单(文档 ID+源版本+模型版本),像备份 catalog,对账、审计、回滚全查它。
Chunk 锚点:按文档结构定位切块,给每块一个稳定"内容地址",改动只影响局部——增量成立的地基。
Upsert:存在则更新、不存在则插入,向量库增量写入的原生姿势,适合小改动直写主索引。
时间点视图:回答"这份答案基于哪一版知识生成"——PITR 思想在 RAG 里的合规审计版。
死信队列:屡次失败的更新任务最终落脚点,等人工介入——防"更新丢了没人知道"。
