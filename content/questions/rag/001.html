设计一个支持日均 100 万查询的企业级 RAG 系统

30秒电梯稿

"我会分五步:第一,先算容量账——日均 100 万、峰值 3000 QPS,按峰值而不是均值设计;第二,分层架构——网关、查询理解、检索、重排、生成五层;第三,检索侧用混合检索 + HNSW 索引 + 语义缓存,把延迟压到 200ms;第四,生成侧用模型分级 + 流式输出控制成本和体验;第五,多可用区部署 + 降级预案保 99.9%,网关统一做 token 成本监控。"

通俗类比

把它想象成一个超大型图书馆 + 快速应答团队:前台(网关)先看你要的书是不是别人刚问过(缓存,直接把现成答案给你);没问过,图书管理员去书架上找相关资料(检索),可能同时在电脑目录和书架上各找一批再合并(混合检索);找回来的资料先按相关度排个序(重排),把最相关的交给写手(LLM)组织成答案。100 万次/天平均下来每秒才 12 个人,但早高峰可能瞬间挤进 3000 人——所以要按高峰备人手,并且让常见问题根本不进馆(缓存挡掉)。

详细拆解

第一步:容量估算(面试第一句先算账,立刻和 80% 的候选人拉开差距)

  • 100 万次/天 ÷ 86400 秒 ≈ 平均 12 QPS;峰值 3000 QPS,峰值是均值的 250 倍(企业内部使用高度集中在工作时间)。
  • 按 3000 QPS 设计:检索 200ms/次 → 需要 600 并发的检索能力 → 向量库分片 + 副本水平扩展。
  • 成本账:平均每次请求消耗 2~3K token,100 万次/天 = 20~30 亿 token/天。这个量级如果全走 GPT-4 级 API 会远超 10 万/月 —— 所以必须靠缓存 + 模型分级 + 私有化/国产模型把大头砍掉。主动把这笔账算给面试官听,是这道题最大的加分点。

第三步:检索层优化(P99 目标 200ms)

  • 语义缓存:把问题的 embedding 和答案一起缓存,新问题来了先算相似度,超过 0.95 直接返回。企业知识问答重复率极高(规章制度、报销流程天天有人问),命中率 30%~60% 很常见,这是整个系统的第一省钱开关。
  • 索引:HNSW(查询快、吃内存)+ 向量量化(PQ/SQ 压缩内存 4~8 倍)。
  • 混合检索:向量管语义("怎么报销"),BM25 管精确关键词("发票号 TB-2024"),RRF 融合。
  • 控制 topk:召回 50 条 → 精排后只留 5 条进生成,LLM 的上下文越短越快越便宜。

第四步:生成层优化

  • 模型分级:网关先用小模型判断问题难度,简单题走便宜模型(成本差 10~50 倍),难题才上旗舰模型。
  • 流式输出:用户感知的是"首字时间"(TTFT),不是总时长。首字 300ms 出来,后面慢慢吐,体验就"快"了。
  • Prompt 精简:系统提示词砍掉废话、历史对话做摘要,token 就是钱。
  • 预生成 FAQ:统计 Top 1000 高频问题,离线生成答案缓存,在线直接命中。

第五步:可用性 99.9% 与监控

  • 99.9% = 全年停机不超过 8.76 小时 → 多可用区部署、检索/生成服务无状态可扩容。
  • 降级预案:向量库挂了 → 降级 BM25 检索;LLM 挂了 → 直接返回 Top5 原文段落 + "生成服务恢复中"。
  • 监控:QPS、P50/P95/P99 延迟、错误率、缓存命中率、每请求 token 成本、答案引用率(答案是否真的来自文档)。
面试官追问
Q:语义缓存命中率你怎么估?
用历史日志做离线回放:把过去 N 天的问题聚类,统计"重复/高度相似问题占比"。企业内部场景一般 30% 起步;再配合 FAQ 预生成可到 50%+。
Q:缓存和知识库更新冲突怎么办(答案过期)?
缓存 key 里带知识库版本号,更新索引时旧版本缓存整体失效;TTL 兜底(如 24 小时)。
Q:怎么保证答案不是模型瞎编的?
强制引用来源:Prompt 要求每个结论标注文档来源,后处理校验"答案中的引用是否真实存在于检索结果里",并对无依据句子打标/过滤。
Q:10 万/月的成本预算你怎么分配?
先私有化部署 Embedding 和 Rerank 模型(GPU 固定成本),LLM 分级:70% 流量由缓存+小模型承接,旗舰模型只处理 10~20% 的复杂问题,再留 20% 余量应对峰值。
术语卡
P99:99% 的请求比这个值快。看长尾,不看平均。
HNSW:跳表思想的多层图索引,查得快、吃内存。
RRF:倒数排名融合,把多路检索结果合成一个榜单。
语义缓存:按"意思像不像"缓存答案,而非一字不差。
TTFT:首 token 时间,流式体验的核心指标。
多可用区(AZ):同地域多个机房,一个炸了另一个顶上。
