系统设计 · Q15

设计一个混合检索系统(向量 + BM25 + 图检索)

⭐⭐⭐⭐⭐ #混合检索#RAG#系统设计
先说人话:RAG 系统里「帮模型找资料」的环节,任何单一招数都有抓瞎的时候——按意思找的,碰到产品编号就糊;按字面找的,碰到换种说法就懵;按关系找的,建库又贵又难。这题让你设计一个三路互补的「找资料流水线」,把三招拼成没有死角的组合。面试官爱问它,是因为一题就能同时考你「三种检索的原理 + 系统级权衡 + 知不知道什么时候不该过度设计」。
30秒电梯稿

"三路并行检索:向量管语义改写、BM25 管精确关键词、图管多跳关系——每一路都有另外两路覆盖不了的失效场景。融合用 RRF(倒数排名融合),因为它不需要跨引擎归一化分数;融合后可选 cross-encoder 重排。性能上三路并行、各自索引调优、图查询限制跳数;进阶做 query 自适应路由,按查询类型动态调三路权重。"

通俗类比

先讲 BM25(用备份系统的索引想):备份系统里有块索引元数据——「块指纹 → 属于哪些文件」。恢复时拿指纹精确查表,一个字节都不用差。BM25 干的就是这个活:先靠倒排索引(「词 → 哪些文档含有它」的表)秒级锁定候选,再给候选打分排序。打分有两个朴素直觉:① 一个词在越多文档里出现,它越不值钱(「的」「了」到处都是,没区分度;「TB-2024-8867」全库独一份,一击命中)——这就是 TF-IDF 的思想;② 同一个词出现 10 次不比出现 3 次相关 3 倍多,收益递减,而且长文档要打折(不然长文档靠篇幅白捡分)。哪里像:都是「先查倒排表锁候选、再精确处理」,都快、都可解释。哪里不像:块指纹全局唯一、查到即答案;自然语言一词多义(「苹果」是水果还是公司),BM25 只看字面,不懂你想表达什么——这个缺口要靠向量路补。

再想象找一个人:向量检索是"按长相气质找"(描述性:"高高瘦瘦戴眼镜的程序猿")——换个说法也能找到,但容易找来一堆相似的;BM25 是"按身份证号找"(精确:"张伟,工号 8867")——一个字都不能差,但你说"那个写代码的张哥"它就懵了;图检索是"按人际关系网找"("他同组同事的 mentor")——多跳关系只有它能顺着链条查。三种合起来,才敢说"找得到"。哪里像:三路各管一种「找人线索」,谁也不是全能。哪里不像:找人三招结果天然都是同一个人,合并答案容易;三路检索返回的是不同文档、不同格式的分数,怎么融合才是本题真正的考点——这正是 RRF 登场的地方。

详细拆解

1. 为什么必须混合(先讲清每路的失效场景,本题的灵魂)

用人话说:三种找法各有「抓瞎时刻」,混合的动机不是「多多益善」,而是互相补位——A 抓瞎的查询恰好在 B 的强项里。

检索路强项失效场景(必须有实例)
向量同义改写("怎么退货"≈"退货政策")型号编号("TB-2024-8867")、低频专有名词被 embedding"糊掉";黑话缩写(内行黑话训练语料里没有)
BM25精确词匹配、编号、罕见词同义改写失效:搜"退款"找不到"我不想买了该怎么办";跨语言查不到
图多跳关系("A部门 leader 下属负责的项目文档")建图成本高;节点名对不上("老王"≠"王工");孤立文档无关系可走

2. 架构(顺着图走一遍:query 进来先预处理,然后三路同时出发——这是并行,不是串行;各自拿到 top-N 后交给 RRF 融合成 top20,再用 Cross-Encoder 精排到 top5,最后送进 LLM 生成):

3. RRF 融合(公式要能写出来)

人话版:三路各自交回一份「排名榜」(不交分数,只交名次),每个文档的 RRF 得分 = 它在各路榜单里「名次的倒数-ish」加起来——在越多的榜上、名次越靠前,总分越高。像三个评委各自给选手排名,谁综合名次好谁晋级,评委们完全不用商量「我的 10 分和你的 10 分是不是一个 10 分」。

score(d) = Σ每路检索 1 / (k + rank该路(d))    # k 常取 60
# 例:文档A 在向量路排第2、BM25路排第10
# score = 1/(60+2) + 1/(60+10) = 0.01613 + 0.01429 ≈ 0.0304
# 对比:只在单路排第1的文档 score = 1/(60+1) ≈ 0.0164 → 文档A 反超
  • 看懂这个例子就懂了 RRF 的价值观:「两边都说好」胜过「一边说最好」——文档A 两路都排进前列,总分 0.0304,反超只在一路拿第 1 的文档(0.0164)。这恰好是我们想要的稳健性:单路的偶然高分坑不到融合结果。
  • RRF 的妙处:只用排名不用分数——向量库给相似度 0.83 和 ES 给 BM25 分 12.6 根本不可比,加权融合需要痛苦的归一化,RRF 直接绕开(出处:Cormack et al., SIGIR 2009)。
  • 可扩展加权 RRF(重要的路 rank 减一个偏移),权重可配置。

4. 图检索构建

  • 离线管道:文档 → 实体抽取(LLM)→ 实体消歧("老王/王工/王明"合并)→ 关系抽取 → 知识图谱( Neo4j );文档和实体双向索引。类比:这一步像给全公司的资产建 CMDB——抽取=盘点资产、消歧=「开发二部那台备份存储」和「型号 BBU-05」合并成一条记录、关系抽取=录入资产间的依赖线;CMDB 建得好,「A 依赖 B、B 依赖 C」这类链式问题才有得查。
  • 在线:query 抽实体 → 图上 2 跳扩展 → 拉回关联文档。跳数限制 ≤2(性能+噪音控制)——跳数不限制,2 跳变 6 跳,拉回来的是整个公司。

5. 性能与平衡

  • 三路并行,整体延迟 = 最慢一路 → 设超时降级(图路 250ms 没回来就先融合另外两路,慢的结果到了再补)。
  • 召回率 vs 精度:topk 调大召回高但重排贵;重排只处理融合后 top20,成本可控。
  • 自适应路由(加分项):轻量分类器判断 query 类型——含编号/专有名词 → BM25 权重高;语义描述 → 向量权重高;含关系词("谁的/属于哪个部门") → 图路启用。避免每次都跑三路,省延迟省钱。

6. 评估:分路评估(每路的 Recall@k)+ 融合后整体评估;用标注好的 query-文档对测试集回归。

面试官追问
Q:为什么用 RRF 而不是把三路分数加权求和?
人话:三路的「分」根本不是一种东西,直接加总就像把人民币、美元、日元按面值相加——数值能加,意义全错。类比:不同监控系统的「健康分」不可直接平均,跨系统聚合要看排名/分位,不看原始分。技术:① 跨引擎分数量纲不可比,归一化脆弱(分布漂移就失效);② 分数对异常值敏感(一个引擎的满分压制其他路);RRF 只用排名,天然免疫这两点。缺点是丢失分数信息(第 1 名和第 2 名差距多大看不见了),补救:融合后用 cross-encoder 重排找回精度。
Q:图检索建图成本高,什么时候才值得上?
人话:只有当「顺藤摸瓜式」的问题是常客时才值得建这套藤蔓。类比:像要不要为一类偶发查询专门建一套资产依赖图谱——如果每天有人问「这台备份存储影响哪些业务」,建 CMDB 就值;一年问两次,临时人肉查更快。技术:有明确的多跳关系型查询需求且占比 > 10~15%(组织架构、产品 BOM、依赖关系),或需要可解释的关联推理时才上;否则向量+BM25 够用——主动说"不过度设计"很加分。
Q:三路延迟差很大,怎么不让慢的拖死整体?
人话:齐步走的队伍速度由最慢的人决定——要么给他设截止时间,要么干脆别让他进场。类比:多副本读策略里常见的「对冲请求」(hedged request):主请求稍慢就立刻向副本补发一个,谁先回用谁。技术:并行 + 超时截止(hedged request 思想);图路结果异步补发或只用于增强上下文;对延迟敏感场景干脆路由层就决定不用图。
Q:BM25 靠字面匹配,那分词和停用词是怎么回事?中文怎么办?
人话:BM25 第一步得把句子切成一个个词,切法直接决定索引建得对不对——切歪了,后面全歪。类比:像备份系统选块大小/指纹算法:切分方案定了,整套索引元数据就绑定了;中途换切法,索引全部重建。技术:① 中文没有空格,必须用分词器(jieba、ES 的 IK 等),专名、型号要加自定义词典,否则"TB-2024-8867"会被切碎,精确匹配直接失效;② 停用词("的/了/is/the")在几乎所有文档都出现、零区分度,建索引时直接丢掉,省空间也防误匹配;③ BM25 = TF 饱和(词频收益递增递减)+ IDF(罕见词更值钱)+ 文档长度归一化三件套,公式细节见 维基 Okapi BM25。工程上 ES/Lucene 默认就是 BM25 打分,开箱即用。
术语卡
BM25:基于词频+逆文档频率+长度归一化的经典关键词打分,精确匹配之王、语义理解之盲。
RRF:倒数排名融合,只看各路名次不看分数,k 常取 60。
Recall@k:前 k 条结果包含正确文档的比例。
Cross-Encoder:query 和文档拼一起打分的重排模型,准但慢。
实体消歧:合并指向同一实体的不同叫法("老王"="王工"="王明")。
Hedged request:对冲请求——主请求慢了就补发副本,先到先用。
