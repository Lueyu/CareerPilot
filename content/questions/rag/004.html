系统设计 · Q15

设计一个混合检索系统(向量 + BM25 + 图检索)

⭐⭐⭐⭐⭐ #混合检索#RAG#系统设计
30秒电梯稿

"三路并行检索:向量管语义改写、BM25 管精确关键词、图管多跳关系——每一路都有另外两路覆盖不了的失效场景。融合用 RRF(倒数排名融合),因为它不需要跨引擎归一化分数;融合后可选 cross-encoder 重排。性能上三路并行、各自索引调优、图查询限制跳数;进阶做 query 自适应路由,按查询类型动态调三路权重。"

通俗类比

想象找一个人:向量检索是"按长相气质找"(描述性:"高高瘦瘦戴眼镜的程序猿")——换个说法也能找到,但容易找来一堆相似的;BM25 是"按身份证号找"(精确:"张伟,工号 8867")——一个字都不能差,但你说"那个写代码的张哥"它就懵了;图检索是"按人际关系网找"("他同组同事的 mentor")——多跳关系只有它能顺着链条查。三种合起来,才敢说"找得到"。

详细拆解

1. 为什么必须混合(先讲清每路的失效场景,本题的灵魂)

检索路强项失效场景(必须有实例)
向量同义改写("怎么退货"≈"退货政策")型号编号("TB-2024-8867")、低频专有名词被 embedding"糊掉";黑话缩写(内行黑话训练语料里没有)
BM25精确词匹配、编号、罕见词同义改写失效:搜"退款"找不到"我不想买了该怎么办";跨语言查不到
图多跳关系("A部门 leader 下属负责的项目文档")建图成本高;节点名对不上("老王"≠"王工");孤立文档无关系可走

2. 架构

3. RRF 融合(公式要能写出来)

score(d) = Σ每路检索 1 / (k + rank该路(d))    # k 常取 60
# 例:文档A 在向量路排第2、BM25路排第10
# score = 1/(60+2) + 1/(60+10) ≈ 0.0307  → 比只在单路排第1的都高
  • RRF 的妙处:只用排名不用分数——向量库给相似度 0.83 和 ES 给 BM25 分 12.6 根本不可比,加权融合需要痛苦的归一化,RRF 直接绕开。
  • 可扩展加权 RRF(重要的路 rank 减一个偏移),权重可配置。

4. 图检索构建

  • 离线管道:文档 → 实体抽取(LLM)→ 实体消歧("老王/王工/王明"合并)→ 关系抽取 → 知识图谱( Neo4j );文档和实体双向索引。
  • 在线:query 抽实体 → 图上 2 跳扩展 → 拉回关联文档。跳数限制 ≤2(性能+噪音控制)。

5. 性能与平衡

  • 三路并行,整体延迟 = 最慢一路 → 设超时降级(图路 250ms 没回来就先融合另外两路,慢的结果到了再补)。
  • 召回率 vs 精度:topk 调大召回高但重排贵;重排只处理融合后 top20,成本可控。
  • 自适应路由(加分项):轻量分类器判断 query 类型——含编号/专有名词 → BM25 权重高;语义描述 → 向量权重高;含关系词("谁的/属于哪个部门") → 图路启用。避免每次都跑三路,省延迟省钱。

6. 评估:分路评估(每路的 Recall@k)+ 融合后整体评估;用标注好的 query-文档对测试集回归。

面试官追问
Q:为什么用 RRF 而不是把三路分数加权求和?
① 跨引擎分数量纲不可比,归一化脆弱(分布漂移就失效);② 分数对异常值敏感(一个引擎的满分压制其他路);RRF 只用排名,天然免疫这两点。缺点是丢失分数信息,补救:融合后用 cross-encoder 重排找回精度。
Q:图检索建图成本高,什么时候才值得上?
有明确的多跳关系型查询需求且占比 > 10~15%(组织架构、产品 BOM、依赖关系),或需要可解释的关联推理时才上;否则向量+BM25 够用——主动说"不过度设计"很加分。
Q:三路延迟差很大,怎么不让慢的拖死整体?
并行 + 超时截止(hedged request 思想);图路结果异步补发或只用于增强上下文;对延迟敏感场景干脆路由层就决定不用图。
术语卡
RRF:倒数排名融合,k 常取 60。
Recall@k:前 k 条结果包含正确文档的比例。
Cross-Encoder:query 和文档拼一起打分的重排模型,准但慢。
实体消歧:合并指向同一实体的不同叫法。
Hedged request:对冲请求,先到先用。
