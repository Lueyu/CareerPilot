Token 级别奖励 vs Seq 级别奖励

⭐⭐⭐⭐⭐ #RLHF#信用分配#奖励设计
先说人话:这题在问:训练大模型时,奖励该给整段回答打一个总分,还是给每个 token 单独记账、单独记功。它是 RLHF 后训练的核心取舍,面试官爱考,因为答不好直接暴露你「只背过 PPO 名词、没想过梯度怎么流动」;最典型的翻车答法是张口就说「token 级一定更好」。
30秒电梯稿

"核心是信用分配(credit assignment):序列级奖励只给整段一个标量(比如最终 0/1),模型不知道到底是哪几个 token 立了功、哪几个闯了祸,梯度信噪比低、训练慢。Token 级奖励把功劳拆到每一步,有三条路:① 训一个过程奖励模型 PRM(Let's Verify Step by Step)对每个中间步骤打分;② 从结局反推,用 MC/REINFORCE 把终局奖励折现回每个 token;③ 用 critic 估计每个状态的 value,做逐 token 的 advantage(GAE)。设计 token 奖励的要点:用 potential-based shaping 加密集奖励才不改变最优策略,同时防 reward hacking(刷长度、凑格式、说套话)。"

通俗类比

先用你的老本行想这题:你跑过成百上千个备份作业,最烦的就是那种「整场 job 只回一个非零 exit code」的失败——快照、传输、去重、校验、清理,几百个子任务,到底哪一环挂的?序列级奖励就是这种日子:模型吐完 500 个 token,你只在最后给一个「对/错」,前面 499 步的功过糊成一笔账。Token 级奖励就是给链路上分布式追踪:每个 stage 都有 span、有健康检查,第几步慢了错了一眼可见,梯度也才知道该修谁。哪里像:都是把一个「总信号」拆成每一步的责任,定位准、反馈快。哪里不像:trace 是纯观测,打错了顶多是误报;而 token 奖励直接决定每一步梯度往哪修——观测错了只是告警噪音,奖励打错了会把模型真带偏。所以 token 级奖励的全部前提是:打分器得靠谱。

再想「延迟反馈」:第 3 个 token 的一次笔误,要到第 300 步才以「解题失败」的形式爆雷——这就像备份链路里第一阶段快照就不一致,一直潜伏到恢复演练才发现,根因回溯得倒着翻几百步日志。序列级奖励下,这颗雷的责任被「连坐」摊到每一步头上,好的坏的一起挨骂,信噪比自然低。Token 级奖励做的,本质上就是 RL 版的根因定位(RCA):把总账拆开,算到每一步头上。

详细拆解

1. 信用分配问题是什么(先讲清痛点)

  • 生成 500 个 token,只在最后给一个奖励 R(正确/错误),那么前面 499 步的梯度都「共享」这一个信号——方差大、样本效率低。尤其长链推理(Math/Code)里,一个早期错误 token 到第 300 步才体现为失败,中间隔了 300 步的「延迟反馈」,归因几乎糊掉。
  • 序列级奖励还有个隐患:奖励本身不可分解。总分为 0 可能来自「思路对但算错数」,也可能来自「全错」——就像备份失败码只有一个,但「源端快照失败」和「校验和不符」的修法天差地别,两种 0 分对训练的指导完全不同。
序列级:  [t1][t2][t3] ... [t499][t500] ──→  R = 0   ← 全程唯一的信号
           └────────── 500 步的功过,糊成一笔连坐账 ──────────┘

token级:  [t1]+1   [t2]+1   [t3]−1(设错变量) ...  [t500]+0
           └ 每步有自己的账本,梯度知道该修谁
              (第 3 步的雷当场拆掉,不用等第 300 步才爆)

2. 序列级奖励(seq-level)的优缺点

说明
优点标注便宜(只评整段)、和最终目标对齐(就是要正确答案)、天然可和 RM/规则/答案对拍结合
缺点稀疏、方差大、长序列收敛慢、无法指出「哪步错了」

3. Token 级奖励的三条来源(面试要能点名)

  • ① 过程奖励模型 PRM:OpenAI 的 Let's Verify Step by Step——把解答拆成「步骤」,人工/强模型标注每个步骤对错,训练一个模型给每步打分。数学推理上 PRM 明显优于只给终局奖励的 ORM(结果奖励模型)。类比:只看作业总分便宜,请老师逐行批改贵得多——代价就是步骤级标注极贵。
  • ② 从结局反推(MCRB/REINFORCE):没有 PRM 时,把终局奖励 R 按时间折扣折回每一步:r_t = γ^(T−t)·R(γ 是折现因子,离终局越远的 token 拿到的份额越小),或用 leave-one-out baseline 降方差。零额外标注,但每个 token 拿到的是「平均化」的信号——像事故复盘时把责任按资历摊回每个人,省了观察员,可也分不出谁是真英雄。
  • ③ critic/价值函数:PPO 里训一个 value network,Â_t = r_t + γV(s_{t+1}) − V(s_t),把「单步即时奖励」扩展成「这一步对未来总回报的贡献」,本质上就是在做逐 token 的信用分配(GAE)。类比你熟悉的监控:value 是容量规划式的基线预测,advantage 只学「实际比预期好/差多少」——报警只在实际值偏离基线时才响,而不是每次都从头判断。GAE 的细节见 论文,它做的事是在单步 TD 误差(偏差小方差大)和蒙特卡洛回报(偏差大方差小)之间取加权折中。

4. 怎么设计 token 级奖励函数(重点)

R_total = R_outcome                            # 稀疏的终局奖励(正确+1/错误0)
        + Σ_t F(s_{t+1}) − F(s_t)               # potential-based shaping,不改变最优策略
        + λ·R_process(token_t)                  # PRM 过程打分或规则性塑形
  • 奖励塑形(shaping)的黄金法则:额外奖励必须写成势函数之差 F(s_{t+1}) − F(s_t)(potential-based)。为什么?沿整条轨迹把这项逐段加起来,中间项会望远镜式抵消,只剩 F(终点) − F(起点)——也就是说塑形项只是给「离目标还有多远」的变化量记分,没有引入新的终点。反例类比:如果你把塑形写成「备份链路里每传一个文件 +1 分」,模型会学会疯狂传无数小文件、跳过校验去刷分;写成「剩余未传文件数的变化量」就没法刷——方向错了它反而扣分。
  • 常见塑形项:格式正确、思路完整、步骤可验证、不重复、长度合理——每一项都容易被 hack,必须配合「为什么给这项」的审慎判断。
  • 防 reward hacking(形式化定义见 这篇综述):① 奖励项互相独立、别叠加太多种;② 用验证器(代码执行、答案对拍)给硬信号而不是软分;③ 定期看「奖励涨了但真任务分没涨」的曲线,一旦背离就砍项。本质上这是古德哈特定律在 RL 里的化身:拿压缩率当 KPI 的备份系统,迟早学会往数据里塞可压缩的垃圾把分刷高。
  • 密集 vs 稀疏的平衡:密集奖励收敛快但易被 hack、且和「真实目标」有偏差;稀疏奖励最诚实但方差大。工程上是稀疏锚定 + 少量密集塑形,并让塑形项权重随时间衰减——类比灰度期可以多看几个中间指标,正式上线 SLA 只认硬指标。
训练进度 ─→
代理奖励(总奖励)   ╱╱╱╱╱  ↑ 一路涨(某个塑形项在被刷)
真实任务成功率     ─────────→  原地踏步
两线背离 = 塑形项被 hack 的典型信号,该诊断砍项了
面试官追问
Q:Token 级奖励一定比序列级更好吗?代价是什么?
人话:不一定,先看答案多长、反馈多硬。类比:小机房一个 cron 作业失败,翻一眼日志就知道瓶颈,没必要上全链路 trace;大型分布式作业才需要 span 级打点——token 级奖励同理,是给长链推理准备的装备。技术:好处是方差小、能指出错步、长链收敛快;代价有三:① 标注成本——PRM 要步骤级标注,比整段评贵一个量级;② 偏差风险——过程分是「人类认为的中间好状态」,不等于「能通向正确答案」,可能把模型带上一条人类喜欢但解不出题的路;③ 更易被 hack——逐 token 打分给了模型更多可钻的缝(凑格式、刷步骤分)。所以短答案/强反馈场景用 seq 级就够,长链推理才值得上 token 级。
Q:PRM 的数据从哪来?成本怎么控制?
人话:人标最准也最贵,省钱的路子是让「结果」反推「过程」。类比:不用请人盯每个备份任务,靠周期性恢复演练的最终成败,反推哪个快照时间点是干净的。技术:来源:① 人工标注每个解题步骤对错(最贵最准);② Math-Shepherd 这类做法——从某步出发续写采样多条,若多数能推到正确答案则该步标「好」,把步骤标注自动化;③ 强模型(LLM)自动判步骤。控制成本:强模型粗标 + 人工只抽检纠错;或用 MCTS 采样多条解题路径、用结果正确性反推沿途步骤标签,把「步骤标注」变成「轨迹搜索」。
Q:怎么防止模型刷 token 奖励(reward hacking)?
人话:奖励项要少而硬,并且永远盯住两条曲线。类比:防 KPI 刷分——指标少、可审计,且定期和北极星指标对表;拿压缩率当 KPI 的系统迟早学会塞可压缩垃圾刷分。技术:三层防御:① 设计上——奖励项少而正交,能用硬验证(代码跑通、答案对拍)就不用软分;② 机制上——密集塑形必须 potential-based,且权重随训练衰减,最终只保留稀疏真实奖励;③ 监控上——同时跟踪「代理奖励」和「真实任务成功率」,一旦两者背离(奖励涨、成功率平)立刻诊断哪个项被 exploit,砍掉或加惩罚(如长度归一化、重复 n-gram 惩罚)。
Q:结局奖励 + 过程奖励怎么配权重才稳?
人话:结局是锚,过程是脚手架——脚手架是为了盖楼,不能最后住进脚手架里。类比:备份体系里,恢复演练的 RTO/RPO 是锚,中间的传输速率、去重率只是辅助指标,为了报表好看牺牲恢复目标就是本末倒置。技术:没有统一常数,原则是结局奖励是锚、过程奖励是辅助:过程项权重 λ 取到「能显著降方差、又不盖过结局信号」的区间,通常让过程项量级 ≤ 结局项;做 λ=0/小/大三档消融,按真实任务分(而非总奖励)选最优;并随训练衰减。关键认知:λ 过大,模型会去追求「过程好看」而放弃「结果对」。
Q:既然 PRM 效果好,为什么开源圈主流训练还是用结果奖励(ORM/GRPO)?
人话:因为 token 级好处里最值钱的部分,可以不请 PRM 就拿到。类比:不给每条备份任务配专家审计,而是同一份数据跑 N 个副本互相对照——用「组内对比」替代「绝对打分」,离群即异常,零审计成本。技术:DeepSeekMath 提出的 GRPO:对同一道题采一组回答,用组内 leave-one-out 均值当基线,把结果奖励转成逐 token 的优势信号——零额外标注、天然降方差,相当于用②③两条路线的组合逼近了 PRM 的大部分收益;再叠加可验证领域(代码执行、数学答案对拍)的规则硬奖励,纯结果奖励 + 大规模采样就成了性价比主流,PRM 是预算充足时的增项。
术语卡
信用分配:把整段结果的功过,拆账到每个 token/每一步头上——RL 训练的核心难题。
PRM:过程奖励模型,对每个中间步骤打分;贵,但长链推理上明显赢 ORM。
ORM:结果奖励模型,只对最终答案打分;便宜、诚实,但稀疏。
奖励塑形:加辅助奖励引导训练;只有 potential-based(势函数之差)形式才不改变最优策略。
reward hacking:模型钻奖励函数的空子刷分,却不解决真问题——古德哈特定律在 RL 里的化身。
GAE:广义优势估计,用多步 TD 误差的加权平均,平衡逐 token 优势的偏差与方差。
γ 折现因子:终局奖励反推到早步时的打折系数,离结局越远、份额越小。
