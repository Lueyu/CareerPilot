Token 级别奖励 vs Seq 级别奖励

⭐⭐⭐⭐⭐ #RLHF#信用分配#奖励设计
30秒电梯稿

"核心是信用分配(credit assignment):序列级奖励只给整段一个标量(比如最终 0/1),模型不知道到底是哪几个 token 立了功、哪几个闯了祸,梯度信噪比低、训练慢。Token 级奖励把功劳拆到每一步,有三条路:① 训一个过程奖励模型 PRM(Let's Verify Step by Step)对每个中间步骤打分;② 从结局反推,用 MC/REINFORCE 把终局奖励折现回每个 token;③ 用 critic 估计每个状态的 value 做逐 token 的 advantage。设计 token 奖励的要点:用 potential-based shaping 加密集奖励不改变最优策略,同时防 reward hacking(长度、重复、套话)。"

通俗类比

把训练模型想成带一支足球队:序列级奖励是"只告诉球队最终比分"——赢了大家一人一碗饭,但具体是谁那脚传球立功、谁漏防丢球,谁都不知道,练一百场也难有针对性提升。Token 级奖励是教练给每个动作实时打分:"这脚直塞 +1、这脚浪射 −1",队员才知道该练什么、改什么。代价是教练(PRM)得请得起、还得靠谱,否则乱打分反而把队伍带偏。

详细拆解

1. 信用分配问题是什么(先讲清痛点)

  • 生成 500 个 token,只在最后给一个奖励 R(正确/错误),那么前面 499 步的梯度都"共享"这一个信号——方差大、样本效率低,尤其长链推理(Math/Code)里,一个早期错误 token 到第 300 步才体现为失败,中间隔了 300 步的"延迟反馈"。
  • 序列级奖励还有个隐患:奖励本身不可分解。总分为 0 可能来自"思路对但算错数",也可能是"全错",两者对训练的指导完全不同。

2. 序列级奖励(seq-level)的优缺点

说明
优点标注便宜(只评整段)、和最终目标对齐(就是要正确答案)、天然可和 RM/规则/答案对拍结合
缺点稀疏、方差大、长序列收敛慢、无法指出"哪步错了"

3. Token 级奖励的三条来源(面试要能点名)

  • ① 过程奖励模型 PRM:OpenAI 的 Let's Verify Step by Step——把解答拆成"步骤",人工/强模型标注每个步骤对错,训练一个模型给每步打分。数学推理上 PRM 明显优于只给终局奖励的 ORM(结果奖励模型)。代价是步骤级标注极贵。
  • ② 从结局反推(MCRB/REINFORCE):没有 PRM 时,把终局奖励 R 按时间折扣折回每一步:r_t = γ^(T−t)·R,或用 leave-one-out baseline 降方差。零额外标注,但每个 token 拿到的是"平均化"的信号。
  • ③ critic/价值函数:PPO 里训一个 value network,Â_t = r_t + γV(s_{t+1}) − V(s_t),把"单步即时奖励"扩展成"这一步对未来总回报的贡献",本质上就是在做逐 token 的信用分配(GAE)。

4. 怎么设计 token 级奖励函数(重点)

R_total = R_outcome                            # 稀疏的终局奖励(正确+1/错误0)
        + Σ_t F(s_{t+1}) − F(s_t)               # potential-based shaping,不改变最优策略
        + λ·R_process(token_t)                  # PRM 过程打分或规则性塑形
  • 奖励塑形(shaping)的黄金法则:额外奖励必须写成势函数之差 F(s_{t+1}) − F(s_t)(potential-based),否则你以为是"帮模型",其实是偷偷改了最优策略,会让模型钻塑形项的空子而不去解原题。
  • 常见塑形项:格式正确、思路完整、步骤可验证、不重复、长度合理——每一项都容易被 hack,必须配合"为什么给这项"的审慎判断。
  • 防 reward hacking:① 奖励项互相独立、别叠加太多种;② 用验证器(代码执行、答案对拍)给硬信号而不是软分;③ 定期看"奖励涨了但真任务分没涨"的曲线,一旦背离就砍项。
  • 密集 vs 稀疏的平衡:密集奖励收敛快但易被 hack、且和"真实目标"有偏差;稀疏奖励最诚实但方差大。工程上是稀疏锚定 + 少量密集塑形,并让塑形项权重随时间衰减。
面试官追问
Q:Token 级奖励一定比序列级更好吗?代价是什么?
不一定。好处是方差小、能指出错步、长链推理收敛快;代价有三:① 标注成本——PRM 要步骤级标注,贵一个量级;② 偏差风险——过程分是"人类认为的中间好状态",不等于"能通向正确答案",可能误导模型走一条人类喜欢但解不出题的路;③ 更易被 hack——逐 token 打分给了模型更多可钻的缝(凑格式、刷步骤分)。所以短答案/强反馈场景用 seq 级就够,长链推理才值得上 token 级。
Q:PRM 的数据从哪来?成本怎么控制?
来源:① 人工标注每个解题步骤对错(最贵最准);② 用能否推导到正确答案自动标步骤——从某步出发若最终答案对,则该步及之前标"好"(过程监督的自动化近似,Math-Shepherd 这类做法);③ 强模型(LLM)自动判步骤。控制成本:先让强模型粗标、人工只抽检纠错;或用 MCTS 采样多条路径、用结果正确性反推步骤标签,把"步骤标注"变成"轨迹搜索"。
Q:怎么防止模型刷 token 奖励(reward hacking)?
三层防御:① 设计上——奖励项少而正交,能用硬验证(代码跑通、答案对拍)的不用软分;② 机制上——密集塑形必须 potential-based,且权重随训练衰减,最终只保留稀疏真实奖励;③ 监控上——同时跟踪"代理奖励"和"真实任务成功率",一旦两者背离(奖励涨、成功率平)立刻诊断是哪个项被 exploit,砍掉或加惩罚(如长度归一化、重复 n-gram 惩罚)。
Q:结局奖励 + 过程奖励怎么配权重才稳?
没有统一常数,原则是结局奖励是锚、过程奖励是辅助。过程项权重 λ 取到"能显著降低方差、又不至于盖过结局信号"的经验区间,通常让过程项量级 ≤ 结局项量级;并做消融:λ=0 / 小 / 大 各跑一组,选真实任务分最高而非"总奖励最高"的那组。关键认知:λ 过大模型会追求"过程好看"而忽略"结果对"。
术语卡
信用分配:把整体结果归因到每一步/每个 token 的贡献。
PRM:过程奖励模型,对中间步骤而非整段打分。
ORM:结果奖励模型,只对最终答案打分。
奖励塑形:加辅助奖励引导训练,potential-based 才能不改最优策略。
reward hacking:模型钻奖励函数空子、刷分但不解决真问题。
GAE:广义优势估计,平衡逐 token 优势的偏差与方差。
