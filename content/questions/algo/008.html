Agent核心 · Q52

agent调用工具不正确怎么办，采用sft或者强化学习怎么来解决？

⭐⭐⭐ #错误修正#微调策略 字节（真题）
30秒电梯稿

"先定位错误类型再选方案。工具调用错误通常分四类：选错工具、参数错/漏、该调不调 / 不该调乱调、格式错。短平快先用工程侧（改 schema 描述、few-shot、校验重试、负样本提示）兜住；根治靠训练：SFT 用『用户话术 → 正确工具调用』的高质量数据（蒸馏 + 负样本）直接教模型对齐，见效快、成本低，适合错误模式固定、有数据的场景；强化学习（RL） 适合有可验证奖励的场景——用 GRPO/PPO 把『调用是否正确、参数是否对、步骤是否冗余』做成奖励，让模型在可执行环境里试错优化，适合复杂多步、规则能判对错的场景。我的路线：先 SFT 打底，再用 RL 在可验证任务上精调，两类数据都要带负样本防『工具上瘾』。"

通俗类比

像教新员工用工具：SFT 是"师傅带着做示范题"——把标准答案（正确调用）一道道演示给他看，他照着学，上手快，但只能学会题里见过的；RL 是"让他在模拟环境里自己练，做对了给奖励"——他试着拧螺丝，拧对加分、拧错扣分，自己摸索出窍门，能应对没见过的活，但前提是得有一个"对错判断器"（奖励）。修工具调用错误，就是先示范（SFT）打基础，再让他带着奖励试错（RL）精进，而且两者都得多练"什么时候别动工具"这道反例题。

详细拆解

1. 先诊断：错误分五类，各配一个监控指标

错误类型表现对应指标
选错工具该查订单却调了物流工具选择准确率
参数错/漏选对了但传参不对、缺必填参数 EM/F1
该调不调该查资料却凭记忆瞎编（幻觉）漏调用率
不该调乱调闲聊也去调工具（工具上瘾）负样本拒绝率
格式错工具调用 JSON 不合法格式通过率

2. 工程侧快速修正（不用训练，先止血）

  • 把工具 description 写清"何时该用/不该用"，参数加枚举和默认值。
  • few-shot 示范正确调用 + 负样本示范"拒绝调用"。
  • 校验 + 重试（错误反馈回喂）、降低 temperature、工具裁剪/合并。
  • 这些能解决 60~80% 的浅层错误，剩下的"顽固错误"再上训练。

3. SFT 方案（监督微调）

  • 数据来源三路：① 线上 bad case 自动捕获（最值钱）；② 强模型蒸馏生成（含负样本、多工具组合、多轮参数补全）；③ 程序化/模板构造覆盖边角。
  • 关键配比：负样本（不该调用）占 20~30%，否则模型得"工具上瘾症"；工具调用样本 : 通用对话样本 ≈ 7:3，防止微调后只会调工具、不会聊天（能力遗忘）。
  • 训练：LoRA 省资源，格式转目标模型的 chat template；数据版本化可复现。
  • 适用与局限：错误模式固定、数据可得时见效快、成本低；但 SFT 只是"模仿正确分布"，逐 token 最大似然没有显式优化"整条轨迹是否成功"，分布外情况仍会错。

4. RL 方案（强化学习）

  • 为什么上 RL：它优化的是轨迹级奖励（整次任务是否成功），能把"最终成败"回传到"中间某一步选错工具"，学到 SFT 教不出的多步组合与自我纠错策略。
  • 算法选型：GRPO（组内相对基线、省掉 critic、DeepSeek-R1 同款，训练更稳）；PPO（经典，clip 目标）；DPO / 在线 DPO（有偏好对时更简单）。工具调用领域关键是可验证奖励。
  • 奖励设计（核心中的核心）：① 格式奖励——JSON 合法、schema 匹配；② 结果奖励——工具真实执行结果是否符合预期 / 任务是否成功（程序化判定，最可靠）；③ 步骤惩罚——冗余调用扣分，防死循环/绕路；④ 负样本拒绝奖励——不该调时不调加分。
  • 坑：奖励 hacking（模型刷格式分、钻规则空子）、训练不稳定、需要可重放环境。对策：格式奖励权重低、结果奖励权重高、用程序化校验而非 LLM 打分做主奖励、定期人工抽检 reward 与真实质量的一致性。

5. SFT vs RL 对比与推荐路线

维度SFTRL
数据监督对（输入 → 正确调用）轨迹 + 奖励信号
优化目标逐 token 最大似然轨迹级奖励
适用错误模式固定、有标注数据可验证、多步、复杂的任务
成本低高（环境/算力/调参）
风险分布外泛化差奖励 hack、训练不稳定
  • 推荐路线：先 SFT 打底（快速对齐正确调用分布）→ 再用 GRPO 在可验证任务上精调（提升轨迹级成功率与抗分布外）→ 全程监控负样本拒绝率防工具上瘾，bad case 回流形成数据飞轮。
面试官追问
Q:SFT 就够了，为什么还要上 RL？
因为 SFT 只做"模仿"，不会"从失败中学习"。它逐 token 求最大似然，无法直接告诉模型"这一步选错工具会导致整条任务失败"；而工具调用是多步的，一步错全盘输，这类轨迹级的对错恰恰是 SFT 损失函数盲区。RL 用轨迹级奖励把"最终成败"回传，能学到多步组合和自我纠错。代价是环境和算力，所以只在有可验证奖励的场景上 RL，不是所有错误都要上。
Q:RL 的奖励函数怎么设计才不被 hack？
三条原则：① 奖励贴近真实成功且可验证——主奖励用程序化校验（工具真实执行结果、规则判对错），别用 LLM 打分当主奖励（容易被讨好）；② 权重分层——格式奖励设低、结果奖励设高，避免模型只刷"格式合法"忽略正确性；③ 加约束——步骤惩罚防绕路、负样本拒绝奖励防工具上瘾。最后定期人工抽检 reward 与真实质量的偏差，发现被钻空子就补规则。
Q:工具调用错误的训练数据从哪来？
三路：① 线上 bad case 自动捕获——选错工具/参数错/格式错的真实轨迹，回流标注，这是最值钱也最贴分布的数据；② 强模型蒸馏——用旗舰模型生成『用户话术 → 正确工具调用』样本，重点覆盖负样本、多工具组合、多轮参数补全；③ 程序化/模板构造——枚举边角（日期格式、空值、枚举边界）。三路合并、去重、过质检后进数据飞轮。
Q:微调后模型"只会调工具不会聊天"怎么办？
这是典型的能力遗忘（catastrophic forgetting）。对策：① 数据配比上混入通用对话样本（约 3 成）；② 负样本占 20~30%，专门教"什么时候别调工具"；③ 训练后测通用能力（对话质量、常识问答）做回归，掉了就回调配比或加通用数据。本质是"工具能力"和"通用能力"的平衡，不是一刀切只喂工具样本。
术语卡
SFT:监督微调，用"输入 → 正确输出"对齐模型。
LoRA:低秩适配，大幅降低微调显存/成本。
RLHF:基于人类/奖励反馈的强化学习。
GRPO:组内相对策略优化，省 critic 的 RL 算法。
DPO:直接偏好优化，用偏好对训练、免显式奖励模型。
工具上瘾:模型不分场合乱调工具，靠负样本治。
奖励 hacking:模型钻奖励规则空子，而非真正变好。
