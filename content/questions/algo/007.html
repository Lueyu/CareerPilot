Agent核心 · Q50

问数据的输入输出格式如何保证大模型输出稳定的json做了哪些工作？

⭐⭐⭐ #格式化输出#稳定性 字节（真题）
先说人话:这题在问:你让大模型吐 JSON,它十次里总有一两次崩——多个逗号、字段拼错、还爱用 markdown 代码块把 JSON 裹一层——你怎么把它管稳?Agent 的工具调用、数据抽取全指着这口 JSON,格式一崩整条链就断。面试官爱考它,是因为一开口就分两种人:只答"prompt 里写清楚点"的,暴露没上过生产;能按"约束→校验→修复→兜底"分层讲清的,才是真修过这条链路的。
30秒电梯稿

"我按『约束 → 校验 → 修复 → 兜底』分层做:① 约束层——优先用 JSON mode / function calling,再配 structured output / guided decoding(把 JSON Schema 编译成语法约束,解码时只允许采样合法 token,非法的从生成那一刻就进不来);② 提示层——给清晰的 schema 定义 + few-shot 示例 + 字段说明,明确"只输出 JSON、不要 markdown 代码块";③ 校验层——用 Pydantic / JSON Schema 做类型、枚举、必填校验,失败把报错喂回去重试一次;④ 修复层——json repair、正则提取代码块、截断补全,都不行就降级(换大模型或返回兜底结构)。输入侧同样先做 schema 规范化再喂模型。核心原则:能用解码约束就别赌 prompt,能程序化校验就别靠人看,能兜底就别让链路挂。效果:首次合法率从九成出头拉到接近 100%,兜底触发率压到千分位。"

通俗类比

把 LLM 输出 JSON 想成一次跨系统接口调用,这题你就秒懂了。纯 prompt 求 JSON,相当于口头约定让对方"按格式给我传个报文"——聪明人十次有九次写得对,但没人兜底,第十次就是生产事故。function calling / guided decoding 相当于把结构写成 Protocol Buffers 的 .proto 文件、由框架生成代码——不合法的结构在"写入之前"就编不出来,约束从"事后检查"前移到了"生成过程"里;再用 JSON Schema 定义这份契约,生成和校验共用一份。之后的 Pydantic 校验 + 重试,相当于接口入口的 schema 门禁 + 带着失败日志重跑作业;json repair 相当于 fsck 修文件系统的小坏块;最后的兜底就是容灾预案——主路径失败也要给调用方一个安全的默认返回,链路永不因格式死掉。

哪里像:都是防御纵深——约束先于检查、检查先于修复、修复之外还有预案,和你设计备份作业的"校验→重试→降级"策略是同一个思路。哪里不像(也是这题真正的考点):传统序列化里,合法性是类型系统/编译器免费送的,写错直接编译不过;而 LLM 是概率采样,"下一个 token 是什么"本身就是抽签——所以约束必须插进解码过程里才有效,只做事后校验永远在抓漏网之鱼。另一个不像:序列化是同一输入必得同一输出,LLM 还有 temperature 这种随机性旋钮,所以除了管结构,还得管采样参数。

别忘了题目里"输入"那半边:喂进去的结构越规整,吐回来的越规整——和备份铁律"垃圾进、垃圾出"一模一样,数据入池前先做格式规范化,永远是最便宜的一步。

详细拆解

1. 为什么 JSON 会不稳(先讲清根因)

LLM 是自回归概率采样:逐 token 生成,每一步都在"猜下一个词",它体内没有"JSON 语法必须合法"的内置约束。输出越长、嵌套越深、特殊字符越多,累积的出错概率越大;超长时还会被 max_tokens 硬截断,留下半截 JSON。而且训练语料里大量 JSON 是被 markdown 代码块包裹出现的,模型有样学样,于是常见错误就有了固定的几类:

错误类型典型样子该谁来救
语法错:尾逗号/坏引号{"a": 1,}L4 修复 / L3 带报错重试
结构错:字段拼错/漏必填/枚举越界"status": "sucess"L3 校验 + 喂回报错重试
包裹错:被 markdown 代码块裹住三个反引号开头的代码围栏包着 {...}L4 正则提取 / L2 提示禁止 / L1 根治
截断错:长度超限戛然而止{"summary": "该方法的主…L4 括号平衡补全 / L2 控制输出长度
夹带私货:JSON 前后混解释文字好的,以下是结果:{...}L4 提取 / L1 约束根治

所以"稳定 JSON"不是靠祈祷,而是靠分层约束 + 验证闭环——每一层只负责接住上一层漏掉的,和防御纵深是一个道理。

2. 输入格式也先做规范(题目问的是"输入输出")

  • 输入侧用统一的 JSON Schema / Pydantic 模型定义字段,把日期时区(统一 ISO8601)、枚举值(先收敛词表)、空值(明确写 null 还是空串)、数字精度(金额定点还是浮点)等先标准化再喂给模型——喂进去的结构越规整,模型越容易吐回规整的结构,这是最便宜的一层"稳定性"。
  • 工具参数、抽取字段都走同一份 schema,一处定义、多处复用——既用来写 prompt,也用来做事后校验,天然保证"要求它的"和"检查它的"是同一份契约,不会出现 prompt 说一套、校验查一套的错位。

3. 输出稳定四层方案(核心)

层手段作用
L1 约束JSON mode / function calling / guided decoding（outlines、guidance、SGLang、vLLM、lm-format-enforcer）把 JSON Schema 编译成有限状态自动机（FSM）/语法，每步只采样合法 token，语法 100% 合法
L2 提示清晰 schema + few-shot + 字段说明 + 禁止 markdown 代码块降低语义歧义，减少"内容错"而不只是"语法错"
L3 校验Pydantic / jsonschema 校验类型、必填、枚举；失败带错误信息重试抓住漏网之鱼并自动纠正
L4 修复json_repair、正则提取、括号平衡、截断补全对轻量语法错误止血
L5 兜底换更大模型重试 / 返回默认结构 + 错误标记保证链路永不因格式挂掉

逐层补几句关键细节:

  • L1 是天花板:guided decoding 的原理是把 schema 编译成有限状态自动机(FSM)或语法规则,在每一步解码时对候选 token 做掩码——"从这里写下去必然语法非法"的 token 直接划掉,模型只能从合法词里选。闭源 API 侧对应 JSON mode / function calling / structured outputs;自建推理侧用 outlines、guidance、SGLang 或 vLLM 的结构化输出。
  • L2 管的是"内容对不对":L1 只保语法,字段含义歧义还得靠 prompt——把 schema 原文贴进去、给 few-shot 示例、每个字段配一句话说明、明确"只输出 JSON,不要用代码块包裹"。
  • L3 用 Pydantic:类型、必填、枚举、正则格式一次全查;校验失败不要静默丢弃,要把具体错误字符串留下来——它是下一步重试的弹药。
  • L5 的原则:宁可返回一个带 error 标记的默认结构让上层自行决策,也不要让整个接口 500——这是"格式问题永不升级为可用性事故"的底线思维。
一个请求的「格式安检流水线」(每层只接上一层漏掉的):

  prompt: schema + few-shot + "只输出 JSON"        ← L2 提示(降低"想错"的概率)
        │
        ▼
  解码约束: JSON mode / guided decoding             ← L1 约束(非法 token 生成时就进不来)
        │
        ▼
  json_repair 轻修复 ──→ Pydantic/jsonschema 校验    ← L4 修复 + L3 校验
                             │
                         合法 → 返回调用方
        非法 │
             ▼
  把「原始输出 + 校验报错」喂回模型重试(通常 1 次修好)  ← L3 闭环
             │ 仍失败
             ▼
  换大模型重试 / 返回带 error 标记的兜底结构 + 告警    ← L5 兜底(链路永不因格式挂掉)

4. 校验 + 重试闭环(最关键的一环)

def stable_json(prompt, schema, max_retry=2):
    for i in range(max_retry + 1):
        raw = llm.chat(prompt, response_format={"type": "json_object"})  # L1 约束
        obj = parse_and_repair(raw)                                        # L4 修复
        err = validate(obj, schema)                                        # L3 校验
        if err is None:
            return obj
        prompt = append_feedback(prompt, raw, err)                         # 把报错喂回模型
    return fallback_structure()                                            # L5 兜底
  • 重试时把上一次的原始输出 + 具体校验错误一起喂回,让模型"看着错改",通常 1 次就能修掉绝大多数问题。为什么必须带上原始输出?因为对话式调用里模型并不"记得"自己上一轮吐了什么,不带原文它就是盲改——这和作业重跑要带上失败日志是同一个道理。
  • 重试要限次(一般 1~2 次足够),不要无限循环烧钱;每次失败都打点计数,超过阈值的 schema 要回头优化 L2——重试率本身就是 prompt 质量的体检报告。

5. 采样参数侧

  • 结构化输出场景把 temperature 调到 0 或接近 0,收紧 top_p,降低随机性——注意:低温度只降方差,不保证语法合法,它解决的是"同样的输入每次输出不一样",不是"输出一定对",所以仍要靠 L1/L3 兜底。

6. 流式场景:用增量解析/状态机边收边验证,未闭合的对象/数组等闭合后再消费,避免拿半截 JSON 去解析失败。这和流式输出是天生的别扭组合——很像边收增量备份流边校验:收到"还没闭合"的数据就先缓存等下一片,千万别拿半截内容去 parse;如果上了 L1 的 guided decoding,流式时每一步都是合法 token,这一层压力会小很多。

7. 上线后监控(把稳定性当运营指标管)

  • 分层打点:首次合法率、修复成功率、重试成功率、兜底触发率四个指标一起看——兜底率突然抬升,通常意味着模型版本回归或 schema 设计有问题。
  • 维护一组黄金集(query + 期望结构),schema 或 prompt 任何改动先跑回归再上线;线上按灰度放量,出问题秒回退。
面试官追问
Q:低温度 + JSON mode 能 100% 保证合法 JSON 吗？
人话:不能。两者叠加能把概率压得很低,但"概率的改善"不等于"承诺",SLA 意义上的保证必须靠校验闭环。类比:像把备份窗口固定到业务低谷,成功率大幅上升——但磁盘该坏还是坏;真正的承诺来自校验+重试+兜底这条闭环,而不是调度时段选得好。技术:temperature=0 是贪心解码,只保证"同样输入同样输出"的确定性,不保证语法;JSON mode 只保证语法合法,不管 schema 符合、不管超长截断、不管流式拼接的边界。所以生产永远是"约束+校验+重试"双闸——约束是第一道闸,校验是最后一道闸,谁都不能单独兜底。
Q:guided decoding 的原理是什么？有什么代价？
人话:把 schema 变成一台"只放行合法 token"的门禁机,模型每写一个字都只能从合法候选里挑,非法的在生成那一刻就被划掉。类比:像 protobuf——结构在"编译期"定死,而不是生成完再检查;也像接口入口的 schema 校验门禁,非法字段根本进不了门。技术:把 JSON Schema 编译成有限状态自动机(FSM)或语法规则,解码每步对 logits 做掩码。代价:① schema 编译与缓存有工程开销;② 闭源 API 能力参差、部分推理框架不支持;③ 屏蔽采样空间可能轻微影响内容质量(创造性任务慎用)和吞吐。开源实现可用 outlines、guidance、SGLang、vLLM。
Q:为什么还要重试，用正则/修复库一步到位不行吗？
人话:修复救"格式写错",救不了"内容写错"——缺个逗号能补,字段拼错、枚举越界这种语义错只能让模型自己改。类比:fsck 能修文件系统的小坏块,修不了"备份写到了错误的卷"——结构伤能补,语义错必须重写。技术:json_repair 覆盖尾逗号、坏引号、代码块包裹这类语法层;语义错(字段名不对、必填缺失、类型不符)要靠把"原始输出+具体校验报错"喂回模型重试,让它看着错改,通常一次修好绝大多数。分工:修复是止血、重试是纠正、校验是裁判,三者缺一不可。
Q:嵌套很深的复杂 JSON 怎么保证？
人话:一次别让模型盖一栋楼,分层施工、每层验收。类比:像不敢一刀切全量备份,拆成逐目录的增量作业,每步校验通过再走下一步——单步复杂度降下来,错了也容易定位。技术:首选 guided decoding 按 JSON Schema 直接约束,FSM 对嵌套结构最稳;其次把复杂结构拆成多步生成——先出骨架(各字段占位),再逐块填充、各自校验;schema 设计上主动扁平化,数组元素独立成子 schema,深层嵌套拆成两次调用,别指望单次生成一口吞下。
Q:JSON mode、function calling、guided decoding 这三个"约束"怎么选？
人话:三者都是把模型往格式上拴,但力度和入口不同:JSON mode 只保"是合法 JSON",不保字段对不对;function calling 保"参数符合工具的 schema",是 Agent 调工具最顺手的入口;guided decoding 把约束做到解码层,最强也最重。类比:像三档质量门禁:先过格式检查,再过 schema 校验,最后干脆上类型系统从源头保证。技术:走闭源 API:工具调用场景直接用 function calling,非工具的结构化抽取用 structured outputs(schema 级约束);自建/开源推理上 outlines、guidance、vLLM 的 guided decoding。无论选哪个,出口都再挂一道 Pydantic 校验做最后闸门。
术语卡
JSON mode:让模型只能产出合法 JSON 语法的开关——只保语法,不保字段符合要求。
function calling:让模型按工具的参数 schema 填参数,Agent 调用工具的标配入口。
JSON Schema:描述 JSON 长什么样的契约文件,类型、必填、枚举全写在这里,约束和校验共用一份。
guided decoding:把 schema 编译成状态机、解码时屏蔽非法 token 的技术,语法合法率 100% 的最强约束。
Pydantic:Python 数据校验库,模型类当 schema 用,类型/必填/枚举一行注解全查。
json repair:修尾逗号、坏引号这类语法小伤的库——修格式不修语义,救急不救错。
temperature:采样温度,越低越确定;调到 0 只降方差,不等于合法性保证。
