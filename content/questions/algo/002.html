Agent核心 · Q6

有微调过 Agent 能力吗？数据集如何收集？

⭐⭐⭐ #Agent#微调#数据集
先说人话:这题在问两件事:你有没有真把一个模型训成「会调工具的 Agent」,以及喂它的数据从哪来、怎么保证干净。面试官用它划开「调过 prompt」和「训过模型」的分界线——答不出负样本和质检流水线,一眼就暴露只停留在用 Agent、没造过 Agent。
30秒电梯稿

"有。先想清楚微调哪个能力——通常四块:工具选择、参数抽取、规划轨迹(ReAct 的 thought+action)、以及『不该调工具时忍住』(负样本)。数据四路来源:① 线上日志回流(good/bad case,最值钱)② 强模型蒸馏(GPT-4/Claude 造样本)③ 人工标注(高质量)④ 模板/合成(补边界)。每条样本过质检:Schema 校验 → 沙箱执行验证 → 一致性反推 → 打分去重。最后按 FC:通用对话 ≈ 7:3 混着训,防灾难性遗忘。数据量上质量比数量重要,单一工具 1~2K 条干净样本就能见效。"

通俗类比

整体像给新同事做带教 + 建错题本。你的 Agent 模型就是一个刚入职的值班工程师,基础素质不错(预训练底子),但没见过你这套业务。带教四件事:① 蒸馏=请老师傅(旗舰模型)按操作手册(工具 schema)示范一遍各种场景怎么处理,录下来当教材——快,能批量铺;② 日志回流=把他上线后处理对、处理错的工单都留档,对的重点强化、错的改完再练——最贴近实战;③ 人工标注=找资深工程师亲自过一遍刁钻案例——金标准但贵;④ 模板合成=像容灾演练脚本,专门构造边界场景(空值、格式错、多轮澄清)逼他练手。

微调 vs prompt,像『把手册内化』vs『每次照手册念』:prompt 工程是给值班工程师一本 runbook,他每次都翻着做——有效,但慢、占上下文、换个措辞可能就不会了;微调是把手册练进肌肉记忆,遇到告警直接反应。哪里像:都是往系统里注入领域知识。哪里不像:手册丢了能补一本,肌肉记忆练歪了要重训——所以喂进训练集的数据必须先过质检,坏样本的破坏是持久的。这正是质检流水线存在的理由。

负样本像容灾的『不该切就不切』:告警系统如果见警就主备切换,误切一次的代价可能比告警本身还大。Agent 也一样——如果训练集里全是「调工具」的样本,模型会对工具上瘾,用户闲聊一句「你好」它也去调天气接口。所以训练集里要混 20~30% 的负样本,专门教它「忍住」。灾难性遗忘则像只练新业务把日常运维全忘光——所以 7:3 混着通用对话样本一起练,老手艺不能丢。

详细拆解

1. 先定义目标能力

Agent 微调 ≠ 通用对话微调,目标更聚焦。拿「天气+机票」这种简单 Agent 举例,四块能力各自的考法和翻车样子:

能力考察什么翻车样子
工具选择该不该调、调哪个问天气却调了订机票的接口
参数抽取参数值、类型、格式对不对城市填成"今天"、日期格式不合法,接口直接报错
规划轨迹(ReAct 的 thought→action 序列)多步任务先想后做、顺序合理还没查天气就把机票订了,顺序颠倒白烧一轮调用
拒绝能力(负样本)不该调时忍住用户闲聊"你好",模型也去调工具——工具上瘾

这四块就是后面数据集的「考纲」:每条样本都要能归到其中一块,归不进去的样本要想清楚为什么收它。

2. 数据收集四路

四路来源各有分工,像四种数据源接同一套备份体系——生产直连最真实但要清洗,异地复制最快但可能带上主库的坏习惯:

  • 真实日志回流:线上用户请求 + 模型输出 + 结果反馈;好样本直接保留,bad case 人工修正后入池。最贴近真实分布、最值钱,但前期没量,要等业务跑起来。
  • 强模型蒸馏(知识蒸馏):用旗舰模型 + few-shot 造样本,速度快、可批量,是冷启动主力。注意它是「照着老师傅抄」,老师傅的习惯性偏见也会一起抄进来,所以要质检兜底。
  • 人工标注:质量最高,但贵且慢,好钢用在刀刃上——只标难例和校验集。
  • 模板/合成:程序化生成边界 case(日期格式、枚举、空值、多轮澄清),保证覆盖——像压测脚本专门打系统边角。
来源成本速度特点角色
真实日志回流低慢(要积累)分布最真实,含脏数据主力 + 飞轮燃料
强模型蒸馏中(调用费)快,可批量覆盖广,可能带强模型偏见冷启动主力
人工标注高最慢金标准难例 + 校验集
模板/合成低快边界覆盖强,自然度弱补漏洞

3. 样本要覆盖的维度

  • 单工具 / 多工具组合 / 并行调用 / 多轮参数澄清 / 规划轨迹 / 负样本(20~30%)。
  • 没有负样本 → 模型"工具上瘾",见谁都想调,这是最常见的翻车点——就像告警系统没配抑制规则,见警就切换,误动作比告警本身伤害大。
正样本:参数抽取对、调用有理有据
  user: "上海今天适合跑步吗"
  assistant: [tool_call] get_weather(city="上海")      ← 会选工具、参数对
  tool 返回: 晴, 28°C
  assistant: "今天上海 28°C 晴,很适合跑步"             ← 会用结果回答

负样本:不该动手时忍住
  user: "你都有什么功能呀?"
  assistant: "我可以查天气、查机票,想试试哪个?"
              ↑ 正确动作是回答,而不是调 get_weather

4. 质量控制(数据决定上限)

这套流水线像备份数据入库前的层层校验,坏数据宁可拦在门外——训练集里的坏样本不像缓存能失效,它会永久烙进模型参数:

  • ① Schema 校验:像写入前的字段类型检查——JSON Schema 验证 tool_call 的参数名、枚举值合法。成本最低,能拦掉最大一批「格式就不对」的废样本。
  • ② 沙箱执行:像备份完成后做恢复演练——样本里的 tool_call 真拿去沙箱调一遍,跑不通的说明模型当时在「编造调用」。
  • ③ 一致性反推:恢复出来的数据得对得上业务;这里反过来问——工具返回的结果真的能支撑最终回答吗?防止「调对了工具、答案却是瞎编的」。
  • ④ 打分去重:LLM 按规则打分 + 聚类去重,像数据入湖前的重删压缩——同质样本堆一万条,信息量还是那一条。
  • 人工抽检 5%~10%:金标准兜底,监控前面四关的漏检率。

5. 训练与防遗忘

  • 配比:工具调用样本 : 通用对话 ≈ 7:3,防止通用能力崩塌(灾难性遗忘)。类比:演练不能只跑新业务场景,日常作业也要照常跑,否则老技能生疏。
  • 方法:全参微调(数据多)或 LoRA(数据少、算力省;只训一小片低秩增量,改动小、遗忘也轻);小学习率、适度 epoch——「小火慢炖」,火大了老知识全糊掉。
  • 格式:转成目标模型的 chat template(不同模型 tool_call 标签写法不同,Qwen 和 Llama 的格式不通用,这步做错训练直接白做)。

6. 数据量与评估

  • 经验值:单一工具 1~2K 条即可见效;工具多、场景复杂 1~5 万;质量 > 数量——1000 条干净样本好过 1 万条带噪样本。
  • 评估指标:工具选择准确率、参数精确匹配率(EM/F1)、负样本拒绝率;留测试集不参与训练,防止「拿训练集考自己」。

最后把四路数据接成数据飞轮,冷启动只是点火,真实价值在循环:

上线版 Agent
   │  线上真实请求
   ▼
日志回流(good / bad case 分拣)──→ bad case 人工修正
   │                                 │
   ▼                                 │
质检入库(混通用对话 7:3)←──────────┘
   │
   ▼
再微调 ──→ 新版上线 ──→ (循环往复,效果越滚越厚)
面试官追问
Q:冷启动,没有任何真实用户数据怎么办?
人话:没有用户数据就先「借」——用强模型示范 + 程序造题,拼出第一批几百条干净样本把方向跑通。类比:像新机房上线前先跑合成压测和演练脚本,不等真实流量来了才发现问题。技术:先定义工具 schema → 用强模型批量生成 (query → tool_call → result → answer) 样本 + 程序化模板补边界;小规模微调上线 → 用线上日志回流滚起来,进入"数据飞轮"。冷启动阶段数据质量比数量关键,几百条干净样本就能验证方向。
Q:微调后模型通用能力下降(灾难性遗忘)怎么防?
人话:只喂 Agent 样本,模型会把普通对话也当成任务来「演」,说话变得很怪——所以老本事要混着练。类比:像值班团队专项集训了三个月容灾切换,结果日常巡检反倒手生了;正确做法是集训和日常排班穿插进行。技术:① 混合训练:FC/Agent 样本里混入通用对话(如 7:3 或 8:2);② LoRA 等参数高效方法改动小、遗忘轻;③ 学习率调小、不过度 epoch;④ 训练后同时测"工具任务指标"和"通用基准(MMLU/闲聊)"双护栏,遗忘超阈值就回退。
Q:怎么评估这次 Agent 微调是有效的?
人话:离线考卷、线上实战、长期监控三层都要看,只报离线分数是自欺。类比:和评估一套备份方案一个逻辑——不能只看备份成功率(离线),还要定期做恢复演练和真实故障下的 RTO 表现(线上),并持续统计失败案例。技术:三层:① 离线——留出测试集测工具选择准确率、参数 EM/F1、负样本拒绝率;② 线上——AB 对比任务成功率、平均工具调用轮次、token 成本;③ 持续——监控 bad case 回流,建立回归集防退化。只报离线分数不看线上,是评估大忌。
Q:为什么不直接靠 prompt,一定要微调?
人话:能靠 prompt 解决就别微调,但有四种情况 prompt 拉不动,必须把知识「练进」模型。类比:prompt 是给新同事一本手册照着念,微调是把手册内化成肌肉记忆——手册太大(工具太多)、要求反应太快(高并发低延迟)时,翻手册就不够了。技术:prompt 零成本、可迭代,但四类场景必须微调:① 小模型自身 FC/规划能力弱,靠 prompt 拉不动;② 专有工具特别多且模型没见过,选错率高;③ 高并发低延迟要求用便宜小模型;④ 格式/风格要高度稳定。决策顺序:先 prompt 验证可行性 → 再用蒸馏数据微调降本增效。
Q:负样本怎么造?造多了会不会矫枉过正,模型永远不敢调工具了?
人话:会,负样本是把双刃剑——比例失控会让模型从「工具上瘾」变成「工具恐惧」,同样废掉。类比:像给告警系统配抑制规则,规则太松见警就切,太紧真故障了也不切——两头都是事故,所以要拿比例和指标反复校准。技术:造法:闲聊/寒暄类用真实日志筛,「工具不存在/信息不足应反问澄清」类用模板构造;配比控制在 20~30%,并单独监控两个方向的错误率——误调用率(该忍没忍)和漏调用率(该调没调),上线后哪个抬头就往哪个方向回调比例。
Q:蒸馏来的样本,会把强模型的错误也一起学进去吗?
人话:会,这是蒸馏的头号坑——强模型也会编造工具调用、抽错参数,抄作业连错题一起抄。类比:像从主库异地复制数据,主库里的脏数据会原样复制过来,所以复制之后必须有清洗和校验,不能裸入湖。技术:① 蒸馏样本必须过质检流水线,尤其沙箱执行这一关,专拦「编造的 tool_call」;② 用多个强模型交叉生成、分歧大的样本丢弃;③ 采样温度调低,减少生成时的随机发挥;④ 高价值场景(高频工具、核心业务)的样本最后过一遍人工,金标准兜底。
术语卡
SFT:有监督微调,用标注样本调整模型行为——把「该怎么做」直接练进参数。
知识蒸馏:强模型的输出当弱模型的训练数据,快但可能连错误一起抄,要过质检。
数据飞轮:线上 bad case 回流→再训练→效果提升的正循环,冷启动只是点火。
负样本:"不该调工具"的样本,防工具上瘾;配比 20~30%,过犹不及。
灾难性遗忘:微调后通用能力退化,靠混入通用数据、LoRA、小学习率来防。
LoRA:低秩适配,只训一小片增量参数,省算力且遗忘轻。
ReAct:Reason+Act 范式,Agent 边想边做,thought/action 序列就是规划能力的载体。
