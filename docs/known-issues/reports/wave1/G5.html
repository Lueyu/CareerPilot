让后台模型密钥与仓库令牌以绑定上下文的密文落库

完成 Wave1 G5，让全局及工作区的后台 LLM、GitHub、GitCode 凭据不再以明文存入数据库，并让缺钥、损坏或被搬运的密文在联网前明确拒绝。交付还包含可重试的显式迁移和面向初学者的机制说明。

先理解你会遇到什么

下面是假设事故，不是用户亲历。你在本地应用里填了一个模型 API key，设置页面显示的只有‘已配置’，GitHub token 也只显示末四位。某天你把数据库备份交给别人排查问题，对方直接打开 app_settings 的 JSONB，就能读到完整 token。页面遮罩只改变浏览器收到什么，并没有改变数据库里保存什么。任何能读数据库或旧备份的人，都可能拿这个凭据访问供应商。G5 的出发点就是修正这两个边界之间的落差。

再假设有人不能破解密文，却可以改数据库。他把工作区 11 的合法密文复制到工作区 22，或把强模型的 key 复制成普通模型 key。只验证‘这段密文确实由我们生成’还不够，因为合法数据也可能被放在错误的位置。本项把原来的设置行和字段路径一起放进认证密文，读取时必须同时对上身份。

这与 Agent 工程的联系是凭据、真实付费调用和仓库读取之间的确定性边界。模型负责生成内容，秘密能否读取、是否允许联网、迁移是否提交都由代码决定。工程产出证明了这些行为在合成夹具中的表现，不代表用户已经亲手实现或掌握，也不代表真实供应商、真实生产部署已经验收。

系统现在如何处理

接收显式设置请求模型沿用现有字段契约，LLM 先读取并验证旧值，再处理省略、空白保留或新凭据。改变 provider/base_url 时仍要提供对应的新 key。
打包字段与身份把 secret 和 context 一起序列化。context 是 [app_settings, 设置 key, 字段路径各部分]，llm:11 已把工作区身份包含在行 key 里。
Fernet 认证加密从部署进程环境取 CAREERPILOT_SECRETS_KEY，用 cryptography 的 Fernet 生成随机化密文；数据库外层只保存 $secret 版本与 ciphertext。
落库与 API 响应SQL 参数中的目标秘密已经是密文，API 只返回 api_key_set、active 或原有 token_hint，工作空间导出不包含 AppSetting。
准备外部调用全局解析器、项目 runtime、播客和仓库读取先 open_setting。只有版本、Fernet 认证及内部 context 都通过，才构造临时的供应商调用配置。
拒绝路径缺钥、错钥、篡改、未迁移明文、未知版本或错误 context 均终止本次读取。安全错误不带原 token 或底层异常，旧缓存不能授权继续联网。

先区分三个对象。明文秘密是供应商真正接受的 API key/token。主密钥是部署方保管的随机 Fernet 密钥。密文容器是数据库里的带版本 JSON。本项使用一个部署主密钥直接加密秘密，没有为每条记录生成数据加密密钥 DEK，也没有用密钥加密密钥 KEK 包装 DEK。因此这里的‘信封’仅指版本化密文容器，不应把它说成传统 DEK/KEK envelope encryption，更没有实现 KMS 或远程密钥包装。

secret_storage.py 是统一边界。seal_setting 识别 llm、github、gitcode 三个设置 family，以及它们的工作区后缀。它递归处理 api_key、以 _api_key 结尾的 strong/reasoning 变体、token/password/secret 等秘密字段，也覆盖嵌套 profile 与列表。非秘密字段保留原来的 JSON 形状。空字段不需要加密，非空明文只被显式写入或离线迁移接受。在线 open_setting 看到非空明文会拒绝，不会把旧格式当作永久兼容路径。

Fernet 的底层加密和认证使用成熟 cryptography 实现，本项没有自己拼接 AES、填充或 MAC。Fernet 不提供外置 AAD 接口，所以 context 放在其认证明文内部，和 secret 一起被加密及完整性保护。解密以后，代码比较 payload.context 与本次期望的行和字段。攻击者只改数据库外壳的字段名，不能让认证载荷中的原身份一起改变。外壳的未知版本也会拒绝，而不是猜测该用哪种解码方式。

密钥只从 os.environ 的 CAREERPILOT_SECRETS_KEY 读取，不进入 Settings 模型，不落 DB、版本库、API 或本次证据文件。每次密文操作重新取得环境值，因此不会因为旧 Fernet 对象仍在缓存中而绕过缺钥或错钥。部署必须把同一个密钥注入 API、scheduler 和 worker，独立保管恢复副本。更换环境值不能自动迁移旧密文；本项没有自动轮换工具。

实际调用方的改造和加密函数同样重要。get_llm_config 服务全局 AgentAdapter 调用，项目 runtime 与播客有各自的 workspace/global 设置选择，repository_credentials 服务项目分析、学习项目、职业资产和公开内容的仓库读取。GitHub 发布器与旧仓库 snapshot 又有独立入口，GitCode snapshot 原来只读环境 token。本次逐一接入验证边界，并去掉未使用的同步 publisher 环境回退工厂。显式传入的临时调用配置仍只在内存中使用，不伪称进程内存已经加密。

异步配置读取取消了 TTL 明文缓存作为来源。否则，即使数据库已被篡改或部署密钥丢失，缓存仍可能继续支撑十秒钟的付费请求。保留的 LLM 同步 active 提示仅包含 provider/api_key 是否存在两个布尔值，不能取代调用前的认证读取。GitHub 的旧缓存刷新函数保留兼容接口，但不存 token。一次已经取到凭据的在途请求不会因此被远程撤销，这与 H1 认证令牌撤销是不同问题。

旧数据迁移通过 migrate_secrets.py 显式执行。操作员提供目标 DSN 所在的环境变量名和 --apply，工具不会隐式选个人默认数据库。它先验证主密钥，再在一个事务中取得 app_settings 表 EXCLUSIVE 锁，按 key 顺序转换目标记录。前面行即使已经 flush，只要后面行存在坏版本或错钥，整笔事务都不提交。成功加密的字段再次执行时只验证并保留原字节，所以 changed_rows 可以为零。并行执行的两个迁移通过表锁串行收敛。

报告中的 secret-context 计算器由父代理提供和浏览器验收。它展示身份、密钥可用性和篡改为何导致拒绝，是清楚标注的概念 UI，不执行真实密码学、网络请求或环境读取，不能替代本项 PostgreSQL 与 Fernet 测试。

迁移命令的非零退出不能单独证明数据库没有提交。缺钥、错钥和损坏行在提交前被发现时，整笔事务回滚；如果提交已完成而响应或清理失败，需要查证数据库状态。幂等设计让操作者可以用同一密钥重跑：已转换内容会验证并原样保留，不再重复加密。

现在尝试在哪里读取

这是身份绑定的概念演示，只使用假数据，不执行加密、不读取环境变量、不访问数据库或模型。真实实现使用 Fernet 验证密文，再校验密文内部携带的表、行和字段身份；具体拒绝行为由后面的实际测试证明。

这种保护针对数据库副本泄露和密文搬运。持有主密钥的受信任进程仍能解密，因此主密钥要在数据库与备份之外单独保管。

为什么选择这个方案

复用现有 AppSetting JSONB 与接口契约，只增加一个明确的秘密读写模块和一个离线命令。没有为 G5 引入新的凭据表、外部密钥服务、F6 备份系统或 H1 鉴权框架。

采用显式调用边界，而不是让 ORM 自动解密所有 value。原始数据库值保持可检查，迁移不会误把已经解密的 ORM 属性当作原始存储；代价是每个现有读取入口都必须盘点并迁移。inventory.md 记录了当前发现的实际入口和环境来源。

Make Operations Idempotent 原则改变了迁移方式。没有把‘迁移到第几行’存在另一个进度文件，而是根据当前行是否已有合法容器决定变化，并用一个事务保证失败回到原状态。

Migrate Callers Then Delete Legacy APIs 原则改变了兼容策略。所有当前秘密读取方一起接入，新代码不保留在线明文读取后门，旧的同步 publisher 环境工厂被删除。Test Behavior, Not Implementation 和 Prove It Works 促使验证落在真实 SQL、实际 API、外部调用零次数和隔离 PostgreSQL 事务结果上。

仍要知道的边界

隔离库证明的是当前逻辑行值不含合成明文。迁移不能保证擦除 PostgreSQL 旧页、WAL、旧 dump 或历史快照中的秘密；操作员需要凭据轮换及介质策略，F6 另管备份归档加密。

主密钥只用部署进程环境，没有实现 OS keyring 接入、KMS、DEK/KEK 包装、自动轮换或自动恢复。丢钥后不能解密，需要显式清除覆盖再重新录入。

应用内存和已取得调用配置的在途请求不属于静态加密保证。同步 active 只作提示；调用仍重新认证。

strong/reasoning 的 JSON 凭据字段已纳入加密与校验，当前实际强模型路由仍来自原有部署 Settings。本项没有新增强模型 UI 或把既有未使用字段变成已支持的路由。

保留学习聊天既有 timeout/cancelled 分类失败，不改相邻 worker 超时行为。相关套件未声称全绿，后续观测改进单独验证。

未运行前端 typecheck/build，因为没有前端源码改动。概念演示另有浏览器检查，未计入密码学验证。

定制租户容器若使用 DB 凭据设置，需要操作员配置其主密钥注入。原生启动继承进程环境，根 Compose 已静态验证 API/worker 映射；未声称所有自定义编排都已部署。

字段加密不替代数据库权限，也不证明整行删除、数据库旧快照回滚或非秘密配置没有被改动。这里验证的是密文内容完整性与位置绑定，恢复和出站访问还需要各自的保护。

面试时可以怎样解释

可以解释一个可复现的工程案例：API 遮罩保护响应，不保护数据库；把成熟认证加密和凭据读取边界结合，才能让备份中的当前秘密成为密文。讲清保护范围比直接说‘系统安全了’更准确。

可以说明复制合法密文为何仍危险，以及为何内部认证 context 能约束工作区和字段。要明确本项是 Fernet 的认证载荷，不冒充 AES-GCM 的外置 AAD 或托管 KMS。

可以展示迁移的原子回滚、重复执行零变化、两个并行迁移收敛和读取失败零联网的测试证据。以上是代理完成的项目产出，不能代替用户本人作答、独立解释或真实生产演练。

检验自己是否理解

为什么 API 只显示末四位仍然需要静态加密？

遮罩发生在返回响应时，数据库中的原值并没有自动改变。读库或拿到 dump 的人绕过了 API，必须检查实际落库值。

为什么把 workspace_id 放在数据库旁边还不够？

攻击者可一起修改未认证的旁边字段。归属必须在受认证的载荷内部，并和本次期望的位置比较。

这里是否实现传统 envelope encryption？

没有。这里是版本化密文容器，一个部署 Fernet 主密钥直接保护秘密，没有每记录 DEK，也没有 KEK 包装。

迁移前几行已 flush，后面发现错钥怎么办？

flush 不是 commit。所有目标行在同一事务中，异常让前面的写入也回滚；修正前置后可用相同命令重试。

密钥缺失时为什么不能回到另一个环境 key？

无法确认保存的凭据是否可用不等于操作员授权换账号。自动回退可能换供应商身份、费用归属或仓库权限，所以必须先拒绝。

删除覆盖后恢复环境默认值，与解密失败回退有什么区别？

DELETE 是显式用户操作；解密失败没有表达授权改变凭据来源。两条路径必须分开。
