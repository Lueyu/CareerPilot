把进程存活与数据库就绪分开，数据库故障不再继续报告可接流量

让 CareerPilot 在数据库不可用时准确返回未就绪，同时保留能用于观察进程的存活入口。调用者可以区分进程没有响应、数据库故障和恢复隔离，减少把业务失败误判成整台 API 已经死掉的情况。

先理解你会遇到什么

设想用户正在提交练习，数据库连接突然断开。API 事件循环仍能处理 HTTP，旧 /healthz 因此继续返回成功。如果容器检查只访问这个地址，面板看起来正常，真正需要读写记录的操作却失败。本次把能回应请求和能访问必要依赖拆成两个明确的问题。

另一个场景是从备份恢复的数据库已经可以执行查询，但恢复核验、凭据或付费状态尚未完成。只做 SELECT 1 会把这样的实例错误放行。这里沿用 F6 恢复闸，探针只读当前状态，既不代替操作员核验，也不自动把隔离标成正常。

对于 Agent 工程，可靠性还包括依赖失败时给出可信信号。任务执行、模型调用和账本写入会跨多个组件，健康信号必须写清证明范围。这个改动提供一项可复查的工程证据，不能据此宣称用户已掌握分布式系统或整套 Agent 已达到高可用。

系统现在如何处理

访问存活入口/healthz → 既有入口处理函数 → 200；不获取数据库连接，不读取恢复表，也不进入 API 身份及限流账本。公开版仍检查配置的 Host。
访问就绪入口/readyz → 个人版或公开版路由 → 共享 readiness_response(service)，服务名由入口固定提供。
开启本次检查共享函数 → 1 秒协作式超时 → 新建本请求独占的 session → 等待连接池及数据库连接。
检查当前依赖同一 session → SELECT 1 → require_normal(session)；后者读取已有恢复控制行并核对安装来源、数据库身份和各项正常状态。
给出响应成功清理 session 后返回 200 和 ok=true；预期数据库、连接、超时或恢复拒绝返回 503 和 ok=false。两种响应均带服务名和 no-store。
基础设施消费个人、公开及租户 API 探针改用 /readyz；反代精确转发探针。worker 仍在 API 就绪后启动，不反过来成为 API 的推测性就绪条件。

核心形状只有一个共享异步函数和固定响应对象。服务名分别为 careerpilot-api 与 careerpilot-public，布尔值只描述这一次检查结果。既有 app.db 拥有 session 工厂，恢复控制表拥有准入状态，探针自己不增加缓存、后台任务或一套新的健康状态表。

每次调用都创建一个 session，并把它直接交给 require_normal。这样连接获取、试查询和恢复判断使用同一个数据库上下文。假如分别开两个连接，试查询成功后恢复检查还可能等待另一条连接，也更难说明超时覆盖了什么。这里的连接独占只限本次请求，不会锁住整个连接池。

超时从进入 session 上下文之前开始，覆盖连接池等待、建立连接、两次查询以及正常清理。它不是给两条查询各分配一秒，也不会使用上一次成功补偿本次超时。asyncio 通过取消协程结束等待，驱动清理可能短暂超过截止时间，所以不能把一秒宣传成操作系统级硬期限。外部取消会继续向上传播。

函数只转换已知依赖异常。SQLAlchemy 异常、asyncpg 数据库异常、操作系统连接异常、超时和 RecoveryBlocked 都产生同一份安全响应。程序错误继续暴露给既有服务错误处理，避免用一个捕获所有异常的分支把代码缺陷永久伪装为数据库不通。

响应不携带连接串、主机、用户名、SQL 或原始错误堆栈。探针没有新增异常日志，因此也不把连接失败详情写入公开响应或探针自己的日志。测试分别注入带合成秘密的驱动及 SQLAlchemy 错误，再检查响应形状与捕获日志。此结论只覆盖本次边界，不是对全项目日志脱敏的审计。

公开版仍使用既有 Host 和来源校验。容器从回环地址访问公开 API 时必须手动提供公开站点的 Host，不能因为是探针就绕过该校验。GET 不需要用户 token 或登录 cookie，错误 Host 仍然被拒绝。个人版原有 scorer_model 存活字段继续保留。

为什么选择这个方案

复用 SessionLocal 与 require_normal，避免另造数据库接入和恢复规则。Foundational Thinking 原则促使本次先确定请求独占 session 与固定响应对象，再写路由；Test Behavior, Not Implementation 原则促使测试通过真实入口断言状态码、正文和故障恢复，不把内部函数调用顺序当验收。

共享函数只承担探针边界，两个入口保留服务身份。这样个人版与公开版对数据库异常、超时和恢复隔离使用同一政策，修改时容易核对；不需要引入健康检查框架、可配置检查注册表或全局结果缓存。

连接预算一秒，公开容器 HTTP 客户端两秒，Docker 探针三秒，给返回和基础设施调用留出空间。个人与租户 Docker 探针仍保留原三秒超时，轮询周期和失败次数也没有借本次任务重新调参。

配置回归逐个检查真实消费方。候选预览只把 CareerPilot 的检查路径改成 readiness，保留 Squabble 配置；ops 服务仍可使用自己的轻量存活。worker 保持启动依赖，不引入互相等待的就绪环。

方案收益代价与决定
两个入口复制实现不新增共享导入，局部代码直接可见两套超时和恢复政策容易漂移，选择共享小函数
在 /healthz 加数据库查询原有容器配置不用迁移会改变轻量存活语义，数据库故障可能触发错误重启动作，因此保留旧入口并新增 /readyz
缓存最近成功或只做 SELECT 1少查恢复表，响应开销更低可能在故障或隔离后继续报告可接流量，与本项目标冲突
把所有 worker 和供应商纳入就绪看起来覆盖范围更广外部服务抖动会阻断普通读写，新 worker 启动也可能造成依赖环，留给独立诊断与 G3 告警

仍要知道的边界

200 只证明本次数据库连接、SELECT 1 和恢复闸成功；它不验证全部表、每条业务查询、worker 心跳、队列积压、模型供应商、费用余额或 SMTP。相关诊断保留在鉴权 ops 路径及独立监控任务。

Docker unhealthy 本身不会杀死并重启还在运行的进程。unless-stopped 面向容器退出后的重启，depends_on 主要处理启动顺序，两者都不保证运行中持续摘流。要自动停止送流量，部署者必须把 readiness 接到有此能力的反代或编排器。

操作员应先在授权实例查看 /healthz，再查 /readyz 的状态码与 JSON。公开版提供正确 Host。只有就绪失败时继续查看受保护诊断和数据库状态，不要为了让容器变绿而删除恢复控制行或绕过核验。数据库恢复后再次访问 /readyz，不能用过去的成功当当前结果。

新建公开实例在显式 F6 安装登记前返回 503 是预期行为。父代理预览会先观察未登记状态，再用既有离线入口登记这份全新自有测试库。本次没有自动 NORMAL、运行时释放 API 或恢复隔离降级。租户配置消费者也必须使用包含本次探针的对应镜像，配置测试没有验证旧固定标签镜像。

检验自己是否理解

数据库停机时为什么 /healthz 还能是 200？

它只回答进程能否处理轻量请求，故意不访问数据库。/readyz 负责报告必要依赖不可用。

SELECT 1 成功为什么仍会是 503？

恢复控制行可能缺失、来源不匹配或处于隔离。探针必须同时通过 require_normal，不能自动解除隔离。

为什么总超时要包住 session 获取，而不是只包 SQL？

连接池可能已经耗尽，建立连接也可能停滞。只限制 SQL 执行无法限制这些等待。

外部任务取消为什么不转换成 ok=false？

取消表示调用者要结束工作，应继续传播并释放资源。吞掉取消会干扰关停和请求生命周期。

为什么还需要检查网页探针？

网页服务器可能把未知路径返回为 index.html，状态也是 200。必须精确反代并核对 JSON，不能只看 HTTP 成功。

Docker unhealthy 会自动重启或摘除流量吗？

不会保证。重启策略主要针对进程退出，启动依赖也不是持续路由控制。部署者需配置消费 readiness 的组件。

这次哪些证据不能互相替代？

ASGI 与真实测试库证明源码行为；镜像、真实反代和容器实际探针证明构建产物。独立审核也不能用作者自查替代。
