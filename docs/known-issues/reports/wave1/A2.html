让题库问句找准主题，也走对处理流程

A2 的目标是让普通中文、英文和中英混合的列题请求保留真实主题，返回有来源、总数清楚的题库清单，同时保留用户要求的解释、比较或回答任务。本报告帮助初学者理解修复原因、代码机制和证据边界。

先理解你会遇到什么

假设你准备学习智能体规划。你已经把一道标题为“智能体规划”的合格题目放进题库，随后在学习对话中输入“题库里有哪些关于智能体规划的题”。你的要求是先看看有哪些真实题目。旧版本却能返回零题。这个场景已在独立 PostgreSQL 测试库复现，题目存在，错误发生在查询词里。系统把“智能体规划的”当作主题，而不是“智能体规划”。多出的一个“的”足以让这个样例的文字匹配失败。

你换成英文输入 What RAG interview questions are in my question bank?，遇到的是另一个问题。旧版本已经提取出 rag，却没有把这句话认作列题请求。接口返回 generating，并排入一个后台生成任务。你要的是确定的库存清单，系统却继续走原任务流程。可见，找什么内容和执行什么动作是两个独立决定。修好其中一个，另一个仍可能错。

先分清历史。PR37 已于 2026-11-26T09:18:34Z 合入 dev，合并提交为 7455ed1e12f5e3d27e4f48f68dc87e1f2966886b。父任务已核实它在本次基线的祖先链中，pr37-current.json 保存了合入状态。原清单里“尚未合入”的描述已经过时。本次保留 PR37 的有效修复，继续补齐仍能复现的句式缺口，不重新合并旧分支。

这项工作与 Agent 工程的关系，在于把用户要求准确转换成系统动作。数据库检索、模型生成、来源引用各有职责。对于查题库库存，程序可以直接给出已有题目；对于解释和比较，系统要保留相应任务。你学习这份报告时，应能说明每个判断由哪段代码负责、哪个测试证明。项目产出不能直接算作你亲手完成或已经掌握的经历。

系统现在如何处理

接收用户消息现有 API 确认会话、角色和动作是否允许清单直出，不能仅凭一个自然语言词就切换所有业务流程。
识别唯一主题子句_single_inventory_subject 查找限定中文或英文句式。只有一个匹配且后面仅剩结束标点或空白时，才返回匹配对象。
分别决定动作与主题is_library_inventory 判断是否只列题；library_terms 提取要查找的词。两者复用同一主题边界，各自保留原有额外条件。
读取有权限的题目library_sources 复用现有题库有效性与工作空间条件，再用主题词和技能条件匹配，计算总数并限制展示数量。
形成可复核的结果清单路径保存 items、total、language 和检索来源摘要，用已有语言模板回复，不让模型重新编写题目标题。
保留其他任务存在额外解释、比较、回答、推荐要求时，继续原任务流程。没有资料库引用的普通讲解回合不注入库内材料。

先看旧英文规则为什么失败。原来的 _LIST_QUESTIONS 能识别 list、show，以及 what 或 which 后面紧接可选 interview 和 questions 的形式。What RAG interview questions 在 What 与 questions 之间多了主题 RAG，因此没有命中原规则。library_terms 的拉丁词元处理已经能保留 rag，所以这个根因是意图判定，不能把它笼统说成检索词完全抽错。

中文原句的问题发生在另一个位置。旧处理先去掉题库指引词，再用中文二至六字片段抽取候选词。“智能体规划的”正好能成为一个六字片段，语法后缀也被带进检索。对于只有正确标题的测试题目，数据库按这个词找不到记录。最终清单为空，是词的边界错了，不是数据库里没有这道题。

修复先声明一个很小的数据结构。_single_inventory_subject 返回私有的 re.Match[str] | None。re.Match 保存正则表达式在原句中找到的内容，也保存内容起止位置。命名组 zh 或 en 给出主题文本，span 给出主题在原句的位置。None 表示这次没有可安全使用的唯一主题。系统没有新增持久化状态，也没有新增跨请求共享的可变对象。

中文句式限于“关于”或“围绕”包住主题，后接“的题”“的题目”“的面试题”或“的问题”。英文句式限于 What 或 Which 开头，主题之后是 questions are in my/the question bank/library，可带 interview。每个主题片段最多一百字符，并限制跨越若干标点。英文还排除了 can、should 之类开头，避免把 What can I learn... 当成库存询问。这些规则是可读的边界，不是完整语言理解能力。

辅助函数不仅要求找到匹配，还要求全文恰好只有一个该类子句，且匹配之后只剩空白或结束标点，之前只包含明确的列题引导词和空白。满足条件时，library_terms 使用主题子串，跳过针对这段主题的全局中文停用词替换。这样保留“智能体规划”，也保留“解释器设计”中的“解释”。其后的拉丁词元处理、中文二至六字切片、去重以及最多八个检索词仍按旧规则执行。长中文主题仍可能被切片，本次没有新增中文分词器。

没有唯一可用主题时，library_terms 继续原有处理，包括 PR37 已支持的“与、和、跟……相关”抽取和按长度从长到短替换中文停用词。先替换长词可避免长指引词被短词先拆开，残留片段。这个回退仍有旧逻辑的限制，但能保住本来应参与检索的全文内容。

is_library_inventory 复用匹配对象，却不把任何主题都当作列题意图。它仍要求出现题库范围标记、题目集合标记和列题触发条件。新的英文有界句式可以补足英文列题触发条件；中文的“关于……的题”本身不新增触发资格。所以“我想学习题库里关于智能体规划的题”仍不自动变成一份清单。API 还保留原有角色、动作及工作流前置条件。

检测附加任务时，函数只临时排除命名主题组对应的原文区间，原始消息不会被改写。主题前后的文字仍然参与 _ADDITIONAL_TASK 检查。因此“解释器设计”和 SQL explain plans 可以作为主题，前面的“请解释 RAG”仍会被识别为动作。对于“题库里有哪些关于智能体规划的题，并解释每道题”，句尾还有实质文本，辅助函数直接回退，附加任务仍可被检出。这里没有把整段匹配内容或整条消息一并忽略。

这个限制来自一次实际发现的中间回归。初版只取第一个主题，会把“列出题库里关于RAG的题，以及关于SQL的题”缩成 rag，丢掉 sql。最终版本对重复或带后续实质内容的句子回退全文处理。三个补充探针显示 rag 和 sql 都保留下来，三个实际数据库测试进一步检查结果或资料来源包含两者。英文多主题样例保留原来的生成路径，中文样例保留原来的清单路径。本次没有宣称新增通用多主题解析。

非作者审核又把主题顺序反过来测试。“列出题库里SQL的题，以及关于RAG的题”只有后半句命中新主题句式，初次冻结版本因此只保留 rag。审核用真实 API 和 PostgreSQL 证明，基线能返回 SQL、RAG 两题，新稿只返回 RAG。这次修正增加 _INVENTORY_PREFIX，只有明确引导词构成的前文才能忽略；SQL、其他主题和复杂前文会让程序回退全文。三条反向或中英混合数据库用例以及两条正常引导词用例补进测试，原有 30 条冻结语料不变。独立审核的失败回执保留，不能因为原先 123 项通过就跳过反例。

library_sources 的职责没有扩大。用户明确引用资料库时，它使用现有 bank_list_question_clause 限制可读范围和合格题目，再检查标题、主题、关键词、标签和技能条件。这里沿用文字包含匹配及既有条件组合，不计算向量相似度，也没有新增排序算法。没有资料库引用时，它返回空来源和空清单，普通讲解不会因此读取无关题目。

走清单路径时，数据库查询同时取到完整命中总数和受上限约束的 items。total 表示符合条件的总数，items 最多一百条。inventory_reply 根据零命中、全部展示或部分展示选择已有文案模板。API 将结果及来源写入消息并标为 completed，不排后台生成任务。零命中是一种正常结果，不会通过模型编造题目来填充。数据库错误处理继续由原调用链负责，这次没有新增吞错后伪装成功的逻辑。

回复语言和证据原文也要分开。现有 HTTP 语言协商可以显式控制库存说明文案，response_language 随调用传入并保存。没有显式语言时，库存语言沿用输入有中文字则中文、否则英文的旧规则。题目标题保持原始记录。测试断言的是响应语言字段、说明文案、标题和历史快照，不是把所有题目正确翻译成另一种语言。

如果你问为什么不直接换一个更强的检索器，要先定位错误发生在哪里。英文原句没有进入清单动作，换排序算法不会改变这个动作判定。中文原句带着错误的主题边界进入查询，提高后端检索能力也不能证明系统理解了原指令。本项先修复已复现的两个决定，再保留 A4 独立评估召回与排序的空间。

为什么选择这个方案

这次复用 study_chat_context.py 的词抽取、清单意图、资料读取和模板回复，公开的 library_terms、is_library_inventory、LibraryRead 不变。新的信息只需要主题文本与原文区间，私有匹配对象已经足够。没有必要为了两个已定位的句式新增一层模型调用或修改存储结构。

保留边界比让规则看起来适用所有句子更有价值。只有唯一完整主题才走新抽取，复杂后缀继续原处理。这会放弃一部分进一步清理复杂句的机会，却避免悄悄丢掉第二个主题或真实动作。三个多主题保护用例记录了这个取舍的具体原因。

动作字样要结合位置解释。把“解释”加入全局允许列表会漏掉真实讲解请求，把“解释”一律当动作又会伤害“解释器设计”。现有匹配对象能提供位置，因此只排除主题子串，保留主题外检查。这是本次最小可核对的区分方式。

修复没有引入运行依赖或新的模型费用。没有新增共享可变状态、事务或并发调度，安全和额度规则仍由原层负责。这些事实不能替代整体并发或计费验收；本项只引用实际覆盖到的定向回归。

本报告按 Explain the Number 原则区分正例主题分母、全部意图分母和数据库测试节点，不把不同范围相加。按 Prove It Works 原则核对已有原始日志、源码摘要及报告最终 JSON；真实产品预览与非作者审核没有由本报告作者执行，留给父任务补入。

方案收益代价与决定
继续增加全局停用词改动起初较短，也不需要新依赖。容易删掉合法主题文字，仍不能统一意图与主题边界。本项未采用。
共享有界主题句式和原文区间意图与词抽取复用一份边界，行为可从源码和少量反例解释。只覆盖限定句式，复杂输入回退并保留旧限制。本项采用。
接入 jieba 或其他中文分词器可进一步研究较长中文主题的切词。分词不能独自决定是否列题，还会引入词典、依赖和新评测范围。本项未接入。
让模型分类或改写查询可以研究更丰富的表达方式。需要延迟、费用、失败与语义保持评测，不能假设模型改写必然正确。本项未调用真实模型。
升级 HybridRAG 或排序检索适合另行研究词义相近与排序质量问题。不能直接修复这次清单意图误判；需要 A4 的召回与 MRR 等独立评测。本项未实施，也未宣称完成 A4。
