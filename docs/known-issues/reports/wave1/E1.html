聊天生成增加工作区准入和进程内执行上限

让跨会话聊天需求先经过有上限的准入判断，避免一个工作区通过大量会话同时启动模型。容量已满时及时返回可重试的拒绝，不留下未被接受的消息，也不破坏原来的流式回复、幂等提交、中断、重试和恢复行为。

先理解你会遇到什么

原来的聊天接口保护单个会话。如果当前会话还有回复正在生成，再发一条消息会收到 409。但用户可以新建许多会话，每个会话都通过检查，随后各自启动一个 FastAPI BackgroundTasks 任务。项目分析 worker 的串行规则管不到这些 API 后台任务。因此，单会话保护不能限制一个工作区实际占用的生成资源。

假设客户端重复打开几十个会话并持续发送请求，每轮又允许等待较长时间，系统会同时连接许多模型流。即使每轮内部保留有限的备用调用次数，所有轮次叠加后也会增加调用量和故障压力。本项限制的是这一批并发生成的规模。它没有引入新的费用账本，也不能保证长时间反复重试的总费用上限。

Agent 工程的难点包含外部调用前的确定性约束。模型输出质量和并发安全是不同的问题。这里的名额、锁、超时和恢复都由代码与数据库决定，LLM 不参与资源分配。这是可以用并发测试说明的工程能力，但本报告只证明项目变更和测试结果，不代表用户本人已经掌握这些概念。

系统现在如何处理

检查身份与已有会话入口沿用 Workspace 和 StudySession 行锁。先处理同 request_id 的幂等重放，再处理结束会话或当前会话已有生成的 409。
识别确定性清单题库清单由已有查询直接完成，不启动 provider，因此继续允许它绕过生成容量。需要模型解释的混合请求仍通过生成准入。
原子检查 accepted 容量读取活 assistant 消息数量。消息必须处于 generating 且 expires_at 尚未过期。工作区行锁保护该工作区，事务 advisory lock 保护跨工作区的共享计数。
保存一轮消息准入通过后才执行会话变化、帮助暴露记录和用户消息写入。用户消息与 assistant 占位在同一事务提交，accepted 事件和 request_id 一起进入 trace。
等待执行许可后台任务先检查当前消息，再等 Semaphore。等待既受秒数限制，也受进程内等待者数量限制。未开始执行的等待任务不续租。
重查并执行取得许可后再次读取状态、attempt 和 expires_at。旧任务不符合条件就退出。有效任务记录 running，启动原有检索、路由和模型流程。
终结与释放完成、失败或取消会写终态。实际 provider 子任务与 heartbeat 清理完成后才归还 Semaphore。过期租约由现有恢复路径标为 interrupted。

实际代码没有独立的 StudyGeneration 表。生成状态已经由 StudyMessage 承担。assistant 消息的 status、attempt 和 expires_at 分别表示当前状态、执行代次和租约截止时间。复用这个结构，可以让准入计数与已有恢复逻辑读取同一份事实，避免再维护一套容易不同步的 reservation 状态。

准入判断不能只有一次 SELECT COUNT。两个请求可能同时看到还有一个名额，然后各自插入消息，最终超过上限。现有 Workspace 行锁已经让同工作区的写请求排队。新增的短事务 advisory lock 让不同工作区的生成准入也依次检查共享上限。锁在提交时释放，模型和网络调用都发生在提交之后，不会长时间占着这些数据库锁。

容量不足的拒绝位于会话上下文更新、mark_help、record_reference_exposure 和消息插入之前。因此，不会出现界面没有接受这轮问题，数据库却已经把问题保存或记成看过答案的情况。retry 也先判断容量，再修改 attempt、内容和 trace。容量被拒绝时，原来的中断草稿和代次保持不变。

幂等和容量的顺序同样重要。一个客户端可能因为响应丢失而重复提交已经被接受的 request_id。这个请求应当取回原来的 ticket，而不是重新占一个名额，也不应因为现在满了就变成 429。原来的同会话 409 继续放在容量判断前，让用户看到与原聊天行为一致的冲突原因。

数据库里的 accepted 和进程里的实际执行不是同一件事。用户按停止后，消息可以立刻变成 interrupted，数据库名额随之释放，但旧 HTTP 流还有清理工作。Semaphore 必须一直持有到旧执行的 finally 完成，否则新的执行可能在旧 provider 还没有退出时启动。本项把许可放在整个执行函数外层，原有的备用调用、取消和 heartbeat 清理都在许可之内。

后台等待也不能无限积累。等待秒数默认五秒，并且不能超过本轮原租约的剩余时间。另一个进程内计数将真实等待者限制到配置的 global limit。这个计数在 await 前同步增加，在成功取得许可、超时和取消时都通过 finally 减少。即使客户端快速停止并重新接受下一代消息，失效等待者也不能无限补入。

等待后必须重查有效性。任务最初排队时属于 attempt 1，等待期间用户可能停止并重试到 attempt 2。取得许可并不意味着 attempt 1 重新有效。_load_turn 会同时检查 generating、相同 attempt 和未过期租约，条件不成立就退出，不进入 provider。真正写入流式片段和终态时，原 publish 的 attempt、status 和租约 fencing 仍然保留。

恢复不是把所有 generating 消息一律重置。其他 API 进程可能仍在正常续租。准入计数只忽略已经过期的租约，原恢复函数再把过期消息收敛为 interrupted，并在 trace 追加 expired 事件。provider calls 不会因为恢复被抹掉，旧代次也不能续租或覆盖新代次。

任务注册改在提交前完成，但仍沿用 BackgroundTasks。注册函数本身抛异常时，请求事务会回滚。若进程在提交成功之后、任务实际开始之前消失，这一波仍依赖短租约过期恢复，不会自动重新调用模型。这是临时准入闸与持久队列的明确边界。

读懂这些概念就能读懂代码

概念人话解释在这里的作用
工作区同一份业务数据和访问归属的范围。限制一个工作区通过多个会话占用多少 accepted 生成。
accepted请求已经保存并承诺执行，但后台函数可能尚未开始。把尚未运行的后台任务也算进容量，不能只统计已经连上模型的请求。
租约需要定期续期的有效执行期限。进程消失后，让遗留消息最终不再占着准入名额。
行锁同一行在事务期间由一个写请求先处理。复用 Workspace 行锁保护同工作区准入。
advisory lock应用约定使用同一个数据库锁编号协调操作。让不同工作区的共享计数与新增 accepted 消息成为串行事务。
Semaphore只有拿到有限许可才能执行，结束后归还许可。限制一个 API 进程的实际生成，并覆盖 provider 取消清理。
fencing旧执行即使稍后恢复，也必须出示当前有效的代次和租约才能写入。防止过期任务或旧 attempt 覆盖重试后的消息。
幂等重放同一请求重复到达，仍返回原来的处理结果。重连或重试 HTTP 请求时不重复接受、生成或占用名额。

为什么选择这个方案

Foundational Thinking 要求先找共享状态的真实主人。这里选择已有 StudyMessage 租约，而不是新增一个同时描述同一轮生成的表。Make Operations Idempotent 让恢复和容量从当前状态推导，不依赖进程曾经打算做什么。

工作区保护复用已有行锁。只有共享 accepted 上限需要额外 advisory lock。锁内不更新其他工作区的消息，避免持有当前工作区行锁时再去等别人的消息行锁，形成倒序等待。

配置使用正数校验，默认每工作区 2、同库 accepted 4、进程实际执行 4。把限制设置成零不会悄悄关闭保护。调整执行许可配置需要重启 API 进程，因为 Semaphore 在首次执行时创建。

没有把所有失败包装成新的通用观测系统。已有请求体 request_id 被复制到 trace，并在 retry 中沿用。provider 自己的请求编号和原调用结果保持原契约。这样独立审核能够聚焦准入和清理，不必同时审核整个 G1。

方案收益代价与决定
只放进程内 Semaphore改动很少，能限制当前进程的执行。不同进程各有自己的许可，而且已经接受的后台任务仍可能不断积累，因此没有单独采用。
复用消息租约、工作区行锁和事务 advisory lock保留原状态归属，不新增表，在入口原子限制活 accepted 数量。采用。实际执行仍依赖各进程自己的 Semaphore，不能声称跨进程 provider 总量受同一个许可池控制。
独立 generation reservation 表能保存每个 attempt 更详细的占位与执行历史。本波没有采用。它需要迁移和第二套恢复规则，容易提前扩大成队列化重构。
直接持久队列化可以统一排队、认领、重放和优雅停机。按已批准排程留在第 5 波，与 outbox 和停机释放一起实施。本波先完成有界准入。

仍要知道的边界

同库 accepted 上限是跨进程原子的。Semaphore 和等待者计数只属于一个 API 进程的事件循环，不是所有 API 与 worker 共用的 provider 许可池。不同进程的取消清理可以短暂重叠。

没有新增持久队列、outbox、自动重放、公平调度或优雅停机。进程在提交后丢失仍由消息租约到期恢复，用户需要按现有方式重试。

没有修改模型调用预算或成本账本。原有单轮调用次数和备用行为保留。此项不能证明总费用有上限，也没有测量真实供应商在连接取消后的远端计算或收费行为。

所有 API 进程应使用一致的容量配置，改 Semaphore 上限需要重启。没有进行多进程真实 provider 压测、生产部署或个人数据验收。

本 worker 不做提交、推送、PR、合并、跟踪文档或 HTML 生成。独立审核和后续 Git 由父代理负责。原工作区已有的复制清单、技能和生成器没有被本 worker 改写。

面试时可以怎样解释

可以说明单会话互斥不等于工作区并发限制，并解释为什么 accepted 任务也必须计数。证据是基线两项红测试和新并发准入测试。

可以解释为什么 COUNT 与 INSERT 之间需要数据库同步，以及为什么不能在模型网络期间持有行锁。证据是 Workspace 行锁、事务 advisory lock 和并发最后一个名额测试。

可以说明取消消息状态和取消实际 HTTP 流之间存在清理窗口，因此 Semaphore 要覆盖整个执行与 finally。合成取消清理测试观察到第二个工作区在旧清理结束前没有进入生成。

可以解释租约解决执行者消失后的有效期，attempt fencing 解决旧执行覆盖新执行。二者不能替代跨进程实际 provider 许可。应把已经验证的项目行为与本人独立讲清、实现和调试的能力分开。

检验自己是否理解

为什么同会话 409 已经存在，还需要工作区容量？

409 只管一个 session。用户新建多个 session 后，每个都能独立启动后台任务，必须再按 workspace 聚合限制。

为什么先检查容量再保存消息？

拒绝表示系统没有接受这轮工作。提前保存会留下幽灵用户消息、改变会话或记录帮助暴露，与返回结果矛盾。

为什么幂等重放要放在容量前？

重放要取回已接受的旧 ticket，不产生新工作。若先查容量，会把同一个请求的网络重试误报为满额。

停止后消息已经 interrupted，为什么不立刻归还 Semaphore？

实际 provider 操作可能仍在退出和清理。提前放开许可会让新执行与旧执行重叠，所以许可要在整个 finally 完成后释放。

租约还没过期，旧 attempt 就一定能继续吗？

不一定。重试会改变 attempt。取得许可和写入结果时都要同时检查状态、代次和有效租约。

有进程内 Semaphore 后，为什么仍要限制等待者数量？

停止可以先释放 DB accepted 名额，但旧 waiter 可能还没醒来。反复 Stop/retry 会不断替换活消息，因此等待秒数和真实等待者数量都需要明确上限。

能否把 global limit 说成整个部署最多四个 provider 调用？

不能。当前 DB 限制的是活 accepted 数量，实际执行许可属于各 API 进程。多进程旧调用的清理可能重叠，这一边界必须明确。
