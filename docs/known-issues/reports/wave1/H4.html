让个人版与公开版共用受限文档解析

让网上下载的面经经过共享的资源检查，并在解析超时或取消时结束相关进程。保留个人版更多文件格式与公开版较小上传限制；错误文件仍有明确原因，同批合法文件可以继续形成待审资料。

先理解你会遇到什么

假设你从网上下载了一份 DOCX 面经，然后导入个人版。DOCX 内部是 ZIP 压缩包，压缩后的文件很小，里面的内容却可能很大。只检查上传文件不到 12 MiB，不能判断后面要展开多少数据。MiB 是按 1024 计算的大小单位，1 MiB 等于 1,048,576 字节。本项所有内存与文件大小政策按代码的字节数理解。这个事故场景用于解释风险，不表示本次发生过真实攻击。

另一种情况是一张文件字节很少、像素却很多的图片。程序把图片转换成 RGB，再转换成数组和做文字识别时，需要分配额外内存。PDF 也有类似问题，文件大小不能代表页数和逐页提取的工作量。H4 分别检查展开量、页数和像素，因为这些指标约束的是不同阶段的开销。

旧个人版用线程处理文档。线程能让接口继续调度其他任务，但解析线程仍使用 API 进程的内存。你取消请求后，停止等待线程也不会自动停止线程里的解析。注册版原有子进程与 Linux 限额，不能据此认为 Windows 也有相同约束。两条入口需要共用可追踪的进程所有权和操作系统资源边界。

这与 Agent 工程的联系在输入处理环节。模型分析面经以前，服务已经要读取、解码和展开文件。提示词要求模型小心，并不能限制这些本地操作的内存。本项产出的是解析与清理机制及证据，不证明用户本人已独立实现或掌握这些知识，也不证明模型回答质量提高。

修改前后有什么区别

观察点修改前修改后
个人版的执行位置文档库在 API 所属进程的线程中运行，共享进程内存。每份文档在独立短期 worker 中解析，父进程负责输入输出、准入和回收。
两版的资源政策注册版已有 Linux rlimit，个人版没有相同资源路径，Windows 也不能靠这段 Linux 代码获得限制。共享 runner 和 worker，根据可信的 personal 或 public 策略名选择政策，Windows Job 和 Linux rlimit 分别实现。
DOCX 检查旧个人版可接受超过共享条目上限的 DOCX，red.log 记录了这个失败。注册版已有部分 ZIP 元数据闸。两版检查条目数、声明展开量、单成员压缩比、路径与加密标记，再分块实际读取和校验 CRC，全部通过后才调用 Document。
PDF 与图片个人版 PDF 没有强制的 30 页拒绝闸，图片在 RGB 转换前没有本项统一像素闸。PDF 在逐页提取前检查最多 30 页，图片在 RGB、数组与 OCR 前检查像素及边长。
取消与超时只取消异步等待，不能据此保证底层线程或子孙进程已结束。取消设置共享事件，并等待拥有者终止、等待和关闭资源。重复取消期间仍保留清理责任。
父子进程协议旧注册版输出缺少本项在父进程聚合前的字节限制。stdout 最多允许 400000 字节，并额外保留一个检测溢出的字节，stderr 丢弃，返回 JSON 再做字段与类型校验。
正常文件与来源个人版有多文件顺序、部分成功和来源元数据，注册版有待审核的导入记录。继续保留这些契约。解析出的正文仍是资料，不会因为解析成功就获得题库批准或本人能力归因。

系统现在如何处理

入口选择政策个人入口 bank 使用 extract_many_async，注册入口 _parse_document 使用 extract_async。入口选择可信策略，文件内容不能自定义内存或时间上限。
检查输入并等待准入runner 检查后缀、空文件和原始字节数。共享信号量在每个 API 进程内最多放行三个直接解析 worker，等待期间也检查取消和截止时间。
创建 worker 并建立限制Windows 父进程成功分配 Job 后才发送输入。Linux worker 在读取输入和导入重型解析库前设置 rlimit，父进程建立独立进程组以便清理。
按格式预检与提取DOCX 先检查并有界读取 ZIP，PDF 先检查页数，图片先检查尺寸。预检通过后才进行后续正文提取或可选 OCR。
返回有界结果worker 返回 ParseResult。父进程限制输出字节并校验 JSON，个人适配器恢复文件元数据，注册适配器返回 text 或 error。
收回资源再交给业务层正常、拒绝、异常、超时和取消都会进入清理。解析文本随后进入已有来源记录和候选审核流程，真实镜像及页面验收由父代理另行补证。

先看三个核心数据结构。document_policy.py 用 frozen dataclass 定义 ParserPolicy 和 ParseResult。frozen 表示实例字段不能在正常赋值操作中被改写。ParserPolicy 集中保存允许格式、文件字节、文字字符、展开量、页数、像素和资源预算。ParseResult 保存 text、chars、warning、error、kind。ErrorKind 用固定名称区分输入、归档、页数、像素、OCR、解码、资源、超时、取消、繁忙、边界和协议错误，避免调用者猜测任意异常文本。

个人策略允许原来的文本类、图片、PDF 和 DOCX。单文件最多 12 MiB，正文最多保留 60000 字符，内存政策为 768 MiB，墙钟预算为 20 秒。注册策略允许 PDF、DOCX、Markdown，单文件最多 6 MiB，正文超过 24000 字符就拒绝，内存政策为 256 MiB，墙钟预算为 10 秒。文件字节数与文字字符数是不同单位，一个汉字的 UTF-8 编码通常不止一个字节。

两套策略共用的格式政策是 DOCX 最多 512 个 ZIP 条目、声明及实际累计展开量最多 16 MiB、每成员最多 200 倍压缩比，PDF 最多 30 页，图片最多 12000000 像素且单边最多 12000。Linux CPU 软限制为 6 秒、硬限制为 7 秒。Windows 使用 Job 的累计 CPU 时间政策 6 秒。这些是配置中的拒绝条件，不是本次测出的速度或攻击拦截率。

每次 parse_document 调用拥有自己的截止时间。截止时间在等待信号量前建立，因此准入等待、创建进程、输入输出和解析都使用同一份单文档墙钟预算。等待名额耗尽预算返回 busy，启动后到期返回 timeout。它不覆盖后续题目提取、审核、数据库和模型调用，也不是整批多文件的统一截止时间。清理还需要等待进程和管道结束，所以 10 秒或 20 秒不能写成接口必定在该时间内响应的性能承诺。

WindowsJob 通过 kernel32 创建 Job Object，设置进程树总内存、累计 CPU 时间、最多四个活动进程和关闭句柄即终止。Job 句柄明确不可继承。父进程先把 worker 分配到 Job，成功后才向 stdin 写入放行字节 1 和文档内容。worker 没有收到这个首字节就退出。赋限失败时返回 boundary_unavailable，并清理已创建的进程，不会退回 API 线程直接解析。

Linux 路径先用 start_new_session 建立新的会话与进程组。worker.main 在读取放行字节和文件内容之前，设置 RLIMIT_AS、RLIMIT_CPU，并禁用 core dump，然后才使用 DOCX、PDF、图片等重型解析库。设置限额失败会让进程退出，不继续无限制解析。这里的 RLIMIT_AS 限制每进程虚拟地址空间，不等于实际常驻内存，也不是整个进程组的总内存上限。

这两个系统的语义不能互换。Windows Job 内存是它拥有的进程树总预算，并有四进程上限。Linux rlimit 通常由子进程继承，但分别约束各进程，父进程用 killpg 清理同组进程。Linux 这段实现没有提供相同的四进程总数闸，也不能阻止主动 setsid 后脱离进程组。不能把两个系统写成完全相同的隔离保证。

父进程仍有线程，但用途变了。一个 I/O 线程写入有界原始字节，另一个读取有界 stdout；异步包装用线程运行这个所有者逻辑。真正的格式展开和解析在 worker 里。worker 环境只挑选解释器运行需要的环境变量，并固定 UTF-8 与相关计算库线程数，不把 API、模型供应商和数据库凭据环境原样传给子进程。清理环境不等于限制文件系统或网络权限。

DOCX 的 check_docx 先读取 ZIP 目录，检查条目数及声明展开量，再检查成员压缩方法、加密位、重复名称、绝对路径、上级路径和冒号，并检查每成员压缩比。代码不会把成员解包到磁盘路径。之后逐成员分块读取，每块最多 65536 字节，并按剩余预算控制下一次读取量。真实累计展开量超限立即拒绝，读到末尾也让 ZIP 库验证 CRC。目录里的尺寸是声明，实际读取是另一层检查，不能只相信声明。

通过 ZIP 检查后，from_docx 才导入并调用成熟的 python-docx Document。注册版 linear_docx 沿正文 XML 的段落顺序读取，保持段落与表格中段落的相对位置。个人版保留先普通段落再表格行的既有方式。共享安全流程并没有强行统一两版的产品内容顺序政策。ZIP 预读与 Document 后续读取会增加工作量，不能把这层检查说成性能优化。

from_pdf 先在已受限 worker 中用 PdfReader 打开文件，拒绝加密 PDF，并在循环调用 extract_text 前检查总页数。查页数本身也要让解析库读取 PDF 结构，因此页数检查不能代替操作系统资源限额。超过 30 页时不进入逐页文字提取。没有可提取文字时返回提示，本项没有增加 PDF 渲染和扫描 PDF OCR 功能。

from_image 先用 Pillow 读取图片头中的宽高。非正尺寸、超边长或超像素直接拒绝，随后才导入 NumPy 和 RapidOCR，创建引擎，执行 RGB 转换、数组转换和识别。缺少可选 OCR 依赖对应 ocr_unavailable，损坏图片对应 decoder_error，超像素对应 image_limit，没有识别文字对应 empty_text。格式被列入允许后缀不代表每种编码都已在所有操作系统实测。

extract 先清理换行、空字符和多余空白，再形成结果。个人版可以截取保留文本，同时让 chars 记录清理后、截取前的原始字符数。例如输入 60001 个 x，返回正文长度 60000，chars 仍为 60001。这里的原始不是原文件字节，也不是包含所有格式标记的文件长度。注册版超过 24000 字符直接返回 text_limit，避免把截断文本当作完整导入。

父进程不会无限累计子进程输出。读取缓冲区最多到 400001 字节，发现超过 400000 就报告 protocol_error 并清理。stderr 直接丢弃，避免错误流堆积或堵塞。JSON 结果必须恰好包含五个字段，类型、字符数、文字上限以及成功失败状态都要一致。失败结果不能夹带正文，成功结果必须有正文且原始字符计数不能小于保留文本。无法识别的退出只能报告进程异常或资源限制，不能推断一定发生了内存耗尽。

取消最容易漏掉的是进程创建途中。run_cancellable 保存一个线程事件和底层任务，用 asyncio.shield 保留底层所有者。外层收到 CancelledError 后设置事件，并继续等待该任务完成清理。再次收到取消也继续等待，最后重新抛出取消。这样即使取消发生在 Popen 已创建进程、但尚未把对象返回给调用者的时候，负责清理的线程也不会被遗弃。

parse_document 的 finally 负责结束 Windows Job 或 Linux 进程组，必要时终止直接 worker，wait 等待直接子进程，等待 I/O 线程结束并关闭管道，最后释放准入名额。正常返回也会先处理残留后代，避免后代仍持有 stdout 让读取挂住。三个名额属于一个 API 进程的共享信号量，并不代表整个部署、所有线程或全部输入内存只有三个单位。

多文件通过 pool.map 汇集结果，返回顺序保持输入顺序。测试里的 first.txt、broken.docx、last.md 得到成功、失败、成功，坏文件不清空另外两个结果。ExtractResult.text 和个人 API 原有的合并逻辑继续限制总保留文字。bank 把实际保留的 text_parts 写入 extracted_source_text 和 source_review，后续题目仍是候选。注册版也把解析失败记为 FAILED，把成功导入放入待审核状态。H4 改变解析执行边界，不赋予资料审批权或本人经历归因。

进程与线程线程共享所属进程的地址空间，进程有独立地址空间。把重型解析移到独立 worker 后，父进程才能用操作系统机制终止和限制它。

CRCZIP 用于检查成员数据一致性的校验值。实际读完成员时发现损坏，检查通过后才让 Document 使用归档。它不是来源真实性或数字签名证明。
Job Object 与 rlimitWindows 的进程管理对象与 Linux 的进程资源限额。建立实际操作系统限制，但两者的总量和继承语义不同。
墙钟时间与 CPU 时间墙钟是现实经过的时间，CPU 时间是处理器实际执行消耗的时间。等待、管道阻塞和运算用不同机制约束，不能只依赖 CPU 限额。
准入信号量同时进入某段工作的名额计数。单 API 进程最多三个直接解析 worker，清理结束释放名额。
取消所有权发起工作的一方必须知道谁负责把底层工作收回。异步请求取消后仍等待拥有 worker 的任务清理，防止只停止界面等待。
有界协议父子进程通信限制字节数，并检查字段内容。子进程输出过多或格式错误时拒绝，不把输出无限装进 API 内存。
失败即拒绝关键资源边界建不起来就终止操作。牺牲不支持环境的可用性，避免悄悄退回无限制解析。
资源约束与权限隔离前者限制消耗，后者限制能访问什么。本项实现资源约束，不提供完整文件系统、网络或低权限沙箱。

为什么选择这个方案

继续复用 python-docx、pypdf、Pillow 和可选 RapidOCR，原因是它们已经负责复杂格式和文字识别。本项围绕这些库建立输入、资源与生命周期边界，不重新编写 DOCX、PDF 或图像解码器。使用成熟库也不意味着可以跳过限制和清理。

选择每文档一个短期 worker，因为每次任务都有独立生命周期，完成后能够丢弃解析器状态，并由父进程明确负责回收。它的代价是重复启动解释器和加载 OCR 引擎。没有吞吐或延迟对比数据，因此不能写成速度提高，也不编造百分比。

个人版 OCR 比纯文本路径需要更多启动资源，所以个人策略使用 768 MiB 和 20 秒墙钟预算，注册策略保留 256 MiB 和 10 秒。实际 Windows 合成图片 OCR 已在该依赖栈和限制下通过，但这不能推广成所有图片、所有机器和 Linux OCR 都保证通过。

保留个人版与注册版的格式、长度和 DOCX 顺序差异，可以减少与安全目标无关的行为改变。复用的部分是解析机制及安全检查，业务入口仍解释自己的成功与失败结果。H3 的来源审核契约继续留在原来的业务层。

ZIP 先检查声明，再有界实际读取，会重复一部分解压工作，但能在 Document 之前发现声明之外的实际读取问题。OS 限额负责覆盖预检本身的开销，格式预检减少已知过量输入进入更昂贵处理的机会，两者各有作用。

精简镜像采用默认排除再精确放行的打包方式。新增三个模块必须分别放行，否则本地能 import，最终镜像仍可能找不到 worker。源码里的放行规则只是打包意图，父代理还要用最终镜像证明文件确实存在并能运行。

方案收益代价与决定
保留 API 线程解析并只加异常捕获改动较少，也能让异步调度继续。线程仍共享 API 内存，取消等待不能可靠停止解析，无法满足本项资源所有权要求，未采用。
每文档一个短期受限进程任务结束即可丢弃状态，资源、管道和后代清理有明确拥有者。重复支付进程与 OCR 启动成本，当前采用，没有宣称性能收益。
常驻解析进程池能复用解释器和 OCR 初始化。要额外解决损坏 worker 替换、累计预算、单任务取消与池健康恢复，超出 H4 和当前证据范围，留在 F1 队列相关范围讨论。
只依赖上传文件大小入口检查成本低，容易向用户解释。不能约束 ZIP 展开量、图片像素和 PDF 页数，保留为第一层检查而不单独依赖。
资源边界不可用时无限制回退在不支持环境中仍能尝试解析。会丢失本项核心保证，未采用。当前明确拒绝，让用户拆分文档、换格式或处理环境问题。
加入部署级队列、cgroup 或完整权限沙箱可以进一步管理跨进程总量或访问权限。本项未实现，也没有对应验收。不能把三名额信号量、Job 或 rlimit 描述成已经具备这些能力。

具体改了哪些代码

server/app/services/document_policy.py

定义不可变 ParserPolicy、ParseResult、ErrorKind、两套可信策略及 400000 字节协议上限，是查每个限制真实数值的入口。

server/app/services/document_runner.py

WindowsJob、parse_document、_read_result 和 run_cancellable 负责准入、赋限、输入放行、有界协议、超时与取消清理。阅读时重点追踪 process、job、管道和名额的拥有者。

server/app/services/document_worker.py

仍要知道的边界

本项没有完整权限沙箱。worker 仍以运行服务的身份访问环境允许的文件和网络，环境变量筛选不能替代访问控制。Linux 进程组也不能阻止主动脱离进程组。源码挂载探针的断网容器配置是该次验证环境，不代表所有产品运行都自动断网。

三个直接 worker 名额只在一个 API 进程内共享，多个 API 进程各自拥有三个名额。它不是部署级队列、全部后代进程数、线程总量、输入缓存总量或整个服务内存配额。Windows Job 的四进程上限与这个三名额也不是同一个计数。

Windows Job 总内存政策与 Linux 每进程虚拟地址空间政策不同。不能用一个操作系统的结果替代另一个，也不能把 Linux rlimit 写成进程组总内存或 cgroup。

本项没有全请求或整批截止时间，没有接口延迟、吞吐或攻击效果基准。配置预算、套件耗时和真实响应速度要分开。启动、OCR 加载和清理都会产生成本。

有效但复杂的文件也可能因预算不足被拒绝。用户需要拆分、缩图或换格式。个人版保留截断正文，不能保证导入原文件的所有内容；chars 表示清理后截取前的字符计数。

OCR 是可选依赖。本次 Windows 合成图片通过，Linux OCR 未验证。没有新增扫描 PDF OCR，没有证明每种允许图片编码、每个复杂表格或所有损坏文件都可处理。

stderr 丢弃能约束输出和阻塞风险，也减少了底层诊断细节。异常退出提示不能精确断言是内存、CPU、解码库故障还是其他进程异常。

最终精简镜像、实际产品浏览器、最终独立审核、PR 与 dev 合入信息仍由父代理验收绑定。教学 DOM 与夹具摘要不替代这些证据。本报告不声明已部署个人实例或生产环境，也不声明真实攻击抵抗能力。

文件解析成功只说明获得资料文本，不表示题目已批准、不表示来源可信，也不表示用户本人经历或能力得到证明。模型提取与学习评分仍受各自的来源和证据规则约束。

现有 pytest_asyncio 关于 fixture loop scope 的弃用警告仍出现在日志中，没有导致本次检查失败。报告保留这一已有说明，不扩展修改测试基础设施。

面试时可以怎样解释

可以先解释问题而不背术语。下载文件的字节数小，不代表展开、逐页提取和图像识别的资源需求小。线程解析仍共享 API 内存，所以本项把重型解析交给受限短期进程，父进程负责准入、输入输出及取消后的回收。

再说明设计取舍。不可变策略让个人与注册入口共用安全机制，同时保留不同格式和正文长度政策。预检必须发生在 Document、逐页 extract_text、RGB 和 OCR 之前。预检本身也会使用解析库与资源，因此还需要 OS 限额。

说明取消时要说出所有者。外层请求取消后设置共享事件，受保护的底层任务继续执行清理，结束进程、等待退出、关闭管道并归还名额，之后才向上抛出取消。只取消 await 或只返回超时，不能证明底层工作已停止。

陈述证据时可以说，现有交接记录包含 85 项针对性通过，其中 12 项是生命周期子集；本机 Windows 真实 Job 与本地 OCR 有证据，Linux 有挂载源码的非 root 功能探针。不要说成 97 项，也不要说 Linux OCR、最终镜像、生产部署或全权限隔离都通过。

这段文字提供可学习的解释，不替用户声称亲手完成了实现。只有在用户自己复现、读懂并能独立解释后，才适合把对应能力写成本人经历。当前工程归因仍是冻结源码、作者交接与父代理后续验收。

检验自己是否理解

为什么文件不到 12 MiB 仍需要 ZIP、页数和像素检查？

原始字节只限制上传体积。ZIP 展开、PDF 逐页提取与图片转数组对应不同资源开销，需要在相关昂贵处理之前分别检查，同时由 OS 限额约束解析本身。

把解析放进 to_thread，为什么不能直接说已隔离内存？

线程使用同一进程的地址空间。它能避免阻塞事件循环，但不能提供独立进程内存边界，取消等待也不会自动停止底层线程。

Windows 为什么要先成功分配 Job，再发送首字节和文件？

首字节是输入放行约定。Job 成功前 worker 等待输入，失败时父进程拒绝并清理，避免未受限进程先开始处理不可信文档。

Linux 的 256 MiB 与 Windows 的 256 MiB 是否表示相同总内存语义？

不是。Linux RLIMIT_AS 是每进程虚拟地址空间限制，子进程继承但分别计算。Windows Job 配置的是它拥有的进程树总内存预算，不能互相替代。

同一请求连续取消两次，为什么还要等待底层任务？

清理责任不能因第二次取消而丢失。run_cancellable 设置事件后继续 shield 等待所有者完成回收，再重新抛出取消。否则创建中的进程或已经运行的后代可能留在后台。

一个 API 有三个名额，部署四个 API 进程就仍只有三个 worker 吗？

不是。每个 API 进程有独立信号量。它只限制本进程的三个直接解析 worker，不约束全部署、所有线程、全部后代或总内存。

个人版 60001 个字符会怎样，为什么不能只看 text 长度？

正文保留 60000 字符，chars 记录清理后截取前的 60001。只看返回正文会漏掉截断事实。注册版采用不同政策，超过 24000 字符直接拒绝。

为什么不能把 85 项与先前 12 项相加？

同一组生命周期测试后来已经包含在最终 85 项套件里。12 是其中子集，多次执行不增加独立测试场景数。

本地 OCR 通过能否证明已经调用远程大模型，或 Linux OCR 也通过？

都不能。实际测试使用本机安装的 RapidOCR 识别合成图片中的 123，没有远程模型调用。Linux 探针明确没有运行可选 OCR。

为什么十二次教学页面检查不能证明超时清理正确？

页面只是把六种预设情景各在两个宽度切换显示，没有创建解析进程。超时清理要看真实进程 PID、退出和恢复的运行证据。

ZIP 目录声明展开量合格，为什么还要实际分块读取？

目录尺寸只是元数据声明。实际读取可以累计真实展开量并触发 CRC 一致性校验，在 Document 使用内容前拒绝异常归档。

解析成功是否表示文档可以指挥 Agent，或题目已经批准？

不能。解析只产生资料文本。来源审核、候选批准、模型行为和本人能力证据仍由各自规则判断，H4 没有提高资料的权限。
