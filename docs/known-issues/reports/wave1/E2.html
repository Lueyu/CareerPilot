私有模型按配置单价预留与结算，部署日预算在联网前生效

让聊天、评分和后台生成共用可追溯的货币预算。每次真实模型请求先留下资金记录，再允许联网；供应商没有可靠用量时明确标为未知，防止备用调用、取消或业务回滚造成漏账。

先理解你会遇到什么

假设你设置每天最多花五分钱。一个聊天请求失败后自动切到备用模型，又因为结果缺少演示而修复一次。用户看见的是一个问题，供应商收到的却是多次真实请求。如果程序只在最终答案保存时记一次成本，失败和修复的费用就会丢失。旧实现还把输入与输出全部按固定每百万 token 两元计算，换模型后成本数字依然不变，因此既挡不住支出，也不能解释费用。

另一种风险出现在并发时。两个工作空间同时读到最后一笔余额，各自判断足够，再一起调用同一个付费密钥。如果预算按空间分别发放，新建空间还能继续获得额度。现在日限额针对本部署全部私有空间求和，删除空间也不会删除其历史财务记录。资金归属保留空间身份，资金上限则属于整个部署。

这项设计与 Agent 工程的联系在于外部调用有真实成本，而且结果和计费证据经常不同步。会写提示词不等于能够控制并发支出。工程实现需要把请求身份、预算、失败语义、重试和数据库事务放在同一个可以验证的行为合同中。

补修时发现一个具体入口遗漏：把自己的聊天整理成面试题时，底层计费闸已经要求调用归属，但这个业务调用没有传入它。结果不是免费调用，而是联网前返回BILLING_SCOPE_REQUIRED。界面功能因此不可用。正确修复是补齐可信归属，不是关闭安全检查或让缺身份的调用默认使用本机所有者。

系统现在如何处理

取得归属API 从已鉴权 workspace 构造不可变 BillingScope；后台任务从持久化任务取得归属；已有 Trace 使用其 workspace_id。
核对价格按照 provider、endpoint、model 三项精确查找部署配置，输入与输出价格必须显式存在。缺价、缺预算或缺归属直接拒绝。
计算预留输入使用 UTF-8 字节数加 384 模板开销作为保守上界，输出使用这次实际发送的 max_tokens。两个上界分别乘配置单价。
原子准入独立短事务取得 PostgreSQL 全局 advisory lock，检查当天是否有超预留异常，再汇总全部署当天占用。足够才插入 RESERVED 并提交。
实际联网只有提交成功后才构造实际 HTTP 请求。网络不占用资金事务锁，SSE、总时限、首内容时限和取消行为保留。
结算或保留可靠用量按冻结价格写入 SETTLED；缺失或无效用量写 UNKNOWN 并保持原占用。结算失败时原始 RESERVED 仍在数据库。
交付业务结果业务可以成功、失败、取消或者回滚。聊天后台持久化预算错误码和终态，HTTP 可拒绝的同步入口返回 429 与 Retry-After。

账本采用每次实际请求一行的形状，没有另建余额行和事件行。每行保存调用 UUID、空间、操作来源、UTC+8 原始账期、请求的 provider、endpoint 与 model、两个价格快照、每日限额快照、输入上界、输出上限、预留额、当前占用、实际额和状态。预留阶段当前占用等于预留额；已知结算后当前占用变为实际额；未知时当前占用不变。汇总当前占用可以直接得到当天资金使用情况。

金额使用 nano-CNY 整数。一元等于十亿 nano-CNY。配置中的人民币单价先用 Decimal 精确转换，计算中不使用二进制浮点。输入和输出的费用相加后除以百万，向上取整到最小货币单位。指标页面可以把整数结果转换为展示数字，但可审计的原始记录始终是整数。

以教学计算器的合成数据为例，输入上界 5000、输出上限 2000，输入每百万两元、输出每百万八元。预留是 5000 乘 2 除百万，加 2000 乘 8 除百万，得到 0.026 元。实际输出只有 500，已知结算是 0.014 元，释放差额 0.012 元。如果供应商没有有效用量，就保留 0.026 元。日预算 0.05 元时，两个完全未结算的同类请求需要 0.052 元，因此只能放行一个。这些价格和用量全部是合成示例，不是供应商报价。

并发安全依靠数据库事务级全局 advisory lock。每个进程都在同一个数据库内取得同一把锁，完成检查和插入后立即释放。第二个竞争者取得锁时会看到第一个已经提交的预留，不能再用旧余额判断。结算也使用同一把锁，所以准入与真实费用更新不会互相穿过。这里没有把网络调用放进锁内，也没有实现后台队列。

可信用量至少需要合法整数输入与输出字段，不能把布尔值当作整数。输入必须大于零，已经收到非空内容时输出也必须大于零。如果 total_tokens 存在，还要等于输入加输出。缺失、全零或矛盾用量只说明供应商证据不足，不能据此退款。显式配置零单价则是另一回事：操作者明确声明价格为零且用量有效时，可以结算为已知零元。

请求失败并不代表免费。流式响应先产生内容和 usage，再发生 JSON 错误或取消时，适配器仍然保存并使用已经收到的有效用量。没有 usage 的异常或取消进入 UNKNOWN。结算由独立任务在取消清理期间执行，数据库事务独立于业务事务；如果进程在结算前崩溃，已提交的预留仍占预算。没有超时自动退款，所以失联不会悄悄恢复可花余额。

结算以调用 UUID 为幂等身份，第一次终态写入获胜。重复回调、并发清理和重试结算不会重复扣费，也不会把后来传入的另一份用量覆盖第一次结算。原始账期不随结算时钟移动：北京时间深夜预留、午夜后完成，费用仍属于预留时那一天。价格调整同样不会改写历史，因为结算读取行内价格，而不是重新读取当前配置。

当真实费用超过预留，系统记录真实金额，不把供应商结果截成预留值。只要当天出现任何一笔这种异常，整个部署当天的后续私有请求都以 RESERVATION_EXCEEDED 拒绝，即使日预算仍很宽裕。这个选择牺牲一部分可用性，让操作者先检查 token 上界和计价规则。新账期可以重新准入；历史异常与真实费用继续保留，本项没有管理页面或自动改账。

预算拒绝使用 BudgetPolicyError，和供应商故障返回 None 的语义不同。普通 provider 失败可以按既有业务规则考虑备用模型，但本地预算拒绝会停止。聊天会把策略码、Retry-After 和拒绝调用写入终态诊断。评分与项目分析也保留可解释的策略分类，防止后台误把预算当成临时网络抖动而反复重试。

费用展示不再重新套固定两元单价。新指标用 configured_price 标明按操作者配置计量，用 unknown 标明没有可靠费用。迁移把缺少计费身份的旧固定价指标归为未知，不把历史估算重新包装成真实账单。configured_price 也不是供应商账单凭证：它只能证明程序按冻结配置和返回用量进行了计算。

计费异常还区分 admission 与 settlement。admission 是联网前拒绝，聊天调用标记 denied；settlement 表示已准入的上游请求可能已收费，聊天保留 unknown、billing_call_id 和已经收到的 usage。结算数据库异常不能写成“没有联网”，也不能因此切到备用模型。本项对实际发生 MockTransport 请求后结算失败的聊天和项目阶段分别保存了回归证据。

计费准入等待与供应商首内容时限分开计时。只有预留提交后才开始供应商计时，避免数据库短锁等待消耗首 token 时限。现有费用页也接收可空金额，未知显示“费用未知”，有效零元显示 ¥0，配置金额显示人民币数值。

generate_question已经拿到被API确认属于当前调用者的工作空间编号。现在把这个编号与会话编号、内容快照摘要放进既有BillingScope，显式交给read_json。后者每次实际调用都经过统一预留与结算。操作标签用于解释来源，不承担去重职责；账本仍为每次真实请求生成自己的记录。保存结果的既有缓存先于模型调用返回，因此重复整理同一快照不会再次占用钱。

为什么选择这个方案

公开模型网关已有整数货币、短事务、先预留再结算的经验，本项复用这种结构，但使用独立表和独立调用身份。私有业务既有聊天又有后台评分，无法把财务记录附在一个可能尚未提交或被删除的业务行上。

比较过每日余额行加请求行加交易事件表的设计。它适合更大规模和专门对账系统，但本项目当前最重要的是单一事实源和可验证的并发准入。直接汇总请求行减少同步维护多份余额的机会，day 索引服务全局日汇总，workspace 加 day 索引用于归属检查。

输入预留使用字节上界而不是推测模型 tokenizer 的平均压缩率。这样更保守，也可能让大输入提前被拒绝。该上界无法证明供应商隐藏模板和额外计价全部受控，因此还要保留超预留记录并暂停当天后续支出。

价格只接受显式配置，默认没有供应商报价。默认十元是部署限额，不是模型价格。连接测试也是真实付费请求，因此与正常业务使用相同计费准入。未配置模型的规则路径继续不联网、不收费。

选择在业务服务明确传参，复用已有BillingScope和网关，而没有新增全局上下文变量，也没有更改请求格式、账户权限、计价规则或数据库结构。错误发生在调用者漏传必需信息，保护性拒绝本身是正确的；把闸门放宽只会掩盖根因。

如何证明修改有效

数据库测试通过 run_isolated_tests.py 创建全新 *_test 数据库。用量、价格、密钥、输入和供应商响应均为合成数据。httpx.MockTransport 代替外部供应商，测试不调用真实模型，不修改个人数据或个人进程。

计费测试没有替换 reserve 或 settle。模拟网络处理器用另一个数据库会话观察已提交的 RESERVED，因而能够验证先持久化再联网。原有纯传输测试显式替换计费边界，它们证明 SSE 和诊断兼容，不能代替账本正确性测试。

旧基线适配器以 6c6e0801c7a0767f649dd6f4f48d6cbdbc486e3a 源码在内存中加载，使用 MockTransport 实际观察到无价格、无 scope、无 max_tokens 仍发出一次请求，证据见 baseline-observation.json。最终新增拒绝用例要求这些场景零联网。

仍要知道的边界

没有调用真实供应商，所以不声明真实模型兼容、真实单价正确或真实账单完全一致。操作者必须显式提供价格，价格为空时已配置的私有调用会拒绝联网。

UNKNOWN 和进程崩溃留下的 RESERVED 没有自动退款或人工管理 UI。本项保守保留占用，需要后续有真实供应商证据的核对流程。

预留能阻止未获准的新请求，但不能撤回已经在途的付费请求。某个请求超预留前已经准入的并发请求仍可能完成并结算。

超预留异常暂停其原始账期后续请求，新 UTC+8 账期可以重新准入，异常历史继续保留。部署全局日预算不等于供应商密钥在其他应用中的总支出。

本项没有实现 G3 成本环比告警、E3 请求限流、后台队列、连接池重构或 URL 出站策略。个人实例未部署，个人库未迁移。

保留已确认基线缺陷 test_study_routing.py::test_generation_deadline_closes_a_stalled_attempt，表现为 timeout 被清理覆盖成 cancelled。本项新增的资金状态与 usage 取消测试均通过，没有用基线名单豁免新增失败。

实际浏览器补查发现，当前默认工作台访问 /ops 会转到 /settings。Ops 费用组件的283项前端测试通过，但该旧页面只挂在 NativeWorkspace 中，默认 App 使用 InterviewWorkspace。E2 没有交付新的运维导航；统一模型出口与计费 API 的验证照常成立。该既有入口缺口以 E2-UI-BASELINE 记录，后续界面交付需按项目设计流程落实。

检验自己是否理解

用户只问了一次，为什么账本会有两行？

备用、修复或重新实际发送都是独立的付费请求，每一次都必须有独立 UUID、预留和结算。用户交互次数不能替代供应商请求次数。

为什么任务取消后仍然占着预算？

取消只证明本地不再等待。供应商可能已处理请求，没有完整可靠 usage 时无法证明免费，因此保留预留为 UNKNOWN。

新建或删除空间能恢复额度吗？

不能。日限额汇总部署内全部私有账本，财务行不随空间删除；空间身份用于归属而不是重复发放额度。

午夜后调价并结算，费用按哪一天哪一价格？

按预留行保存的原始 UTC+8 日期和两个价格快照。当前时钟和新配置不能改写过去。

真实费用只比预留多一点，但日预算还很多，可以继续吗？

本项采用保守策略，当天出现任何超预留就拒绝当天后续私有请求，保留真实金额供核对；次日账期可重新准入。

为什么修复BILLING_SCOPE_REQUIRED时不能直接跳过资金闸？

拒绝说明保护规则生效，但调用者没有提供可信归属。应该从已验证的工作空间和会话补齐身份，让调用继续接受价格、预算和结算约束。跳过检查会把功能恢复建立在漏账风险上。
