H8 · 实现与验证记录

给五处嵌套输入建立边界，并保持题库全集分页完整

完成批准的 Wave1 H8：非法字段、错误类型、过大或过深 JSON 在业务处理前安全拒绝；合法作答、审批、遥测与发布规则保持兼容；题库降低单页上限后，资料库仍取得完整库存。

先理解你会遇到什么

外层请求已经用了 Pydantic，不代表嵌套字典也有契约。旧版 payload 和 assistance 可以携带任意键，数字 1 或字符串 false 容易被当成布尔声明，客户端还可能夹带服务器专属的项目来源字段。旧版 telemetry 虽然最多接收 50 个事件，每个事件的 props 却可以非常大。21 个专门设计的非法输入在旧版模型上全部被接受，这是本次保存的红测试证据。

HTTP 的 Content-Length 是请求方提供的说明，不能充当实际收包计数。客户端可以不提供长度、声明长度为 1，或分成多个 ASGI 事件继续发送。若先调用 request.body() 把所有内容读入内存，再检查字段长度，内存开销已经发生；若深层 JSON 在解码时超出递归能力，事后遍历也来不及。

降低 bank 单页上限会影响 Questions.tsx。它原本一次请求 limit=5000，再在浏览器中按难度、收藏等条件筛选并导出选中项。仅修改 API 上限会导致 422，或只显示第一页却把它当成全集。这是一次必须同时迁移消费者的兼容修改。

与 Agent 工程能力的联系是把不可信输入、资源边界和证据归属落实到可执行代码：模型生成或用户提交的 JSON 必须先验证，再进入确定性服务；自报使用辅助不能撤销服务器观察；材料入库和练习提交不会自动变成独立能力证据。这些是工程结果，不能据此宣称使用者已经亲自掌握相关能力。

系统现在如何处理

既有准入请求先经过 CORS、恢复状态、鉴权与 E3 限流、语言处理。安全计数属于既有准入，不是题库或学习业务写入。
有界接收精确匹配六类 JSON 动作，检查每个实际 http.request 块；任何长度头都不能改变实际字节上限。未命中的上传和 GET/SSE 走原处理。
解码前深度在有限缓冲上识别 UTF-8/16/32，忽略 JSON 字符串中的括号和转义，避免极深结构进入递归解码。
领域校验FastAPI 使用严格 Pydantic 模型。自由 JSON 在 JsonValue 递归验证前先做有界迭代遍历。错误返回 422 的字段位置与消息。
保留业务语义用 exclude_unset=True 导出真实提供的原始字段，再调用既有服务。服务继续检查工作空间、版本、幂等、项目快照和辅助来源。
完整库存客户端以 limit=200 和递增 offset 请求，按 total 验证结束，全部成功才把结果交给页面本地筛选与批量操作。

审批的核心形状是 edits: 正整数 ID → DraftEdit。JSON 对象键天然是字符串，因此边界接受合法的十进制正整数字符串，例如 123，转换为领域整数，而不是用严格 int 机械拒绝所有键。负数、零、非十进制及可能碰撞的非规范键被拒绝。item_ids 和 edits 各最多 200 项。item_ids 缺失或 null 仍是全部审批，空数组仍是不选任何项。

DraftEdit 只包含 _approve_locked_import 真正消费的字段，包括 title、skill_key、answer_html、rubric、short_code、qtype、topic、difficulty、options、company、role、level 和 tags。字符串长度按数据库列或实际内容边界约束，难度是严格的 1 到 5 整数。title 等非空列不能显式为 null；company、options 等合法可空值继续允许。rubric 中的评分点、criteria 和扩展字段作为有界 JSON 保留，避免虚构一个破坏既有评分结构的白名单。生成题仍保留原有结构审核路径。

非 PROJECT 的 ActivityPayload 支持 text_answer 与 answer_text，以及原服务实际支持的六个辅助别名：hint_used/used_hint、reference_viewed/viewed_answer、ai_declared/ai_assisted。顶层和 assistance 内的声明都必须是真正的 JSON 布尔值；1、0、字符串 true/false 和 null 不会被强制转换。项目提交复用相同声明模型，但项目内容和来源只能来自服务器快照路线，客户端不能填 project_contract、source、独立性标记或反馈观察。

兼容的关键不只是字段名称，还包括字段有没有出现。若把所有未传的 bool 默认 false 导出到旧 payload，再计算请求摘要，重试会变成不同请求。这里模型内部可以有默认值，进入业务服务时用 exclude_unset=True，只导出客户端原本提供的位置；不 trim 原答，不改名合并别名，也不把缺失的 assistance 自动插入原 payload。真实数据库测试先用旧服务保存指纹，再通过新 HTTP 模型重复提交，仍得到同一个 submission_id。

归因继续使用原服务的单调合并：服务器知道用户看过参考答案，客户端声明 viewed_answer=false 不能把它抹掉；客户端自报 true 则会保留下来。项目评分仍使用服务器冻结资料，练习运行仍为 PRACTICE。输入模型的工作是拒绝越界数据，而不是创建新的能力证据或替代既有所有权检查。

telemetry props 与 RuleIn.value 的合法业务含义就是自由 JSON。规则模型文档存在 license_policy、auto_merge、fact_check_strictness，存储还允许未来规则；实际 auto_merge 消费 is_enabled。因而本项保留自定义规则键和嵌套配置，只把 key 长度限制到数据库列的 64。共用的 BoundedObject 使用 Pydantic JsonValue，额外限制深度 8、节点总数 1024、单对象 128 个字段、单数组 128 项、键长 128、字符串长 8192，以及有限浮点数。它不篡改合法值。

真实字节边界在接收阶段工作。telemetry 为 128 KiB，学习提交和规则为 512 KiB，导入及审批为 2 MiB。每次 await receive 后，先判断已有缓冲长度加本块是否超限，再决定是否追加；超限立即返回 413，后续块不再读取。上限内的多块合为一份有限 body 重放给 FastAPI。Content-Length 缺失、虚小、虚大以及 chunked 都不参与信任判断。

原始 JSON 深度扫描并不替代 JSON 解析器。它只在有界内容上识别字符串和转义，统计字符串外的结构括号，超过 32 提前返回 422；格式正确与否仍交给 FastAPI。测试包含 1500 层以及 UTF-8、UTF-16、UTF-32。对非有限数字，Pydantic 校验错误不能把原始 NaN/Infinity 原样回显，否则错误响应自己也会编码失败；因此仅这些范围内的 422 返回 type、loc、msg，其他路由继续走框架默认错误处理。

中间件顺序是此次审查中的实质修正。最初把 guard 放得太靠外，会直接返回并跳过 E3 添加 request_id 和扣减配额。最终入站保持 CORS → RecoveryGuard → ApiRateLimit → Language → JsonInputBoundary → FastAPI。真实应用测试证明 413 和深度 422 带 X-Request-ID、正确 CORS，413 还带语言头；受保护规则写入的第一次超限消耗原有限额，下一次正常请求按原策略返回 429。

分页不是把 5000 改成一个更小数字就结束。200 页大小在现有默认 60 和 Bank 页面 20 之上，同时把单次响应最多题数降低到原来的二十五分之一；这只是明确的资源选择，不是性能基准。Questions 全集加载器在每页后检查 total 稳定、没有重复 ID、没有提前空页、没有超过宣告总数，全部成功才发布库存。失败不会把部分列表装作完整；新查询或卸载通过 AbortController 取消旧请求，旧响应不能覆盖新查询。

输入边界的判断

1 KiB 等于 1024 字节，1 MiB 等于 1024 KiB。字符数量与 UTF-8 字节数量不同。真实服务还检查键、字符串、列表、节点总数和自由 JSON 的业务深度；输入通过后，仍要满足鉴权、版本和业务规则。本演示只解释边界判断，不证明实际收包或数据库行为。

为什么选择这个方案

校验集中在API接收输入的位置。业务服务拿到经过检查的数据后，继续负责事务、评分证据和来源归属。这样可以在业务执行前指出字段错误，也能避免在每个函数里重复写一套不一致的检查。

严格模型把字段含义写清楚。例如帮助声明只接受true或false，字符串和数字不能冒充布尔值。自由JSON也有确定的类型和大小边界。前端明确区分加载中、完整可用和失败，不会把未完成的第一页数据当成已取得全部题目。

复用 ASGI receive、FastAPI 校验和框架错误处理，仅增加本项范围所需的字节、深度及错误响应安全；没有引入新的解析器或全局异常信封，没有修改 F7/F8 的生产实现。

旧评分测试使用简化的任务对象，缺少现有计费契约需要的workspace_id、run_id和step_id。补齐合成测试对象能让失败元数据场景走到真正要检查的位置。生产计费仍需要真实归属，不能为了让测试通过而给实际调用补一个默认账户。

Questions页面的筛选、排序、收藏和批量选择依赖同一份完整题目集合。逐页读取完成后再提供全集，能让这些功能继续覆盖后面的题目。当读取失败或发现页面不一致时，页面给出错误和重试入口，不展示一个看似完整的截断结果。

方案收益代价与决定
严格领域模型 + 有界自由 JSON + ASGI receive复用成熟框架、单一输入边界、保留已有服务与指纹需要上限内缓冲及一次浅扫描；本次采用
各路由定制 Request/APIRoute 并引入流式 JSON 解析器可以边接收边解析并减少二次扫描增加依赖、错误映射和漏掉默认 body 读取的风险；本次小体积非流式 JSON 不采用
只检查 Content-Length 或解析后遍历代码少，容易接入无法覆盖缺失或虚假长度，解析前资源已经消耗；不满足本项验收
把每一个 dict 都改成固定白名单文档看起来整齐会误删合法事件属性、发布规则与评分扩展，背离真实领域；不采用

检验自己是否理解

为什么 props 不做固定字段白名单？

它本来承载事件特有自由JSON；正确约束是JSON类型和资源界限。固定白名单会把合法事件配置当成非法输入。

严格 int 为什么不能直接用于 edits 的 JSON 键？

JSON对象键天然是字符串。应只在明确边界把合法正整数文本解析为领域ID，再进行严格验证；值上的布尔和难度仍不能宽松强转。

客户端没传 ai_declared，为何不能总是补 false？

补字段会改变存储原始payload和请求摘要，旧请求重试可能409。模型内部默认值必须通过exclude_unset留在内部。

已有事件数50上限，为何还需要字节上限？

每个事件都能包含很大的嵌套内容；数量、结构和实际字节保护不同资源，三者不能互相替代。

为什么早期413也要经过E3？

它仍是一次请求，应保留相关性ID及受保护主体的限额。安全准入记账可以发生，题库、评分、学习等业务写入必须为零。

limit降到200后，只显示第一页为什么不算完成？

页面本地筛选与批量操作依赖全集。必须逐页取齐或明确报错，不能把部分库存伪装成完整结果。

测试95通过能证明生产并发内存和快照一致吗？

不能。它证明本次契约、ASGI和隔离库场景，未验证服务器单块分配、进程总内存、同总数并发替换和真实浏览器；这些边界必须分开陈述。
