# 意见反馈与 GitHub 贡献

工作台顶栏的 **提意见** 在电脑和手机上都可打开。用户填写文字后，服务端先检查明显的威胁表达，再由配置的审核服务判断内容。审核明确放行才会投递到运营方指定的邮箱。用户可以提出批评或报告自己遇到的问题。

**发起 PR** 用于已经把改动推到 GitHub 分支的贡献者。填写 GitHub 用户名和分支后，在 GitHub 的比较页核对改动，亲自创建目标为 `dev` 的 PR。还没有分支时可从弹窗打开 Fork 入口。比较链接只包含仓库、用户名和分支信息。[贡献流程](../CONTRIBUTING.md)

GitHub 会立即公开提交的 PR。来自外部 Fork 的 PR 在创建、重新打开或修改标题和说明后进入人工审核。工作流用 `content review: pending` 标记待审内容，遇到疑似直接人身威胁时改用 `content review: possible threat`，提醒维护者优先处理。维护者阅读上下文、检查代码并处理标签。自动标记覆盖标题和说明。

## 配置反馈邮箱

在运行 API 的主机上配置以下环境变量。个人版使用仓库根目录 Compose 的 `server` 服务；注册版使用公开部署的 `api` 服务。在 Windows 直接启动 API 时，使用启动进程的环境变量。审核凭据、邮箱授权码和收件地址只保存在服务端私有配置中。

| 环境变量 | 用途 |
| --- | --- |
| `FEEDBACK_TO` | 维护者指定的唯一收件邮箱 |
| `FEEDBACK_SMTP_HOST`、`FEEDBACK_SMTP_PORT` | 发件服务的主机和端口 |
| `FEEDBACK_SMTP_TLS` | `ssl` 使用隐式 TLS，默认端口 465；`starttls` 默认端口 587 |
| `FEEDBACK_SMTP_USERNAME`、`FEEDBACK_SMTP_PASSWORD` | 发件账号和邮件服务商签发的密码或授权码 |
| `FEEDBACK_SMTP_FROM` | 发件服务允许使用的单个发件地址 |
| `FEEDBACK_REVIEW_BASE_URL`、`FEEDBACK_REVIEW_MODEL`、`FEEDBACK_REVIEW_API_KEY` | 专用审核端点、模型和凭据，三项一起设置。模型需支持 HTTPS、OpenAI 兼容的 Chat Completions 和 JSON 对象输出 |

注册版需要配置专用审核服务。建议为审核单独签发有预算限制的密钥，学习助手的模型额度仍由原有账本管理。个人版如果将三项全部留空，可复用启动进程中配置的 `LLM_BASE_URL`、`LLM_MODEL`、`LLM_API_KEY`。审核会消耗所选服务的模型额度。服务端校验模型返回的判定，只有明确放行才发信。

例如用 QQ 邮箱发信，可在邮箱设置启用 SMTP，使用 `smtp.qq.com`、`ssl` 和端口 `465`，将授权码填入服务端密码项。收件方可以与发件方不同。更新配置后重新创建对应的 API 容器或重启 API 进程。

## 发送结果

审核服务只收到用户主动输入的反馈文字和审核指令。审核拒绝时用户可修改后再发。审核服务或发信服务暂不可用时，页面会保留输入并提示重试。通过审核后，反馈以纯文本邮件投递。页面报告成功表示 SMTP 服务器已接收邮件，实际进入收件箱的时间由邮件服务商决定。

每个工作空间每小时最多尝试 5 次，同一数据库所有工作空间合计最多 100 次。同一工作空间重试同一提交时复用提交编号。如果连接恰好在邮件服务器确认前断开，系统会保留「结果待确认」，防止重试造成重复投递。数据库保留提交编号、文本摘要和投递状态，邮件正文只在审核和发送时使用。
