# API 请求限流与日额度

部署方通过 `API_RATE_LIMITS` JSON 配置 `read`、`write`、`llm` 三类额度，示例见根目录 `.env.example`。每类有 `burst` 短时容量、`per_minute` 每分钟补充数、`daily` 每个 UTC+8 自然日的请求硬上限。只能填写范围内的正整数；未知字段、布尔值和浮点数会在加载配置时拒绝。工作空间使用者不能通过业务设置接口放宽这些额度。修改部署配置需要重启进程，所有共用同一数据库的进程应使用同一份策略。

一次 GET 消耗读取额度，其他业务写请求消耗写入额度。可能启动模型的路由还消耗 LLM 额度。`GET /learning/tasks/{id}/content` 可能首次生成教学内容，因此也受 LLM 限额。聊天 SSE 与注册版 coach events 只读取已有结果，不消耗 LLM 额度。缓存命中、模型未配置时的规则降级、重试和失败的业务请求仍按入口能力计数，避免请求体、缓存状态或降级条件变成绕过手段。暂停、取消分析只消耗写入额度，恢复分析另消耗 LLM 额度。开启项目自动分析的设置请求按可能启动生成计数。

中间件复用现有认证函数，并从数据库解析可信 workspace ID。同一 workspace 的 owner token、限定工作空间 token 和注册版多个有效 cookie 会话共享额度。注册版的 `X-Workspace` 不决定归属。工作空间无关的所有者设置和运维 API 使用服务器确定的 `local-owner` 主体，改变 token 表示方法、IP、工作空间头不会得到新的额度。匿名遥测、注册登录等保留各自现有防刷机制；本次不改凭据生命周期。

PostgreSQL 持久行保存每类余额、当天日期与已使用数。每次准入获取同主体事务锁，然后读取数据库时间，同时判断所有桶。任一桶不足会回滚整个准入事务。429 包含正整数秒的 `Retry-After`、安全错误码及与日志一致的服务器生成 `request_id`。日上限拒绝等待下次 UTC+8 零点；多个条件不足时取最长等待时间。日计数不会随时间连续补充，同日重启或修改上限也不会清零。

准入事务在业务开始前提交，不持有连接等待模型或流式响应。准入数据库故障返回安全的 503，不放行业务。准入后客户端断开、业务失败或其他 E1/E2 闸门拒绝，不退还请求计数。它们保护不同资源，E1 限制同时生成数，E2 限制金额，E3 限制请求进入速度和当天次数。

每次成功准入最多清理 100 条过期记录，使用过期索引与 `SKIP LOCKED`。记录过期时间至少覆盖当天结束及短桶完全补满时间。活跃主体最多三类记录，未认证输入不会创建记录。无流量时旧记录仍保留，下一次成功准入继续清理；没有另设后台清扫任务。

新增可付费业务路由时，更新 `server/app/api/rate_limits.py` 中的 `LLM_ROUTES` 并补实际 HTTP 测试。FastAPI 新版的 included-router effective contexts 与普通 APIRoute 都参与匹配。注册版 native gateway 在转发、数据同步与创建目标实例前先检查 cookie 主体。下游独立服务仍按自己的数据库执行准入，网关保留下游 429 的 `Retry-After`。不同数据库不共享计数；本机制不保证跨库全局限额。
