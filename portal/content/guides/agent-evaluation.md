## 一句话结论

Agent 评估 = **固定评测集 + 分层指标 + 稳定的裁判 + 每次改动必跑回归**；没有这套东西，改 prompt 全靠手感，系统永远在薛定谔的「还行」。

## 生活类比

像给运动员做体检：只看「今天赢没赢」（端到端结果）是犯规的——要拆开看体能、技术、心态（分层指标），用同一把尺子量（固定裁判），每次训练后都测（回归），才能知道是哪里进步了哪里受伤了。

## 具体例子

改了一版 prompt 后，100 题评测集跑分：任务完成率 78% → 80%（+2），但工具调用准确率 91% → 84%（-7），平均成本 +35%。结论：新 prompt「答得更全」但啰嗦且更容易调错工具——**不加分层指标，你只会看到 +2% 就合入了**。

## 原理与术语

- **评测集（Eval Set）**：固定的一组测试任务（输入 + 期望行为），从真实流量和失败 case 沉淀，覆盖正常/边界/对抗。
- **分层指标**：任务完成率（最终对不对）、过程指标（工具调用准确率、步数）、效率指标（延迟、成本）。只看一层必然被误导。
- **LLM-as-a-Judge**：用大模型按 rubric 打分。稳定的关键：明确锚点、few-shot 示例、结构化输出、同一模型同一温度。
- **回归测试（Regression）**：每次改 prompt/模型/工具，重跑全量评测集，对比基线，任何指标显著下降就回退。
- **通过率陷阱**：全用简单题 → 95% 通过率毫无信息量；评测集难度要贴近真实分布并保留失败案例。

## 常见误区

- **误区一：用「人工看几条」代替评测集。** 抽样看 5 条永远只看到好的。
- **误区二：只有端到端指标。** 完成率没变但成本翻倍，你看不见。
- **误区三：裁判 prompt 一句话。** 「打分 1-10」这种裁判自己都不可复现，打分方差比改动差异还大。
- **误区四：评测集从不更新。** 系统进化了，评测集还停在三个月前的简单题。
- **误区五：换了模型沿用旧基线。** 基线必须同环境同时刻可比。

## 实践步骤

1. 收集 50-100 条真实任务（含失败 case 与对抗样本），写清输入和期望行为。
2. 定义 rubric：每个任务列出「得分点 + 说清什么算命中」，让裁判有据可依。
3. 接入自动评测脚本：跑评测集 → 输出分层指标表（完成率 / 工具准确率 / 延迟 / 成本）。
4. 固化基线：当前版本全量跑一次，结果存档，作为一切后续改动的对照。
5. 挡板进 CI：prompt/模型/工具任何改动，先跑评测再合入；显著回归 → 自动拒绝。

```python
rubric = {
    "points": [
        {"title": "区分超时与失败", "keywords": ["超时", "失败分类"]},
        {"title": "给出幂等键方案", "keywords": ["幂等"]},
    ],
    "max_points": 5.0,
}
score = judge(question=task, answer=model_output, rubric=rubric)
```
