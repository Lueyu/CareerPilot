## 一句话结论

长对话的成本和延迟随轮次线性膨胀；解法是**结构化状态 + 滚动摘要 + 分层记忆**——重要的东西写字板，最近的东西留原文，其余的压缩成摘要。

## 生活类比

把 Agent 想成一个厨师：**对话上下文是厨房的白板**，写满了就得擦；**显式状态是随身笔记本**——菜做到第几步、盐放没放，都记在本子上，白板擦了也不怕；**长期记忆是菜谱柜**——这桌客人不吃辣，下次来还点单，直接翻柜子。

## 具体例子

一个客服 Agent 处理退货，对话进行到第 40 轮：

- 不压缩：每轮都带着前 39 轮原文 → token 从 2k 涨到 60k，成本和延迟翻 30 倍，且模型开始「忘记」第 3 轮的订单号。
- 压缩后：状态卡只存 `{订单号, 退货原因, 当前步骤, 已确认事项}` 200 token + 最近 5 轮原文 + 前 34 轮的 300 token 摘要 → 总量稳定在 3k 以内，订单号永远不丢。

## 原理与术语

- **工作记忆（Working Memory）**：当前上下文窗口里的内容——最贵、最短命。
- **滚动摘要（Rolling Summary）**：超过 N 轮后，把旧对话压缩成摘要并持续合并更新。
- **结构化状态（Scratchpad / State）**：用固定 schema 存关键变量，而不是指望模型从原文里「想起来」。
- **分层记忆**：工作记忆（本轮）→ 情景记忆（本次会话摘要）→ 语义记忆（跨会话的用户偏好、事实）。
- **记忆检索**：长期记忆按相关性取回（embedding 检索），不是每次全量塞进上下文。

## 常见误区

- **误区一：摘要一切。** 把当前任务的活跃状态也摘要掉，等于让厨师扔了正在用的笔记本。
- **误区二：只存摘要不存结构。** 自然语言摘要里捞「订单号是 A123」很脆；schema 字段才是稳定的。
- **误区三：把记忆当成 RAG 用。** 记忆是"关于用户/任务的事实"，知识库是"领域资料"，混在一起检索质量会互相污染。
- **误区四：压缩不评估。** 压缩后任务完成率降了 10% 你都不知道——压缩策略必须进回归测试。

## 实践步骤

1. 定义状态 schema：这个任务里哪些变量丢了就没法继续（订单号、步骤、已确认项）。
2. 每轮结束把状态显式写入（工具调用或结构化输出），不依赖对话原文。
3. 超过阈值（如 20 轮 / 8k token）触发滚动摘要：旧轮次 → 300 token 摘要，保留最近 5 轮原文 + 状态卡。
4. 跨会话事实写入长期记忆（带时间戳、来源、置信度），下次会话按需检索。
5. 加评测：用 30 轮长对话测试集对比压缩前后的任务完成率与关键信息保真度。
